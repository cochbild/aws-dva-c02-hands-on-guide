Study Sheets and Quizzes — Design

Date: 2026-10-18. Branch: feature/study-quizzes.

Text marked [Claude's call] is a decision that the designer made. The user did not choose it. The builder can change it if there is a good reason.

1. Intent

The user takes the AWS Certified Developer – Associate (DVA-C02) exam in about two weeks (around 2026-11-01). Time is short. The user wants to read first, then test with exam-style questions, then read again only where they are weak.

The user said: "cover everything possible on this exam" and "be thorough." Coverage of the exam is the main goal. The hands-on labs are not the goal of this work.

2. Goals

  1. A study sheet for each of modules 1 to 9. It is dense, exam-focused reading.
  2. Gap sets: a study sheet for each exam topic area that the modules do not teach (see section 6).
  3. A quiz for each study sheet, with AWS-style scenario questions.
  4. Feedback by topic after each quiz. Each question shows a written explanation for the correct answer and for each wrong option. Each weak topic links to its section on the study sheet.
  5. [Claude's call, shown to the user, not rejected] A home page that shows the latest score for each set and the weakest topics across all sets.
  6. [Claude's call, shown to the user, not rejected] A weak-topics quiz that draws questions only from topics where the user missed questions.
  7. [Claude's call, shown to the user, not rejected] A final practice exam: 65 questions with the official domain weighting.

3. Non-goals

  • No changes to the labs, templates, or module READMEs. The only exception is one link from the root README.md to study/index.html.
  • No server, no accounts, no sync between devices.
  • No spaced-repetition scheduler or flash cards.
  • The module 10 capstone gets no quiz.

4. Anti-goals (failure even if it works)

  • Wrong facts. An incorrect limit, default, or service behavior teaches the user a wrong answer before the exam. Accuracy is more important than volume.
  • Lab re-telling. A study sheet that repeats lab steps ("run this command") instead of exam knowledge wastes the user's reading time.
  • Trivia questions. Questions that test recall of one word, instead of scenario judgment, do not prepare the user for the real exam.
  • Copied exam content. All questions must be original. Do not copy from exam dumps or paid practice tests.
  • Late delivery. A full set that arrives in week two is worth less than a partial set the user can use on day one. See section 10.

5. Constraints

  • Static HTML only. The user's global rule: documentation is self-contained HTML. No build step, no frameworks, no package install. Inline or local CSS and JavaScript are allowed.
  • Opened from disk. The user opens the files with file://. Browsers block fetch() of local JSON from a file:// page. Thus question data must load through <script src="..."> tags, not through fetch().
  • No external network. No CDN scripts or web fonts. The pages must work offline.
  • Storage. Progress is kept in localStorage. Wrap each read and write in try/catch. The pages must work, without saved progress, when storage is not available.
  • Writing style. Study sheet prose follows the user's ASD-STE100 rule (short sentences, active voice, common words), by intent. Quiz stems follow the AWS exam style (a scenario, then "Which solution will meet these requirements?" and similar). Do not apply STE to AWS service names or quoted error text.
  • Current exam version. Content must match the current official DVA-C02 exam guide. The builder must read the official guide and use its domains, task statements, and in-scope services list.
  • Light and dark themes. Follow prefers-color-scheme. Readable on a laptop screen. [Claude's call] Phone layout is not required, but do not prevent it.
  • Git rules: work on feature/study-quizzes (or phase branches from it). Do not push to main. Do not push or open a pull request without the user's instruction.

6. Content scope

6.1 Module sets (decided)

One set for each of modules 1 to 9. Use the module README "theory primer" and "exam blueprint mapping" sections and the lab READMEs as a starting point. Add exam knowledge that the module does not include. The module READMEs are a source, not a limit.

6.2 Gap sets (decided: cover the gaps; the exact list is the builder's job)

The builder must compare the official exam guide (all task statements and the in-scope services list) against the nine modules. Make a gap set for each area with no adequate module coverage. Record the comparison as a coverage table in study/coverage.html: each task statement, the set or sets that cover it.

[Claude's call] Likely gap sets, to confirm or change:

  • IAM and STS: policy types, policy evaluation logic, explicit deny, resource-based policies, roles and trust policies, AssumeRole, cross-account access, the credential provider chain, instance profiles, least privilege.
  • Infrastructure as code: CloudFormation (intrinsic functions, parameters, outputs and exports, change sets, stack sets, nested stacks, DeletionPolicy, helper scripts), SAM depth (transform, policy templates, sam local, sam sync), CDK concepts beyond lab 8.7.
  • SDK and application development practices: retries with exponential backoff and jitter, pagination, idempotency, error codes (throttling, 4xx vs 5xx), EC2 instance metadata (IMDSv2), environment configuration, unit testing and mocking, Amazon Q Developer.
  • Architecture patterns: event-driven design, loose coupling, fan-out, choreography vs orchestration, stateless design, caching strategies (lazy loading, write-through, TTL), synchronous vs asynchronous patterns.
  • Containers and compute extras, if lab 8.5, 8.8, and 8.9 do not cover them: ECR, ECS task roles vs execution roles, Elastic Beanstalk deployment policies and .ebextensions, EC2 user data.

6.3 Topics

Each set is divided into topics. A topic is one exam-relevant concept, for example "Lambda reserved vs provisioned concurrency." [Claude's call] Use 6 to 15 topics for each set. Each topic has a stable ID (for example lambda-concurrency). The topic ID is the anchor of its section on the study sheet and the tag on each question.

7. Study sheets

  • One section for each topic, with the topic ID as the section id.
  • Content for each topic: the key facts, numbers to memorize (limits, defaults, timeouts, sizes), "when to use X vs Y" comparisons, and the traps that exam distractors use. Use tables for comparisons.
  • Each topic ends with a short "Exam signals" list: words in a question stem that point to this answer (for example "near real-time to S3 with no code" → Kinesis Data Firehose).
  • Link to the related lab README where one exists, for hands-on review.
  • Cite the AWS documentation page for each number that is easy to get wrong.
  • [Claude's call] A table of contents at the top. A link to the quiz at the top and at the bottom.

8. Quizzes

8.1 Question bank

  • [Claude's call] 30 to 40 questions for each set. Every topic has at least 2 questions. Heavy-weight topics have more.
  • Question types: multiple choice (one correct of four) and multiple response (two or three correct of five or six, stem says "Choose two"). [Claude's call] About 20 to 25 percent multiple response, which matches the real exam.
  • Each question has: ID, set ID, topic ID, exam domain (1 to 4), stem, options, the correct option or options, a "why" text for every option, and a short summary explanation.
  • Distractors must be plausible. Each distractor uses a real AWS feature that does not meet one requirement in the stem. The "why" text names that requirement.

8.2 Quiz behavior

  • [Claude's call] Each attempt shows 15 questions picked at random from the bank, with balanced topic coverage. Option order is random. A "full bank" option shows all questions.
  • The user answers all questions, then submits. There is no feedback during the attempt (this matches the exam).
  • The results page shows: total score, a score for each topic, weak topics first, with a link to each topic section on the study sheet, then every question with the user's answer, the correct answer, and all "why" texts.
  • A multiple-response question is correct only when the selection is exactly correct (this matches the exam).

8.3 Progress and weak topics

  • Save each answer result in localStorage: question ID, topic ID, correct or not, timestamp.
  • [Claude's call] Topic accuracy uses the most recent 5 answers for that topic. A topic is weak when its accuracy is below 80 percent. A topic with no answers is not tested.
  • The home page lists each set with its latest score and a link to its study sheet and quiz. It lists the weak topics across all sets, worst first, each with a link to its study sheet section.
  • The weak-topics quiz draws up to 15 questions from weak topics only, across all sets. It prefers questions the user has missed or not seen.
  • A "reset progress" button on the home page. It asks for confirmation on the page (not with a browser confirm() dialog).

8.4 Final practice exam

  • 65 questions drawn from all banks, weighted by the official domain percentages (at the time of writing: Domain 1 Development 32 percent, Domain 2 Security 26 percent, Domain 3 Deployment 24 percent, Domain 4 Troubleshooting and Optimization 18 percent; confirm against the guide).
  • A visible 130-minute timer. When time ends, the exam submits.
  • A "flag for review" control on each question and a review list before submit, like the real exam.
  • Results page as in 8.2, plus a score for each domain. Results also update topic progress.
  • Total bank size must be large enough to fill 65 questions with the domain weighting. Tag domains on every question with this in mind.

9. File layout

[Claude's call] The builder can change names but must keep one shared quiz engine and data in script files.

study/
  index.html                 home: sets, scores, weak topics, links
  coverage.html              exam guide task statements → sets
  final-exam.html
  weak-topics.html
  assets/
    study.css                shared styles, light and dark
    quiz.js                  shared engine: pick, render, score, store
  sets/
    m01-lambda/
      sheet.html
      quiz.html
      questions.js           window.QUESTION_BANKS.push({ ... })
    m02-databases/ ... m09-observability/
    g-iam-sts/ ...           gap sets
  registry.js                list of sets: id, title, paths, topic list
tools/
  validate-study.*           data checker (see section 11)

Pages that need every bank (home, weak topics, final exam) load registry.js and each questions.js with script tags.

10. Delivery order

The user needs to start studying now. Deliver in phases. The user can use each phase when it is done.

  1. Engine, styles, home page, and module 1 (sheet and quiz) end to end. Then stop for the user to try it and give feedback on format before more content is made.
  2. Modules 2 to 5.
  3. Modules 6 to 9.
  4. Coverage table and gap sets.
  5. Weak-topics quiz and final practice exam.

[Claude's call] The weak-topics quiz can move earlier, into phase 2, because it is small and the user benefits from it at once.

11. Verification

  • Data checker with no dependencies (Node or Python standard library; use a venv for Python). It loads every questions.js and checks: unique question IDs; each topic ID exists in the registry and as an id anchor in the set's sheet.html; the correct-answer count matches the question type; every option has a "why" text; domain is 1 to 4; every topic has at least 2 questions.
  • Fact review. A separate reviewer checks each study sheet and question bank for wrong facts against AWS documentation before the phase is done. Fix or remove any fact the reviewer cannot confirm.
  • Browser check. Open each page from file:// in a browser. Take a quiz, submit, and confirm the results, the links to topic sections, and the saved progress on the home page.
