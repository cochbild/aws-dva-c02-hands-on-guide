Source

  • Guide: AWS Certified Developer - Associate (DVA-C02) exam guide, version 2.1, published December 12, 2024. Location: docs.aws.amazon.com/aws-certification/latest/developer-associate-02. Checked on 2026-10-18.
  • The PDF guide (AWS-Certified-Developer-Associate_Exam-Guide_C02.pdf) has the footer "Version 1.0" and separate knowledge and skills lists. The revisions page compares 2.1 with a 2.0 that has this layout. Version 2.1 replaces it. This page uses version 2.1.
  • Exam change: the AWS certification page says DVA-C03 registration opens October 27, 2026. DVA-C02 is available until November 30, 2026. An exam on or near 2026-11-01 is DVA-C02, so this page uses the DVA-C02 guide.
  • Domain weights (scored content): Domain 1 Development with AWS Services 32%, Domain 2 Security 26%, Domain 3 Deployment 24%, Domain 4 Troubleshooting and Optimization 18%. These weights match assets/quiz.js.
  • Version 2.1 has one list of skills for each task. It has 101 skills in total. The table below has one row for each skill.
  • Emerging topics: the guide lists AI-assisted development skills as unscored pretest items. This page does not make topics for them. The scored skills 1.1.11 and 3.3.6 (Amazon Q Developer) are in the gap set g-dev-practices.

How to read the tables

  • Sets: the planned set IDs that must teach the skill. Module sets: m01-lambda, m02-databases, m03-s3, m04-api-cognito, m05-messaging, m06-step-functions, m07-secrets-kms, m08-cicd, m09-observability. Gap sets start with g-.
  • Status: Covered = the module README teaches the skill. Partial = the module README teaches part of the skill. The set author must add the rest (see Must also cover), or a gap set adds it. Gap = a gap set is the main owner of the skill. A module can touch the skill, but the module README does not teach it enough for the exam.
  • Topics: empty for now. Fill this column with topic IDs after the set content exists.

Must also cover (module sets)

Each module set author must add these items. The module README does not teach them, or teaches them only in part. The numbers are guide skills. Items under "Check" are statements in the module README that can be out of date or wrong. Check each one against the AWS documentation before you use it.

m01-lambda

  • 1.2.7: near-real-time transforms. Lambda with Kinesis and DynamoDB Streams, and the Amazon Data Firehose transformation Lambda.
  • 1.2.4, 3.2.1, 3.3.1: test code. Console test events (private and shareable), sam local invoke with an event file, sam remote invoke.
  • 2.3.2: encrypt environment variables. The default AWS managed key, a customer managed key, and encryption helpers for encryption in transit.
  • 1.2.1: Lambda in a VPC needs a NAT gateway for internet access, or VPC endpoints for AWS services. RDS Proxy for database connection pooling.
  • Storage: /tmp (ephemeral) compared with an Amazon EFS mount (shared, persistent).
  • Function URLs (auth type AWS_IAM or NONE) and response streaming.
  • 4.3.2, 4.3.3, 4.3.7: AWS Lambda Power Tuning and AWS Compute Optimizer for memory choice. Read the REPORT log line (Duration, Max Memory Used, Init Duration).
  • 3.3.3, 3.4.9: an alias as the "approved version" for an environment.

m02-databases

  • 1.3.5: serialization. DynamoDB attribute-value JSON ({"S": "..."}) compared with the document client or marshalling helpers. Binary attributes and base64.
  • DAX: item cache and query cache, write-through, microsecond reads, no strongly consistent reads through the cache.
  • Errors: ProvisionedThroughputExceededException and SDK backoff. BatchWriteItem and BatchGetItem limits and UnprocessedItems / UnprocessedKeys.
  • Projection expressions. Filter expressions apply after the read, so they do not reduce consumed RCUs.
  • DynamoDB Streams view types. Global tables. PartiQL (recognition only).
  • RDS Proxy. IAM database authentication. ElastiCache for Redis (Valkey) compared with Memcached.
  • Check: the README rule "switch billing mode only once every 24 hours". AWS changed this limit. Use the current value from the DynamoDB documentation.

m03-s3

  • CORS configuration for browser uploads and downloads.
  • Access control: bucket policy compared with IAM policy and ACLs. Object Ownership (ACLs disabled by default for new buckets). Block Public Access.
  • S3 Transfer Acceleration. Byte-range GET requests. Presigned POST for browser form uploads.
  • CloudFront with origin access control (OAC) for private content. CloudFront signed URLs compared with S3 presigned URLs.
  • SSE-KMS and KMS request quotas (throttling). S3 Bucket Keys as the fix.
  • 2.2.6: cross-account access to SSE-KMS objects needs the key policy and the bucket policy.
  • Check: S3 Select availability for new customers. Do not teach it as a first choice if AWS no longer offers it to new accounts.

m04-api-cognito

  • 3.4.2: custom domains. Edge-optimized endpoints need the ACM certificate in us-east-1. Regional endpoints need it in the API Region. Base path mappings.
  • 3.2.2: mock integrations for tests. Canary release settings on a stage.
  • Error codes: 400, 403, 429, 502 (bad Lambda proxy response format), 504 (integration timeout). Gateway responses to change status codes and add CORS headers to errors.
  • CORS on REST and HTTP APIs.
  • API caching: default TTL 300 seconds, maximum 3600 seconds. A client sends Cache-Control: max-age=0 to skip the cache. The client needs execute-api:InvalidateCache permission if the stage requires it.
  • Account throttling defaults (10,000 requests per second, 5,000 burst) and the throttle order, from most specific to least specific (usage plan per client and method, usage plan per client, stage and method, account Region limit). Check the order against the API Gateway throttling documentation.
  • Cognito: Lambda triggers (for example pre sign-up, pre token generation). Token lifetimes and refresh. OAuth flows (authorization code with PKCE, client credentials). Groups mapped to IAM roles.
  • WebSocket APIs: $connect, $disconnect, $default, the @connections API.
  • CloudFront: signed URLs compared with signed cookies. Lambda@Edge compared with CloudFront Functions.
  • Check: the README puts the Cache-Control: max-age=0 rule under CloudFront. That rule is API Gateway cache behavior. Check the API Gateway integration timeout value against current documentation.

m05-messaging

  • 3.2.5: test event-driven applications. EventBridge archive and replay, TestEventPattern, and a test listener on the bus.
  • Lambda with SQS: partial batch response (ReportBatchItemFailures). Event source mapping filters. Batching window.
  • SNS: payload-based filter policies (FilterPolicyScope: MessageBody). Raw message delivery.
  • Kinesis: partition keys and hot shards, resharding (split, merge), the KCL and its DynamoDB lease table, ProvisionedThroughputExceededException, the IteratorAge metric.
  • 1.2.7: Firehose transformation Lambda.
  • EventBridge API destinations.
  • Check: SQS maximum message size (AWS raised the limit above 256 KB in 2025). Check: the README says FIFO throughput is "per MessageGroupId". The quota applies per queue, and high throughput mode raises it. Use the current SQS quota page.

m06-step-functions

  • Retry fields: IntervalSeconds, MaxAttempts, BackoffRate, MaxDelaySeconds, JitterStrategy.
  • JSONata query language and workflow variables (new in late 2024). Know that both JSONPath and JSONata exist.
  • Express: synchronous (StartSyncExecution) compared with asynchronous. Use with API Gateway.
  • Redrive of failed Standard executions. The saga (compensation) pattern with Catch.
  • 3.2.2, 3.2.5: the TestState API for one state.
  • The payload size quota for state input and output.
  • Check: the README says Standard is "at-most-once". AWS documentation says Standard is exactly-once. Express is at-least-once (asynchronous) or at-most-once (synchronous).

m07-secrets-kms

  • 2.3.2: Lambda environment variable encryption (shared with m01; m07 covers the KMS side).
  • KMS request quotas and ThrottlingException. Data key caching with the AWS Encryption SDK.
  • Encryption context and the kms:EncryptionContext condition key. Multi-Region keys.
  • Secrets retrieval with caching: client-side caching libraries and the Parameters and Secrets Lambda Extension.
  • Parameter Store: parameter policies (Advanced tier), GetParametersByPath, WithDecryption.
  • Secrets Manager resource policies for cross-account access.
  • AppConfig validators (JSON schema, Lambda) and the AppConfig Agent Lambda extension.
  • ACM: certificates for CloudFront must be in us-east-1. DNS validation compared with email validation. Automatic renewal.
  • Check: the README says customer managed key rotation is "annual". KMS now lets you set a rotation period and rotate on demand. Use the current KMS documentation.

m08-cicd

  • CodeArtifact: domains, repositories, upstream repositories, external connections (npm, PyPI, Maven), get-authorization-token.
  • 3.3.3: Amplify Hosting branch deployments and pull request previews. Container image tags as approved versions. Copilot environments (one line).
  • 3.4.9: CodePipeline triggers on branches and Git tags. Manual approval action with SNS notification.
  • CodeBuild: env section with parameter-store and secrets-manager, cache, reports, local builds.
  • 3.4.8: CodeDeploy automatic rollback on failure or CloudWatch alarm. Rollback deploys the last good revision as a new deployment.
  • AppSpec hook order for EC2/On-Premises, Lambda (BeforeAllowTraffic, AfterAllowTraffic), and ECS.
  • Deployment configuration names, for example CodeDeployDefault.LambdaCanary10Percent5Minutes.
  • 4.1.6: where deployment logs are. CodeDeploy agent logs on the instance, CodeBuild logs in CloudWatch Logs, CloudFormation stack events.
  • ECS rolling update settings (minimum and maximum healthy percent) and the deployment circuit breaker.
  • Elastic Beanstalk: .platform hooks, application version lifecycle policy.
  • Check: the README lists five Beanstalk deployment policies. The current list also has traffic splitting. Check: the README says ECS deployments are blue/green only through CodeDeploy. Check the current ECS deployment options. Check: the current status of CodeCommit for new customers.
  • Fix: lab 8.9 README line 169 says 02-fixthing.config runs before 01-config.config. Alphabetical order runs 01 first. Do not repeat this error in the sheet.

m09-observability

  • 4.1.5: CloudWatch dashboards (automatic and custom, cross-account). CloudWatch Application Signals and ServiceLens. Lambda Insights, Container Insights, Contributor Insights. CloudWatch Synthetics canaries.
  • 4.2.7: structured logging. JSON logs, Lambda advanced logging controls (JSON log format, log level), correlation IDs, Powertools for AWS Lambda Logger.
  • 4.2.6: X-Ray instrumentation in code. Patch SDK clients, add subsegments, the X-Ray daemon on EC2 and ECS (UDP port 2000), AWS Distro for OpenTelemetry. Sampling rules. Groups and filter expressions.
  • 4.2.5: notifications. EventBridge rules on CodeDeploy and CodePipeline state changes to SNS. Developer Tools notification rules. Service Quotas usage metrics with CloudWatch alarms for quota limits.
  • 2.3.5: CloudWatch Logs data protection policies (mask sensitive data, logs:Unmask). Link to appsec-sanitize-mask.
  • 4.3.8, 4.3.9: find bottlenecks. X-Ray service map and latency histograms. Logs Insights stats on @duration and @maxMemoryUsed. Init Duration from the REPORT line.
  • Alarm actions (SNS, Auto Scaling, EC2), metric math, anomaly detection.

Gap sets

Six gap sets cover the gap rows. Topic ID rule: each gap set uses its own prefix (iam-, appsec-, iac-, dev-, arch-, compute-). Module set authors must not use these prefixes. Gap set authors must not use module prefixes such as lambda-, ddb-, s3-, api-, sqs-, kms-, cw-, xray-, code-, or ecs-. Each topic lists the exam knowledge it must contain. The set author can add more.

Candidates from the design spec, section 6.2: "IAM and STS" became g-iam-sts and g-app-security (too many topics for one set). "Infrastructure as code" became g-iac. "SDK and development practices" became g-dev-practices. "Architecture patterns" became g-architecture, with data store choice and storage options added. "Containers and compute extras": module 8 labs 8.5, 8.8, and 8.9 teach ECS roles, ECR, and Beanstalk policies. The remaining gaps (EC2, load balancing, health checks, EKS) became g-compute.

g-iam-sts: IAM and STS for developers

Skills: 2.1.1 (IAM federation), 2.1.3, 2.1.4, 2.1.5, 2.1.6, 2.2.6 (cross-account side). Services: IAM, STS. Domain: mostly 2.

iam-policy-types: Policy types
  • Identity-based policies: AWS managed, customer managed, and inline. When to use each one.
  • Resource-based policies (S3, SQS, SNS, KMS, Lambda, Secrets Manager). They have a Principal element.
  • Permissions boundaries, service control policies, and session policies limit permissions. They never grant permissions.
iam-policy-evaluation: Policy evaluation logic
  • An explicit deny overrides any allow. With no allow, the result is an implicit deny.
  • In one account, an allow in the identity policy or the resource policy is enough.
  • Across accounts, both the identity policy and the resource policy must allow the action.
  • Boundaries and SCPs intersect with identity policies.
iam-policy-elements: Policy elements and conditions
  • Effect, Action, Resource, Condition, Principal, NotAction. ARN formats and wildcards.
  • Common condition keys: aws:SourceIp, aws:SecureTransport, aws:MultiFactorAuthPresent, aws:PrincipalTag, aws:SourceArn.
  • Policy variables, for example ${aws:username}.
iam-roles-trust: Roles and trust policies
  • A role has a trust policy (who can assume it) and permissions policies (what it can do).
  • Service roles and service-linked roles.
  • iam:PassRole: a user needs it to give a role to a service (Lambda, ECS, EC2).
iam-sts-assume-role: STS operations
  • AssumeRole, AssumeRoleWithWebIdentity, AssumeRoleWithSAML, GetSessionToken (MFA), GetCallerIdentity.
  • Temporary credentials: access key ID, secret access key, session token.
  • Session duration: 15 minutes up to the role maximum (1 to 12 hours). Role chaining limits the session to 1 hour.
  • ExternalId for third-party access.
iam-cross-account: Cross-account access
  • Two methods: assume a role in the other account, or use a resource-based policy that names the other account.
  • With a resource-based policy, the caller keeps its own permissions. With a role, the caller gives them up.
  • Confused deputy protection: aws:SourceArn and aws:SourceAccount in resource policies.
iam-credential-chain: Programmatic access and the credential provider chain
  • The SDK default chain: environment variables, shared config and credentials files (profiles), web identity, container credentials, instance profile. The exact order differs a little by SDK.
  • Never put access keys in code. Use roles on AWS compute. Use aws sso login or temporary credentials on a developer machine.
  • Signature Version 4 signs each request. The SDK and CLI do this for you.
iam-compute-roles: Roles for compute
  • EC2 instance profile. Credentials come from the instance metadata service.
  • Lambda execution role (what the function can call) compared with the function resource-based policy (who can invoke the function).
  • ECS task role compared with task execution role (link to m08). EKS Pod Identity and IAM roles for service accounts.
iam-federation: Federation
  • SAML 2.0 compared with OpenID Connect.
  • Web identity federation: AWS recommends Cognito identity pools for mobile and web apps.
  • IAM Identity Center for workforce users and CLI access.
iam-least-privilege: Least privilege and access control models
  • Start from AWS managed policies, then narrow with customer managed policies.
  • IAM Access Analyzer: policy validation and policy generation from CloudTrail activity. Last accessed information.
  • RBAC (roles per job) compared with ABAC (tags on principals and resources).
iam-troubleshooting: Troubleshooting access denied
  • AccessDenied and UnauthorizedOperation errors. Read which policy type denied the call.
  • aws sts decode-authorization-message for encoded failure messages.
  • IAM policy simulator. CloudTrail records denied API calls.

g-app-security: Application security and sensitive data

Skills: 2.1.2, 2.1.7, 2.1.8, 2.2.1, 2.2.5, 2.3.1, 2.3.4, 2.3.5, 2.3.6. Services: Cognito, API Gateway, IAM, CloudWatch Logs, ACM, EC2 key pairs. Domain: 2.

appsec-data-classification: Data classification
  • PII, PHI, and payment data. Classification controls encryption, logging, retention, and access.
  • Know what counts as PII and PHI in an exam scenario.
  • Collect and keep only the data that the application needs.
appsec-sanitize-mask: Sanitizing and masking data
  • Validate input and encode output. Remove or mask sensitive fields before you write logs.
  • CloudWatch Logs data protection policies mask sensitive data. Only principals with logs:Unmask see the original values.
  • S3 Object Lambda to redact data on read (link to m03).
  • Masking (partial display) compared with tokenization and encryption.
appsec-jwt-validation: Bearer tokens and JWT validation
  • JWT parts: header, payload, signature. Validate the signature with the issuer JSON Web Key Set (JWKS).
  • Check iss, aud or client_id, exp, and token_use.
  • ID token compared with access token. Send bearer tokens only over HTTPS.
appsec-fine-grained-authz: Application-level authorization
  • OAuth scopes in access tokens. Method authorization scopes in API Gateway.
  • Cognito groups for roles. A Lambda authorizer returns a policy and context values.
  • ACL-based authorization compared with role-based and attribute-based authorization.
appsec-service-to-service: Cross-service authentication
  • OAuth 2.0 client credentials grant with a Cognito resource server and custom scopes (machine-to-machine).
  • IAM authorization with SigV4 between services (API Gateway AWS_IAM, Lambda function URL AWS_IAM).
  • Mutual TLS on API Gateway custom domains. Private APIs with VPC endpoints.
appsec-multi-tenant: Multi-tenant data access
  • Silo (resource per tenant) compared with pool (shared resource with tenant key) isolation.
  • DynamoDB fine-grained access: the dynamodb:LeadingKeys condition with an identity variable such as ${cognito-identity.amazonaws.com:sub}.
  • S3 prefix per tenant with policy variables. Take the tenant ID from the verified token, not from the request body.
appsec-encryption-in-transit: Encryption in transit
  • TLS for every connection. Deny HTTP with aws:SecureTransport.
  • ACM certificates on ALB, CloudFront, and API Gateway. CloudFront viewer protocol policy (redirect to HTTPS).
  • At rest compared with in transit. Which services encrypt at rest by default.
appsec-dev-certs-keys: Certificates and SSH keys for development
  • EC2 key pairs: create in AWS or import a public key from ssh-keygen. AWS does not keep the private key.
  • Self-signed certificates (for example with OpenSSL) for local development only.
  • AWS Private CA for internal certificates. ACM public certificates for public endpoints.

g-dev-practices: SDK, CLI, testing, and Amazon Q Developer

Skills: 1.1.5, 1.1.7, 1.1.9, 1.1.11, 1.1.13, 1.2.4, 2.1.3 (CLI side), 3.2.1, 3.2.2, 3.2.5, 3.3.1, 3.3.6, 4.1.1, 4.1.7. Services: AWS SDKs, AWS CLI, CloudShell, Amazon Q Developer. Domains: 1, 3, 4.

dev-sdk-retries: SDK retries and backoff
  • SDKs retry throttling errors, 5xx errors, and timeouts. They do not retry most 4xx errors.
  • Exponential backoff with jitter. Why jitter spreads retries from many clients.
  • Retry modes: legacy, standard, adaptive (client-side rate limiting). Set the maximum attempts.
dev-sdk-errors: HTTP status codes and SDK exceptions
  • 400 (validation), 403 (access denied), 404 (not found), 429 (throttling), 500, 502, 503, 504. Which ones to retry.
  • Common exceptions: ThrottlingException, ProvisionedThroughputExceededException, ConditionalCheckFailedException, AccessDeniedException, Lambda TooManyRequestsException.
dev-sdk-pagination: Pagination and batch calls
  • Tokens: NextToken, LastEvaluatedKey, ContinuationToken. SDK paginators.
  • CLI: --page-size, --max-items, --starting-token, --no-paginate.
  • Batch calls can partly fail. Retry unprocessed items with backoff.
dev-idempotency: Idempotency
  • At-least-once delivery (SQS standard, async Lambda, EventBridge) means a handler can run twice.
  • Idempotency keys and client tokens. Conditional writes record "already done".
  • Powertools for AWS Lambda idempotency utility with a DynamoDB table.
dev-resilience: Resilient calls to other services
  • Timeouts on every call. Retries with a limit. Circuit breaker states (closed, open, half-open).
  • Fallback responses and graceful degradation. Dead-letter queues for work that fails many times.
  • Choose Step Functions retries for orchestrated steps and code retries for single calls.
dev-cli-cloudshell: AWS CLI and CloudShell
  • Named profiles, --profile, --region, --output.
  • --query (JMESPath, client side) compared with server-side --filter options. --dry-run for EC2 permission checks. --cli-input-json.
  • CloudShell: browser shell with the console user's credentials, 1 GB persistent home directory in each Region.
dev-unit-testing: Unit tests and mocks
  • Keep business logic out of the handler. Inject SDK clients so tests can replace them.
  • Mock AWS calls with stub libraries (for example moto, botocore Stubber, aws-sdk-client-mock).
  • Test events: JSON payloads for Lambda, API Gateway, and SQS. sam local generate-event makes them.
dev-integration-testing: Integration tests and event-driven tests
  • Test deployed code in a test stack: sam remote invoke, API Gateway test invoke, Lambda console tests.
  • API Gateway mock integrations stand in for a backend that is not ready.
  • Event-driven tests: send an event, then poll the result store with a timeout. EventBridge archive and replay. Step Functions TestState.
dev-debugging: Debugging defects and integration problems
  • Read stack traces in CloudWatch Logs. Reproduce with the same event locally.
  • Integration problems: missing IAM permission, wrong Region or ARN, timeout too short, wrong payload format between services (for example a Lambda proxy response without statusCode gives API Gateway 502).
  • Use X-Ray to find which downstream call fails.
dev-amazon-q: Amazon Q Developer
  • In the IDE: inline code suggestions, chat, code explanation, and agent tasks.
  • 3.3.6: generate unit tests. Code reviews and security scans. Code transformation (for example language version upgrades).
  • Reference tracking shows license information for code similar to open-source code.
  • In the console: help to diagnose errors. Pro tier admin controls. Check current feature names in the Amazon Q Developer documentation.

g-architecture: Architecture patterns and data store choice

Skills: 1.1.1, 1.1.2, 1.1.3, 1.1.4, 1.1.12 (pattern side), 1.3.6, 1.3.9, 4.3.6. Services: OpenSearch Service, Athena, EBS, EFS, with SNS, SQS, EventBridge, Step Functions as examples. Domains: 1, 4.

arch-event-driven: Event-driven architecture and fanout
  • Events (something happened) compared with commands (do this). Producers do not know consumers.
  • Fanout: SNS to many SQS queues, or one EventBridge rule with many targets.
  • When to choose SNS, EventBridge, or SQS (link to m05).
arch-microservices: Monolithic compared with microservices
  • A monolith deploys as one unit. Microservices deploy and scale on their own.
  • Each microservice owns its data and exposes an API or events.
  • Trade-offs: network calls, distributed tracing, and partial failure.
arch-orchestration: Orchestration compared with choreography
  • Orchestration: one controller (Step Functions) runs the steps. Choreography: services react to events.
  • Saga pattern: compensating actions undo earlier steps after a failure.
  • Exam signals: "central visibility" and "approval step" point to orchestration. "Add consumers without changing the producer" points to choreography.
arch-coupling-sync: Coupling and synchronous compared with asynchronous
  • Tight coupling: the caller waits and fails when the callee fails. Loose coupling: a queue or bus sits between them.
  • Synchronous: API Gateway to Lambda, RequestResponse invoke. Asynchronous: Event invoke, SQS, SNS, EventBridge.
  • Queues for load leveling: SQS absorbs spikes and protects a slow backend.
arch-stateless: Stateful compared with stateless
  • Stateless compute keeps no session data between requests, so any instance can serve any request.
  • Store session state outside the compute (DynamoDB, ElastiCache).
  • Sticky sessions keep state on one instance and reduce scaling. Lambda environment reuse is not durable state.
arch-caching-layers: Application-level caching
  • Cache layers: CloudFront, API Gateway cache, ElastiCache, DAX, and in-memory cache in the Lambda execution environment.
  • Choose the layer by what changes and who reads it. Set TTLs to limit stale data.
  • Strategy definitions (lazy loading, write-through) are in m02. This topic covers where to cache.
arch-storage-options: Storage options: block, file, object, ephemeral
  • EBS: block storage in one Availability Zone, usually attached to one instance.
  • EFS: shared NFS file system across Availability Zones. EC2, ECS, and Lambda can mount it.
  • S3: object storage. Instance store and Lambda /tmp: ephemeral, data is lost.
arch-purpose-built-data: Purpose-built data stores
  • Choose by access pattern: DynamoDB (key-value), RDS and Aurora (relational, joins), ElastiCache (in-memory).
  • OpenSearch Service: full-text search and log analytics. DynamoDB data can flow to OpenSearch (streams or zero-ETL integration).
  • Athena: serverless SQL on data in S3. You pay for data scanned. Partitions and columnar formats (Parquet) reduce cost.
