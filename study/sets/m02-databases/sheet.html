DynamoDB keys, partitions, and data serialization

Remember

  • A DynamoDB primary key is a partition key only, or a partition key plus a sort key (composite key).
  • DynamoDB stores each item on one partition. The partition key value selects the partition.
  • Items with the same partition key value are stored together on one partition, in sort key order.
  • Items with the same partition key value form an item collection. One Query can return the whole collection.
  • One partition accepts at most 3,000 reads and 1,000 writes per second.
  • A good partition key has many different values. Examples: userId, orderId, deviceId.
  • A bad partition key has few values. Examples: status, date, countryCode.
  • A bad key sends most requests to one partition. That partition is a hot partition.
  • A hot partition throttles even when the table has unused capacity.
  • On a provisioned table, a hot partition throttles with ProvisionedThroughputExceededException.
  • Adaptive capacity helps a hot partition, but adaptive capacity cannot raise one partition above its limit.
  • Write sharding adds a suffix to a busy key value, for example 2026-10-18#1 to 2026-10-18#10.
  • To read all items of a sharded key value, the application must query each suffix and merge the results.
  • A random suffix spreads writes best, but you must query all suffixes to find one item.
  • A calculated suffix (for example, a hash of the order ID) lets you compute the full key and use GetItem.
  • GetItem, PutItem, UpdateItem, and DeleteItem need the full primary key.
  • PutItem replaces an existing item with the same key. Attributes that you did not send are lost.
  • UpdateItem changes only the attributes that you name, and creates the item if it does not exist (upsert).
  • Use single-table design when the application reads related entities together. Example keys: pk = USER#123, sk = ORDER#456.
  • The maximum DynamoDB item size is 400 KB. Attribute names count toward the size.
  • A partition key value is 1 to 2,048 bytes. A sort key value is 1 to 1,024 bytes.
  • A DynamoDB table has no practical size limit.
  • The low-level API sends each attribute with a data type descriptor, for example {"S": "Fido"} or {"N": "8"}.
  • The data type descriptors are S, N, B, BOOL, NULL, M, L, SS, NS, BS.
  • The low-level API sends numbers as strings to keep precision, and binary values as base64-encoded strings.
  • DynamoDB uses the typed JSON format only for transfer. DynamoDB does not store items as JSON.
  • Marshalling converts native objects to the typed format. Unmarshalling converts the typed format back.
  • In JavaScript v3, use DynamoDBDocumentClient, or marshall and unmarshall, to convert items.
  • In Python, use the boto3 Table resource, or TypeSerializer and TypeDeserializer, to convert items.
  • The boto3 Table resource returns numbers as decimal.Decimal.
  • In Java, the DynamoDB Enhanced Client maps items to classes.
  • DynamoDB Streams records contain Keys, NewImage, and OldImage in the typed format. Unmarshall them in the function code.

Exam signals

  • "Lambda stream handler gets values like {"S": "abc"} instead of plain strings" → unmarshall the image (for example, unmarshall or TypeDeserializer).
  • "Write native JavaScript objects without type descriptors" → DynamoDBDocumentClient, because it adds and removes the type descriptors for you.
  • "Throttling occurs, but the table uses little of its capacity" → hot partition. Use a key with more values, or add a suffix to the key (write sharding).
  • "Store a 2 MB document with its metadata" → put the object in Amazon S3, because the maximum item size is 400 KB. Store the S3 key and the metadata in DynamoDB.
  • "Get a customer and all the customer's orders in one request" → same partition key, different sort keys, and one Query. The items then form one item collection, and one Query returns it.

Explanation

Key facts

  • Each table has a primary key. It is a partition key only, or a partition key plus a sort key (composite key).
  • A partition is a unit of storage and throughput that DynamoDB manages for you. Items with the same partition key value are stored together on one partition, in sort key order.
  • Items with the same partition key value form an item collection. One Query can return the whole collection.
  • DynamoDB hashes the partition key value to choose the partition that stores an item.
  • All requests for one key value go to that one partition, and each partition has a throughput limit (3,000 reads and 1,000 writes per second).
  • Choose a partition key with high cardinality — many different values, such as a user ID or an order ID — so that requests spread across many partitions.
  • A key with few values (for example status = NEW, PAID, SHIPPED) sends most traffic to one or two partitions. Those requests throttle with ProvisionedThroughputExceededException (provisioned table) even when the table has spare capacity.
  • Example: an IoT table with deviceId as the partition key spreads writes from 2 million devices; readingDate sends all of today's writes to one partition.
  • A partition that gets more requests than its limit is a hot partition. A country code or today's date also makes a hot partition.
  • Adaptive capacity (next topic) helps a hot partition, but it cannot raise one partition above its limit.
  • Write sharding spreads the writes for one busy key value over many partitions. Add a suffix to the key value, for example 2026-10-18#1 to 2026-10-18#10. Each suffix is a different key value, so DynamoDB can store it on a different partition.
  • The cost of write sharding: to read all items for that day, the application must query each suffix and merge the results.
  • A random suffix spreads writes best, but you cannot find one item later without querying all suffixes. A calculated suffix (for example, a hash of the order ID) lets you compute the full key and use GetItem.
  • GetItem, PutItem, UpdateItem, and DeleteItem need the full primary key (partition key and, if the table has one, sort key).
  • PutItem writes a whole item. If an item with the same key exists, PutItem replaces it, and attributes that you did not send are lost.
  • UpdateItem changes only the attributes that you name. If the item does not exist, UpdateItem creates it. This "update or insert" behavior is called an upsert.
  • Single-table design stores many entity types in one table with generic keys, for example pk = USER#123, sk = ORDER#456. Related items then share one partition key, so one Query returns a user and the user's orders together. Use it when the application reads related entities together.

Data types and serialization

  • The low-level API sends each attribute as JSON with a data type descriptor: {"S": "Fido"}, {"N": "8"}, {"BOOL": true}, {"M": {...}}, {"L": [...]}.
  • Descriptors: S, N, B, BOOL, NULL, M, L, SS, NS, BS.
  • Numbers travel as strings ({"N": "123.45"}) to keep precision. Binary values travel as base64-encoded strings.
  • DynamoDB uses this JSON format only to send data between the client and the service. It does not store items as JSON.
  • Higher-level SDK tools do the conversion for you. Conversion from native objects to the typed format is marshalling. The reverse conversion is unmarshalling.
    • JavaScript v3: DynamoDBDocumentClient (@aws-sdk/lib-dynamodb), or marshall and unmarshall (@aws-sdk/util-dynamodb).
    • Python: the boto3 resource Table object (numbers come back as decimal.Decimal), or TypeSerializer and TypeDeserializer.
    • Java: the DynamoDB Enhanced Client maps items to classes.
  • DynamoDB Streams records (and the Lambda events built from them) contain Keys, NewImage, and OldImage in this typed format. Unmarshall them in the function code.

DynamoDB capacity units, capacity modes, and throttling

Remember

  • A strongly consistent read costs 1 read unit for each 4 KB.
  • An eventually consistent read costs 0.5 read unit for each 4 KB.
  • A transactional read costs 2 read units for each 4 KB.
  • A standard write costs 1 write unit for each 1 KB.
  • A transactional write costs 2 write units for each 1 KB.
  • Round the item size up to the next 4 KB for reads and to the next 1 KB for writes.
  • UpdateItem uses the larger of the item size before and after the update, even for one attribute.
  • A PutItem that replaces an item also uses the larger of the two item sizes.
  • Provisioned tables use capacity units (RCU, WCU). On-demand tables use request units with the same sizes.
  • On-demand mode bills for each request and scales automatically.
  • Use on-demand mode for unknown or spiky traffic and new applications. AWS calls on-demand the default and recommended mode.
  • Provisioned mode bills each hour for the capacity that you set, used or not.
  • Use provisioned mode for steady, predictable traffic that you can forecast.
  • Auto scaling keeps usage near a target utilization, for example 70% of the provisioned capacity.
  • Auto scaling reacts only after usage stays high for several minutes, so a sudden spike can throttle.
  • A table can switch from on-demand to provisioned at any time.
  • A table can switch to on-demand up to 4 times in a rolling 24-hour window. Older study material says one switch every 24 hours.
  • Burst capacity keeps up to 300 seconds (5 minutes) of unused read and write capacity for short spikes.
  • Do not count burst capacity as provisioned capacity. DynamoDB can use burst capacity for maintenance without notice.
  • Adaptive capacity gives more throughput to hot partitions automatically, at no extra cost.
  • Adaptive capacity cannot go above the table's total capacity or the partition maximum.
  • ProvisionedThroughputExceededException means that a provisioned table or GSI is over its capacity.
  • ThrottlingException means that an on-demand table went over a partition limit or its maximum throughput.
  • ThrottlingException also occurs when control plane calls, such as CreateTable or UpdateTable, come too fast.
  • RequestLimitExceeded means that the account throughput quota is reached. Request a quota increase from AWS Support.
  • The AWS SDKs retry throttled requests automatically with exponential backoff.
  • Without an SDK, retry 5xx errors and throttling errors with exponential backoff.
  • Use ReturnConsumedCapacity (TOTAL or INDEXES) to see the capacity units that a request used.

Exam signals

  • "New application, traffic is unknown, least operational overhead" → on-demand mode, because it scales automatically and needs no capacity planning.
  • "Steady traffic, lowest cost" → provisioned mode with auto scaling. Steady traffic lets you set capacity close to real use, which costs less than paying for each request.
  • "Calculate RCU for N reads of X KB" → round X up to 4 KB steps. One strongly consistent read uses 1 unit for each step.
  • "Calculate RCU for eventually consistent reads" → halve the strongly consistent result.
  • "Calculate RCU for transactional reads" → double the strongly consistent result.
  • "ProvisionedThroughputExceededException in the logs" → retry with exponential backoff, increase capacity, or fix a hot key.

Explanation

  • UpdateItem uses the larger of the item size before and after the update, even when it changes only one attribute. PutItem that replaces an item also uses the larger size.
  • Example: 10 strongly consistent reads each second of 6 KB items. 6 KB rounds up to 8 KB, which is 2 units. Total: 20 RCU. Eventually consistent: 10 RCU.
  • Example: 5 writes each second of 2.5 KB items. 2.5 KB rounds up to 3 KB, which is 3 units. Total: 15 WCU.
  • Provisioned tables use read and write capacity units (RCU, WCU). On-demand tables use read and write request units with the same sizes.

Burst, adaptive capacity, and throttling

  • Burst capacity: DynamoDB keeps up to 300 seconds (5 minutes) of unused read and write capacity. A short spike above the provisioned capacity can use it and not throttle.
  • Do not count burst capacity as part of your provisioned capacity. DynamoDB can also use it for maintenance without notice.
  • Adaptive capacity: DynamoDB gives more throughput to hot partitions automatically, at no extra cost. An uneven workload then throttles less. It cannot go above the table's total capacity or the partition maximum.
  • ProvisionedThroughputExceededException: a provisioned table or GSI is over its capacity.
  • ThrottlingException: an on-demand table went over a partition limit or its maximum throughput, or table-management calls such as CreateTable or UpdateTable (control plane calls) came too fast.
  • RequestLimitExceeded: the account throughput quota is reached. Request a quota increase from AWS Support.
  • The AWS SDKs retry throttled requests automatically with exponential backoff. Without an SDK, retry 5xx errors and throttling errors with backoff.
  • Use ReturnConsumedCapacity (TOTAL or INDEXES) to see the units that a request used. Use it to check your capacity calculations or to find expensive requests.

Read consistency, Query, Scan, PartiQL, and batch operations

Remember

  • DynamoDB reads are eventually consistent by default. Consistency is usually reached within seconds.
  • Set ConsistentRead to true for a strongly consistent read. A strongly consistent read costs twice as much.
  • Tables and LSIs support strongly consistent reads.
  • GSIs and DynamoDB Streams support only eventually consistent reads.
  • A Query reads one item collection and needs equality on the partition key in KeyConditionExpression.
  • A Scan reads, and charges for, every item in the table or index.
  • Use Query when you know the partition key value. Use Scan only for small tables or one-time jobs.
  • Query sort key conditions are =, <, <=, >, >=, BETWEEN, and begins_with.
  • Query returns results in ascending sort key order by default. ScanIndexForward=false returns descending order.
  • FilterExpression runs after the read. FilterExpression reduces the data returned, not the capacity used.
  • ProjectionExpression returns only the named attributes, but does not reduce the capacity used.
  • Each Query or Scan call returns a maximum of 1 MB.
  • To get the next page, send LastEvaluatedKey as ExclusiveStartKey.
  • Limit sets the maximum number of items to evaluate, not the number of matching items.
  • DynamoDB applies the filter after Limit, so a page can have fewer matching items than Limit, or none.
  • A parallel scan uses Segment and TotalSegments. A parallel scan finishes faster but uses capacity faster.
  • Use a parallel scan for a large table when the table has spare capacity.
  • DynamoDB rejects reserved words, such as Comment or Size, as attribute names in an expression.
  • Replace a reserved attribute name with a placeholder (#n) in ExpressionAttributeNames.
  • Put expression values in ExpressionAttributeValues (:v).
  • PartiQL is a SQL-compatible query language for DynamoDB: SELECT, INSERT, UPDATE, DELETE.
  • The PartiQL APIs are ExecuteStatement, BatchExecuteStatement, and ExecuteTransaction.
  • A PartiQL SELECT without equality (or IN) on the partition key can run a full table scan.
  • An IAM policy can deny PartiQL statements that run full table scans.
  • PartiQL has the same performance as the other DynamoDB operations. SQL syntax does not make scans cheaper.
  • BatchGetItem reads up to 100 items and 16 MB. Unread keys come back in UnprocessedKeys.
  • BatchWriteItem accepts up to 25 put or delete requests and 16 MB.
  • BatchWriteItem cannot do update requests. Unwritten items come back in UnprocessedItems.
  • A batch operation is not atomic. Some items can succeed while others fail.
  • A batch operation saves network round trips, but each item costs the same capacity as a single request.
  • Retry unprocessed batch items with exponential backoff. The usual cause is throttling.

Exam signals

  • "Scan with a filter is slow and expensive" → a Query on the table or on a GSI with a suitable key. The Scan reads the whole table; the Query reads only the matching item collection.
  • "Read must return the value written a moment ago" → ConsistentRead=true on the table (not on a GSI, because GSIs support only eventually consistent reads).
  • "Query returns only part of the results" → paginate with LastEvaluatedKey, because each call returns at most 1 MB.
  • "Latest 10 orders for a customer" → Query with ScanIndexForward=false and Limit=10. With a date sort key, descending order puts the newest orders first.
  • "BatchWriteItem response has UnprocessedItems" → retry those items with exponential backoff.
  • "Query DynamoDB with SQL-like syntax" → PartiQL (ExecuteStatement).

Explanation

Read consistency

  • Reads are eventually consistent by default. Consistency is usually reached within seconds.
  • DynamoDB keeps copies of each item in several storage locations and needs a short time to update all of them. An eventually consistent read can come from a copy that does not have the latest write yet.
  • Set ConsistentRead to true for a strongly consistent read. It returns the latest data and costs twice as much.
  • Tables and LSIs support strongly consistent reads. GSIs and DynamoDB Streams support only eventually consistent reads.

Use Query when you know the partition key value. Use Scan only for small tables or one-time jobs, because it reads, and charges for, every item.

  • Sort key conditions in a Query: =, <, <=, >, >=, BETWEEN, begins_with.
  • ScanIndexForward=false returns results in descending sort key order. The default is ascending.
  • FilterExpression runs after the read. It reduces the data returned, not the capacity used. You pay for every item that DynamoDB reads, also the items that the filter removes.
  • ProjectionExpression returns only the attributes that you name. It does not reduce the capacity used, because DynamoDB calculates capacity from the full item size.
  • Each Query or Scan call returns a maximum of 1 MB. If the response has LastEvaluatedKey, send it as ExclusiveStartKey to get the next page.
  • Limit sets the maximum number of items to evaluate, not the number of matching items. DynamoDB applies the filter after the limit, so a page can contain fewer matching items than Limit, or none.
  • Parallel scan: set Segment and TotalSegments. Workers scan segments at the same time.
  • A parallel scan finishes faster but uses capacity faster. Use it for a large table when the table has spare capacity.
  • Some attribute names are reserved words, for example Comment or Size. DynamoDB rejects them in an expression. Replace each one with a placeholder in ExpressionAttributeNames (#n).
  • Put values in ExpressionAttributeValues (:v).

PartiQL

  • PartiQL is a SQL-compatible query language for DynamoDB: SELECT, INSERT, UPDATE, DELETE.
  • APIs: ExecuteStatement, BatchExecuteStatement, and ExecuteTransaction. You can also run it in the console, NoSQL Workbench, and the AWS CLI.
  • A SELECT without an equality (or IN) condition on the partition key in the WHERE clause can run a full table scan. A full table scan reads every item, so it is slow and uses much read capacity.
  • An IAM policy can deny PartiQL statements that run full table scans.
  • PartiQL operations have the same availability, latency, and performance as the other DynamoDB data operations. SQL syntax does not make scans cheaper.

Secondary indexes: LSI and GSI

Remember

  • A local secondary index (LSI) has the same partition key as the table and a different sort key.
  • A global secondary index (GSI) can have any partition key and an optional sort key.
  • You can create an LSI only when you create the table. You can create a GSI at any time.
  • A table can have 5 LSIs and 20 GSIs (default quota).
  • An LSI supports eventually and strongly consistent reads. A GSI supports only eventually consistent reads.
  • An LSI uses the table's capacity. A GSI has its own capacity in provisioned mode.
  • An LSI fetches attributes that are not in the projection from the table, at extra cost and latency.
  • A GSI cannot return attributes that are not in its projection.
  • With an LSI, one item collection (table plus all LSIs) has a limit of 10 GB. A GSI has no such limit.
  • When an item collection reaches 10 GB, writes that make it larger fail with ItemCollectionSizeLimitExceededException.
  • Choose an LSI for a different sort key on the same partition key with strongly consistent reads, at table creation.
  • Choose a GSI for a different partition key, or when the table already exists.
  • The projection types are KEYS_ONLY (smallest), INCLUDE (keys plus named attributes), and ALL (largest).
  • A larger projection costs more storage and index writes, but more queries get their data from the index alone.
  • Use Query or Scan on an index. GetItem and BatchGetItem do not work on an index.
  • GSI key values do not have to be unique. Only the table's primary key must be unique.
  • A sparse index contains only the items that have the index key attribute.
  • Use a sparse index to find a small set of items, for example open orders.
  • DynamoDB updates a GSI asynchronously, so a GSI query can return data that is not current.
  • A GSI without enough write capacity throttles writes to the base table.
  • Give a GSI write capacity equal to or greater than the write capacity of the table.
  • A write that changes an index key value uses two index writes: a delete and a put.

Exam signals

  • "Query on a different attribute, table already in production" → add a GSI. You can add a GSI at any time, and it can use a different partition key.
  • "Strongly consistent reads with an alternative sort key" → LSI (create with the table). GSIs do not support strongly consistent reads.
  • "Writes to the table throttle, table has spare WCU" → a GSI is short of write capacity. A GSI without enough write capacity throttles writes to the base table.
  • "Find the few items that need attention without a Scan" → sparse GSI. Only items that have the index key attribute are in the index, so a Query reads only those items.
  • "GSI query does not return an attribute" → project the attribute into the index (INCLUDE or ALL). A GSI cannot fetch attributes from the table.

Key facts

  • The projection is the set of table attributes that DynamoDB copies into the index. Types: KEYS_ONLY (smallest), INCLUDE (keys plus named attributes), ALL (largest).
  • A larger projection costs more storage and index writes, but more queries can get their data from the index alone.
  • Use Query or Scan on an index. GetItem and BatchGetItem do not work on an index.
  • GSI key values do not have to be unique, so a Query on a GSI can return many items for one key value. Only the table's primary key must be unique.
  • Sparse index: an item without the index key attribute is not in the index. Use it to find a small set of items, for example open orders.
  • DynamoDB updates a GSI asynchronously. A GSI query can return data that is not current.
  • If a GSI does not have enough write capacity, DynamoDB throttles writes to the base table. Give the GSI write capacity equal to or greater than the table.
  • A write that changes an index key value uses two index writes: delete the old entry and put the new entry.
  • When an item collection reaches 10 GB on a table with an LSI, writes that make it larger fail with ItemCollectionSizeLimitExceededException.

Conditional writes, atomic counters, and transactions

Remember

  • A ConditionExpression works on PutItem, UpdateItem, and DeleteItem.
  • A false condition fails the write with ConditionalCheckFailedException, and nothing changes.
  • To create an item only when the key does not exist, use the condition attribute_not_exists(pk).
  • Without a condition, PutItem replaces an existing item and gives no error.
  • The condition functions are attribute_exists, attribute_not_exists, attribute_type, begins_with, contains, and size.
  • Optimistic locking prevents a lost update with a version number in the item.
  • For optimistic locking, write SET version = :new with the condition version = :old. On failure, read again and retry.
  • A failed condition still uses write capacity: the size of the existing item, minimum 1 WCU.
  • ReturnValuesOnConditionCheckFailure=ALL_OLD returns the current item with the exception, so no second read is necessary.
  • The ReturnValues options are NONE (default), ALL_OLD, UPDATED_OLD, ALL_NEW, and UPDATED_NEW.
  • Use ALL_NEW or UPDATED_NEW to get the result of an update without a second read.
  • An atomic counter uses UpdateItem with SET views = views + :one or ADD views :one.
  • An atomic counter changes the value on the server, needs no read, and counts every concurrent update.
  • An atomic counter is not idempotent. A retry after a timeout can count twice.
  • Use a conditional update, not an atomic counter, when exact counts matter, for example money.
  • TransactWriteItems accepts Put, Update, Delete, and ConditionCheck actions.
  • TransactGetItems accepts Get actions.
  • A DynamoDB transaction has up to 100 items and 4 MB.
  • A transaction can use one or more tables in the same account and the same Region.
  • A transaction costs two reads or writes for each item (prepare and commit), also when the transaction fails.
  • All actions in a transaction succeed, or none succeed.
  • Two actions in one transaction cannot target the same item. The request fails with a validation error.
  • Send a ClientRequestToken with TransactWriteItems to make a retry idempotent for 10 minutes.
  • The same ClientRequestToken with different parameters returns IdempotentParameterMismatch.
  • A failed transaction returns TransactionCanceledException. CancellationReasons lists the reason for each item, in request order.
  • A standard write that conflicts with a running transaction fails with TransactionConflictException.
  • You cannot run a transaction on an index.
  • Use BatchWriteItem, not transactions, for bulk loads that do not need all-or-nothing behavior.

Exam signals

  • "Two users update the same item, one update is lost" → optimistic locking with a version attribute and a condition expression. The second write fails because the version changed.
  • "Register a user name only if it is not taken" → PutItem with attribute_not_exists. The write fails if an item with that key already exists.
  • "Move money between two accounts, all or nothing" → TransactWriteItems.
  • "Write the order only if the customer account is active (another item)" → ConditionCheck in a transaction. A ConditionCheck tests an item without changing it, and a false result cancels the whole transaction.
  • "Network timeout, retry must not apply the transaction twice" → same ClientRequestToken. DynamoDB treats the retry as the same request.

Explanation

Conditional writes

  • Add a ConditionExpression to PutItem, UpdateItem, or DeleteItem. If the condition is false, the write fails with ConditionalCheckFailedException and nothing changes.
  • To create an item only when no item with that key exists, add the condition attribute_not_exists(pk). Without it, PutItem replaces the existing item and gives no error.
  • Functions: attribute_exists, attribute_not_exists, attribute_type, begins_with, contains, size.
  • Optimistic locking prevents a lost update. A lost update occurs when client A reads an item, client B changes it, and client A then writes over B's change.
  • To use optimistic locking, keep a version number in the item. Write with SET version = :new and the condition version = :old.
  • If another client wrote first, the version changed, and the write fails with ConditionalCheckFailedException. Read the item again and retry.
  • A failed condition still uses write capacity: the size of the existing item, minimum 1 WCU.
  • ReturnValuesOnConditionCheckFailure=ALL_OLD returns the current item with the exception. You do not need a second read.
  • ReturnValues on writes: NONE (default), ALL_OLD, UPDATED_OLD, ALL_NEW, UPDATED_NEW. Use ALL_NEW or UPDATED_NEW to get the result of an update, for example a new counter value, without a second read.

Atomic counters

  • UpdateItem with SET views = views + :one (or ADD views :one) changes the value on the server. No read is needed. Two clients that add at the same time both count, because DynamoDB applies each update to the current value.
  • An atomic counter is not idempotent: if the same request runs twice, the value changes twice. After a timeout, the first request can already have succeeded, so a retry counts twice.
  • Use a conditional update when exact counts matter, for example money.

DynamoDB Streams

Remember

  • A DynamoDB stream records item-level changes (insert, modify, remove) in near real time.
  • A DynamoDB stream keeps each record for 24 hours.
  • For longer retention, use Amazon Kinesis Data Streams for DynamoDB (a separate feature).
  • Each stream record appears exactly one time in the stream.
  • Stream records are in order for each item (each primary key), not for the whole table.
  • A PutItem or UpdateItem that does not change data writes no stream record.
  • You cannot edit StreamViewType. Disable the stream and enable a new one.
  • A new stream has a new ARN, so update each consumer, for example the Lambda event source mapping.
  • Let a maximum of two processes read the same stream shard at the same time. More readers can be throttled.
  • A transaction writes one stream record for each changed item, and the records can arrive at different times.
  • To read all items of a transaction together, a consumer must use TransactGetItems.
  • KEYS_ONLY records contain only the key attributes. The consumer must read the table for other attributes.
  • NEW_IMAGE records contain the item after the change.
  • OLD_IMAGE records contain the item before the change.
  • NEW_AND_OLD_IMAGES records contain the item before and after the change.
  • A Lambda event source mapping polls the stream and invokes the function with batches of records.
  • By default, one Lambda function instance processes one shard, in order.
  • The Lambda execution role needs dynamodb:DescribeStream, dynamodb:GetRecords, dynamodb:GetShardIterator, and dynamodb:ListStreams.
  • The AWSLambdaDynamoDBExecutionRole managed policy includes the four stream permissions.
  • ParallelizationFactor (up to 10) processes one shard with more instances and keeps the order for each item.
  • Use filter criteria on the event source mapping to invoke the function only for matching records, for example INSERT.

Exam signals

  • "Send an email when a new item is added, with the item data" → stream with NEW_IMAGE and a Lambda trigger with an INSERT filter.
  • "Audit log must show old and new values" → NEW_AND_OLD_IMAGES, because only this view has the item both before and after the change.
  • "Consumer was down for two days and lost changes" → 24-hour retention. Use Kinesis Data Streams for DynamoDB for longer retention.

Explanation

Key facts

  • A stream records item-level changes (insert, modify, remove) in near real time. DynamoDB keeps each record for 24 hours.
  • Each stream record appears exactly one time in the stream. Records for one item appear in the order of the changes.
  • Ordering is for each item (each primary key), not for the whole table.
  • A PutItem or UpdateItem that does not change data writes no stream record.
  • You cannot edit StreamViewType. Disable the stream and enable a new one.

TTL, backups, and global tables

Remember

  • To use TTL, enable TTL on the table and name one attribute.
  • Store the TTL expiry time as a Number in Unix epoch time, in seconds.
  • The TTL process ignores items where the TTL attribute is not a Number.
  • A TTL value in milliseconds is far in the future, so the item does not expire.
  • DynamoDB deletes expired items typically within a few days after expiry. Older study material says 48 hours.
  • TTL deletes do not use write capacity.
  • Expired items that are not deleted yet still appear in reads. Use a filter expression to remove them.
  • A TTL delete appears in DynamoDB Streams with userIdentity type Service and principal dynamodb.amazonaws.com.
  • TTL deletes also remove the item from LSIs and GSIs.
  • Point-in-time recovery (PITR) makes continuous backups and restores to any second in the recovery period.
  • The PITR recovery period is 1 to 35 days, and you set it.
  • A PITR restore always creates a new table.
  • The latest PITR restorable time is typically about 5 minutes before the current time.
  • An on-demand backup is a full backup that you start. An on-demand backup stays until you delete it.
  • An on-demand backup restores to a new table.
  • Use PITR for protection from accidental writes or deletes. Use on-demand backups for long-term retention.
  • A global table has replica tables in two or more Regions. Applications read and write in any replica Region.
  • The default global table mode is multi-Region eventual consistency (MREC), with asynchronous replication typically within a second.
  • MREC resolves conflicts with last writer wins for each item. The change with the earlier timestamp is lost.
  • In MREC, transactions are atomic only in the Region where they run.
  • Multi-Region strong consistency (MRSC) replicates each write synchronously to another Region before it returns success.
  • MRSC has an RPO of zero.
  • MRSC needs exactly three Regions: three replicas, or two replicas and one witness.
  • You cannot read from or write to an MRSC witness.
  • Choose MRSC when every strongly consistent read in every Region must return the latest write.
  • MRSC writes are slower than MREC writes, because each write waits for another Region.
  • MRSC does not support TTL, LSIs, or transactions.

Exam signals

  • "Delete session items after 24 hours at no cost" → TTL with an epoch-seconds Number attribute, because TTL deletes use no write capacity.
  • "Expired items still appear in queries" → expected, because TTL can take a few days to delete them. Filter on the TTL attribute.
  • "Restore the table to its state from 10 minutes before a bad deploy" → PITR (to a new table), because PITR restores to any second in the recovery period.
  • "Low-latency reads and writes for users in several Regions" → global tables, because each Region has a local replica that accepts reads and writes.

Explanation

Time to live (TTL)

  • Enable TTL on the table and name one attribute. Store the expiry time as a Number in Unix epoch time, in seconds.
  • The TTL process ignores items where the attribute is not a Number. A value in milliseconds is far in the future, so the item does not expire.
  • DynamoDB deletes expired items typically within a few days after expiry. Older material says 48 hours.
  • TTL deletes do not use write capacity.
  • Expired items that are not deleted yet still appear in reads. Use a filter expression to remove them from Query and Scan results.
  • A TTL delete goes to DynamoDB Streams as a service delete. The record has userIdentity type Service and principal dynamodb.amazonaws.com. Use these fields to tell TTL deletes from user deletes, for example to archive only expired items.
  • TTL deletes also remove the item from LSIs and GSIs.

  • The latest restorable time is typically about 5 minutes before the current time.
  • Use PITR for protection from accidental writes or deletes. Use on-demand backups for long-term retention.

Global tables

  • A global table has replica tables in two or more Regions. Applications read and write in any replica Region.
  • Default mode: multi-Region eventual consistency (MREC). Replication is asynchronous, typically within a second.
  • MREC conflict rule: last writer wins, for each item. If two Regions change the same item at about the same time, DynamoDB keeps the change with the later timestamp. The other change is lost.
  • Multi-Region strong consistency (MRSC) replicates each write synchronously to another Region before it returns success. Its RPO (recovery point objective: the maximum data loss after a failure) is zero.
  • MRSC needs exactly three Regions: three replicas, or two replicas and one witness.
  • A witness is a DynamoDB-managed component in the third Region that supports replication; you cannot read from it or write to it.
  • Choose MRSC when every strongly consistent read in every Region must return the latest write. Writes are slower than in MREC, because each write waits for another Region.
  • MRSC does not support TTL, LSIs, or transactions.
  • In MREC, transactions are atomic only in the Region where they run. Other Regions can see part of a transaction while it replicates.

DynamoDB security: IAM, encryption, and network access

Remember

  • Applications get DynamoDB access through IAM roles, for example a Lambda execution role. Give only the necessary actions and tables.
  • dynamodb:LeadingKeys limits access to items whose partition key matches a value, for example the caller's Cognito identity ID.
  • Use dynamodb:LeadingKeys with the ForAllValues modifier, for example ForAllValues:StringEquals.
  • dynamodb:Attributes limits the attributes that a request can access.
  • With dynamodb:Attributes, require dynamodb:Select = SPECIFIC_ATTRIBUTES and limit dynamodb:ReturnValues.
  • A read without a projection, or a write with ReturnValues=ALL_OLD or ALL_NEW, returns the whole item.
  • Do not allow Scan in a per-user policy. A Scan returns all items, whatever the leading key.
  • A policy with policy variables needs "Version": "2012-10-17". The older version, 2008-10-17, does not support policy variables.
  • A DynamoDB table supports resource-based policies of up to 20 KB, for example for cross-account access.
  • DynamoDB always encrypts data at rest: tables, indexes, streams, backups, and global tables. You cannot turn it off.
  • The AWS owned key is the default, belongs to DynamoDB, and has no extra charge.
  • The AWS managed key (aws/dynamodb) is in your account, is managed by AWS KMS, and has AWS KMS charges.
  • A customer managed key is in your account, has AWS KMS charges, and lets you control the key policy and rotation.
  • Choose the AWS owned key when you have no key requirements.
  • Choose the AWS managed key to see key use in CloudTrail without control of the key.
  • Choose a customer managed key when you must control the key policy or rotation.
  • You can change the encryption key type of an existing DynamoDB table.
  • DynamoDB uses HTTPS endpoints.
  • Use the AWS Database Encryption SDK to encrypt attribute values before the application sends them.
  • A gateway VPC endpoint lets private subnets reach DynamoDB without a NAT gateway or internet access.

DynamoDB Accelerator (DAX)

Remember

  • DAX is an in-memory cache for DynamoDB only.
  • DAX reduces eventually consistent read latency from milliseconds to microseconds.
  • DAX is API-compatible with DynamoDB. The application uses the DAX client, with few code changes.
  • DAX runs in a VPC. DAX clients must be in the VPC, and security groups control access.
  • A DAX cluster has one primary node and 0 to 10 read replicas.
  • AWS recommends at least three DAX nodes in different Availability Zones.
  • The DAX item cache holds GetItem and BatchGetItem results. The default TTL is 5 minutes.
  • The DAX query cache holds Query and Scan results, with its own TTL.
  • The DAX query cache returns a cached result only for an identical Query or Scan request.
  • Writes through DAX are write-through: DAX writes to DynamoDB first, then updates the item cache.
  • Writes do not update or clear the DAX query cache. A cached Query result can be stale until its TTL ends.
  • Writes made directly to DynamoDB do not update the DAX cache.
  • DAX passes strongly consistent reads and TransactGetItems to DynamoDB and does not cache the results.
  • DAX caches "not found" results (negative caching) until the cache TTL ends.
  • A DAX cache hit does not use table read capacity.
  • Do not use DAX for strongly consistent reads. DAX adds cost and no speed for them.
  • Do not use DAX for write-heavy applications or applications with few repeated reads.
  • Do not use DAX when single-digit millisecond reads from DynamoDB are fast enough.

Exam signals

  • "Microsecond reads from DynamoDB, fewest code changes" → DAX.
  • "Read-heavy table with hot keys, reduce RCU cost" → DAX, because a cache hit does not use table read capacity.
  • "Application needs strongly consistent reads and uses DAX" → the reads go to DynamoDB. DAX gives no benefit for them.
  • "New item does not appear in a repeated Query through DAX" → query cache TTL. Writes do not clear the query cache, so the old result stays until its TTL ends.
  • "Cache in front of RDS or other sources" → ElastiCache, not DAX. DAX works only with DynamoDB.

Explanation

Key facts

  • DAX is an in-memory cache for DynamoDB. It reduces eventually consistent read latency from milliseconds to microseconds.
  • DAX is API-compatible with DynamoDB. The application uses the DAX client, with few code changes.
  • DAX runs in a VPC. Clients must be in the VPC. Control access with security groups.
  • A cluster has one primary node and 0 to 10 read replicas.
  • AWS recommends at least three nodes in different Availability Zones, so that the cluster still serves reads when one node or one zone fails.
  • Item cache: results of GetItem and BatchGetItem. Default TTL: 5 minutes.
  • Query cache: results of Query and Scan. DAX uses the full set of request parameters as the cache key, so only an identical Query or Scan gets the cached result. It has its own TTL.
  • Writes through DAX are write-through: DAX writes to DynamoDB first, then updates the item cache.
  • Writes do not update or clear the query cache. A cached Query result can be stale until its TTL ends.
  • Writes made directly to DynamoDB (not through DAX) do not update the DAX cache.
  • DAX passes strongly consistent reads and TransactGetItems to DynamoDB and does not cache the results.
  • DAX also caches "not found" results (negative caching). If another client then creates the item directly in DynamoDB, DAX can return "not found" until the cache TTL ends.

When not to use DAX

  • The application needs strongly consistent reads. DAX sends these reads to DynamoDB, so it adds cost and no speed.
  • The application is write-heavy, or has few repeated reads. A cache helps only when the same data is read many times.
  • The application does not need microsecond reads. DynamoDB alone already reads in single-digit milliseconds.

RDS and Aurora: availability, replicas, and backups

Remember

  • An RDS Multi-AZ DB instance has one standby for high availability and failover.
  • Multi-AZ replication is synchronous, so a failover loses no data.
  • A Multi-AZ standby does not serve reads and cannot be in another Region.
  • Multi-AZ failover is automatic and typically takes 60 to 120 seconds.
  • On failover, RDS points the endpoint DNS record to the standby. Applications reconnect to the same endpoint name.
  • Set the JVM DNS TTL to 60 seconds or less, so that a Java application finds the new address after failover.
  • A Multi-AZ DB cluster deployment has two standby instances, and both standby instances can serve reads.
  • An RDS read replica is for read scaling, reporting, and disaster recovery.
  • Read replica replication is asynchronous, so a read from a replica can return old data.
  • One RDS primary can have up to 15 read replicas (default quota). Older study material says 5.
  • A read replica can be in another Region (cross-Region replica).
  • Read replica failover is manual: promote the replica to a standalone DB instance.
  • RDS does not add or remove read replicas automatically. Applications must send reads to the replica endpoints.
  • Choose Multi-AZ to survive the failure of the primary instance or its Availability Zone.
  • Choose read replicas to move read traffic off the primary. You can use Multi-AZ and read replicas together.
  • RDS automated backup retention is 0 to 35 days. A value of 0 turns off automated backups and point-in-time restore.
  • The default backup retention is 1 day with the API or CLI, and 7 days in the console.
  • Point-in-time restore always creates a new DB instance.
  • RDS uploads transaction logs to Amazon S3 every 5 minutes, so the latest restorable time is about 5 minutes ago.
  • Manual RDS snapshots stay until you delete them.
  • Aurora storage keeps six copies of the data across three Availability Zones.
  • An Aurora cluster has one writer and up to 15 Aurora Replicas.
  • Aurora Replicas share the cluster storage. On failover, Aurora makes one replica the new writer.
  • The Aurora cluster (writer) endpoint points to the current primary and follows failover.
  • The Aurora reader endpoint balances connections across the Aurora Replicas.
  • An Aurora custom endpoint is a group of instances that you choose, for example for analytics queries.
  • An Aurora instance endpoint connects to one instance, for diagnosis or tuning.
  • One Aurora Serverless v2 ACU is about 2 GiB of memory with matching CPU and network.
  • Aurora Serverless v2 scales from 0 to 256 ACUs, depending on the engine version, in steps as small as 0.5 ACU.
  • A minimum of 0 ACUs turns on automatic pause and resume on supported versions.
  • A paused Aurora Serverless v2 instance costs nothing for compute, but storage is still charged.
  • The first connection after a pause waits typically about 15 seconds while the instance resumes.
  • An Aurora cluster can mix Serverless v2 and provisioned instances.
  • The promotion tier of a reader sets the order in which Aurora chooses a new writer on failover.
  • Serverless v2 readers in tiers 0 and 1 scale with the writer. Readers in tiers 2 to 15 scale on their own load.

Exam signals

  • "Survive an Availability Zone failure with automatic failover" → Multi-AZ, because the standby in another zone takes over automatically.
  • "Reporting queries slow down the production database" → read replica (or Aurora reader endpoint).
  • "Unpredictable or intermittent database load, pay for use" → Aurora Serverless v2.
  • "Restore the database to 3:15 PM yesterday" → point-in-time restore to a new instance.

Secure connections to RDS and Aurora

Remember

  • Do not put database passwords in code, templates, or plain environment variables.
  • Store database passwords in AWS Secrets Manager and read them at run time with the IAM role.
  • Secrets Manager can rotate database credentials automatically.
  • RDS can manage the master user password in Secrets Manager for you.
  • IAM database authentication works with MariaDB, MySQL, and PostgreSQL on RDS and Aurora.
  • With IAM database authentication, the application uses an authentication token as the password.
  • An IAM database authentication token is valid for 15 minutes.
  • IAM database authentication needs an IAM policy that allows rds-db:connect for the database user.
  • IAM database authentication uses SSL/TLS and stores no password in the database or the application.
  • Each Lambda function instance opens its own database connection, so a traffic spike can exhaust database connections.
  • RDS Proxy keeps a pool of database connections and shares them among clients.
  • Use RDS Proxy when many Lambda functions or short connections open too many connections.
  • RDS Proxy keeps application connections during a failover and connects to the standby.
  • Clients can authenticate to RDS Proxy with IAM.
  • RDS Proxy connects to the database with Secrets Manager credentials or IAM database authentication.
  • RDS Proxy must be in the same VPC as the database, and RDS Proxy cannot be publicly accessible.
  • The RDS Data API is an HTTPS endpoint for SQL statements on Aurora.
  • The Data API needs no persistent connection, no database driver, and no VPC configuration.
  • A Data API call gives the cluster ARN and the ARN of a Secrets Manager secret.
  • The Data API runs queries on the writer instance only, so the Data API does not spread reads over replicas.
  • The Data API response size limit is 1 MiB.
  • The Data API does not support the small burstable db.t instance classes.
  • Turn on RDS encryption at rest (AWS KMS) when you create the DB instance.
  • You cannot encrypt an existing unencrypted DB instance in place.
  • To encrypt an existing database, take a snapshot, copy it with encryption, and restore a new instance.
  • A blue/green deployment can also create an encrypted green environment from an unencrypted DB instance.
  • You cannot turn off RDS encryption. Replicas and snapshots of an encrypted instance are encrypted.
  • You cannot share a snapshot that uses the AWS managed key with another account.
  • Use a customer managed key to share encrypted snapshots with another account.
  • To copy an encrypted snapshot to another Region, give a KMS key in the destination Region.

Exam signals

  • "No database password in the application, short-lived credentials" → IAM database authentication.
  • "Store and rotate the database password automatically" → Secrets Manager.
  • "Lambda functions exhaust database connections" → RDS Proxy.
  • "Query Aurora from Lambda without VPC configuration or connection management" → RDS Data API.
  • "Existing database must be encrypted" → snapshot, encrypted copy, restore.

Explanation

Credentials

  • Do not put database passwords in code, templates, or plain environment variables. Store them in AWS Secrets Manager and read them at run time with the IAM role.
  • Secrets Manager can rotate database credentials automatically. RDS can also manage the master user password in Secrets Manager for you.

IAM database authentication

  • Engines: MariaDB, MySQL, PostgreSQL (RDS and Aurora).
  • The application gets an authentication token (signed with the caller's IAM credentials, like any AWS API request) and uses it as the password. A token is valid for 15 minutes.
  • The IAM policy allows rds-db:connect for the database user.
  • Traffic uses SSL/TLS. No password is stored in the database or the application.

RDS Proxy

  • Each Lambda function instance opens its own database connection. A traffic spike can then reach the database's maximum connections, and new connections fail.
  • RDS Proxy keeps a pool of database connections and shares them among clients. Use it when many Lambda functions or short connections open too many connections.
  • Keeps application connections during a failover and connects to the standby.
  • Clients can authenticate with IAM. The proxy connects to the database with Secrets Manager credentials or IAM database authentication.
  • The proxy must be in the same VPC as the database. It cannot be publicly accessible.

RDS Data API (Aurora)

  • An HTTPS endpoint for SQL statements. The caller needs no persistent connection, no database driver, and no VPC configuration.
  • The call gives the cluster ARN and the ARN of a Secrets Manager secret with the database credentials.
  • Data API runs queries on the writer instance only, so it does not spread reads over replicas.
  • The Data API response size limit is 1 MiB.
  • Data API does not support the small burstable db.t instance classes.

Encryption at rest

  • Turn on encryption (AWS KMS) when you create the DB instance. You cannot encrypt an existing unencrypted instance in place.
  • To encrypt an existing database: take a snapshot, copy the snapshot with encryption turned on, and restore a new instance from the copy.
  • A blue/green deployment can also create an encrypted green environment from an unencrypted DB instance.
  • You cannot turn off encryption. Replicas and snapshots of an encrypted instance are encrypted.
  • You cannot share a snapshot that uses the AWS managed key, because you cannot change that key's policy to give another account access. Use a customer managed key to share encrypted snapshots with another account.
  • To copy an encrypted snapshot to another Region, give a KMS key in the destination Region.

Caching strategies: lazy loading, write-through, and TTL

Remember

  • Lazy loading (cache-aside) reads the cache first. On a miss, the application reads the database and writes the result to the cache.
  • Lazy loading puts only requested data in the cache.
  • With lazy loading, a failed cache node is not fatal. The new node fills on misses.
  • A lazy loading cache miss costs three trips: cache, database, and cache write.
  • Lazy loading data can become stale, because a database update does not change the cached copy.
  • Write-through writes the cache each time the application writes the database.
  • Write-through data in the cache is never stale.
  • With write-through, a new cache node has missing data until the next write.
  • Write-through causes cache churn: the cache fills with written data that nobody reads.
  • Write-through adds latency to each write.
  • Choose lazy loading when users read only part of the data and can accept some stale data.
  • Choose write-through when cached data must match the database after each update.
  • A cache TTL sets the number of seconds until a key expires. A read of an expired key is a miss.
  • Add a TTL to lazy loading to limit stale data.
  • Add a TTL to write-through to remove data that nobody reads.
  • Use lazy loading and write-through together with a TTL to get the advantages of both.
  • In read-through, the cache, not the application, loads data from the database on a miss.
  • DAX is read-through for eventually consistent reads.
  • DAX is write-through for writes that you send through DAX.
  • A direct write to DynamoDB is write-around: write latency stays low, but the DAX cache can be stale.
  • Common cache uses are query results, session state, leaderboards (sorted sets), and rate-limit counters.

Exam signals

  • "Cache only the data that users read" → lazy loading.
  • "Cached data must never be stale after an update" → write-through.
  • "Users see old prices for hours" → add or reduce the TTL, or add write-through.
  • "After a cache node is replaced, every request is slow for a while" → lazy loading fills the new node on misses (expected).

ElastiCache and MemoryDB

Remember

  • Valkey or Redis OSS supports complex data types: strings, lists, sets, sorted sets, hashes, and more.
  • Valkey or Redis OSS supports replication, automatic failover, backup and restore, and pub/sub.
  • Valkey or Redis OSS is not multi-threaded.
  • Memcached has simple data types and is multi-threaded (uses all CPU cores of a node).
  • Memcached has no replication, no automatic failover, and no pub/sub.
  • Memcached supports backup and restore only for serverless caches.
  • Choose Valkey or Redis OSS for data structures, replication, high availability, or backups.
  • Choose Memcached for the simplest model, large multi-threaded nodes, and scale out and in.
  • Node-based ElastiCache clusters run in a VPC. A Lambda function needs VPC access and a security group rule.
  • ElastiCache encryption in transit is always on for serverless caches.
  • For node-based ElastiCache clusters, set TransitEncryptionEnabled to turn on encryption in transit.
  • The Valkey or Redis OSS AUTH token works only with encryption in transit turned on.
  • AUTH gives every client with the token full access.
  • Role-based access control (RBAC) replaces AUTH, with a password and an access string for each user.
  • An RBAC access string sets which commands a user can run and which keys the user can use.
  • ElastiCache IAM authentication needs Valkey 7.2 or later, or Redis OSS 7.0 or later.
  • ElastiCache IAM authentication needs TLS and an IAM policy with elasticache:Connect.
  • An ElastiCache IAM authentication token is valid for 15 minutes.
  • An ElastiCache IAM-authenticated connection closes after 12 hours unless it authenticates again.
  • MemoryDB is a durable, in-memory primary database, compatible with Valkey and Redis OSS.
  • MemoryDB stores every write in a Multi-AZ transactional log before it returns success.
  • MemoryDB gives microsecond reads and single-digit millisecond writes.
  • MemoryDB reads from primary nodes are strongly consistent. Reads from replica nodes are eventually consistent.
  • MemoryDB uses access control lists (ACLs) for user authentication.
  • Use ElastiCache as a cache in front of an existing primary database or data store.
  • Use MemoryDB as the primary database when you want Redis-compatible data structures and durability.
  • Since 2026, node-based ElastiCache for Valkey 9.0 offers optional durability. Older study material says that ElastiCache is never durable.
  • Valkey 9.0 durability uses synchronous writes (designed for zero data loss) or asynchronous writes (up to 10 seconds of loss).
  • Exam questions usually mean "ElastiCache = cache, MemoryDB = durable primary database".

Exam signals

  • "Leaderboard with ranking" → Valkey or Redis OSS sorted sets, because a sorted set keeps its members in order by score.
  • "Simple object cache, multi-threaded, no persistence needed" → Memcached.
  • "Redis-compatible data that must not be lost, no other database" → MemoryDB.
  • "Cache query results from an RDS database" → ElastiCache.
  • "Authenticate to the cache without a long-lived password" → ElastiCache IAM authentication.

ElastiCache security

  • Node-based clusters run in a VPC. A Lambda function needs VPC access and a security group rule to reach the cluster.
  • Encryption in transit: always on for serverless caches. For node-based clusters, set TransitEncryptionEnabled.
  • The Valkey or Redis OSS AUTH token works only with encryption in transit turned on. The client sends the token on each connection, and without TLS anyone who can see the network traffic can read it.
  • AUTH gives every client with the token full access.
  • Role-based access control (RBAC) replaces AUTH. It gives each user a password and an access string: a list of rules that sets which commands the user can run and which keys the user can use.
  • IAM authentication (Valkey 7.2 or later, Redis OSS 7.0 or later): needs TLS and an IAM policy with elasticache:Connect. The token is valid for 15 minutes. The connection closes after 12 hours unless it authenticates again.

MemoryDB

  • MemoryDB is a durable, in-memory primary database, compatible with Valkey and Redis OSS.
  • It stores every write in a Multi-AZ transactional log before it returns success to the client.
  • Performance: microsecond reads and single-digit millisecond writes.
  • Reads from primary nodes are strongly consistent. Reads from replica nodes are eventually consistent, because replicas receive writes asynchronously.
  • MemoryDB uses access control lists (ACLs) for user authentication.

ElastiCache compared with MemoryDB

  • ElastiCache: a cache in front of an existing primary database or data store.
  • MemoryDB: the primary database itself, when you want Redis-compatible data structures and durability with no separate database.
  • Older study material says that ElastiCache is never durable. Since 2026, node-based ElastiCache for Valkey 9.0 offers optional durability with a Multi-AZ transactional log: synchronous writes (designed for zero data loss) or asynchronous writes (up to 10 seconds of data loss on failure).
  • Exam questions still usually mean "ElastiCache = cache, MemoryDB = durable primary database".
