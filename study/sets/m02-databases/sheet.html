DynamoDB keys, partitions, and data serialization

Key facts

  • Each table has a primary key. It is a partition key only, or a partition key plus a sort key (composite key).
  • DynamoDB hashes the partition key value to select a physical partition. Items with the same partition key are stored together, in sort key order.
  • Items with the same partition key value form an item collection. One Query can return the whole collection.
  • Use a partition key with high cardinality (many distinct values), for example a user ID or an order ID. Requests then spread across partitions.
  • A key with few values (status, country, today's date) makes a hot partition. Requests to that partition throttle, even when the table has spare capacity.
  • Write sharding: add a random or calculated suffix to the partition key value (for example 2026-10-18#7) to spread writes for one logical key.
  • GetItem, PutItem, UpdateItem, and DeleteItem need the full primary key (partition key and, if the table has one, sort key).
  • PutItem replaces an item that has the same key. UpdateItem creates the item if it does not exist (upsert).
  • Single-table design stores many entity types in one table with generic keys, for example pk = USER#123, sk = ORDER#456.

Numbers to memorize

ItemValue

Data types and serialization

  • The low-level API sends each attribute as JSON with a data type descriptor: {"S": "Fido"}, {"N": "8"}, {"BOOL": true}, {"M": {...}}, {"L": [...]}.
  • Descriptors: S, N, B, BOOL, NULL, M, L, SS, NS, BS.
  • Numbers travel as strings ({"N": "123.45"}) to keep precision. Binary values travel as base64-encoded strings.
  • DynamoDB uses JSON only on the wire. It does not store items as JSON.
  • Higher-level SDK tools convert native objects to and from this format (marshalling):
    • JavaScript v3: DynamoDBDocumentClient (@aws-sdk/lib-dynamodb), or marshall and unmarshall (@aws-sdk/util-dynamodb).
    • Python: the boto3 resource Table object (numbers come back as decimal.Decimal), or TypeSerializer and TypeDeserializer.
    • Java: the DynamoDB Enhanced Client maps items to classes.
  • DynamoDB Streams records (and the Lambda events built from them) contain Keys, NewImage, and OldImage in this typed format. Unmarshall them in the function code.

Exam signals

  • "Lambda stream handler gets values like {"S": "abc"} instead of plain strings" → unmarshall the image (for example, unmarshall or TypeDeserializer).
  • "Write native JavaScript objects without type descriptors" → DynamoDBDocumentClient.
  • "Throttling on one key while the table uses little of its capacity" → hot partition. Use a higher-cardinality key or write sharding.
  • "Store a 2 MB document with its metadata" → put the object in Amazon S3. Store the S3 key and the metadata in DynamoDB.
  • "Get a customer and all the customer's orders in one request" → same partition key, different sort keys, and one Query.

DynamoDB capacity units, capacity modes, and throttling

Capacity unit sizes

OperationCost
Strongly consistent read1 read unit for each 4 KB
Eventually consistent read0.5 read unit for each 4 KB
Transactional read2 read units for each 4 KB
Standard write1 write unit for each 1 KB
Transactional write2 write units for each 1 KB
  • Round the item size up to the next 4 KB for reads and to the next 1 KB for writes.
  • UpdateItem uses the larger of the item size before and after the update, even when it changes only one attribute. PutItem that replaces an item also uses the larger size.
  • Example: 10 strongly consistent reads each second of 6 KB items. 6 KB rounds up to 8 KB, which is 2 units. Total: 20 RCU. Eventually consistent: 10 RCU.
  • Example: 5 writes each second of 2.5 KB items. 2.5 KB rounds up to 3 KB, which is 3 units. Total: 15 WCU.
  • Provisioned tables use read and write capacity units (RCU, WCU). On-demand tables use read and write request units with the same sizes.

Capacity modes

ItemOn-demandProvisioned
BillingPay for each requestPay for the capacity that you set, each hour, used or not
Best forUnknown or spiky traffic, new applications. AWS calls it the default and recommended mode for most workloads.Steady, predictable traffic that you can forecast
ScalingAutomaticAuto scaling (Application Auto Scaling) with a target utilization. The console suggests 70%.
Switch to the other modeTo provisioned: at any timeTo on-demand: up to 4 times in a rolling 24-hour window

Older study material says "one switch every 24 hours". That rule is out of date.

Burst, adaptive capacity, and throttling

  • Burst capacity: DynamoDB keeps up to 300 seconds (5 minutes) of unused read and write capacity for short spikes.
  • Adaptive capacity: DynamoDB gives more throughput to hot partitions automatically. It cannot go above the table's total capacity or the partition maximum.
  • ProvisionedThroughputExceededException: a provisioned table or GSI is over its capacity.
  • ThrottlingException: request rate too high (for example on-demand limits, or control plane calls too fast).
  • RequestLimitExceeded: the account throughput quota is reached.
  • The AWS SDKs retry throttled requests automatically with exponential backoff. Without an SDK, retry 5xx errors and throttling errors with backoff.
  • Use ReturnConsumedCapacity (TOTAL or INDEXES) to see the units that a request used.

Exam signals

  • "New application, traffic is unknown, least operational overhead" → on-demand mode.
  • "Steady traffic, lowest cost" → provisioned mode with auto scaling.
  • "Calculate RCU for N reads of X KB" → round X up to 4 KB steps. Halve the result for eventually consistent reads. Double it for transactional reads.
  • "ProvisionedThroughputExceededException in the logs" → retry with exponential backoff, increase capacity, or fix a hot key.

Read consistency, Query, Scan, PartiQL, and batch operations

Read consistency

  • Reads are eventually consistent by default. A read can miss a write that completed a short time before.
  • Set ConsistentRead to true for a strongly consistent read. It returns the latest data and costs twice as much.
  • Tables and LSIs support strongly consistent reads. GSIs and DynamoDB Streams support only eventually consistent reads.

Query compared with Scan

ItemQueryScan
What it readsOne item collection (one partition key value)Every item in the table or index
Required inputKeyConditionExpression with equality on the partition keyNone
CostSize of the matching itemsSize of all items read
  • Sort key conditions in a Query: =, <, <=, >, >=, BETWEEN, begins_with.
  • ScanIndexForward=false returns results in descending sort key order. The default is ascending.
  • FilterExpression runs after the read. It reduces the data returned, not the capacity used.
  • ProjectionExpression returns only the attributes that you name. It does not reduce the capacity used.
  • Each Query or Scan call returns a maximum of 1 MB. If the response has LastEvaluatedKey, send it as ExclusiveStartKey to get the next page.
  • Limit sets the maximum number of items to evaluate, not the number of matching items.
  • Parallel scan: set Segment and TotalSegments. Workers scan segments at the same time. It finishes faster but uses capacity faster.
  • Use ExpressionAttributeNames (#n) for attribute names that are reserved words, and ExpressionAttributeValues (:v) for values.

PartiQL

  • PartiQL is a SQL-compatible query language for DynamoDB: SELECT, INSERT, UPDATE, DELETE.
  • APIs: ExecuteStatement, BatchExecuteStatement, and ExecuteTransaction. You can also run it in the console, NoSQL Workbench, and the AWS CLI.
  • A SELECT without an equality (or IN) condition on the partition key in the WHERE clause can run a full table scan. An IAM policy can deny PartiQL statements that run full table scans.
  • PartiQL operations have the same availability, latency, and performance as the other DynamoDB data operations. SQL syntax does not make scans cheaper.

Batch operations

OperationLimitNotes
BatchGetItem100 items, 16 MBUnread keys come back in UnprocessedKeys
BatchWriteItem25 put or delete requests, 16 MBNo update requests. Not atomic. Unwritten items come back in UnprocessedItems.
  • Retry unprocessed items with exponential backoff. The usual cause is throttling.

Exam signals

  • "Scan with a filter is slow and expensive" → a Query on the table or on a GSI with a suitable key.
  • "Read must return the value written a moment ago" → ConsistentRead=true on the table (not on a GSI).
  • "Query returns only part of the results" → paginate with LastEvaluatedKey.
  • "Latest 10 orders for a customer" → Query with ScanIndexForward=false and Limit=10.
  • "BatchWriteItem response has UnprocessedItems" → retry those items with exponential backoff.
  • "Query DynamoDB with SQL-like syntax" → PartiQL (ExecuteStatement).

Secondary indexes: LSI and GSI

Comparison

ItemLocal secondary index (LSI)Global secondary index (GSI)
KeySame partition key as the table, different sort keyAny partition key and optional sort key
When you create itOnly when you create the tableAt any time
Number for each table520 (default quota)
Read consistencyEventually or strongly consistentEventually consistent only
ThroughputUses the table's capacityHas its own capacity (provisioned mode)
Attributes not in the projectionDynamoDB fetches them from the table, at extra cost and latencyNot available from the index
Size limit10 GB for each partition key value (item collection), table plus all LSIsNo item collection limit

Key facts

  • Projection types: KEYS_ONLY (smallest), INCLUDE (keys plus named attributes), ALL (largest).
  • Use Query or Scan on an index. GetItem and BatchGetItem do not work on an index.
  • GSI key values do not have to be unique.
  • Sparse index: an item without the index key attribute is not in the index. Use it to find a small set of items, for example open orders.
  • DynamoDB updates a GSI asynchronously. A GSI query can return data that is not current.
  • If a GSI does not have enough write capacity, DynamoDB throttles writes to the base table. Give the GSI write capacity equal to or greater than the table.
  • A write that changes an index key value uses two index writes: delete the old entry and put the new entry.
  • When an item collection reaches 10 GB on a table with an LSI, writes that make it larger fail with ItemCollectionSizeLimitExceededException.

Exam signals

  • "Query on a different attribute, table already in production" → add a GSI.
  • "Strongly consistent reads with an alternative sort key" → LSI (create with the table).
  • "Writes to the table throttle, table has spare WCU" → a GSI is short of write capacity.
  • "Find the few items that need attention without a Scan" → sparse GSI.
  • "GSI query does not return an attribute" → project the attribute into the index (INCLUDE or ALL).

Conditional writes, atomic counters, and transactions

Conditional writes

  • Add a ConditionExpression to PutItem, UpdateItem, or DeleteItem. If the condition is false, the write fails with ConditionalCheckFailedException and nothing changes.
  • Create only, no overwrite: attribute_not_exists(pk).
  • Functions: attribute_exists, attribute_not_exists, attribute_type, begins_with, contains, size.
  • Optimistic locking: keep a version number. Write with SET version = :new and the condition version = :old. On failure, read the item again and retry.
  • A failed condition still uses write capacity: the size of the existing item, minimum 1 WCU.
  • ReturnValuesOnConditionCheckFailure=ALL_OLD returns the current item with the exception. You do not need a second read.
  • ReturnValues on writes: NONE (default), ALL_OLD, UPDATED_OLD, ALL_NEW, UPDATED_NEW.

Atomic counters

  • UpdateItem with SET views = views + :one (or ADD views :one) changes the value on the server. No read is needed.
  • An atomic counter is not idempotent. A retry after a timeout can count twice. Use a conditional update when exact counts matter, for example money.

Transactions

ItemValue
APIsTransactWriteItems (Put, Update, Delete, ConditionCheck) and TransactGetItems (Get)
SizeUp to 100 items and 4 MB in one transaction
ScopeOne or more tables in the same account and the same Region
CostTwo reads or writes for each item (prepare and commit). The capacity is used also when the transaction fails.
IdempotencyClientRequestToken is valid for 10 minutes. The same token with different parameters returns IdempotentParameterMismatch.
  • All actions succeed or none succeed. Two actions cannot target the same item.
  • A failed transaction returns TransactionCanceledException. CancellationReasons lists the reason for each item, in request order.
  • A standard PutItem, UpdateItem, or DeleteItem that conflicts with a running transaction fails with TransactionConflictException.
  • You cannot run a transaction on an index.
  • Use BatchWriteItem, not transactions, for bulk loads that do not need all-or-nothing behavior.

Exam signals

  • "Two users update the same item, one update is lost" → optimistic locking with a version attribute and a condition expression.
  • "Register a user name only if it is not taken" → PutItem with attribute_not_exists.
  • "Move money between two accounts, all or nothing" → TransactWriteItems.
  • "Write the order only if the customer account is active (another item)" → ConditionCheck in a transaction.
  • "Network timeout, retry must not apply the transaction twice" → same ClientRequestToken.

DynamoDB Streams

Key facts

  • A stream records item-level changes (insert, modify, remove) in near real time. DynamoDB keeps each record for 24 hours.
  • Each stream record appears exactly one time in the stream. Records for one item appear in the order of the changes.
  • Ordering is for each item (each primary key), not for the whole table.
  • A PutItem or UpdateItem that does not change data writes no stream record.
  • You cannot edit StreamViewType. Disable the stream and enable a new one. The new stream has a new ARN.
  • Design for a maximum of two processes that read the same shard at the same time.
  • A transaction writes one stream record for each changed item. Consumers must not expect transaction atomicity in the stream.
  • For longer retention, use Amazon Kinesis Data Streams for DynamoDB (a separate feature).

StreamViewType

ValueContent of each record
KEYS_ONLYKey attributes only
NEW_IMAGEThe item after the change
OLD_IMAGEThe item before the change
NEW_AND_OLD_IMAGESBoth images

Lambda as the consumer

  • A Lambda event source mapping polls the stream. By default, one function instance processes one shard, in order.
  • The execution role needs dynamodb:DescribeStream, dynamodb:GetRecords, dynamodb:GetShardIterator, and dynamodb:ListStreams. The AWSLambdaDynamoDBExecutionRole managed policy includes them.
  • ParallelizationFactor (up to 10) processes one shard with more instances and keeps the order of changes for each item.
  • Use filter criteria on the event source mapping to invoke the function only for matching records, for example eventName INSERT.
  • Error controls (bisect batch, retries, on-failure destination, partial batch response) are in the Module 1 sheet.

Exam signals

  • "Send an email when a new item is added, with the item data" → stream with NEW_IMAGE and a Lambda trigger with an INSERT filter.
  • "Audit log must show old and new values" → NEW_AND_OLD_IMAGES.
  • "Consumer was down for two days and lost changes" → 24-hour retention. Use Kinesis Data Streams for DynamoDB for longer retention.

References: DynamoDB Streams, Quotas (readers for each shard). Lab: Lab 2.6 Streams.

TTL, backups, and global tables

Time to live (TTL)

  • Enable TTL on the table and name one attribute. Store the expiry time as a Number in Unix epoch time, in seconds.
  • The TTL process ignores items where the attribute is not a Number. A value in milliseconds is far in the future, so the item does not expire.
  • DynamoDB deletes expired items typically within a few days after expiry. Older material says 48 hours.
  • TTL deletes do not use write capacity.
  • Expired items that are not deleted yet still appear in reads. Use a filter expression to remove them from Query and Scan results.
  • A TTL delete goes to DynamoDB Streams as a service delete. The record has userIdentity type Service and principal dynamodb.amazonaws.com.
  • TTL deletes also remove the item from LSIs and GSIs.

Backups

ItemPoint-in-time recovery (PITR)On-demand backup
What it isContinuous backups. Restore to any second in the recovery period.A full backup that you start
RetentionRecovery period of 1 to 35 days (you set it)Until you delete it
Restore targetAlways a new tableA new table
  • The latest restorable time is typically about 5 minutes before the current time.
  • Use PITR for protection from accidental writes or deletes. Use on-demand backups for long-term retention.

Global tables

  • A global table has replica tables in two or more Regions. Applications read and write in any replica Region.
  • Default mode: multi-Region eventual consistency (MREC). Replication is asynchronous, typically within a second.
  • MREC conflict rule: last writer wins, for each item.
  • Multi-Region strong consistency (MRSC) replicates each write synchronously and gives an RPO of zero. It needs exactly three Regions: three replicas, or two replicas and one witness.
  • MRSC does not support TTL, LSIs, or transactions.
  • In MREC, transactions are atomic only in the Region where they run. Other Regions can see part of a transaction while it replicates.

Exam signals

  • "Delete session items after 24 hours at no cost" → TTL with an epoch-seconds Number attribute.
  • "Expired items still appear in queries" → expected. Filter on the TTL attribute.
  • "Restore the table to its state from 10 minutes before a bad deploy" → PITR (to a new table).
  • "Low-latency reads and writes for users in several Regions" → global tables.

References: TTL, PITR (recovery period), Global tables: how they work. Lab: Lab 2.7 TTL and capacity.

DynamoDB security: IAM, encryption, and network access

Access control

  • Applications get access through IAM roles, for example a Lambda execution role. Give only the actions and tables that the code needs.
  • Fine-grained access control uses IAM condition keys:
    • dynamodb:LeadingKeys: limits access to items whose partition key matches a value, for example ${cognito-identity.amazonaws.com:sub}. Use it with ForAllValues:StringEquals.
    • dynamodb:Attributes: limits the attributes that a request can access.
    • dynamodb:Select and dynamodb:ReturnValues: stop requests that return all attributes.
  • Do not allow Scan in a per-user policy. A Scan returns all items, whatever the leading key.
  • Policies that use policy variables need "Version": "2012-10-17".
  • Tables also support resource-based policies (maximum 20 KB), for example for cross-account access.

Encryption

Key typeWhere the key isCost
AWS owned key (default)Owned by DynamoDBNo extra charge
AWS managed key (aws/dynamodb)In your account, managed by AWS KMSAWS KMS charges
Customer managed keyIn your account. You control the key policy and rotation.AWS KMS charges
  • DynamoDB always encrypts data at rest: tables, indexes, streams, backups, and global tables. You cannot turn it off.
  • You can change the key type of an existing table.
  • DynamoDB uses HTTPS endpoints. For client-side encryption of attribute values, use the AWS Database Encryption SDK.

Network access

  • A gateway VPC endpoint for DynamoDB lets resources in private subnets reach DynamoDB without a NAT gateway or internet access.

Exam signals

  • "Each mobile user can read and write only their own items" → IAM policy with dynamodb:LeadingKeys and the Cognito identity ID.
  • "Hide some attributes from a role" → dynamodb:Attributes with dynamodb:Select set to SPECIFIC_ATTRIBUTES.
  • "Audit and control the encryption key, rotate it yourself" → customer managed KMS key.
  • "Lambda in a private subnet must reach DynamoDB with no internet path" → DynamoDB gateway endpoint.

References: Fine-grained access control with IAM conditions, Encryption at rest, Constraints (resource policy size, key changes). Lab: Lab 2.1 Table basics.

DynamoDB Accelerator (DAX)

Key facts

  • DAX is an in-memory cache for DynamoDB. It reduces eventually consistent read latency from milliseconds to microseconds.
  • DAX is API-compatible with DynamoDB. The application uses the DAX client, with few code changes.
  • DAX runs in a VPC. Clients must be in the VPC. Control access with security groups.
  • A cluster has one primary node and 0 to 10 read replicas. AWS recommends at least three nodes in different Availability Zones.
  • Item cache: results of GetItem and BatchGetItem. Default TTL: 5 minutes.
  • Query cache: results of Query and Scan, stored by request parameters. It has its own TTL.
  • Writes through DAX are write-through: DAX writes to DynamoDB first, then updates the item cache.
  • Writes do not update or clear the query cache. A cached Query result can be stale until its TTL ends.
  • Writes made directly to DynamoDB (not through DAX) do not update the DAX cache.
  • DAX passes strongly consistent reads and TransactGetItems to DynamoDB and does not cache the results.
  • DAX also caches "not found" results (negative caching).

When not to use DAX

  • The application needs strongly consistent reads.
  • The application is write-heavy, or has few repeated reads.
  • The application does not need microsecond reads.

Exam signals

  • "Microsecond reads from DynamoDB, fewest code changes" → DAX.
  • "Read-heavy table with hot keys, reduce RCU cost" → DAX.
  • "Application needs strongly consistent reads and uses DAX" → the reads go to DynamoDB. DAX gives no benefit for them.
  • "New item does not appear in a repeated Query through DAX" → query cache TTL.
  • "Cache in front of RDS or other sources" → ElastiCache, not DAX. DAX works only with DynamoDB.

References: DAX overview and use cases, DAX: how it works (cache TTL), DAX consistency models. Lab: Lab 2.7 (DAX theory section).

RDS and Aurora: availability, replicas, and backups

Multi-AZ compared with read replicas (RDS)

ItemMulti-AZ DB instance (standby)Read replica
PurposeHigh availability and failoverRead scaling, reporting, disaster recovery
ReplicationSynchronousAsynchronous
Serves readsNoYes
NumberOne standbyUp to 15 for each primary (default quota)
Other RegionNoYes (cross-Region replica)
FailoverAutomatic. Typically 60 to 120 seconds.Manual: promote the replica to a standalone DB instance
  • On failover, RDS changes the DNS record of the endpoint to the standby. Applications reconnect to the same endpoint name. For Java, set the JVM DNS TTL to 60 seconds or less.
  • A Multi-AZ DB cluster deployment is different. It has two readable standby instances.
  • RDS does not add or remove read replicas automatically. Applications must send reads to the replica endpoints.
  • Older study material says 5 read replicas. The current quota is 15.

Backups

  • Automated backups: retention of 0 to 35 days. 0 turns off automated backups and point-in-time restore.
  • Default retention: 1 day when you create the instance with the API or CLI, 7 days in the console.
  • Point-in-time restore always creates a new DB instance. RDS uploads transaction logs to Amazon S3 every 5 minutes.
  • Manual snapshots stay until you delete them.

Aurora

  • Aurora storage keeps six copies of the data across three Availability Zones.
  • A cluster has one writer and up to 15 Aurora Replicas. The replicas share the cluster storage.
  • Endpoints:
    • Cluster (writer) endpoint: the current primary. It follows failover.
    • Reader endpoint: balances connections across the Aurora Replicas.
    • Custom endpoint: a group of instances that you choose.
    • Instance endpoint: one instance, for diagnosis or tuning.

Aurora Serverless v2

  • Capacity unit: ACU. One ACU is about 2 GiB of memory with matching CPU and network.
  • Range: 0 to 256 ACUs, depending on the engine version. Scaling steps can be as small as 0.5 ACU.
  • A minimum of 0 ACUs turns on automatic pause and resume on supported versions.
  • A cluster can mix Serverless v2 and provisioned instances. Readers in promotion tiers 0 and 1 scale with the writer.

Exam signals

  • "Survive an Availability Zone failure with automatic failover" → Multi-AZ.
  • "Reporting queries slow down the production database" → read replica (or Aurora reader endpoint).
  • "Unpredictable or intermittent database load, pay for use" → Aurora Serverless v2.
  • "Restore the database to 3:15 PM yesterday" → point-in-time restore to a new instance.

References: Multi-AZ DB instance, Multi-AZ failover (time, DNS), RDS quotas (read replicas), Backup retention, Aurora endpoints, Aurora Serverless v2 capacity. Labs: Lab 2.8 RDS MySQL, Lab 2.9 Aurora Serverless.

Secure connections to RDS and Aurora

Credentials

  • Do not put database passwords in code, templates, or plain environment variables. Store them in AWS Secrets Manager and read them at run time with the IAM role.
  • Secrets Manager can rotate database credentials automatically. RDS can also manage the master user password in Secrets Manager for you.

IAM database authentication

  • Engines: MariaDB, MySQL, PostgreSQL (RDS and Aurora).
  • The application gets an authentication token (signed with SigV4) and uses it as the password. A token is valid for 15 minutes.
  • The IAM policy allows rds-db:connect for the database user.
  • Traffic uses SSL/TLS. No password is stored in the database or the application.

RDS Proxy

  • Pools and shares database connections. Use it when many Lambda functions or short connections open too many connections.
  • Keeps application connections during a failover and connects to the standby.
  • Clients can authenticate with IAM. The proxy connects to the database with Secrets Manager credentials or IAM database authentication.
  • The proxy must be in the same VPC as the database. It cannot be publicly accessible.

RDS Data API (Aurora)

  • An HTTPS endpoint for SQL statements. The caller needs no persistent connection, no database driver, and no VPC configuration.
  • The call gives the cluster ARN and the ARN of a Secrets Manager secret with the database credentials.
  • Data API runs queries on the writer instance only. The response size limit is 1 MiB. It does not support T DB instance classes.

Encryption at rest

  • Turn on encryption (AWS KMS) when you create the DB instance. You cannot encrypt an existing unencrypted instance in place.
  • To encrypt an existing database: take a snapshot, copy the snapshot with encryption turned on, and restore a new instance from the copy.
  • A blue/green deployment can also create an encrypted green environment from an unencrypted DB instance.
  • You cannot turn off encryption. Replicas and snapshots of an encrypted instance are encrypted.
  • You cannot share a snapshot that uses the AWS managed key. Use a customer managed key to share encrypted snapshots with another account.
  • To copy an encrypted snapshot to another Region, give a KMS key in the destination Region.

Exam signals

  • "No database password in the application, short-lived credentials" → IAM database authentication.
  • "Store and rotate the database password automatically" → Secrets Manager.
  • "Lambda functions exhaust database connections" → RDS Proxy.
  • "Query Aurora from Lambda without VPC configuration or connection management" → RDS Data API.
  • "Existing database must be encrypted" → snapshot, encrypted copy, restore.

References: IAM database authentication (token lifetime), RDS Proxy, RDS Data API, Data API limitations, Encrypting RDS resources. Labs: Lab 2.8 RDS MySQL, Lab 2.9 Aurora Serverless.

Caching strategies: lazy loading, write-through, and TTL

Comparison

ItemLazy loading (cache-aside)Write-through
How it worksRead the cache. On a miss, read the database, then write the result to the cache.Each database write also writes the cache.
AdvantagesOnly requested data is in the cache. A failed node is not fatal: the new node fills on misses.Data in the cache is never stale.
DisadvantagesCache miss penalty: three trips (cache, database, cache write). Data can become stale.Missing data on a new node until the next write. Cache churn: most written data is never read. Each write has extra latency.

Key facts

  • TTL sets the number of seconds until a key expires. A read of an expired key is a miss, so the application loads fresh data.
  • Add a TTL to lazy loading to limit stale data. Add a TTL to write-through to remove data that nobody reads.
  • Use lazy loading and write-through together with a TTL to get the advantages of both.
  • Read-through: the cache loads data from the database on a miss, not the application. DAX works this way for eventually consistent reads.
  • DAX is write-through for writes that you send through DAX. Writing directly to DynamoDB is write-around: it keeps write latency low but the cache can be stale.
  • Common uses: database query results, session state, leaderboards (sorted sets), and rate-limit counters.

Exam signals

  • "Cache only the data that users read" → lazy loading.
  • "Cached data must never be stale after an update" → write-through.
  • "Users see old prices for hours" → add or reduce the TTL, or add write-through.
  • "After a cache node is replaced, every request is slow for a while" → lazy loading fills the new node on misses (expected).

ElastiCache security

  • Node-based clusters run in a VPC. A Lambda function needs VPC access and a security group rule to reach the cluster.
  • Encryption in transit: always on for serverless caches. For node-based clusters, set TransitEncryptionEnabled.
  • The Valkey or Redis OSS AUTH token works only with encryption in transit turned on. Role-based access control (RBAC) replaces AUTH, with users and access strings.
  • IAM authentication (Valkey 7.2 or later, Redis OSS 7.0 or later): needs TLS and an IAM policy with elasticache:Connect. The token is valid for 15 minutes. The connection closes after 12 hours unless it authenticates again.

MemoryDB

  • MemoryDB is a durable, in-memory primary database, compatible with Valkey and Redis OSS.
  • It stores every write in a Multi-AZ transactional log before it returns success to the client.
  • Performance: microsecond reads and single-digit millisecond writes.
  • Reads from primary nodes are strongly consistent. Reads from replica nodes are eventually consistent.
  • MemoryDB uses access control lists (ACLs) for user authentication.

ElastiCache compared with MemoryDB

  • ElastiCache: a cache in front of an existing primary database or data store.
  • MemoryDB: the primary database itself, when you want Redis-compatible data structures and durability with no separate database.
  • Older study material says that ElastiCache is never durable. Since 2026, node-based ElastiCache for Valkey 9.0 offers optional durability with a Multi-AZ transactional log: synchronous writes (designed for zero data loss) or asynchronous writes (up to 10 seconds of data loss on failure). Exam questions still usually mean "ElastiCache = cache, MemoryDB = durable primary database".

Exam signals

  • "Leaderboard with ranking" → Valkey or Redis OSS sorted sets.
  • "Simple object cache, multi-threaded, no persistence needed" → Memcached.
  • "Redis-compatible data that must not be lost, no other database" → MemoryDB.
  • "Cache query results from an RDS database" → ElastiCache.
  • "Authenticate to the cache without a long-lived password" → ElastiCache IAM authentication.
