Secrets Manager: secrets, versions, and staging labels

Key facts

  • A secret holds a value in SecretString (usually JSON) or SecretBinary. Most secrets use SecretString.
  • Secrets Manager always encrypts the secret value with AWS KMS. The default key is the AWS managed key aws/secretsmanager. You can choose a customer managed key.
  • Each change to the value (PutSecretValue or UpdateSecret) creates a new version.
  • A staging label is a name that is attached to one version, for example AWSCURRENT. Applications ask for a label, not a version ID. When a label moves to a new version, the application gets the new value with no code change. GetSecretValue with no version returns the version with AWSCURRENT.
  • You cannot delete one version directly. Remove all its labels with UpdateSecretVersionStage. Secrets Manager then removes it in the background.
  • DeleteSecret does not delete the secret at once. It schedules deletion after a recovery window, so you can undo a mistake. During the window, GetSecretValue fails with InvalidRequestException, so applications that use the secret stop working. RestoreSecret cancels the deletion and keeps the same ARN.
  • ForceDeleteWithoutRecovery is a DeleteSecret option that deletes the secret with no recovery window. You cannot recover it. Use it with caution, for example for test secrets. Deletion is still a background task, so a new secret with the same name may need a retry.
  • You can replicate a secret to other Regions with ReplicateSecretToRegions. Secrets Manager keeps the replicas in sync with the primary secret. An application then reads the replica in its own Region, which gives low latency and keeps working if the primary Region fails.

Staging labels

LabelMeaning
AWSCURRENTThe active value. Applications read this label.
AWSPENDINGThe new value during a rotation, before the rotation completes.
AWSPREVIOUSThe last known good value. Secrets Manager adds it to the old version when AWSCURRENT moves.
Custom labelsLabels that you add. Maximum 20 labels across all versions of a secret. Example: a test fleet reads a CANARY label on a new version while production still reads AWSCURRENT.

Exam signals

  • "Read the value that was active before the last rotation" → GetSecretValue with VersionStage=AWSPREVIOUS.
  • "A secret was deleted by mistake yesterday" → RestoreSecret during the recovery window.
  • "Application in a second Region must read the same secret with low latency" → replicate the secret to that Region.
  • "Store a 100 KB certificate bundle as one secret" → too large. The limit is 64 KB.

Secrets Manager rotation

Key facts

  • Rotation changes the secret value and the credential in the database or service at the same time. Two forms of rotation exist. Managed rotation: the service that owns the secret (for example, Amazon RDS) rotates it with no Lambda function. Rotation by Lambda function: a Lambda function rotates the secret. Use managed rotation when the service offers it, because you have no function to write or maintain.
  • Secrets Manager gives rotation function templates for Amazon RDS, Amazon Aurora, Amazon Redshift, and Amazon DocumentDB. Use the generic template for other secrets.
  • The console can create the rotation function and its execution role for you.
  • The rotation function must reach both Secrets Manager and the database. A Lambda function in a VPC can reach only resources in that VPC, unless the VPC gives it internet access. The Secrets Manager API is a public endpoint. Without a Secrets Manager VPC endpoint or a NAT gateway, the function waits for the API until the timeout, and the rotation fails. It also needs a network path to the database, so you cannot simply move it out of the VPC.
  • "Rotate immediately when the secret is stored" starts a rotation when you save the configuration. If you clear it, the first rotation follows the schedule.

The four steps of a rotation function

  1. createSecret: make a new value and store it as a new version with AWSPENDING.
  2. setSecret: change the credential in the database or service.
  3. testSecret: use the AWSPENDING value to connect. If the test fails, the rotation stops before finishSecret, so AWSCURRENT does not move to a value that does not work.
  4. finishSecret: move AWSCURRENT to the new version. Secrets Manager adds AWSPREVIOUS to the old version.

Rotation strategies (database secrets)

StrategyHow it worksUse when
Single userChanges the password of one user. Open connections stay open.Most use cases. setSecret changes the password in the database before finishSecret moves AWSCURRENT. In that short time, an application that reads AWSCURRENT gets the old password and its login fails, so add retries.

  • "Rotate RDS credentials automatically with the least effort" → Secrets Manager with the RDS rotation template or managed rotation.
  • "Rotation fails with a timeout; the function is in a private subnet" → add a Secrets Manager VPC endpoint or a NAT gateway.
  • "Users must not see failed logins during rotation" → alternating users strategy, because the credentials that applications read stay valid while the other user's password changes.
  • "Which step changes the database password" → setSecret.

Reading secrets: caching, Lambda, and cross-account access

Key facts

  • To read a secret, a principal needs secretsmanager:GetSecretValue. If a customer managed key encrypts the secret, the principal also needs kms:Decrypt on that key.
  • Cache secrets in the application. Each GetSecretValue call costs money and counts toward the request rate.
  • Secrets Manager has client-side caching components for Java, Python, .NET, Go, and Rust. Use them in code that runs outside Lambda, or in Lambda without the extension.
  • The AWS Parameters and Secrets Lambda Extension is a Lambda layer. It runs a small HTTP server inside the execution environment. The function code sends an HTTP GET to localhost:2773. The extension returns the cached value, or calls Secrets Manager or Parameter Store when the value is not in the cache. It works with every runtime and needs no SDK code for the call.
  • A cache keeps a value until its TTL (time to live) ends. After a rotation, the cache can still return the old password, and logins fail until the TTL ends. Lower the cache TTL, or request versionStage=AWSCURRENT again after an authentication error.

Lambda environment variables and KMS

  • AWS recommends Secrets Manager, not environment variables, for database credentials. Any user who can view the function configuration and decrypt with its key can read an environment variable. Environment variables also have no rotation.
  • Lambda always encrypts environment variables at rest. By default it uses an AWS managed key, with no setup and no charge.
  • You can choose a customer managed key for encryption at rest. Then only users with kms:Decrypt on that key can view or manage the variables in the console.
  • Users who can view the function configuration and can decrypt with the key can read the values. To hide them from a user, deny kms:Decrypt on the key.
  • Encryption helpers for encryption in transit are a console option. They encrypt a value on the client side with a customer managed key before Lambda receives it. Lambda then stores and shows only the ciphertext, so the plaintext does not appear in the console or in API responses. The function code must decrypt it, and the execution role needs kms:Decrypt.

Cross-account access (all three are necessary)

  1. Attach a resource-based policy to the secret that allows the other account's role.
  2. Encrypt the secret with a customer managed key. Add the other account's role to the key policy (kms:Decrypt). You cannot use aws/secretsmanager across accounts, because you cannot change the key policy of an AWS managed key to allow another account.
  3. Attach an IAM policy to the role in the other account. Allow secretsmanager:GetSecretValue on the secret and kms:Decrypt on the key.

Exam signals

  • "Lambda reads a secret on every invoke; reduce cost and latency with no SDK changes" → Parameters and Secrets Lambda Extension.
  • "Cross-account read fails with a KMS error; the secret uses the default key" → re-encrypt the secret with a customer managed key and update its key policy.
  • "Function uses an old password after rotation" → cache is stale. Shorten the TTL or refresh on an authentication error.
  • "Database password is in an environment variable" → move it to Secrets Manager, because users who can view the function configuration can read the variable, and Secrets Manager can rotate the password.
  • "Environment variable must stay encrypted until the code uses it, even in the console" → encryption helpers with a customer managed key, and decrypt in code.

Decision rules

  • Choose Secrets Manager for database credentials that must rotate. It is the only one of the three with built-in rotation.
  • Choose Parameter Store SecureString for a static secret at the lowest cost. A Standard parameter has no storage charge and is encrypted with KMS. Secrets Manager charges for each secret each month.
  • Choose Parameter Store String in a hierarchy for plain configuration values, with one path for each environment (for example /myapp/prod/). One GetParametersByPath call loads the whole path.
  • Choose AppConfig for feature flags, or for configuration that must roll out slowly and roll back on an alarm. Parameter Store and Secrets Manager give a new value to all readers at once, with no gradual rollout and no automatic rollback.

Exam signals

  • "Automatic rotation" or "RDS credentials" → Secrets Manager.
  • "MOST cost-effective place for an API key that never changes" → Parameter Store SecureString.
  • "Turn on a feature for 10 percent of users first" → AppConfig feature flag with a gradual deployment strategy.

Parameter policies (Advanced tier only)

  • Expiration: Parameter Store deletes the parameter at a date and time.
  • ExpirationNotification: sends an Amazon EventBridge event before the expiration, so the team can replace the value before Parameter Store deletes it.
  • NoChangeNotification: sends an EventBridge event if nobody changes the parameter for a time. Use it as a reminder to change a password or token that must not stay the same too long.
  • Maximum 10 policies for each parameter.

Key facts

  • A standard SecureString uses KMS Encrypt directly. A standard value (maximum 4 KB) fits in the 4,096-byte limit of Encrypt. An advanced value can be 8 KB, which is larger than that limit. An advanced SecureString uses envelope encryption with the AWS Encryption SDK (see "Envelope encryption" below).
  • To write a standard SecureString, a principal needs kms:Encrypt. For an advanced one, kms:GenerateDataKey. To read either, kms:Decrypt.
  • Parameter Store sends the encryption context PARAMETER_ARN (the ARN of the parameter) to KMS. Many parameters can share one KMS key. A kms:EncryptionContext:PARAMETER_ARN condition in an IAM policy or key policy lets a role decrypt only one parameter with that key.

Exam signals

  • "Parameter must delete itself after 30 days" → Advanced tier with an Expiration policy.
  • "Value is 6 KB" → Advanced tier (Standard maximum is 4 KB).
  • "Error: policies are only supported on Advanced tier" → change the parameter to Advanced.
  • "Stop paying for an Advanced parameter" → delete it and create a Standard parameter, because you cannot change an Advanced parameter back to Standard.

Parameter Store: hierarchies, versions, decryption, and throughput

Key facts

  • Names with forward slashes make a hierarchy, for example /myapp/prod/db/host. A hierarchy can have a maximum of 15 levels.
  • GetParametersByPath returns all parameters under a path. Add Recursive to include all lower levels.
  • GetParameters returns a maximum of 10 parameters by name in one call.
  • Use IAM policies on paths, for example parameter/myapp/prod/*, to separate environments. A role for the test environment then cannot read production values.
  • GetParameter does not decrypt a SecureString by default. Without WithDecryption, the call returns the encrypted value as a string of ciphertext. Set WithDecryption to true. The caller also needs kms:Decrypt on the key.
  • Each PutParameter with Overwrite creates a new numeric version. Read an old version with name:version.
  • Labels are names for versions. Read a label with name:label. Move a label to roll back without code changes.
  • AllowedPattern is a regular expression. Parameter Store rejects values that do not match.

Throughput (for each account and Region)

APIDefault throughputHigher throughput
GetParameter, GetParameters, GetParametersByPath40 TPS shared by the three APIsGetParameter 10,000 TPS, GetParameters 1,000 TPS, GetParametersByPath 100 TPS

TPS means transactions (API calls) per second. The limit applies to all calls from all applications in the account and Region together. For example, 40 instances that each call GetParameter one time each second use all of the default 40 TPS.

  • Higher throughput is a setting for the account and Region. It is separate from the parameter tier. It has a charge for each API interaction. One interaction is one parameter in a response, so a GetParameters call that returns 10 parameters counts as 10 interactions.
  • Too many requests cause ThrottlingException (Rate exceeded). First cache the values, then turn on higher throughput if necessary.

Exam signals

  • "Load all configuration for one environment at startup in few calls" → GetParametersByPath with Recursive.
  • "GetParameter returns an encrypted string" → add WithDecryption.
  • "AccessDeniedException from KMS on GetParameter" → the role lacks kms:Decrypt on the customer managed key.
  • "ThrottlingException when many instances start at the same time" → cache values. If that is not enough, turn on higher throughput.

References: Parameter hierarchies, GetParameters (10 names), Parameter Store throughput. Lab: Lab 7.2 Parameter Store.

AppConfig: resources, profiles, and retrieval

Resources

ResourcePurpose
ApplicationA namespace for one application, for example "checkout-service"
EnvironmentA deployment target, for example "beta" or "prod". You attach CloudWatch alarms here for rollback.
Configuration profileTells AppConfig where the configuration data is stored, which type it is (feature flags or freeform), and which validators check it
Deployment strategyTells AppConfig how fast to give the new data to targets, and how long to watch alarms after that (the bake time)
DeploymentOne release of a configuration version to an environment with a strategy

Profile types and sources

  • Feature flags: on and off switches (with optional attributes) that turn features on or off with no code deployment. They are stored in the AppConfig hosted configuration store. AppConfig validates the flag format automatically.
  • Freeform: any configuration data, for example JSON, YAML, or text. Choose it for configuration that is not a flag, or when the data must stay in another service. The data can be in the hosted store, Amazon S3, AWS CodePipeline, Secrets Manager, Parameter Store, or SSM documents.
  • A profile can have up to two validators: a JSON Schema (freeform only) or a Lambda function.
  • AppConfig runs validators when you call StartDeployment. Invalid data does not deploy.

Retrieval

  • Without an agent, call StartConfigurationSession one time to get a token. Then call GetLatestConfiguration with that token. Each response gives a new token, and you must send the new token in the next call. The body is empty when the data has not changed, so the client keeps the copy that it already has.
  • GetConfiguration is the old API and is deprecated.
  • For Lambda, add the AWS AppConfig Agent Lambda extension as a layer. The function calls localhost:2772. The extension caches data and polls in the background.
  • The extension polls every 45 seconds by default (AWS_APPCONFIG_EXTENSION_POLL_INTERVAL_SECONDS).

Exam signals

  • "Read feature flags in Lambda with the least code and fewer API calls" → AppConfig Agent Lambda extension.
  • "Reject a configuration that does not match a schema before it reaches production" → JSON Schema validator on the profile.
  • "Custom validation logic" → Lambda validator, because a JSON Schema checks only the structure and types of the data. A Lambda function can run any check in code.

References: Configuration profiles, Validators, AppConfig Lambda extension settings, Retrieving configuration data (session tokens). Lab: Lab 7.3 AppConfig feature flags.

AppConfig: deployment strategies and rollback

Key facts

  • A strategy has a growth type (Linear or Exponential), a step percentage (growth factor), a deployment time, and a bake time.
  • Linear adds the same percentage of targets at each step, for example 20, 40, 60, 80, 100 percent. Exponential doubles the percentage at each step, for example 2, 4, 8, 16 percent. Exponential exposes very few targets first, then finishes quickly.
  • Deployment time is the total time in which AppConfig gives the data to all targets, in steps. It is not a timeout.
  • Bake time: after the data reaches 100 percent of targets, AppConfig watches CloudWatch alarms for this time. If an alarm goes off, AppConfig rolls back.
  • AppConfig also rolls back if an alarm goes into ALARM or INSUFFICIENT_DATA during the rollout. You add the alarms to the environment. An alarm with missing metric data can therefore cause a rollback.
  • StopDeployment rolls back a deployment that is still in progress.
  • Automatic rollback needs an IAM role that lets AppConfig read the alarms (cloudwatch:DescribeAlarms). Without the role, AppConfig cannot read the alarm state and does not roll back.
  • You can deploy only one configuration at a time to an environment. A second deployment to that environment must wait until the first deployment completes or you stop it. You can deploy to different environments at the same time.

Predefined strategies

StrategyRolloutBake time
AppConfig.Linear20PercentEvery6Minutes20 percent every 6 minutes, 30 minutes in total. AWS recommended for production.30 minutes

Exam signals

  • "Roll back a bad configuration automatically when the error rate rises" → CloudWatch alarm on the environment plus a strategy with bake time.
  • "Release the change at once in a test environment" → AppConfig.AllAtOnce.
  • "Gradual configuration change with no new code deployment" → AppConfig, not a Lambda alias or CodeDeploy. A Lambda alias and CodeDeploy shift traffic between versions of code. AppConfig changes only the configuration data that running code reads.

Choose a customer managed key when you must control the key policy, share the key with another account, call the key from your own code, or set the rotation. Choose an AWS managed or AWS owned key when the service only needs to encrypt your data at rest and you do not need that control.

Key facts

  • Symmetric keys (SYMMETRIC_DEFAULT, AES-256-GCM) use one secret key that never leaves KMS unencrypted. Every encrypt and decrypt is a call to KMS. Most AWS services use them. Choose a symmetric key unless you have a reason for an asymmetric key.
  • Asymmetric keys (RSA, ECC) have a private key that stays in KMS and a public key that you can download. They sign and verify, or encrypt with the public key. Choose one when a party outside AWS must encrypt data or verify a signature without a call to KMS.
  • An alias is a name for a key, for example alias/orders. UpdateAlias points the alias to a different key. Code that uses the alias does not change.
  • The alias/aws/ prefix is reserved for AWS managed keys.
  • Multi-Region keys have the same key ID (prefix mrk-) and key material in each Region. Key material is the secret value that a key uses to encrypt. Data encrypted in one Region decrypts in another with no cross-Region call. Use them for client-side encrypted data that moves between Regions, for example in a DynamoDB global table or for disaster recovery.
  • Each multi-Region key has its own key policy, grants, and aliases. You cannot convert a single-Region key to a multi-Region key. To change, create a new multi-Region key and encrypt the data again with it.

Exam signals

  • "Full control of the key policy" or "share with another account" → customer managed key.
  • "Least operational overhead, no key management, no audit need" → AWS owned or AWS managed key, because AWS creates, rotates, and controls these keys, and they have no monthly fee.
  • "Client-side encrypted data must decrypt in a second Region during a Regional outage" → multi-Region key.
  • "Change the key without changing application code" → use an alias, then UpdateAlias.

Envelope encryption, data keys, and encryption context

Envelope encryption steps

Envelope encryption uses two keys. A data key encrypts the data in your application, outside KMS. The KMS key encrypts only the small data key. KMS Encrypt accepts a maximum of 4,096 bytes, and each call goes over the network. With a data key, a large file needs only one KMS call, and the bulk encryption runs locally.

  1. Call GenerateDataKey with a symmetric KMS key. KMS returns Plaintext (the data key) and CiphertextBlob (the same data key, encrypted).
  2. Encrypt the data locally with the plaintext data key.
  3. Remove the plaintext data key from memory.
  4. Store the encrypted data key with the encrypted data.
  5. To decrypt, send the encrypted data key to Decrypt. Use the returned plaintext key to decrypt the data locally.

API comparison

APIUse
EncryptEncrypts up to 4,096 bytes directly with the KMS key. For small secrets only.
GenerateDataKeyReturns a plaintext and an encrypted data key. Use it to encrypt data now.
GenerateDataKeyWithoutPlaintextReturns only the encrypted data key. Use it when a different component encrypts later.
DecryptFor symmetric ciphertext, you do not need to give the key ID. The ciphertext contains it.
ReEncryptDecrypts and encrypts again under a different key, inside KMS. The plaintext never leaves KMS. Use it to move ciphertext (for example, encrypted data keys) to a new KMS key.

Encryption context

  • A set of non-secret key-value pairs that describe the data, for example {"tenant":"42"}. KMS uses it as additional authenticated data: it is not encrypted, but it is cryptographically bound to the ciphertext.
  • Decrypt must use the same context (exact, case-sensitive match). If not, KMS returns InvalidCiphertextException. A request that sends {"tenant":"7"} cannot decrypt data that was encrypted with {"tenant":"42"}. A ciphertext that was moved to a different record also fails to decrypt, when the context names the record.
  • CloudTrail logs the context in plaintext. Do not put secrets in it.
  • Use the kms:EncryptionContext:<key> condition to allow decryption only for one tenant or one resource.

Request quotas

  • Cryptographic operations on symmetric keys share one quota for each account and Region. The default depends on the Region: 100,000 requests per second in us-east-1, us-west-2, and eu-west-1; 20,000 in us-east-2, eu-central-1, ap-northeast-1, and some other Regions; 10,000 in all other Regions.
  • Calls that AWS services make for you (for example, S3 SSE-KMS) count toward your quota. Too many calls cause ThrottlingException.
  • Fixes: reuse data keys (AWS Encryption SDK data key caching), use S3 Bucket Keys, or request a quota increase. Data key caching uses one data key for many messages, so the application calls GenerateDataKey less often.
  • Without a Bucket Key, S3 calls KMS for each request on an encrypted object. With a Bucket Key, S3 gets a short-lived bucket-level key from KMS and uses it to create data keys for new objects. S3 then calls KMS much less often. S3 Bucket Keys can reduce KMS request costs by up to 99 percent.

Exam signals

  • "Encrypt a 5 MB file with KMS" → envelope encryption with GenerateDataKey, not Encrypt.
  • "Decrypt fails with InvalidCiphertextException" → wrong or missing encryption context, or the wrong ciphertext.
  • "ThrottlingException from KMS during S3 uploads" → S3 Bucket Keys, or a quota increase.
  • "A service must prepare keys now, and another service encrypts later" → GenerateDataKeyWithoutPlaintext, because the first service never receives the plaintext data key. The second service calls Decrypt to get it.

References: Encrypt (4,096 bytes), GenerateDataKeyWithoutPlaintext, KMS request quotas, S3 Bucket Keys, Encryption context (additional authenticated data), Data key caching. Lab: Lab 7.4 KMS envelope encryption.

Key rotation, disabling, and deletion

Rotation

KeyAutomatic rotation
Customer managed, symmetric, key material from KMSOptional. Off by default. EnableKeyRotation. Period 90 to 2,560 days, default 365 days. DisableKeyRotation turns it off. Older study material and the module README say rotation is annual only. The custom period (90 to 2,560 days) and on-demand rotation were added in April 2024.
AWS managed keyEvery year. You cannot change it.
Asymmetric, HMAC, or custom key store keysNot supported. Rotate manually: create a new key and move the alias.
Imported key material (symmetric)No automatic rotation. On-demand rotation is supported. Older study material says imported key material cannot be rotated. On-demand rotation was added in June 2025.
  • On-demand rotation (RotateKeyOnDemand) rotates the key material at once. It does not change the automatic schedule.
  • Rotation keeps the same key ID, key ARN, aliases, and policies. KMS keeps all old key material, so old ciphertext still decrypts. No code changes are necessary.
  • Rotation does not re-encrypt data and does not rotate data keys. Rotation changes only the key material that KMS uses for new encryption. Data keys that you already made, and the data they encrypt, stay the same.

Disable and delete

  • DisableKey stops all cryptographic use at once. Calls such as Decrypt then fail with DisabledException. EnableKey reverses it.
  • Prefer disable when you are not sure, because deletion cannot be undone. Disable the key first, and set a CloudWatch alarm on attempts to use it. If nothing fails, you can then delete it.
  • ScheduleKeyDeletion sets a waiting period of 7 to 30 days. The default is 30 days. The waiting period gives you time to find applications that still need the key.
  • During the waiting period, the key state is Pending deletion. The key cannot encrypt or decrypt, and calls fail with KMSInvalidStateException. CancelKeyDeletion stops the deletion. The key is then disabled, so call EnableKey to use it again.
  • After deletion, data encrypted under the key cannot be recovered.
  • You can delete only customer managed keys.

Exam signals

  • "Rotate key material every 180 days with least effort" → automatic rotation with RotationPeriodInDays = 180.
  • "Rotate now after a suspected exposure of the key material, keep the same key ID" → on-demand rotation.
  • "Rotate an asymmetric key" → create a new key and point the alias to it.
  • "Key was scheduled for deletion by mistake" → CancelKeyDeletion before the waiting period ends.

Key policies, IAM, grants, and cross-account access

Key facts

  • Every KMS key has exactly one key policy. No principal can use the key unless the key policy allows it, directly or through IAM. This is different from most AWS resources, where an IAM policy alone can give access.
  • The statement with "Principal": {"AWS": "arn:aws:iam::<account>:root"} and kms:* lets IAM policies in that account give access. Here root means the whole account, not only the root user. The statement does not give access to any user by itself.
  • If the key policy does not have that statement, IAM policies that allow access have no effect. IAM policies that deny access still apply.
  • The default key policy from the API contains only the root statement. The console adds key administrator and key user statements.
  • Key administrators can manage the key but cannot use it for cryptographic operations.
  • An explicit deny in any policy wins.

Grants

  • A grant gives one grantee principal permission for specific operations on one key. A grant can allow, but cannot deny. Use a grant for temporary access: you create it, use it, and delete it with no change to the key policy or IAM policies.
  • Grants do not expire on their own. Delete a grant with RetireGrant or RevokeGrant.
  • The retiring principal is a principal that the grant names as allowed to retire it. It retires the grant when it finishes the task. A key administrator usually revokes a grant to take access away.
  • KMS is eventually consistent: a new grant can take a few seconds, sometimes several minutes, to be known in all of KMS. Until then, a call that uses the grant can get an access denied error. Pass the grant token from CreateGrant in the call to use the grant at once.
  • AWS services (for example, Amazon EBS) create grants to use your key for you. The condition kms:GrantIsForAWSResource allows this only for AWS services. Put this condition on the kms:CreateGrant statement in the key policy. Then an AWS service can create grants for your resources, but the principal cannot call CreateGrant directly to give the key to any other principal.
  • Limit: 50,000 grants for each KMS key.

Useful condition keys

Condition keyEffect
kms:ViaServiceAllows use only through a named service, for example s3.us-east-1.amazonaws.com
kms:CallerAccountAllows all principals of one account
kms:EncryptionContext:<key>Allows use only with a matching encryption context

Use kms:ViaService when principals must use the key only through one service, not with direct KMS calls. Use kms:CallerAccount to allow every principal in one account without a list of each role. Use kms:EncryptionContext:<key> to limit a principal to one tenant or one resource.

Cross-account use (both are necessary)

  1. In the key owner account, allow the other account (or a role in it) in the key policy.
  2. In the other account, attach an IAM policy that allows the KMS actions on the key ARN.

The other account must use the key ARN or alias ARN, not the alias name. An alias name such as alias/orders has no account in it, so KMS looks for it in the caller's own account. KMS counts cross-account requests toward the quota of the calling account.

Exam signals

  • "IAM policy allows kms:Decrypt but the call is denied" → the key policy does not allow the principal or the account root.
  • "Give temporary, revocable access to a key without changing the key policy" → create a grant, because a grant adds permission without a policy change, and retiring or revoking it removes the permission.
  • "Use the key only from Amazon S3" → kms:ViaService condition.
  • "Account B cannot decrypt with the key in Account A" → check both the key policy in A and the IAM policy in B.

ACM certificates and AWS Private CA

Key facts

  • ACM public certificates for integrated services (CloudFront, Elastic Load Balancing, API Gateway, and others) have no charge. ACM manages their renewal.
  • A standard ACM public certificate is for integrated AWS services only. You cannot export it to an EC2 instance. ACM also offers exportable public certificates, at a charge for each certificate. Older study material says no ACM public certificate can be exported. Exportable certificates were added in June 2025.
  • ACM certificates are Regional. A resource can use only a certificate in its own Region. CloudFront is a global service, and it reads certificates only from us-east-1. API Gateway edge-optimized endpoints use CloudFront, so they also use certificates in us-east-1. A Regional API or a load balancer uses a certificate in its own Region. A certificate in another Region does not appear in the certificate list in the CloudFront or API Gateway console.
  • A wildcard protects one level only. *.example.com covers a.example.com, but not example.com or a.b.example.com.
  • ACM does not renew imported certificates. Import a new certificate before expiry. If you do not, clients get TLS errors after the certificate expires.
  • AWS Private CA is a managed private CA for internal TLS, mutual TLS, and devices. Browsers do not trust its certificates. General-purpose mode costs $400 for each CA each month.

  • "Certificate renews with no manual work" → DNS validation, and keep the CNAME record.
  • "Cover example.com and all first-level subdomains" → example.com plus *.example.com in one certificate.
  • "Internal services need private certificates from a managed CA" → AWS Private CA.
