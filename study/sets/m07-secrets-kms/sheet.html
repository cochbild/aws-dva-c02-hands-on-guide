Secrets Manager: secrets, versions, and staging labels

Remember

  • A secret stores its value in SecretString (usually JSON) or SecretBinary.
  • Secrets Manager always encrypts the secret value with AWS KMS.
  • Secrets Manager uses the AWS managed key aws/secretsmanager by default, or a customer managed key that you choose.
  • Each value change with PutSecretValue or UpdateSecret creates a new secret version.
  • A staging label is a name attached to one version of a secret. Example: AWSCURRENT.
  • Applications request a staging label, not a version ID, so a label move needs no code change.
  • GetSecretValue with no version returns the version that has AWSCURRENT.
  • AWSPENDING marks the new value during a rotation, before the rotation completes.
  • AWSPREVIOUS marks the last known good value, on the old version after AWSCURRENT moves.
  • A secret can have a maximum of 20 custom staging labels across all its versions.
  • You cannot delete one secret version directly.
  • To remove a secret version, remove all its labels with UpdateSecretVersionStage.
  • Above 100 versions, Secrets Manager removes unlabeled versions of a secret, but not versions less than 24 hours old.
  • DeleteSecret schedules deletion after a recovery window of 7 to 30 days (default 30 days).
  • During the recovery window, GetSecretValue fails with InvalidRequestException.
  • RestoreSecret cancels a scheduled deletion and keeps the same ARN.
  • ForceDeleteWithoutRecovery deletes a secret with no recovery window, and you cannot recover the secret.
  • After a forced deletion, a new secret with the same name can need a retry, because deletion runs in the background.
  • ReplicateSecretToRegions copies a secret to other Regions and keeps the replicas in sync with the primary.
  • A replica secret gives low latency in its own Region and keeps working if the primary Region fails.
  • The maximum secret value size is 65,536 bytes (64 KB).
  • GetSecretValue has a fixed (not adjustable) limit of 10,000 requests per second for each Region.
  • A secret costs $0.40 each month, plus $0.05 for each 10,000 API calls.

Exam signals

  • "Read the value that was active before the last rotation" → GetSecretValue with VersionStage=AWSPREVIOUS.
  • "A secret was deleted by mistake yesterday" → RestoreSecret during the recovery window.
  • "Application in a second Region must read the same secret with low latency" → replicate the secret to that Region.
  • "Store a 100 KB certificate bundle as one secret" → too large. The limit is 64 KB.

Explanation

Key facts

  • A secret holds a value in SecretString (usually JSON) or SecretBinary. Most secrets use SecretString.
  • Secrets Manager always encrypts the secret value with AWS KMS. The default key is the AWS managed key aws/secretsmanager. You can choose a customer managed key.
  • Each change to the value (PutSecretValue or UpdateSecret) creates a new version.
  • A staging label is a name that is attached to one version, for example AWSCURRENT. Applications ask for a label, not a version ID.
  • When a label moves to a new version, the application gets the new value with no code change.
  • GetSecretValue with no version returns the version with AWSCURRENT.
  • You cannot delete one version directly. Remove all its labels with UpdateSecretVersionStage. Secrets Manager then removes it in the background.
  • DeleteSecret does not delete the secret at once. It schedules deletion after a recovery window, so you can undo a mistake.
  • During the window, GetSecretValue fails with InvalidRequestException, so applications that use the secret stop working.
  • RestoreSecret cancels the deletion and keeps the same ARN.
  • ForceDeleteWithoutRecovery is a DeleteSecret option that deletes the secret with no recovery window. You cannot recover it. Use it with caution, for example for test secrets.
  • Deletion is still a background task, so a new secret with the same name may need a retry.
  • You can replicate a secret to other Regions with ReplicateSecretToRegions. Secrets Manager keeps the replicas in sync with the primary secret. An application then reads the replica in its own Region, which gives low latency and keeps working if the primary Region fails.

Secrets Manager rotation

Remember

  • Rotation changes the secret value and the credential in the database or service at the same time.
  • In managed rotation, the service that owns the secret (for example, Amazon RDS) rotates it with no Lambda function.
  • In rotation by Lambda function, a Lambda function rotates the secret.
  • Use managed rotation when the service offers it, because you have no function to write or maintain.
  • Secrets Manager gives rotation function templates for Amazon RDS, Aurora, Redshift, and DocumentDB.
  • For other secrets, use the generic rotation function template.
  • The console can create the rotation function and its execution role for you.
  • A rotation function has four steps in this order: createSecret, setSecret, testSecret, finishSecret.
  • createSecret stores the new value as a new version with AWSPENDING.
  • setSecret changes the credential in the database or service.
  • testSecret connects with the AWSPENDING value.
  • A failed testSecret stops the rotation before AWSCURRENT moves.
  • finishSecret moves AWSCURRENT to the new version, and Secrets Manager adds AWSPREVIOUS to the old version.
  • A rotation function in a VPC needs a Secrets Manager VPC endpoint or a NAT gateway to reach the public Secrets Manager API.
  • Without a Secrets Manager VPC endpoint or NAT gateway, a VPC rotation function waits until the timeout, and the rotation fails.
  • Do not move a rotation function out of the VPC, because the function also needs a network path to the database.
  • The single user strategy changes the password of one user, and open connections stay open.
  • With single user rotation, logins can fail briefly between setSecret and finishSecret, so add retries.
  • The alternating users strategy rotates the password of a second, cloned user that AWSCURRENT does not use.
  • The alternating users strategy needs a separate secret with superuser credentials to clone the user.
  • Choose single user when a few failed logins with retries are acceptable.
  • Choose alternating users for high availability, when you can store a superuser secret.
  • Amazon RDS Proxy does not support the alternating users strategy.
  • Secrets Manager can rotate a secret at most every 4 hours.
  • The rotation window is the period in which Secrets Manager can start the rotation.
  • The smallest rotation window is 1 hour.
  • A rotation schedule uses rate() or cron() expressions, in UTC.
  • "Rotate immediately when the secret is stored" starts a rotation when you save the configuration.
  • If you clear "Rotate immediately when the secret is stored", the first rotation follows the schedule.

Exam signals

  • "Rotate RDS credentials automatically with the least effort" → Secrets Manager with the RDS rotation template or managed rotation.
  • "Rotation fails with a timeout; the function is in a private subnet" → add a Secrets Manager VPC endpoint or a NAT gateway.
  • "Users must not see failed logins during rotation" → alternating users strategy. The credentials that applications read stay valid while the other user's password changes.
  • "Which step changes the database password" → setSecret.

Explanation

Key facts

  • Rotation changes the secret value and the credential in the database or service at the same time. Two forms of rotation exist.
  • Managed rotation: the service that owns the secret (for example, Amazon RDS) rotates it with no Lambda function.
  • Rotation by Lambda function: a Lambda function rotates the secret.
  • Use managed rotation when the service offers it, because you have no function to write or maintain.
  • Secrets Manager gives rotation function templates for Amazon RDS, Amazon Aurora, Amazon Redshift, and Amazon DocumentDB. Use the generic template for other secrets.
  • The console can create the rotation function and its execution role for you.
  • The rotation function must reach both Secrets Manager and the database. A Lambda function in a VPC can reach only resources in that VPC, unless the VPC gives it internet access.
  • The Secrets Manager API is a public endpoint. Without a Secrets Manager VPC endpoint or a NAT gateway, the function waits for the API until the timeout, and the rotation fails.
  • The function also needs a network path to the database, so you cannot simply move it out of the VPC.
  • "Rotate immediately when the secret is stored" starts a rotation when you save the configuration. If you clear it, the first rotation follows the schedule.

The four steps of a rotation function

  1. createSecret: make a new value and store it as a new version with AWSPENDING.
  2. setSecret: change the credential in the database or service.
  3. testSecret: use the AWSPENDING value to connect. If the test fails, the rotation stops before finishSecret, so AWSCURRENT does not move to a value that does not work.
  4. finishSecret: move AWSCURRENT to the new version. Secrets Manager adds AWSPREVIOUS to the old version.

Reading secrets: caching, Lambda, and cross-account access

Remember

  • To read a secret, a principal needs secretsmanager:GetSecretValue.
  • If a customer managed key encrypts a secret, the reader also needs kms:Decrypt on that key.
  • Cache secrets in the application, because each GetSecretValue call costs money and counts toward the request rate.
  • Secrets Manager caching components exist for Java, Python, .NET, Go, and Rust.
  • Use the Secrets Manager caching components outside Lambda, or in Lambda without the extension.
  • The AWS Parameters and Secrets Lambda Extension is a Lambda layer that runs a local HTTP server with a cache.
  • Function code sends an HTTP GET to localhost:2773 to read a value from the Parameters and Secrets Lambda Extension.
  • The Parameters and Secrets Lambda Extension works with every runtime and needs no SDK code for the call.
  • The extension secret path is /secretsmanager/get?secretId=....
  • Each extension request needs the X-Aws-Parameters-Secrets-Token header with the session token of the function.
  • The extension cache TTL is 300 seconds by default for secrets and for parameters.
  • SECRETS_MANAGER_TTL sets the extension secret cache TTL, from 0 to 300 seconds.
  • The extension cache holds 1,000 items by default.
  • After a rotation, a cache can return the old password until its TTL ends, and logins fail.
  • To fix a stale cache, lower the TTL, or request versionStage=AWSCURRENT again after an authentication error.
  • AWS recommends Secrets Manager, not Lambda environment variables, for database credentials.
  • Lambda environment variables have no rotation.
  • Lambda always encrypts environment variables at rest, by default with an AWS managed key at no charge.
  • A user who can view the function configuration and decrypt with its key can read the environment variables.
  • To hide Lambda environment variables from a user, use a customer managed key and deny that user kms:Decrypt on the key.
  • Encryption helpers encrypt an environment variable on the client side, so the console and API show only ciphertext.
  • With encryption helpers, the function code decrypts the value, and the execution role needs kms:Decrypt.
  • Cross-account secret access needs a resource-based policy on the secret that allows the other account's role.
  • Cross-account secret access needs a customer managed key whose key policy allows the other account's role kms:Decrypt.
  • Cross-account secret access needs an IAM policy on the other account's role for GetSecretValue and kms:Decrypt.
  • The aws/secretsmanager key cannot work across accounts, because you cannot change an AWS managed key policy.

Exam signals

  • "Lambda reads a secret on every invoke; reduce cost and latency with no SDK changes" → Parameters and Secrets Lambda Extension.
  • "Cross-account read fails with a KMS error; the secret uses the default key" → re-encrypt the secret with a customer managed key and update its key policy.
  • "Function uses an old password after rotation" → cache is stale. Shorten the TTL or refresh on an authentication error.
  • "Database password is in an environment variable" → move it to Secrets Manager. Users who can view the function configuration can read the variable, and Secrets Manager can rotate the password.
  • "Environment variable must stay encrypted until the code uses it, even in the console" → encryption helpers with a customer managed key, and decrypt in code.

Lambda environment variables and KMS

  • AWS recommends Secrets Manager, not environment variables, for database credentials.
  • Any user who can view the function configuration and decrypt with its key can read an environment variable. Environment variables also have no rotation.
  • Lambda always encrypts environment variables at rest. By default it uses an AWS managed key, with no setup and no charge.
  • You can choose a customer managed key for encryption at rest. Then only users with kms:Decrypt on that key can view or manage the variables in the console.
  • Users who can view the function configuration and can decrypt with the key can read the values. To hide them from a user, deny kms:Decrypt on the key.
  • Encryption helpers for encryption in transit are a console option. They encrypt a value on the client side with a customer managed key before Lambda receives it.
  • Lambda then stores and shows only the ciphertext, so the plaintext does not appear in the console or in API responses.
  • The function code must decrypt the value, and the execution role needs kms:Decrypt.

Cross-account access (all three are necessary)

  1. Attach a resource-based policy to the secret that allows the other account's role.
  2. Encrypt the secret with a customer managed key. Add the other account's role to the key policy (kms:Decrypt). You cannot use aws/secretsmanager across accounts, because you cannot change the key policy of an AWS managed key to allow another account.
  3. Attach an IAM policy to the role in the other account. Allow secretsmanager:GetSecretValue on the secret and kms:Decrypt on the key.

Choosing Secrets Manager, Parameter Store, or AppConfig

Remember

  • Secrets Manager is the only one of the three services with built-in automatic rotation.
  • Choose Secrets Manager for database credentials that must rotate.
  • Choose Parameter Store SecureString for a static secret at the lowest cost.
  • A Standard Parameter Store parameter has no storage charge.
  • Secrets Manager charges $0.40 for each secret each month, plus API calls.
  • Choose Parameter Store String in a hierarchy for plain configuration values, with one path for each environment.
  • One GetParametersByPath call loads all parameters under a path, for example /myapp/prod/.
  • Choose AppConfig for feature flags, or for configuration that must roll out slowly and roll back on an alarm.
  • Parameter Store and Secrets Manager give a new value to all readers at once, with no gradual rollout and no automatic rollback.
  • The maximum value size is 64 KB in Secrets Manager, and 4 KB (Standard) or 8 KB (Advanced) in Parameter Store.
  • Secrets Manager has built-in cross-Region replication, but Parameter Store does not.
  • Only AppConfig validates configuration before deployment, with a JSON Schema or a Lambda function.
  • Parameter Store can only check a value with AllowedPattern.
  • AppConfig charges for each configuration request.

Exam signals

  • "Automatic rotation" or "RDS credentials" → Secrets Manager.
  • "MOST cost-effective place for an API key that never changes" → Parameter Store SecureString.
  • "Turn on a feature for 10 percent of users first" → AppConfig feature flag with a gradual deployment strategy.

Parameter Store: types, tiers, and policies

Remember

  • Parameter Store has three parameter types: String, StringList (comma-separated values), and SecureString.
  • Only SecureString parameters are encrypted with KMS.
  • A SecureString uses the default key aws/ssm, or a customer managed key.
  • A SecureString can use only a symmetric KMS key.
  • The Standard tier is the default and has no additional charge.
  • The Advanced tier charges for each parameter.
  • The Standard tier allows 10,000 parameters in each account and Region, and the Advanced tier allows 100,000.
  • The maximum parameter value size is 4 KB in the Standard tier and 8 KB in the Advanced tier.
  • Only Advanced tier parameters support parameter policies and sharing with other accounts.
  • You can upgrade a Standard parameter to Advanced.
  • You cannot change an Advanced parameter back to Standard.
  • To get a Standard parameter from an Advanced one, delete the parameter and create it again.
  • The Expiration policy deletes the parameter at a date and time.
  • The ExpirationNotification policy sends an EventBridge event before the expiration.
  • The NoChangeNotification policy sends an EventBridge event if nobody changes the parameter for a time.
  • A parameter can have a maximum of 10 policies.
  • A Standard SecureString uses KMS Encrypt directly, because 4 KB fits in the 4,096-byte Encrypt limit.
  • An Advanced SecureString uses envelope encryption with the AWS Encryption SDK, because 8 KB exceeds the Encrypt limit.
  • To write a Standard SecureString, a principal needs kms:Encrypt.
  • To write an Advanced SecureString, a principal needs kms:GenerateDataKey.
  • To read any SecureString, a principal needs kms:Decrypt.
  • Parameter Store sends the parameter ARN to KMS as the encryption context PARAMETER_ARN.
  • A kms:EncryptionContext:PARAMETER_ARN condition lets a role decrypt only one parameter with a shared KMS key.

Exam signals

  • "Parameter must delete itself after 30 days" → Advanced tier with an Expiration policy.
  • "Value is 6 KB" → Advanced tier (Standard maximum is 4 KB).
  • "Error: policies are only supported on Advanced tier" → change the parameter to Advanced.
  • "Stop paying for an Advanced parameter" → delete it and create a Standard parameter. You cannot change an Advanced parameter back to Standard.

Parameter policies (Advanced tier only)

  • Expiration: Parameter Store deletes the parameter at a date and time.
  • ExpirationNotification: sends an Amazon EventBridge event before the expiration, so the team can replace the value before Parameter Store deletes it.
  • NoChangeNotification: sends an EventBridge event if nobody changes the parameter for a time. Use it as a reminder to change a password or token that must not stay the same too long.
  • Maximum 10 policies for each parameter.

Key facts

  • A standard SecureString uses KMS Encrypt directly. A standard value (maximum 4 KB) fits in the 4,096-byte limit of Encrypt.
  • An advanced value can be 8 KB, which is larger than that limit. An advanced SecureString uses envelope encryption with the AWS Encryption SDK (see "Envelope encryption" below).
  • To write a standard SecureString, a principal needs kms:Encrypt. For an advanced one, kms:GenerateDataKey. To read either, kms:Decrypt.
  • Parameter Store sends the encryption context PARAMETER_ARN (the ARN of the parameter) to KMS. Many parameters can share one KMS key.
  • A kms:EncryptionContext:PARAMETER_ARN condition in an IAM policy or key policy lets a role decrypt only one parameter with that key.

Parameter Store: hierarchies, versions, decryption, and throughput

Remember

  • Parameter names with forward slashes make a hierarchy. Example: /myapp/prod/db/host.
  • A parameter hierarchy can have a maximum of 15 levels.
  • GetParametersByPath returns all parameters under a path.
  • Add Recursive to GetParametersByPath to include all lower levels.
  • GetParameters returns a maximum of 10 parameters by name in one call.
  • To separate environments, use IAM policies on parameter paths. Example: parameter/myapp/prod/*.
  • GetParameter does not decrypt a SecureString by default and returns ciphertext.
  • To get the plaintext of a SecureString, set WithDecryption to true and allow kms:Decrypt on the key.
  • Each PutParameter with Overwrite creates a new numeric version.
  • To read an old parameter version, use name:version.
  • A parameter label is a name for a version.
  • To read a parameter version by label, use name:label.
  • To roll back a parameter with no code change, move the label to an older version.
  • AllowedPattern is a regular expression, and Parameter Store rejects values that do not match it.
  • By default, GetParameter, GetParameters, and GetParametersByPath share 40 TPS in each account and Region.
  • The Parameter Store TPS limit applies to all applications in the account and Region together.
  • Higher throughput raises GetParameter to 10,000 TPS, GetParameters to 1,000 TPS, and GetParametersByPath to 100 TPS.
  • Higher throughput is an account and Region setting, separate from the parameter tier.
  • Higher throughput charges for each API interaction.
  • One Parameter Store API interaction is one parameter in a response.
  • Too many Parameter Store requests cause ThrottlingException (Rate exceeded).
  • To fix Parameter Store throttling, cache the values first, then turn on higher throughput if necessary.

Exam signals

  • "Load all configuration for one environment at startup in few calls" → GetParametersByPath with Recursive.
  • "GetParameter returns an encrypted string" → add WithDecryption.
  • "AccessDeniedException from KMS on GetParameter" → the role lacks kms:Decrypt on the customer managed key.
  • "ThrottlingException when many instances start at the same time" → cache values. If that is not enough, turn on higher throughput.

Explanation

Key facts

  • Names with forward slashes make a hierarchy, for example /myapp/prod/db/host. A hierarchy can have a maximum of 15 levels.
  • GetParametersByPath returns all parameters under a path. Add Recursive to include all lower levels.
  • GetParameters returns a maximum of 10 parameters by name in one call.
  • Use IAM policies on paths, for example parameter/myapp/prod/*, to separate environments. A role for the test environment then cannot read production values.
  • GetParameter does not decrypt a SecureString by default. Without WithDecryption, the call returns the encrypted value as a string of ciphertext.
  • Set WithDecryption to true. The caller also needs kms:Decrypt on the key.
  • Each PutParameter with Overwrite creates a new numeric version. Read an old version with name:version.
  • Labels are names for versions. Read a label with name:label. Move a label to roll back without code changes.
  • AllowedPattern is a regular expression. Parameter Store rejects values that do not match.

AppConfig: resources, profiles, and retrieval

Remember

  • An AppConfig application is a namespace for one application. Example: "checkout-service".
  • An AppConfig environment is a deployment target, such as "beta" or "prod", and holds the CloudWatch alarms for rollback.
  • A configuration profile tells AppConfig the data location, the type (feature flags or freeform), and the validators.
  • A deployment strategy tells AppConfig how fast to release new data and how long to watch alarms (the bake time).
  • An AppConfig deployment releases one configuration version to one environment with one strategy.
  • A feature flag profile holds on and off switches that change features with no code deployment.
  • Feature flags are stored in the AppConfig hosted configuration store, and AppConfig validates the flag format automatically.
  • A freeform profile holds any configuration data, for example JSON, YAML, or text.
  • Choose a freeform profile for data that is not a flag, or for data that must stay in another service.
  • Freeform data can be in the hosted store, S3, CodePipeline, Secrets Manager, Parameter Store, or SSM documents.
  • A configuration profile can have up to two validators: a JSON Schema (freeform only) or a Lambda function.
  • AppConfig runs validators when you call StartDeployment, and invalid data does not deploy.
  • Without an agent, call StartConfigurationSession one time to get a token, then call GetLatestConfiguration.
  • Each GetLatestConfiguration response gives a new token, and the next call must send that new token.
  • GetLatestConfiguration returns an empty body when the data has not changed, so the client keeps its copy.
  • GetConfiguration is the old AppConfig API and is deprecated.

AppConfig: deployment strategies and rollback

Remember

  • An AppConfig deployment strategy has a growth type, a step percentage (growth factor), a deployment time, and a bake time.
  • Linear growth adds the same percentage of targets at each step. Example: 20, 40, 60, 80, 100 percent.
  • Exponential growth doubles the percentage at each step. Example: 2, 4, 8, 16 percent.
  • Exponential growth exposes very few targets first, then finishes quickly.
  • Deployment time is the total time to give the data to all targets.
  • AppConfig deployment time is not a timeout.
  • Bake time is the time AppConfig watches CloudWatch alarms after the data reaches 100 percent of targets.
  • AppConfig rolls back if an environment alarm goes into ALARM or INSUFFICIENT_DATA during the rollout or bake time.
  • An alarm with missing metric data can cause an AppConfig rollback, because it goes into INSUFFICIENT_DATA.
  • StopDeployment rolls back an AppConfig deployment that is still in progress.
  • Automatic rollback needs an IAM role that allows AppConfig cloudwatch:DescribeAlarms.
  • Without the cloudwatch:DescribeAlarms role, AppConfig cannot read alarm state and does not roll back.
  • AppConfig deploys only one configuration at a time to one environment.
  • A second deployment to the same environment waits until the first completes or you stop it.
  • AppConfig can deploy to different environments at the same time.
  • AppConfig.Linear20PercentEvery6Minutes releases 20 percent every 6 minutes (30 minutes total), with a 30-minute bake time.
  • AppConfig.Canary10Percent20Minutes is exponential, 10 percent growth, over 20 minutes, with a 10-minute bake time.
  • AppConfig.AllAtOnce releases to all targets at once, with a 10-minute bake time.
  • AppConfig.Linear50PercentEvery30Seconds releases half every 30 seconds (1 minute total), with a 1-minute bake time.
  • For production, choose Linear20PercentEvery6Minutes or Canary10Percent20Minutes, which AWS recommends.
  • For test environments, choose AllAtOnce or Linear50PercentEvery30Seconds, where speed matters more than safety.

Exam signals

  • "Roll back a bad configuration automatically when the error rate rises" → CloudWatch alarm on the environment plus a strategy with bake time.
  • "Release the change at once in a test environment" → AppConfig.AllAtOnce.
  • "Gradual configuration change with no new code deployment" → AppConfig, not a Lambda alias or CodeDeploy. AppConfig changes only the configuration data that running code reads.
  • "Lambda alias or CodeDeploy for a configuration change" → wrong choice. A Lambda alias and CodeDeploy shift traffic between versions of code.

KMS key types, aliases, and multi-Region keys

Remember

  • KMS has three key types: customer managed keys, AWS managed keys (aws/<service>), and AWS owned keys.
  • You write and change the key policy of a customer managed key.
  • You can view an AWS managed key policy, but you cannot change it.
  • An AWS owned key is not in your account, and you cannot see its key policy.
  • Only a customer managed key can be used in your own code.
  • A customer managed key can be used from another account through its key policy.
  • An AWS managed key cannot be used from another account.
  • Customer managed key rotation is optional.
  • AWS managed keys rotate automatically every year.
  • A customer managed key has a monthly fee plus usage fees.
  • An AWS managed key has no monthly fee, but usage fees can apply.
  • An AWS owned key has no fee.
  • Choose a customer managed key to control the key policy, share the key, call the key from code, or set rotation.
  • Choose an AWS managed or AWS owned key when the service only needs to encrypt data at rest.
  • A symmetric key (SYMMETRIC_DEFAULT, AES-256-GCM) never leaves KMS unencrypted, so every encrypt and decrypt calls KMS.
  • Most AWS services use symmetric keys.
  • Choose a symmetric key unless you have a reason for an asymmetric key.
  • An asymmetric key (RSA, ECC) has a private key that stays in KMS and a public key that you can download.
  • Choose an asymmetric key when a party outside AWS must encrypt or verify a signature with no call to KMS.
  • A KMS alias is a name for a key. Example: alias/orders.
  • UpdateAlias points an alias to a different key, and code that uses the alias does not change.
  • The alias/aws/ prefix is reserved for AWS managed keys.
  • Multi-Region keys have the same key ID (prefix mrk-) and key material in each Region.
  • Data encrypted with a multi-Region key in one Region decrypts in another Region with no cross-Region call.
  • Use multi-Region keys for client-side encrypted data that moves between Regions. Examples: DynamoDB global tables, disaster recovery.
  • Each multi-Region key has its own key policy, grants, and aliases.
  • You cannot convert a single-Region key to a multi-Region key.
  • To move to a multi-Region key, create a new multi-Region key and encrypt the data again.

Exam signals

  • "Full control of the key policy" or "share with another account" → customer managed key.
  • "Least operational overhead, no key management, no audit need" → AWS owned or AWS managed key. AWS creates, rotates, and controls these keys, and they have no monthly fee.
  • "Client-side encrypted data must decrypt in a second Region during a Regional outage" → multi-Region key.
  • "Change the key without changing application code" → use an alias, then UpdateAlias.

Envelope encryption, data keys, and encryption context

Remember

  • In envelope encryption, a data key encrypts the data locally, and the KMS key encrypts only the data key.
  • KMS Encrypt accepts a maximum of 4,096 bytes, so use it for small secrets only.
  • With envelope encryption, a large file needs only one KMS call, and the bulk encryption runs locally.
  • GenerateDataKey returns Plaintext (the data key) and CiphertextBlob (the same data key, encrypted).
  • After you encrypt the data, remove the plaintext data key from memory.
  • Store the encrypted data key with the encrypted data.
  • To decrypt envelope-encrypted data, send the encrypted data key to Decrypt, then decrypt the data locally.
  • GenerateDataKeyWithoutPlaintext returns only the encrypted data key.
  • Use GenerateDataKeyWithoutPlaintext when a different component encrypts the data later.
  • Decrypt of symmetric ciphertext needs no key ID, because the ciphertext contains it.
  • ReEncrypt moves ciphertext to a different KMS key inside KMS, and the plaintext never leaves KMS.
  • An encryption context is a set of non-secret key-value pairs that describe the data. Example: {"tenant":"42"}.
  • KMS binds the encryption context to the ciphertext as additional authenticated data, but does not encrypt the context.
  • Decrypt must use the same encryption context, with an exact, case-sensitive match.
  • A wrong or missing encryption context makes Decrypt fail with InvalidCiphertextException.
  • CloudTrail logs the encryption context in plaintext, so do not put secrets in the encryption context.
  • The kms:EncryptionContext:<key> condition allows decryption only for one tenant or one resource.
  • KMS cryptographic operations on symmetric keys share one request quota for each account and Region.
  • The KMS request quota is 100,000 per second in us-east-1, us-west-2, and eu-west-1.
  • The KMS request quota is 20,000 per second in us-east-2, eu-central-1, ap-northeast-1, and some other Regions.
  • The KMS request quota is 10,000 per second in all other Regions.
  • KMS calls that AWS services make for you, for example S3 SSE-KMS, count toward your quota.
  • Too many KMS calls cause ThrottlingException.
  • To fix KMS throttling, reuse data keys with data key caching, use S3 Bucket Keys, or request a quota increase.
  • An S3 Bucket Key lets S3 call KMS much less often and can reduce KMS request costs by up to 99 percent.

Exam signals

  • "Encrypt a 5 MB file with KMS" → envelope encryption with GenerateDataKey, not Encrypt.
  • "Decrypt fails with InvalidCiphertextException" → wrong or missing encryption context, or the wrong ciphertext.
  • "ThrottlingException from KMS during S3 uploads" → S3 Bucket Keys, or a quota increase.
  • "A service must prepare keys now, and another service encrypts later" → GenerateDataKeyWithoutPlaintext. The first service never receives the plaintext data key, and the second service calls Decrypt to get it.

Explanation

Envelope encryption steps

Envelope encryption uses two keys. A data key encrypts the data in your application, outside KMS. The KMS key encrypts only the small data key.

KMS Encrypt accepts a maximum of 4,096 bytes, and each call goes over the network. With a data key, a large file needs only one KMS call, and the bulk encryption runs locally.

  1. Call GenerateDataKey with a symmetric KMS key. KMS returns Plaintext (the data key) and CiphertextBlob (the same data key, encrypted).
  2. Encrypt the data locally with the plaintext data key.
  3. Remove the plaintext data key from memory.
  4. Store the encrypted data key with the encrypted data.
  5. To decrypt, send the encrypted data key to Decrypt. Use the returned plaintext key to decrypt the data locally.

API comparison

APIUse
EncryptEncrypts up to 4,096 bytes directly with the KMS key. For small secrets only.
GenerateDataKeyReturns a plaintext and an encrypted data key. Use it to encrypt data now.
GenerateDataKeyWithoutPlaintextReturns only the encrypted data key. Use it when a different component encrypts later.
DecryptFor symmetric ciphertext, you do not need to give the key ID. The ciphertext contains it.
ReEncryptDecrypts and encrypts again under a different key, inside KMS. The plaintext never leaves KMS. Use it to move ciphertext (for example, encrypted data keys) to a new KMS key.

Encryption context

  • A set of non-secret key-value pairs that describe the data, for example {"tenant":"42"}. KMS uses it as additional authenticated data: it is not encrypted, but it is cryptographically bound to the ciphertext.
  • Decrypt must use the same context (exact, case-sensitive match). If not, KMS returns InvalidCiphertextException.
  • A request that sends {"tenant":"7"} cannot decrypt data that was encrypted with {"tenant":"42"}.
  • A ciphertext that was moved to a different record also fails to decrypt, when the context names the record.
  • CloudTrail logs the context in plaintext. Do not put secrets in it.
  • Use the kms:EncryptionContext:<key> condition to allow decryption only for one tenant or one resource.

Request quotas

  • Cryptographic operations on symmetric keys share one quota for each account and Region. The default depends on the Region: 100,000 requests per second in us-east-1, us-west-2, and eu-west-1; 20,000 in us-east-2, eu-central-1, ap-northeast-1, and some other Regions; 10,000 in all other Regions.
  • Calls that AWS services make for you (for example, S3 SSE-KMS) count toward your quota. Too many calls cause ThrottlingException.
  • Fixes: reuse data keys (AWS Encryption SDK data key caching), use S3 Bucket Keys, or request a quota increase.
  • Data key caching uses one data key for many messages, so the application calls GenerateDataKey less often.
  • Without a Bucket Key, S3 calls KMS for each request on an encrypted object.
  • With a Bucket Key, S3 gets a short-lived bucket-level key from KMS and uses it to create data keys for new objects. S3 then calls KMS much less often.
  • S3 Bucket Keys can reduce KMS request costs by up to 99 percent.

Key rotation, disabling, and deletion

Remember

  • Automatic rotation of a symmetric customer managed key is optional and off by default.
  • EnableKeyRotation turns on automatic rotation of a KMS key.
  • The automatic rotation period is 90 to 2,560 days, default 365 days. Older study material says rotation is annual only.
  • DisableKeyRotation turns off automatic rotation.
  • An AWS managed key rotates every year, and you cannot change the rotation.
  • Asymmetric, HMAC, and custom key store keys have no automatic rotation.
  • To rotate an asymmetric, HMAC, or custom key store key, create a new key and move the alias.
  • Imported key material has no automatic rotation, but supports on-demand rotation. Older study material says it cannot rotate.
  • On-demand rotation (RotateKeyOnDemand) rotates the key material at once and does not change the automatic schedule.
  • Key rotation keeps the same key ID, key ARN, aliases, and policies, so no code changes are necessary.
  • KMS keeps all old key material after rotation, so old ciphertext still decrypts.
  • Key rotation does not re-encrypt data and does not rotate data keys.
  • DisableKey stops all cryptographic use of a key at once.
  • EnableKey reverses DisableKey.
  • A disabled key makes calls such as Decrypt fail with DisabledException.
  • Disable a key before you delete it, and set a CloudWatch alarm on attempts to use it.
  • ScheduleKeyDeletion sets a waiting period of 7 to 30 days (default 30 days).
  • A key in the Pending deletion state cannot encrypt or decrypt.
  • Calls to a key in the Pending deletion state fail with KMSInvalidStateException.
  • CancelKeyDeletion stops the deletion and leaves the key disabled.
  • After CancelKeyDeletion, call EnableKey to use the key again.
  • After a KMS key is deleted, data encrypted under the key cannot be recovered.
  • You can delete only customer managed keys.

Exam signals

  • "Rotate key material every 180 days with least effort" → automatic rotation with RotationPeriodInDays = 180.
  • "Rotate now after a suspected exposure of the key material, keep the same key ID" → on-demand rotation.
  • "Rotate an asymmetric key" → create a new key and point the alias to it.
  • "Key was scheduled for deletion by mistake" → CancelKeyDeletion before the waiting period ends.

Key policies, IAM, grants, and cross-account access

Remember

  • Every KMS key has exactly one key policy.
  • No principal can use a KMS key unless the key policy allows it, directly or through IAM.
  • For a KMS key, an IAM policy alone cannot give access, unlike most AWS resources.
  • The key policy statement for arn:aws:iam::<account>:root with kms:* lets IAM policies in that account give access.
  • In a key policy, root means the whole account, not only the root user.
  • The root statement does not give access to any user by itself.
  • Without the root statement, IAM policies that allow KMS access have no effect, but IAM deny statements still apply.
  • The default key policy from the API contains only the root statement.
  • The console default key policy adds key administrator and key user statements.
  • Key administrators can manage a KMS key but cannot use it for cryptographic operations.
  • An explicit deny in any policy wins.
  • A grant gives one grantee principal permission for specific operations on one KMS key.
  • A KMS grant can allow, but cannot deny.
  • Use a grant for temporary access with no change to the key policy or IAM policies.
  • KMS grants do not expire on their own.
  • Delete a KMS grant with RetireGrant or RevokeGrant.
  • The retiring principal retires a grant when it finishes the task.
  • A key administrator usually revokes a grant to take access away.
  • A new grant can take seconds to minutes to take effect, because KMS is eventually consistent.
  • To use a new grant at once, pass the grant token from CreateGrant in the call.
  • The kms:GrantIsForAWSResource condition lets only AWS services, for example Amazon EBS, create grants.
  • Put kms:GrantIsForAWSResource on the kms:CreateGrant statement in the key policy.
  • A KMS key can have a maximum of 50,000 grants.
  • The kms:ViaService condition allows key use only through a named service. Example: s3.us-east-1.amazonaws.com.
  • The kms:CallerAccount condition allows all principals of one account, with no list of each role.
  • The kms:EncryptionContext:<key> condition limits a principal to one tenant or one resource.
  • Cross-account KMS use needs the key policy in the owner account to allow the other account or role.
  • Cross-account KMS use also needs an IAM policy in the other account that allows the KMS actions on the key ARN.
  • Another account must use the key ARN or alias ARN, not the alias name.
  • An alias name such as alias/orders resolves in the caller's own account.
  • KMS counts cross-account requests toward the quota of the calling account.

  • "IAM policy allows kms:Decrypt but the call is denied" → the key policy does not allow the principal or the account root.
  • "Give temporary, revocable access to a key without changing the key policy" → create a grant. A grant adds permission without a policy change, and retiring or revoking it removes the permission.
  • "Use the key only from Amazon S3" → kms:ViaService condition.
  • "Account B cannot decrypt with the key in Account A" → check both the key policy in A and the IAM policy in B.

  • Every KMS key has exactly one key policy. No principal can use the key unless the key policy allows it, directly or through IAM.
  • This is different from most AWS resources, where an IAM policy alone can give access.

ACM certificates and AWS Private CA

Remember

  • ACM public certificates for integrated services, such as CloudFront, Elastic Load Balancing, and API Gateway, have no charge.
  • ACM manages the renewal of public certificates for integrated services.
  • A standard ACM public certificate cannot be exported to an EC2 instance.
  • ACM exportable public certificates have a charge for each certificate. Older study material says no ACM public certificate can be exported.
  • ACM certificates are Regional, so a resource can use only a certificate in its own Region.
  • CloudFront reads certificates only from us-east-1.
  • API Gateway edge-optimized endpoints use CloudFront, so their certificates must be in us-east-1.
  • A Regional API or a load balancer uses an ACM certificate in its own Region.

Explanation

Key facts

  • ACM public certificates for integrated services (CloudFront, Elastic Load Balancing, API Gateway, and others) have no charge. ACM manages their renewal.
  • A standard ACM public certificate is for integrated AWS services only. You cannot export it to an EC2 instance.
  • ACM also offers exportable public certificates, at a charge for each certificate. Older study material says no ACM public certificate can be exported. Exportable certificates were added in June 2025.
  • ACM certificates are Regional. A resource can use only a certificate in its own Region.
  • CloudFront is a global service, and it reads certificates only from us-east-1. API Gateway edge-optimized endpoints use CloudFront, so they also use certificates in us-east-1.
  • A Regional API or a load balancer uses a certificate in its own Region.
  • A certificate in another Region does not appear in the certificate list in the CloudFront or API Gateway console.
  • A wildcard protects one level only. *.example.com covers a.example.com, but not example.com or a.b.example.com.
  • ACM does not renew imported certificates. Import a new certificate before expiry. If you do not, clients get TLS errors after the certificate expires.
  • AWS Private CA is a managed private CA for internal TLS, mutual TLS, and devices. Browsers do not trust its certificates. General-purpose mode costs $400 for each CA each month.
