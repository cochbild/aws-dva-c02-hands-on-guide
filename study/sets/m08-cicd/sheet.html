Source and package repositories: CodeCommit and CodeArtifact

Remember

  • A commit to a Git repository (CodeCommit, GitHub, GitLab, Bitbucket) can start a pipeline.
  • For CodeCommit and Amazon S3 sources, an EventBridge rule starts the pipeline.
  • For GitHub, GitLab, and Bitbucket, a connection (AWS CodeConnections) lets CodePipeline read the repository and receive push events.
  • Use branches for environments and Git tags for releases.
  • A V2 pipeline can filter triggers on branches, tags, and file paths.
  • AWS CodeCommit is a managed Git service. IAM controls access to it.
  • AWS closed CodeCommit to new customers in July 2024 and made it available again in November 2025.
  • CodeCommit HTTPS Git credentials and SSH keys belong to an IAM user. A federated user or a role cannot get them.
  • For federated access or temporary credentials with CodeCommit, use git-remote-codecommit. It needs no Git credentials.
  • To stop some users from pushing to a branch, use an IAM Deny with the codecommit:References condition.
  • A branch Deny must cover codecommit:GitPush and the merge actions. Otherwise a pull request merge can change the branch.
  • AWS CodeArtifact is a managed package repository for npm, PyPI, Maven, NuGet, and other formats.
  • A CodeArtifact domain groups repositories, stores each asset one time, and encrypts all assets with one KMS key.
  • One CodeArtifact repository can hold several package formats.
  • A CodeArtifact repository searches its upstream repositories when it does not have a requested package.
  • A CodeArtifact repository can have up to 10 upstream repositories.
  • An external connection links a CodeArtifact repository to a public repository, such as npmjs.com, PyPI, or Maven Central.
  • A CodeArtifact repository can have only one external connection.
  • CodeArtifact stores a copy of each public package, so builds can still download it during a public repository outage.
  • Recommended CodeArtifact pattern: one repository has the external connection, and the other repositories use it as an upstream.
  • aws codeartifact login configures npm, pip, twine, dotnet, nuget, and swift with the endpoint and a token.
  • For Maven and Gradle, call get-authorization-token and put the token in the tool settings yourself.
  • A CodeArtifact token is valid for 12 hours by default. You can set 15 minutes to 12 hours.
  • A CodeArtifact token needs codeartifact:GetAuthorizationToken and sts:GetServiceBearerToken. Without either, the call fails with AccessDenied.

Exam signals

  • "Builds must get open-source packages through a private, approved repository" → CodeArtifact with an external connection. Builds download from your repository, and the repository gets public packages for them.
  • "Maven build cannot authenticate to CodeArtifact" → call get-authorization-token and pass the token, for example in CODEARTIFACT_AUTH_TOKEN.
  • "Developers use federation or temporary credentials with CodeCommit" → git-remote-codecommit.
  • "Only senior developers can push to main" → IAM Deny with codecommit:References.

Explanation

Git repositories and triggers

  • A commit to a Git repository (CodeCommit, GitHub, GitLab, Bitbucket) can start a pipeline. CodePipeline detects the change in one of two ways.
  • For CodeCommit and Amazon S3 sources, an EventBridge rule starts the pipeline.
  • For GitHub, GitLab, and Bitbucket, a connection (AWS CodeConnections) is an authorized link that lets CodePipeline read the repository and receive its push events.
  • Use branches for environments and Git tags for releases. For example, a push to the dev branch deploys to test, and a push of tag v1.4.0 starts the production release.
  • A V2 pipeline can filter triggers on branches, tags, and file paths, so that only the matching pushes start it.

CodeCommit (short note)

  • AWS CodeCommit is a managed Git service. IAM controls access. Exam guide v2.1 does not list it, but questions can still describe it.
  • AWS closed CodeCommit to new customers in July 2024. AWS made it available to new customers again in November 2025.
  • HTTPS Git credentials and SSH keys belong to an IAM user. A federated user or a role has no IAM user, so it cannot get these credentials.
  • For federated access or temporary credentials, use git-remote-codecommit. This Git extension signs each Git request with the AWS credentials of your AWS CLI profile. It needs no Git credentials.
  • To stop some users from pushing to a branch, use an IAM Deny policy on codecommit:GitPush and the merge actions, with the codecommit:References condition (for example refs/heads/main).
  • An explicit Deny overrides every Allow, so the users keep their other CodeCommit permissions.
  • Deny the merge actions too, because otherwise a user can change main with a pull request merge in the console.

CodeArtifact

  • AWS CodeArtifact is a managed package repository for npm, PyPI, Maven, NuGet, and other formats.
  • A domain groups repositories.
  • An asset is a file of a package version, such as an npm .tgz file. The domain stores each asset one time, even when ten repositories hold that version. It encrypts all assets with one KMS key.
  • A repository holds package versions. One repository can hold several package formats.
  • An upstream repository is a repository that another (downstream) repository searches when it does not have a requested package. The package manager uses only the downstream repository endpoint, but it gets packages from both repositories.
  • A repository can have up to 10 upstream repositories.
  • An external connection links a repository to a public repository, such as npmjs.com, PyPI, or Maven Central.
  • When a build requests a package that the repository does not have, CodeArtifact gets it from the public repository and stores a copy. Builds can still download that stored copy when the public repository has an outage.
  • Each repository can have only one external connection.
  • Recommended pattern: one repository in the domain has the external connection. Other repositories use it as an upstream. Then you manage only one connection, and each public package version comes in one time for all teams.
  • Authenticate with aws codeartifact login (npm, pip, twine, dotnet, nuget, swift). This command gets a token and writes the repository endpoint and the token into the configuration of that tool.
  • For tools that login does not support (for example, Maven and Gradle), call get-authorization-token and put the token in the tool settings yourself.
  • The token is valid for 12 hours by default. You can set 15 minutes to 12 hours. After it expires, the package manager gets authentication errors until you get a new token.
  • Getting a token needs codeartifact:GetAuthorizationToken and sts:GetServiceBearerToken. CodeArtifact tokens are service bearer tokens that AWS STS creates. Without either permission, the call fails with AccessDenied.

CodeBuild buildspec: phases, artifacts, and reports

Remember

  • The default buildspec file is buildspec.yml in the root of the source directory.
  • To use another buildspec name or path, set it in the project, or set buildspecOverride on StartBuild.
  • A buildspec in an S3 bucket must be in the same Region as the build project.
  • A build project uses only one buildspec at a time.
  • Use buildspec version: 0.2. In 0.2, all commands run in the same shell instance.
  • In buildspec version 0.1, each command ran in a separate shell, so a cd or variable did not carry to the next command.
  • The buildspec phases are install, pre_build, build, and post_build.
  • Select runtimes with runtime-versions in the install phase.
  • A phase finally block runs even if a command in commands fails.
  • When a command fails, CodeBuild skips the remaining commands in that block and runs the finally block.
  • on-failure: ABORT stops the build. on-failure: CONTINUE goes to the next phase.
  • on-failure: RETRY retries the build up to 3 times.
  • RETRY-count sets the number of retries. RETRY-regex sets the error message that causes a retry.
  • CodeBuild always attempts the UPLOAD_ARTIFACTS phase, even if the BUILD phase fails.
  • Without run-as, buildspec commands run as root.
  • artifacts.files lists the paths to include. '**/*' means all files, recursively.
  • discard-paths: yes puts all artifact files at the top level, with no directories.
  • base-directory makes artifact paths relative to that directory. Files outside that directory are not in the artifact.
  • secondary-artifacts creates more than one output artifact. Each identifier must match the project secondaryArtifacts setting.
  • A build that only pushes an image to Amazon ECR or only runs tests does not need artifacts.
  • The buildspec reports section sends test or code coverage results to a report group.
  • CodeBuild test report formats: JUnit XML (the default), NUnit, TestNG, Cucumber JSON, and Visual Studio TRX.
  • CodeBuild coverage report formats: JaCoCo, Cobertura, Clover, and SimpleCov.
  • The CodeBuild build timeout default is 60 minutes. The range is 5 to 2,160 minutes (36 hours).
  • The CodeBuild queued timeout is 5 to 480 minutes.
  • A CodeBuild test report is available for 30 days after creation.
  • CodeDeploy reads appspec.yml only from the root of the bundle.

Exam signals

  • "Run a cleanup command even when tests fail" → put it in the phase finally block.
  • "Use buildspec-release.yml for some builds" → set the buildspec path in the project, or override it on StartBuild.
  • "appspec.yml must be at the root of the artifact" → list it in artifacts.files, and use discard-paths or base-directory to control the layout.
  • "Deployment fails, and appspec.yml is in a subdirectory of the artifact" → move it to the root. CodeDeploy reads appspec.yml only from the root of the bundle.
  • "Show test pass and fail trends" → CodeBuild reports.

Explanation

Key facts

  • The default buildspec file is buildspec.yml in the root of the source directory.
  • To use a different name or path, set the buildspec in the project, or set buildspecOverride on StartBuild.
  • You can store the buildspec in an S3 bucket. The bucket must be in the same Region as the build project.
  • A build project uses only one buildspec at a time.
  • Use version: 0.2. In 0.2, all commands run in the same shell instance, so a cd or a variable from one command is still in effect for the next command.
  • In version 0.1, each command ran in a separate shell, so a later command did not see these changes.

  • Each phase can have a finally block. The finally commands run even if a command in commands fails.
  • When a command fails, CodeBuild skips the remaining commands in that block and runs the finally block.
  • on-failure on a phase sets what happens when that phase fails.
  • ABORT stops the build. CONTINUE goes to the next phase, for example to run a report step after failed tests.
  • RETRY retries the build up to 3 times. RETRY-count and RETRY-regex set the number of retries and the error message that causes a retry.
  • CodeBuild always attempts the UPLOAD_ARTIFACTS phase, even if the BUILD phase fails. So you can get the output files of a failed build to find the cause.
  • run-as sets the Linux user. Without it, commands run as root.

Artifacts

  • artifacts.files: the paths to include. '**/*' means all files, recursively.
  • discard-paths: yes puts all files at the top level of the artifact, with no directories. Example: target/app.jar becomes app.jar at the root of the .zip file.
  • base-directory makes paths relative to that directory. The directory itself is not in the artifact.
  • Example: with base-directory: dist, the file dist/index.html is index.html in the artifact. Files outside dist are not in the artifact.
  • secondary-artifacts creates more than one output artifact, for example one .zip file for CodeDeploy and one for a test team. Each identifier in the buildspec must match an artifact in the project secondaryArtifacts setting.
  • You do not need artifacts if the build only pushes an image to Amazon ECR or only runs tests.

Reports

  • The reports section sends test or code coverage results to a report group. The console then shows each test with its pass or fail result, and the trend across builds. Without it, you must read test results in the build log.
  • Test formats include JUnit XML (the default), NUnit, TestNG, Cucumber JSON, and Visual Studio TRX.
  • Coverage formats include JaCoCo, Cobertura, Clover, and SimpleCov.

CodeBuild environment: variables, secrets, cache, Docker, and VPC

Remember

  • env.variables holds plaintext values that the console and the AWS CLI can show. Do not put secrets there.
  • env.parameter-store reads values from Parameter Store. The CodeBuild service role needs ssm:GetParameters.
  • env.secrets-manager reads from Secrets Manager. The format is secret-id:json-key:version-stage:version-id.
  • In env.secrets-manager, only secret-id is required. Without a json-key, the variable gets the whole secret text.
  • For a Secrets Manager secret in another account, use the secret ARN, not the secret name.
  • CodeBuild masks Parameter Store and Secrets Manager values in the logs, but masking matches only the exact stored value.
  • A command that changes a secret value (for example, Base64 encoding) and prints it shows the changed value in the log.
  • env.exported-variables makes build variables available to later CodePipeline actions. Example: #{BuildVariables.IMAGE_TAG}.
  • Do not create CodeBuild variables that start with CODEBUILD_. AWS reserves this prefix.
  • CodeBuild variable precedence: the StartBuild call (highest), then the build project, then the buildspec (lowest).
  • A CodeBuild cache has two types: Amazon S3 and local.
  • An S3 cache is available to every build host. Use it for small to medium files that take longer to build than to download.
  • A local cache is available only to builds on the same host. Use it for large files and frequent builds.
  • A CodeBuild local cache does not work for builds in a VPC.
  • CodeBuild local cache modes: source cache, Docker layer cache, and custom cache. You can select one or more.
  • The Docker layer cache works on Linux only and requires privileged mode.
  • To run docker build in CodeBuild, turn on privileged mode.
  • To push to Amazon ECR, the service role needs ECR permissions, and the build must run docker login first.
  • By default, a CodeBuild build runs outside your VPC and cannot reach private resources such as an RDS database.
  • A CodeBuild build in a VPC needs private subnets with a route to a NAT gateway or NAT instance.
  • An internet gateway alone does not work for CodeBuild, because CodeBuild does not assign public IP addresses.
  • CodeBuild security groups need no inbound rules.
  • CodeBuild sends build logs to CloudWatch Logs, Amazon S3, or both.
  • A CodeBuild build runs with the project service role. Add permissions to that role, not to the user who starts the build.
  • To test a buildspec on your computer, run the CodeBuild agent locally with Docker (codebuild_build.sh).

Exam signals

  • "Database password is in plaintext in the buildspec" → move it to Secrets Manager or a SecureString parameter, and reference it in env. The build gets the same variable name, and CodeBuild masks the value in logs.
  • "Build in a VPC cannot download packages" → private subnet with a route to a NAT gateway, because the build has no public IP address.
  • "Cannot connect to the Docker daemon" → turn on privileged mode. Without it, the Docker daemon cannot start in the build container.
  • "Builds download the same dependencies every time" → configure a cache.

Explanation

Environment variables

  • env.variables holds plaintext values. The console and the AWS CLI can show them. Do not put secrets there.
  • env.parameter-store reads values from Systems Manager Parameter Store. The service role needs ssm:GetParameters.
  • env.secrets-manager reads from Secrets Manager. Format: secret-id:json-key:version-stage:version-id. Only secret-id is required.
  • Example: DB_PASSWORD: prod/db:password puts the password key of the JSON secret prod/db into the variable DB_PASSWORD.
  • Without a json-key, the variable gets the whole secret text.
  • For a secret in another account, use the secret ARN, not the name. A secret name finds secrets only in the account of the build.
  • CodeBuild masks Parameter Store and Secrets Manager values in the logs. Masking matches only the exact stored value. If a command changes the value (for example, Base64 encoding) and prints it, the log shows the changed value.
  • env.exported-variables makes variables available to later actions in CodePipeline. Example: the build exports IMAGE_TAG, and the deploy action uses it as #{BuildVariables.IMAGE_TAG}, where BuildVariables is the namespace of the build action.
  • Do not create variables that start with CODEBUILD_. AWS reserves this prefix for the variables that CodeBuild sets itself, such as CODEBUILD_SRC_DIR.

Precedence when one name is set in more than one place

  1. The value in the StartBuild call (highest).
  2. The value in the build project.
  3. The value in the buildspec (lowest).

Use this order to change a value for one build without editing the buildspec. For example, set STAGE=prod in the StartBuild call to override STAGE=dev in the buildspec.

Cache

  • A cache keeps files, such as downloaded dependencies, from one build so that later builds do not download or build them again.
  • Two cache types: Amazon S3 and local.
  • An S3 cache is in a bucket, so every build host can use it. Choose it for small to medium files that take longer to build than to download.
  • A local cache is on the build host, so only builds that run on that host can use it. Choose it for large files and frequent builds, because it has no network transfer time.
  • Local cache does not work for builds in a VPC.
  • Local cache modes: source cache (Git metadata, so a build downloads only new commits), Docker layer cache (image layers), and custom cache (directories that you list in the buildspec cache paths). You can select one or more.
  • Docker layer cache works on Linux only. It requires privileged mode, because the Docker daemon must run in the build container to reuse layers.

Docker builds

  • To run docker build in a build, turn on privileged mode. It lets the Docker daemon run in the build container.
  • To push to Amazon ECR, the service role needs ECR permissions, and the build must sign in to ECR first. The docker push command uses the Docker sign-in, not the IAM role, so it fails without docker login.

VPC

  • By default, a build runs outside your VPC and cannot reach private resources. Configure a VPC, subnets, and security groups to reach private resources such as an RDS database.
  • Select private subnets only. Route internet traffic through a NAT gateway or NAT instance. Without that route, commands such as pip install or npm install time out.
  • An internet gateway alone does not work. A resource needs a public IP address to use an internet gateway, and CodeBuild does not assign public IP addresses to its network interfaces.
  • Security groups for builds need no inbound rules. The build only opens outbound connections, and security groups allow the response traffic automatically.

Logs and permissions

  • CodeBuild sends build logs to CloudWatch Logs, Amazon S3, or both.
  • The build runs with the project service role. Add permissions there, not to the user who starts the build.
  • A missing permission shows as an AccessDenied error in the build log, even when the user who started the build has that permission.
  • To test a buildspec on your computer, run the CodeBuild agent locally with Docker (codebuild_build.sh).

CodeDeploy for Lambda and AWS SAM traffic shifting

Remember

  • A Lambda alias points to a function version and can send a percentage of invocations to a second version.
  • CodeDeploy shifts Lambda traffic by changing the alias weights.
  • Clients must invoke the alias. A call with the unqualified function name runs $LATEST and skips the traffic split.
  • The Lambda AppSpec lists the function Name, Alias, CurrentVersion, and TargetVersion.
  • CodeDeploy Lambda deployments have no agent and no instances. Only traffic moves.
  • Lambda canary configurations move 10 percent first, then the remaining 90 percent after 5, 10, 15, or 30 minutes.
  • Lambda linear configurations move 10 percent more every 1, 2, 3, or 10 minutes until all traffic moves.
  • CodeDeployDefault.LambdaAllAtOnce moves all traffic at once.
  • You can create a custom canary or linear configuration, for example 20 percent every 5 minutes.
  • Use canary to test on a small share of users for a fixed time, then move the rest in one step.
  • Use linear to increase traffic in equal steps, so that a problem affects fewer users before an alarm stops it.
  • Use all at once when speed matters more than risk, for example in a development account.
  • The Lambda deployment hooks are BeforeAllowTraffic (before any traffic moves) and AfterAllowTraffic (after all traffic moves).
  • Use BeforeAllowTraffic to test the new version before any user reaches it.
  • A Lambda hook function must call PutLifecycleEventHookExecutionStatus with Succeeded or Failed.
  • If CodeDeploy gets no hook status within one hour, the deployment fails.
  • The hook function role needs the codedeploy:PutLifecycleEventHookExecutionStatus permission.
  • SAM AutoPublishAlias publishes a new version when the code changes and points the alias at it.
  • SAM DeploymentPreference needs AutoPublishAlias. Without it, SAM returns an error.
  • SAM DeploymentPreference sets Type, Alarms, and Hooks (PreTraffic, PostTraffic).
  • SAM creates the CodeDeploy application and deployment group for you.
  • CodeDeploy rolls back the deployment if a hook fails or an alarm goes into the ALARM state.

Exam signals

  • "10 percent of traffic for 10 minutes, then the rest" → canary (Canary10Percent10Minutes).
  • "Increase traffic in equal steps" → linear.
  • "Roll back automatically when errors increase" → CloudWatch alarms in the deployment preference.
  • "Hook tests pass, but the deployment fails after one hour" → the hook did not call PutLifecycleEventHookExecutionStatus.

Explanation

Key facts

  • A Lambda alias is a name (for example live) that points to a function version. An alias can send a percentage of invocations to a second version.
  • CodeDeploy shifts traffic by changing these alias weights.
  • Clients must invoke the alias. A call with the unqualified function name runs $LATEST, so it skips the alias and the traffic split.
  • The Lambda AppSpec lists the function Name, Alias, CurrentVersion, and TargetVersion.
  • Lambda deployments have no agent and no instances. Only traffic moves.
  • You can create a custom canary or linear configuration when the predefined percentages and intervals do not fit, for example 20 percent every 5 minutes.

Hooks

  • Two hooks: BeforeAllowTraffic (before any traffic moves) and AfterAllowTraffic (after all traffic moves).
  • Use BeforeAllowTraffic to run tests against the new version before any user reaches it. Use AfterAllowTraffic to check the result after the shift.
  • Each hook is a Lambda function. It must call PutLifecycleEventHookExecutionStatus with Succeeded or Failed.
  • If CodeDeploy gets no status within one hour, the deployment fails.
  • The hook function role needs the codedeploy:PutLifecycleEventHookExecutionStatus permission.

AWS SAM

  • AutoPublishAlias publishes a new version when the code changes and points the alias at it. DeploymentPreference needs it: without AutoPublishAlias, SAM returns an error.
  • DeploymentPreference sets Type (for example Canary10Percent10Minutes), Alarms, and Hooks (PreTraffic, PostTraffic).
  • SAM creates the CodeDeploy application and deployment group for you.
  • If a hook fails or an alarm goes into the ALARM state, CodeDeploy rolls back the deployment.

CodeDeploy for EC2: AppSpec, hooks, rollbacks, and troubleshooting

Remember

  • The CodeDeploy agent must run on each instance. The agent downloads the revision and runs the hook scripts.
  • CodeDeploy instances need an IAM instance profile that can read the revision from Amazon S3 (or GitHub).
  • The CodeDeploy service role for EC2/On-Premises uses the AWSCodeDeployRole managed policy.
  • A CodeDeploy deployment group selects instances by tags or by Auto Scaling group.
  • With an Auto Scaling group, CodeDeploy installs the current revision on each new instance that the group launches.
  • Put appspec.yml at the root of the revision bundle. The files section maps source to destination.
  • An in-place deployment updates the same instances. Each instance is out of service during its update.
  • A blue/green deployment updates replacement instances. The load balancer moves traffic to them.
  • Choose in-place when you cannot pay for extra instances and a slower rollback is acceptable.
  • Choose blue/green for a fast rollback and no loss of capacity, if you can pay for a second set of instances.
  • The EC2 hook order is ApplicationStop, BeforeInstall, AfterInstall, ApplicationStart, ValidateService.
  • DownloadBundle, Install, BlockTraffic, and AllowTraffic are reserved for the agent. You cannot attach scripts to them.
  • The six EC2 traffic hooks (BeforeBlockTraffic to AfterAllowTraffic) run only if the deployment group has a load balancer.
  • ApplicationStop uses the AppSpec and scripts from the last successful revision.
  • ApplicationStop does not run on the first deployment to an instance.
  • If a broken ApplicationStop script blocks every deployment, deploy with --ignore-application-stop-failures.
  • Use BeforeInstall for pre-install tasks, AfterInstall for configuration and permissions, and ValidateService to check the result.
  • The hook script timeout default is 3,600 seconds. 3,600 seconds is also the maximum for all scripts in one lifecycle event.
  • Wait at least 5 minutes after you tag an instance before you deploy to it.
  • A terminated instance during a lifecycle event can take up to one hour to show Failed.
  • CodeDeployDefault.OneAtATime is the default EC2 deployment configuration.
  • OneAtATime fails as soon as any instance except the last one fails. A failure on only the last instance still succeeds.
  • HalfAtATime updates up to half of the instances at a time. It succeeds if at least half succeed.
  • AllAtOnce updates all instances at once. It succeeds if at least one instance succeeds.
  • A custom configuration sets a minimum healthy hosts value, as a number or a percentage.
  • A zonal configuration updates one Availability Zone at a time. Zonal settings need a custom configuration.
  • Choose OneAtATime for the most capacity and AllAtOnce for the fastest deployment.
  • A CodeDeploy rollback is a new deployment with a new deployment ID. It deploys the last known good revision.
  • Automatic rollback triggers are a failed deployment or a CloudWatch alarm threshold.
  • For a destination file that no earlier deployment put there, CodeDeploy fails the deployment by default. Other options: overwrite or retain.
  • The CodeDeploy deployment log (Amazon Linux) is /opt/codedeploy-agent/deployment-root/deployment-logs/codedeploy-agent-deployments.log.
  • The CodeDeploy agent log is /var/log/aws/codedeploy-agent/codedeploy-agent.log. Script output is in scripts.log.
  • The CodeDeploy agent writes logs only to the instance disk. To see them in CloudWatch, install the CloudWatch agent.
  • Common CodeDeploy failures: the agent is not running, the tags do not match, or the instance profile cannot read the bucket.
  • CloudFormation stack events show the first resource that failed.

Exam signals

  • "Change file permissions after the files are copied" → AfterInstall.
  • "ApplicationStop fails, and fixing the script in the new revision does not help" → the old revision's script runs. Use --ignore-application-stop-failures.
  • "Restore the last good version automatically" → automatic rollback on failure or alarm.
  • "Deploy fast but keep half of the fleet in service" → HalfAtATime.

Explanation

Key facts

  • The CodeDeploy agent must run on each instance. It downloads the revision and runs the hook scripts.
  • The instances need an IAM instance profile that can read the revision from Amazon S3 (or GitHub).
  • CodeDeploy needs a service role. CodeDeploy uses it to read instance tags, Auto Scaling groups, and load balancers. For EC2/On-Premises, attach the AWSCodeDeployRole managed policy.
  • A deployment group selects instances by tags or by Auto Scaling group. Choose an Auto Scaling group when the fleet scales: CodeDeploy then installs the current revision on each new instance that the group launches.
  • Put appspec.yml at the root of the revision bundle. The files section maps source to destination.

CodePipeline: stages, actions, approvals, and executions

Remember

  • A CodePipeline pipeline has stages, and each stage has actions.
  • Actions with the same runOrder number run in parallel. A higher number starts after the lower numbers finish.
  • CodePipeline action categories: Source, Build, Test, Deploy, Approval, and Invoke.
  • An Invoke action runs a Lambda function or a Step Functions state machine.
  • CodePipeline actions pass input and output artifacts through an S3 artifact store.
  • With more than one source action, all source actions run again when one source changes.
  • A failed action stops the execution. You can retry the failed stage.
  • Disable a transition to stop executions from entering a stage, for example during a production change freeze.
  • At a disabled transition, the newest execution waits. When you enable the transition, the newest execution enters the stage.
  • A CloudFormation action error shows the first failed resource when the role has cloudformation:DescribeStackEvents.
  • A manual approval action stops the pipeline until a person approves or rejects.
  • An approval action can publish to an SNS topic in the same Region and include a URL for review.
  • A rejected approval, or no response within seven days, has the same result as a failed action.
  • Approvers need the codepipeline:PutApprovalResult permission.
  • SUPERSEDED is the default execution mode. A newer execution can replace an older one that waits between stages.
  • QUEUED mode (V2 only) runs executions one by one, in order. It skips none.
  • PARALLEL mode (V2 only) runs executions at the same time. It has no stage rollback.
  • Choose SUPERSEDED when only the newest commit matters. Choose QUEUED when every commit must deploy, in order.
  • Choose PARALLEL when executions are independent, for example to test feature branches at the same time.
  • V2 pipeline triggers can filter on Git tags, branches, pull requests, and file paths.
  • V2 pipeline-level variables get values when an execution starts. Actions use them as #{variables.name}.
  • V2 stage rollback runs a stage again with the source revisions and variables of an earlier successful execution.
  • V2 stage conditions check rules before a stage starts, or after it succeeds or fails.
  • A stage condition result can fail the stage, skip the stage, or roll it back.
  • V2 automatic stage retry retries a failed stage or its failed actions with no manual step.
  • The V2 Commands action runs shell commands on CodeBuild compute, with no CodeBuild project to create.
  • CREATE_UPDATE creates the stack, or updates it if it exists.
  • CHANGE_SET_REPLACE creates a change set and does not change the stack.
  • CHANGE_SET_EXECUTE runs the change set and changes the stack.
  • REPLACE_ON_FAILURE deletes and creates again a stack in a failed state. Use it for tests only.
  • REPLACE_ON_FAILURE deletes the stack resources too, unless their DeletionPolicy is Retain.
  • A DeletionPolicy of Snapshot saves a snapshot before the delete. Snapshot is the default for most RDS databases.
  • DELETE_ONLY deletes the stack.
  • To review infrastructure changes first, use CHANGE_SET_REPLACE, then CHANGE_SET_EXECUTE.

Elastic Beanstalk deployment policies and blue/green

Remember

  • All at once is the default DeploymentPolicy. It deploys to existing instances and causes downtime.
  • Rolling deploys to existing instances one batch at a time. It has no downtime, but less capacity.
  • Rolling with additional batch deploys to new and existing instances. It keeps full capacity.
  • Immutable deploys to new instances in a second Auto Scaling group. Rollback terminates the new instances.
  • Traffic splitting deploys to new instances and sends a percentage of traffic to them.
  • Traffic splitting rollback reroutes traffic and terminates the new instances.
  • All at once, Rolling, and Rolling with additional batch roll back with a manual redeploy.
  • Elastic Beanstalk blue/green is not a deployment policy. It deploys to a new environment.
  • Elastic Beanstalk blue/green rolls back when you swap the URLs back.
  • Choose All at once for speed when downtime is acceptable, for example in development.
  • Choose Rolling to avoid downtime with no extra instance cost, if reduced capacity is acceptable.
  • Choose Rolling with additional batch to keep full capacity for the cost of one extra batch.
  • Choose Immutable for the safest deployment and the fastest rollback.
  • Choose Traffic splitting to test the new version on a percentage of real users first.
  • Only Elastic Beanstalk blue/green changes DNS. All other methods keep the same DNS name.
  • After a DNS change, some clients keep the old address in their DNS cache and reach the old environment.
  • Rolling, Rolling with additional batch, and Traffic splitting need a load-balanced environment.
  • Traffic splitting needs an Application Load Balancer.
  • All at once and Immutable also work in single-instance environments.
  • Traffic splitting defaults: 10 percent of traffic to the new version, and an evaluation time of 5 minutes.
  • If the new instances stay healthy during evaluation, traffic splitting moves all traffic to them and terminates the old instances.
  • If the new instances are not healthy, traffic splitting moves traffic back and terminates the new instances.
  • The Elastic Beanstalk batch size is a percentage or a fixed number of instances.
  • Use a percentage batch size when the number of instances changes, so that each batch grows with the fleet.
  • Use a fixed batch size when you must know how many instances are out of service at a time.
  • For Elastic Beanstalk blue/green, deploy to a second environment, test it, then use Swap environment URLs (CNAME swap).
  • Use Elastic Beanstalk blue/green when the new version cannot run alongside the old version, or when resource configuration changes.
  • A database coupled to one Elastic Beanstalk environment blocks blue/green. Keep the database outside the environment.
  • When you terminate the old environment, its deletion policy deletes a coupled database, or keeps only a snapshot, unless the policy is Retain.

Elastic Beanstalk environments, configuration, and databases

Remember

  • An Elastic Beanstalk application has application versions and environments. Each environment runs one version.
  • An Elastic Beanstalk web server environment serves HTTP.
  • An Elastic Beanstalk worker environment processes messages from an Amazon SQS queue.
  • Use a worker environment for long tasks, such as image processing or email, so that the web tier stays fast.
  • In a worker environment, a daemon sends each SQS message as an HTTP POST to http://localhost/ on port 80.
  • In a worker environment, a 200 OK response deletes the message.
  • In a worker environment, any other response returns the message to the queue after the error visibility timeout.
  • After the maximum retries (default 10), a worker message goes to the dead-letter queue.
  • An automatically generated worker queue has a dead-letter queue by default.
  • Put cron.yaml in the source bundle to queue periodic tasks in a worker environment.
  • Leader election makes one instance queue each periodic task, so the job does not run on every instance.
  • Elastic Beanstalk periodic tasks do not work with a FIFO queue.
  • Elastic Beanstalk uses CloudFormation to create the environment resources.
  • Platform hooks (Amazon Linux 2 and later) go in .platform/hooks/: prebuild, predeploy, and postdeploy.
  • The prebuild hook runs after the bundle is extracted, before the app and web server are configured.
  • The predeploy hook runs before the app moves to its final location. The postdeploy hook runs last.
  • .platform/confighooks/ runs for configuration deployments, which apply changed settings with no new application version.
  • Platform hook files run in lexicographical order, as root. A non-zero exit code fails the deployment.
  • .ebextensions commands run before the bundle is extracted, so they cannot see your code.
  • .ebextensions commands run before prebuild.
  • container_commands run after the bundle is extracted and before the app is deployed, so they can change your code.
  • container_commands run before predeploy.
  • Elastic Beanstalk configuration precedence: direct settings, then saved configurations, then .ebextensions files, then default values.
  • Direct settings come from the console, the EB CLI, the AWS CLI, or an SDK.
  • .ebextensions files are YAML or JSON files with the .config extension, at the root of the source bundle.
  • .ebextensions files run in alphabetical order.
  • When the console creates an environment, it applies recommended values for DeploymentPolicy, BatchSize, and BatchSizeType.
  • When the EB CLI creates an environment, it applies recommended values for BatchSize and BatchSizeType.
  • Recommended values are direct settings, so they override the same options in .ebextensions.
  • To let a configuration file set these options, first remove the direct settings with the AWS CLI or the EB CLI.
  • A database that you add in Elastic Beanstalk is coupled to the environment.
  • A coupled database gives the app RDS_HOSTNAME, RDS_PORT, RDS_DB_NAME, RDS_USERNAME, and RDS_PASSWORD.
  • A coupled database has the same lifecycle as the environment.
  • When you terminate the environment, the deletion policy decides what happens to the coupled database: Snapshot, Delete, or Retain.
  • For production, use a decoupled database outside the environment. Several environments can use it, and blue/green works.
  • Elastic Beanstalk has a quota of 1,000 application versions per Region, across all applications.
  • At the application version quota, you cannot create a new version, so deployments of new code fail.
  • An application version lifecycle policy deletes old versions by count or by age.
  • An application version lifecycle policy can also delete the source bundle from Amazon S3.

  • "Cannot create new application versions" → quota reached. Add a version lifecycle policy.
  • "Value in .ebextensions is ignored" → a setting with higher precedence (direct or saved configuration) overrides it.
