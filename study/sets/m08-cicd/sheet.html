Source and package repositories: CodeCommit and CodeArtifact

Git repositories and triggers

  • A commit to a Git repository (CodeCommit, GitHub, GitLab, Bitbucket) can start a pipeline. CodePipeline uses EventBridge or a connection to detect the change.
  • Use branches for environments and Git tags for releases. A V2 pipeline can filter triggers on branches, tags, and file paths.

CodeCommit (short note)

  • AWS CodeCommit is a managed Git service. IAM controls access. Exam guide v2.1 does not list it, but questions can still describe it.
  • AWS closed CodeCommit to new customers in July 2024. AWS made it available to new customers again in November 2025.
  • HTTPS Git credentials and SSH keys belong to an IAM user. With federated access or temporary credentials, use git-remote-codecommit.
  • To stop some users from pushing to a branch, use an IAM Deny policy on codecommit:GitPush and the merge actions, with the codecommit:References condition (for example refs/heads/main).

CodeArtifact

  • AWS CodeArtifact is a managed package repository for npm, PyPI, Maven, NuGet, and other formats.
  • A domain groups repositories. The domain stores each asset one time and encrypts all assets with one KMS key.
  • A repository holds package versions. One repository can hold several package formats.
  • An upstream repository makes its packages available through the downstream repository endpoint.
  • An external connection links a repository to a public repository, such as npmjs.com, PyPI, or Maven Central. Each repository can have only one external connection.
  • Recommended pattern: one repository in the domain has the external connection. Other repositories use it as an upstream.
  • Authenticate with aws codeartifact login (npm, pip, twine, dotnet, nuget, swift) or get-authorization-token (for example, Maven and Gradle).
  • The token is valid for 12 hours by default. You can set 15 minutes to 12 hours.
  • Getting a token needs codeartifact:GetAuthorizationToken and sts:GetServiceBearerToken.

Exam signals

  • "Builds must get open-source packages through a private, approved repository" → CodeArtifact with an external connection.
  • "Maven build cannot authenticate to CodeArtifact" → call get-authorization-token and pass the token, for example in CODEARTIFACT_AUTH_TOKEN.
  • "Developers use federation or temporary credentials with CodeCommit" → git-remote-codecommit.
  • "Only senior developers can push to main" → IAM Deny with codecommit:References.

CodeBuild buildspec: phases, artifacts, and reports

Key facts

  • The default buildspec file is buildspec.yml in the root of the source directory.
  • To use a different name or path, set the buildspec in the project, or set buildspecOverride on StartBuild.
  • You can store the buildspec in an S3 bucket. The bucket must be in the same Region as the build project.
  • A build project uses only one buildspec at a time.
  • Use version: 0.2. In 0.2, all commands run in the same shell instance, so cd and variables carry over.

Phases

PhaseTypical use
installInstall packages and tools. Select runtimes with runtime-versions.
pre_buildSign in to Amazon ECR. Install dependencies.
buildCompile, run tests, package.
post_buildPackage artifacts, push a Docker image, send notifications.
  • Each phase can have a finally block. The finally commands run even if a command in commands fails.
  • When a command fails, CodeBuild skips the remaining commands in that block and runs the finally block.
  • on-failure on a phase: ABORT, CONTINUE (go to the next phase), or RETRY variants.
  • CodeBuild always attempts the UPLOAD_ARTIFACTS phase, even if the BUILD phase fails.
  • run-as sets the Linux user. Without it, commands run as root.

Artifacts

  • artifacts.files: the paths to include. '**/*' means all files, recursively.
  • discard-paths: yes puts all files at the top level of the artifact, with no directories.
  • base-directory makes paths relative to that directory. The directory itself is not in the artifact.
  • secondary-artifacts creates more than one output artifact. The project must define each one.
  • You do not need artifacts if the build only pushes an image to Amazon ECR or only runs tests.

Reports

  • The reports section sends test or code coverage results to a report group.
  • Test formats include JUnit XML (the default), NUnit, TestNG, Cucumber JSON, and Visual Studio TRX.
  • Coverage formats include JaCoCo, Cobertura, Clover, and SimpleCov.

Numbers to memorize

ItemValue
Build timeoutDefault 60 minutes. Range 5 to 2,160 minutes (36 hours).
Queued timeout5 to 480 minutes
Test report availability30 days after creation

Exam signals

  • "Run a cleanup command even when tests fail" → put it in the phase finally block.
  • "Use buildspec-release.yml for some builds" → set the buildspec path in the project, or override it on StartBuild.
  • "appspec.yml must be at the root of the artifact" → list it in artifacts.files. Use discard-paths or base-directory to control the layout.
  • "Show test pass and fail trends" → CodeBuild reports.

CodeBuild environment: variables, secrets, cache, Docker, and VPC

Environment variables

  • env.variables holds plaintext values. The console and the AWS CLI can show them. Do not put secrets there.
  • env.parameter-store reads values from Systems Manager Parameter Store. The service role needs ssm:GetParameters.
  • env.secrets-manager reads from Secrets Manager. Format: secret-id:json-key:version-stage:version-id. Only secret-id is required.
  • For a secret in another account, use the secret ARN, not the name.
  • CodeBuild masks Parameter Store and Secrets Manager values in the logs. A changed value (for example, Base64) is not masked.
  • env.exported-variables makes variables available to later actions in CodePipeline.
  • Do not create variables that start with CODEBUILD_. AWS reserves this prefix.

Precedence when one name is set in more than one place

  1. The value in the StartBuild call (highest).
  2. The value in the build project.
  3. The value in the buildspec (lowest).

Cache

  • Two cache types: Amazon S3 and local.
  • Local cache modes: source cache, Docker layer cache, and custom cache. You can select one or more.
  • Docker layer cache works on Linux only and requires privileged mode.

Docker builds

  • To run docker build in a build, turn on privileged mode. It lets the Docker daemon run in the build container.
  • To push to Amazon ECR, the service role needs ECR permissions, and the build must sign in to ECR first.

VPC

  • Configure a VPC, subnets, and security groups to reach private resources such as an RDS database.
  • Select private subnets only. Route internet traffic through a NAT gateway or NAT instance.
  • An internet gateway alone does not work. CodeBuild does not assign public IP addresses to its network interfaces.
  • Security groups for builds need no inbound rules.

Logs and permissions

  • CodeBuild sends build logs to CloudWatch Logs, Amazon S3, or both.
  • The build runs with the project service role. Add permissions there, not to the user who starts the build.
  • To test a buildspec on your computer, run the CodeBuild agent locally with Docker (codebuild_build.sh).

Exam signals

  • "Database password is in plaintext in the buildspec" → move it to Secrets Manager or a SecureString parameter. Reference it in env.
  • "Build in a VPC cannot download packages" → private subnet with a route to a NAT gateway.
  • "Cannot connect to the Docker daemon" → turn on privileged mode.
  • "Builds download the same dependencies every time" → configure a cache.

References: Buildspec env section, Build caching, CodeBuild with a VPC. Lab: Lab 8.2 CodeBuild.

CodeDeploy for Lambda and AWS SAM traffic shifting

Key facts

  • CodeDeploy shifts traffic between two versions of a function through an alias. Clients must invoke the alias.
  • The Lambda AppSpec lists the function Name, Alias, CurrentVersion, and TargetVersion.
  • Lambda deployments have no agent and no instances. Only traffic moves.
  • You can create a custom canary or linear configuration.

Predefined deployment configurations

TypeNames (prefix CodeDeployDefault.Lambda)Behavior
CanaryCanary10Percent5Minutes, 10Minutes, 15Minutes, 30Minutes10 percent first. The remaining 90 percent after the interval.
LinearLinear10PercentEvery1Minute, Every2Minutes, Every3Minutes, Every10Minutes10 percent more at each interval until all traffic moves
All at onceAllAtOnceAll traffic at once

Hooks

  • Two hooks: BeforeAllowTraffic (before any traffic moves) and AfterAllowTraffic (after all traffic moves).
  • Each hook is a Lambda function. It must call PutLifecycleEventHookExecutionStatus with Succeeded or Failed.
  • If CodeDeploy gets no status within one hour, the deployment fails.
  • The hook function role needs the codedeploy:PutLifecycleEventHookExecutionStatus permission.

AWS SAM

  • AutoPublishAlias publishes a new version when the code changes and points the alias at it.
  • DeploymentPreference sets Type (for example Canary10Percent10Minutes), Alarms, and Hooks (PreTraffic, PostTraffic).
  • SAM creates the CodeDeploy application and deployment group for you.
  • If a hook fails or an alarm goes into the ALARM state, CodeDeploy rolls back the deployment.

Exam signals

  • "10 percent of traffic for 10 minutes, then the rest" → canary (Canary10Percent10Minutes).
  • "Increase traffic in equal steps" → linear.
  • "Roll back automatically when errors increase" → CloudWatch alarms in the deployment preference.
  • "Hook tests pass, but the deployment fails after one hour" → the hook did not call PutLifecycleEventHookExecutionStatus.

References: Deployment configurations, AppSpec hooks, SAM gradual deployments. Lab: Lab 8.3 CodeDeploy for Lambda.

CodeDeploy for EC2: AppSpec, hooks, rollbacks, and troubleshooting

Key facts

  • The CodeDeploy agent must run on each instance. It downloads the revision and runs the hook scripts.
  • The instances need an IAM instance profile that can read the revision from Amazon S3 (or GitHub).
  • CodeDeploy needs a service role. For EC2/On-Premises, attach the AWSCodeDeployRole managed policy.
  • A deployment group selects instances by tags or by Auto Scaling group.
  • Put appspec.yml at the root of the revision bundle. The files section maps source to destination.

In-place compared to blue/green

ItemIn-placeBlue/green
InstancesThe same instances get the new revisionA new set of replacement instances gets the new revision
TrafficEach instance is out of service during its updateThe load balancer moves traffic to the replacement instances
RollbackDeploy the last good revision againSend traffic back to the original instances, if you keep them

Hook order (in-place, with a load balancer)

BeforeBlockTraffic → BlockTraffic → AfterBlockTraffic → ApplicationStop → DownloadBundle → BeforeInstall → Install → AfterInstall → ApplicationStart → ValidateService → BeforeAllowTraffic → AllowTraffic → AfterAllowTraffic

  • DownloadBundle, Install, BlockTraffic, and AllowTraffic are reserved for the agent. You cannot attach scripts to them.
  • The six traffic hooks run only if the deployment group has a load balancer.
  • ApplicationStop uses the AppSpec and scripts from the last successful revision. It does not run on the first deployment to an instance.
  • If a broken ApplicationStop script blocks every deployment, create a deployment with --ignore-application-stop-failures.
  • Use BeforeInstall for pre-install tasks, AfterInstall for configuration and permissions, and ValidateService to check the result.

Numbers to memorize

ItemValue
Hook script timeoutDefault 3,600 seconds. 3,600 seconds is also the maximum for all scripts in one lifecycle event.
Wait after you tag an instanceAt least 5 minutes before you deploy, so that CodeDeploy can read the tags
Terminated instance during a lifecycle eventThe deployment can take up to one hour to show Failed

Deployment configurations (EC2/On-Premises)

NameIn-place behavior
CodeDeployDefault.OneAtATime (default)One instance at a time. Fails at the first failure, except on the last instance.
CodeDeployDefault.HalfAtATimeUp to half of the instances at a time. Succeeds if at least half succeed.
CodeDeployDefault.AllAtOnceAll instances at once. Succeeds if at least one instance succeeds.
CustomSet a minimum healthy hosts value (number or percentage). Zonal settings need a custom configuration.

Rollbacks

  • A rollback is a new deployment with a new deployment ID. It deploys the last known good revision.
  • Turn on automatic rollback on the deployment group or deployment. Triggers: the deployment fails, or a CloudWatch alarm threshold is met.
  • For files that are already at the destination, select one: fail the deployment, overwrite, or retain.

Troubleshooting

  • Deployment log (Amazon Linux): /opt/codedeploy-agent/deployment-root/deployment-logs/codedeploy-agent-deployments.log.
  • Agent log: /var/log/aws/codedeploy-agent/codedeploy-agent.log. Script output: scripts.log under the deployment folder.
  • To see the logs in CloudWatch, install the CloudWatch agent on the instances.
  • Common causes of failure: the agent is not running, the tags do not match, or the instance profile cannot read the bucket.
  • Other deployment logs: CodeBuild writes build logs to CloudWatch Logs. CloudFormation stack events show the first resource that failed.

Exam signals

  • "Change file permissions after the files are copied" → AfterInstall.
  • "ApplicationStop fails, and fixing the script in the new revision does not help" → the old revision's script runs. Use --ignore-application-stop-failures.
  • "Restore the last good version automatically" → automatic rollback on failure or alarm.
  • "Deploy fast but keep half of the fleet in service" → HalfAtATime.

References: AppSpec hooks, Deployment configurations, Rollback and redeploy, Troubleshoot instances, Deployment logs. Lab: Lab 8.4 CodeDeploy for EC2.

CodeDeploy blue/green for Amazon ECS

Key facts

  • CodeDeploy creates a replacement (green) task set with the new task definition. Then it moves load balancer traffic to it.
  • The ECS service must use the CODE_DEPLOY deployment controller.
  • The deployment group names two target groups and a production listener. A test listener is optional.
  • The ECS AppSpec lists TaskDefinition, and LoadBalancerInfo with ContainerName and ContainerPort.
  • ECS deployments have no agent. Hooks are Lambda functions, as for Lambda deployments.
  • The service role can use the AWSCodeDeployRoleForECS managed policy.

Hooks, in order

HookWhen it runs
BeforeInstallBefore CodeDeploy creates the replacement task set. No rollback is possible here.
AfterInstallAfter the replacement task set exists and has a target group
AfterAllowTestTrafficAfter the test listener sends traffic to the replacement task set
BeforeAllowTrafficBefore production traffic moves to the replacement task set
AfterAllowTrafficAfter production traffic moves to the replacement task set

Predefined configurations

  • CodeDeployDefault.ECSCanary10Percent5Minutes and ECSCanary10Percent15Minutes.
  • CodeDeployDefault.ECSLinear10PercentEvery1Minutes and ECSLinear10PercentEvery3Minutes.
  • CodeDeployDefault.ECSAllAtOnce. With a Network Load Balancer, only this predefined configuration is supported.

Note: native ECS strategies

Since 2025, the ECS deployment controller also has native blue/green, linear, and canary strategies, with Lambda lifecycle hooks and a bake time. Exam questions usually describe the CodeDeploy pattern. Read the stem for the service that it names.

Exam signals

  • "Test the new task set on port 8080 before customers see it" → test listener and an AfterAllowTestTraffic hook.
  • "CodeDeploy blue/green for ECS" → CODE_DEPLOY controller and two target groups.
  • "Network Load Balancer with CodeDeploy canary" → not supported. Only ECSAllAtOnce.

References: ECS AppSpec hooks, ECS deployment configurations, ECS native blue/green, ECS linear and canary (October 2025). Lab: Lab 8.5 CodeDeploy for ECS.

CodePipeline: stages, actions, approvals, and executions

Key facts

  • A pipeline has stages. Each stage has actions. Actions in a stage can run in parallel or in order (runOrder).
  • Action categories: Source, Build, Test, Deploy, Approval, Invoke.
  • Actions pass input and output artifacts through an S3 artifact store.
  • With more than one source action, all source actions run again when one source changes.
  • A failed action stops the execution. You can retry the failed stage, or a newer execution can take its place.
  • Disable a transition to stop executions from entering a stage.
  • If a CloudFormation deploy action fails, the error message shows the first failed resource when the role has cloudformation:DescribeStackEvents.

Manual approval

  • An approval action stops the pipeline until a person approves or rejects.
  • It can publish to an SNS topic in the same Region and include a URL for review.
  • Rejected, or no response within seven days: the result is the same as a failed action.
  • Approvers need the codepipeline:PutApprovalResult permission.

Execution modes

ModeBehaviorPipeline type
SUPERSEDED (default)A newer execution can replace an older one that waits between stagesV1 and V2
QUEUEDExecutions run one by one, in order. None is skipped.V2 only
PARALLELExecutions run at the same time and do not wait. No stage rollback.V2 only

V2-only features

  • Triggers with filters on Git tags, branches, pull requests, and file paths.
  • Pipeline-level variables, stage rollback, stage conditions, automatic stage retry, and the Commands action.

CloudFormation deploy action modes

ModeWhat it does
CREATE_UPDATECreates the stack, or updates it if it exists
CHANGE_SET_REPLACECreates a change set (replaces an existing one with the same name). Does not change the stack.
CHANGE_SET_EXECUTERuns the change set and changes the stack
REPLACE_ON_FAILUREDeletes and creates again a stack in a failed state. For tests only.
DELETE_ONLYDeletes the stack

Exam signals

  • "A person must approve before production" → manual approval action, with SNS for notification.
  • "Process every commit in order" → V2 pipeline in QUEUED mode.
  • "Review infrastructure changes before they apply" → CHANGE_SET_REPLACE, approval, then CHANGE_SET_EXECUTE.
  • "Start only when a release tag is pushed" → V2 trigger with a Git tag filter.

References: How pipeline executions work, V1 and V2 pipeline types, Manual approvals, CloudFormation action reference. Lab: Lab 8.6 CodePipeline.

Pipeline security: service roles, encryption, and cross-account access

Roles in a pipeline

RoleUsed byNeeds
CodePipeline service roleCodePipelineAccess to the artifact bucket and permission to start each action
CodeBuild service roleThe build containerLogs, artifact bucket, and any service the build calls (ECR, Parameter Store, Secrets Manager)
CodeDeploy service roleCodeDeployAWSCodeDeployRole (EC2), AWSCodeDeployRoleForLambda, or AWSCodeDeployRoleForECS
EC2 instance profileThe CodeDeploy agent on each instanceRead access to the revision bucket
CloudFormation role (RoleArn)CloudFormation in a deploy actionPermission to create the stack resources. The pipeline role needs iam:PassRole for it.

Cross-account pipelines

  • Use a customer managed AWS KMS key for the artifact store. The default AWS managed key does not work across accounts.
  • The key policy must allow the other account. The artifact bucket policy must also allow it.
  • The other account creates a role that the pipeline service role can assume. The action uses that role (roleArn).
  • For cross-account actions, identify the key by key ID or key ARN. Aliases work only in the account that owns the key.

Least privilege

  • To let only some people approve, allow codepipeline:PutApprovalResult on that approval action only.
  • Keep secrets in Secrets Manager or Parameter Store. Do not put secrets in source code, plaintext variables, or artifacts.
  • Grant each service role only the actions and resources it uses.

Exam signals

  • "Pipeline in account A deploys to account B" → customer managed KMS key, bucket policy, and a role in account B.
  • "Only release managers can approve" → IAM policy with codepipeline:PutApprovalResult on that action.
  • "Agent cannot download the revision" → the instance profile lacks S3 read access.

References: Cross-account pipelines, CodeDeploy service role, CodeDeploy instance profile. Lab: Lab 8.6 CodePipeline.

AWS CDK: constructs, bootstrap, and CLI commands

Key facts

  • The AWS CDK defines infrastructure in code (TypeScript, Python, Java, C#, Go). It synthesizes CloudFormation templates.
  • A CDK deployment is a CloudFormation stack deployment. Rollback and change sets work as in CloudFormation.
  • CDK v1 support ended on June 1, 2023. Use CDK v2.

Construct levels

LevelWhat it isExample
L1One-to-one with a CloudFormation resource. Names start with Cfn.CfnFunction
L2One resource with useful defaults and helper methodslambda.Function, table.grantReadData(fn)
L3 (patterns)Several resources that work togetherLambdaRestApi

Bootstrap

  • Bootstrap each AWS environment (account and Region) before you deploy to it: cdk bootstrap aws://ACCOUNT/REGION.
  • Bootstrap creates an S3 bucket for assets, an ECR repository for images, and IAM roles for deployment.
  • The bootstrap stack name is CDKToolkit by default.
  • Without bootstrap, only stacks with no assets and a template under 51,200 bytes deploy.

CLI commands

CommandWhat it does
cdk synthSynthesizes the CloudFormation template locally
cdk diffCompares the app with the deployed stack
cdk deploySynthesizes and deploys through CloudFormation. Asks for approval of security-broadening changes by default.
cdk deploy --hotswapUpdates some resources (for example, Lambda code) directly through service APIs. Development only, because it causes drift.
cdk watchDeploys automatically when files change. Uses hotswap by default.
cdk destroyDeletes the stack. The CDKToolkit stack stays.

Exam signals

  • "First CDK deploy in a new account or Region fails" → run cdk bootstrap.
  • "Preview the changes before deploy" → cdk diff.
  • "Give a function read access to a table with least privilege" → L2 grant method, such as grantReadData.
  • "Fastest code update loop in a dev account" → cdk watch or --hotswap. Never in production.

References: CDK bootstrapping, cdk deploy reference. Lab: Lab 8.7 CDK introduction.

ECS task definitions, services, and deployments

Key facts

  • A task definition is the versioned blueprint: images, CPU, memory, ports, environment, roles, and network mode. Each change makes a new revision.
  • A task is a running copy of a task definition. A service keeps the desired number of tasks running and connects to a load balancer.
  • Fargate tasks must use the awsvpc network mode. Each task gets its own elastic network interface and private IP address.
  • The EC2 launch type also supports bridge, host, and none.
  • Task placement strategies apply to the EC2 launch type: binpack, random, and spread.

Numbers to memorize

ItemValue
Fargate ephemeral storage (platform 1.4.0 and later)20 GiB minimum by default, up to 200 GiB
minimumHealthyPercent default (replica service)100 percent
maximumPercent default (replica service)200 percent

Rolling updates

  • minimumHealthyPercent is the lower limit of running, healthy tasks. It rounds up.
  • maximumPercent is the upper limit of running and pending tasks. It rounds down.
  • Example: 4 tasks, minimum 50 percent: ECS can stop 2 old tasks before it starts 2 new tasks. No extra capacity is needed.
  • The deployment circuit breaker fails a deployment when tasks cannot reach a steady state. With rollback on, ECS returns to the last successful deployment.
  • CloudWatch alarms can also fail and roll back a rolling deployment, based on application metrics.
  • The circuit breaker works only with the rolling update (ECS) deployment type.

Deployment controllers

  • ECS: rolling update, and the newer native blue/green, linear, and canary strategies.
  • CODE_DEPLOY: blue/green through CodeDeploy.
  • EXTERNAL: a third-party deployment tool.

AWS Copilot: a CLI that creates ECS applications, separate environments such as test and prod, and pipelines.

Exam signals

  • "Move from EC2 bridge mode to Fargate" → change the network mode to awsvpc.
  • "Deploy without extra cluster capacity" → lower minimumHealthyPercent, keep maximumPercent at 100.
  • "New tasks keep failing; stop and go back automatically" → deployment circuit breaker with rollback.

References: Rolling update, DeploymentConfiguration (defaults), Fargate task storage, Task placement strategies. Lab: Lab 8.8 ECS Fargate.

Amazon ECR: authentication, scanning, tags, and lifecycle

Authentication

  • The Docker CLI does not support IAM authentication. Get a token first: aws ecr get-login-password | docker login --username AWS --password-stdin REGISTRY.
  • The token is valid for 12 hours. It has the same permissions as the IAM principal that got it.
  • Getting a token needs ecr:GetAuthorizationToken. Pulling also needs ecr:BatchGetImage and ecr:GetDownloadUrlForLayer.
  • For cross-account pulls, add a repository policy that allows the other account.

Image scanning

TypeScansFrequency
BasicOperating system vulnerabilities (CVE database)Manual or scan on push
Enhanced (Amazon Inspector)Operating system and programming language packagesScan on push or continuous. Amazon Inspector sends findings to EventBridge.

Tags and lifecycle

  • Tag immutability stops a push that uses an existing tag. ECR returns ImageTagAlreadyExistsException.
  • Immutability applies to all tags, except tags you list as exclusions.
  • Lifecycle policies delete images automatically, for example untagged images older than a number of days, or more than a count.
  • You cannot change the encryption settings of a repository after you create it.
  • Use image tags as approved versions: deploy a specific version tag (for example v1.4.2) to test, then the same tag to production. Do not deploy from latest.
  • ECS resolves an image tag to an image digest when a deployment starts. All tasks in the deployment run the same image, even if someone pushes the tag again.

Exam signals

  • "Release tags must never be overwritten" → tag immutability.
  • "Delete old untagged images automatically" → lifecycle policy.
  • "Push worked yesterday and fails today with an auth error" → token expired after 12 hours. Run get-login-password again.
  • "Scan for language package vulnerabilities continuously" → enhanced scanning.

References: Registry authentication, Image scanning, Tag mutability, Lifecycle policies. Lab: Lab 8.8 ECS Fargate.

Elastic Beanstalk deployment policies and blue/green

Comparison

PolicyDowntimeCode deployed toFailed deploymentRollback
All at once (default DeploymentPolicy)YesExisting instancesDowntimeManual redeploy
RollingNo, but less capacityExisting instances, one batch at a timeOne batch out of serviceManual redeploy
Rolling with additional batchNo, full capacityNew and existing instancesMinimal if the first batch failsManual redeploy
ImmutableNoNew instances in a second Auto Scaling groupMinimalTerminate the new instances
Traffic splittingNoNew instances. A percentage of traffic goes to them.Only the test trafficReroute traffic, terminate new instances
Blue/green (not a policy)NoA new environmentMinimalSwap the URLs back
  • Only blue/green changes DNS. All other methods keep the same DNS name.
  • Rolling, Rolling with additional batch, and Traffic splitting need a load-balanced environment. Traffic splitting needs an Application Load Balancer.
  • All at once and Immutable also work in single-instance environments.
  • Traffic splitting defaults: 10 percent of traffic to the new version, evaluation time 5 minutes.
  • Batch size: a percentage or a fixed number of instances.

Blue/green with Elastic Beanstalk

  • Clone or create a second environment and deploy the new version there.
  • Test it, then use Swap environment URLs (CNAME swap).
  • Use it when the new version cannot run alongside the old version, or when resource configuration changes.
  • A database that is coupled to one environment blocks this pattern. Keep the database outside the environment.

Exam signals

  • "Fastest, downtime is acceptable" → All at once.
  • "Keep full capacity at the lowest extra cost" → Rolling with additional batch.
  • "Fastest and safest rollback, new instances only" → Immutable.
  • "Send 10 percent of real traffic to the new version" → Traffic splitting.
  • "New platform version cannot run next to the old one" → blue/green with a CNAME swap.

Elastic Beanstalk environments, configuration, and databases

Key facts

  • An application has application versions and environments. Each environment runs one version.
  • Web server environments serve HTTP. Worker environments process messages from an Amazon SQS queue.
  • In a worker environment, a daemon reads the queue and sends an HTTP POST to http://localhost/ on port 80.
  • A 200 OK response deletes the message. Other responses return the message to the queue after a timeout.
  • Put cron.yaml in the source bundle to queue periodic tasks. Periodic tasks do not work with a FIFO queue.
  • Elastic Beanstalk uses CloudFormation to create the environment resources.

Platform hooks (Amazon Linux 2 and later)

  • Put executable scripts in .platform/hooks/ in the source bundle: prebuild, predeploy, and postdeploy.
  • prebuild runs after the bundle is extracted, before the app and web server are configured. predeploy runs before the app moves to its final location. postdeploy runs last.
  • .platform/confighooks/ uses the same subdirectories for configuration deployments that do not replace instances.
  • Files in each directory run in lexicographical order, as root. A non-zero exit code fails the deployment.
  • .ebextensions commands run before prebuild. container_commands run before predeploy.

Configuration precedence (highest first)

  1. Settings applied directly to the environment (console, EB CLI, AWS CLI, SDK).
  2. Saved configurations.
  3. Configuration files in .ebextensions. They run in alphabetical order: 01-config.config runs before 02-fixthing.config.
  4. Default values.
  • .ebextensions files are YAML or JSON files with the .config extension, at the root of the source bundle.
  • The console overrides DeploymentPolicy and batch size settings with recommended values. You cannot set these in a configuration file for an environment created in the console.

Databases

  • A database that you add in Elastic Beanstalk is coupled to the environment. The app gets RDS_HOSTNAME, RDS_PORT, RDS_DB_NAME, RDS_USERNAME, and RDS_PASSWORD.
  • Deletion policy for a coupled database: Snapshot, Delete, or Retain.
  • For production, use a decoupled database (external to the environment). Several environments can use it, and blue/green works.

Application versions

  • Quota: 1,000 application versions per Region, across all applications.
  • A lifecycle policy deletes old versions by count or by age. It can also delete the source bundle from Amazon S3.

Exam signals

  • "Run a job every night in a worker environment" → cron.yaml.
  • "Database must survive environment termination" → database outside the environment.
  • "Cannot create new application versions" → quota reached. Add a version lifecycle policy.
  • "Value in .ebextensions is ignored" → a setting with higher precedence (direct or saved configuration) overrides it.

References: Configuration options and precedence, Worker environments, Adding a database, Version lifecycle, Elastic Beanstalk quotas. Lab: Lab 8.9 Beanstalk and Amplify.

AWS Amplify Hosting

Key facts

  • Amplify Hosting connects to a Git repository. It builds and deploys the web app on each push.
  • It hosts static sites and single-page apps. It also hosts server-side rendered apps such as Next.js.
  • Each connected branch is a separate environment with its own URL, for example main for production and dev for testing. Merge to a branch to promote an approved version.
  • Build settings: the console settings apply unless the repository has an amplify.yml file at its root.
  • Web previews deploy each pull request to a unique preview URL. Amplify deletes the preview when the pull request closes.
  • For public repositories, web previews are not available for apps that need an IAM service role.
  • Access control protects a branch, or all branches, with a user name and password.
  • Each pull request preview counts toward the quota of 50 branches for each app.

Front-end web app from Git with automatic builds, least effortAmplify Hosting

  • "React app in GitHub, deploy on every push, least operational overhead" → Amplify Hosting.
  • "Preview each pull request" → Amplify web previews.
  • "Password protect the dev branch" → Amplify access control.
