Source and package repositories: CodeCommit and CodeArtifact

Git repositories and triggers

  • A commit to a Git repository (CodeCommit, GitHub, GitLab, Bitbucket) can start a pipeline. CodePipeline detects the change in one of two ways. For CodeCommit and Amazon S3 sources, an EventBridge rule starts the pipeline. For GitHub, GitLab, and Bitbucket, a connection (AWS CodeConnections) is an authorized link that lets CodePipeline read the repository and receive its push events.
  • Use branches for environments and Git tags for releases. For example, a push to the dev branch deploys to test, and a push of tag v1.4.0 starts the production release. A V2 pipeline can filter triggers on branches, tags, and file paths, so that only the matching pushes start it.

CodeCommit (short note)

  • AWS CodeCommit is a managed Git service. IAM controls access. Exam guide v2.1 does not list it, but questions can still describe it.
  • AWS closed CodeCommit to new customers in July 2024. AWS made it available to new customers again in November 2025.
  • HTTPS Git credentials and SSH keys belong to an IAM user. A federated user or a role has no IAM user, so it cannot get these credentials. For federated access or temporary credentials, use git-remote-codecommit. This Git extension signs each Git request with the AWS credentials of your AWS CLI profile. It needs no Git credentials.
  • To stop some users from pushing to a branch, use an IAM Deny policy on codecommit:GitPush and the merge actions, with the codecommit:References condition (for example refs/heads/main). An explicit Deny overrides every Allow, so the users keep their other CodeCommit permissions. Deny the merge actions too, because otherwise a user can change main with a pull request merge in the console.

CodeArtifact

  • AWS CodeArtifact is a managed package repository for npm, PyPI, Maven, NuGet, and other formats.
  • A domain groups repositories. An asset is a file of a package version, such as an npm .tgz file. The domain stores each asset one time, even when ten repositories hold that version. It encrypts all assets with one KMS key.
  • A repository holds package versions. One repository can hold several package formats.
  • An upstream repository is a repository that another (downstream) repository searches when it does not have a requested package. The package manager uses only the downstream repository endpoint, but it gets packages from both repositories. A repository can have up to 10 upstream repositories.
  • An external connection links a repository to a public repository, such as npmjs.com, PyPI, or Maven Central. When a build requests a package that the repository does not have, CodeArtifact gets it from the public repository and stores a copy. Builds can still download that stored copy when the public repository has an outage. Each repository can have only one external connection.
  • Recommended pattern: one repository in the domain has the external connection. Other repositories use it as an upstream. Then you manage only one connection, and each public package version comes in one time for all teams.
  • Authenticate with aws codeartifact login (npm, pip, twine, dotnet, nuget, swift). This command gets a token and writes the repository endpoint and the token into the configuration of that tool. For tools that login does not support (for example, Maven and Gradle), call get-authorization-token and put the token in the tool settings yourself.
  • The token is valid for 12 hours by default. You can set 15 minutes to 12 hours. After it expires, the package manager gets authentication errors until you get a new token.
  • Getting a token needs codeartifact:GetAuthorizationToken and sts:GetServiceBearerToken. CodeArtifact tokens are service bearer tokens that AWS STS creates. Without either permission, the call fails with AccessDenied.

Exam signals

  • "Builds must get open-source packages through a private, approved repository" → CodeArtifact with an external connection, because builds then download from your repository, and the repository gets public packages for them.
  • "Maven build cannot authenticate to CodeArtifact" → call get-authorization-token and pass the token, for example in CODEARTIFACT_AUTH_TOKEN.
  • "Developers use federation or temporary credentials with CodeCommit" → git-remote-codecommit.
  • "Only senior developers can push to main" → IAM Deny with codecommit:References.

CodeBuild buildspec: phases, artifacts, and reports

Key facts

  • The default buildspec file is buildspec.yml in the root of the source directory.
  • To use a different name or path, set the buildspec in the project, or set buildspecOverride on StartBuild.
  • You can store the buildspec in an S3 bucket. The bucket must be in the same Region as the build project.
  • A build project uses only one buildspec at a time.
  • Use version: 0.2. In 0.2, all commands run in the same shell instance, so a cd or a variable from one command is still in effect for the next command. In version 0.1, each command ran in a separate shell, so a later command did not see these changes.

Phases

PhaseTypical use
installInstall packages and tools. Select runtimes with runtime-versions.
pre_buildSign in to Amazon ECR. Install dependencies.
buildCompile, run tests, package.
post_buildPackage artifacts, push a Docker image, send notifications.
  • Each phase can have a finally block. The finally commands run even if a command in commands fails.
  • When a command fails, CodeBuild skips the remaining commands in that block and runs the finally block.
  • on-failure on a phase sets what happens when that phase fails. ABORT stops the build. CONTINUE goes to the next phase, for example to run a report step after failed tests. RETRY retries the build up to 3 times. RETRY-count and RETRY-regex set the number of retries and the error message that causes a retry.
  • CodeBuild always attempts the UPLOAD_ARTIFACTS phase, even if the BUILD phase fails. So you can get the output files of a failed build to find the cause.
  • run-as sets the Linux user. Without it, commands run as root.

Artifacts

  • artifacts.files: the paths to include. '**/*' means all files, recursively.
  • discard-paths: yes puts all files at the top level of the artifact, with no directories. Example: target/app.jar becomes app.jar at the root of the .zip file.
  • base-directory makes paths relative to that directory. The directory itself is not in the artifact. Example: with base-directory: dist, the file dist/index.html is index.html in the artifact. Files outside dist are not in the artifact.
  • secondary-artifacts creates more than one output artifact, for example one .zip file for CodeDeploy and one for a test team. Each identifier in the buildspec must match an artifact in the project secondaryArtifacts setting.
  • You do not need artifacts if the build only pushes an image to Amazon ECR or only runs tests.

Reports

  • The reports section sends test or code coverage results to a report group. The console then shows each test with its pass or fail result, and the trend across builds. Without it, you must read test results in the build log.
  • Test formats include JUnit XML (the default), NUnit, TestNG, Cucumber JSON, and Visual Studio TRX.
  • Coverage formats include JaCoCo, Cobertura, Clover, and SimpleCov.

Numbers to memorize

ItemValue
Build timeoutDefault 60 minutes. Range 5 to 2,160 minutes (36 hours).
Queued timeout (how long a build can wait for compute before it starts)5 to 480 minutes
Test report availability30 days after creation

Exam signals

  • "Run a cleanup command even when tests fail" → put it in the phase finally block.
  • "Use buildspec-release.yml for some builds" → set the buildspec path in the project, or override it on StartBuild.
  • "appspec.yml must be at the root of the artifact" → list it in artifacts.files. Use discard-paths or base-directory to control the layout. CodeDeploy reads appspec.yml only from the root of the bundle, so a deployment fails if the file is in a subdirectory.
  • "Show test pass and fail trends" → CodeBuild reports.

CodeBuild environment: variables, secrets, cache, Docker, and VPC

Environment variables

  • env.variables holds plaintext values. The console and the AWS CLI can show them. Do not put secrets there.
  • env.parameter-store reads values from Systems Manager Parameter Store. The service role needs ssm:GetParameters.
  • env.secrets-manager reads from Secrets Manager. Format: secret-id:json-key:version-stage:version-id. Only secret-id is required. Example: DB_PASSWORD: prod/db:password puts the password key of the JSON secret prod/db into the variable DB_PASSWORD. Without a json-key, the variable gets the whole secret text.
  • For a secret in another account, use the secret ARN, not the name. A secret name finds secrets only in the account of the build.
  • CodeBuild masks Parameter Store and Secrets Manager values in the logs. Masking matches only the exact stored value. If a command changes the value (for example, Base64 encoding) and prints it, the log shows the changed value.
  • env.exported-variables makes variables available to later actions in CodePipeline. Example: the build exports IMAGE_TAG, and the deploy action uses it as #{BuildVariables.IMAGE_TAG}, where BuildVariables is the namespace of the build action.
  • Do not create variables that start with CODEBUILD_. AWS reserves this prefix for the variables that CodeBuild sets itself, such as CODEBUILD_SRC_DIR.

Precedence when one name is set in more than one place

  1. The value in the StartBuild call (highest).
  2. The value in the build project.
  3. The value in the buildspec (lowest).

Use this order to change a value for one build without editing the buildspec. For example, set STAGE=prod in the StartBuild call to override STAGE=dev in the buildspec.

Cache

  • A cache keeps files, such as downloaded dependencies, from one build so that later builds do not download or build them again.
  • Two cache types: Amazon S3 and local. An S3 cache is in a bucket, so every build host can use it. Choose it for small to medium files that take longer to build than to download.
  • A local cache is on the build host, so only builds that run on that host can use it. Choose it for large files and frequent builds, because it has no network transfer time. Local cache does not work for builds in a VPC.
  • Local cache modes: source cache (Git metadata, so a build downloads only new commits), Docker layer cache (image layers), and custom cache (directories that you list in the buildspec cache paths). You can select one or more.
  • Docker layer cache works on Linux only. It requires privileged mode, because the Docker daemon must run in the build container to reuse layers.

Docker builds

  • To run docker build in a build, turn on privileged mode. It lets the Docker daemon run in the build container.
  • To push to Amazon ECR, the service role needs ECR permissions, and the build must sign in to ECR first. The docker push command uses the Docker sign-in, not the IAM role, so it fails without docker login.

VPC

  • By default, a build runs outside your VPC and cannot reach private resources. Configure a VPC, subnets, and security groups to reach private resources such as an RDS database.
  • Select private subnets only. Route internet traffic through a NAT gateway or NAT instance. Without that route, commands such as pip install or npm install time out.
  • An internet gateway alone does not work. A resource needs a public IP address to use an internet gateway, and CodeBuild does not assign public IP addresses to its network interfaces.
  • Security groups for builds need no inbound rules. The build only opens outbound connections, and security groups allow the response traffic automatically.

Logs and permissions

  • CodeBuild sends build logs to CloudWatch Logs, Amazon S3, or both.
  • The build runs with the project service role. Add permissions there, not to the user who starts the build. A missing permission shows as an AccessDenied error in the build log, even when the user who started the build has that permission.
  • To test a buildspec on your computer, run the CodeBuild agent locally with Docker (codebuild_build.sh).

Exam signals

  • "Database password is in plaintext in the buildspec" → move it to Secrets Manager or a SecureString parameter. Reference it in env. The build gets the same variable name, and CodeBuild masks the value in logs.
  • "Build in a VPC cannot download packages" → private subnet with a route to a NAT gateway, because the build has no public IP address.
  • "Cannot connect to the Docker daemon" → turn on privileged mode. Without it, the Docker daemon cannot start in the build container.
  • "Builds download the same dependencies every time" → configure a cache.

CodeDeploy for Lambda and AWS SAM traffic shifting

Key facts

  • A Lambda alias is a name (for example live) that points to a function version. An alias can send a percentage of invocations to a second version. CodeDeploy shifts traffic by changing these alias weights.
  • Clients must invoke the alias. A call with the unqualified function name runs $LATEST, so it skips the alias and the traffic split.
  • The Lambda AppSpec lists the function Name, Alias, CurrentVersion, and TargetVersion.
  • Lambda deployments have no agent and no instances. Only traffic moves.
  • You can create a custom canary or linear configuration when the predefined percentages and intervals do not fit, for example 20 percent every 5 minutes.

Predefined deployment configurations

TypeNames (prefix CodeDeployDefault.Lambda)Behavior
CanaryCanary10Percent5Minutes, 10Minutes, 15Minutes, 30Minutes10 percent first. The remaining 90 percent after the interval.
LinearLinear10PercentEvery1Minute, Every2Minutes, Every3Minutes, Every10Minutes10 percent more at each interval until all traffic moves
All at onceAllAtOnceAll traffic at once

Choose canary to test the new version on a small share of users for a fixed time, and then move the rest in one step. Choose linear to increase traffic in equal steps, so that a problem affects fewer users before an alarm stops it. Choose all at once when speed matters more than risk, for example in a development account.

Hooks

  • Two hooks: BeforeAllowTraffic (before any traffic moves) and AfterAllowTraffic (after all traffic moves). Use BeforeAllowTraffic to run tests against the new version before any user reaches it. Use AfterAllowTraffic to check the result after the shift.
  • Each hook is a Lambda function. It must call PutLifecycleEventHookExecutionStatus with Succeeded or Failed.
  • If CodeDeploy gets no status within one hour, the deployment fails.
  • The hook function role needs the codedeploy:PutLifecycleEventHookExecutionStatus permission.

AWS SAM

  • AutoPublishAlias publishes a new version when the code changes and points the alias at it. DeploymentPreference needs it: without AutoPublishAlias, SAM returns an error.
  • DeploymentPreference sets Type (for example Canary10Percent10Minutes), Alarms, and Hooks (PreTraffic, PostTraffic).
  • SAM creates the CodeDeploy application and deployment group for you.
  • If a hook fails or an alarm goes into the ALARM state, CodeDeploy rolls back the deployment.

Exam signals

  • "10 percent of traffic for 10 minutes, then the rest" → canary (Canary10Percent10Minutes).
  • "Increase traffic in equal steps" → linear.
  • "Roll back automatically when errors increase" → CloudWatch alarms in the deployment preference.
  • "Hook tests pass, but the deployment fails after one hour" → the hook did not call PutLifecycleEventHookExecutionStatus.

References: Deployment configurations, AppSpec hooks, SAM gradual deployments, SAM DeploymentPreference. Lab: Lab 8.3 CodeDeploy for Lambda.

CodeDeploy for EC2: AppSpec, hooks, rollbacks, and troubleshooting

Key facts

  • The CodeDeploy agent must run on each instance. It downloads the revision and runs the hook scripts.
  • The instances need an IAM instance profile that can read the revision from Amazon S3 (or GitHub).
  • CodeDeploy needs a service role. CodeDeploy uses it to read instance tags, Auto Scaling groups, and load balancers. For EC2/On-Premises, attach the AWSCodeDeployRole managed policy.
  • A deployment group selects instances by tags or by Auto Scaling group. Choose an Auto Scaling group when the fleet scales: CodeDeploy then installs the current revision on each new instance that the group launches.
  • Put appspec.yml at the root of the revision bundle. The files section maps source to destination.

In-place compared to blue/green

ItemIn-placeBlue/green
InstancesThe same instances get the new revisionA new set of replacement instances gets the new revision
TrafficEach instance is out of service during its updateThe load balancer moves traffic to the replacement instances
RollbackDeploy the last good revision againSend traffic back to the original instances, if you keep them

Choose in-place when you cannot pay for extra instances and a slower rollback is acceptable. Choose blue/green when you need a fast rollback and no loss of capacity, and you can pay for a second set of instances during the deployment.

Hook order (in-place, with a load balancer)

BeforeBlockTraffic → BlockTraffic → AfterBlockTraffic → ApplicationStop → DownloadBundle → BeforeInstall → Install → AfterInstall → ApplicationStart → ValidateService → BeforeAllowTraffic → AllowTraffic → AfterAllowTraffic

  • DownloadBundle, Install, BlockTraffic, and AllowTraffic are reserved for the agent. You cannot attach scripts to them.
  • The six traffic hooks run only if the deployment group has a load balancer.
  • ApplicationStop uses the AppSpec and scripts from the last successful revision. The reason: it must stop the application that runs now, and only the old revision knows how to stop it. It does not run on the first deployment to an instance, because there is no old revision.
  • If a broken ApplicationStop script blocks every deployment, create a deployment with --ignore-application-stop-failures.
  • Use BeforeInstall for pre-install tasks, AfterInstall for configuration and permissions, and ValidateService to check the result.

Numbers to memorize

ItemValue
Hook script timeoutDefault 3,600 seconds. 3,600 seconds is also the maximum for all scripts in one lifecycle event.
Wait after you tag an instanceAt least 5 minutes before you deploy, so that CodeDeploy can read the tags
Terminated instance during a lifecycle eventThe deployment can take up to one hour to show Failed. CodeDeploy gives each lifecycle event a one-hour window, and a terminated instance has no agent to report a result.

Deployment configurations (EC2/On-Premises)

NameIn-place behavior
CodeDeployDefault.OneAtATime (default)One instance at a time. The deployment fails as soon as any instance except the last one fails. A failure on only the last instance still gives a successful deployment.
CodeDeployDefault.HalfAtATimeUp to half of the instances at a time. Succeeds if at least half succeed.
CodeDeployDefault.AllAtOnceAll instances at once. Succeeds if at least one instance succeeds.
CustomSet a minimum healthy hosts value (number or percentage): the instances that must stay in service during the deployment. A zonal configuration also sets healthy hosts for each Availability Zone, so CodeDeploy updates one zone at a time. Zonal settings need a custom configuration.

Choose OneAtATime for the most capacity and the slowest deployment. Choose HalfAtATime for a balance. Choose AllAtOnce for the fastest deployment when a short loss of capacity is acceptable.

Rollbacks

  • A rollback is a new deployment with a new deployment ID. It deploys the last known good revision.
  • Turn on automatic rollback on the deployment group or deployment. Triggers: the deployment fails, or a CloudWatch alarm threshold is met.
  • A file can be at the destination that no earlier deployment put there, for example a file that someone copied manually. For such files, select one: fail the deployment (the default), overwrite the file with the revision version, or retain the file on the instance.

Troubleshooting

  • Deployment log (Amazon Linux): /opt/codedeploy-agent/deployment-root/deployment-logs/codedeploy-agent-deployments.log.
  • Agent log: /var/log/aws/codedeploy-agent/codedeploy-agent.log. Script output: scripts.log under the deployment folder.
  • The CodeDeploy agent writes these logs only to the instance disk. To see the logs in CloudWatch, install the CloudWatch agent on the instances.
  • Common causes of failure: the agent is not running, the tags do not match, or the instance profile cannot read the bucket.
  • Other deployment logs: CodeBuild writes build logs to CloudWatch Logs. CloudFormation stack events show the first resource that failed.

Exam signals

  • "Change file permissions after the files are copied" → AfterInstall.
  • "ApplicationStop fails, and fixing the script in the new revision does not help" → the old revision's script runs. Use --ignore-application-stop-failures.
  • "Restore the last good version automatically" → automatic rollback on failure or alarm.
  • "Deploy fast but keep half of the fleet in service" → HalfAtATime.

CodeDeploy blue/green for Amazon ECS

Key facts

  • A task set is a group of tasks in one service that all run the same task definition. CodeDeploy creates a replacement (green) task set with the new task definition. Then it moves load balancer traffic to it from the original (blue) task set.
  • The ECS service must use the CODE_DEPLOY deployment controller. This setting gives control of deployments for the service to CodeDeploy instead of ECS.
  • The deployment group names two target groups and a production listener. One target group holds the blue tasks and the other holds the green tasks. CodeDeploy moves traffic by changing which target group the production listener sends traffic to.
  • A test listener is optional. It is a second listener, for example on port 8080, that sends traffic to the green tasks before customers reach them. Use it to run tests on the new version.
  • The ECS AppSpec lists TaskDefinition, and LoadBalancerInfo with ContainerName and ContainerPort.
  • ECS deployments have no agent. Hooks are Lambda functions, as for Lambda deployments.
  • The service role can use the AWSCodeDeployRoleForECS managed policy.

Hooks, in order

HookWhen it runs
BeforeInstallBefore CodeDeploy creates the replacement task set. No rollback is possible here, because nothing has changed yet.
AfterInstallAfter the replacement task set exists and has a target group
AfterAllowTestTrafficAfter the test listener sends traffic to the replacement task set
BeforeAllowTrafficBefore production traffic moves to the replacement task set
AfterAllowTrafficAfter production traffic moves to the replacement task set

Predefined configurations

  • CodeDeployDefault.ECSCanary10Percent5Minutes and ECSCanary10Percent15Minutes.
  • CodeDeployDefault.ECSLinear10PercentEvery1Minutes and ECSLinear10PercentEvery3Minutes.
  • CodeDeployDefault.ECSAllAtOnce. With a Network Load Balancer, only this predefined configuration is supported.

A canary configuration moves 10 percent of production traffic to the replacement task set, then the remaining 90 percent after 5 or 15 minutes. A linear configuration moves 10 percent more every 1 or 3 minutes until all traffic moves.

Note: native ECS strategies

Since 2025, the ECS deployment controller also has native blue/green, linear, and canary strategies, with Lambda lifecycle hooks and a bake time. Exam questions usually describe the CodeDeploy pattern. Read the stem for the service that it names.

Exam signals

  • "Test the new task set on port 8080 before customers see it" → test listener and an AfterAllowTestTraffic hook.
  • "CodeDeploy blue/green for ECS" → CODE_DEPLOY controller and two target groups.
  • "Network Load Balancer with CodeDeploy canary" → not supported. Only ECSAllAtOnce.

CodePipeline: stages, actions, approvals, and executions

Key facts

  • A pipeline has stages. Each stage has actions. Actions in a stage can run in parallel or in order (runOrder). Actions with the same runOrder number run in parallel. An action with a higher number starts after the lower numbers finish.
  • Action categories: Source, Build, Test, Deploy, Approval, Invoke. An Invoke action runs a Lambda function or a Step Functions state machine, for example to run a custom check.
  • Actions pass input and output artifacts through an S3 artifact store.
  • With more than one source action, all source actions run again when one source changes. So every execution gets the current revision of every source.
  • A failed action stops the execution. You can retry the failed stage, or a newer execution can take its place.
  • A transition is the link between two stages. Disable a transition to stop executions from entering a stage, for example during a production change freeze. The newest execution waits at the transition. In SUPERSEDED mode, a newer execution replaces an older waiting one. When you enable the transition, the newest execution enters the stage.
  • If a CloudFormation deploy action fails, the error message shows the first failed resource when the role has cloudformation:DescribeStackEvents.

Manual approval

  • An approval action stops the pipeline until a person approves or rejects.
  • It can publish to an SNS topic in the same Region and include a URL for review.
  • Rejected, or no response within seven days: the result is the same as a failed action.
  • Approvers need the codepipeline:PutApprovalResult permission.

Execution modes

ModeBehaviorPipeline type
SUPERSEDED (default)A newer execution can replace an older one that waits between stagesV1 and V2
QUEUEDExecutions run one by one, in order. None is skipped.V2 only
PARALLELExecutions run at the same time and do not wait. No stage rollback.V2 only

A stage processes one execution at a time in SUPERSEDED and QUEUED modes. Choose SUPERSEDED when only the newest commit matters, because it skips older waiting executions. Choose QUEUED when every commit must deploy, in order. Choose PARALLEL when executions are independent, for example to test feature branches at the same time.

V2-only features

  • Triggers with filters on Git tags, branches, pull requests, and file paths.
  • Pipeline-level variables: values that you set when an execution starts (with a default value), and that actions use as #{variables.name}.
  • Stage rollback: run a stage again with the source revisions and variables of an earlier successful execution, manually or automatically when the stage fails.
  • Stage conditions: rules that the pipeline checks before a stage starts, or after it succeeds or fails, for example a CloudWatch alarm or a deployment time window. The result can fail or skip the stage, or roll it back.
  • Automatic stage retry: the pipeline retries a failed stage or its failed actions with no manual step.
  • The Commands action: runs shell commands on CodeBuild compute that CodePipeline manages, with no CodeBuild project to create.

CloudFormation deploy action modes

ModeWhat it does
CREATE_UPDATECreates the stack, or updates it if it exists
CHANGE_SET_REPLACECreates a change set (replaces an existing one with the same name). Does not change the stack.
CHANGE_SET_EXECUTERuns the change set and changes the stack
REPLACE_ON_FAILUREDeletes and creates again a stack in a failed state. For tests only, because the delete removes every resource in the stack, including databases and their data.
DELETE_ONLYDeletes the stack

A change set is a list of the resource changes that CloudFormation will make, created before it makes them. Choose CREATE_UPDATE to deploy directly. Choose CHANGE_SET_REPLACE and then CHANGE_SET_EXECUTE when a person must review the changes first.

Exam signals

  • "A person must approve before production" → manual approval action, with SNS for notification.
  • "Process every commit in order" → V2 pipeline in QUEUED mode.
  • "Review infrastructure changes before they apply" → CHANGE_SET_REPLACE, approval, then CHANGE_SET_EXECUTE.
  • "Start only when a release tag is pushed" → V2 trigger with a Git tag filter.

Pipeline security: service roles, encryption, and cross-account access

Roles in a pipeline

RoleUsed byNeeds
CodePipeline service roleCodePipelineAccess to the artifact bucket and permission to start each action
CodeBuild service roleThe build containerLogs, artifact bucket, and any service the build calls (ECR, Parameter Store, Secrets Manager)
CodeDeploy service roleCodeDeployAWSCodeDeployRole (EC2), AWSCodeDeployRoleForLambda, or AWSCodeDeployRoleForECS
EC2 instance profileThe CodeDeploy agent on each instanceRead access to the revision bucket
CloudFormation role (RoleArn)CloudFormation in a deploy actionPermission to create the stack resources. The pipeline role needs iam:PassRole for it.

iam:PassRole is the permission to give a role to an AWS service. Without it, the deploy action fails with an AccessDenied error that names iam:PassRole. This check stops a user from giving a service more permissions than the user has.

Cross-account pipelines

  • Use a customer managed AWS KMS key for the artifact store. The other account must decrypt the artifacts, so the key policy must allow it. You cannot change the key policy of an AWS managed key, so the default key does not work across accounts.
  • The key policy must allow the other account. The artifact bucket policy must also allow it.
  • The other account creates a role that the pipeline service role can assume. The action uses that role (roleArn).
  • For cross-account actions, identify the key by key ID or key ARN. An alias is looked up in the account that uses it, so the other account cannot find your key by its alias.

Least privilege

  • To let only some people approve, allow codepipeline:PutApprovalResult on that approval action only.
  • Keep secrets in Secrets Manager or Parameter Store. Do not put secrets in source code, plaintext variables, or artifacts.
  • Grant each service role only the actions and resources it uses.

Exam signals

  • "Pipeline in account A deploys to account B" → customer managed KMS key, bucket policy, and a role in account B.
  • "Only release managers can approve" → IAM policy with codepipeline:PutApprovalResult on that action.
  • "Agent cannot download the revision" → the instance profile lacks S3 read access.

AWS CDK: constructs, bootstrap, and CLI commands

Key facts

  • The AWS CDK defines infrastructure in code (TypeScript, Python, Java, C#, Go). It synthesizes CloudFormation templates: it runs your code and writes the CloudFormation template that the code describes.
  • A CDK deployment is a CloudFormation stack deployment. Rollback and change sets work as in CloudFormation.
  • CDK v1 support ended on June 1, 2023. Use CDK v2.

Construct levels

LevelWhat it isExample
L1One-to-one with a CloudFormation resource. Names start with Cfn.CfnFunction
L2One resource with useful defaults and helper methodslambda.Function, table.grantReadData(fn)
L3 (patterns)Several resources that work togetherLambdaRestApi

Choose L2 for most resources, because it has safe defaults and grant methods for least-privilege IAM policies. Choose L1 when you need a CloudFormation property that the L2 construct does not support. Choose L3 when a pattern matches your whole design, for example an API Gateway API in front of one Lambda function.

Bootstrap

  • Bootstrap each AWS environment (account and Region) before you deploy to it: cdk bootstrap aws://ACCOUNT/REGION.
  • Bootstrap creates an S3 bucket for assets, an ECR repository for images, and IAM roles for deployment. Assets are local files that the app needs, such as Lambda code folders and Docker images. cdk deploy uploads them to this bucket and repository.
  • The bootstrap stack name is CDKToolkit by default.
  • Without bootstrap, only stacks with no assets and a template under 51,200 bytes deploy. 51,200 bytes is the CloudFormation limit for a template that is sent directly in the API call. A larger template must first go to an S3 bucket, and the bootstrap stack creates that bucket.

CLI commands

CommandWhat it does
cdk synthSynthesizes the CloudFormation template locally
cdk diffCompares the app with the deployed stack
cdk deploySynthesizes and deploys through CloudFormation. Asks for approval of security-broadening changes by default: changes that add IAM permissions or open security group rules. Use --require-approval never in a pipeline, where nobody can answer.
cdk deploy --hotswapUpdates some resources (for example, Lambda code) directly through service APIs. Development only, because it causes drift: the real resources no longer match what the CloudFormation stack records.
cdk watchDeploys automatically when files change. Uses hotswap by default.
cdk destroyDeletes the stack. The CDKToolkit stack stays.

Exam signals

  • "First CDK deploy in a new account or Region fails" → run cdk bootstrap.
  • "Preview the changes before deploy" → cdk diff.
  • "Give a function read access to a table with least privilege" → L2 grant method, such as grantReadData.
  • "Fastest code update loop in a dev account" → cdk watch or --hotswap. Never in production.

ECS task definitions, services, and deployments

Key facts

  • A task definition is the versioned blueprint: images, CPU, memory, ports, environment, roles, and network mode. Each change makes a new revision.
  • A task is a running copy of a task definition. A service keeps the desired number of tasks running and connects to a load balancer.
  • Fargate tasks must use the awsvpc network mode. Each task gets its own elastic network interface and private IP address, so you can attach security groups to each task. A Fargate task definition with another network mode fails to register.
  • The EC2 launch type also supports bridge, host, and none. In bridge mode, containers use a Docker virtual network and map container ports to host ports. In host mode, containers use the network of the EC2 instance directly. In none mode, containers have no external network.
  • Task placement strategies choose the EC2 instance for each new task. They apply to the EC2 launch type only. binpack fills each instance before it uses the next one, so you need fewer instances (lower cost). spread places tasks evenly, for example across Availability Zones (higher availability). random places tasks on any instance that fits.

Numbers to memorize

ItemValue
Fargate ephemeral storage (platform 1.4.0 and later)20 GiB by default. You can set up to 200 GiB.
minimumHealthyPercent default (replica service)100 percent
maximumPercent default (replica service)200 percent

Rolling updates

  • minimumHealthyPercent is the lower limit of running, healthy tasks. It rounds up.
  • maximumPercent is the upper limit of running and pending tasks. It rounds down.
  • Example: 4 tasks, minimum 50 percent: ECS can stop 2 old tasks before it starts 2 new tasks. No extra capacity is needed.
  • With the defaults (100 and 200 percent), ECS starts new tasks before it stops old ones. The cluster must have free capacity for up to twice the desired count during the deployment.
  • The deployment circuit breaker fails a deployment when tasks cannot reach a steady state (the desired number of tasks running and healthy). Without it, ECS keeps starting failing tasks again and again. With rollback on, ECS returns to the last successful deployment.
  • CloudWatch alarms can also fail and roll back a rolling deployment, based on application metrics.
  • The circuit breaker works only with the rolling update (ECS) deployment type.

Deployment controllers

  • ECS: rolling update, and the newer native blue/green, linear, and canary strategies.
  • CODE_DEPLOY: blue/green through CodeDeploy.
  • EXTERNAL: a third-party deployment tool.

AWS Copilot: a CLI that creates ECS applications, separate environments such as test and prod, and pipelines.

Exam signals

  • "Move from EC2 bridge mode to Fargate" → change the network mode to awsvpc.
  • "Deploy without extra cluster capacity" → lower minimumHealthyPercent, keep maximumPercent at 100. A maximum of 100 stops ECS from running more tasks than the desired count, and the lower minimum lets ECS stop old tasks first.
  • "New tasks keep failing; stop and go back automatically" → deployment circuit breaker with rollback.

Secrets in task definitions

  • Reference a Secrets Manager secret or a Parameter Store parameter in the container secrets section.
  • The execution role needs secretsmanager:GetSecretValue or ssm:GetParameters.
  • It also needs kms:Decrypt if the secret uses a customer managed key.
  • ECS injects the values as environment variables when the container starts. The agent gets the values before the container runs, so it uses the execution role, not the task role. If the agent cannot get a value, the task stops before the container starts.

Exam signals

  • "Task cannot pull its image" or "no logs in CloudWatch" → task execution role.
  • "Container code gets AccessDenied from S3 or DynamoDB" → task role.
  • "Task fails to start because it cannot get a secret" → execution role lacks secretsmanager:GetSecretValue.
  • "Do not put credentials in the image" → use the task role. ECS gives the containers temporary credentials for the task role, and the AWS SDK finds them automatically.

Amazon ECR: authentication, scanning, tags, and lifecycle

Authentication

  • The Docker CLI does not support IAM authentication. Get a token first: aws ecr get-login-password | docker login --username AWS --password-stdin REGISTRY.
  • The token is valid for 12 hours. It has the same permissions as the IAM principal that got it.
  • Getting a token needs ecr:GetAuthorizationToken. Pulling also needs ecr:BatchGetImage and ecr:GetDownloadUrlForLayer.
  • For cross-account pulls, add a repository policy that allows the other account. A repository policy is a resource-based policy on the repository. The pulling principal also needs the ECR pull permissions in its own account.

Image scanning

TypeScansFrequency
BasicOperating system vulnerabilities (CVE database)Manual or scan on push
Enhanced (Amazon Inspector)Operating system and programming language packagesScan on push or continuous. Amazon Inspector sends findings to EventBridge.

Choose basic scanning for operating system CVEs at no extra Amazon Inspector cost. Choose enhanced scanning when you must find vulnerabilities in language packages (for example npm or pip packages), or when images must be scanned again as new CVEs appear.

Tags and lifecycle

  • A tag is a name, such as v1.4.2, that points to one image. By default, a new push can move a tag to a different image. Tag immutability stops a push that uses an existing tag. ECR returns ImageTagAlreadyExistsException. So a tag always means the same image in test and in production.
  • Immutability applies to all tags, except tags you list as exclusions.
  • Lifecycle policies delete images automatically, for example untagged images older than a number of days, or more than a count.
  • You cannot change the encryption settings of a repository after you create it. To change them, create a new repository and push the images to it.
  • Use image tags as approved versions: deploy a specific version tag (for example v1.4.2) to test, then the same tag to production. Do not deploy from latest. Each new push moves latest, so production could get an image that nobody tested.
  • ECS resolves an image tag to an image digest when a deployment starts. All tasks in the deployment run the same image, even if someone pushes the tag again.

Exam signals

  • "Release tags must never be overwritten" → tag immutability.
  • "Delete old untagged images automatically" → lifecycle policy.
  • "Push worked yesterday and fails today with an auth error" → token expired after 12 hours. Run get-login-password again.
  • "Scan for language package vulnerabilities continuously" → enhanced scanning.

References: Registry authentication, Image scanning, Tag mutability, Lifecycle policies. Lab: Lab 8.8 ECS Fargate.

Elastic Beanstalk deployment policies and blue/green

Comparison

PolicyDowntimeCode deployed toFailed deploymentRollback
All at once (default DeploymentPolicy)YesExisting instancesDowntimeManual redeploy
RollingNo, but less capacityExisting instances, one batch at a timeOne batch out of serviceManual redeploy

Choose All at once for speed when downtime is acceptable, for example in development. Choose Rolling to avoid downtime with no extra instance cost, if reduced capacity is acceptable. Choose Rolling with additional batch to keep full capacity for the cost of one extra batch. Choose Immutable for the safest deployment and the fastest rollback. Choose Traffic splitting to test the new version on a percentage of real users first.

  • Only blue/green changes DNS. All other methods keep the same DNS name. After a DNS change, some clients keep the old address in their DNS cache for a time, so they reach the old environment.
  • Rolling, Rolling with additional batch, and Traffic splitting need a load-balanced environment. Traffic splitting needs an Application Load Balancer.
  • All at once and Immutable also work in single-instance environments.
  • Traffic splitting defaults: 10 percent of traffic to the new version, evaluation time 5 minutes. During the evaluation time, Elastic Beanstalk watches the health of the new instances. If they stay healthy, it moves all traffic to them and terminates the old instances. If not, it moves traffic back and terminates the new instances.
  • Batch size: a percentage or a fixed number of instances. Use a percentage when the number of instances changes, so that each batch grows with the fleet. Use a fixed number when you must know how many instances are out of service at a time.

Blue/green with Elastic Beanstalk

  • Clone or create a second environment and deploy the new version there.
  • Test it, then use Swap environment URLs (CNAME swap).
  • Use it when the new version cannot run alongside the old version, or when resource configuration changes.
  • A database that is coupled to one environment blocks this pattern. When you terminate the old environment, its deletion policy deletes the database, or keeps only a snapshot, unless the policy is Retain. Keep the database outside the environment.

Exam signals

  • "Fastest, downtime is acceptable" → All at once.
  • "Keep full capacity at the lowest extra cost" → Rolling with additional batch.
  • "Fastest and safest rollback, new instances only" → Immutable.
  • "Send 10 percent of real traffic to the new version" → Traffic splitting.
  • "New platform version cannot run next to the old one" → blue/green with a CNAME swap.

Elastic Beanstalk environments, configuration, and databases

Key facts

  • An application has application versions and environments. Each environment runs one version.
  • Web server environments serve HTTP. Worker environments process messages from an Amazon SQS queue. Use a worker environment for long tasks, such as image processing or email, so that the web tier stays fast.
  • In a worker environment, a daemon (a background process that Elastic Beanstalk runs on each instance) reads the queue. It sends each message as an HTTP POST to http://localhost/ on port 80. Your application only handles the POST request.
  • A 200 OK response deletes the message. Any other response returns the message to the queue after the error visibility timeout, so another attempt can process it. After the maximum retries (default 10), the message goes to the dead-letter queue. An automatically generated queue has a dead-letter queue by default.
  • Put cron.yaml in the source bundle to queue periodic tasks. Leader election makes one instance put each task in the queue, and one instance processes it, so the job does not run on every instance. Periodic tasks do not work with a FIFO queue.
  • Elastic Beanstalk uses CloudFormation to create the environment resources.

Platform hooks (Amazon Linux 2 and later)

  • Put executable scripts in .platform/hooks/ in the source bundle: prebuild, predeploy, and postdeploy.
  • prebuild runs after the bundle is extracted, before the app and web server are configured. predeploy runs before the app moves to its final location. postdeploy runs last.
  • .platform/confighooks/ uses the same subdirectories for configuration deployments that do not replace instances. A configuration deployment applies changed environment settings, such as environment variables, with no new application version.
  • Files in each directory run in lexicographical order, as root. A non-zero exit code fails the deployment.
  • .ebextensions commands run before the application bundle is extracted, so they cannot see your code. They run before prebuild. container_commands run after the bundle is extracted and before the application is deployed, so they can see and change your code. They run before predeploy.

Configuration precedence (highest first)

  1. Settings applied directly to the environment (console, EB CLI, AWS CLI, SDK).
  2. Saved configurations.
  3. Configuration files in .ebextensions. They run in alphabetical order: 01-config.config runs before 02-fixthing.config.
  4. Default values.
  • .ebextensions files are YAML or JSON files with the .config extension, at the root of the source bundle.
  • When the console or the EB CLI creates an environment, it applies recommended values (console: DeploymentPolicy, BatchSize, BatchSizeType; EB CLI: BatchSize, BatchSizeType). These are direct settings, so they override the same options in .ebextensions. To let a configuration file set these options, remove the direct settings with the AWS CLI or the EB CLI first.

Databases

  • A database that you add in Elastic Beanstalk is coupled to the environment. The app gets RDS_HOSTNAME, RDS_PORT, RDS_DB_NAME, RDS_USERNAME, and RDS_PASSWORD.
  • A coupled database has the same lifecycle as the environment. When you terminate the environment, its deletion policy decides what happens to the database: Snapshot, Delete, or Retain.
  • For production, use a decoupled database (external to the environment). Several environments can use it, and blue/green works.

Application versions

  • Quota: 1,000 application versions per Region, across all applications. At the quota, you cannot create a new version, so deployments of new code fail.
  • A lifecycle policy deletes old versions by count or by age. It can also delete the source bundle from Amazon S3.

Exam signals

  • "Run a job every night in a worker environment" → cron.yaml.
  • "Database must survive environment termination" → database outside the environment.
  • "Cannot create new application versions" → quota reached. Add a version lifecycle policy.
  • "Value in .ebextensions is ignored" → a setting with higher precedence (direct or saved configuration) overrides it.

AWS Amplify Hosting

Key facts

  • Amplify Hosting connects to a Git repository. It builds and deploys the web app on each push.
  • It hosts static sites and single-page apps. It also hosts server-side rendered apps such as Next.js.
  • Each connected branch is a separate environment with its own URL, for example main for production and dev for testing. Merge to a branch to promote an approved version.
  • Build settings: the console settings apply unless the repository has an amplify.yml file at its root.
  • Web previews deploy each pull request to a unique preview URL. Amplify deletes the preview when the pull request closes.
  • For public repositories, web previews are not available for apps that need an IAM service role. This rule stops other people from opening a pull request with code that runs with the IAM permissions of your app.
  • Access control protects a branch, or all branches, with a user name and password. Use it to keep a test site private without changes to the application code.
  • Each pull request preview counts toward the quota of 50 branches for each app. Close pull requests when they are done, so that open previews do not use up this quota.

  • "React app in GitHub, deploy on every push, least operational overhead" → Amplify Hosting.
  • "Preview each pull request" → Amplify web previews.
  • "Password protect the dev branch" → Amplify access control.
