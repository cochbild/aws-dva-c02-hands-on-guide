Log groups, retention, and structured logging

Which service answers which question

QuestionService
What did the application write?CloudWatch Logs
How does the system perform over time?CloudWatch metrics and alarms
Where did one request go, and which call was slow?AWS X-Ray
Who called which AWS API, and when?AWS CloudTrail

Key facts

  • A log event is one record. A log stream is a sequence of events from one source. A log group holds streams that share retention, monitoring, and access settings.
  • You set retention, encryption, metric filters, and subscription filters on the log group.
  • By default, CloudWatch Logs keeps log data indefinitely (Never expire). Set a retention policy to control storage cost.
  • Lambda writes to the log group /aws/lambda/<function-name> by default. If Lambda creates the group, the group has no retention policy.
  • To set retention as code, define an AWS::Logs::LogGroup with the same name and RetentionInDays in your template.
  • CloudWatch Logs does not delete expired events immediately. Deletion typically occurs up to 72 hours after the retention period ends.
  • To remove a retention policy (Never expire), call DeleteRetentionPolicy.
  • Sources: AWS services (for example, Lambda), the CloudWatch agent on EC2 and on-premises servers, and the PutLogEvents API.
  • Log classes: Standard and Infrequent Access. Metric filters, subscription filters, and embedded metric format (EMF) need the Standard class.

Structured logging

  • Write each log event as one JSON object. Logs Insights then discovers the fields automatically, and filters can match on fields.
  • Add a correlation ID (for example, the request ID or an order ID) to every log event. You can then follow one request across services.
  • Lambda advanced logging controls: log format Text (default) or JSON. Set them on the function (LoggingConfig). No code change is necessary for supported runtimes and logging methods.
  • Log-level filtering needs the JSON log format. Application levels: TRACE, DEBUG, INFO, WARN, ERROR, FATAL (default INFO). System levels: DEBUG, INFO, WARN (default INFO).
  • Lambda sends logs at the selected level and less detailed levels. Example: level WARN drops INFO and DEBUG output.
  • A log level that the code sets (for example, Python setLevel()) takes precedence over the function setting.
  • Powertools for AWS Lambda (Logger) writes structured JSON logs with Lambda context fields.

Exam signals

  • "Send only ERROR logs from production, no code change" → JSON log format, application log level ERROR.
  • "Follow one order through several services in the logs" → structured JSON logs with a correlation ID.
  • "Log storage cost grows every month" → set a retention policy on the log group.
  • "Set retention for a Lambda log group in the template" → declare AWS::Logs::LogGroup named /aws/lambda/<name> with RetentionInDays.
  • "Which IAM user deleted the table?" → CloudTrail, not CloudWatch Logs.

Metric filters, subscription filters, and export

Comparison

FeatureWhat it doesUse it for

Subscription filterSends matching log events in near real time to a destinationStream logs to Lambda, Kinesis Data Streams, Amazon Data Firehose, or OpenSearch Service
Export task (CreateExportTask)Copies log data in a time range to an S3 bucketOne-time or batch archive. Not real time.

Metric filters

  • Filters do not apply to old data. They publish data points only for events that arrive after you create the filter.
  • The metric value is a fixed number (for example, 1 for each match) or a value from the log event.
  • Default value: the value to report for a period with logs but no matches. Set it to 0 to avoid gaps. You cannot set a default value if the filter has dimensions.
  • You can add dimensions and a unit. A change of unit later has no effect.
  • Metric filters deliver at least once. Duplicate data points can occur.

Subscription filters

  • CloudWatch Logs sends events base64-encoded and gzip-compressed. A Lambda destination reads them from awslogs.data, then decodes and decompresses them.
  • Events usually arrive in less than three minutes after ingestion.
  • A Lambda destination needs a resource-based policy that allows CloudWatch Logs to invoke it.
  • Delivery is at least once. CloudWatch Logs retries retryable errors for up to 24 hours.
  • Cross-account delivery is supported (cross-account cross-Region subscriptions).

Numbers to memorize

ItemValue
Metric filters for each log group100
Subscription filters for each log group5 (older material says 2)
Account-level subscription filters1 for each Region

Exam signals

  • "Alarm when the word ERROR appears more than 10 times in 5 minutes" → metric filter, then a CloudWatch alarm.
  • "New metric filter shows no data for last week" → filters do not apply to past events. Use Logs Insights for past data.
  • "Stream logs in near real time to Amazon S3 or OpenSearch" → subscription filter to Firehose.
  • "Lambda subscriber gets unreadable data" → base64-decode and gunzip awslogs.data.

Logs Insights queries and finding bottlenecks

Key facts

  • Logs Insights runs interactive queries on log data. It is read-only. It does not change stored logs.
  • Languages: Logs Insights QL, OpenSearch PPL, and OpenSearch SQL.
  • Commands are joined with the pipe character (|). Main commands: fields, filter, stats, sort, limit, parse, display, dedup.
  • parse extracts fields from unstructured text. It supports glob patterns (*) and regular expressions with named groups.
  • stats functions include count(), sum(), avg(), min(), max(), and pct(field, 99). Use bin(5m) for time buckets.
  • System fields: @message, @timestamp, @ingestionTime, @logStream, @log.
  • Lambda logs also give @requestId, @duration, @billedDuration, @type, @maxMemoryUsed, and @memorySize.
  • JSON log fields are discovered automatically. Use dot notation for nested fields (userIdentity.type).
  • Cost is based on the amount of data scanned. Use a narrow time range and only the log groups you need.
  • From the API: StartQuery returns a queryId. Then call GetQueryResults.

Numbers to memorize

ItemValue
Query timeout60 minutes (the lab README says 60 seconds; that is wrong)
Log groups in one query (logGroupNames)50
Concurrent Logs Insights QL queries100 for each account, including dashboard queries (older material says 30)

Find performance bottlenecks in logs

  • Each Lambda invocation writes a REPORT line with Duration, Billed Duration, Memory Size, and Max Memory Used. Init Duration shows only after a cold start.
  • p99 duration: filter @type = "REPORT" | stats pct(@duration, 99) by bin(5m)
  • Memory headroom: filter @type = "REPORT" | stats max(@maxMemoryUsed), max(@memorySize). Max memory near memory size means the function needs more memory.
  • Slowest requests: filter @type = "REPORT" | sort @duration desc | limit 20, then search @requestId for the application log lines.
  • Use X-Ray traces with the logs to see which downstream call is slow. See the X-Ray topics.

Exam signals

  • "Query logs to find the cause of errors, with no new infrastructure" → Logs Insights.
  • "Extract a value from unstructured log text" → parse.
  • "Find p95 or p99 latency from Lambda REPORT lines" → stats pct(@duration, 99).
  • "Queries are slow and expensive" → narrow the time range and the log groups.

References: Logs Insights (timeout, results, concurrency), StartQuery, Query syntax, Discovered fields. Lab: Lab 9.2 Logs Insights queries.

Log encryption and sensitive data masking

Encryption with AWS KMS

  • CloudWatch Logs always encrypts log data at rest. By default it uses server-side encryption (AES-GCM, 256-bit).
  • To control the key, associate a customer managed KMS key with the log group: create-log-group --kms-key-id or associate-kms-key.
  • CloudWatch Logs supports only symmetric KMS keys.
  • The key policy must allow the CloudWatch Logs service principal (logs.<region>.amazonaws.com) in the same Region as the key.
  • Use the condition key kms:EncryptionContext:aws:logs:arn to limit the key to one log group.
  • Only new data uses the key. Association can take up to 5 minutes.
  • If you disable or delete the key, or remove CloudWatch Logs access, CloudWatch Logs cannot read the encrypted data.
  • You cannot associate a KMS key with an existing log group in the console. Use the CLI or API.

Data protection policies (masking)

  • A data protection policy finds sensitive data (for example, credit card numbers, AWS secret keys, PII, PHI) with managed or custom data identifiers.
  • Matching data is masked in all outputs: the console, Logs Insights, metric filters, and subscription filters.
  • Only principals with the logs:Unmask permission can see unmasked data.
  • Masking applies at ingestion. Events ingested before the policy stay unmasked.
  • Scope: one policy for each log group, or an account-level policy for all existing and future log groups.
  • CloudWatch Logs emits the LogEventsWithFindings metric in the AWS/Logs namespace.

Exam signals

  • "Logs contain credit card numbers. Only auditors can see them" → data protection policy, and logs:Unmask only for auditors.
  • "Encrypt logs with a key that the company controls" → associate a customer managed symmetric KMS key.
  • "associate-kms-key fails with an access error" → add the CloudWatch Logs service principal to the key policy.

References: Encrypt log data with AWS KMS, Mask sensitive log data. Lab: Module 9 overview.

Metrics, dimensions, resolution, and retention

Key facts

  • A metric is a time-ordered set of data points. A name, a namespace, and zero or more dimensions identify it.
  • AWS namespaces use AWS/<service>. Do not start a custom namespace with AWS/.
  • A dimension is a name/value pair. Each unique combination of dimensions is a separate metric. Do not use high-cardinality values (request ID, user ID) as dimensions.
  • CloudWatch does not aggregate custom metrics across dimensions. Retrieve them with the same dimensions you published.
  • Metrics exist only in the Region where you create them. You cannot delete a metric. It expires after 15 months with no new data.
  • Data point time stamps: up to 2 weeks in the past and up to 2 hours in the future.
  • A new metric can take up to 15 minutes to appear in ListMetrics.
  • Percentile statistics need raw data points. They are not available if a metric has negative values.

Resolution and retention

  • CloudWatch aggregates older data to the next longer period. It does not delete it at once.
  • Standard resolution = 1-minute granularity. High resolution = 1-second granularity (custom metrics only).
  • Read high-resolution data with a period of 1, 5, 10, 30 seconds, or a multiple of 60 seconds.

Exam signals

  • "EC2 memory utilization is not in CloudWatch" → CloudWatch agent.
  • "Need 1-minute EC2 metrics" → detailed monitoring.
  • "Need 1-second data from last week" → not possible. High-resolution data points are kept for 3 hours only.
  • "Metric bill grew after a code change" → a high-cardinality dimension creates many metrics.

Custom metrics: PutMetricData, EMF, and the CloudWatch agent

Comparison

MethodHow it worksBest for

Embedded metric format (EMF)The code writes a JSON log event. CloudWatch Logs extracts the metrics. No metric API call from the code.Lambda and containers that already send logs. Metrics and log context stay together.
CloudWatch agentCollects in-guest system metrics (memory, disk), logs, StatsD and collectd metrics, and tracesEC2 instances and on-premises servers

PutMetricData limits

  • Up to 1,000 different metrics in one request. Request size up to 1 MB (gzip compression supported).
  • Up to 150 values for each metric with the Values and Counts arrays. This method keeps percentile statistics.
  • A statistic set (Sum, Minimum, Maximum, SampleCount) reduces calls. It loses percentiles unless all values are equal.
  • Up to 30 dimensions for each metric. StorageResolution 1 = high resolution; 60 = standard (default).

EMF rules

  • The log event must be one valid JSON object with a root member _aws.
  • _aws contains Timestamp (milliseconds since epoch) and CloudWatchMetrics, an array of directives.
  • Each directive has Namespace, Dimensions (an array of dimension sets), and Metrics (Name, optional Unit, optional StorageResolution).
  • Metric values and dimension values must be members at the root of the JSON object. Nested members do not work.
  • Each dimension set creates a separate metric. A dimension set has up to 30 keys.
  • Up to 100 metric definitions in one log event. A metric value array has up to 100 values.
  • Time stamp: no more than 14 days in the past or 2 hours in the future.
  • If the JSON is not valid EMF, the event stays a normal log line and no metric is created.
  • Cost: you pay for log ingestion and storage and for the custom metrics. You do not pay PutMetricData request charges.
  • Libraries such as Powertools for AWS Lambda write EMF for you.

Exam signals

  • "Lambda custom metrics with no extra latency and no API calls" → EMF.
  • "EMF lines are in the logs but the metric does not appear" → check the _aws structure and that targets are root members.
  • "Too many PutMetricData calls" → batch data points, or use statistic sets or Values/Counts.
  • "Collect memory and disk metrics from EC2 or on-premises servers" → CloudWatch agent.

References: PutMetricData (limits), Publish custom metrics, EMF specification, EMF cost (Serverless Lens), CloudWatch agent. Lab: Lab 9.3 Custom metrics and EMF.

Metric alarms and missing data

Key facts

  • A metric alarm watches one metric or one metric math expression and compares it to a threshold.
  • Metric math alarm example: an error rate of 100*errors/invocations from the Lambda Errors and Invocations metrics. The expression must give one time series. You cannot alarm on a SEARCH expression.
  • States: OK, ALARM, INSUFFICIENT_DATA. There are no other states.
  • Period: the length of one data point. Evaluation Periods (N): how many recent data points to evaluate. Datapoints to Alarm (M): how many of them must breach.
  • "M out of N": 3 of the last 5 periods breach → EvaluationPeriods 5, DatapointsToAlarm 3.
  • An alarm performs actions only when its state changes. Auto Scaling actions repeat each minute while the state stays.
  • Use a period equal to or longer than the metric resolution. Example: at least 300 seconds for EC2 basic monitoring.
  • High-resolution alarm: period 10 or 30 seconds, on a high-resolution metric only. Extra charge.
  • Test actions with SetAlarmState. The state lasts until the next evaluation.
  • You can create an alarm for a custom metric before the metric exists. Include all of its dimensions.
  • Alarm history is kept for 30 days.

Missing data (TreatMissingData)

ValueBehavior
missing (default)If all data points in the evaluation range are missing, the alarm goes to INSUFFICIENT_DATA
notBreachingMissing points count as good (within the threshold)
breachingMissing points count as bad (breaching)
ignoreThe alarm keeps its current state
  • For a metric that reports data only when a problem occurs, use notBreaching.
  • For a heartbeat metric where silence means failure, use breaching.
  • Alarms on AWS/DynamoDB metrics default to ignore.

Lambda metrics to alarm on

  • Errors counts function errors only: exceptions from your code and runtime errors such as timeouts.
  • A handler that returns a normal response with an error status code (for example, statusCode: 500) is not a function error. Errors does not increase.
  • Throttles is separate. Throttled requests do not count as Invocations or Errors.

Exam signals

  • "Alarm stays in INSUFFICIENT_DATA because the metric has gaps" → TreatMissingData notBreaching.
  • "Alarm only if 3 of 5 minutes breach" → EvaluationPeriods 5, DatapointsToAlarm 3.
  • "Errors stays 0 but users see failures" → the code catches errors and returns a response. Throw, or publish a custom metric.
  • "Test the notification without a real failure" → SetAlarmState.

References: Missing data, Using alarms, Lambda metrics. Lab: Lab 9.5 Alarms.

Alarm actions, notifications, composite alarms, and anomaly detection

Alarm actions

ActionMetric alarmComposite alarm
Amazon SNS notificationYesYes
Invoke a Lambda functionYesYes
EC2 action (stop, terminate, reboot, recover)Yes (EC2 metrics)No
EC2 Auto Scaling actionYesNo
Systems Manager OpsItem or Incident Manager incidentYes (ALARM state only)Yes (ALARM state only)
  • A Lambda alarm action invokes the function asynchronously.
  • The function needs a resource-based policy that allows the principal lambda.alarms.cloudwatch.amazonaws.com. Limit it with AWS:SourceAccount or AWS:SourceArn.
  • Alarms also send state-change events to Amazon EventBridge.

Notifications for deployments and quotas

  • CodeDeploy sends state-change events to EventBridge, for example CodeDeploy Deployment State-change Notification with states such as SUCCESS and FAILURE. Create a rule with an SNS topic or a Lambda function as the target.
  • CodePipeline sends CodePipeline Pipeline Execution State Change events to EventBridge, with states such as FAILED and SUCCEEDED. A rule with an SNS target notifies the team. Stage and action events also exist.
  • Developer Tools console notification rules notify on events in CodeBuild, CodeCommit, CodeDeploy, and CodePipeline. Targets: SNS topics and chat applications (AWS Chatbot, now Amazon Q Developer in chat applications). A notification rule creates an EventBridge rule for you.
  • Quota limits: many services publish usage metrics in the AWS/Usage namespace. Use the metric math function SERVICE_QUOTA(m1). Alarm on m1/SERVICE_QUOTA(m1)*100, for example above 80 percent.

Composite alarms

  • A composite alarm uses a rule expression over the states of other alarms: ALARM(), OK(), INSUFFICIENT_DATA(), with AND, OR, NOT, TRUE, FALSE.
  • The rule can include metric alarms and other composite alarms. It cannot use a metric directly.
  • Use it to reduce alarm noise: remove actions from the child alarms and put one action on the composite alarm.
  • An actions suppressor alarm can stop composite alarm actions, for example during maintenance.
  • Cross-account composite alarms are not supported.

Anomaly detection

  • CloudWatch trains a model on up to two weeks of metric data. You can turn it on before two weeks of data exist.
  • The model includes trends and hourly, daily, and weekly patterns.
  • The alarm compares the metric to a band of expected values (ANOMALY_DETECTION_BAND). A higher threshold value makes the band wider.
  • You can alarm above the band, below the band, or outside the band.
  • You can exclude time periods (for example, a deployment) from training.

Exam signals

  • "Two alarms send two notifications for one incident" → composite alarm with AND, actions only on the composite.
  • "Metric has a daily pattern, static threshold gives false alarms" → anomaly detection alarm.
  • "Alarm must run custom remediation code" → Lambda alarm action with a resource-based policy.
  • "Composite alarm must reboot an instance" → not possible. Put the EC2 action on a metric alarm.
  • "Email the team when a deployment fails" → EventBridge rule on CodeDeploy state change, or a notification rule, to SNS.
  • "Warn before the account reaches a service quota" → alarm on the usage metric with SERVICE_QUOTA.

X-Ray traces, segments, annotations, and metadata

Key facts

  • A segment records the work of one service for a request: host, request, response, timing, errors.
  • A subsegment records finer work inside a segment, such as a call to DynamoDB, an HTTP API, or a SQL database.
  • A trace collects all segments for one request. A trace ID connects them.
  • The trace ID and sampling decision travel in the HTTP header X-Amzn-Trace-Id.
  • For services that do not send segments (for example, DynamoDB), X-Ray builds inferred segments from your subsegments.
  • X-Ray builds a service graph from the segments. The console shows it as the service map (trace map).
  • Error types: Error = 4xx, Fault = 5xx, Throttle = 429.
  • Filter expressions find traces. Groups use a filter expression and publish CloudWatch metrics every minute.
  • Choose a node or an edge on the trace map to see a latency histogram. Select a duration range to see only the slow traces. A node histogram does not include network time. An edge histogram does.

  • "Search traces by customer ID" → annotation (not metadata).
  • "Store the full payload with the trace, no search needed" → metadata.
  • "Find which downstream call adds latency" → subsegments on the trace timeline and the service map.
  • "Requests from one service do not join the upstream trace" → propagate the X-Amzn-Trace-Id header.

X-Ray instrumentation, daemon, sampling, and permissions

Daemon

  • The X-Ray daemon listens on UDP port 2000, collects segments, and sends them in batches to the X-Ray API.
  • On ECS with bridge networking, set AWS_XRAY_DAEMON_ADDRESS in the application container to point to the daemon container.
  • On ECS, attach the write policy to the task role. On EC2 and Elastic Beanstalk, attach it to the instance profile role.
  • CloudWatch agent version 1.300025.0 and later can collect X-Ray and OpenTelemetry traces. You then need no separate daemon.
  • The X-Ray SDKs and daemon entered maintenance mode on February 25, 2026 (security fixes only). AWS recommends OpenTelemetry, for example AWS Distro for OpenTelemetry (ADOT).

Instrumentation (X-Ray SDK)

  • Instrument AWS SDK clients and HTTP clients to record subsegments for downstream calls. For example, Python patch_all().
  • Create custom subsegments for your own code blocks.
  • Add annotations and metadata to segments or subsegments.

Sampling

  • Default: the first request each second (the reservoir) and 5 percent of additional requests (the rate).
  • Rule fields: priority (1 to 9999, lower is evaluated first), reservoir, rate, service name, service type, host, HTTP method, URL path, resource ARN.
  • Rules in the X-Ray service apply without a redeploy. X-Ray shares the reservoir across all instances.
  • Local rules in a JSON file need a redeploy to change. Each instance applies its own reservoir.
  • The first X-Ray-enabled service makes the sampling decision. Downstream services follow it.
  • For Lambda, you cannot change the sampling rate.

IAM managed policies

AWSXRayDaemonWriteAccessxray:PutTraceSegments, xray:PutTelemetryRecords, and reading sampling rules and targets
AWSXrayReadOnlyAccessRead traces, service graphs, groups, and sampling rules (console users)

Exam signals

  • "Lambda active tracing is on but no traces arrive" → execution role needs AWSXRayDaemonWriteAccess permissions.
  • "Trace an ECS application" → daemon sidecar on UDP 2000, task role with write access.
  • "Trace all checkout requests without redeploying" → sampling rule in X-Ray with a high priority and rate 100 percent.
  • "New instrumentation that AWS still develops" → OpenTelemetry (ADOT), not the X-Ray SDK.

Event history and trails

  • Event history is on by default. It shows the past 90 days of management events in one Region. No charge. No trail needed.
  • Event history filters on one attribute at a time. Use lookup-events (LookupEvents) from the CLI or API.
  • A trail delivers events to an S3 bucket. Optional: CloudWatch Logs and Amazon EventBridge.
  • Keep events longer than 90 days with a trail (or a CloudTrail Lake event data store). Use S3 Lifecycle rules to archive or delete.
  • A trail records events from the time you create it. It does not add past events.
  • CloudTrail delivers log files about every 5 minutes. The average delay is about 5 minutes. It is not guaranteed.
  • One copy of ongoing management events in a trail has no CloudTrail charge. S3 storage is charged.
  • Multi-Region trail: records events in all enabled Regions. Trails created in the console are multi-Region. AWS recommends this.
  • Trails created with the CLI or API are single-Region by default.
  • Organization trail: logs events for all accounts in an AWS Organizations organization. Member accounts cannot change it.
  • Send a trail to CloudWatch Logs to use metric filters and alarms on API activity.
  • Each event includes eventName, eventSource, userIdentity, sourceIPAddress, requestParameters, and responseElements.

CloudTrail integrity, encryption, Insights, and EventBridge

Log file integrity validation

  • Turn on log file integrity validation on the trail. CloudTrail then creates a hash for every log file.
  • Every hour, CloudTrail delivers a digest file. It contains the hashes of the last hour's log files and is signed with a private key.
  • Algorithms: SHA-256 for hashing, SHA-256 with RSA for signing.
  • Validation tells you if a log file was changed, deleted, or not changed after delivery. Validate with the AWS CLI (aws cloudtrail validate-logs).
  • Digest files go to the same bucket, in a separate folder.

Encryption

  • Trails created in the console use SSE-KMS by default. If you do not use SSE-KMS, CloudTrail uses SSE-S3.
  • The KMS key must be in the same Region as the S3 bucket.
  • To read SSE-KMS log files, a user needs S3 read permission and decrypt permission on the KMS key.
  • The key policy must allow CloudTrail to use the key.

CloudTrail Insights

  • Insights analyzes management events and finds unusual API call rates (write APIs) and unusual API error rates (read and write APIs).
  • Turn it on for a trail or event data store. Extra charge.
  • For a trail, Insights events can take up to 36 hours to start after you turn it on.

EventBridge integration

  • CloudTrail sends events to the default event bus with detail-type AWS API Call via CloudTrail. Sign-in events use AWS Console Signin via CloudTrail.
  • A trail with logging turned on is required.
  • Rules in the default ENABLED state match write management events and data events.
  • Read-only management events (Get*, List*, Describe*) match only rules in the ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS state.
  • Use an EventBridge rule to react in near real time, for example to invoke a Lambda function with the event details.

Exam signals

  • "Prove that log files were not changed" → log file integrity validation.
  • "Company must control the key for trail logs" → SSE-KMS with a customer managed key. Readers need kms:Decrypt.
  • "Detect an unusual spike in API calls or errors" → CloudTrail Insights.
  • "Run code when someone deletes a bucket" → EventBridge rule on AWS API Call via CloudTrail.
