Log groups, retention, and structured logging

Which service answers which question

QuestionService
What did the application write?CloudWatch Logs
How does the system perform over time?CloudWatch metrics and alarms
Where did one request go, and which call was slow?AWS X-Ray
Who called which AWS API, and when?AWS CloudTrail

Key facts

  • A log event is one record. A log stream is a sequence of events from one source. A log group holds streams that share retention, monitoring, and access settings.
  • You set retention, encryption, metric filters, and subscription filters on the log group.
  • By default, CloudWatch Logs keeps log data indefinitely (Never expire). Set a retention policy to control storage cost.
  • Lambda writes to the log group /aws/lambda/<function-name> by default. If Lambda creates the group, the group has no retention policy. CloudWatch Logs then keeps every log event forever, and the storage bill grows each month.
  • To set retention as code, define an AWS::Logs::LogGroup with the same name and RetentionInDays in your template.
  • CloudWatch Logs does not delete expired events immediately. Deletion typically occurs up to 72 hours after the retention period ends.
  • To remove a retention policy (Never expire), call DeleteRetentionPolicy.
  • Log events come from three kinds of sources: AWS services that write logs for you (for example, Lambda), the CloudWatch agent on EC2 and on-premises servers, and your own code that calls the PutLogEvents API.
  • Each log group has a log class: Standard or Infrequent Access. Infrequent Access has a lower ingestion price per GB but fewer features. Metric filters, subscription filters, embedded metric format (EMF), and Live Tail need the Standard class.
  • Choose Infrequent Access for logs that you keep only for occasional queries or later investigation (forensics). Choose Standard for logs that feed alarms, metrics, or real-time streams. You cannot change the class after you create the log group.

Structured logging

  • Write each log event as one JSON object (structured logging). Logs Insights then discovers each JSON key as a field. You can query filter orderId = "A-123" directly, with no text parsing.
  • Add a correlation ID to every log event. A correlation ID is one value, such as the request ID or an order ID, that every service writes for the same request. Search for that value to follow one request across services.
  • Lambda advanced logging controls are function settings (LoggingConfig) that change the log output without a code change. The log format is Text (default) or JSON. No code change is necessary for supported runtimes and logging methods.
  • Lambda writes two kinds of logs. Application logs are the lines that your code writes. System logs are the lines that the Lambda service writes, such as the START and REPORT lines.
  • Log-level filtering needs the JSON log format. With the Text format, Lambda sends every line. Application levels: TRACE, DEBUG, INFO, WARN, ERROR, FATAL (default INFO). System levels: DEBUG, INFO, WARN (default INFO).
  • Lambda sends logs at the selected level and less detailed levels. Example: level WARN drops INFO and DEBUG output. Fewer lines reach CloudWatch Logs, so ingestion cost goes down.
  • A log level that the code sets (for example, Python setLevel()) takes precedence over the function setting. Example: if the code calls setLevel(INFO), a function setting of WARN has no effect, and INFO lines still arrive.
  • Powertools for AWS Lambda is an open-source library from AWS. Its Logger writes structured JSON logs and adds Lambda context fields (for example, the request ID and cold start) to each line. Use it when you want structured logs with little code.

Exam signals

  • "Send only ERROR logs from production, no code change" → JSON log format, application log level ERROR, because log-level filtering is a function setting that works only with the JSON format.
  • "Follow one order through several services in the logs" → structured JSON logs with a correlation ID, because one query on that ID then finds the lines from every service.
  • "Log storage cost grows every month" → set a retention policy on the log group, because the default (Never expire) keeps every event forever.
  • "Set retention for a Lambda log group in the template" → declare AWS::Logs::LogGroup named /aws/lambda/<name> with RetentionInDays, because a group that Lambda creates has no retention policy.
  • "Which IAM user deleted the table?" → CloudTrail, not CloudWatch Logs, because CloudTrail records each AWS API call and its caller. Application logs record only what your code writes.

Metric filters, subscription filters, and export

Comparison

FeatureWhat it doesUse it for
Metric filterMatches a filter pattern in new log events and publishes a CloudWatch metricCount errors, extract a number, then alarm on it
Subscription filterSends matching log events in near real time to a destinationStream logs to Lambda, Kinesis Data Streams, Amazon Data Firehose, or OpenSearch Service
Export task (CreateExportTask)Copies log data in a time range to an S3 bucketOne-time or batch archive. Not real time.

Choose a metric filter when you need a number to graph or alarm on. Choose a subscription filter when another system must receive the log events themselves within minutes. Choose an export task when you need a copy of old logs in S3 and a delay is acceptable.

Metric filters

  • Filters do not apply to old data. They publish data points only for events that arrive after you create the filter.
  • The metric value is a fixed number (for example, 1 for each match) or a value from the log event.
  • Default value: the value to report for a period with logs but no matches. Without it, a minute with no matches has no data point, so the graph has gaps and an alarm sees missing data. Set it to 0 so that each such minute reports 0. You cannot set a default value if the filter has dimensions.
  • You can add dimensions and a unit. Set the correct unit when you create the filter, because a change of unit later has no effect.
  • Metric filters deliver at least once. Duplicate data points can occur, so a count can be slightly higher than the real number of matches.

Subscription filters

  • CloudWatch Logs sends events base64-encoded and gzip-compressed. A Lambda destination reads them from awslogs.data, then decodes and decompresses them.
  • Events usually arrive in less than three minutes after ingestion.
  • A Lambda destination needs a resource-based policy that allows CloudWatch Logs (logs.amazonaws.com) to invoke it. Without that policy, CloudWatch Logs cannot deliver the events. Add it with aws lambda add-permission (the AddPermission API).
  • Delivery is at least once, so the destination can receive the same event twice. CloudWatch Logs retries retryable errors (for example, throttling or HTTP 5xx) for up to 24 hours.
  • A subscription filter can send log events to a stream in another account or Region (cross-account cross-Region subscription). Use it to collect logs from many accounts in one central account, for example for a security team.

ItemValue

An account-level subscription filter is one filter that applies to all log groups in the account and Region, except the log groups that you exclude. A log group-level filter applies to one log group only.

Exam signals

  • "Alarm when the word ERROR appears more than 10 times in 5 minutes" → metric filter, then a CloudWatch alarm, because an alarm needs a metric and the metric filter turns each match into a data point.
  • "New metric filter shows no data for last week" → filters do not apply to past events. Use Logs Insights for past data, because it queries the stored events directly.
  • "Stream logs in near real time to Amazon S3 or OpenSearch" → subscription filter to Firehose, because a subscription filter cannot write to S3 directly. Firehose receives the stream and delivers it to S3 or OpenSearch Service.
  • "Lambda subscriber gets unreadable data" → base64-decode and gunzip awslogs.data, because CloudWatch Logs encodes and compresses the events before it sends them.

Logs Insights queries and finding bottlenecks

Key facts

  • Logs Insights runs interactive queries on log data. It is read-only. It does not change stored logs.
  • Languages: Logs Insights QL, OpenSearch PPL, and OpenSearch SQL.
  • Commands are joined with the pipe character (|). Each command works on the output of the command before it. Main commands: fields (choose the fields to show), filter (keep matching events), stats (calculate totals and other values), sort, limit (keep the first N rows), parse, display, dedup (remove duplicate rows).
  • parse extracts fields from unstructured text. It supports glob patterns (*) and regular expressions with named groups. Example: parse @message "user=* action=*" as user, action.
  • stats functions include count(), sum(), avg(), min(), max(), and pct(field, 99). pct(field, 99) gives the 99th percentile (p99): 99 percent of the values are at or below it. Use p99 for latency, because an average hides the few slow requests. bin(5m) groups the results into 5-minute time buckets.
  • System fields: @message (the raw log text), @timestamp (the event time), @ingestionTime (the time CloudWatch Logs received it), @logStream, @log (the log group).
  • Lambda logs also give @requestId, @duration, @billedDuration, @type, @maxMemoryUsed, and @memorySize. @type is the kind of system line, for example REPORT.
  • JSON log fields are discovered automatically. Use dot notation for nested fields (userIdentity.type).
  • Cost is based on the amount of data scanned. Use a narrow time range and only the log groups you need. Less data scanned also makes the query finish sooner.
  • From the API, a query is asynchronous. StartQuery returns a queryId at once. Then call GetQueryResults with that ID until the status is Complete.

Find performance bottlenecks in logs

  • Each Lambda invocation writes a REPORT line with Duration, Billed Duration, Memory Size, and Max Memory Used. Init Duration shows only after a cold start.
  • A cold start occurs when Lambda must create a new execution environment for a request. Lambda then loads your code and runs the code outside the handler before the handler starts. Init Duration is the time for that work, and the request is slower.
  • p99 duration over time: filter @type = "REPORT" | stats pct(@duration, 99) by bin(5m). A high p99 in some buckets shows when the slow requests occur.
  • Memory headroom: filter @type = "REPORT" | stats max(@maxMemoryUsed), max(@memorySize). Max memory near memory size means the function needs more memory. In Lambda, more memory also gives more CPU, so a function near its memory limit can run slowly.
  • Slowest requests: filter @type = "REPORT" | sort @duration desc | limit 20, then search @requestId for the application log lines.
  • Use X-Ray traces with the logs to see which downstream call is slow. See the X-Ray topics.

Exam signals

  • "Query logs to find the cause of errors, with no new infrastructure" → Logs Insights, because it queries the logs already stored in CloudWatch Logs. You set up nothing new.
  • "Extract a value from unstructured log text" → parse, because plain text has no fields until parse creates them.
  • "Find p95 or p99 latency from Lambda REPORT lines" → stats pct(@duration, 99), because pct is the percentile function and @duration comes from the REPORT line.
  • "Queries are slow and expensive" → narrow the time range and the log groups, because both time and cost depend on the amount of data scanned.

Log encryption and sensitive data masking

Encryption with AWS KMS

  • CloudWatch Logs always encrypts log data at rest. By default it uses server-side encryption (AES-GCM, 256-bit).
  • To control the key, associate a customer managed KMS key with the log group: create-log-group --kms-key-id or associate-kms-key. Choose this when a policy requires that the company controls who can use the key, can audit its use, and can turn it off.
  • CloudWatch Logs supports only symmetric KMS keys. An asymmetric key cannot encrypt the log group.
  • The key policy must allow the CloudWatch Logs service principal (logs.<region>.amazonaws.com) in the same Region as the key. The reason: the CloudWatch Logs service, not your code, calls KMS to encrypt and decrypt the data. Without this statement, the association fails with an access error.
  • Use the condition key kms:EncryptionContext:aws:logs:arn to limit the key to one log group. Without the condition, CloudWatch Logs can use the key for any log group.
  • Only new data uses the key. Association can take up to 5 minutes.
  • If you disable or delete the key, or remove CloudWatch Logs access, CloudWatch Logs cannot read the encrypted data.
  • You cannot associate a KMS key with an existing log group in the console. Use the CLI or API.

Data protection policies (masking)

  • A data protection policy finds sensitive data with data identifiers. A data identifier is a pattern for one kind of data, for example credit card numbers or AWS secret keys. AWS supplies managed identifiers, and you can write custom ones. Identifiers also cover PII (personally identifiable information) and PHI (protected health information).
  • Matching data is masked in all outputs: the console, Logs Insights, metric filters, and subscription filters.
  • Only principals with the logs:Unmask permission can see unmasked data.
  • Masking applies at ingestion. Events ingested before the policy stay unmasked.
  • Scope: one policy for each log group, or an account-level policy for all existing and future log groups.
  • CloudWatch Logs emits the LogEventsWithFindings metric in the AWS/Logs namespace. CloudWatch Logs emits it when it detects sensitive data in log events. Create an alarm on it to learn when an application starts to write sensitive data.

Exam signals

  • "Logs contain credit card numbers. Only auditors can see them" → data protection policy, and logs:Unmask only for auditors, because the policy masks the numbers for everyone who does not have logs:Unmask.
  • "Encrypt logs with a key that the company controls" → associate a customer managed symmetric KMS key, because the default encryption uses a key that AWS controls.
  • "associate-kms-key fails with an access error" → add the CloudWatch Logs service principal to the key policy, because CloudWatch Logs itself must use the key.

References: Encrypt log data with AWS KMS, Mask sensitive log data. Lab: Module 9 overview.

Metrics, dimensions, resolution, and retention

Key facts

  • A metric is a time-ordered set of data points. A name, a namespace, and zero or more dimensions identify it.
  • A namespace is a container that groups related metrics, for example AWS/EC2. AWS namespaces use AWS/<service>. Do not start a custom namespace with AWS/, to avoid a conflict with AWS service namespaces.
  • A dimension is a name/value pair, for example InstanceId=i-0abc. Each unique combination of dimension values is a separate metric, and CloudWatch bills each custom metric separately.
  • Do not use high-cardinality values as dimensions. High cardinality means many different values, such as a request ID or a user ID. A RequestId dimension creates one new metric for each request. The bill grows, and each metric holds only one or two data points, so the graphs show nothing useful. Put such values in logs instead.
  • CloudWatch does not aggregate custom metrics across dimensions. Retrieve them with the same dimensions you published. Example: you publish Latency with Service and Operation. A request for Latency with only Service returns no data. To get a per-service total, also publish that dimension set.
  • Metrics exist only in the Region where you create them. You cannot delete a metric. It expires after 15 months with no new data.
  • Data point time stamps: up to 2 weeks in the past and up to 2 hours in the future.
  • A new metric can take up to 15 minutes to appear in ListMetrics. A script or console search can therefore miss a metric that you just created.
  • Percentile statistics (for example, p99) need the individual values. If you publish only a statistic set (a summary of Sum, Minimum, Maximum, and SampleCount), CloudWatch cannot calculate percentiles. See the next topic. Percentiles are also not available if a metric has negative values.

  • CloudWatch aggregates older data to the next longer period. It does not delete it at once. Example: 1-minute data points are kept for 15 days. After that, you can see the same data only as 5-minute data points.
  • Resolution is how often a metric can store a data point. Standard resolution stores one data point for each minute. High resolution stores one data point for each second, and only custom metrics can use it.
  • Read high-resolution data with a period of 1, 5, 10, 30 seconds, or a multiple of 60 seconds.

  • "Need 1-minute EC2 metrics" → detailed monitoring, because basic monitoring sends data points every 5 minutes.
  • "Need 1-second data from last week" → not possible. High-resolution data points are kept for 3 hours only.
  • "Metric bill grew after a code change" → a high-cardinality dimension creates many metrics, because each new dimension value is a new billed metric.

Choose EMF in Lambda and containers, because the function only writes a log line and does not wait for an API call. Choose PutMetricData when the code does not send logs to CloudWatch Logs, for example a script that publishes one value. Choose the CloudWatch agent for operating system data from a server.

PutMetricData limits

  • Up to 1,000 different metrics in one request. Request size up to 1 MB (gzip compression supported).
  • Up to 150 values for each metric with the Values and Counts arrays. Values lists the distinct values, and Counts says how many times each value occurred. CloudWatch still has every value, so percentile statistics stay available.
  • A statistic set is a summary that you calculate before you publish: Sum, Minimum, Maximum, and SampleCount. It reduces calls. CloudWatch no longer has the individual values, so it cannot calculate percentiles unless all values are equal.
  • Up to 30 dimensions for each metric. StorageResolution 1 = high resolution; 60 = standard (default).

EMF rules

  • The log event must be one valid JSON object with a root member _aws.
  • _aws contains Timestamp (milliseconds since epoch) and CloudWatchMetrics, an array of directives. A directive tells CloudWatch which members of the log event are metrics and which are dimensions.
  • Each directive has Namespace, Dimensions (an array of dimension sets), and Metrics (Name, optional Unit, optional StorageResolution). A dimension set is a list of dimension names, for example ["Service", "Operation"].
  • Metric values and dimension values must be members at the root of the JSON object. Nested members do not work. Example: {"_aws": {...}, "Latency": 120, "Service": "cart"} works. {"_aws": {...}, "data": {"Latency": 120}} creates no metric.
  • Each dimension set creates a separate metric. A dimension set has up to 30 keys. Example: the sets ["Service"] and ["Service", "Operation"] give two metrics, so you can graph both the per-service total and each operation.
  • Up to 100 metric definitions in one log event. A metric value array has up to 100 values.
  • Time stamp: no more than 14 days in the past or 2 hours in the future.
  • If the JSON is not valid EMF, the event stays a normal log line and no metric is created.
  • Cost: you pay for log ingestion and storage and for the custom metrics. You do not pay PutMetricData request charges.
  • Libraries such as Powertools for AWS Lambda write EMF for you.

Exam signals

  • "Lambda custom metrics with no extra latency and no API calls" → EMF, because the function writes a log line and CloudWatch Logs creates the metric.
  • "EMF lines are in the logs but the metric does not appear" → check the _aws structure and that targets are root members, because an event that is not valid EMF stays a normal log line.
  • "Too many PutMetricData calls" → batch data points, or use statistic sets or Values/Counts, because one call can then carry many values.
  • "Collect memory and disk metrics from EC2 or on-premises servers" → CloudWatch agent, because it runs inside the server and reads operating system data.

Metric alarms and missing data

Key facts

  • A metric alarm watches one metric or one metric math expression and compares it to a threshold.
  • Metric math calculates a new time series from other metrics. Example: an error rate of 100*errors/invocations from the Lambda Errors and Invocations metrics. An alarm on the rate does not fire just because traffic grows. The expression must give one time series. You cannot alarm on a SEARCH expression, because a search can return many time series.
  • States: OK, ALARM, INSUFFICIENT_DATA. There are no other states.
  • Period: the length of one data point. Evaluation Periods (N): how many recent data points to evaluate. Datapoints to Alarm (M): how many of them must breach.
  • "M out of N": 3 of the last 5 periods breach → EvaluationPeriods 5, DatapointsToAlarm 3.
  • An alarm performs actions only when its state changes. An alarm that stays in ALARM for an hour sends one SNS notification, not one each minute. Auto Scaling actions are the exception: they repeat each minute while the state stays.
  • Use a period equal to or longer than the time between data points of the metric. Example: at least 300 seconds for EC2 basic monitoring. With a 60-second period, four of every five periods have no data point, so the alarm often evaluates missing data instead of real values.
  • High-resolution alarm: period 10 or 30 seconds, on a high-resolution metric only. Extra charge.
  • Test actions with SetAlarmState. The state lasts until the next evaluation.
  • You can create an alarm for a custom metric before the metric exists. Include all of its dimensions, because each dimension combination is a different metric. With a missing dimension, the alarm watches a metric that never receives data.
  • Alarm history is kept for 30 days.

Missing data (TreatMissingData)

ValueBehavior
missing (default)If all data points in the evaluation range are missing, the alarm goes to INSUFFICIENT_DATA
notBreachingMissing points count as good (within the threshold)
breachingMissing points count as bad (breaching)
ignoreThe alarm keeps its current state
  • For a metric that reports data only when a problem occurs, use notBreaching. Example: a function that runs a few times each day has no Errors data points most of the time. The default (missing) shows INSUFFICIENT_DATA, and notBreaching shows OK.
  • For a heartbeat metric where silence means failure, use breaching. Example: a job publishes a metric every minute. If the job stops, the data stops, and the alarm goes to ALARM.
  • Use ignore when a gap tells you nothing, so the alarm keeps the state it had.
  • Alarms on AWS/DynamoDB metrics default to ignore. When a table has no traffic, its alarms stay in their current state.

Lambda metrics to alarm on

  • Errors counts function errors only: exceptions from your code and runtime errors such as timeouts.
  • A handler that returns a normal response with an error status code (for example, statusCode: 500) is not a function error. Errors does not increase.
  • Throttles is separate. A throttled request is one that Lambda rejects because the function has no free concurrency. Throttled requests do not count as Invocations or Errors.

Exam signals

  • "Alarm stays in INSUFFICIENT_DATA because the metric has gaps" → TreatMissingData notBreaching, because the gaps then count as good data points.
  • "Alarm only if 3 of 5 minutes breach" → EvaluationPeriods 5, DatapointsToAlarm 3.
  • "Errors stays 0 but users see failures" → the code catches errors and returns a response. Lambda sees a success, so Errors does not count it. Throw the error, or publish a custom metric.
  • "Test the notification without a real failure" → SetAlarmState, because the forced state change runs the alarm actions.

Alarm actions, notifications, composite alarms, and anomaly detection

Alarm actions

ActionMetric alarmComposite alarm

Invoke a Lambda functionYesYes
EC2 action (stop, terminate, reboot, recover)Yes (EC2 metrics)No
EC2 Auto Scaling actionYesNo
Systems Manager OpsItem or Incident Manager incidentYes (ALARM state only)Yes (ALARM state only)
  • A Lambda alarm action invokes the function asynchronously. CloudWatch hands the event to Lambda and does not wait for the result, so the alarm does not know if the function failed.
  • The function needs a resource-based policy that allows the principal lambda.alarms.cloudwatch.amazonaws.com. Without it, the alarm changes state but the function never runs. Limit the policy with AWS:SourceAccount or AWS:SourceArn, so that only your alarms can invoke the function.
  • Alarms also send state-change events to Amazon EventBridge. Use an EventBridge rule when a target that is not a direct alarm action (for example, a Step Functions state machine) must react.

Notifications for deployments and quotas

  • CodeDeploy sends state-change events to EventBridge, for example CodeDeploy Deployment State-change Notification with states such as SUCCESS and FAILURE. Create a rule with an SNS topic or a Lambda function as the target.
  • CodePipeline sends CodePipeline Pipeline Execution State Change events to EventBridge, with states such as FAILED and SUCCEEDED. A rule with an SNS target notifies the team. Stage and action events also exist.
  • Developer Tools console notification rules notify on events in CodeBuild, CodeCommit, CodeDeploy, and CodePipeline. Targets: SNS topics and chat applications (AWS Chatbot, now Amazon Q Developer in chat applications). A notification rule creates an EventBridge rule for you.
  • Quota limits: many services publish usage metrics in the AWS/Usage namespace. In metric math, m1 is the ID that you give the usage metric. The function SERVICE_QUOTA(m1) returns the current quota for that usage. Alarm on m1/SERVICE_QUOTA(m1)*100 (usage as a percentage of the quota), for example above 80 percent. The alarm stays correct when the quota changes, because no number is hardcoded.

Composite alarms

  • A composite alarm uses a rule expression over the states of other alarms: ALARM(), OK(), INSUFFICIENT_DATA(), with AND, OR, NOT, TRUE, FALSE.
  • The rule can include metric alarms and other composite alarms. It cannot use a metric directly.
  • Use it to reduce alarm noise (many notifications for one problem). Remove actions from the child alarms and put one action on the composite alarm. The team then gets one notification, and only when the combined rule is true.
  • An actions suppressor is another alarm that you name on the composite alarm. While the suppressor is in ALARM, the composite alarm does not run its actions. Example: a maintenance alarm stops pages during a planned deployment.
  • Cross-account composite alarms are not supported.

Anomaly detection

  • CloudWatch trains a model on up to two weeks of metric data. You can turn it on before two weeks of data exist.
  • The model includes trends and hourly, daily, and weekly patterns.
  • The alarm compares the metric to a band of expected values (ANOMALY_DETECTION_BAND). The band moves with the pattern, so 5,000 requests can be normal at noon and abnormal at 3 AM. A higher threshold value makes the band wider: fewer false alarms, but small anomalies can pass unseen.
  • You can alarm above the band, below the band, or outside the band.
  • You can exclude time periods (for example, a deployment) from training.

Exam signals

  • "Two alarms send two notifications for one incident" → composite alarm with AND, actions only on the composite, because the child alarms then send nothing.
  • "Metric has a daily pattern, static threshold gives false alarms" → anomaly detection alarm, because its band follows the daily pattern and one fixed number cannot.
  • "Alarm must run custom remediation code" → Lambda alarm action with a resource-based policy, because the policy lets CloudWatch invoke the function.
  • "Composite alarm must reboot an instance" → not possible. Put the EC2 action on a metric alarm.
  • "Email the team when a deployment fails" → EventBridge rule on CodeDeploy state change, or a notification rule, to SNS, because CodeDeploy already sends these events and SNS sends the email with no code.
  • "Warn before the account reaches a service quota" → alarm on the usage metric with SERVICE_QUOTA, because the alarm compares usage with the real quota.

X-Ray traces, segments, annotations, and metadata

Key facts

  • A segment records the work of one service for a request: host, request, response, timing, errors.
  • A subsegment records finer work inside a segment, such as a call to DynamoDB, an HTTP API, or a SQL database.
  • A trace collects all segments for one request. A trace ID connects them.
  • The trace ID and sampling decision travel in the HTTP header X-Amzn-Trace-Id. Each service passes the header to the next one. If a service drops it, the next service starts a new, separate trace.
  • For services that do not send segments (for example, DynamoDB), X-Ray builds inferred segments from your subsegments. DynamoDB then appears as a node on the map even though DynamoDB sends no trace data.
  • X-Ray builds a service graph from the segments. The console shows it as the service map (trace map).
  • X-Ray sorts errors into three types. Error is a client error (HTTP 4xx), so the caller sent a bad request. Fault is a server error (HTTP 5xx), so the service failed. Throttle is HTTP 429 (Too Many Requests).
  • Filter expressions find traces, for example annotation[customer_tier] = "gold" or responsetime > 5. A group is a saved filter expression. X-Ray publishes CloudWatch metrics for each group every minute, so you can alarm on the traces that match it.
  • Choose a node or an edge on the trace map to see a latency histogram. Select a duration range to see only the slow traces. A node histogram does not include network time. An edge histogram does.

  • "Store the full payload with the trace, no search needed" → metadata, because metadata accepts objects and lists.

  • "Requests from one service do not join the upstream trace" → propagate the X-Amzn-Trace-Id header, because the trace ID in that header connects the segments.

X-Ray instrumentation, daemon, sampling, and permissions

Turn on tracing

Elastic BeanstalkXRayEnabled option runs the daemon on the instances

Amazon EC2 or on-premisesInstall and run the daemon or the CloudWatch agent

Daemon

  • The X-Ray daemon is a small program that runs next to your application. It listens on UDP port 2000, collects segments, and sends them in batches to the X-Ray API. The SDK sends segments to the local daemon over UDP, so the application does not wait for calls to X-Ray.
  • On ECS with bridge networking, set AWS_XRAY_DAEMON_ADDRESS in the application container to point to the daemon container (for example, xray-daemon:2000 with a container link). The SDK sends to 127.0.0.1:2000 by default, and in bridge mode the daemon is not at that address. With awsvpc networking, the containers share one network interface, so the default address works.
  • On ECS, attach the write policy to the task role, because the daemon container makes its AWS calls with the task role. The task execution role only pulls images and sends container logs for ECS. On EC2 and Elastic Beanstalk, attach the policy to the instance profile role.
  • CloudWatch agent version 1.300025.0 and later can collect X-Ray and OpenTelemetry traces. You then need no separate daemon.
  • The X-Ray SDKs and daemon entered maintenance mode on February 25, 2026 (security fixes only). AWS recommends OpenTelemetry, for example AWS Distro for OpenTelemetry (ADOT).

Instrumentation (X-Ray SDK)

  • Instrument AWS SDK clients and HTTP clients to record subsegments for downstream calls. To instrument a client means to wrap it so that the SDK records each call. For example, Python patch_all() wraps boto3, requests, and other supported libraries. Without it, the trace shows your service but none of its downstream calls.
  • Create custom subsegments for your own code blocks, for example to time one slow function.
  • Add annotations and metadata to segments or subsegments.

Sampling

  • Sampling means that X-Ray records only some requests, to limit cost and overhead. A sampling rule sets which requests to record.
  • Default: the first request each second (the reservoir) and 5 percent of additional requests (the rate). Example: at 101 requests each second, X-Ray records 1 + 5 (5 percent of 100) = 6 requests each second.
  • Rule fields: priority (1 to 9999, lower is evaluated first), reservoir, rate, service name, service type, host, HTTP method, URL path, resource ARN. The first rule that matches a request decides its sampling.
  • Rules in the X-Ray service apply without a redeploy, because the SDK reads them from X-Ray. X-Ray shares the reservoir across all instances, so the reservoir is a total for the whole fleet.
  • Local rules in a JSON file need a redeploy to change. Each instance applies its own reservoir, so 10 instances with a reservoir of 1 record up to 10 requests each second.
  • The first X-Ray-enabled service makes the sampling decision and writes it in the trace header. Downstream services follow it. Example: if API Gateway does not sample a request, the Lambda function behind it does not record that request either.
  • For Lambda, you cannot change the sampling rate. Lambda records 1 request each second and 5 percent of additional requests.

Exam signals

  • "Lambda active tracing is on but no traces arrive" → execution role needs AWSXRayDaemonWriteAccess permissions, because Lambda sends the trace data with the execution role.
  • "Trace an ECS application" → daemon sidecar on UDP 2000, task role with write access. A sidecar is a second container in the same task.
  • "Trace all checkout requests without redeploying" → sampling rule in X-Ray with a low priority number (evaluated first) and rate 100 percent, because the SDK reads service rules with no redeploy.
  • "New instrumentation that AWS still develops" → OpenTelemetry (ADOT), not the X-Ray SDK, because the X-Ray SDKs get security fixes only.

CloudTrail events, trails, and Event history

Event types

TypeExamplesLogged by default?
Management events (control plane)CreateBucket, RunInstances, CreateUser, ConsoleLoginYes
Data events (data plane)S3 GetObject and PutObject, Lambda Invoke, DynamoDB PutItemNo. Add them to a trail. Extra charge.
Network activity eventsAPI calls through VPC endpointsNo. Extra charge.
Insights eventsUnusual API call rate or error rateNo. Extra charge.

Management events (control plane) are calls that create, change, or delete resources and settings. Data events (data plane) are calls that read or write the data inside a resource, such as an object in a bucket. Data events are usually far more numerous, so CloudTrail logs them only when you ask and charges for them.

Event history and trails

  • Event history is on by default. It shows the past 90 days of management events in one Region. No charge. No trail needed.
  • Event history filters on one attribute at a time. Example: you can search by user name or by event name, but not by both in one search. Use lookup-events (LookupEvents) from the CLI or API.
  • A trail is a configuration that delivers events to an S3 bucket as log files. It can also send them to CloudWatch Logs and Amazon EventBridge.
  • Keep events longer than 90 days with a trail (or a CloudTrail Lake event data store). Use S3 Lifecycle rules to archive or delete.
  • A trail records events from the time you create it. It does not add past events.
  • CloudTrail delivers log files about every 5 minutes. The average delay is about 5 minutes. It is not guaranteed. To react to an API call in near real time, use an EventBridge rule, not the S3 log files.
  • One copy of ongoing management events in a trail has no CloudTrail charge. S3 storage is charged.
  • Multi-Region trail: records events in all enabled Regions. Trails created in the console are multi-Region. AWS recommends this, because a single-Region trail misses activity in other Regions, for example resources that an attacker creates there.
  • Trails created with the CLI or API are single-Region by default.
  • Organization trail: logs events for all accounts in an AWS Organizations organization. Member accounts cannot change it.
  • Send a trail to CloudWatch Logs to use metric filters and alarms on API activity.
  • Each event includes eventName, eventSource, userIdentity, sourceIPAddress, requestParameters, and responseElements.

  • "Who deleted the resource two days ago, no trail exists" → CloudTrail Event history, because it keeps 90 days of management events with no trail.
  • "S3 GetObject calls do not appear in CloudTrail" → data events are off by default. Add them to the trail.
  • "Keep API activity for 7 years" → trail to S3, with S3 Lifecycle rules, because Event history keeps only 90 days and S3 can keep files for any time.

CloudTrail integrity, encryption, Insights, and EventBridge

Log file integrity validation

  • Turn on log file integrity validation on the trail. CloudTrail then creates a hash for every log file. A hash is a short value calculated from the file content. If one byte of the file changes, the hash changes.
  • Every hour, CloudTrail delivers a digest file. It contains the hashes of the last hour's log files and is signed with a private key that only CloudTrail has. Nobody else can create a valid signature, so a person who changes a log file cannot also change the digest to match.
  • Algorithms: SHA-256 for hashing, SHA-256 with RSA for signing.
  • Validation tells you if a log file was changed, deleted, or not changed after delivery. Validate with the AWS CLI (aws cloudtrail validate-logs).
  • Digest files go to the same bucket, in a separate folder.

Encryption

  • Trails created in the console use SSE-KMS by default. If you do not use SSE-KMS, CloudTrail uses SSE-S3.
  • The KMS key must be in the same Region as the S3 bucket.
  • To read SSE-KMS log files, a user needs S3 read permission and decrypt permission on the KMS key. With S3 permission only, the read fails with an access denied error.
  • The key policy must allow CloudTrail to use the key, because CloudTrail encrypts each log file when it writes the file.

CloudTrail Insights

  • Insights analyzes management events and finds unusual API call rates (write APIs) and unusual API error rates (read and write APIs). It learns the normal rate for the account and reports a spike, for example a script that suddenly calls TerminateInstances 500 times. It does not report each single call.
  • Turn it on for a trail or event data store. Extra charge.
  • For a trail, Insights events can take up to 36 hours to start after you turn it on.

EventBridge integration

  • CloudTrail sends events to the default event bus with detail-type AWS API Call via CloudTrail. Sign-in events use AWS Console Signin via CloudTrail.
  • A trail with logging turned on is required. Without it, these events do not reach EventBridge, and the rule never matches.
  • Rules in the default ENABLED state match write management events and data events.
  • Read-only management events (Get*, List*, Describe*) match only rules in the ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS state. Example: a rule in the default state for DescribeInstances never invokes its target.
  • Use an EventBridge rule to react in near real time, for example to invoke a Lambda function with the event details.

Exam signals

  • "Prove that log files were not changed" → log file integrity validation, because the signed digest files show any change or deletion.
  • "Company must control the key for trail logs" → SSE-KMS with a customer managed key. Readers need kms:Decrypt.
  • "Detect an unusual spike in API calls or errors" → CloudTrail Insights, because it compares the current rate with the normal rate.
  • "Run code when someone deletes a bucket" → EventBridge rule on AWS API Call via CloudTrail, because the rule receives each matching API call in near real time and passes the details to the target.

References: Log file integrity validation, SSE-KMS for CloudTrail, CloudTrail Insights, EventBridge and CloudTrail events. Lab: Lab 9.6 CloudTrail.
