Log groups, retention, and structured logging

Remember

  • CloudWatch Logs answers the question "What did the application write?"
  • CloudWatch metrics and alarms answer the question "How does the system perform over time?"
  • AWS X-Ray answers the question "Where did one request go, and which call was slow?"
  • AWS CloudTrail answers the question "Who called which AWS API, and when?"
  • A log stream is a sequence of log events from one source.
  • A log group holds log streams that share retention, monitoring, and access settings.
  • You set retention, encryption, metric filters, and subscription filters on the log group.
  • CloudWatch Logs keeps log data indefinitely by default (Never expire).
  • Lambda writes to the log group /aws/lambda/<function-name> by default.
  • A log group that Lambda creates has no retention policy, so CloudWatch Logs keeps every event forever.
  • To set retention as code, declare AWS::Logs::LogGroup with the same name and RetentionInDays.
  • Log retention values go from 1 day to 3,653 days (10 years), from a fixed list.
  • CloudWatch Logs typically deletes expired events up to 72 hours after the retention period ends, not immediately.
  • To remove a retention policy (Never expire), call DeleteRetentionPolicy.
  • A log event has a maximum size of 1 MB (1,024 KB). Older study material says 256 KB.
  • A PutLogEvents batch has a maximum size of 1 MB.
  • Log events come from AWS services such as Lambda, the CloudWatch agent, and your own PutLogEvents calls.
  • The Infrequent Access log class has a lower ingestion price per GB, but fewer features.
  • Metric filters, subscription filters, EMF, and Live Tail need the Standard log class.
  • Use Infrequent Access for logs that you keep only for occasional queries or forensics.
  • You cannot change the log class after you create the log group.
  • Structured logging writes each log event as one JSON object, so Logs Insights discovers each key as a field.
  • A correlation ID is one value that every service writes for the same request.
  • Lambda LoggingConfig sets the log format to Text (default) or JSON, with no code change.
  • Lambda log-level filtering needs the JSON log format, because the Text format sends every line.
  • Lambda application log levels are TRACE, DEBUG, INFO, WARN, ERROR, and FATAL.
  • Lambda system log levels are DEBUG, INFO, and WARN.
  • The default Lambda application log level and system log level is INFO.
  • Lambda sends logs at the selected level and less detailed levels. Example: WARN drops INFO and DEBUG.
  • A log level that the code sets (for example, setLevel()) takes precedence over the function setting.
  • The Powertools for AWS Lambda Logger writes structured JSON logs with Lambda context fields, with little code.

Exam signals

  • "Send only ERROR logs from production, no code change" → JSON log format and application log level ERROR. Log-level filtering is a function setting that works only with the JSON format.
  • "Follow one order through several services in the logs" → structured JSON logs with a correlation ID. One query on that ID then finds the lines from every service.
  • "Log storage cost grows every month" → set a retention policy on the log group. The default (Never expire) keeps every event forever.
  • "Set retention for a Lambda log group in the template" → declare AWS::Logs::LogGroup named /aws/lambda/<name> with RetentionInDays. A group that Lambda creates has no retention policy.
  • "Which IAM user deleted the table?" → CloudTrail, not CloudWatch Logs. CloudTrail records each AWS API call and its caller, but application logs record only what your code writes.

Key facts

  • A log event is one record.
  • A log stream is a sequence of events from one source.
  • A log group holds streams that share retention, monitoring, and access settings.
  • You set retention, encryption, metric filters, and subscription filters on the log group.
  • By default, CloudWatch Logs keeps log data indefinitely (Never expire). Set a retention policy to control storage cost.
  • Lambda writes to the log group /aws/lambda/<function-name> by default.
  • If Lambda creates the group, the group has no retention policy. CloudWatch Logs then keeps every log event forever, and the storage bill grows each month.
  • To set retention as code, define an AWS::Logs::LogGroup with the same name and RetentionInDays in your template.
  • CloudWatch Logs does not delete expired events immediately. Deletion typically occurs up to 72 hours after the retention period ends.
  • To remove a retention policy (Never expire), call DeleteRetentionPolicy.
  • Log events come from three kinds of sources: AWS services that write logs for you (for example, Lambda), the CloudWatch agent on EC2 and on-premises servers, and your own code that calls the PutLogEvents API.
  • Each log group has a log class: Standard or Infrequent Access. Infrequent Access has a lower ingestion price per GB but fewer features.
  • Metric filters, subscription filters, embedded metric format (EMF), and Live Tail need the Standard class.
  • Choose Infrequent Access for logs that you keep only for occasional queries or later investigation (forensics). Choose Standard for logs that feed alarms, metrics, or real-time streams.
  • You cannot change the class after you create the log group.

Structured logging

  • Write each log event as one JSON object (structured logging). Logs Insights then discovers each JSON key as a field. You can query filter orderId = "A-123" directly, with no text parsing.
  • Add a correlation ID to every log event. A correlation ID is one value, such as the request ID or an order ID, that every service writes for the same request. Search for that value to follow one request across services.
  • Lambda advanced logging controls are function settings (LoggingConfig) that change the log output. The log format is Text (default) or JSON. No code change is necessary for supported runtimes and logging methods.
  • Lambda writes two kinds of logs. Application logs are the lines that your code writes. System logs are the lines that the Lambda service writes, such as the START and REPORT lines.
  • Log-level filtering needs the JSON log format. With the Text format, Lambda sends every line.
  • Application levels: TRACE, DEBUG, INFO, WARN, ERROR, FATAL (default INFO). System levels: DEBUG, INFO, WARN (default INFO).
  • Lambda sends logs at the selected level and less detailed levels. Example: level WARN drops INFO and DEBUG output. Fewer lines reach CloudWatch Logs, so ingestion cost goes down.
  • A log level that the code sets (for example, Python setLevel()) takes precedence over the function setting. Example: if the code calls setLevel(INFO), a function setting of WARN has no effect, and INFO lines still arrive.
  • Powertools for AWS Lambda is an open-source library from AWS. Its Logger writes structured JSON logs and adds Lambda context fields (for example, the request ID and cold start) to each line. Use it when you want structured logs with little code.

Metric filters, subscription filters, and export

Remember

  • A metric filter matches a filter pattern in new log events and publishes a CloudWatch metric.
  • A subscription filter sends matching log events in near real time to a destination.
  • Subscription filter destinations are Lambda, Kinesis Data Streams, Amazon Data Firehose, and OpenSearch Service.
  • An export task (CreateExportTask) copies log data in a time range to an S3 bucket, not in real time.
  • Use a metric filter when you need a number to graph or alarm on.
  • Use a subscription filter when another system must receive the log events themselves within minutes.
  • Use an export task when you need a copy of old logs in S3 and a delay is acceptable.
  • A subscription filter cannot write to S3 directly, so send the logs to Firehose to stream them to S3.
  • A metric filter does not apply to old data, only to events that arrive after you create it.
  • A metric filter value is a fixed number (for example, 1 for each match) or a value from the log event.
  • Set the metric filter default value to 0, so that a minute with logs but no matches reports 0.
  • A minute with no log events at all has no metric filter data point, even with a default value.
  • You cannot set a default value on a metric filter that has dimensions.
  • Set the correct unit when you create a metric filter, because a later change of unit has no effect.
  • Metric filters deliver at least once, so a count can be slightly higher than the real number of matches.
  • CloudWatch Logs sends subscription events base64-encoded and gzip-compressed in awslogs.data.
  • Subscription filter events usually arrive less than three minutes after ingestion.
  • A Lambda subscription destination needs a resource-based policy for logs.amazonaws.com, added with AddPermission.
  • Subscription filter delivery is at least once, so the destination can receive the same event twice.
  • CloudWatch Logs retries retryable subscription errors (throttling, HTTP 5xx) for up to 24 hours.
  • A subscription filter can send log events to another account or Region, to collect logs in one central account.
  • A log group can have at most 100 metric filters.
  • A log group can have at most 5 subscription filters. Older study material says 2.
  • An account-level subscription filter applies to all log groups in the account and Region, except excluded groups.
  • An account can have 1 account-level subscription filter in each Region.
  • An account can have 1 active export task.

Exam signals

  • "Alarm when the word ERROR appears more than 10 times in 5 minutes" → metric filter, then a CloudWatch alarm. An alarm needs a metric, and the metric filter turns each match into a data point.
  • "New metric filter shows no data for last week" → use Logs Insights for past data. Filters do not apply to past events, but Logs Insights queries the stored events directly.
  • "Stream logs in near real time to Amazon S3 or OpenSearch" → subscription filter to Firehose. A subscription filter cannot write to S3 directly, so Firehose receives the stream and delivers it to S3 or OpenSearch Service.
  • "Lambda subscriber gets unreadable data" → base64-decode and gunzip awslogs.data. CloudWatch Logs encodes and compresses the events before it sends them.

Metric filters

  • Filters do not apply to old data. They publish data points only for events that arrive after you create the filter.
  • The metric value is a fixed number (for example, 1 for each match) or a value from the log event.
  • Default value: the value to report for a period with logs but no matches. Without it, a minute with no matches has no data point, so the graph has gaps and an alarm sees missing data.
  • Set the default value to 0 so that each such minute reports 0. A minute with no log events at all still has no data point.
  • You cannot set a default value if the filter has dimensions.
  • You can add dimensions and a unit. Set the correct unit when you create the filter, because a change of unit later has no effect.
  • Metric filters deliver at least once. Duplicate data points can occur, so a count can be slightly higher than the real number of matches.

Subscription filters

  • CloudWatch Logs sends events base64-encoded and gzip-compressed. A Lambda destination reads them from awslogs.data, then decodes and decompresses them.
  • Events usually arrive in less than three minutes after ingestion.
  • A Lambda destination needs a resource-based policy that allows CloudWatch Logs (logs.amazonaws.com) to invoke it. Without that policy, CloudWatch Logs cannot deliver the events. Add it with aws lambda add-permission (the AddPermission API).
  • Delivery is at least once, so the destination can receive the same event twice.
  • CloudWatch Logs retries retryable errors (for example, throttling or HTTP 5xx) for up to 24 hours.
  • A subscription filter can send log events to a stream in another account or Region (cross-account cross-Region subscription). Use it to collect logs from many accounts in one central account, for example for a security team.

Logs Insights queries and finding bottlenecks

Remember

  • Logs Insights runs interactive, read-only queries on log data and does not change stored logs.
  • Logs Insights supports Logs Insights QL (the native language), OpenSearch PPL, and OpenSearch SQL.
  • Logs Insights joins commands with the pipe (|), and each command works on the output of the previous command.
  • The main Logs Insights commands are fields, filter, stats, sort, limit, parse, display, and dedup.
  • To extract fields from unstructured text, use parse with a glob pattern (*) or a regular expression.
  • The stats functions include count(), sum(), avg(), min(), max(), and pct().
  • pct(field, 99) gives the 99th percentile (p99): 99 percent of the values are at or below it.
  • Use p99 for latency, because an average hides the few slow requests.
  • bin(5m) groups Logs Insights results into 5-minute time buckets.
  • The system field @message holds the raw log text, and @log holds the log group.
  • The system field @timestamp is the event time, and @ingestionTime is the time CloudWatch Logs received it.
  • Lambda logs add @requestId, @duration, @billedDuration, @type, @maxMemoryUsed, and @memorySize.
  • Logs Insights discovers JSON log fields automatically, and dot notation reads nested fields. Example: userIdentity.type.
  • Logs Insights cost depends on the amount of data scanned.
  • To make a Logs Insights query cheaper and faster, use a narrow time range and only the necessary log groups.
  • An API query is asynchronous: StartQuery returns a queryId at once.
  • Call GetQueryResults with the queryId until the status is Complete.
  • A Logs Insights query times out after 60 minutes. Older study material (the lab README) says 60 seconds.
  • One Logs Insights query can search at most 50 log groups (logGroupNames).
  • An account can run 100 concurrent Logs Insights QL queries, including dashboard queries. Older study material says 30.
  • Logs Insights keeps query results for 7 days.
  • Each Lambda invocation writes a REPORT line with Duration, Billed Duration, Memory Size, and Max Memory Used.
  • The Lambda REPORT line shows Init Duration only after a cold start.
  • A cold start occurs when Lambda must create a new execution environment for a request.
  • Init Duration is the time Lambda needs to load your code and run the code outside the handler.
  • Max Memory Used near Memory Size means that the Lambda function needs more memory.
  • In Lambda, more memory also gives more CPU, so a function near its memory limit can run slowly.
  • To find the slowest requests, sort REPORT lines by @duration, then search their @requestId.
  • To see which downstream call is slow, use X-Ray traces with the logs.

Exam signals

  • "Query logs to find the cause of errors, with no new infrastructure" → Logs Insights. Logs Insights queries the logs already stored in CloudWatch Logs, so you set up nothing new.
  • "Extract a value from unstructured log text" → parse. Plain text has no fields until parse creates them.
  • "Find p95 or p99 latency from Lambda REPORT lines" → stats pct(@duration, 99). pct is the percentile function, and @duration comes from the REPORT line.
  • "Queries are slow and expensive" → narrow the time range and the log groups. Both time and cost depend on the amount of data scanned.

Explanation

Key facts

  • Logs Insights runs interactive queries on log data. It is read-only. It does not change stored logs.
  • Languages: Logs Insights QL, OpenSearch PPL, and OpenSearch SQL. All three query the same log data.
  • Logs Insights QL is the native language and the one this sheet uses. Choose PPL or SQL if your team already knows them from OpenSearch.
  • Commands are joined with the pipe character (|). Each command works on the output of the command before it. Main commands: fields (choose the fields to show), filter (keep matching events), stats (calculate totals and other values), sort, limit (keep the first N rows), parse, display, dedup (remove duplicate rows).
  • parse extracts fields from unstructured text. It supports glob patterns (*) and regular expressions with named groups. Example: parse @message "user=* action=*" as user, action.
  • stats functions include count(), sum(), avg(), min(), max(), and pct(field, 99).
  • pct(field, 99) gives the 99th percentile (p99): 99 percent of the values are at or below it. Use p99 for latency, because an average hides the few slow requests.
  • bin(5m) groups the results into 5-minute time buckets.
  • System fields: @message (the raw log text), @timestamp (the event time), @ingestionTime (the time CloudWatch Logs received it), @logStream, @log (the log group).
  • Lambda logs also give @requestId, @duration, @billedDuration, @type, @maxMemoryUsed, and @memorySize. @type is the kind of system line, for example REPORT.
  • JSON log fields are discovered automatically. Use dot notation for nested fields (userIdentity.type).
  • Cost is based on the amount of data scanned. Use a narrow time range and only the log groups you need. Less data scanned also makes the query finish sooner.
  • From the API, a query is asynchronous. StartQuery returns a queryId at once. Then call GetQueryResults with that ID until the status is Complete.

Find performance bottlenecks in logs

  • Each Lambda invocation writes a REPORT line with Duration, Billed Duration, Memory Size, and Max Memory Used. Init Duration shows only after a cold start.
  • A cold start occurs when Lambda must create a new execution environment for a request. Lambda then loads your code and runs the code outside the handler before the handler starts. Init Duration is the time for that work, and the request is slower.
  • p99 duration over time: filter @type = "REPORT" | stats pct(@duration, 99) by bin(5m). A high p99 in some buckets shows when the slow requests occur.

  • Slowest requests: filter @type = "REPORT" | sort @duration desc | limit 20, then search @requestId for the application log lines.

Log encryption and sensitive data masking

Remember

  • CloudWatch Logs always encrypts log data at rest, by default with server-side encryption (AES-GCM, 256-bit).
  • To control the encryption key, associate a customer managed KMS key with the log group.
  • To associate a KMS key, use create-log-group --kms-key-id or associate-kms-key.
  • Use a customer managed key when the company must control who uses the key, audit its use, and turn it off.
  • CloudWatch Logs supports only symmetric KMS keys, not asymmetric keys.
  • The KMS key policy must allow logs.<region>.amazonaws.com in the same Region as the key.
  • The CloudWatch Logs service, not your code, calls KMS to encrypt and decrypt log data.
  • Without the CloudWatch Logs statement in the key policy, the key association fails with an access error.
  • To limit a KMS key to one log group, use the condition key kms:EncryptionContext:aws:logs:arn.
  • A KMS key encrypts only new log data, and earlier events keep their earlier encryption.
  • A KMS key association can take up to 5 minutes.
  • If you disable or delete the KMS key, or remove CloudWatch Logs access, CloudWatch Logs cannot read the encrypted data.
  • To associate a KMS key with an existing log group, use the CLI or API, not the console.
  • A data protection policy finds sensitive data with managed or custom data identifiers.
  • Data identifiers find data such as credit card numbers, AWS secret keys, PII, and PHI.
  • A data protection policy masks matching data in the console, Logs Insights, metric filters, and subscription filters.
  • Only principals with the logs:Unmask permission can see unmasked data.
  • Masking applies at ingestion, so events ingested before the data protection policy stay unmasked.
  • A data protection policy applies to one log group, or account-wide to all existing and future log groups.
  • To learn when an application writes sensitive data, alarm on LogEventsWithFindings in AWS/Logs.

Exam signals

  • "Logs contain credit card numbers. Only auditors can see them" → data protection policy, and logs:Unmask only for auditors. The policy masks the numbers for everyone who does not have logs:Unmask.
  • "Encrypt logs with a key that the company controls" → associate a customer managed symmetric KMS key. The default encryption uses a key that AWS controls.
  • "associate-kms-key fails with an access error" → add the CloudWatch Logs service principal to the key policy. CloudWatch Logs itself must use the key.

Explanation

Encryption with AWS KMS

  • CloudWatch Logs always encrypts log data at rest. By default it uses server-side encryption (AES-GCM, 256-bit).
  • To control the key, associate a customer managed KMS key with the log group: create-log-group --kms-key-id or associate-kms-key.
  • Choose this when a policy requires that the company controls who can use the key, can audit its use, and can turn it off.
  • CloudWatch Logs supports only symmetric KMS keys. An asymmetric key cannot encrypt the log group.
  • The key policy must allow the CloudWatch Logs service principal (logs.<region>.amazonaws.com) in the same Region as the key. The reason: the CloudWatch Logs service, not your code, calls KMS to encrypt and decrypt the data. Without this statement, the association fails with an access error.
  • Use the condition key kms:EncryptionContext:aws:logs:arn to limit the key to one log group. Without the condition, CloudWatch Logs can use the key for any log group.
  • Only new data uses the key. Events ingested before the association keep their earlier encryption.
  • Association can take up to 5 minutes.
  • If you disable or delete the key, or remove CloudWatch Logs access, CloudWatch Logs cannot read the encrypted data.
  • You cannot associate a KMS key with an existing log group in the console. Use the CLI or API.

Data protection policies (masking)

  • A data protection policy finds sensitive data with data identifiers. A data identifier is a pattern for one kind of data, for example credit card numbers or AWS secret keys.
  • AWS supplies managed identifiers, and you can write custom ones. Identifiers also cover PII (personally identifiable information) and PHI (protected health information).
  • Matching data is masked in all outputs: the console, Logs Insights, metric filters, and subscription filters.
  • Only principals with the logs:Unmask permission can see unmasked data.
  • Masking applies at ingestion. Events ingested before the policy stay unmasked.
  • Scope: one policy for each log group, or an account-level policy for all existing and future log groups.
  • CloudWatch Logs emits the LogEventsWithFindings metric in the AWS/Logs namespace when it detects sensitive data in log events. Create an alarm on it to learn when an application starts to write sensitive data.

Metrics, dimensions, resolution, and retention

Remember

  • A metric is a time-ordered set of data points, identified by a name, a namespace, and zero or more dimensions.
  • A namespace groups related metrics, and AWS namespaces use the form AWS/<service>.
  • Do not start a custom namespace with AWS/, to avoid a conflict with AWS service namespaces.
  • A dimension is a name/value pair, for example InstanceId=i-0abc.
  • Each unique combination of dimension values is a separate metric, and CloudWatch bills each custom metric separately.
  • Put high-cardinality values, such as a request ID or a user ID, in logs, not in dimensions.
  • A high-cardinality dimension makes the metric bill grow, and each metric holds only one or two data points.
  • CloudWatch does not aggregate custom metrics across dimensions.
  • To retrieve a custom metric, use the same dimensions that you published.
  • To get a per-service total, also publish the metric with only the Service dimension.
  • A metric exists only in the Region where you create it.
  • You cannot delete a metric, but a metric expires after 15 months with no new data.
  • A data point time stamp can be up to 2 weeks in the past and up to 2 hours in the future.
  • Alarms check data at the current UTC time, so use the current time for data points when you can.
  • A data point time stamp that is not current can leave an alarm in INSUFFICIENT_DATA or delay it.
  • A data point stamped 24 hours ago or more can take at least 48 hours to appear in GetMetricData.
  • A new metric can take up to 15 minutes to appear in ListMetrics.
  • CloudWatch cannot calculate percentiles from a statistic set, because percentiles need the individual values.
  • CloudWatch cannot calculate percentiles for a metric that has negative values.
  • CloudWatch keeps high-resolution data points (period less than 60 seconds) for 3 hours.
  • CloudWatch keeps 60-second data points for 15 days.
  • CloudWatch keeps 300-second (5-minute) data points for 63 days.
  • CloudWatch keeps 3,600-second (1-hour) data points for 455 days (15 months).
  • CloudWatch aggregates older data points to the next longer period instead of deleting them at once.
  • Standard resolution stores one data point for each minute.
  • High resolution stores one data point for each second, and only custom metrics can use it.
  • Read high-resolution data with a period of 1, 5, 10, or 30 seconds, or a multiple of 60 seconds.
  • EC2 basic monitoring is the default: 5-minute data points (status checks 1 minute), at no charge.
  • EC2 detailed monitoring gives 1-minute data points, with a charge for each metric.
  • AWS/EC2 has no memory or disk-space utilization metric.
  • To collect EC2 memory and disk data, install the CloudWatch agent inside the instance.

Exam signals

  • "EC2 memory utilization is not in CloudWatch" → CloudWatch agent. AWS/EC2 has no memory metric, and the agent collects it from inside the instance.
  • "Need 1-minute EC2 metrics" → detailed monitoring. Basic monitoring sends data points every 5 minutes.
  • "Need 1-second data from last week" → not possible. High-resolution data points are kept for 3 hours only.
  • "Metric bill grew after a code change" → a high-cardinality dimension creates many metrics. Each new dimension value is a new billed metric.

Explanation

Key facts

  • A metric is a time-ordered set of data points. A name, a namespace, and zero or more dimensions identify it.
  • A namespace is a container that groups related metrics, for example AWS/EC2. AWS namespaces use AWS/<service>.
  • Do not start a custom namespace with AWS/, to avoid a conflict with AWS service namespaces.
  • A dimension is a name/value pair, for example InstanceId=i-0abc.
  • Each unique combination of dimension values is a separate metric, and CloudWatch bills each custom metric separately.
  • Do not use high-cardinality values as dimensions. High cardinality means many different values, such as a request ID or a user ID.
  • A RequestId dimension creates one new metric for each request. The bill grows, and each metric holds only one or two data points, so the graphs show nothing useful.
  • Put high-cardinality values in logs instead.
  • CloudWatch does not aggregate custom metrics across dimensions. Retrieve them with the same dimensions you published.
  • Example: you publish Latency with Service and Operation. A request for Latency with only Service returns no data. To get a per-service total, also publish that dimension set.
  • Metrics exist only in the Region where you create them.
  • You cannot delete a metric. It expires after 15 months with no new data.
  • Data point time stamps: up to 2 weeks in the past and up to 2 hours in the future. Use the current time when you can.
  • Alarms check data at the current UTC time, so data points with other time stamps can leave an alarm in INSUFFICIENT_DATA or delay it.
  • A data point stamped 24 hours ago or more can take at least 48 hours to appear in GetMetricData.
  • A new metric can take up to 15 minutes to appear in ListMetrics. A script or console search can therefore miss a metric that you just created.
  • Percentile statistics (for example, p99) need the individual values. If you publish only a statistic set (a summary of Sum, Minimum, Maximum, and SampleCount), CloudWatch cannot calculate percentiles. See the next topic.
  • Percentiles are also not available if a metric has negative values.

Custom metrics: PutMetricData, EMF, and the CloudWatch agent

Remember

  • PutMetricData is a synchronous API call with a request charge, and needs cloudwatch:PutMetricData.
  • With EMF (embedded metric format), the code writes a JSON log event and CloudWatch Logs extracts the metrics.
  • EMF needs no metric API call from the code.
  • The CloudWatch agent collects in-guest system metrics (memory, disk), logs, StatsD and collectd metrics, and traces.
  • Use EMF in Lambda and containers, because the function only writes a log line and does not wait for an API call.
  • Use PutMetricData when the code does not send logs to CloudWatch Logs. Example: a script that publishes one value.
  • Use the CloudWatch agent for operating system data from EC2 instances and on-premises servers.
  • One PutMetricData request carries up to 1,000 different metrics.
  • A PutMetricData request has a maximum size of 1 MB, and gzip compression is supported.
  • PutMetricData accepts up to 150 values for each metric with the Values and Counts arrays.
  • With Values and Counts, CloudWatch still has every value, so percentile statistics stay available.
  • A statistic set (Sum, Minimum, Maximum, SampleCount) reduces PutMetricData calls.
  • CloudWatch cannot calculate percentiles from a statistic set, unless all values are equal.
  • A PutMetricData metric can have up to 30 dimensions.
  • Set StorageResolution to 1 for high resolution (one data point each second).
  • Set StorageResolution to 60, or leave it out, for standard resolution (one data point each minute).
  • An EMF log event must be one valid JSON object with a root member _aws.
  • The EMF _aws member contains Timestamp (milliseconds since epoch) and the CloudWatchMetrics array of directives.
  • An EMF directive has Namespace, Dimensions (an array of dimension sets), and Metrics.
  • EMF metric values and dimension values must be root members of the JSON object, because nested members create no metric.
  • Each EMF dimension set creates a separate metric. Example: ["Service"] and ["Service", "Operation"] give two metrics.
  • An EMF dimension set has up to 30 keys.
  • One EMF log event has up to 100 metric definitions.
  • An EMF metric value array has up to 100 values.
  • An EMF time stamp must be no more than 14 days in the past or 2 hours in the future.
  • CloudWatch does not publish an EMF metric whose time stamp is outside the 14-day and 2-hour window.
  • If the JSON is not valid EMF, the event stays a normal log line and CloudWatch creates no metric.
  • EMF costs log ingestion, log storage, and custom metrics, but no PutMetricData request charges.
  • Libraries such as Powertools for AWS Lambda write EMF for you.

Exam signals

  • "Lambda custom metrics with no extra latency and no API calls" → EMF. The function writes a log line, and CloudWatch Logs creates the metric.
  • "EMF lines are in the logs but the metric does not appear" → check the _aws structure and that targets are root members. An event that is not valid EMF stays a normal log line.
  • "Too many PutMetricData calls" → batch data points, or use statistic sets or Values/Counts. One call can then carry many values.
  • "Collect memory and disk metrics from EC2 or on-premises servers" → CloudWatch agent. The agent runs inside the server and reads operating system data.

Metric alarms and missing data

Remember

  • A metric alarm watches one metric or one metric math expression and compares it to a threshold.
  • Metric math calculates a new time series from other metrics. Example: 100*errors/invocations.
  • An alarm on an error rate does not fire just because traffic grows.
  • A metric math expression in an alarm must give one time series.
  • You cannot alarm on a SEARCH expression, because a search can return many time series.
  • An alarm has only three states: OK, ALARM, and INSUFFICIENT_DATA.
  • The alarm Period is the length of one data point.
  • Evaluation Periods (N) is the number of recent data points that the alarm evaluates.
  • Datapoints to Alarm (M) is the number of those N data points that must breach.
  • For "3 of the last 5 periods breach", set EvaluationPeriods to 5 and DatapointsToAlarm to 3.
  • An alarm performs actions only when its state changes.
  • An alarm that stays in ALARM for an hour sends one SNS notification, not one each minute.
  • Auto Scaling alarm actions repeat each minute while the alarm state stays the same.
  • Use an alarm period equal to or longer than the time between data points. Example: at least 300 seconds for EC2 basic monitoring.
  • An alarm period shorter than the data interval sees mostly missing data and uses TreatMissingData.
  • A high-resolution alarm uses a period of 10 or 30 seconds, on a high-resolution metric only.
  • Use a high-resolution alarm when you must react within seconds, for example to a fast-growing queue backlog.
  • A high-resolution alarm costs more, so use a 60-second period when a one-minute delay is acceptable.
  • To test alarm actions, call SetAlarmState, which sets a state that lasts until the next evaluation.
  • You can create an alarm for a custom metric before the metric exists.
  • An alarm on a custom metric must include all its dimensions, or the alarm never receives data.
  • CloudWatch keeps alarm history for 30 days.
  • TreatMissingData missing is the default: all points missing sends the alarm to INSUFFICIENT_DATA.
  • TreatMissingData notBreaching counts missing points as good (within the threshold).
  • TreatMissingData breaching counts missing points as bad (breaching).
  • TreatMissingData ignore keeps the current alarm state.
  • Use notBreaching for a metric that reports data only when a problem occurs, such as Errors.
  • Use breaching for a heartbeat metric, where silence means failure.
  • Use ignore when a gap tells you nothing.
  • Alarms on AWS/DynamoDB metrics default to ignore.
  • The Lambda Errors metric counts only function errors: code exceptions and runtime errors such as timeouts.
  • A Lambda handler that returns statusCode: 500 is not a function error, so Errors does not increase.
  • The Lambda Throttles metric counts requests that Lambda rejects because the function has no free concurrency.
  • Throttled Lambda requests do not count as Invocations or Errors.

Exam signals

  • "Alarm stays in INSUFFICIENT_DATA because the metric has gaps" → TreatMissingData notBreaching. The gaps then count as good data points.
  • "Alarm only if 3 of 5 minutes breach" → EvaluationPeriods 5, DatapointsToAlarm 3.
  • "Errors stays 0 but users see failures" → throw the error, or publish a custom metric. The code catches errors and returns a response, so Lambda sees a success and Errors does not count it.
  • "Test the notification without a real failure" → SetAlarmState. The forced state change runs the alarm actions.

Alarm actions, notifications, composite alarms, and anomaly detection

Remember

  • Metric alarms and composite alarms can both send SNS notifications and invoke Lambda functions.
  • Only a metric alarm can run EC2 actions (stop, terminate, reboot, recover), and only on EC2 metrics.
  • Only a metric alarm, not a composite alarm, can run EC2 Auto Scaling actions.
  • An alarm creates a Systems Manager OpsItem or an Incident Manager incident only in the ALARM state.
  • A Lambda alarm action invokes the function asynchronously, so the alarm does not see the function result.
  • For a Lambda alarm action, Lambda queues the event and retries a failed run.
  • A Lambda alarm action needs a resource-based policy that allows lambda.alarms.cloudwatch.amazonaws.com.
  • Without the resource-based policy, the alarm changes state but the Lambda function never runs.
  • Limit the Lambda resource-based policy with AWS:SourceAccount or AWS:SourceArn, so only your alarms invoke it.
  • Alarms also send state-change events to Amazon EventBridge.
  • Use an EventBridge rule when a target that is not a direct alarm action, such as Step Functions, must react.
  • CodeDeploy sends deployment state-change events (SUCCESS, FAILURE) to EventBridge.
  • CodePipeline sends CodePipeline Pipeline Execution State Change events (FAILED, SUCCEEDED) to EventBridge.
  • To notify a team about a deployment result, use an EventBridge rule with an SNS topic or Lambda target.
  • Developer Tools notification rules notify on CodeBuild, CodeCommit, CodeDeploy, and CodePipeline events.
  • Notification rule targets are SNS topics and chat applications (AWS Chatbot, now Amazon Q Developer in chat applications).
  • A notification rule creates an EventBridge rule for you.
  • Many services publish usage metrics in the AWS/Usage namespace.
  • The metric math function SERVICE_QUOTA(m1) returns the current quota for the usage metric m1.
  • To warn before a quota is reached, alarm on m1/SERVICE_QUOTA(m1)*100, for example above 80 percent.
  • A SERVICE_QUOTA alarm stays correct when the quota changes, because no number is hardcoded.
  • A composite alarm uses a rule expression over the states of other alarms.
  • Composite alarm rules use ALARM(), OK(), INSUFFICIENT_DATA(), AND, OR, NOT, TRUE, and FALSE.
  • A composite alarm rule can include metric alarms and other composite alarms, but not a metric directly.
  • To reduce alarm noise, remove actions from the child alarms and put one action on the composite alarm.
  • While an actions suppressor alarm is in ALARM, the composite alarm does not run its actions.
  • CloudWatch does not support cross-account composite alarms.
  • Anomaly detection trains a model on up to two weeks of metric data.
  • You can turn on anomaly detection before two weeks of data exist.
  • The anomaly detection model includes trends and hourly, daily, and weekly patterns.
  • An anomaly detection alarm compares the metric to a band of expected values (ANOMALY_DETECTION_BAND).
  • A higher anomaly detection threshold makes the band wider: fewer false alarms, but small anomalies can pass unseen.
  • Alarm above the anomaly band when only high values are bad, such as errors or latency.
  • Alarm below the anomaly band when a drop is bad, such as an order count.
  • Alarm outside the anomaly band when both directions matter.
  • You can exclude time periods, such as a deployment, from anomaly detection training.

Exam signals

  • "Two alarms send two notifications for one incident" → composite alarm with AND, actions only on the composite. The child alarms then send nothing.
  • "Metric has a daily pattern, static threshold gives false alarms" → anomaly detection alarm. Its band follows the daily pattern, and one fixed number cannot.
  • "Alarm must run custom remediation code" → Lambda alarm action with a resource-based policy. The policy lets CloudWatch invoke the function.
  • "Composite alarm must reboot an instance" → not possible. Put the EC2 action on a metric alarm.
  • "Email the team when a deployment fails" → EventBridge rule on CodeDeploy state change, or a notification rule, to SNS. CodeDeploy already sends these events, and SNS sends the email with no code.
  • "Warn before the account reaches a service quota" → alarm on the usage metric with SERVICE_QUOTA. The alarm compares usage with the real quota.

X-Ray traces, segments, annotations, and metadata

Remember

  • An X-Ray segment records the work of one service for a request: host, request, response, timing, and errors.
  • An X-Ray subsegment records finer work inside a segment, such as a call to DynamoDB, an HTTP API, or SQL.
  • An X-Ray trace collects all segments for one request, and a trace ID connects them.
  • The trace ID and the sampling decision travel in the HTTP header X-Amzn-Trace-Id.
  • If a service drops the X-Amzn-Trace-Id header, the next service starts a new, separate trace.
  • For a service that sends no segments, such as DynamoDB, X-Ray builds inferred segments from your subsegments.
  • X-Ray builds a service graph from the segments, and the console shows it as the trace map.
  • The X-Ray Error type is a client error (HTTP 4xx).
  • The X-Ray Fault type is a server error (HTTP 5xx).
  • The X-Ray Throttle type is HTTP 429 (Too Many Requests).
  • X-Ray filter expressions find traces. Examples: annotation[customer_tier] = "gold", responsetime > 5.
  • An X-Ray group is a saved filter expression.
  • X-Ray publishes CloudWatch metrics for each group every minute, so you can alarm on the matching traces.
  • To see a latency histogram, choose a node or an edge on the trace map.
  • A node latency histogram excludes network time and shows the time inside one service.
  • An edge latency histogram includes network time and shows the latency that the caller sees.
  • X-Ray indexes annotations for filter expressions, but X-Ray does not index metadata.
  • An annotation is a simple key-value pair with a string, number, or Boolean value.
  • X-Ray metadata accepts any type, including objects and lists.
  • X-Ray indexes up to 50 annotations for each trace.
  • An X-Ray segment document has a maximum size of 64 KB, and this size also limits metadata.
  • Use annotations for values that you search on, such as customer tier, order ID, or game ID.
  • Use metadata for debug data, such as full request or response bodies.
  • X-Ray keeps trace data and service graphs for 30 days.

Exam signals

  • "Search traces by customer ID" → annotation (not metadata). Only annotations are indexed for filter expressions.
  • "Store the full payload with the trace, no search needed" → metadata. Metadata accepts objects and lists.
  • "Find which downstream call adds latency" → subsegments on the trace timeline and the service map. Each subsegment records the time of one downstream call.
  • "Requests from one service do not join the upstream trace" → propagate the X-Amzn-Trace-Id header. The trace ID in that header connects the segments.

Explanation

Key facts

  • A segment records the work of one service for a request: host, request, response, timing, errors.
  • A subsegment records finer work inside a segment, such as a call to DynamoDB, an HTTP API, or a SQL database.
  • A trace collects all segments for one request. A trace ID connects them.
  • The trace ID and sampling decision travel in the HTTP header X-Amzn-Trace-Id. Each service passes the header to the next one. If a service drops it, the next service starts a new, separate trace.
  • For services that do not send segments (for example, DynamoDB), X-Ray builds inferred segments from your subsegments. DynamoDB then appears as a node on the map even though DynamoDB sends no trace data.
  • X-Ray builds a service graph from the segments. The console shows it as the service map (trace map).
  • X-Ray sorts errors into three types. Error is a client error (HTTP 4xx), so the caller sent a bad request.
  • Fault is a server error (HTTP 5xx), so the service failed.
  • Throttle is HTTP 429 (Too Many Requests).
  • Filter expressions find traces, for example annotation[customer_tier] = "gold" or responsetime > 5.
  • A group is a saved filter expression. X-Ray publishes CloudWatch metrics for each group every minute, so you can alarm on the traces that match it.
  • Choose a node or an edge on the trace map to see a latency histogram. Select a duration range to see only the slow traces.
  • A node histogram does not include network time. An edge histogram does.
  • Use the edge histogram to see the latency that the caller sees, including the network. Use the node histogram to see the time spent inside one service.

Remember

  • To trace Lambda, turn on active tracing (TracingConfig Mode: Active, SAM Tracing: Active).

Daemon

  • The X-Ray daemon is a small program that runs next to your application. It listens on UDP port 2000, collects segments, and sends them in batches to the X-Ray API. The SDK sends segments to the local daemon over UDP, so the application does not wait for calls to X-Ray.

  • On EC2 and Elastic Beanstalk, attach the policy to the instance profile role.
  • CloudWatch agent version 1.300025.0 and later can collect X-Ray and OpenTelemetry traces. You then need no separate daemon.

Instrumentation (X-Ray SDK)

  • Instrument AWS SDK clients and HTTP clients to record subsegments for downstream calls. To instrument a client means to wrap it so that the SDK records each call.
  • For example, Python patch_all() wraps boto3, requests, and other supported libraries. Without it, the trace shows your service but none of its downstream calls.
  • Create custom subsegments for your own code blocks, for example to time one slow function.
  • Add annotations and metadata to segments or subsegments.

Sampling

  • Sampling means that X-Ray records only some requests, to limit cost and overhead. A sampling rule sets which requests to record.
  • Default: the first request each second (the reservoir) and 5 percent of additional requests (the rate). Example: at 101 requests each second, X-Ray records 1 + 5 (5 percent of 100) = about 6 requests each second.
  • Rule fields: priority (1 to 9999, lower is evaluated first), reservoir, rate, service name, service type, host, HTTP method, URL path, resource ARN. The first rule that matches a request decides its sampling.
  • Rules in the X-Ray service apply without a redeploy, because the SDK reads them from X-Ray.
  • X-Ray shares the reservoir across all instances, so the reservoir is a total for the whole fleet.
  • Local rules in a JSON file need a redeploy to change.
  • With local rules, each instance applies its own reservoir, so 10 instances with a reservoir of 1 record up to 10 requests each second.
  • The first X-Ray-enabled service makes the sampling decision and writes it in the trace header. Downstream services follow it. Example: if API Gateway does not sample a request, the Lambda function behind it does not record that request either.
  • For Lambda, you cannot change the sampling rate. Lambda records 1 request each second and 5 percent of additional requests.

CloudTrail integrity, encryption, Insights, and EventBridge

Remember

  • With log file integrity validation turned on, CloudTrail creates a hash for every log file.
  • A hash is a short value from the file content, and a change of one byte changes the hash.
  • Every hour, CloudTrail delivers a digest file with the hashes of the last hour's log files.
  • CloudTrail signs each digest file with a private key that only CloudTrail has.
  • A person who changes a log file cannot also change the signed digest file to match.
  • Integrity validation uses SHA-256 for hashing and SHA-256 with RSA for signing.
  • Integrity validation shows if a log file was changed, deleted, or not changed after delivery.
  • To validate CloudTrail log files, run aws cloudtrail validate-logs.
  • CloudTrail puts digest files in the same bucket as the log files, in a separate folder.
  • Trails created in the console use SSE-KMS by default.
  • Without SSE-KMS, CloudTrail encrypts log files with SSE-S3.
  • The CloudTrail KMS key must be in the same Region as the S3 bucket that receives the log files.
  • To read SSE-KMS log files, a user needs S3 read permission and decrypt permission on the KMS key.
  • With S3 read permission only, a read of an SSE-KMS log file fails with an access denied error.
  • The KMS key policy must allow CloudTrail to use the key, because CloudTrail encrypts each log file.
  • CloudTrail Insights finds unusual API call rates (write APIs) and unusual API error rates (read and write APIs).
  • CloudTrail Insights analyzes management events and learns the normal rate for the account.
  • CloudTrail Insights reports a spike, not each single call.
  • Turn on CloudTrail Insights for a trail or an event data store, at an extra charge.
  • For a trail, CloudTrail Insights events can take up to 36 hours to start.
  • CloudTrail sends events to the default event bus with detail-type AWS API Call via CloudTrail.
  • CloudTrail sign-in events use the detail-type AWS Console Signin via CloudTrail.
  • CloudTrail events reach EventBridge only from a trail with logging turned on, or the rule never matches.
  • EventBridge rules in the default ENABLED state match write management events and data events.
  • Read-only management events match only rules in the ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS state. Examples: Get*, List*, Describe*.
  • A rule in the default state for DescribeInstances never invokes its target.
  • To react to an API call in near real time, use an EventBridge rule, for example to invoke Lambda.

  • "Company must control the key for trail logs" → SSE-KMS with a customer managed key. Readers need kms:Decrypt.
  • "Detect an unusual spike in API calls or errors" → CloudTrail Insights. CloudTrail Insights compares the current rate with the normal rate.
  • "Run code when someone deletes a bucket" → EventBridge rule on AWS API Call via CloudTrail. The rule receives each matching API call in near real time and passes the details to the target.
