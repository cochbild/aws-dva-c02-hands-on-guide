Orchestration, sagas, and starting executions

Remember

  • AWS Step Functions runs a state machine. You write the state machine in the Amazon States Language (ASL), a JSON format.
  • One run of a state machine is an execution. Each execution gets JSON input and makes JSON output.
  • In orchestration, one central workflow decides which step runs next. Step Functions is the orchestration service.
  • In choreography, services react to events through SNS, SQS, or EventBridge. No central controller exists.
  • Step Functions keeps the workflow state, the retries, and the error paths out of your function code.
  • Step Functions assumes the state machine execution role for each call to another service.
  • A missing permission in the execution role makes the task fail with States.Permissions or an access denied error.
  • A saga is a sequence of local transactions in different services, without one database transaction across them.
  • When a later saga step fails, compensating steps undo the earlier steps, usually in reverse order.
  • In a Step Functions saga, a Catch on each step sends the failure to its compensating step.
  • Make each saga step and each compensating step idempotent, because a retry can run a step again.
  • A saga gives eventual consistency, not isolation. Other requests can see the data between steps.
  • StartExecution works for Standard and Express and returns only an executionArn, not the result.
  • StartSyncExecution works for Express only. The call waits and returns the workflow result.
  • StartSyncExecution on a Standard state machine fails with StateMachineTypeNotSupported.
  • To get a result after StartExecution, call DescribeExecution (Standard only) or read the place the workflow writes to.
  • An API Gateway HTTP API uses the subtypes StepFunctions-StartExecution, StepFunctions-StartSyncExecution, and StepFunctions-StopExecution.
  • An API Gateway REST API starts a workflow with an AWS service integration and an IAM role that allows the action.
  • An EventBridge rule or schedule can start a state machine. EventBridge needs a role that allows states:StartExecution.
  • A parent state machine starts a nested workflow with a Task on arn:aws:states:::states:startExecution.
  • With .sync, the parent waits for the child execution to complete. Without .sync, the parent continues at once.

Exam signals

  • "Coordinate several Lambda functions with branching, retries, and a visual history" → Step Functions.
  • "Fan out one event to many independent subscribers" → Amazon SNS or EventBridge (choreography), not Step Functions. The subscribers do not depend on each other, so no central controller has to decide an order.
  • "HTTP client must get the workflow result in the same request" → API Gateway with StartSyncExecution on an Express workflow. StartExecution returns only the execution ARN, not the result.
  • "Start the workflow when an object lands in S3" → EventBridge rule with the state machine as the target. Turn on EventBridge notifications on the bucket so that S3 sends the "Object Created" event to EventBridge.
  • "Undo the flight and hotel bookings when the payment fails" → saga pattern with Catch and compensating steps.

Explanation

Key facts

  • AWS Step Functions runs a state machine. You write the state machine in the Amazon States Language (ASL), a JSON format.
  • One run of a state machine is an execution. Each execution gets JSON input and makes JSON output.
  • Orchestration: one central workflow decides which step runs next. Step Functions is the orchestration service.
  • Choreography: services react to events from each other (Amazon SNS, Amazon SQS, Amazon EventBridge). There is no central controller.
  • Step Functions keeps the workflow state, the retries, and the error paths out of your function code. Without it, each function must call the next function and contain its own retry code.
  • The state machine uses an IAM execution role to call other services. Step Functions assumes this role for each call. If the role does not allow an action, the task fails with States.Permissions or an access denied error.

Saga pattern (compensating transactions)

  • A saga is a sequence of local transactions in different services. There is no single database transaction across the services.
  • If a later step fails, the workflow runs compensating steps that undo the earlier steps, usually in reverse order.
  • In Step Functions, a Catch on each step sends the failure to its compensating step. For example, a failed payment goes to "cancel car rental", then "cancel flight", then a Fail state.
  • Make each step and each compensating step idempotent: a second run with the same input has the same effect as one run. A retry can run a step again, and an idempotent step then does not book or refund two times.
  • The saga gives eventual consistency, not isolation. Other requests can see the data between steps, for example a flight that is booked before the payment fails and the compensating step cancels it.

State types and Choice rules

Remember

  • A Task state does one unit of work: a Lambda function, an AWS service API, an activity, or an HTTPS API.
  • Task, Parallel, and Map states support Retry and Catch.
  • A Choice state branches on the input. A Choice state has no Retry or Catch.
  • A Choice state cannot end the execution, so it has no End field. Each rule names its own Next.
  • A Wait state pauses for Seconds, SecondsPath, Timestamp, or TimestampPath.
  • No compute runs during a Wait state. Use a Wait state in place of a Lambda function that sleeps.
  • In a Standard workflow, a Wait state costs one state transition, not function run time.
  • In an Express workflow, the time in a Wait state counts toward the billed duration.
  • A Parallel state runs fixed branches at the same time.
  • A Map state runs the same steps for each item in a dataset.
  • A Pass state passes or reshapes data and injects a fixed value with Result. A Pass state cannot run code.
  • Succeed and Fail states are terminal. A Succeed or Fail state has no Next field.
  • A Fail state ends the execution with failure and sets Error and Cause.
  • Step Functions examines Choice rules in the order of the Choices array. The first match wins.
  • With no matching rule and no Default, the execution fails with States.NoChoiceMatched.
  • Choice operators have types. NumericGreaterThan does not match the string "500".
  • Add Path to an operator to compare with another input value. Example: NumericLessThanPath.
  • IsPresent, IsNull, IsNumeric, and IsString test a field.
  • A Choice comparison on a missing field fails with States.Runtime. States.ALL cannot catch that error.
  • To protect a comparison on a field that can be missing, put IsPresent before it in an And.
  • And, Or, and Not combine Choice rules. Only the top-level rule has Next.
  • StringMatches supports only the * wildcard, not regular expressions.
  • To match a literal asterisk in StringMatches, write \\* in the JSON definition.

Exam signals

  • "Execution fails when the input matches no branch" → add Default to the Choice state.
  • "Pause until a date in the input, up to 30 days" → Wait state with TimestampPath in a Standard workflow. TimestampPath reads the date from the input, and only Standard can run longer than 5 minutes.
  • "A Fail state with a Next field" → invalid ASL. Succeed and Fail are terminal: they end the execution, so no state can come after them.
  • "Large amounts go to the wrong branch" → check the rule order. The first matching rule wins.

Choice rules

  • Step Functions examines the rules in the order of the Choices array. The first match wins.
  • Use Default for input that matches no rule. With no match and no Default, the execution fails with States.NoChoiceMatched.
  • Operators have types: StringEquals, NumericGreaterThanEquals, BooleanEquals, TimestampLessThan, and more. A numeric operator does not match a string value. For example, NumericGreaterThan does not match the string "500", so Step Functions goes to the next rule or to Default.
  • Add Path to an operator to compare with another input value instead of a fixed value. For example, "Variable": "$.total", "NumericLessThanPath": "$.limit" compares two fields of the input.
  • IsPresent, IsNull, IsNumeric, and IsString test a field.
  • Use IsPresent in an And before a comparison on a field that can be missing. A comparison on a missing field fails with States.Runtime. States.ALL cannot catch that error, so the execution always fails.
  • And, Or, and Not combine rules. Only the top-level rule has Next.
  • StringMatches supports the * wildcard only, for example "log-*.txt". It does not support regular expressions. To match a literal asterisk, write \\* in the JSON definition.

Input and output processing, JSONata, and variables

Remember

  • JSONPath fields apply in this order: InputPath, Parameters, ResultSelector, ResultPath, OutputPath.
  • InputPath selects part of the state input. The default is $ (all input).
  • Parameters builds the task input. A key that ends in .$ takes a path or an intrinsic function.
  • Without .$, a value such as "$.order.id" is a literal string, not a path.
  • ResultSelector builds a new object from the task result.
  • OutputPath selects part of the output for the next state. The default is $.
  • ResultPath with "$" or no value makes the result replace the whole input.
  • ResultPath: "$.validation" keeps the input and adds the result under validation.
  • ResultPath: null discards the result. The output is the original input.
  • $$ is the Context object: data about the execution, not the state input. Example: $$.Task.Token.
  • In a Map state, $$.Map.Item.Value is the current item and $$.Map.Item.Index is its position.
  • The optimized lambda:invoke integration returns invoke metadata. The function output is in Payload.
  • To pass only the Lambda function output, select $.Payload with ResultSelector or OutputPath.
  • Intrinsic functions do small data operations without a Lambda function. Examples: States.Format, States.UUID, States.MathAdd.
  • Intrinsic functions work in JSONPath states only.
  • Step Functions has two query languages: JSONPath and JSONata. Set the language with QueryLanguage.
  • Without QueryLanguage, a state machine uses JSONPath.
  • AWS recommends JSONata for new state machines. One expression can filter, reshape, and compute values.
  • JSONata states use Arguments in place of Parameters. An expression is inside {% %}.
  • In JSONata, one Output field replaces InputPath, ResultSelector, ResultPath, and OutputPath.
  • In JSONata, $states.input is the state input and $states.result is the task result.
  • In JSONata, $states.errorOutput is the error in a Catch, and $states.context is the Context object.
  • The Assign field stores a variable. A later state reads the variable as $name.
  • A variable is available to all later states. State output goes only to the next state.
  • Variables work in JSONPath and JSONata states. In JSONPath, you cannot use a variable in ResultPath.
  • A value that a state assigns is available from the next state. The assigning state still sees the old value.
  • Parallel branches and Inline Map iterations can read outer variables, but a variable that a branch assigns stops existing when that state completes.
  • Distributed Map cannot read outer variables. Pass the value to each item with ItemSelector.
  • Variable limits: 256 KiB for one variable, 256 KiB for one Assign field, 10 MiB for one execution.
  • Input or output of a task, state, or execution has a hard limit of 256 KiB.
  • Data larger than 256 KiB fails with States.DataLimitExceeded. Store large data in S3 and pass the bucket and key.

Exam signals

  • "Keep the original input and add the Lambda result" → ResultPath: "$.result".
  • "Next state sees StatusCode and Payload, not the function output" → select $.Payload with ResultSelector or OutputPath.
  • "Data between states is larger than 256 KiB" → store it in Amazon S3 and pass the bucket and key.
  • "Generate a unique ID without a Lambda function" → States.UUID().
  • "Step 5 needs a value from step 1, and steps 2 to 4 do not need it" → store it in a variable with Assign.

ResultPath values

  • "$" or no ResultPath: the result replaces the whole input.
  • "$.validation": the output is the input plus the result under validation.
  • null: Step Functions discards the result. The output is the original input.

Key facts

  • Without .$, a value such as "$.order.id" is a literal string, not a path.
  • $$ is the Context object: data about the execution itself, not the state input. Examples: $$.Execution.Input (the original execution input), $$.Task.Token (the token for a callback task), $$.Map.Item.Value and $$.Map.Item.Index (the current Map item and its position).
  • The optimized lambda:invoke integration returns invoke metadata (StatusCode, ExecutedVersion, and others). The function output is in Payload.
  • Without a filter, the next state gets the metadata object, not the function output. Use ResultSelector or OutputPath with $.Payload.
  • Intrinsic functions do small data operations in the definition, so you do not need a Lambda function for them. They work in JSONPath states only: States.Format, States.StringToJson, States.JsonToString, States.Array, States.ArrayPartition, States.MathAdd, States.UUID, States.Hash, States.Base64Encode, and others.

JSONata and variables

  • Step Functions has two query languages: JSONPath and JSONata. Set QueryLanguage on the state machine or on one state. Without it, the state machine uses JSONPath.
  • AWS recommends JSONata for new state machines. One JSONata expression can filter, reshape, and compute values. The same work in JSONPath needs several path fields and intrinsic functions.
  • JSONata states use Arguments (in place of Parameters) and Output (in place of the path fields). One Output field replaces InputPath, ResultSelector, ResultPath, and OutputPath. An expression is inside {% %}.
  • In JSONata, $states.input is the state input, $states.result is the task result, $states.errorOutput is the error in a Catch, and $states.context is the Context object.
  • Variables: the Assign field stores a value. A later state reads it as $name. State output goes only to the next state, but a variable is available to all later states.
  • Variables work in JSONPath and JSONata states.
  • In JSONPath, you cannot use a variable in ResultPath. ResultPath names a location in the input, not a value.
  • A value that a state assigns is available from the next state. The same state still sees the old value, because Step Functions evaluates all expressions before it assigns.
  • Parallel branches and Map iterations can read outer variables, but they have their own scope. A variable that a branch assigns stops existing when the Parallel or Map state completes. Use the state output to pass data out of the branch.
  • Distributed Map cannot read outer variables. Pass the value to each item with ItemSelector instead.
  • Limits: 256 KiB for one variable, 256 KiB for all variables in one Assign field, 10 MiB for all variables in one execution.

Standard and Express workflows

Remember

  • A Standard workflow runs for at most 1 year. An Express workflow runs for at most 5 minutes.
  • Standard is exactly-once. A Standard step runs again only if you configure Retry.
  • Asynchronous Express is at-least-once, so a step can run more than one time.
  • Synchronous Express is at-most-once: a step runs one time or not at all.
  • Standard charges for each state transition. Express charges for executions, duration, and memory.
  • Express is usually less expensive at high volume because Express does not charge for each state transition.
  • Step Functions keeps Standard execution history for 90 days after the execution closes.
  • DescribeExecution and GetExecutionHistory work for Standard. For Express history, enable CloudWatch Logs.
  • Standard supports Request Response, .sync, and .waitForTaskToken. Express supports Request Response only.
  • Express does not support activities, Distributed Map, or redrive. Standard supports all three.
  • Asynchronous Express (StartExecution, an event, or a nested workflow) does not wait. Read the result from CloudWatch Logs.
  • Synchronous Express (StartSyncExecution) makes the caller wait and returns the result.
  • A synchronous Express request from the console expires after 60 seconds. Use the SDK or CLI for up to 5 minutes.
  • You cannot change the workflow type of a state machine. Create a new state machine.
  • Use Standard for long, durable, or auditable work, and for non-idempotent steps such as payments.
  • Use Express for short, high-volume event processing where each step is idempotent.
  • Standard StartExecution with the same name and input as a running execution returns the same response, without a second execution.
  • Standard StartExecution with a used name and different input, or after the execution closed, fails with ExecutionAlreadyExists.
  • Express does not manage idempotency. The same execution name can start concurrent Express executions.
  • A Standard parent can call an Express child for the high-volume idempotent steps to reduce cost.

Exam signals

  • "High volume, each run takes less than a minute, idempotent, lowest cost" → Express. Express charges by executions, duration, and memory, not for each state transition.
  • "Human approval that can take days" or "run longer than 5 minutes" → Standard. Express stops at 5 minutes and does not support the callback pattern.
  • "Step must never run twice, for example charging a card" → Standard (exactly-once). Asynchronous Express is at-least-once, so it can charge two times.
  • "Client retries StartExecution and must not create a duplicate run" → Standard with a unique business ID as the execution name. Standard does not start a second execution with a name that is already in use.

Execution semantics tell you how many times a step can run. Exactly-once: each step runs one time. At-least-once: a step can run more than one time, so a duplicate charge or email is possible. At-most-once: a step runs one time or not at all.

Choose Standard for long, durable, or auditable work, and for steps that must not run twice. Choose Express for short, high-volume event processing where each step is idempotent.

Express is usually less expensive at high volume because it does not charge for each state transition.

Key facts

  • Asynchronous Express (StartExecution, an event, or a nested workflow): the caller gets confirmation that the workflow started. It does not wait. Read the result from CloudWatch Logs.
  • Synchronous Express (StartSyncExecution, from API Gateway, Lambda, or the SDK): the caller waits and gets the result. A synchronous request from the console expires after 60 seconds. Use the SDK or CLI for up to 5 minutes.
  • You cannot change the workflow type after you create the state machine. Create a new state machine.
  • Standard is for non-idempotent actions, such as payments. A non-idempotent action has a new effect each time it runs: a second run charges the card again.
  • Express is for idempotent, high-volume event processing, where a second run does no harm.
  • Standard: a StartExecution call with the same name and the same input as a running execution returns the same response. It does not start a second execution. A call with the same name and a different input, or after that execution closed, fails with ExecutionAlreadyExists.
  • Express: Step Functions does not manage idempotency. The same name can start concurrent executions. A client that retries StartExecution starts a second run, so each step must be idempotent.
  • A Standard parent can call an Express child for the high-volume idempotent part. This can reduce cost.
  • The parent keeps the non-idempotent steps (for example approval and payment). The child runs the many short idempotent steps (for example notifications and inventory updates) without per-transition pricing.

Error handling with Retry and Catch

Remember

  • Task, Parallel, and Map states support Retry and Catch.
  • An unhandled error fails the whole execution.
  • Retriers run first. A catcher runs only after the matching retrier stops, or when no retrier matches.
  • Step Functions uses the first retrier or catcher in array order that matches the error name.
  • Put specific error names first and States.ALL last, alone in its ErrorEquals.
  • Each retrier counts its attempts separately. After MaxAttempts, the next matching error goes to the catchers.
  • Each retry counts as a state transition. Standard workflows bill retries.
  • Retrier defaults: IntervalSeconds 1, MaxAttempts 3, BackoffRate 2.0, JitterStrategy NONE.
  • MaxAttempts 0 means never retry.
  • MaxDelaySeconds sets an upper limit for one wait. By default, a wait has no upper limit.
  • IntervalSeconds 2 and BackoffRate 2 give waits of 2, 4, and 8 seconds (exponential backoff).
  • JitterStrategy: FULL makes each wait random, so many failed executions do not retry at the same moment.
  • States.ALL matches any error except States.Runtime and States.DataLimitExceeded.
  • States.TaskFailed matches any error except States.Timeout, so a retrier for it also retries business errors.
  • States.Timeout means a task exceeded TimeoutSeconds or HeartbeatSeconds, or an execution exceeded its limit.
  • States.HeartbeatTimeout means a task sent no heartbeat within HeartbeatSeconds.
  • States.Permissions means the execution role does not have the permission to run the task.
  • States.DataLimitExceeded means a payload is larger than 256 KiB. Name it explicitly to catch it.
  • States.Runtime means Step Functions could not process the data. States.Runtime is not retriable and always fails the execution.
  • States.ExceedToleratedFailureThreshold means a Distributed Map had more failed items than the threshold.
  • A catcher has ErrorEquals, Next, and an optional ResultPath.
  • A catcher without ResultPath replaces the input with the error output (Error and Cause).
  • To keep the input and add the error, use "ResultPath": "$.error" on the catcher.
  • Lambda service errors have the name Lambda.<ErrorName>. Errors from your function code keep their own type.
  • Catch business errors from your function code by name so that the workflow does not retry them.
  • Add a retrier for Lambda.ServiceException, Lambda.AWSLambdaException, Lambda.SdkClientException, and Lambda.ClientExecutionTimeoutException.
  • The AWS example retrier for transient Lambda errors uses IntervalSeconds 2, MaxAttempts 6, and BackoffRate 2.
  • Lambda throttling shows as Lambda.TooManyRequestsException.

Exam signals

  • "Retry with exponential backoff and jitter" → Retry with BackoffRate and JitterStrategy: FULL.
  • "Fallback state lost the original input" → add ResultPath to the catcher. Without it, the error output replaces the input.
  • "Retry everything except timeouts" → retrier for States.Timeout with MaxAttempts: 0, then States.ALL. The first matching retrier wins, so a timeout matches the first retrier and is never retried.
  • "Catch States.ALL did not catch the failure" → States.Runtime or States.DataLimitExceeded. These are the two errors that States.ALL does not match.

Explanation

Key facts

  • Task, Parallel, and Map states support Retry and Catch.
  • An unhandled error fails the whole execution.
  • Retriers run first. Step Functions uses a catcher only after the matching retrier stops, or when no retrier matches.
  • Step Functions scans retriers and catchers in array order and uses the first one that matches the error name. Put specific error names first and States.ALL last.
  • Each retrier counts its attempts separately. When one retrier reaches its MaxAttempts, the next error that it matches goes to the catchers.
  • Each retry counts as a state transition. Standard workflows bill retries.
  • Errors from the Lambda service, such as throttling or a service fault, have the name Lambda.<ErrorName>.
  • An error that your function code throws keeps its own error type, for example InvalidOrderError. Catch those business errors by name so that the workflow does not retry them.

Catch and ResultPath

  • A catcher has ErrorEquals, Next, and an optional ResultPath.
  • With no ResultPath, the error output (Error and Cause) replaces the input.
  • Use "ResultPath": "$.error" to keep the input and add the error.

Transient Lambda errors

AWS recommends a retrier for Lambda.ServiceException, Lambda.AWSLambdaException, Lambda.SdkClientException, and Lambda.ClientExecutionTimeoutException. These are temporary 500 errors in the Lambda service, not bugs in your code, so a retry usually succeeds.

Without a retrier, one of these errors fails the whole execution.

The documented example uses IntervalSeconds 2, MaxAttempts 6, and BackoffRate 2.

Throttling shows as Lambda.TooManyRequestsException.

Timeouts, heartbeats, and quotas

Remember

  • The default Task TimeoutSeconds is 99,999,999 seconds, so ASL sets no useful timeout by default.
  • A task that never answers keeps the execution open until the execution limit.
  • Set TimeoutSeconds on each Task state. A task that runs longer fails with States.Timeout.
  • Set HeartbeatSeconds lower than TimeoutSeconds. The worker calls SendTaskHeartbeat regularly.
  • A missed heartbeat fails the task with States.HeartbeatTimeout or States.Timeout. Match both in a retrier or catcher.
  • Use a heartbeat for long callback tasks to detect a worker that stopped.
  • A 2-hour job with HeartbeatSeconds 600 fails within 10 minutes after the worker crashes.
  • A top-level TimeoutSeconds limits the whole execution. A longer execution fails with States.Timeout.
  • An Express execution that runs longer than 5 minutes fails with States.Timeout.
  • Maximum execution time is 1 year for Standard and 5 minutes for Express. Both are hard quotas.
  • A Standard execution history has a hard quota of 25,000 events. The execution fails at this quota.
  • Step Functions keeps Standard execution history for 90 days after the execution closes.
  • The payload size limit is 256 KiB.
  • The state machine definition size limit is 1 MB.
  • An execution name has at most 80 characters and is unique in the account and Region.
  • You can redrive an execution for 14 days after the execution closes.
  • A loop or a large Inline Map adds history events on each pass and can reach the 25,000-event quota.
  • To avoid the 25,000-event quota, use a Distributed Map. Each child execution has its own history.
  • To avoid the 25,000-event quota, continue the work in a new execution from a Task state or a Lambda function.

Exam signals

  • "Execution stuck in RUNNING because a worker crashed" → set TimeoutSeconds and HeartbeatSeconds. The default timeout is so long that the task waits for an answer that never comes.
  • "Long loop fails after many iterations" → 25,000-event history quota. Continue as a new execution or use a Distributed Map.
  • "Express executions fail after 5 minutes" → use a Standard workflow. You cannot raise the Express limit.

Explanation

Key facts

  • By default, ASL sets no useful timeout. The TimeoutSeconds default is 99,999,999 seconds. A task that never answers keeps the execution open until the execution limit.
  • Set TimeoutSeconds on each Task state. A task that runs longer fails with States.Timeout.
  • Set HeartbeatSeconds lower than TimeoutSeconds. The worker calls SendTaskHeartbeat regularly to show that it is still alive.
  • If no heartbeat arrives within HeartbeatSeconds, the task fails. AWS docs list both States.HeartbeatTimeout and States.Timeout for a missed heartbeat. Match both in a retrier or catcher.
  • Use a heartbeat for long callback tasks. A heartbeat failure tells you that the worker stopped, not that the job is slow. Example: a 2-hour job with HeartbeatSeconds 600 fails within 10 minutes after the worker crashes, not after 2 hours.
  • A state machine can have a top-level TimeoutSeconds for the whole execution. When the execution runs longer, it fails with States.Timeout. Use it to stop an execution that loops or waits too long.
  • An Express execution that runs longer than 5 minutes fails with States.Timeout.

Parallel, Inline Map, and Distributed Map

Remember

  • Each Parallel branch gets a copy of the input. All branches run at the same time.
  • A Parallel state output is an array with one element for each branch, in branch order.
  • An unhandled error in one branch fails the Parallel state and stops the other branches.
  • A running Lambda function continues after its Parallel state fails. Make the branch steps idempotent.
  • Inline Map is the default mode and runs up to 40 concurrent iterations.
  • Inline Map reads a JSON array from the state input (256 KiB limit) and works in Standard and Express.
  • Inline Map iterations add events to the parent history (25,000-event quota).
  • Distributed Map runs up to 10,000 parallel child executions. Each child execution has its own history.
  • Distributed Map reads a JSON array, or an S3 source through ItemReader. Example: a CSV file.
  • Distributed Map needs a Standard parent. Child executions are Standard or Express (ExecutionType).
  • Use Inline Map for a small array in the state input with 40 or fewer concurrent iterations.
  • Use Distributed Map for a large S3 dataset, more than 40 concurrent iterations, or more than 25,000 history events.
  • ItemsPath selects the array (default $).
  • ItemSelector builds the input for each item and replaces the old Parameters field.
  • ItemProcessor holds the Map steps and replaces the old Iterator field.
  • MaxConcurrency 0 (default) sets no limit. Inline Map still runs at most 40 iterations at the same time.
  • In Inline Map, one failed iteration fails the Map state.
  • A Retry on an Inline Map state runs all iterations again, also the iterations that succeeded.
  • To retry only the failed item, put the Retry on the Task inside ItemProcessor.
  • ItemBatcher sends a batch of small items to each Distributed Map child execution.
  • ResultWriter writes the Distributed Map child results to files in S3.
  • A Distributed Map without ResultWriter returns all results as one array, which must fit in 256 KiB.
  • A Map Run is the set of child executions that one Distributed Map state starts.
  • ToleratedFailurePercentage or ToleratedFailureCount lets some items fail. The default is 0.
  • A Map Run above its failure threshold fails with States.ExceedToleratedFailureThreshold.
  • A Distributed Map execution role needs states:StartExecution on its own state machine to start child executions.

Exam signals

  • "Process millions of records in a CSV file in S3 with high concurrency" → Distributed Map with ItemReader.
  • "Need more than 40 concurrent iterations" → Distributed Map. Inline Map stops at 40.
  • "Some bad records must not fail the whole job" → ToleratedFailurePercentage. The default threshold is 0, so one failed record fails the Map Run.
  • "Run three independent lookups at the same time" → Parallel state. Parallel runs a fixed set of different branches.
  • "Run the same steps for each item" → Map state, not Parallel.

Explanation

Parallel state

  • Each branch gets a copy of the input. All branches run at the same time.
  • The output is an array with one element for each branch, in branch order. Use $[0], $[1], and so on.
  • If one branch fails and the Parallel state does not handle the error, the Parallel state fails and stops the other branches.
  • A Lambda function that already runs continues to run after the Parallel state fails. Its side effects (for example a database write) can still happen, so make the branch steps idempotent.

Map modes

Choose Inline for a small array that is already in the state input and needs 40 or fewer iterations at the same time.

Choose Distributed for a large dataset in Amazon S3, for more than 40 concurrent iterations, or when the iterations would push the parent history past 25,000 events.

Map fields

  • ItemsPath selects the array (default $).
  • ItemSelector builds the input for each item. ItemSelector replaces the old Parameters field.
  • ItemProcessor holds the steps. It replaces the old Iterator field.
  • MaxConcurrency 0 (default) means no limit that you set. Inline mode still runs a maximum of 40 iterations at the same time.
  • Inline mode: one failed iteration fails the Map state. A Retry on the Map state runs all iterations again, also the iterations that succeeded. Make the item steps idempotent, or put the Retry on the Task inside ItemProcessor.
  • Distributed mode: ItemBatcher sends a batch of items to each child execution, so fewer child executions run. Use it when each item is small, for example one row of a CSV file.
  • Distributed mode: ResultWriter writes the child execution results (input, output, and status) to files in Amazon S3. Without it, the Map state returns all results as one array in its output, which must fit in 256 KiB.
  • A Map Run is the set of child executions that one Distributed Map state starts.
  • ToleratedFailurePercentage or ToleratedFailureCount lets some items fail. The default is 0, so one failed item fails the Map Run. Above the threshold, the Map Run fails with States.ExceedToleratedFailureThreshold.
  • The execution role needs states:StartExecution on the state machine to start Distributed Map child executions. The child executions run the same state machine, so the role must allow it to start itself. Without this permission, no child execution starts.

Service integration patterns and activities

Remember

  • Request Response is the default pattern. Step Functions calls the API and moves on after the HTTP response.
  • Run a Job (.sync) starts a job and waits until the job completes.
  • Wait for Callback (.waitForTaskToken) sends a task token and pauses until the token comes back.
  • Use Request Response when the next state does not need the work to finish. Example: a notification.
  • Use .sync when an AWS job (Glue, Batch, ECS) must complete before the next state.
  • Use .waitForTaskToken when a person or an outside system decides when the step is done.
  • A task token is a unique ID for one paused task. The receiver sends the token back.
  • .sync examples: Batch, ECS/Fargate, EKS, Glue, EMR, Athena, CodeBuild, SageMaker AI, and Step Functions.
  • .waitForTaskToken examples: Lambda, SQS, SNS, EventBridge, API Gateway, ECS, and Step Functions.
  • The DynamoDB optimized integration supports Request Response only.
  • Lambda does not support .sync, because Invoke already waits for the function to return.
  • Express workflows support Request Response only.
  • AWS SDK integrations (aws-sdk:<service>:<apiAction>) call over two hundred services without Lambda code.
  • AWS SDK integrations support Request Response and, in Standard, .waitForTaskToken. AWS SDK integrations do not support .sync.
  • AWS recommends an optimized integration when one exists. Use an AWS SDK integration for other services and actions.
  • The optimized Lambda Invoke converts the output from escaped JSON to a JSON object.
  • Put the token in the payload with "TaskToken.$": "$$.Task.Token". Step Functions does not add the token.
  • Without the token in the payload, the receiver cannot resume the task, and the execution waits until it times out.
  • The callback receiver calls SendTaskSuccess or SendTaskFailure with the token. SendTaskHeartbeat shows progress.
  • A callback task waits up to the one-year execution limit unless you set TimeoutSeconds or HeartbeatSeconds.
  • With lambda:invoke.waitForTaskToken, the heartbeat timer starts after the function returns.
  • An activity is a worker that you host anywhere: EC2, ECS, on premises, or a mobile device.
  • An activity worker polls with GetActivityTask, does the work, and calls SendTaskSuccess or SendTaskFailure.
  • Activities work in Standard workflows only.
  • An activity worker needs only outbound HTTPS, so it works behind a firewall that blocks inbound traffic.

Exam signals

  • "Wait until the Glue job or ECS task finishes, no polling code" → .sync.
  • "Pause for human approval or a third-party system" → .waitForTaskToken and SendTaskSuccess.
  • "Write to DynamoDB from the workflow without a Lambda function" → dynamodb:putItem integration. Step Functions calls the DynamoDB API directly from the Task state.
  • "Worker runs on premises and polls for work" → activity.

IAM, encryption, and logging data

Remember

  • The execution role gives the state machine its permissions. Grant only the actions and resources that the definition uses.
  • The caller needs its own permission, for example states:StartExecution, separate from the execution role.
  • For a Lambda version or alias, the policy resource must include the qualifier or :*.
  • An unqualified Lambda function ARN in the policy gives Access Denied for a qualified FunctionName.
  • .sync and .waitForTaskToken integrations need additional IAM permissions.
  • A .sync task needs a status action such as glue:GetJobRun, or EventBridge rule actions such as events:PutRule.
  • Without the .sync status permissions, the task can get stuck or see the job completion late.
  • For a cross-account task, set Credentials with a RoleArn in the other account.
  • A cross-account task with Credentials does not need a resource-based policy in the other account.
  • Task tokens work only from principals in the same AWS account.
  • The caller of SendTaskSuccess needs the states:SendTaskSuccess IAM permission.
  • Executions inherit the state machine tags, so an aws:ResourceTag condition also controls access to executions.
  • Step Functions always encrypts data at rest with an AWS owned key. You cannot turn this encryption off.
  • A symmetric customer managed KMS key on a state machine or activity encrypts the definition and execution history.
  • Use a customer managed key when you must control, rotate, disable, or audit the key yourself.
  • Standard and asynchronous Express need kms:Decrypt and kms:GenerateDataKey in the execution role.
  • Synchronous Express needs kms:Decrypt in the execution role.
  • The data key reuse period is 60 to 900 seconds. The default is 300 seconds.
  • A shorter data key reuse period means more KMS calls.
  • A disabled or deleted key makes running executions fail and stops new executions from starting.
  • Log level ALL logs every event. OFF logs nothing.
  • Log level ERROR logs only error events, such as a failed task or a failed execution.
  • Log level FATAL logs only the end of an execution that failed, timed out, or was aborted.
  • includeExecutionData controls whether logs contain input, output, and variables. Set it to false for sensitive data.
  • Do not put secrets in the execution input, because input shows in history and logs.
  • Store a secret in AWS Secrets Manager and read it in the step that needs it.

Exam signals

  • "Task fails with States.Permissions or Access Denied" → fix the execution role, not the caller. Step Functions runs each task with the execution role, not with the permissions of the caller who started the execution.
  • "Encrypt execution history with a key we control and audit" → customer managed KMS key on the state machine.
  • "Logs must not contain customer data, but must show failures" → level ERROR and includeExecutionData false.
  • "Call a resource in another account" → Credentials field with a cross-account role.

Explanation

IAM

  • The execution role gives the state machine its permissions. Grant only the actions and resources that the definition uses.
  • The caller needs its own permission, for example states:StartExecution. This is separate from the execution role.
  • For Lambda with a version or alias in FunctionName, the policy resource must include the qualifier or :*. An unqualified function ARN gives Access Denied.
  • .sync and .waitForTaskToken integrations need additional IAM permissions.
  • For .sync, Step Functions must check the job status. It polls with a Describe or Get action (for example glue:GetJobRun) or uses a managed EventBridge rule (events:PutTargets, events:PutRule, events:DescribeRule). Without these permissions, the task can get stuck or see the job completion late.
  • Cross-account task: set Credentials with a RoleArn in the other account. The execution role assumes that role and calls the resource with temporary credentials. The other account does not need a resource-based policy on the resource.
  • Task tokens work only from principals in the same AWS account. The caller of SendTaskSuccess needs the states:SendTaskSuccess IAM permission.
  • Executions inherit the tags of the state machine for tag-based authorization. An IAM policy with an aws:ResourceTag condition on the state machine then also controls access to its executions, for example DescribeExecution.

Encryption at rest

  • Step Functions always encrypts data at rest with an AWS owned key. You cannot turn this off.
  • You can add a symmetric customer managed KMS key on a state machine (Standard or Express) or an activity. The key encrypts the definition and execution history.
  • Choose a customer managed key when you must control, rotate, disable, or audit the key yourself. You cannot do these things with an AWS owned key.
  • The execution role needs kms:Decrypt and kms:GenerateDataKey for Standard and asynchronous Express. Synchronous Express needs kms:Decrypt.
  • The data key reuse period is 60 to 900 seconds. The default is 300 seconds. It is the maximum time that Step Functions reuses one data key.
  • When the period ends, Step Functions calls GenerateDataKey again, so a shorter period means more KMS calls.
  • If you disable or delete the key, running executions fail and new executions cannot start.

Logging data

  • Log levels: ALL logs every event.
  • ERROR logs only error events, such as a failed task or a failed execution.
  • FATAL logs only the end of an execution that failed, timed out, or was aborted.
  • OFF logs nothing.
  • includeExecutionData controls whether logs contain input, output, and variables. Set it to false for sensitive data. The logs then still show which step failed, but not the data.
  • Do not put secrets in the execution input. Input shows in history and logs. Store the secret in AWS Secrets Manager and read it in the step that needs it.

Logs, tracing, events, and redrive

Remember

  • For Standard, the console graph view and GetExecutionHistory show every event for 90 days.
  • Express keeps no history in Step Functions. Configure CloudWatch Logs to see Express executions.
  • The console turns on logging for a new Express workflow. The API, CLI, and CloudFormation do not.
  • CloudWatch Logs delivery is best effort. AWS does not guarantee that every log entry arrives, or when.
  • For a guaranteed record, write to a data store such as DynamoDB from a workflow step, or use Standard.
  • Use a log group name that starts with /aws/vendedlogs/states.
  • The CloudWatch Logs resource policy has a 5,120-character limit. Many log groups can fill the policy.
  • When the resource policy is near its limit, CloudWatch Logs automatically allows log groups whose names start with /aws/vendedlogs/.
  • A full resource policy blocks logging to a new log group whose name does not start with /aws/vendedlogs/.
  • To use X-Ray, turn on tracing on the state machine.
  • X-Ray tracing needs xray:PutTraceSegments, xray:PutTelemetryRecords, xray:GetSamplingRules, and xray:GetSamplingTargets in the execution role.
  • X-Ray does not trace Distributed Map child executions. Use the Map Run details or CloudWatch Logs.
  • Only Standard workflows send Execution Status Change events to the EventBridge default bus.
  • Execution Status Change events have the source aws.states. Statuses include FAILED, TIMED_OUT, and ABORTED.
  • To alert on failed executions without a definition change, use an EventBridge rule on Execution Status Change events.
  • The ExecutionThrottled metric counts state entries and retries throttled at the account state transition quota.
  • RedriveExecution restarts a failed, aborted, or timed-out Standard execution from the failed step.
  • A redrive does not run the successful steps again.
  • You can redrive for 14 days after the execution closes.
  • Redrive uses the same definition and input. To use a changed definition, start a new execution.
  • Redrive resets retry counts to 0, so each retrier can again make all its MaxAttempts.
  • Redrives count as state transitions.

Exam signals

  • "Cannot see past Express executions" → enable CloudWatch Logs on the state machine. Step Functions keeps no history for Express, so the logs are the only record.
  • "Notify the team when an execution fails or times out" → EventBridge rule on Execution Status Change. Standard workflows send these events automatically.
  • "Resume a failed execution without running the completed steps again" → redrive. A new StartExecution starts again at the first step.
  • "Find which step adds latency" → X-Ray tracing. X-Ray shows the time of each step and each downstream call.

Explanation

Key facts

  • Standard: the console graph view and GetExecutionHistory show every event for 90 days.
  • Express: no history in Step Functions. Configure CloudWatch Logs.
  • The console turns on logging for a new Express workflow. The API, CLI, and CloudFormation do not.
  • CloudWatch Logs delivery is best effort: AWS does not guarantee that every log entry arrives, or when. For a guaranteed record, write to a data store such as DynamoDB from a workflow step, or use Standard.
  • Use a log group name that starts with /aws/vendedlogs/states.
  • When you turn on logging, Step Functions adds the log group to the CloudWatch Logs resource policy. That policy has a 5,120-character limit, and many log groups can fill it. Then the state machine cannot send logs to a new log group.
  • When the policy comes near the limit, CloudWatch Logs automatically allows logging to log groups whose names start with /aws/vendedlogs/.
  • X-Ray: turn on tracing on the state machine. The execution role needs xray:PutTraceSegments, xray:PutTelemetryRecords, xray:GetSamplingRules, and xray:GetSamplingTargets.
  • X-Ray does not trace Distributed Map child executions. Steps inside the items do not appear in the trace. Use the Map Run details or CloudWatch Logs to find a slow item.
  • Only Standard workflows send Execution Status Change events to the EventBridge default bus. The source is aws.states. Statuses include FAILED, TIMED_OUT, and ABORTED.
  • Use an EventBridge rule on these events to send alerts without a change to the definition.
  • The ExecutionThrottled CloudWatch metric counts state entries and retries that Step Functions throttled because the account reached its state transition quota. Throttled steps start later, so executions run slower.

  • RedriveExecution restarts a failed, aborted, or timed-out Standard execution from the failed step. Successful steps do not run again.
  • You can redrive for 14 days after the execution closes.
  • Redrive uses the same definition and input. If you change the definition, start a new execution.
  • Redrive resets retry counts to 0, so each retrier can again make all its MaxAttempts.
  • Redrives count as state transitions.

Versions, aliases, testing, and AWS SAM deployment

Remember

  • A version is a numbered, immutable snapshot of a state machine. A version ARN ends with :<number>.
  • Publish a version with PublishStateMachineVersion, or with publish true on create or update.
  • An alias points to one or two versions. With two versions, the alias splits traffic by weight.
  • Alias weights total 100 percent. Example: 90 percent to version 3 and 10 percent to version 4.
  • An unqualified state machine ARN runs the most recent revision, also when you did not publish it as a version.
  • Use the alias ARN in callers so that a release or a rollback does not need a code change.
  • CANARY shifts a small percentage first and shifts the rest after the interval if no alarm goes into the ALARM state.
  • LINEAR shifts equal increments with equal minutes between them.
  • ALL_AT_ONCE shifts 100 percent at once and monitors the alarms.
  • CloudFormation rolls back a gradual deployment if a listed CloudWatch alarm goes into the ALARM state.
  • In AWS SAM, use Definition for an inline definition or DefinitionUri for a file.
  • DefinitionSubstitutions replaces ${Name} placeholders in the ASL file. Example: !GetAtt MyFunction.Arn.
  • CloudFormation does not process !GetAtt or !Ref inside a separate ASL file.
  • The SAM Type is STANDARD (default) or EXPRESS.
  • SAM Policies adds policies to the generated execution role.
  • SAM Role uses your own role, and SAM then ignores Policies.
  • SAM Events starts the state machine from sources such as an API or a schedule.
  • SAM AutoPublishAlias publishes a version and updates the alias. DeploymentPreference sets a gradual deployment.
  • TestState runs one state definition without a create or update of a state machine.
  • Inspection level INFO (default) shows the output or the error.
  • Inspection level DEBUG also shows each data processing step, such as afterInputPath and afterResultPath.
  • Inspection level TRACE shows the raw HTTP request and response, for HTTP Tasks only.
  • TestState status RETRIABLE means that the error matches a retrier.
  • TestState status CAUGHT_ERROR means that a catcher handles the error. nextState names the fallback state.
  • The TestState caller needs states:TestState. Without a mock, the caller also needs iam:PassRole.
  • With the AWS CLI or SDK, TestState can mock a service result or an error. With a mock, the role is optional.
  • Map, Parallel, activity, .sync, and .waitForTaskToken states need a mock in TestState.

Exam signals

  • "Send 10 percent of executions to the new workflow, roll back on an alarm" → alias with DeploymentPreference type CANARY and Alarms.
  • "ASL file needs ARNs of resources in the same template" → DefinitionSubstitutions. Intrinsic functions do not work inside the ASL file, so SAM fills the placeholders at deployment time.
  • "Callers must not change the ARN when we release" → alias ARN.
  • "Test one Task state and see how InputPath and ResultPath change the data, without deploying" → TestState with DEBUG.

Explanation

Versions and aliases

  • A version is a numbered, immutable snapshot of the state machine. Its ARN ends with :<number>.
  • Publish with PublishStateMachineVersion, or set publish to true on CreateStateMachine or UpdateStateMachine.
  • An alias points to one or two versions. With two versions, it splits traffic by weight.
  • The weights total 100 percent. Example: 90 percent to version 3 and 10 percent to version 4 tests version 4 on a small part of the traffic.
  • An execution started with the unqualified state machine ARN (no :<number> or alias name) uses the most recent revision. A revision is the state machine as it is after the last update (definition, role, logging, and tracing), also when you did not publish it as a version.
  • Callers that use the alias ARN do not change when you point the alias to a new version. Use the alias ARN in callers so that a release or a rollback does not need a code change.

AWS SAM (AWS::Serverless::StateMachine)

  • Definition (inline) or DefinitionUri (a file, for example statemachine/order.asl.json).
  • DefinitionSubstitutions replaces ${Name} placeholders in the definition with values such as !GetAtt MyFunction.Arn. You need it because CloudFormation does not process !GetAtt or !Ref inside a separate ASL file.
  • Type: STANDARD (default) or EXPRESS.
  • Policies adds SAM policy templates or IAM policies to the generated execution role. Role uses your own role, and SAM then ignores Policies.
  • Events starts the state machine from sources such as an API or a schedule.
  • Logging and Tracing configure CloudWatch Logs and X-Ray.
  • AutoPublishAlias publishes a version and updates the alias. DeploymentPreference sets a gradual deployment for that alias.

Test one state with the TestState API

  • TestState runs one state definition. You do not create or update a state machine.
  • You can also send a full definition and name the state to test with stateName.
  • Inspection levels: INFO (default) shows the output or the error. DEBUG also shows each data processing step (afterInputPath, afterParameters, afterResultSelector, afterResultPath). TRACE shows the raw HTTP request and response, for HTTP Tasks only.
  • The response gives status and nextState. SUCCEEDED and FAILED are clear.
  • RETRIABLE means that the error matches a retrier. CAUGHT_ERROR means that a catcher handles the error, and nextState names the fallback state.
  • The caller needs states:TestState. Without a mock, the caller also needs iam:PassRole for the execution role, and the role needs the permissions that the state uses.
  • With the AWS CLI or SDK, you can mock a service result or an error. Then the role is optional. Map, Parallel, activity, .sync, and .waitForTaskToken states need a mock.
