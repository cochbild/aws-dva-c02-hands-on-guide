Orchestration, sagas, and starting executions

Key facts

  • AWS Step Functions runs a state machine. You write the state machine in the Amazon States Language (ASL), a JSON format.
  • One run of a state machine is an execution. Each execution gets JSON input and makes JSON output.
  • Orchestration: one central workflow decides which step runs next. Step Functions is the orchestration service.
  • Choreography: services react to events from each other (Amazon SNS, Amazon SQS, Amazon EventBridge). There is no central controller.
  • Step Functions keeps the workflow state, the retries, and the error paths out of your function code.
  • The state machine uses an IAM execution role to call other services.

Saga pattern (compensating transactions)

  • A saga is a sequence of local transactions in different services. There is no single database transaction across the services.
  • If a later step fails, the workflow runs compensating steps that undo the earlier steps, usually in reverse order.
  • In Step Functions, a Catch on each step sends the failure to its compensating step. For example, a failed payment goes to "cancel car rental", then "cancel flight", then a Fail state.
  • Make each step and each compensating step idempotent. The saga gives eventual consistency, not isolation.

Ways to start an execution

CallerHow
AWS SDK or AWS CLIStartExecution (Standard and Express). StartSyncExecution (Express only) waits and returns the result.
Amazon API GatewayHTTP API integration subtypes StepFunctions-StartExecution, StepFunctions-StartSyncExecution, and StepFunctions-StopExecution. A REST API uses an AWS service integration. API Gateway needs an IAM role that allows the action.
Amazon EventBridgeA rule or a schedule with the state machine as the target. EventBridge needs an IAM role that allows states:StartExecution.
Another state machineA Task state with arn:aws:states:::states:startExecution (optionally .sync). This is a nested workflow.
  • StartExecution returns an executionArn at once. The caller does not get the workflow result.
  • StartSyncExecution on a Standard state machine fails with StateMachineTypeNotSupported.

Exam signals

  • "Coordinate several Lambda functions with branching, retries, and a visual history" → Step Functions.
  • "Fan out one event to many independent subscribers" → Amazon SNS or EventBridge (choreography), not Step Functions.
  • "HTTP client must get the workflow result in the same request" → API Gateway with StartSyncExecution on an Express workflow.
  • "Start the workflow when an object lands in S3" → EventBridge rule with the state machine as the target.
  • "Undo the flight and hotel bookings when the payment fails" → saga pattern with Catch and compensating steps.

State types and Choice rules

State types

TypePurposeNotes
TaskDo one unit of work: a Lambda function, an AWS service API, an activity, or an HTTPS API.Supports Retry and Catch.
ChoiceBranch on the input.No End field. Next only inside each rule. No Retry or Catch.
WaitPause for Seconds, SecondsPath, Timestamp, or TimestampPath.No compute runs during the wait.
ParallelRun fixed branches at the same time.Supports Retry and Catch.
MapRun the same steps for each item in a dataset.Supports Retry and Catch.
PassPass or reshape data. Inject a fixed value with Result.Cannot run code.
SucceedEnd the execution with success.Terminal. No Next.
FailEnd the execution with failure. Set Error and Cause.Terminal. No Next.

Choice rules

  • Step Functions examines the rules in the order of the Choices array. The first match wins.
  • Use Default for input that matches no rule. With no match and no Default, the execution fails with States.NoChoiceMatched.
  • Operators have types: StringEquals, NumericGreaterThanEquals, BooleanEquals, TimestampLessThan, and more. A numeric operator does not match a string value.
  • Add Path to an operator to compare with another input value, for example NumericLessThanPath.
  • IsPresent, IsNull, IsNumeric, and IsString test a field. And, Or, and Not combine rules.
  • StringMatches supports the * wildcard only.

Exam signals

  • "Execution fails when the input matches no branch" → add Default to the Choice state.
  • "Pause until a date in the input, up to 30 days" → Wait state with TimestampPath in a Standard workflow.
  • "A Fail state with a Next field" → invalid ASL. Succeed and Fail are terminal.
  • "Large amounts go to the wrong branch" → check the rule order. The first matching rule wins.

Input and output processing, JSONata, and variables

JSONPath fields, in order

OrderFieldWhat it doesDefault
1InputPathSelects part of the state input.$ (all input)
2ParametersBuilds the input for the task. A key that ends in .$ takes a path or an intrinsic function.None
3ResultSelectorBuilds a new object from the task result.None
4ResultPathPuts the result into the state input.$ (result replaces the input)
5OutputPathSelects part of the output for the next state.$

ResultPath values

  • "$" or no ResultPath: the result replaces the whole input.
  • "$.validation": the output is the input plus the result under validation.
  • null: Step Functions discards the result. The output is the original input.

Key facts

  • Without .$, a value such as "$.order.id" is a literal string, not a path.
  • $$ is the Context object: $$.Execution.Input, $$.Task.Token, $$.Map.Item.Value, $$.Map.Item.Index.
  • The optimized lambda:invoke integration returns metadata. The function output is in Payload. Use ResultSelector or OutputPath with $.Payload.
  • Intrinsic functions work in JSONPath states only: States.Format, States.StringToJson, States.JsonToString, States.Array, States.ArrayPartition, States.MathAdd, States.UUID, States.Hash, States.Base64Encode, and others.

JSONata and variables

  • Step Functions has two query languages: JSONPath and JSONata. Set QueryLanguage on the state machine or on one state. Without it, the state machine uses JSONPath.
  • AWS recommends JSONata for new state machines.
  • JSONata states use Arguments (in place of Parameters) and Output (in place of the path fields). An expression is inside {% %}.
  • In JSONata, $states.input is the state input, $states.result is the task result, $states.errorOutput is the error in a Catch, and $states.context is the Context object.
  • Variables: the Assign field stores a value. A later state reads it as $name. State output goes only to the next state, but a variable is available to all later states.
  • Variables work in JSONPath and JSONata states. In JSONPath, you cannot use a variable in ResultPath.
  • A new value is available from the next state. Parallel branches and Map iterations can read outer variables but have their own scope. Distributed Map cannot read outer variables.
  • Limits: 256 KiB for one variable, 256 KiB for all variables in one Assign field, 10 MiB for all variables in one execution.

Numbers to memorize

ItemValue
Input or output of a task, state, or execution256 KiB (hard quota). Larger data fails with States.DataLimitExceeded.

Exam signals

  • "Keep the original input and add the Lambda result" → ResultPath: "$.result".
  • "Next state sees StatusCode and Payload, not the function output" → select $.Payload with ResultSelector or OutputPath.
  • "Data between states is larger than 256 KiB" → store it in Amazon S3 and pass the bucket and key.
  • "Generate a unique ID without a Lambda function" → States.UUID().
  • "Step 5 needs a value from step 1, and steps 2 to 4 do not need it" → store it in a variable with Assign.

Standard and Express workflows

Comparison

ItemStandardExpress
Maximum duration1 year5 minutes
Execution semanticsExactly-once. A step runs again only if you configure Retry.Asynchronous: at-least-once. Synchronous: at-most-once.
Pricing basisNumber of state transitionsNumber of executions, duration, and memory
Execution historyKept by Step Functions for 90 days after the execution closes. DescribeExecution and GetExecutionHistory work.Not kept by Step Functions. Enable CloudWatch Logs to see it.
Integration patternsRequest Response, .sync, .waitForTaskTokenRequest Response only
Activities and Distributed MapSupportedNot supported
RedriveSupportedNot supported
Start APIStartExecutionStartExecution (asynchronous) or StartSyncExecution (synchronous)

Key facts

  • Asynchronous Express (StartExecution, an event, or a nested workflow): the caller gets confirmation that the workflow started. It does not wait. Read the result from CloudWatch Logs.
  • Synchronous Express (StartSyncExecution, from API Gateway, Lambda, or the SDK): the caller waits and gets the result. A synchronous request from the console expires after 60 seconds. Use the SDK or CLI for up to 5 minutes.
  • You cannot change the workflow type after you create the state machine. Create a new state machine.
  • Standard is for non-idempotent actions, such as payments. Express is for idempotent, high-volume event processing.
  • Standard: a StartExecution call with the same name and the same input as a running execution returns the same response. It does not start a second execution. A call with the same name and a different input, or after that execution closed, fails with ExecutionAlreadyExists.
  • Express: Step Functions does not manage idempotency. The same name can start concurrent executions.
  • A Standard parent can call an Express child for the high-volume idempotent part. This can reduce cost.

Exam signals

  • "High volume, each run takes less than a minute, idempotent, lowest cost" → Express.
  • "Human approval that can take days" or "run longer than 5 minutes" → Standard.
  • "Step must never run twice, for example charging a card" → Standard (exactly-once).
  • "Client retries StartExecution and must not create a duplicate run" → Standard with a unique business ID as the execution name.

References: Choosing workflow type (semantics and idempotency), Best practices (cost). Lab: Lab 6.2 Standard vs Express.

Error handling with Retry and Catch

Key facts

  • Task, Parallel, and Map states support Retry and Catch.
  • An unhandled error fails the whole execution.
  • Retriers run first. Step Functions uses a catcher only after the matching retrier stops, or when no retrier matches.
  • Step Functions scans retriers and catchers in array order. Each retrier counts its attempts separately.
  • Each retry counts as a state transition. Standard workflows bill retries.
  • Lambda errors have the name Lambda.<ErrorName>. An error from your function code has the error type that the function returns.

Retrier fields

FieldDefaultNotes
ErrorEqualsRequiredError names to match
IntervalSeconds1Wait before the first retry
MaxAttempts30 means never retry
BackoffRate2.0Multiplier for each later wait
MaxDelaySecondsNo limitUpper limit for one wait
JitterStrategyNONEFULL makes each wait random between 0 and the calculated wait

Predefined error names

NameMeaning
States.ALLMatches any error name, except States.Runtime and States.DataLimitExceeded. Must be alone in ErrorEquals and in the last retrier or catcher.
States.TaskFailedMatches any error except States.Timeout.
States.TimeoutTask ran longer than TimeoutSeconds, or missed HeartbeatSeconds. Also an execution that ran longer than its limit.
States.HeartbeatTimeoutTask did not send a heartbeat within HeartbeatSeconds.
States.PermissionsThe execution role does not have the permission to run the task.
States.DataLimitExceededPayload is larger than 256 KiB. States.ALL does not catch it. Name it explicitly to catch it.
States.RuntimeFor example, a path applied to a null payload. Not retriable. States.ALL does not catch it.
States.ExceedToleratedFailureThresholdA Distributed Map had more failed items than the threshold.

Catch and ResultPath

  • A catcher has ErrorEquals, Next, and an optional ResultPath.
  • With no ResultPath, the error output (Error and Cause) replaces the input.
  • Use "ResultPath": "$.error" to keep the input and add the error.

Transient Lambda errors

AWS recommends a retrier for Lambda.ServiceException, Lambda.AWSLambdaException, Lambda.SdkClientException, and Lambda.ClientExecutionTimeoutException. The documented example uses IntervalSeconds 2, MaxAttempts 6, and BackoffRate 2. Throttling shows as Lambda.TooManyRequestsException.

Exam signals

  • "Retry with exponential backoff and jitter" → Retry with BackoffRate and JitterStrategy: FULL.
  • "Fallback state lost the original input" → add ResultPath to the catcher.
  • "Retry everything except timeouts" → retrier for States.Timeout with MaxAttempts: 0, then States.ALL.
  • "Catch States.ALL did not catch the failure" → States.Runtime or States.DataLimitExceeded.

References: Handling errors (retrier defaults, error names), Best practices (Lambda service exceptions). Lab: Lab 6.3 Error handling.

Timeouts, heartbeats, and quotas

Key facts

  • By default, ASL sets no useful timeout. The TimeoutSeconds default is 99,999,999 seconds. A task that never answers keeps the execution open until the execution limit.
  • Set TimeoutSeconds on each Task state. A task that runs longer fails with States.Timeout.
  • Set HeartbeatSeconds lower than TimeoutSeconds. The worker calls SendTaskHeartbeat to show progress.
  • Use a heartbeat for long callback tasks. A heartbeat failure tells you that the worker stopped, not that the job is slow.
  • A state machine can have a top-level TimeoutSeconds for the whole execution.
  • An Express execution that runs longer than 5 minutes fails with States.Timeout.

Numbers to memorize

QuotaValue
Maximum execution timeStandard 1 year. Express 5 minutes. Hard quotas.
Execution history size (Standard)25,000 events. The execution fails at this quota. Hard quota.
Execution history retention (Standard)90 days after the execution closes
Payload size256 KiB
State machine definition size1 MB
Execution name80 characters maximum. Unique in the account and Region.
Redrive period14 days after the execution closes

Avoid the 25,000-event quota

  • Use a Distributed Map. Each child execution has its own history.
  • Start a new execution from a Task state to continue the work.
  • Use a Lambda function that starts a new execution of the state machine.

Exam signals

  • "Execution stuck in RUNNING because a worker crashed" → set TimeoutSeconds and HeartbeatSeconds.
  • "Long loop fails after many iterations" → 25,000-event history quota. Continue as a new execution or use a Distributed Map.
  • "Express executions fail after 5 minutes" → use a Standard workflow. You cannot raise the Express limit.

References: Step Functions quotas, Task state (TimeoutSeconds and HeartbeatSeconds defaults), Best practices (timeouts, history quota). Lab: Lab 6.3 Error handling.

Parallel, Inline Map, and Distributed Map

Parallel state

  • Each branch gets a copy of the input. All branches run at the same time.
  • The output is an array with one element for each branch, in branch order. Use $[0], $[1], and so on.
  • If one branch fails and the Parallel state does not handle the error, the Parallel state fails and stops the other branches.
  • A Lambda function that already runs continues to run after the Parallel state fails.

Map modes

ItemInline (default)Distributed
ConcurrencyUp to 40 concurrent iterationsUp to 10,000 parallel child executions
InputA JSON array in the state input (256 KiB limit)A JSON array, or an Amazon S3 source through ItemReader (for example a CSV or JSON file, or a list of objects)
HistoryIn the parent execution history (25,000-event quota)Each child execution has its own history
Workflow typeStandard and ExpressStandard parent only. Child executions are Standard or Express (ExecutionType).

Map fields

  • ItemsPath selects the array (default $). ItemSelector builds the input for each item. ItemSelector replaces the old Parameters field.
  • ItemProcessor holds the steps. It replaces the old Iterator field.
  • MaxConcurrency 0 (default) means no limit that you set. Inline mode still runs a maximum of 40 iterations at the same time.
  • Inline mode: one failed iteration fails the Map state. A Retry on the Map state runs all iterations again.
  • Distributed mode: ItemBatcher sends items in batches. ResultWriter writes results to Amazon S3.
  • ToleratedFailurePercentage or ToleratedFailureCount lets some items fail. The default is 0. Above the threshold, the Map Run fails with States.ExceedToleratedFailureThreshold.
  • The execution role needs states:StartExecution on the state machine to start Distributed Map child executions.

Exam signals

  • "Process millions of records in a CSV file in S3 with high concurrency" → Distributed Map with ItemReader.
  • "Need more than 40 concurrent iterations" → Distributed Map.
  • "Some bad records must not fail the whole job" → ToleratedFailurePercentage.
  • "Run three independent lookups at the same time" → Parallel state.

References: Parallel state, Inline Map (40 iterations), Distributed Map (10,000 child executions). Lab: Lab 6.4 Parallel and Map.

Service integration patterns and activities

Three patterns

PatternResource exampleBehavior
Request Response (default)arn:aws:states:::sns:publishStep Functions calls the API and moves on after the HTTP response. It does not wait for a job.
Run a Job (.sync)arn:aws:states:::glue:startJobRun.syncStep Functions starts the job and waits until the job completes.
Wait for Callback (.waitForTaskToken)arn:aws:states:::sqs:sendMessage.waitForTaskTokenStep Functions sends a task token and pauses until SendTaskSuccess or SendTaskFailure returns the token.

Which services support which pattern (optimized integrations, examples)

PatternExamples
.syncAWS Batch, Amazon ECS/Fargate, Amazon EKS, AWS Glue, Amazon EMR, Amazon Athena, AWS CodeBuild, Amazon SageMaker AI, Step Functions (startExecution.sync)
.waitForTaskTokenAWS Lambda, Amazon SQS, Amazon SNS, Amazon EventBridge, Amazon API Gateway, Amazon ECS, Step Functions
NeitherAmazon DynamoDB (Request Response only). Lambda does not support .sync.
  • Express workflows support Request Response only.
  • AWS SDK integrations (arn:aws:states:::aws-sdk:<service>:<apiAction>) call over two hundred services without Lambda code. They support Request Response and, in Standard workflows, .waitForTaskToken. They do not support .sync.
  • Optimized integrations, for example arn:aws:states:::dynamodb:putItem, have special handling for some services.

Callback details

  • Put the token in the payload with "TaskToken.$": "$$.Task.Token". Step Functions does not add the token for you.
  • The receiver calls SendTaskSuccess or SendTaskFailure with the token. SendTaskHeartbeat shows progress.
  • A callback task waits until the execution reaches its one-year limit, unless you set TimeoutSeconds or HeartbeatSeconds.
  • With lambda:invoke.waitForTaskToken, the heartbeat timer starts after the function returns.

Activities

  • An activity is a worker that you host anywhere: Amazon EC2, Amazon ECS, on premises, or a mobile device.
  • The worker polls with GetActivityTask, does the work, and calls SendTaskSuccess or SendTaskFailure.
  • Activities work in Standard workflows only. The worker needs only outbound HTTPS connections.

Exam signals

  • "Wait until the Glue job or ECS task finishes, no polling code" → .sync.
  • "Pause for human approval or a third-party system" → .waitForTaskToken and SendTaskSuccess.
  • "Write to DynamoDB from the workflow without a Lambda function" → dynamodb:putItem integration.
  • "Worker runs on premises and polls for work" → activity.

References: Service integration patterns (support table), Lambda integration, Activities. Lab: Lab 6.5 Integration patterns.

IAM, encryption, and logging data

IAM

  • The execution role gives the state machine its permissions. Grant only the actions and resources that the definition uses.
  • The caller needs its own permission, for example states:StartExecution. This is separate from the execution role.
  • For Lambda with a version or alias in FunctionName, the policy resource must include the qualifier or :*. An unqualified function ARN gives Access Denied.
  • .sync and .waitForTaskToken integrations need additional IAM permissions.
  • Cross-account task: set Credentials with a RoleArn in the other account. The execution role assumes that role.
  • Task tokens work only from principals in the same AWS account. The caller of SendTaskSuccess needs that IAM permission.
  • Executions inherit the tags of the state machine for tag-based authorization.

Encryption at rest

  • Step Functions always encrypts data at rest with an AWS owned key. You cannot turn this off.
  • You can add a symmetric customer managed KMS key on a state machine (Standard or Express) or an activity. The key encrypts the definition and execution history.
  • The execution role needs kms:Decrypt and kms:GenerateDataKey for Standard and asynchronous Express. Synchronous Express needs kms:Decrypt.
  • The data key reuse period is 60 to 900 seconds. The default is 300 seconds.
  • If you disable or delete the key, running executions fail and new executions cannot start.

Logging data

  • Log levels: ALL, ERROR, FATAL, OFF.
  • includeExecutionData controls whether logs contain input, output, and variables. Set it to false for sensitive data.
  • Do not put secrets in the execution input. Input shows in history and logs.

Exam signals

  • "Task fails with States.Permissions or Access Denied" → fix the execution role, not the caller.
  • "Encrypt execution history with a key we control and audit" → customer managed KMS key on the state machine.
  • "Logs must not contain customer data, but must show failures" → level ERROR and includeExecutionData false.
  • "Call a resource in another account" → Credentials field with a cross-account role.

References: Encryption at rest, Task state (Credentials), Lambda integration (qualified ARNs), CloudWatch Logs. Lab: Lab 6.5 Integration patterns.

Logs, tracing, events, and redrive

Key facts

  • Standard: the console graph view and GetExecutionHistory show every event for 90 days.
  • Express: no history in Step Functions. Configure CloudWatch Logs. The console turns on logging for a new Express workflow. The API, CLI, and CloudFormation do not.
  • CloudWatch Logs delivery is best effort. For a guaranteed record, write to a data store or use Standard.
  • Use a log group name that starts with /aws/vendedlogs/states. This avoids the 5,120-character CloudWatch Logs resource policy limit.
  • X-Ray: turn on tracing on the state machine. The execution role needs xray:PutTraceSegments, xray:PutTelemetryRecords, xray:GetSamplingRules, and xray:GetSamplingTargets.
  • X-Ray does not trace Distributed Map child executions.
  • Only Standard workflows send Execution Status Change events to the EventBridge default bus. The source is aws.states. Statuses include FAILED, TIMED_OUT, and ABORTED.
  • The ExecutionThrottled CloudWatch metric shows state transition throttling.

Redrive

  • RedriveExecution restarts a failed, aborted, or timed-out Standard execution from the failed step. Successful steps do not run again.
  • You can redrive for 14 days after the execution closes.
  • Redrive uses the same definition and input. If you change the definition, start a new execution.
  • Redrive resets retry counts. Redrives count as state transitions.

Exam signals

  • "Cannot see past Express executions" → enable CloudWatch Logs on the state machine.
  • "Notify the team when an execution fails or times out" → EventBridge rule on Execution Status Change.
  • "Resume a failed execution without running the completed steps again" → redrive.
  • "Find which step adds latency" → X-Ray tracing.

References: CloudWatch Logs, X-Ray tracing, EventBridge events, Redrive (14 days). Lab: Lab 6.2 Standard vs Express.

Versions, aliases, testing, and AWS SAM deployment

Versions and aliases

  • A version is a numbered, immutable snapshot of the state machine. Its ARN ends with :<number>.
  • Publish with PublishStateMachineVersion, or set publish to true on CreateStateMachine or UpdateStateMachine.
  • An alias points to one or two versions. With two versions, it splits traffic by weight. The weights total 100 percent.
  • An execution started with the unqualified state machine ARN uses the most recent revision.
  • Callers that use the alias ARN do not change when you point the alias to a new version.

Gradual deployment (AWS::StepFunctions::StateMachineAlias DeploymentPreference)

TypeBehavior
CANARYShifts a small percentage first. Shifts the rest after the interval if no alarm goes into the ALARM state.
LINEARShifts equal increments with equal minutes between them.
ALL_AT_ONCEShifts 100 percent at once and monitors the alarms.

CloudFormation rolls back if a listed CloudWatch alarm goes into the ALARM state.

AWS SAM (AWS::Serverless::StateMachine)

  • Definition (inline) or DefinitionUri (a file, for example statemachine/order.asl.json).
  • DefinitionSubstitutions replaces ${Name} placeholders in the definition with values such as !GetAtt MyFunction.Arn.
  • Type: STANDARD (default) or EXPRESS.
  • Policies adds SAM policy templates or IAM policies to the generated execution role. Role uses your own role, and SAM then ignores Policies.
  • Events starts the state machine from sources such as an API or a schedule. Logging and Tracing configure CloudWatch Logs and X-Ray.
  • AutoPublishAlias publishes a version and updates the alias. DeploymentPreference sets a gradual deployment for that alias.

Test one state with the TestState API

  • TestState runs one state definition. You do not create or update a state machine.
  • You can also send a full definition and name the state to test with stateName.
  • Inspection levels: INFO (default) shows the output or the error. DEBUG also shows each data processing step (afterInputPath, afterParameters, afterResultSelector, afterResultPath). TRACE shows the raw HTTP request and response, for HTTP Tasks only.
  • The response gives status (for example SUCCEEDED, FAILED, RETRIABLE, CAUGHT_ERROR) and nextState.
  • The caller needs states:TestState. Without a mock, the caller also needs iam:PassRole for the execution role, and the role needs the permissions that the state uses.
  • With the AWS CLI or SDK, you can mock a service result or an error. Then the role is optional. Map, Parallel, activity, .sync, and .waitForTaskToken states need a mock.

Exam signals

  • "Send 10 percent of executions to the new workflow, roll back on an alarm" → alias with DeploymentPreference type CANARY and Alarms.
  • "ASL file needs ARNs of resources in the same template" → DefinitionSubstitutions.
  • "Callers must not change the ARN when we release" → alias ARN.
  • "Test one Task state and see how InputPath and ResultPath change the data, without deploying" → TestState with DEBUG.

References: TestState API, Versions, Aliases, DeploymentPreference, AWS::Serverless::StateMachine. Lab: Lab 6.1 ASL basics.
