Buckets, objects, consistency, and request rates

Key facts

  • A bucket is in one AWS Region. Objects do not leave the Region unless you copy or replicate them.
  • By default, a general purpose bucket name must be unique across all AWS accounts in the partition. You cannot change the name or the Region after you create the bucket.
  • An object has a key, data, and metadata. User-defined metadata uses the x-amz-meta- prefix.
  • All buckets and objects are private by default. Block Public Access is on by default for new buckets.
  • Use ListObjectsV2 for new code. It is the current version of the list API and replaces the older ListObjects. Use HeadObject to read the metadata (for example size and content type) without the download of the body. It is the low-cost way to check that an object exists.
  • ListObjectsV2 returns up to 1,000 keys in each response. If IsTruncated is true, send the NextContinuationToken value as ContinuationToken in the next request.
  • Amazon S3 Select (SelectObjectContent) is no longer available to new customers. Do not choose it for a new design. Older study material shows it as the way to query part of an object.

Consistency

  • S3 gives strong read-after-write consistency for PUT and DELETE of objects, in all Regions. Strong consistency means that a read always sees the latest successful write. A GET or LIST that starts after a successful write returns the new data, so code does not need a delay or a retry loop.
  • An update to one key is atomic. A reader gets the old object or the new object, never a mix.
  • S3 does not lock objects for concurrent writers. If two PUT requests to the same key occur together, the request with the latest timestamp wins. Both requests succeed, so the other write is lost with no error.
  • To stop an overwrite of an existing key, use a conditional write. Send the header If-None-Match: * on PutObject or CompleteMultipartUpload. If an object with that key already exists, S3 rejects the write with HTTP 412 Precondition Failed and keeps the existing object.
  • Bucket configurations are eventually consistent: a change to a bucket setting takes some time to reach all parts of S3. For this reason, AWS recommends that you wait 15 minutes after you first enable versioning before you write objects.
  • Older study material says that S3 is eventually consistent for overwrites and deletes. That rule is out of date.

Numbers to memorize

  • A prefix is the first part of an object key, before the object name. For example, the key raw/device-7/reading.json has the prefix raw/device-7/. S3 gives request capacity to each prefix separately, so the rates in the table apply to each prefix, not to the whole bucket.
  • S3 scales to a higher request rate gradually. While S3 scales, requests above the current capacity fail with HTTP 503 (Slow Down). The error is temporary. Retry with exponential backoff (wait longer after each failed try), so that the writes complete without data loss.
  • Spread keys across more prefixes to get more total throughput. For example, 10 prefixes can give 55,000 reads per second (10 × 5,500). If all keys start with the same prefix, such as raw/, all requests share the capacity of that one prefix. Add a value such as a device ID or a hash after raw/ to spread the keys.

Exam signals

  • "Read the object immediately after the PUT returns" → S3 is strongly consistent. No delay or retry loop is necessary.
  • "503 Slow Down at high request rates" → more prefixes, because the request rate limit applies to each prefix. Also retry with exponential backoff, because the 503 errors stop when S3 finishes scaling.
  • "Do not overwrite the object if the key exists" → conditional write with If-None-Match: *. S3 returns 412 if the key exists.

  • Availability is the percentage of time that you can read the object. Durability is the protection against data loss. All classes in the table have the same durability (11 nines).
  • Minimum billable size: S3 bills a smaller object as if it were 128 KB. Minimum storage duration: S3 bills each object for at least that number of days.
  • Choose by how often you read the data. AWS designs S3 Standard for data read more than once a month, and Standard-IA and One Zone-IA for about once a month. Glacier Instant Retrieval is for about once a quarter, Glacier Flexible Retrieval for about once a year, and Glacier Deep Archive for less than once a year.
  • For each archived object in Glacier Flexible Retrieval or Glacier Deep Archive, S3 adds 40 KB of metadata. S3 bills 32 KB at the archive rate and 8 KB at the S3 Standard rate. Many very small archived objects can cost more than you expect.

Key facts

  • S3 Standard is the default class when the upload does not specify a class.
  • Intelligent-Tiering moves each object between access tiers by how recently it was read. A new object starts in the Frequent Access tier. After 30 days with no access, it moves to the Infrequent Access tier, and after 90 days to the Archive Instant Access tier. A read moves it back to Frequent Access. All three tiers give millisecond access. It has a small monitoring fee for each object and no retrieval fees.
  • Intelligent-Tiering does not monitor objects smaller than 128 KB. They stay in the Frequent Access tier.
  • One Zone-IA stores data in one Availability Zone only. If that Availability Zone is destroyed, the data is lost. Use it only for data that you can create again, for example thumbnails or a replica copy.
  • If you delete or move an object before its minimum storage duration, you pay for the rest of that duration.
  • Glacier Flexible Retrieval and Glacier Deep Archive objects are archived: a GetObject request fails with InvalidObjectState until you restore the object. Call RestoreObject to make a temporary readable copy for a number of days. The storage class of the original object does not change.

Exam signals

  • "Unknown or changing access pattern, no retrieval fees" → S3 Intelligent-Tiering.
  • "Rarely accessed, but must be available in milliseconds" → S3 Glacier Instant Retrieval.
  • "Archive for years, 48 hours to restore is acceptable, lowest cost" → S3 Glacier Deep Archive with Bulk retrieval.
  • "Need a few archived files in minutes" → Glacier Flexible Retrieval with Expedited retrieval.
  • "Data can be created again, lowest cost infrequent access" → S3 One Zone-IA. It costs less because it uses one Availability Zone, and the data is lost if that zone is lost.

Lifecycle rules

Key facts

  • A lifecycle rule has a filter (prefix, tags, object size, or a combination) and one or more actions.
  • Transition actions move objects to a colder storage class. Expiration actions delete objects.
  • For a versioned bucket, use NoncurrentVersionTransition and NoncurrentVersionExpiration for old versions. NewerNoncurrentVersions (1 to 100) keeps that number of recent noncurrent versions. S3 deletes a noncurrent version only when both the NoncurrentDays value and the NewerNoncurrentVersions value are exceeded.
  • In a versioned bucket, Expiration on the current version adds a delete marker. It does not remove data. The old data becomes a noncurrent version, and you pay for it until a NoncurrentVersionExpiration action deletes it.
  • An expired object delete marker is a delete marker with no noncurrent versions. They stay after their old versions expire and make LIST requests slower. Remove these with ExpiredObjectDeleteMarker set to true. You cannot use it with Days in the same rule, because an Expiration with Days already removes expired delete markers when they are old enough. To remove them as soon as they become the only version, use a separate rule with only ExpiredObjectDeleteMarker.
  • AbortIncompleteMultipartUpload deletes the parts of uploads that did not complete after a number of days. Without it, you pay for these parts until someone aborts the upload. A rule with this action cannot use a tag filter.
  • Transitions go in one direction only: from warmer classes (more frequent access, higher storage cost) to colder classes (less frequent access, lower storage cost). A rule cannot move an object from S3 Glacier Deep Archive to another class.
  • Lifecycle transitions are asynchronous: S3 runs them in the background. An object can change class some time after the rule date, not at an exact time.

Rules that changed recently

  • Since September 2024, by default, lifecycle rules do not transition objects smaller than 128 KB. To transition them, add an object size filter such as ObjectSizeGreaterThan.
  • Since July 2026, new lifecycle rules can transition objects to S3 Standard-IA or S3 One Zone-IA on the day that you create them. Older study material says that objects must stay 30 days in S3 Standard first. The 30-day minimum storage charge for the IA classes still applies.
  • One rule cannot transition an object out of a class before the minimum storage duration of that class. Example: a rule moves objects to Glacier Instant Retrieval (90-day minimum) on day 4. The next transition in that rule, to Deep Archive, must be on day 94 or later.

When actions conflict on the same day

  • Permanent deletion wins over transition.
  • Transition wins over creation of a delete marker.
  • If an object qualifies for S3 Glacier Flexible Retrieval and S3 Standard-IA, S3 chooses S3 Glacier Flexible Retrieval.

Exam signals

  • "Storage cost grows, but the object list does not show the data" → incomplete multipart uploads. S3 bills their parts, but ListObjectsV2 does not show them. Add AbortIncompleteMultipartUpload.
  • "Delete old versions 30 days after they become noncurrent" → NoncurrentVersionExpiration with NoncurrentDays 30.
  • "Small objects do not transition" → the 128 KB default. Add an object size filter.
  • "Move, then delete on a schedule, with no code" → one lifecycle rule with transition and expiration actions.

Versioning, MFA Delete, and Object Lock

Versioning

  • A bucket is in one of three states: unversioned (default), versioning-enabled, or versioning-suspended.
  • After you enable versioning, the bucket can never return to unversioned. You can only suspend versioning.
  • In a versioning-suspended bucket, each new PUT, POST, or copy gets the version ID null. It overwrites an existing null version of the key, and the data of that null version is lost. Older versions with real version IDs stay.
  • Objects that existed before you enabled versioning have the version ID null.
  • Each version is a full object. You pay for the storage of every version.
  • A DELETE without a version ID adds a delete marker. The delete marker becomes the current version. The data stays.
  • To restore the object, delete the delete marker. To delete a version permanently, send a DELETE with its version ID.

MFA Delete

  • MFA Delete requires an MFA code to permanently delete a version or to change the versioning state.
  • Only the bucket owner (root account) can enable MFA Delete.
  • You cannot enable MFA Delete in the console. Use the AWS CLI (put-bucket-versioning --mfa) or the API.
  • You cannot use MFA Delete with lifecycle configurations.

Object Lock

  • Object Lock stores object versions as write-once-read-many (WORM): after S3 writes a version, nobody can overwrite or delete it until the lock ends. It works only with versioning enabled.
  • You can enable Object Lock when you create a bucket or on an existing bucket. After you enable it, you cannot disable Object Lock or suspend versioning.
  • A lock protects one object version, not the key. A new PUT to the same key still succeeds and creates a new version. A DELETE without a version ID still adds a delete marker. The locked version stays unchanged.
  • A retention period is a fixed time (a retain-until date) during which the version stays locked. Each retention period uses compliance mode or governance mode.
ProtectionBehavior
Compliance modeNo user can delete or overwrite the version, including the root user. You cannot shorten the period or change the mode.
Governance modeUsers with s3:BypassGovernanceRetention can delete or change the lock. The request must include the x-amz-bypass-governance-retention:true header.
Legal holdHas no end date. It stays until a user with s3:PutObjectLegalHold removes it. It is independent of the retention period.

Choose compliance mode when a regulation says that nobody may delete the data for a fixed time. Choose governance mode when most users must not delete the data, but a few administrators need a way to override a lock, for example to fix a mistake. Choose a legal hold when the end date is not known, for example during an audit or a lawsuit.

Exam signals

  • "Recover from accidental deletes and overwrites" → versioning.
  • "Restore a deleted object in a versioned bucket" → delete the delete marker.
  • "Require MFA to permanently delete versions" → MFA Delete, enabled by the root user with the CLI.
  • "No one, not even root, can delete for 7 years" → Object Lock compliance mode.
  • "Protect until the audit ends, end date unknown" → legal hold, because it has no end date and stays until someone removes it.

Replication

Key facts

  • Replication copies objects asynchronously to one or more destination buckets: the write to the source returns first, and S3 copies the object later. The buckets can be in the same account or in different accounts.
  • Cross-Region Replication (CRR) copies to a bucket in another Region. Choose CRR when a rule requires a copy far from the source (disaster recovery), when users in another Region need lower latency, or when compute in a second Region must read the data.
  • Same-Region Replication (SRR) copies to a bucket in the same Region. Choose SRR to collect logs from several buckets into one bucket, to copy production data into a test account, or when the data must not leave the Region (data sovereignty). SRR has no data transfer charge.
  • Versioning must be enabled on the source and on each destination bucket. If you disable versioning on a destination bucket later, replication fails and the source objects get the replication status FAILED.
  • S3 needs an IAM role with permission to replicate. For a cross-account destination, the destination bucket policy must allow the source owner.
  • Live replication does not copy objects that existed before you added the rule. Use S3 Batch Replication (a one-time S3 Batch Operations job) for existing objects and for objects that failed.
  • If the source bucket uses Object Lock, the destination buckets must also use Object Lock.
  • S3 Replication Time Control (RTC) replicates 99.99 percent of new objects within 15 minutes, backed by a service level agreement (SLA). Without RTC, replication has no time guarantee, and a large object can take hours.
  • You can replicate into a different storage class, for example S3 Glacier Deep Archive in the destination. Use this for a backup copy that you expect to read rarely.

Exam signals

  • "Copy existing objects to the new destination" → S3 Batch Replication.
  • "Replicate within 15 minutes with an SLA" → S3 Replication Time Control.
  • "Replication setup fails" → check versioning on both buckets and the replication role.

References: Replication overview, Replication requirements (versioning, FAILED status, replication time). Lab: Module 3 overview.

Numbers to memorize

Part size5 MiB to 5 GiB. The last part has no minimum.
When to consider multipartObjects of 100 MB or larger

Multipart flow

  1. CreateMultipartUpload returns an UploadId.
  2. UploadPart sends each part. Parts can upload in parallel and in any order. Each part returns an ETag.
  3. CompleteMultipartUpload sends the part numbers and ETags. S3 builds the object in part-number order.
  4. AbortMultipartUpload stops the upload and deletes the parts.
  • An upload that you start has no expiry. Until you complete or abort it, you pay for the stored parts. ListObjectsV2 does not show them. ListMultipartUploads does. Add an AbortIncompleteMultipartUpload lifecycle rule so that S3 deletes them for you.
  • A part smaller than 5 MiB that is not the last part makes CompleteMultipartUpload fail with EntityTooSmall.
  • If one part fails, upload only that part again. The other parts stay in S3, so a network error does not restart the whole file.
  • The ETag of a multipart object is not the MD5 of the whole object. S3 calculates it from the checksums of the parts. If you compare it with the MD5 of the local file, the values do not match even when the data is correct. Use additional checksums (for example CRC32 or SHA-256) to check integrity.
  • The SDK transfer managers and the AWS CLI s3 cp command use multipart upload automatically for large files.

Transfer Acceleration

  • Transfer Acceleration sends data to the nearest CloudFront edge location, then over the AWS network to the bucket. The data spends less time on the public internet, so long-distance transfers are faster. Use it when users are far from the bucket Region, for example on other continents. It can add data transfer charges.
  • Enable it on the bucket. Then use the endpoint <bucket>.s3-accelerate.amazonaws.com.
  • The bucket name must be DNS-compliant and must not contain periods.
  • After you enable it, the speed increase can take up to 20 minutes to start.

Downloads

  • Use byte-range GET requests (the Range header) to download parts of a large object in parallel.

Exam signals

  • "Upload a 20 GB file" → multipart upload. A single PUT allows 5 GB.
  • "Resume a failed upload without starting again" → multipart upload. Upload only the failed parts.
  • "Users on other continents upload slowly to one bucket" → Transfer Acceleration.
  • "EntityTooSmall on complete" → parts must be at least 5 MiB, except the last part.

Presigned URLs

Key facts

  • A presigned URL gives time-limited access to one object for one HTTP method. The user of the URL does not need AWS credentials.
  • The URL uses the credentials and the permissions of the principal that created it. If that principal cannot do the action, the URL fails.
  • The SDK creates the URL locally with SigV4 (Signature Version 4, the AWS process that signs a request with a secret access key). Creating the URL does not call AWS, so the SDK does not check that the object exists or that the permissions are correct. S3 checks them when someone uses the URL.
  • A presigned URL is a bearer token: S3 accepts it from anyone who holds it and does not check who sends the request. Anyone who has the URL can use it, many times, until it expires. Treat the URL as a secret.
  • A URL for PutObject works only for PUT. Create a separate URL for GET.
  • A presigned PUT replaces an existing object with the same key.
  • Parameters such as ContentType and ServerSideEncryption become signed headers. The client must send the same values, or S3 returns 403 SignatureDoesNotMatch. A backend uses this to force upload settings.
  • S3 checks the expiration time when the request starts. A download that started before expiration can finish.

Expiration limits

Signed withMaximum validity
S3 console1 minute to 12 hours
IAM user long-term keys (CLI or SDK, SigV4)7 days (604,800 seconds)
Temporary credentials (IAM role, STS)Ends when the credentials expire, even if the URL asks for longer. AssumeRole sessions last 1 hour by default.

To share a file for several days, sign the URL with long-term IAM user keys (maximum 7 days). A URL that a Lambda function or an EC2 instance signs uses role credentials, so it stops working when those credentials expire, often after a few hours.

Limit or stop presigned URLs

  • You cannot revoke one URL. But a URL stops working when the signing credentials are revoked, deleted, or deactivated.
  • Keep ExpiresIn short. If someone leaks the URL, it then works for less time.
  • Bucket policy condition s3:signatureAge denies requests with an old signature (value in milliseconds).
  • Conditions aws:SourceIp (public endpoint) or aws:SourceVpce / aws:SourceVpc (VPC endpoint) limit the network path.

Presigned POST (browser form upload)

  • A presigned POST lets an HTML form or browser script upload directly to S3 with an HTTP POST. The backend signs a POST policy.
  • The POST policy has an expiration and conditions. Conditions can fix the bucket, limit the key with starts-with, and limit the file size with content-length-range.
  • S3 rejects an upload that does not meet the conditions.
  • SDK helpers: generate_presigned_post (Python) and createPresignedPost (JavaScript v3).
  • Choose a presigned POST when the backend must limit the upload size or allow many key names under one prefix. A presigned PUT URL is for one exact key, and a POST policy adds content-length-range and starts-with conditions.

Exam signals

  • "Browser or mobile client uploads directly to S3 without AWS credentials" → backend returns a presigned PUT URL.
  • "Backend must force the encryption type or content type of client uploads" → sign those headers into the URL.
  • "URL fails before ExpiresIn" → it was signed with temporary credentials that expired.
  • "Share a private file for 3 days from the CLI" → aws s3 presign --expires-in 259200 with IAM user credentials.
  • "HTML form upload, limit the file size and the key prefix" → presigned POST with content-length-range and starts-with.
  • "Private content for paying users, served through CloudFront" → CloudFront signed URLs or signed cookies, with OAC on the bucket.

SSE means server-side encryption: S3 receives the plaintext data and encrypts it before it stores it. Choose SSE-S3 when you need encryption with no key management. Choose SSE-KMS when you must control key access with a key policy, see each key use in CloudTrail, or disable the key. Choose SSE-C when the company must keep its own keys outside AWS. Choose client-side encryption when AWS must never receive the plaintext.

Key facts

  • Server-side encryption encrypts object data, not object metadata.
  • Default bucket encryption (PutBucketEncryption) applies when an upload does not specify encryption. A request header can choose a different supported type.
  • To encrypt an existing object with a new setting, copy the object onto itself with CopyObject.
  • For SSE-KMS objects, do not send encryption headers on GET or HEAD. S3 returns HTTP 400.

SSE-C

  • Send the algorithm (AES256), the base64 key, and the base64 MD5 of the key with each PUT and GET.
  • You must use HTTPS. S3 rejects SSE-C requests over HTTP, because each request carries the encryption key.
  • If you lose the key, you lose the object. The console does not support SSE-C uploads.
  • Since April 2026, S3 blocks SSE-C on new general purpose buckets and on existing buckets in accounts with no SSE-C objects. Older study material does not have this rule. A blocked request gets HTTP 403 AccessDenied. To allow it, set BlockedEncryptionTypes to NONE with PutBucketEncryption.

Enforce encryption with a bucket policy

  • Encryption in transit: deny all actions when aws:SecureTransport is false.
  • Require SSE-KMS: deny s3:PutObject with the condition "Null": {"s3:x-amz-server-side-encryption-aws-kms-key-id": "true"}. This condition matches uploads that do not send the KMS key ID header, so S3 rejects them.
  • Require one specific KMS key: use the s3:x-amz-server-side-encryption-aws-kms-key-id condition with the full key ARN.
  • A deny policy rejects uploads that do not meet the rule. Default encryption encrypts uploads that send no header. Use the policy to reject, and default encryption to encrypt without client changes.

Exam signals

  • "Audit each use of the key, control rotation and key access" → SSE-KMS with a customer managed key.
  • "Data must be encrypted before it leaves the application" → client-side encryption.
  • "Company must supply and keep its own keys, no KMS" → SSE-C (enable it on new buckets first).
  • "Deny any request that does not use HTTPS" → aws:SecureTransport false in a deny statement.
  • "Old exam text says objects are not encrypted by default" → out of date. SSE-S3 applies to all new uploads.

SSE-KMS permissions, Bucket Keys, and cross-account access

Permissions

OperationKMS permission on the key
PutObject with SSE-KMSkms:GenerateDataKey
GetObject of an SSE-KMS objectkms:Decrypt
Multipart upload with SSE-KMSkms:GenerateDataKey and kms:Decrypt

A multipart upload needs kms:Decrypt because S3 must decrypt and read the encrypted parts before it completes the upload. Without it, small uploads work and multipart uploads fail with AccessDenied.

  • The caller needs the S3 permission and the KMS permission. An S3 allow alone does not decrypt the object.
  • The KMS key must be in the same Region as the bucket. S3 supports only symmetric encryption KMS keys.
  • S3 uses envelope encryption: it encrypts the data with a data key, and KMS encrypts that data key with the KMS key. KMS creates a unique data key for the object and returns a plaintext copy and an encrypted copy. S3 encrypts the object with the plaintext copy and stores the encrypted copy with the object. To read the object, S3 asks KMS to decrypt the data key.

Cross-account access

  • You cannot share objects encrypted with the AWS managed key aws/s3 across accounts. You cannot edit the key policy of an AWS managed key, so you cannot allow another account to use it. Use a customer managed key.
  • The key policy of the customer managed key must allow the other account. The bucket policy must also allow the other account. The principal in the other account needs an IAM policy for S3 and KMS.
  • Use the full key ARN, not an alias. KMS looks up an alias in the account of the requester. A cross-account upload can then encrypt the object with a key that belongs to the requester, not to the bucket owner.
  • KMS counts cross-account requests against the quota of the calling account.

S3 Bucket Keys

  • Without a Bucket Key, S3 calls KMS for each object request. A Bucket Key is a short-lived bucket-level key from KMS. S3 keeps it for a limited time and uses it to create data keys for many objects, so S3 calls KMS less often.
  • Bucket Keys can reduce KMS request costs by up to 99 percent. No client changes are necessary.
  • Bucket Keys apply to new objects only. To use one for an existing object, copy the object.
  • The encryption context is a set of key-value pairs that S3 sends to KMS with each encrypt and decrypt request. By default S3 uses the object ARN. Policies can use it in conditions to limit key use. With a Bucket Key, the encryption context is the bucket ARN, not the object ARN. Policies that check the object ARN then stop matching, so update them to use the bucket ARN.
  • With a Bucket Key, CloudTrail shows fewer KMS events, and they show the bucket ARN.

Throttling

  • Each SSE-KMS upload or download makes a KMS request (without a Bucket Key). These requests count toward the shared KMS request quota of the account in the Region.
  • Over the quota, KMS throttles the requests (ThrottlingException). Fix with Bucket Keys, or request a quota increase.

Exam signals

  • "KMS costs are high, or KMS throttles S3 requests" → enable S3 Bucket Keys, because they cut the number of KMS requests.
  • "Small uploads work, multipart uploads get AccessDenied" → add kms:Decrypt, because S3 must decrypt the parts to complete the upload.
  • "Other account gets AccessDenied for SSE-KMS objects" → customer managed key with a key policy for that account, and a bucket policy.
  • "Key policy uses the object ARN in encryption context, access fails after a change" → Bucket Key changed the context to the bucket ARN.

References: SSE-KMS permissions and cross-account use, Multipart upload and KMS permissions, S3 Bucket Keys, KMS request quotas. Lab: Lab 3.4 Encryption variants.

Bucket policies, Object Ownership, and access points

Policy evaluation

  • Access to S3 uses IAM identity policies, bucket policies, access point policies, and (when enabled) ACLs.
  • In the same account, an allow in the IAM policy or in the bucket policy is enough. An explicit deny in any policy wins.
  • Across accounts, the bucket policy (or access point policy) must allow the other account, and the IAM policy in the other account must allow the action.
  • Bucket ARN (arn:aws:s3:::bucket) is for bucket actions such as s3:ListBucket. Object ARN (arn:aws:s3:::bucket/*) is for object actions such as s3:GetObject. If a statement uses the wrong ARN, it does not match the action, and the request gets AccessDenied.

Object Ownership and ACLs

SettingBehavior
Bucket owner enforced (default)ACLs are disabled. The bucket owner owns every object. Policies control all access.
Bucket owner preferredACLs are enabled. The bucket owner owns new objects written with the bucket-owner-full-control canned ACL.
Object writerACLs are enabled. The uploading account owns the object.

An ACL (access control list) is an older way to grant access on one bucket or one object. A canned ACL is a predefined set of grants, such as bucket-owner-full-control. Keep Bucket owner enforced for new buckets. Choose Bucket owner preferred or Object writer only when an existing application still needs ACLs.

  • With ACLs disabled, a PUT with an ACL other than bucket owner full control fails with AccessControlListNotSupported.
  • AWS recommends that you keep ACLs disabled and use policies.

Block Public Access

  • Block Public Access settings are on by default for new buckets. They override policies and ACLs that grant public access. S3 rejects a new bucket policy that grants public access while these settings are on.
  • You can set them on the account, the bucket, and each access point.

Access points and VPC access

  • An access point is a named endpoint with its own access point policy. A bucket has only one bucket policy, with a 20 KB size limit. When many applications share a bucket, that one policy grows large, and each change can break other applications. Give each application its own access point and policy instead.
  • You can configure an access point to accept requests only from a VPC.
  • From a VPC, use a gateway endpoint for S3 so traffic does not use the internet. A gateway endpoint is an entry in the subnet route tables that sends S3 traffic over the AWS network. Instances in private subnets can then reach S3 with no internet gateway or NAT gateway.
  • To allow only VPC traffic, deny requests in the bucket policy when aws:SourceVpce (or aws:SourceVpc) does not match. aws:SourceIp does not work for requests through a VPC endpoint, because IAM does not include that key in those requests.

Exam signals

  • "Another account uploads, the bucket owner must own the objects, no ACLs" → Bucket owner enforced.
  • "Many applications share one bucket, the bucket policy is too large" → one access point for each application.
  • "Only allow access from our VPC endpoint" → bucket policy deny with aws:SourceVpce.
  • "Public bucket policy is rejected when saved" → Block Public Access is on.

References: Object Ownership, Block Public Access, Access points, Network condition keys, aws:SourceIp and VPC endpoints. Lab: Lab 3.1 Bucket basics.

Static websites, CloudFront OAC, and CORS

Static website hosting

  • Website endpoint: http://<bucket>.s3-website-<region>.amazonaws.com or http://<bucket>.s3-website.<region>.amazonaws.com, by Region.
  • Configure an index document and an optional error document. The website endpoint supports redirects.
  • The website endpoint serves only publicly readable content, because browsers send unsigned requests to it. Turn off Block Public Access for the bucket and add a bucket policy that allows s3:GetObject to everyone. If you do not, every page returns 403.
  • The website endpoint does not support HTTPS or access points. It supports only GET and HEAD on objects.
  • For HTTPS, put Amazon CloudFront in front of the content, or use AWS Amplify Hosting.
  • Requester Pays buckets do not allow access through the website endpoint.

CloudFront with origin access control (OAC)

  • Origin access control (OAC) lets CloudFront send signed (SigV4) requests to a private S3 bucket. The bucket stays private, and Block Public Access can stay on. Users cannot go around CloudFront to S3, because S3 accepts only the signed CloudFront requests.
  • The bucket policy allows the service principal cloudfront.amazonaws.com, with a condition AWS:SourceArn equal to the distribution ARN. Without this condition, any CloudFront distribution in any account could read the bucket.
  • For SSE-KMS objects, the KMS key policy must also allow cloudfront.amazonaws.com for that distribution.
  • AWS recommends OAC instead of the legacy origin access identity (OAI). OAI does not support SSE-KMS, dynamic requests (PUT, POST, DELETE), or newer Regions.
  • OAC works with the S3 REST endpoint, not with a website endpoint. CloudFront treats a website endpoint as a custom origin (an ordinary web server) and does not sign requests to it, so the bucket must be public.
  • With OAC, keep Object Ownership at Bucket owner enforced (the default).

CORS

  • An origin is the scheme, domain, and port of a web page, for example https://app.example.com. A browser blocks JavaScript requests to a different origin unless the server allows it. Configure CORS (cross-origin resource sharing) on the bucket that receives the requests.
  • Before a cross-origin request such as a PUT, the browser sends a preflight OPTIONS request. S3 answers it from the CORS configuration of the bucket. If no rule matches, the browser blocks the real request and shows a CORS error.
  • Rule elements: AllowedOrigins (which pages can call), AllowedMethods (GET, PUT, POST, DELETE, HEAD), AllowedHeaders (request headers allowed in the preflight), ExposeHeaders (response headers that JavaScript can read), and MaxAgeSeconds (how long the browser caches the preflight response).
  • A configuration can have up to 100 rules. The console accepts only JSON.
  • S3 uses the first rule that matches the origin, the method, and the requested headers.
  • CORS does not grant permission. Policies and ACLs still apply.
  • To read a response header in JavaScript (for example ETag in a browser multipart upload), list it in ExposeHeaders.

Exam signals

  • "Browser shows a CORS error when the page calls the bucket" → CORS configuration on the target bucket.
  • "Static site must use HTTPS and a custom domain" → CloudFront in front of S3.
  • "Users must reach the files only through CloudFront, bucket stays private" → OAC and a bucket policy for the distribution.
  • "CloudFront with OAC returns 403 for SSE-KMS objects" → add the distribution to the KMS key policy.
  • "Website returns 403 for every page" → objects are not public: Block Public Access or a missing bucket policy.

References: Website endpoints, CORS, CORS configuration elements, CloudFront OAC. Lab: Lab 3.1 Bucket basics.

Event notifications and EventBridge

Direct event notifications

  • Destinations: Amazon SNS topic, Amazon SQS queue, AWS Lambda function, and Amazon EventBridge.
  • SQS FIFO queues are not supported as a direct destination. Use EventBridge to reach a FIFO queue.
  • Delivery is at least once, so the same event can arrive two times. Events usually arrive in seconds, but can take a minute or longer. Make consumers idempotent: processing the same event two times must give the same result as one time. For example, check whether the thumbnail already exists before you create it.
  • S3 invokes Lambda asynchronously: S3 hands the event to Lambda and does not wait for the function result. The function resource-based policy must allow s3.amazonaws.com, or S3 cannot invoke the function.
  • The SQS queue policy or SNS topic policy must allow S3 to send messages.
  • Event types include s3:ObjectCreated:* (Put, Post, Copy, CompleteMultipartUpload), s3:ObjectRemoved:*, restore, replication, lifecycle, and tagging events. s3:ObjectCreated:Put alone misses copies, POST uploads, and multipart uploads.
  • The message has a Records array with the bucket name and the object key. It does not contain the object data.

Filters

  • Filter only by key prefix and key suffix. Wildcards (*) are not allowed.
  • For the same event type, rules cannot overlap. Two rules with the same prefix fail unless their suffixes do not overlap. S3 rejects the configuration when you save it.
  • Rules for different event types can overlap.
  • To send one event to several consumers, send it to an SNS topic or use EventBridge. With SNS fan-out, S3 sends the event once to the topic, and SNS delivers a copy to each subscriber, for example an SQS queue and a Lambda function.

EventBridge

  • Turn on EventBridge for the bucket. S3 then sends all supported events to the default event bus. You do not choose event types on the bucket.
  • EventBridge rules filter on any field, for example object size or key patterns, and send to many target types.
  • Event format: source is aws.s3, detail-type is for example Object Created.
  • Choose direct notifications for a prefix or suffix filter and one destination for each event type. Choose EventBridge when you need filters on other fields, several targets for the same event, or a target that direct notifications do not support, such as an SQS FIFO queue.

Loops

  • If the function writes to the bucket that invokes it, each write creates a new event, and the function invokes itself in a loop. The invocations and the cost grow quickly. Use a second bucket, or limit the trigger to an input prefix that the function does not write to.

Exam signals

  • "Several services must react to each upload" → SNS fan-out or EventBridge.
  • "Filter on object size or on a pattern in the middle of the key" → EventBridge rule, because direct notifications filter only on key prefix and suffix.
  • "Send S3 events to a FIFO queue" → EventBridge.
  • "Function processed the same upload twice" → at-least-once delivery. Make the code idempotent.
  • "Function runs again and again after it writes its output" → write to another bucket or prefix.

References: Event notifications, Key name filtering, Using EventBridge. Lab: Lab 3.6 Event notifications.

S3 Object Lambda

Availability

  • Since November 7, 2025, S3 Object Lambda is available only to existing customers and to some AWS Partner Network partners.
  • AWS alternatives: invoke Lambda through CloudFront, API Gateway, or a function URL, or process the data in the client.
  • The exam guide was written before this change. Learn how Object Lambda works, but expect current AWS designs to use the alternatives.

Key facts

  • Object Lambda runs your Lambda function on GET, HEAD, and LIST requests to change the data that S3 returns. The stored object does not change.
  • Applications send requests to an Object Lambda Access Point. It invokes your function, and the function reads the original object through a standard access point (the supporting access point).
  • Use cases: redact PII, convert formats, resize or watermark images, filter rows.
  • Object Lambda does not change PUT or DELETE. To change data on write, use an event notification and a function.

The GetObject function

  1. Read getObjectContext from the event: inputS3Url, outputRoute, and outputToken.
  2. Download the original object from inputS3Url. It is a presigned URL.
  3. Transform the data.
  4. Call WriteGetObjectResponse with RequestRoute, RequestToken, and the new body.
  • The execution role needs s3-object-lambda:WriteGetObjectResponse (managed policy AmazonS3ObjectLambdaExecutionRolePolicy).
  • WriteGetObjectResponse is the only way the function sends data back to the caller. S3 ignores the return value of the function. If the function returns before it calls WriteGetObjectResponse, the caller gets HTTP 500.
  • The function has up to 60 seconds to send the complete response.

Exam signals

  • "Different applications need different views of the same object, no copies" → Object Lambda (existing customers), or Lambda behind CloudFront or API Gateway.
  • "Clients get 500 errors from the Object Lambda Access Point" → the function did not call WriteGetObjectResponse.
  • "Transform data when it is uploaded" → not Object Lambda. Use an ObjectCreated event.

References: Object Lambda availability change, Writing Object Lambda functions, Object Lambda IAM policies. Lab: Lab 3.7 S3 Object Lambda.
