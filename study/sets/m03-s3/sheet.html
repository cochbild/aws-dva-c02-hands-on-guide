Buckets, objects, consistency, and request rates

Key facts

  • A bucket is in one AWS Region. Objects do not leave the Region unless you copy or replicate them.
  • By default, a general purpose bucket name must be unique across all AWS accounts in the partition. You cannot change the name or the Region after you create the bucket.
  • An object has a key, data, and metadata. User-defined metadata uses the x-amz-meta- prefix.
  • All buckets and objects are private by default. Block Public Access is on by default for new buckets.
  • Use ListObjectsV2 for new code. Use HeadObject to read metadata without the body.
  • ListObjectsV2 returns up to 1,000 keys in each response. If IsTruncated is true, send the NextContinuationToken value as ContinuationToken in the next request.
  • Amazon S3 Select (SelectObjectContent) is no longer available to new customers. Do not choose it for a new design. Older study material shows it as the way to query part of an object.

Consistency

  • S3 gives strong read-after-write consistency for PUT and DELETE of objects, in all Regions. A read or LIST after a successful write returns the new data.
  • An update to one key is atomic. A reader gets the old object or the new object, never a mix.
  • S3 does not lock objects for concurrent writers. If two PUT requests to the same key occur together, the latest timestamp wins.
  • To stop an overwrite of an existing key, use a conditional write on PutObject or CompleteMultipartUpload.
  • Bucket configurations are eventually consistent. AWS recommends that you wait 15 minutes after you first enable versioning before you write objects.
  • Older study material says that S3 is eventually consistent for overwrites and deletes. That rule is out of date.

Numbers to memorize

ItemValue
Request rate for each partitioned prefixAt least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second
Number of prefixes in a bucketNo limit
Bucket policy size20 KB
Durability (all storage classes except Reduced Redundancy)99.999999999% (11 nines)
  • S3 scales to a higher request rate gradually. During scaling, clients can get HTTP 503 (Slow Down) errors. Retry with exponential backoff.
  • Spread requests across more prefixes to get more total throughput. For example, 10 prefixes can give 55,000 reads per second.

Exam signals

  • "Read the object immediately after the PUT returns" → S3 is strongly consistent. No delay or retry loop is necessary.
  • "503 Slow Down at high request rates" → more prefixes, and retries with exponential backoff.
  • "Do not overwrite the object if the key exists" → conditional write.

Lifecycle rules

Key facts

  • A lifecycle rule has a filter (prefix, tags, object size, or a combination) and one or more actions.
  • Transition actions move objects to a colder storage class. Expiration actions delete objects.
  • For a versioned bucket, use NoncurrentVersionTransition and NoncurrentVersionExpiration for old versions. NewerNoncurrentVersions keeps a number of recent versions (1 to 100).
  • In a versioned bucket, Expiration on the current version adds a delete marker. It does not remove data.
  • An expired object delete marker is a delete marker with no noncurrent versions. Remove these with ExpiredObjectDeleteMarker set to true. You cannot use it with Days in the same rule.
  • AbortIncompleteMultipartUpload deletes the parts of uploads that did not complete after a number of days. A rule with this action cannot use a tag filter.
  • Transitions follow a waterfall: from warmer classes to colder classes. A rule cannot move an object from S3 Glacier Deep Archive to another class.
  • Lifecycle transitions are asynchronous. An object can transition some time after the rule date.

Rules that changed recently

  • Since September 2024, by default, lifecycle rules do not transition objects smaller than 128 KB. To transition them, add an object size filter such as ObjectSizeGreaterThan.
  • Since July 2026, new lifecycle rules can transition objects to S3 Standard-IA or S3 One Zone-IA on the day that you create them. Older study material says that objects must stay 30 days in S3 Standard first. The 30-day minimum storage charge for the IA classes still applies.
  • One rule cannot transition an object out of a class before the minimum storage duration of that class. Example: after Glacier Instant Retrieval on day 4, a Deep Archive transition must be on day 94 or later.

When actions conflict on the same day

  • Permanent deletion wins over transition.
  • Transition wins over creation of a delete marker.
  • If an object qualifies for S3 Glacier Flexible Retrieval and S3 Standard-IA, S3 chooses S3 Glacier Flexible Retrieval.

Exam signals

  • "Storage cost grows, but the object list does not show the data" → incomplete multipart uploads. Add AbortIncompleteMultipartUpload.
  • "Delete old versions 30 days after they become noncurrent" → NoncurrentVersionExpiration with NoncurrentDays 30.
  • "Small objects do not transition" → the 128 KB default. Add an object size filter.
  • "Move, then delete on a schedule, with no code" → one lifecycle rule with transition and expiration actions.

Versioning, MFA Delete, and Object Lock

Versioning

  • A bucket is in one of three states: unversioned (default), versioning-enabled, or versioning-suspended.
  • After you enable versioning, the bucket can never return to unversioned. You can only suspend versioning.
  • In a versioning-suspended bucket, each new PUT, POST, or copy gets the version ID null. It overwrites an existing null version of the key. Older versions with real version IDs stay.
  • Objects that existed before you enabled versioning have the version ID null.
  • Each version is a full object. You pay for the storage of every version.
  • A DELETE without a version ID adds a delete marker. The delete marker becomes the current version. The data stays.
  • To restore the object, delete the delete marker. To delete a version permanently, send a DELETE with its version ID.

MFA Delete

  • MFA Delete requires an MFA code to permanently delete a version or to change the versioning state.
  • Only the bucket owner (root account) can enable MFA Delete.
  • You cannot enable MFA Delete in the console. Use the AWS CLI (put-bucket-versioning --mfa) or the API.
  • You cannot use MFA Delete with lifecycle configurations.

Object Lock

  • Object Lock stores object versions as write-once-read-many (WORM). It works only with versioning enabled.
  • You can enable Object Lock when you create a bucket or on an existing bucket. After you enable it, you cannot disable Object Lock or suspend versioning.
  • A lock protects one object version. A new PUT to the same key creates a new version. A simple DELETE adds a delete marker.
ProtectionBehavior
Compliance modeNo user can delete or overwrite the version, including the root user. You cannot shorten the period or change the mode.
Governance modeUsers with s3:BypassGovernanceRetention can delete or change the lock. The request must include the x-amz-bypass-governance-retention:true header.
Legal holdHas no end date. It stays until a user with s3:PutObjectLegalHold removes it. It is independent of the retention period.

Exam signals

  • "Recover from accidental deletes and overwrites" → versioning.
  • "Restore a deleted object in a versioned bucket" → delete the delete marker.
  • "Require MFA to permanently delete versions" → MFA Delete, enabled by the root user with the CLI.
  • "No one, not even root, can delete for 7 years" → Object Lock compliance mode.
  • "Protect until the audit ends, end date unknown" → legal hold.

Replication

Key facts

  • Replication copies objects asynchronously to one or more destination buckets. The buckets can be in the same account or in different accounts.
  • Cross-Region Replication (CRR) copies to another Region: compliance distance, lower latency for users, compute in two Regions.
  • Same-Region Replication (SRR) copies in the same Region: log aggregation, production to test copies, data sovereignty. SRR has no data transfer charge.
  • Versioning must be enabled on the source and on each destination bucket.
  • S3 needs an IAM role with permission to replicate. For a cross-account destination, the destination bucket policy must allow the source owner.
  • Live replication does not copy objects that existed before you added the rule. Use S3 Batch Replication for existing objects and for objects that failed.
  • If the source bucket uses Object Lock, the destination buckets must also use Object Lock.
  • S3 Replication Time Control (RTC) replicates 99.99 percent of new objects within 15 minutes, with an SLA.
  • You can replicate into a different storage class, for example S3 Glacier Deep Archive in the destination.

Exam signals

  • "Copy existing objects to the new destination" → S3 Batch Replication.
  • "Replicate within 15 minutes with an SLA" → S3 Replication Time Control.
  • "Replication setup fails" → check versioning on both buckets and the replication role.

References: Replication overview, Replication requirements. Lab: Module 3 overview.

Multipart upload and Transfer Acceleration

Numbers to memorize

ItemValue
Single PutObjectUp to 5 GB
Console uploadUp to 160 GB
Multipart upload object sizeUp to 50 TB (48.8 TiB). Older study material says 5 TB.
Parts for each upload1 to 10,000
Part size5 MiB to 5 GiB. The last part has no minimum.
When to consider multipartObjects of 100 MB or larger

Multipart flow

  1. CreateMultipartUpload returns an UploadId.
  2. UploadPart sends each part. Parts can upload in parallel and in any order. Each part returns an ETag.
  3. CompleteMultipartUpload sends the part numbers and ETags. S3 builds the object in part-number order.
  4. AbortMultipartUpload stops the upload and deletes the parts.
  • Until you complete or abort the upload, you pay for the stored parts. ListObjectsV2 does not show them. ListMultipartUploads does.
  • A part smaller than 5 MiB that is not the last part makes CompleteMultipartUpload fail with EntityTooSmall.
  • If one part fails, upload only that part again.
  • The ETag of a multipart object is not the MD5 of the whole object. Use additional checksums (for example CRC32 or SHA-256) to check integrity.
  • The SDK transfer managers and the AWS CLI s3 cp command use multipart upload automatically for large files.

Transfer Acceleration

  • Transfer Acceleration sends data through CloudFront edge locations, then over the AWS network to the bucket. Use it for long-distance uploads and downloads.
  • Enable it on the bucket. Then use the endpoint <bucket>.s3-accelerate.amazonaws.com.
  • The bucket name must be DNS-compliant and must not contain periods.
  • After you enable it, the speed increase can take up to 20 minutes to start.

Downloads

  • Use byte-range GET requests (the Range header) to download parts of a large object in parallel.

Exam signals

  • "Upload a 20 GB file" → multipart upload. A single PUT allows 5 GB.
  • "Resume a failed upload without starting again" → multipart upload. Upload only the failed parts.
  • "Users on other continents upload slowly to one bucket" → Transfer Acceleration.
  • "EntityTooSmall on complete" → parts must be at least 5 MiB, except the last part.

Presigned URLs

Key facts

  • A presigned URL gives time-limited access to one object for one HTTP method. The user of the URL does not need AWS credentials.
  • The URL uses the credentials and the permissions of the principal that created it. If that principal cannot do the action, the URL fails.
  • The SDK creates the URL locally with SigV4. Creating the URL does not call AWS.
  • A presigned URL is a bearer token. Anyone who has the URL can use it, many times, until it expires.
  • A URL for PutObject works only for PUT. Create a separate URL for GET.
  • A presigned PUT replaces an existing object with the same key.
  • Parameters such as ContentType and ServerSideEncryption become signed headers. The client must send the same values, or S3 returns 403 SignatureDoesNotMatch. A backend uses this to force upload settings.
  • S3 checks the expiration time when the request starts. A download that started before expiration can finish.

Expiration limits

Signed withMaximum validity
S3 console1 minute to 12 hours
IAM user long-term keys (CLI or SDK, SigV4)7 days (604,800 seconds)
Temporary credentials (IAM role, STS)Ends when the credentials expire, even if the URL asks for longer. AssumeRole sessions last 1 hour by default.
EC2 instance profile credentialsAbout 6 hours

Limit or stop presigned URLs

  • You cannot revoke one URL. But a URL stops working when the signing credentials are revoked, deleted, or deactivated.
  • Keep ExpiresIn short.
  • Bucket policy condition s3:signatureAge denies requests with an old signature (value in milliseconds).
  • Conditions aws:SourceIp (public endpoint) or aws:SourceVpce / aws:SourceVpc (VPC endpoint) limit the network path.

Presigned POST (browser form upload)

  • A presigned POST lets an HTML form or browser script upload directly to S3 with an HTTP POST. The backend signs a POST policy.
  • The POST policy has an expiration and conditions. Conditions can fix the bucket, limit the key with starts-with, and limit the file size with content-length-range.
  • S3 rejects an upload that does not meet the conditions.
  • SDK helpers: generate_presigned_post (Python) and createPresignedPost (JavaScript v3).

S3 presigned URL compared with CloudFront signed URL

Exam signals

  • "Browser or mobile client uploads directly to S3 without AWS credentials" → backend returns a presigned PUT URL.
  • "Backend must force the encryption type or content type of client uploads" → sign those headers into the URL.
  • "URL fails before ExpiresIn" → it was signed with temporary credentials that expired.
  • "Share a private file for 3 days from the CLI" → aws s3 presign --expires-in 259200 with IAM user credentials.
  • "HTML form upload, limit the file size and the key prefix" → presigned POST with content-length-range and starts-with.
  • "Private content for paying users, served through CloudFront" → CloudFront signed URLs or signed cookies, with OAC on the bucket.

Encryption options and enforcement

Comparison

OptionWho manages the keyNotes
SSE-S3 (AES256)Amazon S3Default for all new uploads since January 5, 2023. No extra cost.
SSE-KMS (aws:kms)AWS KMS: AWS managed key aws/s3 or a customer managed keyKey policy control, CloudTrail record of key use, KMS request charges. See the SSE-KMS topic.
DSSE-KMS (aws:kms:dsse)AWS KMSTwo layers of encryption. S3 Bucket Keys are not supported.
SSE-CYou. You send the key with each request.S3 never stores the key. Since April 2026, disabled by default for new general purpose buckets and for existing buckets in accounts with no SSE-C objects.
Client-side encryptionYouEncrypt before upload, for example with the Amazon S3 Encryption Client. S3 never sees plaintext.

Key facts

  • Server-side encryption encrypts object data, not object metadata.
  • Default bucket encryption (PutBucketEncryption) applies when an upload does not specify encryption. A request header can choose a different supported type.
  • To encrypt an existing object with a new setting, copy the object onto itself with CopyObject.
  • For SSE-KMS objects, do not send encryption headers on GET or HEAD. S3 returns HTTP 400.

SSE-C

  • Send the algorithm (AES256), the base64 key, and the base64 MD5 of the key with each PUT and GET.
  • You must use HTTPS. S3 rejects SSE-C requests over HTTP.
  • If you lose the key, you lose the object. The console does not support SSE-C uploads.
  • Since April 2026, S3 blocks SSE-C on new general purpose buckets and on existing buckets in accounts with no SSE-C objects. Older study material does not have this rule. A blocked request gets HTTP 403 AccessDenied. To allow it, set BlockedEncryptionTypes to NONE with PutBucketEncryption.

Enforce encryption with a bucket policy

  • Encryption in transit: deny all actions when aws:SecureTransport is false.
  • Require SSE-KMS: deny s3:PutObject when s3:x-amz-server-side-encryption-aws-kms-key-id is null.
  • Require one specific KMS key: use the s3:x-amz-server-side-encryption-aws-kms-key-id condition with the full key ARN.
  • A deny policy rejects uploads that do not meet the rule. Default encryption encrypts uploads that send no header. Use the policy to reject, and default encryption to encrypt without client changes.

Exam signals

  • "Audit each use of the key, control rotation and key access" → SSE-KMS with a customer managed key.
  • "Data must be encrypted before it leaves the application" → client-side encryption.
  • "Company must supply and keep its own keys, no KMS" → SSE-C (enable it on new buckets first).
  • "Deny any request that does not use HTTPS" → aws:SecureTransport false in a deny statement.
  • "Old exam text says objects are not encrypted by default" → out of date. SSE-S3 applies to all new uploads.

References: SSE-KMS (requiring encryption), SSE-C (April 2026 default), Client-side encryption. Lab: Lab 3.4 Encryption variants.

SSE-KMS permissions, Bucket Keys, and cross-account access

Permissions

OperationKMS permission on the key
PutObject with SSE-KMSkms:GenerateDataKey
GetObject of an SSE-KMS objectkms:Decrypt
Multipart upload with SSE-KMSkms:GenerateDataKey and kms:Decrypt
  • The caller needs the S3 permission and the KMS permission. An S3 allow alone does not decrypt the object.
  • The KMS key must be in the same Region as the bucket. S3 supports only symmetric encryption KMS keys.
  • S3 uses envelope encryption: KMS creates a data key, S3 encrypts the object with it, and S3 stores the encrypted data key with the object.

Cross-account access

  • You cannot share objects encrypted with the AWS managed key aws/s3 across accounts. Use a customer managed key.
  • The key policy of the customer managed key must allow the other account. The bucket policy must also allow the other account. The principal in the other account needs an IAM policy for S3 and KMS.
  • Use the full key ARN, not an alias. An alias resolves in the account of the requester.
  • KMS counts cross-account requests against the quota of the calling account.

S3 Bucket Keys

  • A Bucket Key is a short-lived bucket-level key from KMS. S3 uses it to create data keys, so S3 calls KMS less often.
  • Bucket Keys can reduce KMS request costs by up to 99 percent. No client changes are necessary.
  • Bucket Keys apply to new objects only. To use one for an existing object, copy the object.
  • With a Bucket Key, the encryption context is the bucket ARN, not the object ARN. Update IAM or key policies that use the object ARN as encryption context.
  • With a Bucket Key, CloudTrail shows fewer KMS events, and they show the bucket ARN.

Throttling

  • Each SSE-KMS upload or download makes a KMS request (without a Bucket Key). These requests count toward the shared KMS request quota of the account in the Region.
  • Over the quota, KMS throttles the requests (ThrottlingException). Fix with Bucket Keys, or request a quota increase.

Exam signals

  • "KMS costs are high, or KMS throttles S3 requests" → enable S3 Bucket Keys.
  • "Small uploads work, multipart uploads get AccessDenied" → add kms:Decrypt.
  • "Other account gets AccessDenied for SSE-KMS objects" → customer managed key with a key policy for that account, and a bucket policy.
  • "Key policy uses the object ARN in encryption context, access fails after a change" → Bucket Key changed the context to the bucket ARN.

References: SSE-KMS permissions and cross-account use, S3 Bucket Keys, KMS request quotas. Lab: Lab 3.4 Encryption variants.

Bucket policies, Object Ownership, and access points

Policy evaluation

  • Access to S3 uses IAM identity policies, bucket policies, access point policies, and (when enabled) ACLs.
  • In the same account, an allow in the IAM policy or in the bucket policy is enough. An explicit deny in any policy wins.
  • Across accounts, the bucket policy (or access point policy) must allow the other account, and the IAM policy in the other account must allow the action.
  • Bucket ARN (arn:aws:s3:::bucket) is for bucket actions such as s3:ListBucket. Object ARN (arn:aws:s3:::bucket/*) is for object actions such as s3:GetObject.

Object Ownership and ACLs

SettingBehavior
Bucket owner enforced (default)ACLs are disabled. The bucket owner owns every object. Policies control all access.
Bucket owner preferredACLs are enabled. The bucket owner owns new objects written with the bucket-owner-full-control canned ACL.
Object writerACLs are enabled. The uploading account owns the object.
  • With ACLs disabled, a PUT with an ACL other than bucket owner full control fails with AccessControlListNotSupported.
  • AWS recommends that you keep ACLs disabled and use policies.

Block Public Access

  • Block Public Access settings are on by default for new buckets. They override policies and ACLs that grant public access.
  • You can set them on the account, the bucket, and each access point.

Access points and VPC access

  • An access point is a named endpoint with its own access point policy. Use access points to manage access to a shared dataset for many applications.
  • You can configure an access point to accept requests only from a VPC.
  • From a VPC, use a gateway endpoint for S3 so traffic does not use the internet.
  • To allow only VPC traffic, deny requests in the bucket policy when aws:SourceVpce (or aws:SourceVpc) does not match. aws:SourceIp does not work for requests through a VPC endpoint.

Exam signals

  • "Another account uploads, the bucket owner must own the objects, no ACLs" → Bucket owner enforced.
  • "Many applications share one bucket, the bucket policy is too large" → one access point for each application.
  • "Only allow access from our VPC endpoint" → bucket policy deny with aws:SourceVpce.
  • "Public bucket policy is rejected when saved" → Block Public Access is on.

References: Object Ownership, Block Public Access, Access points, Network condition keys. Lab: Lab 3.1 Bucket basics.

Static websites, CloudFront OAC, and CORS

Static website hosting

  • Website endpoint: http://<bucket>.s3-website-<region>.amazonaws.com or http://<bucket>.s3-website.<region>.amazonaws.com, by Region.
  • Configure an index document and an optional error document. The website endpoint supports redirects.
  • The website endpoint serves only publicly readable content. Turn off Block Public Access for the bucket and add a bucket policy that allows s3:GetObject to everyone.
  • The website endpoint does not support HTTPS or access points. It supports only GET and HEAD on objects.
  • For HTTPS, put Amazon CloudFront in front of the content, or use AWS Amplify Hosting.
  • Requester Pays buckets do not allow access through the website endpoint.

CloudFront with origin access control (OAC)

  • OAC lets CloudFront send signed requests to a private S3 bucket. The bucket stays private, and Block Public Access can stay on.
  • The bucket policy allows the service principal cloudfront.amazonaws.com, with a condition AWS:SourceArn equal to the distribution ARN.
  • For SSE-KMS objects, the KMS key policy must also allow cloudfront.amazonaws.com for that distribution.
  • AWS recommends OAC instead of the legacy origin access identity (OAI). OAI does not support SSE-KMS, dynamic requests (PUT, POST, DELETE), or newer Regions.
  • OAC works with the S3 REST endpoint, not with a website endpoint. A website endpoint is a custom origin.
  • With OAC, keep Object Ownership at Bucket owner enforced (the default).

CORS

  • A browser blocks JavaScript requests to a different origin unless the server allows it. Configure CORS on the bucket that receives the requests.
  • Rule elements: AllowedOrigins, AllowedMethods (GET, PUT, POST, DELETE, HEAD), AllowedHeaders, ExposeHeaders, MaxAgeSeconds.
  • A configuration can have up to 100 rules. The console accepts only JSON.
  • S3 uses the first rule that matches the origin, the method, and the requested headers.
  • CORS does not grant permission. Policies and ACLs still apply.
  • To read a response header in JavaScript (for example ETag in a browser multipart upload), list it in ExposeHeaders.

Exam signals

  • "Browser shows a CORS error when the page calls the bucket" → CORS configuration on the target bucket.
  • "Static site must use HTTPS and a custom domain" → CloudFront in front of S3.
  • "Users must reach the files only through CloudFront, bucket stays private" → OAC and a bucket policy for the distribution.
  • "CloudFront with OAC returns 403 for SSE-KMS objects" → add the distribution to the KMS key policy.
  • "Website returns 403 for every page" → objects are not public: Block Public Access or a missing bucket policy.

References: Website endpoints, CORS, CORS configuration elements, CloudFront OAC. Lab: Lab 3.1 Bucket basics.

Event notifications and EventBridge

Direct event notifications

  • Destinations: Amazon SNS topic, Amazon SQS queue, AWS Lambda function, and Amazon EventBridge.
  • SQS FIFO queues are not supported as a direct destination. Use EventBridge to reach a FIFO queue.
  • Delivery is at least once. Events usually arrive in seconds, but can take a minute or longer. Make consumers idempotent.
  • S3 invokes Lambda asynchronously. The function resource-based policy must allow s3.amazonaws.com.
  • The SQS queue policy or SNS topic policy must allow S3 to send messages.
  • Event types include s3:ObjectCreated:* (Put, Post, Copy, CompleteMultipartUpload), s3:ObjectRemoved:*, restore, replication, lifecycle, and tagging events. s3:ObjectCreated:Put alone misses copies, POST uploads, and multipart uploads.
  • The message has a Records array with the bucket name and the object key. It does not contain the object data.

Filters

  • Filter only by key prefix and key suffix. Wildcards (*) are not allowed.
  • For the same event type, rules cannot overlap. Two rules with the same prefix fail unless their suffixes do not overlap.
  • Rules for different event types can overlap.
  • To send one event to several consumers, send it to an SNS topic (fan-out) or use EventBridge.

EventBridge

  • Turn on EventBridge for the bucket. S3 then sends all supported events to the default event bus. You do not choose event types on the bucket.
  • EventBridge rules filter on any field, for example object size or key patterns, and send to many target types.
  • Event format: source is aws.s3, detail-type is for example Object Created.

Loops

  • If the function writes to the bucket that invokes it, it can invoke itself in a loop. Use a second bucket, or limit the trigger to an input prefix.

Exam signals

  • "Several services must react to each upload" → SNS fan-out or EventBridge.
  • "Filter on object size or on a pattern in the middle of the key" → EventBridge rule.
  • "Send S3 events to a FIFO queue" → EventBridge.
  • "Function processed the same upload twice" → at-least-once delivery. Make the code idempotent.
  • "Function runs again and again after it writes its output" → write to another bucket or prefix.

References: Event notifications, Key name filtering, Using EventBridge. Lab: Lab 3.6 Event notifications.

S3 Object Lambda

Availability

  • Since November 7, 2025, S3 Object Lambda is available only to existing customers and to some AWS Partner Network partners.
  • AWS alternatives: invoke Lambda through CloudFront, API Gateway, or a function URL, or process the data in the client.
  • The exam guide was written before this change. Learn how Object Lambda works, but expect current AWS designs to use the alternatives.

Key facts

  • Object Lambda runs your Lambda function on GET, HEAD, and LIST requests to change the data that S3 returns. The stored object does not change.
  • An Object Lambda Access Point uses a standard access point (the supporting access point) to get the data.
  • Use cases: redact PII, convert formats, resize or watermark images, filter rows.
  • Object Lambda does not change PUT or DELETE. To change data on write, use an event notification and a function.

The GetObject function

  1. Read getObjectContext from the event: inputS3Url, outputRoute, and outputToken.
  2. Download the original object from inputS3Url. It is a presigned URL.
  3. Transform the data.
  4. Call WriteGetObjectResponse with RequestRoute, RequestToken, and the new body.
  • The execution role needs s3-object-lambda:WriteGetObjectResponse (managed policy AmazonS3ObjectLambdaExecutionRolePolicy).
  • If the function returns before it calls WriteGetObjectResponse, the caller gets HTTP 500. S3 ignores the return value of the function.
  • The function has up to 60 seconds to send the complete response.

Exam signals

  • "Different applications need different views of the same object, no copies" → Object Lambda (existing customers), or Lambda behind CloudFront or API Gateway.
  • "Clients get 500 errors from the Object Lambda Access Point" → the function did not call WriteGetObjectResponse.
  • "Transform data when it is uploaded" → not Object Lambda. Use an ObjectCreated event.
