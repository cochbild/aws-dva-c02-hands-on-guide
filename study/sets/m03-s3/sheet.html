Buckets, objects, consistency, and request rates

Remember

  • An S3 bucket is in one AWS Region. Objects stay in that Region unless you copy or replicate them.
  • By default, a general purpose bucket name must be unique across all AWS accounts in the partition.
  • You cannot change the name or the Region of a bucket after you create the bucket.
  • User-defined object metadata uses the x-amz-meta- prefix.
  • All S3 buckets and objects are private by default.
  • Block Public Access is on by default for new buckets.
  • Use ListObjectsV2 for new code, not the older ListObjects.
  • ListObjectsV2 returns up to 1,000 keys in each response.
  • When IsTruncated is true, send NextContinuationToken as ContinuationToken in the next list request.
  • Use HeadObject to read metadata or to check that an object exists, without the download of the body.
  • S3 Select (SelectObjectContent) is not available to new customers. Do not choose S3 Select for a new design.
  • S3 gives strong read-after-write consistency for PUT and DELETE of objects in all Regions. Older study material says S3 is eventually consistent.
  • A GET or LIST that starts after a successful write returns the new data, so code needs no delay or retry loop.
  • An update to one S3 key is atomic: a reader gets the old object or the new object, never a mix.
  • S3 does not lock objects: when two PUT requests to one key occur together, the latest timestamp wins with no error.
  • To stop an overwrite of an existing key, send If-None-Match: * on PutObject or CompleteMultipartUpload.
  • A conditional write to an existing key fails with HTTP 412 Precondition Failed, and S3 keeps the existing object.
  • Bucket configurations are eventually consistent. Wait 15 minutes after you first enable versioning before you write objects.
  • Each prefix supports at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second.
  • A bucket has no limit on the number of prefixes.
  • A bucket policy has a maximum size of 20 KB.
  • S3 durability is 99.999999999% (11 nines) for all storage classes except Reduced Redundancy.
  • While S3 scales, requests above the current capacity fail with HTTP 503 (Slow Down). Retry with exponential backoff.
  • To get more total throughput, spread keys across more prefixes. Example: 10 prefixes give 55,000 reads per second.

Exam signals

  • "Read the object immediately after the PUT returns" → S3 is strongly consistent. No delay or retry loop is necessary.
  • "503 Slow Down at high request rates" → more prefixes. The request rate limit applies to each prefix.
  • "503 Slow Down at high request rates" → retry with exponential backoff. The 503 errors stop when S3 finishes scaling.
  • "Do not overwrite the object if the key exists" → conditional write with If-None-Match: *. S3 returns 412 if the key exists.

Explanation

Key facts

  • A bucket is in one AWS Region. Objects do not leave the Region unless you copy or replicate them.
  • By default, a general purpose bucket name must be unique across all AWS accounts in the partition. A partition is a group of Regions, for example aws (standard Regions), aws-cn (China Regions), and aws-us-gov (AWS GovCloud (US)).
  • You cannot change the name or the Region after you create the bucket.
  • An object has a key, data, and metadata. User-defined metadata uses the x-amz-meta- prefix.
  • All buckets and objects are private by default. Block Public Access is on by default for new buckets.
  • Use ListObjectsV2 for new code. It is the current version of the list API and replaces the older ListObjects.
  • Use HeadObject to read the metadata (for example size and content type) without the download of the body. It is the low-cost way to check that an object exists.
  • ListObjectsV2 returns up to 1,000 keys in each response. If IsTruncated is true, send the NextContinuationToken value as ContinuationToken in the next request.
  • Amazon S3 Select (SelectObjectContent) is no longer available to new customers. Do not choose it for a new design. Older study material shows it as the way to query part of an object.

Consistency

  • S3 gives strong read-after-write consistency for PUT and DELETE of objects, in all Regions. Strong consistency means that a read always sees the latest successful write. A GET or LIST that starts after a successful write returns the new data, so code does not need a delay or a retry loop.
  • An update to one key is atomic. A reader gets the old object or the new object, never a mix.
  • S3 does not lock objects for concurrent writers. If two PUT requests to the same key occur together, the request with the latest timestamp wins. Both requests succeed, so the other write is lost with no error.
  • To stop an overwrite of an existing key, use a conditional write. Send the header If-None-Match: * on PutObject or CompleteMultipartUpload. If an object with that key already exists, S3 rejects the write with HTTP 412 Precondition Failed and keeps the existing object.
  • Bucket configurations are eventually consistent: a change to a bucket setting takes some time to reach all parts of S3. For this reason, AWS recommends that you wait 15 minutes after you first enable versioning before you write objects.
  • Older study material says that S3 is eventually consistent for overwrites and deletes. That rule is out of date.

Storage classes and archive retrieval

Remember

  • S3 Standard is the default storage class when the upload does not specify a class.
  • All S3 storage classes in the comparison table have the same durability: 11 nines.
  • S3 Standard has 99.99% designed availability, no minimum storage duration, and no minimum billable size.
  • S3 Standard-IA has 99.9% availability, a 30-day minimum duration, a 128 KB minimum billable size, and a retrieval fee.
  • S3 One Zone-IA has 99.5% availability, one Availability Zone, a 30-day minimum duration, a 128 KB minimum billable size, and a retrieval fee.
  • S3 Glacier Instant Retrieval gives millisecond access with a retrieval fee, a 90-day minimum duration, and a 128 KB minimum billable size.
  • S3 Glacier Flexible Retrieval has a 90-day minimum duration and needs a restore before a read: minutes to hours.
  • S3 Glacier Deep Archive has a 180-day minimum duration and needs a restore before a read: hours.
  • S3 Intelligent-Tiering has no minimum storage duration and no minimum billable size.
  • The optional Intelligent-Tiering archive tiers need a restore before a read.
  • S3 Intelligent-Tiering and Glacier Instant Retrieval have 99.9% availability. Flexible Retrieval and Deep Archive have 99.99% after restore.
  • S3 bills an object that is smaller than the minimum billable size as if the object were 128 KB.
  • If you delete or move an object before its minimum storage duration, you pay for the rest of that duration.
  • Choose S3 Standard for data read more than once a month, and Standard-IA or One Zone-IA for about once a month.
  • Choose Glacier Instant Retrieval for about once a quarter, Flexible Retrieval for about once a year, and Deep Archive for less than once a year.
  • Glacier Flexible Retrieval and Deep Archive add 40 KB of metadata to each archived object: 32 KB archive rate, 8 KB Standard rate.
  • Intelligent-Tiering moves an object to Infrequent Access after 30 days with no access, and to Archive Instant Access after 90 days.
  • A read moves an Intelligent-Tiering object back to the Frequent Access tier.
  • Intelligent-Tiering has a small monitoring fee for each object and no retrieval fees.
  • Intelligent-Tiering does not monitor objects smaller than 128 KB. Those objects stay in the Frequent Access tier.
  • One Zone-IA data is lost if its Availability Zone is destroyed. Use One Zone-IA only for data that you can create again.
  • A GetObject on a Glacier Flexible Retrieval or Deep Archive object fails with InvalidObjectState until you restore the object.
  • RestoreObject makes a temporary readable copy for a number of days. The storage class of the original object does not change.
  • Expedited retrieval from Glacier Flexible Retrieval takes 1–5 minutes, for objects under 250 MB.
  • Glacier Deep Archive has no Expedited retrieval tier.
  • Standard retrieval (the default) takes 3–5 hours from Flexible Retrieval and within 12 hours from Deep Archive.
  • Bulk retrieval (the lowest cost) takes 5–12 hours from Flexible Retrieval and within 48 hours from Deep Archive.
  • Buy provisioned capacity when Expedited retrievals must always succeed. Without it, S3 can refuse Expedited requests at high demand.

Exam signals

  • "Unknown or changing access pattern, no retrieval fees" → S3 Intelligent-Tiering.
  • "Rarely accessed, but must be available in milliseconds" → S3 Glacier Instant Retrieval.
  • "Archive for years, 48 hours to restore is acceptable, lowest cost" → S3 Glacier Deep Archive with Bulk retrieval.
  • "Need a few archived files in minutes" → Glacier Flexible Retrieval with Expedited retrieval.
  • "Data can be created again, lowest cost infrequent access" → S3 One Zone-IA. It costs less because it uses one Availability Zone, and the data is lost if that zone is lost.

Lifecycle rules

Remember

  • A lifecycle rule has a filter (prefix, tags, object size, or a combination) and one or more actions.
  • A lifecycle Transition action moves objects to a colder storage class.
  • A lifecycle Expiration action deletes objects.
  • For old versions in a versioned bucket, use NoncurrentVersionTransition and NoncurrentVersionExpiration.
  • NewerNoncurrentVersions (1 to 100) keeps that number of recent noncurrent versions.
  • S3 deletes a noncurrent version only when both NoncurrentDays and NewerNoncurrentVersions are exceeded.
  • In a versioned bucket, Expiration on the current version adds a delete marker and does not remove data.
  • You pay for a noncurrent version until a NoncurrentVersionExpiration action deletes the version.
  • An expired object delete marker is a delete marker with no noncurrent versions.
  • An expired object delete marker stays after its old versions expire and has a minimal storage charge.
  • To remove expired object delete markers, set ExpiredObjectDeleteMarker to true.
  • ExpiredObjectDeleteMarker cannot be in the same rule as Days. Put ExpiredObjectDeleteMarker in a separate rule.
  • AbortIncompleteMultipartUpload deletes the parts of incomplete multipart uploads after a number of days.
  • Without AbortIncompleteMultipartUpload, you pay for incomplete upload parts until someone aborts the upload.
  • A rule with AbortIncompleteMultipartUpload cannot use a tag filter.
  • Lifecycle transitions go only from warmer classes to colder classes.
  • A lifecycle rule cannot move an object from S3 Glacier Deep Archive to another class.
  • Lifecycle transitions are asynchronous: an object can change class some time after the rule date.
  • Since September 2024, lifecycle rules do not transition objects smaller than 128 KB by default. Add ObjectSizeGreaterThan to transition them.
  • Since July 2026, new rules can transition objects to Standard-IA or One Zone-IA immediately. Older study material says 30 days in Standard first.
  • The 30-day minimum storage charge for Standard-IA and One Zone-IA still applies to lifecycle transitions.
  • One lifecycle rule cannot transition an object out of a class before the minimum storage duration of that class.
  • A rule that moves objects to Glacier Instant Retrieval on day 4 can move them again on day 94 or later.
  • When lifecycle actions conflict on the same day, permanent deletion wins over transition.
  • When lifecycle actions conflict on the same day, transition wins over creation of a delete marker.
  • When an object qualifies for Glacier Flexible Retrieval and Standard-IA, S3 chooses Glacier Flexible Retrieval.

Exam signals

  • "Storage cost grows, but the object list does not show the data" → add AbortIncompleteMultipartUpload. S3 bills the parts of incomplete multipart uploads, but ListObjectsV2 does not show them.
  • "Delete old versions 30 days after they become noncurrent" → NoncurrentVersionExpiration with NoncurrentDays 30.
  • "Small objects do not transition" → the 128 KB default. Add an object size filter.
  • "Move, then delete on a schedule, with no code" → one lifecycle rule with transition and expiration actions.

Explanation

Key facts

  • A lifecycle rule has a filter (prefix, tags, object size, or a combination) and one or more actions.
  • Transition actions move objects to a colder storage class. Expiration actions delete objects.
  • For a versioned bucket, use NoncurrentVersionTransition and NoncurrentVersionExpiration for old versions.
  • NewerNoncurrentVersions (1 to 100) keeps that number of recent noncurrent versions. S3 deletes a noncurrent version only when both the NoncurrentDays value and the NewerNoncurrentVersions value are exceeded.
  • In a versioned bucket, Expiration on the current version adds a delete marker. It does not remove data. The old data becomes a noncurrent version, and you pay for it until a NoncurrentVersionExpiration action deletes it.
  • An expired object delete marker is a delete marker with no noncurrent versions. They stay after their old versions expire and have a minimal storage charge.
  • Remove expired object delete markers with ExpiredObjectDeleteMarker set to true. You cannot use it with Days in the same rule, because an Expiration with Days already removes expired delete markers when they are old enough.
  • To remove expired object delete markers as soon as they become the only version, use a separate rule with only ExpiredObjectDeleteMarker.
  • AbortIncompleteMultipartUpload deletes the parts of uploads that did not complete after a number of days. Without it, you pay for these parts until someone aborts the upload. A rule with this action cannot use a tag filter.
  • Transitions go in one direction only: from warmer classes (more frequent access, higher storage cost) to colder classes (less frequent access, lower storage cost). A rule cannot move an object from S3 Glacier Deep Archive to another class.
  • Lifecycle transitions are asynchronous: S3 runs them in the background. An object can change class some time after the rule date, not at an exact time.

Rules that changed recently

  • Since September 2024, by default, lifecycle rules do not transition objects smaller than 128 KB. To transition them, add an object size filter such as ObjectSizeGreaterThan.
  • Since July 2026, new lifecycle rules can transition objects to S3 Standard-IA or S3 One Zone-IA on the day that you create them. Older study material says that objects must stay 30 days in S3 Standard first. The 30-day minimum storage charge for the IA classes still applies.
  • One rule cannot transition an object out of a class before the minimum storage duration of that class. Example: a rule moves objects to Glacier Instant Retrieval (90-day minimum) on day 4. The next transition in that rule, to Deep Archive, must be on day 94 or later.

When actions conflict on the same day

  • Permanent deletion wins over transition.
  • Transition wins over creation of a delete marker.
  • If an object qualifies for S3 Glacier Flexible Retrieval and S3 Standard-IA, S3 chooses S3 Glacier Flexible Retrieval.
  • Example: one rule moves logs/ objects to S3 Standard-IA after 365 days, and another rule expires the same objects after 365 days. S3 expires the objects, because a change of storage class has no value for an object that S3 deletes.

Versioning, MFA Delete, and Object Lock

Remember

  • An S3 bucket is unversioned (the default), versioning-enabled, or versioning-suspended.
  • After you enable versioning, a bucket can never return to unversioned. You can only suspend versioning.
  • In a versioning-suspended bucket, each new PUT, POST, or copy gets version ID null and overwrites the existing null version.
  • In a versioning-suspended bucket, older versions with real version IDs stay.
  • Objects that existed before you enabled versioning have the version ID null.
  • Each S3 version is a full object, and you pay for the storage of every version.
  • A DELETE without a version ID adds a delete marker, which becomes the current version. The data stays.
  • To restore a deleted object in a versioned bucket, delete the delete marker.
  • To delete a version permanently, send a DELETE with the version ID.
  • MFA Delete requires an MFA code to permanently delete a version or to change the versioning state.
  • Only the bucket owner (root account) can enable MFA Delete.
  • You cannot enable MFA Delete in the console. Use the CLI (put-bucket-versioning --mfa) or the API.
  • You cannot use MFA Delete with lifecycle configurations.
  • Object Lock stores object versions as write-once-read-many (WORM) and works only with versioning enabled.
  • You can enable Object Lock when you create a bucket or on an existing bucket.
  • After you enable Object Lock, you cannot disable Object Lock or suspend versioning.
  • Object Lock protects one object version, not the key. A new PUT to the same key still creates a new version.
  • A DELETE without a version ID on a locked object still adds a delete marker. The locked version stays unchanged.
  • Each Object Lock retention period uses compliance mode or governance mode.
  • In compliance mode, no user can delete or overwrite the version, including the root user.
  • In compliance mode, you cannot shorten the retention period or change the mode.
  • In governance mode, users with s3:BypassGovernanceRetention can delete or change the lock.
  • A governance mode bypass request must include the x-amz-bypass-governance-retention:true header.
  • A legal hold has no end date. A legal hold stays until a user with s3:PutObjectLegalHold removes it.
  • A legal hold is independent of the retention period.
  • Choose compliance mode when a regulation says that nobody may delete the data for a fixed time.
  • Choose governance mode when most users must not delete the data, but a few administrators need to override a lock.
  • Choose a legal hold when the end date is not known, for example during an audit or a lawsuit.

Exam signals

  • "Recover from accidental deletes and overwrites" → versioning.
  • "Restore a deleted object in a versioned bucket" → delete the delete marker.
  • "Require MFA to permanently delete versions" → MFA Delete, enabled by the root user with the CLI.
  • "No one, not even root, can delete for 7 years" → Object Lock compliance mode.
  • "Protect until the audit ends, end date unknown" → legal hold, because it has no end date and stays until someone removes it.

Explanation

Versioning

  • A bucket is in one of three states: unversioned (default), versioning-enabled, or versioning-suspended.
  • After you enable versioning, the bucket can never return to unversioned. You can only suspend versioning.
  • In a versioning-suspended bucket, each new PUT, POST, or copy gets the version ID null. It overwrites an existing null version of the key, and the data of that null version is lost. Older versions with real version IDs stay.
  • Objects that existed before you enabled versioning have the version ID null.
  • Each version is a full object. You pay for the storage of every version.
  • A DELETE without a version ID adds a delete marker. The delete marker becomes the current version. The data stays.
  • To restore the object, delete the delete marker. To delete a version permanently, send a DELETE with its version ID.

MFA Delete

  • MFA Delete requires an MFA code to permanently delete a version or to change the versioning state.
  • Only the bucket owner (root account) can enable MFA Delete.
  • You cannot enable MFA Delete in the console. Use the AWS CLI (put-bucket-versioning --mfa) or the API.
  • You cannot use MFA Delete with lifecycle configurations.

Object Lock

  • Object Lock stores object versions as write-once-read-many (WORM): after S3 writes a version, nobody can overwrite or delete it until the lock ends.
  • Object Lock works only with versioning enabled.
  • You can enable Object Lock when you create a bucket or on an existing bucket. After you enable it, you cannot disable Object Lock or suspend versioning.
  • A lock protects one object version, not the key. A new PUT to the same key still succeeds and creates a new version.
  • A DELETE without a version ID still adds a delete marker. The locked version stays unchanged.
  • A retention period is a fixed time (a retain-until date) during which the version stays locked. Each retention period uses compliance mode or governance mode.

Replication

Remember

  • S3 replication copies objects asynchronously to one or more destination buckets.
  • Replication destination buckets can be in the same account or in different accounts.
  • Cross-Region Replication (CRR) copies objects to a bucket in another Region.
  • Choose CRR for disaster recovery, for lower latency in another Region, or for compute in a second Region.
  • Same-Region Replication (SRR) copies objects to a bucket in the same Region.
  • Choose SRR to collect logs into one bucket, to copy production data to a test account, or for data sovereignty.
  • SRR has no data transfer charge.
  • Replication requires versioning on the source bucket and on each destination bucket.
  • If you disable versioning on a destination bucket later, replication fails and source objects get the status FAILED.
  • S3 replication needs an IAM role with permission to replicate.
  • For a cross-account destination, the destination bucket policy must allow the source owner.
  • Live replication does not copy objects that existed before you added the rule.
  • Use S3 Batch Replication to copy existing objects and objects that failed to replicate.
  • If the source bucket uses Object Lock, the destination buckets must also use Object Lock.
  • S3 Replication Time Control (RTC) replicates 99.99 percent of new objects within 15 minutes, with an SLA.
  • Without RTC, replication has no time guarantee, and a large object can take hours.
  • Replication can write to a different storage class, for example S3 Glacier Deep Archive for a rarely read backup.

Exam signals

  • "Copy existing objects to the new destination" → S3 Batch Replication.
  • "Replicate within 15 minutes with an SLA" → S3 Replication Time Control.
  • "Replication setup fails" → check versioning on both buckets and the replication role.

Explanation

Key facts

  • Replication copies objects asynchronously to one or more destination buckets: the write to the source returns first, and S3 copies the object later.
  • The buckets can be in the same account or in different accounts.
  • Cross-Region Replication (CRR) copies to a bucket in another Region. Choose CRR when a rule requires a copy far from the source (disaster recovery), when users in another Region need lower latency, or when compute in a second Region must read the data.
  • Same-Region Replication (SRR) copies to a bucket in the same Region. Choose SRR to collect logs from several buckets into one bucket, to copy production data into a test account, or when the data must not leave the Region (data sovereignty).
  • SRR has no data transfer charge.
  • Versioning must be enabled on the source and on each destination bucket. If you disable versioning on a destination bucket later, replication fails and the source objects get the replication status FAILED.
  • S3 needs an IAM role with permission to replicate.
  • For a cross-account destination, the destination bucket policy must allow the source owner.
  • Live replication does not copy objects that existed before you added the rule. Use S3 Batch Replication (a one-time S3 Batch Operations job) for existing objects and for objects that failed.
  • If the source bucket uses Object Lock, the destination buckets must also use Object Lock.
  • S3 Replication Time Control (RTC) replicates 99.99 percent of new objects within 15 minutes, backed by a service level agreement (SLA). Without RTC, replication has no time guarantee, and a large object can take hours.
  • You can replicate into a different storage class, for example S3 Glacier Deep Archive in the destination. Use this for a backup copy that you expect to read rarely.

Multipart upload and Transfer Acceleration

Remember

  • A single PutObject uploads an object of up to 5 GB.
  • The S3 console uploads an object of up to 160 GB.
  • Multipart upload supports objects up to 50 TB (48.8 TiB). Older study material says 5 TB.
  • A multipart upload has 1 to 10,000 parts.
  • Each multipart part is 5 MiB to 5 GiB. The last part has no minimum size.
  • Consider multipart upload for objects of 100 MB or larger.
  • CreateMultipartUpload returns an UploadId.
  • UploadPart sends each part, in parallel and in any order. Each part returns an ETag.
  • CompleteMultipartUpload sends the part numbers and ETags. S3 builds the object in part-number order.
  • AbortMultipartUpload stops the upload and deletes the parts.
  • An incomplete multipart upload has no expiry. You pay for the parts until you complete or abort the upload.
  • ListObjectsV2 does not show the parts of incomplete uploads. ListMultipartUploads shows them.
  • Add an AbortIncompleteMultipartUpload lifecycle rule so that S3 deletes incomplete uploads for you.

Remember

  • SSE-S3 (AES256) is the default for all new uploads since January 5, 2023, at no extra cost.

  • SSE-KMS adds KMS request charges.
  • DSSE-KMS (aws:kms:dsse) gives two independent layers of encryption, for compliance rules that require multilayer encryption.
  • DSSE-KMS costs more than SSE-KMS.
  • DSSE-KMS does not support S3 Bucket Keys.
  • With SSE-C, you send the key with each request, and S3 never stores the key.

  • Choose SSE-KMS to control key access with a key policy, to see each key use in CloudTrail, or to disable the key.
  • Choose SSE-C when the company must keep its own keys outside AWS.
  • Choose client-side encryption when AWS must never receive the plaintext.
  • Server-side encryption encrypts object data, not object metadata.
  • Default bucket encryption applies when an upload does not specify encryption. A request header can choose a different supported type.
  • To encrypt an existing object with a new setting, copy the object onto itself with CopyObject.
  • Do not send encryption headers on GET or HEAD of an SSE-KMS object. S3 returns HTTP 400.

SSE-KMS permissions, Bucket Keys, and cross-account access

Remember

  • PutObject with SSE-KMS needs kms:GenerateDataKey on the key.
  • GetObject of an SSE-KMS object needs kms:Decrypt on the key.
  • A multipart upload with SSE-KMS needs kms:GenerateDataKey and kms:Decrypt.
  • Without kms:Decrypt, small SSE-KMS uploads work, but multipart uploads fail with AccessDenied.
  • The caller of an SSE-KMS operation needs the S3 permission and the KMS permission. An S3 allow alone does not decrypt.
  • The KMS key for SSE-KMS must be in the same Region as the bucket.
  • S3 supports only symmetric encryption KMS keys.
  • S3 uses envelope encryption: a data key encrypts the object, and the KMS key encrypts the data key.
  • S3 stores the encrypted data key with the object. To read the object, S3 asks KMS to decrypt the data key.
  • You cannot share objects encrypted with the AWS managed key aws/s3 across accounts. Use a customer managed key.
  • You cannot edit the key policy of an AWS managed key.
  • Cross-account SSE-KMS access needs a key policy, a bucket policy, and an IAM policy for S3 and KMS.
  • Use the full KMS key ARN, not an alias. KMS looks up an alias in the account of the requester.
  • KMS counts cross-account requests against the quota of the calling account.
  • An S3 Bucket Key is a short-lived bucket-level key that S3 uses to create data keys for many objects.
  • S3 Bucket Keys can reduce KMS request costs by up to 99 percent, with no client changes.
  • S3 Bucket Keys apply to new objects only. To use a Bucket Key for an existing object, copy the object.
  • By default, the S3 encryption context is the object ARN.
  • With a Bucket Key, the encryption context is the bucket ARN. Update policies that check the object ARN.
  • With a Bucket Key, CloudTrail shows fewer KMS events, and the events show the bucket ARN.
  • Without a Bucket Key, each SSE-KMS upload or download makes a KMS request against the shared account quota in the Region.
  • Over the quota, KMS throttles requests with ThrottlingException. Fix with Bucket Keys or a quota increase.

Bucket policies, Object Ownership, and access points

Remember

  • Access to S3 uses IAM identity policies, bucket policies, access point policies, and ACLs when ACLs are enabled.
  • In the same account, an allow in the IAM policy or in the bucket policy is enough.
  • An explicit deny in any S3 access policy wins.
  • Across accounts, the bucket policy must allow the other account, and the IAM policy in that account must allow the action.
  • Use the bucket ARN (arn:aws:s3:::bucket) for bucket actions such as s3:ListBucket.
  • Use the object ARN (arn:aws:s3:::bucket/*) for object actions such as s3:GetObject.
  • A policy statement with the wrong ARN does not match the action, and the request gets AccessDenied.
  • Bucket owner enforced (the default) disables ACLs. The bucket owner owns every object.
  • Bucket owner preferred enables ACLs. The bucket owner owns new objects written with the bucket-owner-full-control canned ACL.
  • Object writer enables ACLs. The uploading account owns the object.
  • Keep Bucket owner enforced for new buckets. Choose the other settings only when an existing application still needs ACLs.
  • With ACLs disabled, a PUT with an ACL other than bucket owner full control fails with AccessControlListNotSupported.
  • Block Public Access settings are on by default for new buckets.
  • Block Public Access overrides policies and ACLs that grant public access.
  • S3 rejects a new bucket policy that grants public access while Block Public Access is on.
  • You can set Block Public Access on the account, the bucket, and each access point.
  • An access point is a named endpoint with its own access point policy.
  • A bucket has only one bucket policy, with a 20 KB size limit.
  • When many applications share a bucket, give each application its own access point and policy.
  • An access point with the network origin VPC rejects requests from outside the VPC.
  • You set the network origin of an access point when you create the access point. You cannot change it later.
  • A gateway endpoint for S3 lets private subnets reach S3 with no internet gateway or NAT gateway.
  • To allow only VPC traffic, deny requests when aws:SourceVpce or aws:SourceVpc does not match.
  • aws:SourceIp does not work for requests through a VPC endpoint.

  • An access point is a named endpoint with its own access point policy.

  • From a VPC, use a gateway endpoint for S3 so traffic does not use the internet. A gateway endpoint is an entry in the subnet route tables that sends S3 traffic over the AWS network. Instances in private subnets can then reach S3 with no internet gateway or NAT gateway.

  • The S3 website endpoint supports redirects.
  • The S3 website endpoint serves only publicly readable content.
  • The S3 REST endpoint serves public and private content. The website endpoint serves only public content.
  • For an S3 website, turn off Block Public Access and allow s3:GetObject to everyone. If not, every page returns 403.
  • The S3 website endpoint does not support HTTPS or access points.
  • The S3 website endpoint supports only GET and HEAD on objects.
  • For HTTPS on a static site, put Amazon CloudFront in front of the content, or use AWS Amplify Hosting.
  • Requester Pays buckets do not allow access through the website endpoint. Any request gets 403 Access Denied.
  • Origin access control (OAC) lets CloudFront send signed (SigV4) requests to a private S3 bucket.
  • With OAC, the bucket stays private, Block Public Access stays on, and users cannot go around CloudFront to S3.
  • The OAC bucket policy allows cloudfront.amazonaws.com with AWS:SourceArn equal to the distribution ARN.
  • Without the AWS:SourceArn condition, a CloudFront distribution in another account could read the bucket.
  • For SSE-KMS objects behind OAC, the KMS key policy must allow cloudfront.amazonaws.com for that distribution.
  • AWS recommends OAC instead of the legacy origin access identity (OAI).
  • OAI does not support SSE-KMS, dynamic requests (PUT, POST, DELETE), or newer Regions.
  • OAC works with the S3 REST endpoint, not with a website endpoint.
  • With OAC, keep Object Ownership at Bucket owner enforced (the default).
  • A browser blocks JavaScript requests to a different origin unless the server allows the requests with CORS.
  • Configure CORS on the bucket that receives the cross-origin requests.
  • Before a cross-origin request such as a PUT, the browser sends a preflight OPTIONS request.
  • If no CORS rule matches the preflight, the browser blocks the real request and shows a CORS error.
  • The CORS rule elements are AllowedOrigins, AllowedMethods, AllowedHeaders, ExposeHeaders, and MaxAgeSeconds.
  • AllowedHeaders lists the request headers that the preflight allows.
  • MaxAgeSeconds sets how long the browser caches the preflight response.
  • A CORS configuration can have up to 100 rules.
  • S3 uses the first CORS rule that matches the origin, the method, and the requested headers.
  • CORS does not grant permission. Policies and ACLs still apply.
  • To read a response header such as ETag in JavaScript, list the header in ExposeHeaders.

Exam signals

  • "Browser shows a CORS error when the page calls the bucket" → CORS configuration on the target bucket.
  • "Static site must use HTTPS and a custom domain" → CloudFront in front of S3.
  • "Users must reach the files only through CloudFront, bucket stays private" → OAC and a bucket policy for the distribution.
  • "CloudFront with OAC returns 403 for SSE-KMS objects" → add the distribution to the KMS key policy.
  • "Website returns 403 for every page" → objects are not public: Block Public Access or a missing bucket policy.

Explanation

Static website hosting

  • Website endpoint: http://<bucket>.s3-website-<region>.amazonaws.com or http://<bucket>.s3-website.<region>.amazonaws.com, by Region.
  • Configure an index document and an optional error document. The website endpoint supports redirects.
  • The website endpoint serves only publicly readable content (the REST endpoint serves both public and private content). Turn off Block Public Access for the bucket and add a bucket policy that allows s3:GetObject to everyone. If you do not, every page returns 403.
  • The website endpoint does not support HTTPS or access points. It supports only GET and HEAD on objects.
  • For HTTPS, put Amazon CloudFront in front of the content, or use AWS Amplify Hosting.
  • Requester Pays buckets do not allow access through the website endpoint. S3 must authenticate each request to a Requester Pays bucket to identify and bill the requester, and the website endpoint serves anonymous requests. Any request receives 403 Access Denied.

CloudFront with origin access control (OAC)

  • Origin access control (OAC) lets CloudFront send signed (SigV4) requests to a private S3 bucket. The bucket stays private, and Block Public Access can stay on. Users cannot go around CloudFront to S3, because S3 accepts only the signed CloudFront requests.
  • The bucket policy allows the service principal cloudfront.amazonaws.com, with a condition AWS:SourceArn equal to the distribution ARN. Without this condition, the policy trusts the CloudFront service itself, so a distribution in another account could read the bucket.
  • For SSE-KMS objects, the KMS key policy must also allow cloudfront.amazonaws.com for that distribution, because CloudFront must call kms:Decrypt to read the object for the viewer.
  • AWS recommends OAC instead of the legacy origin access identity (OAI). OAI does not support SSE-KMS, dynamic requests (PUT, POST, DELETE), or newer Regions.
  • OAC works with the S3 REST endpoint, not with a website endpoint. CloudFront treats a website endpoint as a custom origin (an ordinary web server) and does not sign requests to it, so the bucket must be public.
  • With OAC, keep Object Ownership at Bucket owner enforced (the default).

CORS

  • An origin is the scheme, domain, and port of a web page, for example https://app.example.com. A browser blocks JavaScript requests to a different origin unless the server allows it. Configure CORS (cross-origin resource sharing) on the bucket that receives the requests.
  • Before a cross-origin request such as a PUT, the browser sends a preflight OPTIONS request. S3 answers it from the CORS configuration of the bucket. If no rule matches, the browser blocks the real request and shows a CORS error.
  • Rule elements: AllowedOrigins (which pages can call), AllowedMethods (GET, PUT, POST, DELETE, HEAD), AllowedHeaders (request headers allowed in the preflight), ExposeHeaders (response headers that JavaScript can read), and MaxAgeSeconds (how long the browser caches the preflight response).
  • A configuration can have up to 100 rules. The console accepts only JSON.
  • S3 uses the first rule that matches the origin, the method, and the requested headers.
  • CORS does not grant permission. Policies and ACLs still apply.
  • To read a response header in JavaScript (for example ETag in a browser multipart upload), list it in ExposeHeaders.

Event notifications and EventBridge

Remember

  • S3 event notification destinations are SNS topics, SQS queues, Lambda functions, and EventBridge.
  • SQS FIFO queues are not supported as a direct destination. Use EventBridge to reach a FIFO queue.
  • S3 event delivery is at least once, so the same event can arrive two times.
  • S3 events usually arrive in seconds, but can take a minute or longer.
  • Make S3 event consumers idempotent: processing one event two times gives the same result as one time.
  • S3 invokes Lambda asynchronously and does not wait for the function result.
  • The Lambda resource-based policy must allow s3.amazonaws.com, or S3 cannot invoke the function.
  • The SQS queue policy or SNS topic policy must allow S3 to send messages.
  • s3:ObjectCreated:* covers Put, Post, Copy, and CompleteMultipartUpload.
  • Other S3 event types include s3:ObjectRemoved:*, restore, replication, lifecycle, and tagging events.
  • s3:ObjectCreated:Put alone misses copies, POST uploads, and multipart uploads.
  • An S3 event message has a Records array with the bucket name and the object key, not the object data.
  • Direct event notifications filter only by key prefix and key suffix. Wildcards (*) are not allowed.
  • For the same event type, notification rules cannot overlap. S3 rejects the configuration when you save it.
  • Notification rules for different event types can overlap.
  • To send one S3 event to several consumers, use SNS fan-out or EventBridge.
  • With EventBridge turned on, S3 sends all supported events to the default event bus.
  • You do not choose event types on the bucket for EventBridge.
  • EventBridge rules filter on any field, for example object size or key patterns, and send to many target types.
  • An S3 event in EventBridge has source aws.s3 and a detail-type such as Object Created.
  • Choose direct notifications for a prefix or suffix filter and one destination for each event type.
  • Choose EventBridge for filters on other fields, several targets for one event, or an SQS FIFO queue target.
  • A function that writes to the bucket that invokes it runs in a loop. Use a second bucket or a separate input prefix.

Exam signals

  • "Several services must react to each upload" → SNS fan-out or EventBridge.
  • "Filter on object size or on a pattern in the middle of the key" → EventBridge rule, because direct notifications filter only on key prefix and suffix.
  • "Send S3 events to a FIFO queue" → EventBridge.
  • "Function processed the same upload twice" → at-least-once delivery. Make the code idempotent.
  • "Function runs again and again after it writes its output" → write to another bucket or prefix.

Explanation

Direct event notifications

  • Destinations: Amazon SNS topic, Amazon SQS queue, AWS Lambda function, and Amazon EventBridge.
  • SQS FIFO queues are not supported as a direct destination. Use EventBridge to reach a FIFO queue.
  • Delivery is at least once, so the same event can arrive two times. Events usually arrive in seconds, but can take a minute or longer.
  • Make consumers idempotent: processing the same event two times must give the same result as one time. For example, check whether the thumbnail already exists before you create it.
  • S3 invokes Lambda asynchronously: S3 hands the event to Lambda and does not wait for the function result.
  • The function resource-based policy must allow s3.amazonaws.com, or S3 cannot invoke the function.
  • The SQS queue policy or SNS topic policy must allow S3 to send messages.
  • Event types include s3:ObjectCreated:* (Put, Post, Copy, CompleteMultipartUpload), s3:ObjectRemoved:*, restore, replication, lifecycle, and tagging events. s3:ObjectCreated:Put alone misses copies, POST uploads, and multipart uploads.
  • The message has a Records array with the bucket name and the object key. It does not contain the object data.

Filters

  • Filter only by key prefix and key suffix. Wildcards (*) are not allowed.
  • For the same event type, rules cannot overlap. Two rules with the same prefix fail unless their suffixes do not overlap. S3 rejects the configuration when you save it.
  • Rules for different event types can overlap.
  • To send one event to several consumers, send it to an SNS topic or use EventBridge. With SNS fan-out, S3 sends the event once to the topic, and SNS delivers a copy to each subscriber, for example an SQS queue and a Lambda function.

EventBridge

  • Turn on EventBridge for the bucket. S3 then sends all supported events to the default event bus. You do not choose event types on the bucket.
  • EventBridge rules filter on any field, for example object size or key patterns, and send to many target types.
  • Event format: source is aws.s3, detail-type is for example Object Created.
  • Choose direct notifications for a prefix or suffix filter and one destination for each event type.
  • Choose EventBridge when you need filters on other fields, several targets for the same event, or a target that direct notifications do not support, such as an SQS FIFO queue.

Loops

  • If the function writes to the bucket that invokes it, each write creates a new event, and the function invokes itself in a loop. The invocations and the cost grow quickly. Use a second bucket, or limit the trigger to an input prefix that the function does not write to.

S3 Object Lambda

Remember

  • Since November 7, 2025, S3 Object Lambda is available only to existing customers and to some AWS Partner Network partners.
  • Alternatives to Object Lambda: invoke Lambda through CloudFront, API Gateway, or a function URL, or process the data in the client.
  • S3 Object Lambda runs your Lambda function on GET, HEAD, and LIST requests to change the data that S3 returns.
  • Object Lambda does not change the stored object.
  • Applications send requests to an Object Lambda Access Point, which invokes the function.
  • The Object Lambda function reads the original object through a standard access point (the supporting access point).
  • Object Lambda use cases: redact PII, convert formats, resize or watermark images, filter rows.
  • Object Lambda does not change PUT or DELETE. To change data on write, use an event notification and a function.
  • The Object Lambda event has getObjectContext with inputS3Url, outputRoute, and outputToken.
  • The inputS3Url value is a presigned URL for the original object.
  • The Object Lambda function calls WriteGetObjectResponse with RequestRoute, RequestToken, and the new body.
  • The execution role needs s3-object-lambda:WriteGetObjectResponse (managed policy AmazonS3ObjectLambdaExecutionRolePolicy).
  • WriteGetObjectResponse is the only way the function sends data back. S3 ignores the function return value.
  • If the function returns before it calls WriteGetObjectResponse, the caller gets HTTP 500.
  • An Object Lambda function has up to 60 seconds to send the complete response.

Exam signals

  • "Different applications need different views of the same object, no copies" → Object Lambda (existing customers), or Lambda behind CloudFront or API Gateway.
  • "Clients get 500 errors from the Object Lambda Access Point" → the function did not call WriteGetObjectResponse.
  • "Transform data when it is uploaded" → not Object Lambda. Use an ObjectCreated event.

Explanation

Availability

  • Since November 7, 2025, S3 Object Lambda is available only to existing customers and to some AWS Partner Network partners.
  • AWS alternatives: invoke Lambda through CloudFront, API Gateway, or a function URL, or process the data in the client.
  • The exam guide was written before this change. Learn how Object Lambda works, but expect current AWS designs to use the alternatives.

Key facts

  • Object Lambda runs your Lambda function on GET, HEAD, and LIST requests to change the data that S3 returns. The stored object does not change.
  • Applications send requests to an Object Lambda Access Point. It invokes your function, and the function reads the original object through a standard access point (the supporting access point).
  • Use cases: redact PII, convert formats, resize or watermark images, filter rows.
  • Object Lambda does not change PUT or DELETE. To change data on write, use an event notification and a function.

The GetObject function

  1. Read getObjectContext from the event: inputS3Url, outputRoute, and outputToken.
  2. Download the original object from inputS3Url. It is a presigned URL.
  3. Transform the data.
  4. Call WriteGetObjectResponse with RequestRoute, RequestToken, and the new body.
  • The execution role needs s3-object-lambda:WriteGetObjectResponse (managed policy AmazonS3ObjectLambdaExecutionRolePolicy).
  • WriteGetObjectResponse is the only way the function sends data back to the caller. S3 ignores the return value of the function. If the function returns before it calls WriteGetObjectResponse, the caller gets HTTP 500.
  • The function has up to 60 seconds to send the complete response.
