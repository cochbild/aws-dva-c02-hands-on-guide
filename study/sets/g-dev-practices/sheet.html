SDK retries and backoff

Key facts

  • The AWS SDKs and the AWS CLI retry failed requests automatically. You do not write a retry loop for single SDK calls.
  • The SDK retries two kinds of errors. A transient error is a temporary failure, so the same request can succeed a moment later: timeouts, connection errors, HTTP 500, 502, 503, 504. A throttling error means that the service rejected the request because the caller sent requests faster than its limit: for example ThrottlingException, TooManyRequestsException, ProvisionedThroughputExceededException, SlowDown.
  • The SDK does not retry most client errors, for example AccessDeniedException, ValidationException, and ResourceNotFoundException. The cause is in the request itself, so a retry sends the same request and gets the same error. Fix the request instead.
  • Exponential backoff: the maximum wait doubles after each failed attempt. A throttled request waits up to 1 second before the first retry and up to 2 seconds before the second retry. The longer waits give the service time to recover.
  • Jitter makes each wait a random value between zero and that maximum. Without jitter, many clients that fail at the same time also retry at the same time, and the retries fail together again. Jitter spreads the retries over time.
  • "Max attempts" counts the first request too. A value of 3 means one request and up to two retries. A value of 1 turns off retries.

Retry modes

ModeBehavior
standardThe same rules in all SDKs. Exponential backoff with jitter. A retry quota (a token bucket) limits retries: each retry spends tokens from a fixed budget, and successful requests put tokens back. When many requests fail for a long time, the budget empties. The SDK then returns errors at once instead of retrying, so the application fails fast and adds no retry load. Default 3 attempts. Default mode in AWS CLI version 2. AWS recommends this mode.
adaptiveStandard mode plus a client-side rate limiter. After throttling responses, it can delay the first attempt of new requests, not only retries. Use it for a client that calls one resource and gets frequent throttling. Do not use it for a client that calls many resources. The limiter applies to all requests from the client, so throttling on one table also slows calls to other tables.
legacyThe older behavior of each SDK. It differs between languages. Default mode in AWS CLI version 1 (5 attempts in total).

Settings

SettingEnvironment variableConfig file key
Retry modeAWS_RETRY_MODEretry_mode
Max attemptsAWS_MAX_ATTEMPTSmax_attempts
  • Precedence: client configuration in code, then environment variable, then ~/.aws/config, then the SDK default.
  • In standard mode, the maximum wait between two attempts is 20 seconds.
  • AWS published updated retry defaults in 2026 (opt-in with AWS_NEW_RETRIES_2026 until they become the default). Older study material and the exam use the values above.
  • With the AWS CLI, add --debug and search the output for "retry" to see retry attempts.

Exam signals

  • "Many clients retry at the same moment and overload the service" → exponential backoff with jitter.
  • "Change retry behavior without a code change" → AWS_MAX_ATTEMPTS or AWS_RETRY_MODE, or the config file. The SDK reads these settings when it creates the client, so the code stays the same.
  • "Client sends to one table and gets throttled often, slow down automatically" → adaptive retry mode, because only adaptive mode delays new requests after throttling. Standard mode delays only retries.
  • "Retry an AccessDeniedException" → wrong. A missing permission does not go away with time, so every retry fails. Fix the permissions.

References: Retry behavior (AWS SDKs and Tools Reference Guide), AWS CLI retries.

Key facts

  • Decide by the error code, not only by the HTTP status. One status can mean different things: a DynamoDB 400 can be ValidationException (do not retry) or ProvisionedThroughputExceededException (retry). The SDK matches the error code first.
  • A 500 on a single-item DynamoDB write (PutItem, UpdateItem, DeleteItem) can mean that the write succeeded. The server can apply the write and then fail before it sends the response. A plain retry of an increment then adds the amount two times. Read the item, or use a condition expression, before you retry.
  • Log the request ID from the error. AWS Support uses it to find the request.

Exam signals

  • "ProvisionedThroughputExceededException at peaks" → retries with exponential backoff (SDK default), because a short peak ends and capacity is free again. If the error continues, add capacity or use on-demand mode.
  • "ConditionalCheckFailedException on a duplicate write" → expected for an idempotent write. The condition failed because the first write already stored the item. Catch it and continue.
  • "Lambda Invoke returns 429" → concurrency limit. Retry with backoff, because concurrency becomes free when running invocations end. Or raise the concurrency.
  • "S3 returns 503 Slow Down" → back off and retry. S3 supports at least 3,500 PUT, COPY, POST, or DELETE requests and 5,500 GET or HEAD requests per second for each prefix. A prefix is the start of the object key, for example logs/2026/. Spread requests across more prefixes to get more total throughput.

References: Error handling with DynamoDB, Which errors are retried, Optimizing Amazon S3 performance (request rates per prefix).

Pagination and batch calls

Pagination tokens

APIResponse fieldSend it back as
Most list APIsNextTokenNextToken
DynamoDB Query and ScanLastEvaluatedKeyExclusiveStartKey
Amazon S3 ListObjectsV2NextContinuationToken (with IsTruncated)ContinuationToken
  • A list call returns one page, which has a maximum size. For example, ListObjectsV2 returns up to 1,000 keys. When more data exists, the response also contains a token (the field in the table above). Send the token in the next request to get the next page. A response without a token is the last page.
  • Code that reads only the first response misses data. It sees no error, only an incomplete result, for example a count of 1,000 for a bucket with 4,200 objects.
  • SDK paginators follow the tokens for you. Use them instead of a manual loop.
  • A DynamoDB page stops at 1 MB of data. A filter expression runs after the read, so a page can have zero items and still have a LastEvaluatedKey. Continue until the response has no LastEvaluatedKey. Do not stop at the first empty page.

AWS CLI pagination options

OptionEffect
(default)The CLI makes as many calls as necessary and returns all items.
--page-sizeFewer items in each API call. The CLI still returns the full list. Use it when calls time out.
--max-itemsThe CLI prints only this number of items and returns a NextToken.
--starting-tokenContinue from the NextToken of a previous command.
--no-paginateThe CLI makes only one call and returns only the first page.

Choose --page-size when you need the complete list but each call times out, because each call then returns less data. Choose --max-items with --starting-token when you want to process a long list in parts, one run at a time.

Batch calls

  • A batch call can partly fail. The call returns success (HTTP 200), but the response lists the failed items. Code that checks only the status loses those items without an error.
  • DynamoDB BatchWriteItem returns UnprocessedItems. BatchGetItem returns UnprocessedKeys. The most likely cause is throttling: a table in the batch does not have enough capacity for all the items.
  • Retry only the unprocessed items, with exponential backoff. An immediate retry is likely to be throttled again.
  • Some SDK high-level clients retry unprocessed items for you, for example the boto3 batch_writer and the DynamoDB Enhanced Client for Java.

Exam signals

  • "The function returns only some of the items" → the code ignores the pagination token. Use a paginator.
  • "list-objects on a large bucket times out in the CLI" → --page-size. Each call then asks for fewer items and completes in time, and the CLI still returns the full list.
  • "BatchWriteItem succeeds but some items are missing" → retry UnprocessedItems with exponential backoff.

References: AWS CLI pagination, DynamoDB batch operations and error handling, ListObjectsV2 (up to 1,000 keys per response).

Idempotency

Key facts

  • An idempotent operation gives the same result when it runs one time or many times.
  • Many event sources deliver at least once: they promise to deliver each event, but they can deliver the same event more than one time. Examples: SQS standard queues, Lambda asynchronous invocation, EventBridge, and SDK retries after a timeout. A handler can run two times for one event. Without idempotency, the second run repeats the action, for example a second card charge.
  • An idempotency key is a value that is the same for every copy of one logical request, for example an order ID or a hash of the payload. The handler uses it to recognize a copy.
  • Record "already done" with a conditional write, for example DynamoDB PutItem with attribute_not_exists(pk). The first write with a key succeeds. A later write with the same key fails with ConditionalCheckFailedException, which means "duplicate: skip the action".
  • Some APIs take a client token. The service remembers the token. When a request arrives again with the same token and parameters, the retry succeeds without a new action (the result can show updated status). Amazon EC2 RunInstances takes ClientToken (up to 64 ASCII characters). DynamoDB TransactWriteItems takes ClientRequestToken.
  • EC2: the same client token with different parameters fails with IdempotentParameterMismatch. A token belongs to one request, so new parameters need a new token.

Powertools for AWS Lambda idempotency utility

  • Stores a record for each idempotency key in a DynamoDB table (partition key attribute id by default).
  • A repeated event returns the saved result. The function code does not run again.
  • Records expire after 1 hour (3,600 seconds) by default. Change it with expires_after_seconds. A duplicate that arrives after the record expired runs the code again. Set the window longer than the longest expected resend delay.
  • event_key_jmespath selects the part of the event that makes the key, for example the order ID in the body. By default, the whole event is the key. Some fields change between copies of one request: a redelivered SQS message has a new receipt handle and receive count, and a message that the producer sends again has a new message ID. A key from the whole event then does not match.
  • A duplicate that arrives while the first run is in progress raises IdempotencyAlreadyInProgressError. The first run has no saved result yet, so the utility stops the copy instead of running the code two times at once.
  • If the function raises an unhandled exception, the utility deletes the record, so a retry can run.

Exam signals

  • "Customers are charged two times when the queue delivers a message again" → idempotency key and a conditional write (or the Powertools idempotency utility).
  • "Retry a launch request after a timeout without a second instance" → ClientToken.
  • "Duplicates with no errors in the logs" → at-least-once delivery. A second delivery is normal behavior, not a failure, so nothing is logged as an error. Make the handler idempotent.

References: Powertools for AWS Lambda (Python) idempotency, Idempotency in Amazon EC2 API requests.

Resilient calls to other services

Key facts

  • Set a timeout on every network call. A call without a timeout can wait until the Lambda function times out. Lambda then stops the function, so your code cannot log the error or react, and you pay for the wait.
  • Retry transient failures a limited number of times, with exponential backoff and jitter. A limit is necessary because retries without a limit can run until the function times out.
  • Retry only operations that are safe to repeat, or make them idempotent first. A retry of an operation that already succeeded, for example a payment, repeats the action.
  • A fallback returns a default or cached answer when a dependency fails. The user gets a reduced result instead of an error (graceful degradation). Example: show popular products when the recommendation service is down.
  • A dead-letter queue (DLQ) is a separate queue that receives messages that failed processing too many times. Failed messages then stop using retries and stay available for later analysis.

Circuit breaker

A circuit breaker is an object between the caller and a dependency. It counts failures and stops calls to a dependency that is down. Use it when a dependency can be down for a long time, not only for a few seconds.

StateBehavior
ClosedCalls go to the dependency. The breaker counts failures.
OpenAfter failures pass a threshold, the breaker trips. Calls fail at once and do not go to the dependency.
Half-openAfter a wait, the breaker lets a test call go through. Success closes the circuit. Failure opens it again.
  • A circuit breaker stops retries that are unlikely to succeed. The caller does not wait for timeouts, and its threads stay free. The failing service gets no extra load while it recovers.
  • AWS sample: a Step Functions workflow stores the circuit status in a DynamoDB table. The status must be in a shared store because every workflow execution must read the same status. After repeated failures, the workflow writes an "open" record with an expiry time. While that record is not expired, calls fail at once. After the expiry time, the workflow ignores the record and calls the service again. DynamoDB Time to Live (TTL) deletes the expired records later.

Where to put retries

  • One SDK call: the SDK retry settings.
  • A step in a workflow: a Step Functions Retry field (IntervalSeconds, MaxAttempts, BackoffRate) and a Catch field. Retry runs the step again with growing waits. Catch sends the workflow to an error-handling state when the retries end. No retry code in the function.
  • Queue consumers: SQS retries for you. A message that the consumer does not delete becomes visible again after the visibility timeout, and the consumer receives it again. After maxReceiveCount receives, SQS moves the message to the dead-letter queue.

Exam signals

  • "A third-party API is down for long periods; stop calling it and fail fast" → circuit breaker. Retries only make each request wait longer during a long outage.
  • "Show cached data when the recommendation service fails" → fallback.
  • "Retry one workflow step with backoff without code" → Step Functions Retry.

References: Circuit breaker pattern, Retry with backoff pattern.

AWS CLI and CloudShell

Profiles and options

  • Files: ~/.aws/credentials (access keys) and ~/.aws/config (Region, output, roles, IAM Identity Center).
  • In config, a named profile section is [profile dev]. In credentials, it is [dev]. If you write [dev] in config, the CLI does not read it as a profile and reports that the profile does not exist.
  • Global options: --profile, --region, --output (json, yaml, yaml-stream, text, table), --debug.
  • --cli-input-json reads all parameters from a JSON file. --generate-cli-skeleton makes a template for that file. Use them for a command with many parameters that you run again and again, or that you keep in source control.

Credential precedence (AWS CLI)

The CLI checks these sources in order and uses the first one that has credentials. It ignores all later sources. Example: old AWS_ACCESS_KEY_ID environment variables override the profile in the credentials file, so commands run with the wrong identity.

  1. Command line options
  2. Environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN, AWS_PROFILE)
  3. Assume role, then assume role with web identity. An assume-role profile sets role_arn and source_profile. The CLI calls AWS STS with the source profile credentials and uses the temporary role credentials that STS returns.
  4. IAM Identity Center (aws configure sso, then aws sso login)
  5. Credentials file
  6. Custom process (the credential_process setting runs an external program that prints credentials)
  7. Config file
  8. Container credentials (Amazon ECS task role)
  9. Amazon EC2 instance profile credentials (from the instance metadata service)

Credentials in code

  • Do not put access keys in code or in environment variables of a function. Access keys are long-term: they work until someone deletes them, so a leaked key stays useful to an attacker. Create the SDK client without keys. The default credential chain is the fixed order of sources that the SDK searches for credentials. On AWS compute, it finds the temporary credentials of the role, which AWS rotates automatically.
  • On AWS compute, use a role: Lambda execution role, ECS task role, EC2 instance profile.
  • On a developer machine, use IAM Identity Center (aws sso login) for short-term credentials.

IMDSv2

  • The instance metadata service (IMDS) is a local endpoint on every EC2 instance at 169.254.169.254. It gives the instance its data, including the temporary credentials of the instance profile role. The SDK reads the credentials from it.
  • IMDSv1 answers any simple GET. IMDSv2 is session-oriented: a client must first get a session token. First send PUT http://169.254.169.254/latest/api/token with the header X-aws-ec2-metadata-token-ttl-seconds.
  • The token lives from 1 second to 6 hours (21,600 seconds). Send it in the X-aws-ec2-metadata-token header on each GET.
  • When IMDSv2 is required (HttpTokens = required), a request without a valid token gets 401 - Unauthorized.
  • The hop limit is the number of network hops that the token response can travel. The default hop limit for the PUT response is 1, or 2 for AMIs registered with ImdsSupport v2.0. A container with its own network (for example Docker bridge mode) is one hop further away. With a limit of 1, the container does not get the token, so its SDK cannot get role credentials. AWS recommends a hop limit of 2 for containers.
  • Current SDK and CLI versions use IMDSv2 automatically. Old versions must be upgraded before you require IMDSv2. Otherwise their requests get 401 and the application has no credentials.

Filtering and checks

FeatureWhere it runsNotes
--filter, --filters, --filter-expressionServer sideThe service returns only matching records. Less data comes over the network.
--query (JMESPath)Client sideThe full response comes to the client first. Runs after server-side filters.

Choose a server-side filter to reduce the data that comes over the network. Choose --query to select or reshape fields in the output, for example only the instance IDs. You can use both in one command.

AWS CloudShell

  • A browser-based shell in the console. It uses the credentials of the console user. The AWS CLI is pre-installed.
  • 1 GB of persistent storage in $HOME for each Region, at no cost.
  • If you do not use CloudShell in a Region for 120 days, AWS deletes the home directory data of that Region.
  • A session ends after 20–30 minutes without keyboard or pointer input.
  • Outbound internet access only. No inbound ports and no public IP address. You cannot host a server in CloudShell that other users reach.

Exam signals

  • "Run CLI commands from the browser with no local install or keys" → CloudShell.
  • "Check permissions to launch an instance without launching it" → --dry-run.
  • "Reduce the data returned for a large list" → server-side filter, not --query. --query runs on the client after the full response arrives.
  • "Developer needs short-term credentials on a laptop" → IAM Identity Center and aws sso login. The credentials expire, so no long-term key stays on the laptop.
  • "Protect instance credentials from SSRF" → require IMDSv2. In server-side request forgery (SSRF), an attacker makes the application send a request to a URL that the attacker chooses. Such a request is usually a simple GET, which IMDSv1 answers. IMDSv2 first needs a PUT request to get a token. The attack usually cannot choose the HTTP method, so it never gets a token.

References: CLI configuration and credentials precedence, CLI filtering, IMDSv2, IMDS options for new instances (hop limit), CloudShell quotas, IMDSv2 and SSRF (AWS Security Blog).

Unit tests and mocks

Key facts

  • A unit test checks your code without calls to real AWS services. It is fast and costs nothing.
  • Keep business logic out of the handler. The handler parses the event and calls plain functions that you can test. A test can then call those functions directly, without a full Lambda event.
  • Inject the SDK client (pass it in as a parameter). A test can then pass a fake client. If the code creates its own client inside the function, a test must patch the SDK module to replace it, which is more fragile. Injection is simpler and works in every language.
  • A mock or stub is a fake object that returns the responses that the test sets. Mock AWS calls with a stub library, for example moto or the botocore Stubber (Python), or aws-sdk-client-mock (JavaScript SDK v3).
  • Test the error paths too: throttling, ConditionalCheckFailedException, and timeouts.

Test events

  • A test event is a JSON payload in the same shape as the real event: API Gateway proxy event, SQS batch, S3 notification, and others.
  • sam local generate-event <service> <event> prints a sample event, for example sam local generate-event s3 put.
  • sam local invoke -e event.json runs the function locally in a container with that event. Docker (or a compatible container runtime) must be installed.
  • sam local start-api runs the API locally for HTTP tests.
  • The Lambda console has private test events and shareable test events. Only the creator can use a private event. Other users in the same account can use a shareable event (they need the EventBridge schema registry permissions), so a team does not create the same event by hand many times.

Exam signals

  • "Test the handler without calls to DynamoDB" → inject the client and use a mock or stub.
  • "Create a sample SQS event for a local test" → sam local generate-event sqs receive-message.
  • "Run the function locally with an event file" → sam local invoke -e.

References: sam local generate-event, sam local invoke, Testing Lambda functions in the console.

Integration tests and event-driven tests

Test deployed code

  • Deploy to a separate test stack. Test against real services there. These tests find problems that mocks hide, for example a missing IAM permission, a wrong resource name, or a wrong event format. A separate stack keeps test data out of production.
  • sam remote invoke sends an event to a deployed resource: a Lambda function, a Step Functions state machine, an SQS queue, or a Kinesis data stream.
  • sam remote test-event (put, get, list, delete) manages shareable test events. They are stored in the Amazon EventBridge schema registry.
  • sam remote invoke --test-event-name uses a shareable test event.
  • The API Gateway console Test feature calls a REST API method before you deploy the API.

Mock APIs

  • An API Gateway mock integration (REST API) returns a response from API Gateway. No backend is called.
  • A mapping template is a template in API Gateway that transforms a request or a response. In a mock integration, the integration request mapping template selects the status code, for example {"statusCode": 200}. The integration response template then sets the body that the client receives.
  • Use it to let front-end teams work before the backend is ready.
  • For your own code, replace an external HTTP dependency with a stub server or a mock in tests.

Event-driven tests

  • Asynchronous flows do not return a result to the caller. Send an event, then poll the result store (for example a DynamoDB table) until the result appears or a timeout ends.
  • EventBridge archive and replay: an archive keeps events from one event bus (indefinitely by default, or for a set number of days). A replay sends them again to the same bus. Use it to process past events again after you fix a bug, or to test new code with real past events. The archive must exist before the events arrive, because only archived events can be replayed.
  • EventBridge adds a replay-name field to each replayed event. A target can use it to recognize a replayed event.
  • Step Functions TestState API tests one state without a deployed state machine. The inspection level sets how much detail the result shows:
    • INFO (default): the state output, or the error.
    • DEBUG: also the data after each processing step (InputPath, Parameters, ResultSelector, ResultPath). Use it to check how a state changes its data.
    • TRACE: also the raw HTTP request and response. It works only for an HTTP Task. Other state types return an error.
  • TestState can mock service integration results. With a mock, the IAM role is optional, because the test calls no real service and needs no permissions.

Exam signals

  • "Front-end team needs the API before the backend exists" → API Gateway mock integration. API Gateway itself returns the response, so no backend is necessary.
  • "Share a test event with the team for a deployed function" → shareable test events (sam remote test-event).
  • "Re-process last week's events with the fixed consumer" → EventBridge archive and replay.
  • "Check a ResultPath without running the whole workflow" → TestState with DEBUG.

References: sam remote invoke, sam remote test-event, API Gateway mock integrations, EventBridge archive and replay, Step Functions TestState.

Debugging defects and integration problems

Key facts

  • Start with the CloudWatch Logs of the function. Read the stack trace and the request ID.
  • Reproduce the failure with the same event: copy it from the log into a local test (sam local invoke -e) or a console test event.
  • Use AWS X-Ray to find which downstream call fails or is slow. X-Ray records each call to another service as a separate part of the trace, with its duration and any error.

Common integration problems

SymptomLikely cause
AccessDeniedException or 403 from an AWS serviceThe execution role has no permission for the action or the resource ARN. A KMS key policy can also block access.
ResourceNotFoundException for a resource that existsWrong Region in the client, or wrong name or ARN (for example a different stage or environment).
Function times out on a call to another serviceFunction timeout too short, no SDK timeout, or no network route. A Lambda function in a VPC has no internet access and no public IP address. It needs a NAT gateway or a VPC endpoint to reach AWS services. Without a route, every call waits until it times out.
API Gateway returns 502 with a Lambda proxy integrationThe function returned a response that is not in the proxy format. It must return statusCode and a string body.
API Gateway returns 504The integration took longer than the API Gateway integration timeout (29 seconds by default for REST APIs). API Gateway stops waiting, even if the function still runs.
Messages fail again and againA "poison" message: a message that the code can never process, for example because of bad data. Each retry fails the same way. Look in the dead-letter queue and log the payload.

Exam signals

  • "Lambda proxy integration, 502 Bad Gateway, function logs show success" → the response format is wrong. The function ran, but API Gateway cannot read its return value as an HTTP response.
  • "Works in us-east-1, ResourceNotFoundException in eu-west-1" → the client Region or the resource name.
  • "Find which of five downstream calls adds the delay" → X-Ray.

References: Lambda proxy output format, Troubleshooting Lambda, REST API quotas (integration timeout).

Amazon Q Developer

In the IDE

  • Inline suggestions: code completions while you type.
  • Chat: questions about code and AWS. Amazon Q uses the open file as context. You can add files, folders, or the workspace.
  • Agentic coding: Amazon Q changes your files directly. You see a diff and can undo the change.
  • Unit test generation (formerly /test): Amazon Q generates unit tests for your code.
  • Documentation generation (formerly /doc): READMEs and other documentation.
  • Code reviews (formerly /review): SAST security scanning, secrets detection (for example hardcoded passwords), infrastructure as code issues, and code quality issues. SAST (static application security testing) reads the source code without running it and finds vulnerabilities such as SQL injection and cross-site scripting. Use code reviews to find these problems in the IDE before you commit the code.
  • Code transformation: language and OS-level upgrades, for example Java version upgrades and .NET porting. Amazon Q changes the code and the dependencies for the whole project, and you review the changes. Use it instead of manual file-by-file edits.

Code references

  • A suggestion can be similar to open-source code. Amazon Q then shows a code reference with the license and the source repository. The license can set rules for your use of that code, so your team can check it before you accept the suggestion.
  • The reference log lists accepted suggestions that have references.
  • A Pro tier administrator can block suggestions with code references for the whole organization.

In the console and tiers

  • In the AWS Management Console, Diagnose with Amazon Q explains common errors (for example missing IAM permissions) and gives steps to fix them.
  • Free tier: no cost, with monthly usage limits. Sign in to the IDE with an AWS Builder ID (no AWS account necessary).
  • Pro tier (Amazon Q Developer Pro): paid, higher limits, and advanced features. An organization subscribes its IAM Identity Center users. Administrators manage settings in the Amazon Q Developer console.
  • AWS plans to end support for the Amazon Q Developer IDE plugins on April 30, 2027. AWS names Kiro as the replacement for the IDE plugins. The exam guide still lists Amazon Q Developer.

Exam signals

  • "Generate unit tests for existing code with the least effort" → Amazon Q Developer unit test generation.
  • "Find hardcoded secrets and vulnerabilities before commit" → Amazon Q Developer code review.
  • "Know the license of suggested code that is similar to open source" → code references.
  • "Upgrade a Java 8 application to a newer Java version" → Amazon Q Developer transformation.

References: Chatting with Amazon Q Developer about code, Code reviews, Code references, Tiers of service, Diagnosing console errors.
