Policy types

Policies that grant permissions

TypeAttached toKey points
AWS managed policyUsers, groups, rolesAWS creates and updates it. You cannot change its permissions. One policy can attach to many identities.
Customer managed policyUsers, groups, rolesYou create and change it. It has its own ARN. A change applies to every identity that has the policy. IAM keeps earlier versions, so you can roll back.
Inline policyOne user, group, or roleStrict one-to-one relationship with the identity. IAM deletes it when you delete the identity. If a policy can apply to more than one identity, use a managed policy.
Resource-based policyA resource: S3 bucket, SQS queue, SNS topic, KMS key, Lambda function, Secrets Manager secret, and othersHas a Principal element that names who gets access. A role trust policy is a resource-based policy on the role.

Policies that only limit permissions

TypeApplies toKey points
Permissions boundaryOne IAM user or role (not a group)A managed policy that sets the maximum permissions that identity-based policies can give. It does not grant permissions.
Service control policy (SCP)IAM users and roles in member accounts of AWS OrganizationsSets the maximum permissions for an account or OU. It never grants permissions. Needs an organization with all features turned on.
Resource control policy (RCP)Resources in member accountsSets the maximum permissions on resources of supported services. It never grants permissions.
Session policyOne role session or federated user sessionYou pass it when you call AssumeRole (or a similar API). The session gets the intersection of the role policies and the session policy.

Key facts

  • Start from AWS managed policies for speed. Copy one into a customer managed policy when you must change it.
  • A boundary is a common way to let developers create roles safely. Allow iam:CreateRole only with the iam:PermissionsBoundary condition key set to the approved boundary ARN.
  • An SCP affects every user and role in the account, including the member account root user. A boundary affects only the user or role that has it.

Exam signals

  • "Same permissions on many roles, change in one place" → customer managed policy.
  • "Permissions must be deleted with the user" or "strict one-to-one" → inline policy.
  • "Developers create roles, but the roles must never exceed X" → permissions boundary.
  • "No identity in any member account can do X, even an administrator" → SCP.
  • "Restrict one session to fewer permissions than the role" → session policy.

References: Managed policies and inline policies, Permissions boundaries, Service control policies.

Policy evaluation logic

Order of evaluation (one account)

  1. By default, AWS denies every request (implicit deny). The root user is the exception.
  2. AWS looks for a Deny that matches in all policy types. One explicit deny gives a final Deny.
  3. RCPs and SCPs: if they do not allow the action, the result is Deny.
  4. Resource-based policy: in the same account, an allow here can be enough (see the table below).
  5. Identity-based policies: with no allow, the result is an implicit deny.
  6. Permissions boundary: if it does not allow the action, the result is Deny.
  7. Session policy: if the session has one and it does not allow the action, the result is Deny.

Rules to memorize

  • An explicit deny always wins over any allow, in any policy type.
  • In one account, an allow in the identity-based policy or in the resource-based policy is enough for most services.
  • Exceptions: a role trust policy and a KMS key policy must allow the principal. An identity-based policy alone is not enough for them.
  • Across accounts, the identity-based policy and the resource-based policy must both allow the action. See the cross-account topic.
  • Effective permissions with a boundary = identity-based policy ∩ boundary.
  • Effective permissions with an SCP and a boundary = identity-based policy ∩ boundary ∩ SCP.

Resource-based policy in the same account: which limits apply

Principal named in the resource-based policyLimited by an implicit deny in a boundary or session policy?
IAM user ARNNo (also not limited by an implicit deny in the identity-based policy)
IAM role ARNYes
Role session ARN (arn:aws:sts::…:assumed-role/…)No
Any principalAn explicit deny in any policy still denies the request

SCP facts

  • SCPs do not affect users or roles in the management account.
  • SCPs do not affect service-linked roles.
  • SCPs do not affect principals from outside the organization that use a resource-based policy.
  • If you remove FullAWSAccess and add no other allow, all actions in member accounts fail.

Exam signals

  • "User has AdministratorAccess but still gets AccessDenied" → an explicit deny somewhere, an SCP, or a boundary.
  • "Add an allow to fix it" when an explicit deny exists → wrong. Remove or narrow the deny.
  • "Identity policy allows DynamoDB, boundary allows only S3" → DynamoDB calls fail.
  • "Same-account bucket policy names the role; role has no S3 permissions; no boundary" → access works.

References: How AWS evaluates requests to allow or deny, Permissions boundaries (effective permissions), SCP effects on permissions.

Policy elements and conditions

Elements

ElementMeaning
VersionUse "2012-10-17". Without it, policy variables such as ${aws:username} are literal text.
EffectAllow or Deny.
Action / NotActionservice:Operation, wildcards allowed (s3:Get*). NotAction matches every action except the listed ones.
ResourceARNs: arn:partition:service:region:account:resource. S3 ARNs have no Region and no account.

ConditionOperator + key + value, for example StringEquals, ArnLike, Bool, IpAddress. Add IfExists to match when the key is absent.

Condition keys to know

KeyUse
aws:SecureTransportIs the request sent with TLS? Deny when false to require HTTPS.
aws:MultiFactorAuthPresentWas MFA used? In a Deny, use BoolIfExists with false. Plain Bool does not deny requests made with long-term access keys, because the key is absent.

Policy variables

  • Syntax: ${aws:username}, ${aws:PrincipalTag/team}. Use them in the resource part of an ARN and in string or ARN conditions.
  • Example: "Resource": "arn:aws:s3:::my-bucket/home/${aws:username}/*" gives each IAM user a private prefix with one policy.
  • aws:username exists only for IAM users. It is not present for roles, the root user, or IAM Identity Center users.

Exam signals

  • "Deny all requests that do not use HTTPS" → bucket policy Deny with aws:SecureTransport = false.
  • "One policy for all users, each user only their own folder" → ${aws:username} with Version 2012-10-17.
  • "Require MFA, also for CLI calls made with access keys" → Deny with BoolIfExists on aws:MultiFactorAuthPresent = false.

References: Global condition context keys, Policy variables, NotAction.

Roles and trust policies

Key facts

  • A role has two policy kinds. The trust policy says who can assume the role. The permissions policies say what the role can do.
  • A trust policy for a service uses a service principal, for example "Principal": {"Service": "lambda.amazonaws.com"} with "Action": "sts:AssumeRole".
  • A role has no long-term credentials. A principal that assumes it gets temporary credentials.
  • When a principal assumes a role, it gives up its own permissions for that session.

Service role compared with service-linked role

Service roleService-linked role
Who creates itYouThe service (or you, through the service or IAM)
Who sets the permissionsYou. You can edit them.The service. You can view them but not edit them.
PathAny/aws-service-role/
Who can assume itPrincipals in the trust policyOnly the linked service (unless the service defines otherwise)
DeletionAny timeDelete the related resources first
Limited by SCPsYesNo

iam:PassRole

  • To give a role to a service (Lambda function, EC2 instance, ECS task, CloudFormation stack), the user needs iam:PassRole on that role.
  • Limit it with the Resource element (role ARNs) and the iam:PassedToService condition key.
  • PassRole is a permission, not an API call. CloudTrail has no PassRole event. Look at the event that created the resource, for example CreateFunction.
  • You can pass a role only to a service in the same account.

Exam signals

  • "Not authorized to perform iam:PassRole" → add iam:PassRole for that role ARN to the user, not to the role.
  • "Service cannot assume the role" → fix the trust policy (service principal), not the permissions policy.
  • "Change permissions of AWSServiceRoleFor…" → not possible. The service owns them.

References: Pass a role to a service, Service-linked roles, Roles give up original permissions.

Key facts

  • Temporary credentials have three parts: access key ID, secret access key, and session token. The application must send all three.

  • "Lambda function assumes another role for 2 hours and fails" → role chaining, 1-hour maximum.
  • "IAM user with access keys must use MFA on the CLI" → GetSessionToken with the MFA code.

Cross-account access

Two methods

Assume a role in the other accountResource-based policy names the other account
Setup in the resource accountRole with a trust policy that names the caller account or roleResource policy (bucket policy, queue policy, key policy) that names the caller
Setup in the caller accountIdentity policy that allows sts:AssumeRole on the role ARNIdentity policy that allows the action on the resource ARN
Caller permissionsThe caller gives up its own permissions while it uses the roleThe caller keeps its own permissions
Use whenThe service has no resource-based policy, or you need many servicesYou must work in both accounts at the same time, for example copy data

Key facts

  • Across accounts, both the identity-based policy and the resource-based policy must allow the request. AWS evaluates both accounts.
  • If the resource policy names the account (arn:aws:iam::111122223333:root), that account must still give the access to its users or roles with identity policies. It cannot give more than the resource policy allows.
  • Cross-account KMS: the key policy in the key account must allow the other account. The caller identity policy must allow the KMS actions. You cannot change the key policy of an AWS managed key, so share a customer managed key.
  • Cross-account access works only inside one partition (for example, not from aws to aws-cn).

Confused deputy

  • Third party (cross-account): the vendor gives you a unique external ID. Your role trust policy names the vendor account and requires sts:ExternalId. The external ID is not a secret.
  • AWS service (cross-service): when a resource policy allows a service principal (for example s3.amazonaws.com or cloudtrail.amazonaws.com), add aws:SourceArn and aws:SourceAccount conditions.

Exam signals

  • "Read from account B and write to account A in one step" → resource-based policy in B. The caller keeps its permissions.
  • "Cross-account role does not work, trust policy is correct" → caller identity policy lacks sts:AssumeRole.
  • "SaaS vendor needs access to many customer accounts" → role with sts:ExternalId.
  • "Only my bucket can invoke this function through S3" → aws:SourceArn and aws:SourceAccount.

References: Cross-account policy evaluation, Cross account resource access, The confused deputy problem, External IDs for third parties.

Programmatic access and the credential provider chain

How the chain works

  • The SDK checks a list of sources in order. It stops at the first source that has credentials.
  • The SDK refreshes temporary credentials automatically when they expire.
  • The exact order differs a little between SDKs. These rules are the same in all of them:
  1. Credentials that you pass in code come first.
  2. Environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN) come next.
  3. Then profiles and providers: assume role, web identity, IAM Identity Center, the shared credentials and config files, and a custom process.
  4. Container credentials (ECS task role, EKS Pod Identity) come near the end.
  5. EC2 instance profile credentials from the instance metadata service (IMDS) come last.

Example: AWS CLI v2 order

Command line options, environment variables, assume role, assume role with web identity, IAM Identity Center, credentials file, custom process, config file, container credentials, EC2 instance profile.

Recommended access by place

Where the code runsUse
Lambda, EC2, ECS, EKSThe role of the compute service. Do not put access keys in code or environment variables.
Developer computer, workforce useraws configure sso one time, then aws sso login. Short-term credentials.
CI/CD outside AWS (for example GitHub Actions)OIDC federation to an IAM role

Last choiceIAM user long-term access keys. Rotate them. Never commit them.

Signature Version 4

  • AWS API requests are signed with Signature Version 4 (SigV4). The SDKs and the CLI sign for you.
  • If you sign requests yourself and the signature is wrong, AWS denies the request.

Exam signals

  • "Code uses old keys, the credentials file has new keys" → environment variables win over the credentials file.
  • "Remove hardcoded keys from an app on EC2, fewest changes" → attach an instance profile and create the client with no explicit credentials.
  • "Developers need CLI access with no long-term keys" → IAM Identity Center with aws sso login.

References: Standardized credential providers, AWS CLI credential precedence, Boto3 credential order.

Comparison

Pairs that the exam mixes up

  • Lambda execution role: what the function can call. Function resource-based policy: who can invoke the function (for example s3.amazonaws.com or events.amazonaws.com with lambda:InvokeFunction).
  • ECS task role: what the application code can call. Task execution role: what the ECS agent needs to pull images from ECR, send logs to CloudWatch Logs, and get secrets for the task.
  • EKS Pod Identity: no OIDC provider, one trust principal for all clusters. IRSA: needs an OIDC provider and a trust policy for each cluster.

EC2 instance metadata

  • IMDSv2 uses a session token. Get it with a PUT to /latest/api/token, then send it in the X-aws-ec2-metadata-token header.
  • Token TTL: up to 6 hours (21,600 seconds).
  • Set token use to required to turn off IMDSv1. This protects against SSRF attacks that read credentials.
  • The PUT response hop limit is 1 by default. Containers on the instance can need a larger hop limit.
  • EC2 role credentials are not subject to the role maximum session duration.
  • To change permissions, edit the role policies. The change applies to all instances that use the role.

Exam signals

  • "ECS task pulls the image but the app gets AccessDenied on DynamoDB" → add the permission to the task role.
  • "Task fails to pull the image from ECR" → task execution role.
  • "S3 or EventBridge cannot invoke the function" → function resource-based policy, not the execution role.
  • "Same EKS app in many clusters, no trust policy change for each cluster" → EKS Pod Identity.
  • "Protect instance credentials from SSRF" → require IMDSv2.

References: IAM roles for EC2, Credentials from instance metadata, IMDSv2, ECS task IAM role, EKS Pod Identity, Container credential provider, Lambda environment variables (reserved variables). Related sets: Lambda permissions, ECS task role and task execution role.

Federation

Which federation to use

UsersUseIdentity sources
Workforce, many accounts in AWS OrganizationsIAM Identity Center (AWS recommends it for human users)SAML 2.0 IdP, AWS Managed Microsoft AD, Identity Center directory
One standalone account, machine users, or small short-term deploymentsIAM identity provider (SAML 2.0 or OIDC) and IAM rolesSAML 2.0, OIDC
Users of your mobile or web appAmazon Cognito identity pool (with a user pool or another IdP)Cognito user pool, OIDC, SAML 2.0, social providers

SAML 2.0 compared with OIDC

  • SAML 2.0: XML assertion. Corporate IdPs such as Active Directory Federation Services. STS API: AssumeRoleWithSAML.
  • OIDC: JSON Web Token (JWT). Web IdPs and tools such as GitHub Actions. STS API: AssumeRoleWithWebIdentity.

Cognito identity pools

  • Identity pools exchange a token for temporary AWS credentials for an IAM role.
  • Enhanced flow (recommended): GetId, then GetCredentialsForIdentity. The identity pool chooses the role. Credentials are valid for 1 hour.
  • Basic flow: GetId, GetOpenIdToken, then AssumeRoleWithWebIdentity. The app chooses the role.
  • Use one role for authenticated identities and one for unauthenticated (guest) identities.

Key facts

  • Do not put long-term AWS credentials in a mobile app, a browser app, or a CI system.
  • A role for OIDC federation trusts the IAM OIDC identity provider and uses sts:AssumeRoleWithWebIdentity. Limit it with conditions on token claims (for example the audience and subject).

Exam signals

  • "Mobile app users sign in with Google and upload to S3" → Cognito identity pool.
  • "Employees use corporate AD to reach many AWS accounts" → IAM Identity Center.
  • "GitHub Actions deploys without stored keys" → IAM OIDC provider and a role.

References: Identity providers and federation, OIDC federation, Identity pools authentication flow.

Troubleshooting access denied

Read the error message

Most messages have the form User: ARN is not authorized to perform: action on resource: ARN because context. The context names the policy type.

Phrase in the messageMeaning
with an explicit deny in a type policyA Deny statement in that policy type. It can also show the policy ARN.
because no type policy allows the action actionImplicit deny. No allow in that policy type.

Policy types in messages include: identity-based, resource-based, permissions boundary, session, service control, resource control, VPC endpoint, and role trust policy. If more than one type denies, the message shows only one of them.

Tools

  • aws sts decode-authorization-message: some services (for example EC2 with UnauthorizedOperation) return an encoded message. Decoding needs the sts:DecodeAuthorizationMessage permission. The result shows explicit or implicit deny, the principal, the action, the resource, and the condition values.
  • IAM policy simulator: tests identity-based policies, boundaries, SCPs, and resource-based policies that you give it. It sends no real request. It does not support RCPs.
  • CloudTrail: records API calls, also calls that AWS denied. A denied call has an errorCode such as AccessDenied.
  • aws sts get-caller-identity: confirms which principal the code really uses.

Checklist

  1. Confirm the principal with get-caller-identity.
  2. Read the policy type in the error message.
  3. Look for an explicit deny (identity, resource, boundary, SCP).
  4. Check for an allow in the identity policy, or in the resource policy for same-account access.
  5. For cross-account access, check both accounts. For SSE-KMS objects, also check the key policy and kms:Decrypt.

Exam signals

  • "Encoded authorization failure message" → decode-authorization-message.
  • "Error says explicit deny in a service control policy" → the organization administrator must change the SCP. IAM changes in the account do not help.
  • "Cross-account S3 GetObject denied, bucket policy is correct, objects use SSE-KMS" → key policy and kms:Decrypt permission.

References: Troubleshoot access denied messages, DecodeAuthorizationMessage, IAM policy simulator.
