Policy types

Remember

  • AWS managed policies, customer managed policies, inline policies, and resource-based policies grant permissions.
  • Permissions boundaries, SCPs, RCPs, and session policies only limit permissions. They never grant permissions.
  • AWS creates and updates an AWS managed policy. You cannot change its permissions.
  • You create and change a customer managed policy. A change applies to every identity that has the policy.
  • IAM keeps earlier versions of a customer managed policy, so you can roll back.
  • An inline policy has a strict one-to-one relationship with one user, group, or role.
  • IAM deletes an inline policy when you delete its identity.
  • A resource-based policy has a Principal element that names who gets access to the resource.
  • A role trust policy is a resource-based policy on the role.
  • A permissions boundary attaches to one IAM user or role, not to a group.
  • A permissions boundary sets the maximum permissions that identity-based policies can give.
  • An SCP sets the maximum permissions for an account or an OU in AWS Organizations.
  • An SCP needs an organization with all features turned on.
  • An SCP affects every user and role in a member account, including the member account root user.
  • An RCP sets the maximum permissions on resources, also for principals from outside your organization.
  • An SCP cannot limit principals from outside your organization. Use an RCP for them.
  • A session policy is passed in AssumeRole (or a similar API) and gives one session fewer permissions than the role.
  • To let developers create roles safely, allow iam:CreateRole only when iam:PermissionsBoundary equals the approved boundary ARN.
  • Without the iam:PermissionsBoundary condition, a developer can create an AdministratorAccess role and escalate privileges.

Exam signals

  • "Same permissions on many roles, change in one place" → customer managed policy.
  • "Permissions must be deleted with the user" or "strict one-to-one" → inline policy. IAM deletes an inline policy together with its identity.
  • "Developers create roles, but the roles must never exceed X" → permissions boundary. It caps each role that has it and does not affect other administrators.
  • "No identity in any member account can do X, even an administrator" → SCP. An SCP limits every user and role in the account, also the root user.
  • "Restrict one session to fewer permissions than the role" → session policy. It applies only to the session that passes it.

Key facts

  • Start from AWS managed policies for speed. Copy one into a customer managed policy when you must change it.
  • A boundary is a common way to let developers create roles safely. Allow iam:CreateRole only with the iam:PermissionsBoundary condition key set to the approved boundary ARN. Without this condition, a developer can create a role with AdministratorAccess and use it to get more access than the developer has (privilege escalation).
  • An SCP affects every user and role in the account, including the member account root user. A boundary affects only the user or role that has it.

Policy evaluation logic

Remember

  • By default, AWS denies every request. This default is an implicit deny.
  • The root user is the exception to the implicit deny. The root user has full access by default.
  • An explicit deny always wins over any allow, in any policy type.
  • If an RCP, an SCP, a boundary, or a session policy does not allow the action, the result is Deny.
  • In one account, an allow in the identity-based policy or the resource-based policy is enough for most services.
  • A role trust policy and a KMS key policy must allow the principal. An identity-based policy alone is not enough.
  • A KMS key policy that names the account root ARN lets identity-based policies in that account give access to the key.
  • Across accounts, the identity-based policy and the resource-based policy must both allow the action.
  • With a boundary, a principal can do only the actions that both the identity-based policy and the boundary allow.
  • With an SCP and a boundary, the identity-based policy, the boundary, and the SCP must all allow the action.
  • A same-account resource-based policy that names a role ARN is still limited by the boundary and the session policy.
  • A same-account resource-based policy that names a user ARN or a role session ARN ignores an implicit deny in a boundary or session policy.
  • SCPs do not affect users or roles in the management account. Keep workloads out of the management account.
  • SCPs do not affect service-linked roles.
  • An SCP does not limit a user from outside the organization. Use an RCP for that case.
  • By default, AWS attaches the FullAWSAccess SCP to every OU and account, so the default SCP limits nothing.
  • If you remove FullAWSAccess and add no other allow, all actions in member accounts fail.

Exam signals

  • "User has AdministratorAccess but still gets AccessDenied" → an explicit deny somewhere, an SCP, or a boundary.
  • "Add an allow to fix it" when an explicit deny exists → wrong. Remove or narrow the deny.
  • "Identity policy allows DynamoDB, boundary allows only S3" → DynamoDB calls fail. Both policies must allow the action.
  • "Same-account bucket policy names the role; role has no S3 permissions; no boundary" → access works. In one account, an allow in the resource-based policy is enough.

Explanation

Order of evaluation (one account)

  1. By default, AWS denies every request. This is an implicit deny: no policy allows the request. The root user is the exception, because it has full access by default.
  2. AWS looks for a Deny that matches in all policy types. One explicit deny gives a final Deny.
  3. RCPs and SCPs: if they do not allow the action, the result is Deny.
  4. Resource-based policy: in the same account, an allow here can be enough (see the table below).
  5. Identity-based policies: with no allow, the result is an implicit deny.
  6. Permissions boundary: if it does not allow the action, the result is Deny.
  7. Session policy: if the session has one and it does not allow the action, the result is Deny.

Rules to memorize

  • An explicit deny always wins over any allow, in any policy type.
  • In one account, an allow in the identity-based policy or in the resource-based policy is enough for most services.
  • Exceptions: a role trust policy and a KMS key policy must allow the principal. An identity-based policy alone is not enough for them. A key policy that names the account (arn:aws:iam::account-id:root) lets identity-based policies in that account give access to the key.
  • Across accounts, the identity-based policy and the resource-based policy must both allow the action. See the cross-account topic.
  • With a boundary, the principal can do only the actions that both the identity-based policy and the boundary allow.
  • With an SCP and a boundary, all three must allow the action: the identity-based policy, the boundary, and the SCP.

SCP facts

  • SCPs do not affect users or roles in the management account. Keep workloads out of the management account for this reason.
  • SCPs do not affect service-linked roles.
  • SCPs limit only users and roles in your member accounts. If a bucket policy allows a user from an account outside the organization, your SCP does not limit that user. Use an RCP for that case.
  • By default, AWS attaches the FullAWSAccess SCP to every OU and account. It allows all actions, so the default SCP limits nothing. If you remove FullAWSAccess and add no other allow, all actions in member accounts fail.

Policy elements and conditions

Remember

  • Set Version to "2012-10-17". Without it, policy variables such as ${aws:username} are literal text.
  • The Principal element exists only in resource-based policies and trust policies.
  • NotAction matches every action except the listed ones. Use it mostly with Deny.
  • NotAction with Allow allows all other actions, also new ones.
  • S3 ARNs have no Region and no account. Example: arn:aws:s3:::my-bucket/*.
  • A Condition has an operator, a key, and a value.
  • An operator with IfExists also matches when the request does not include the key.
  • To require HTTPS, deny requests where aws:SecureTransport is false.
  • To require MFA in a Deny, use BoolIfExists on aws:MultiFactorAuthPresent with false.
  • Plain Bool on aws:MultiFactorAuthPresent does not deny requests made with long-term access keys, because the key is absent.
  • aws:SourceIp is not present when a request comes through a VPC endpoint. Use aws:VpcSourceIp there.
  • An Allow with an IpAddress condition does not match a request through a VPC endpoint, so AWS denies it.
  • aws:PrincipalTag is a tag on the caller. aws:ResourceTag is a tag on the resource.
  • aws:RequestTag and aws:TagKeys are the tags that the request tries to add.
  • Use aws:SourceArn and aws:SourceAccount to protect against the confused deputy problem with AWS service principals.
  • Use aws:PrincipalOrgID in a resource-based policy to allow every principal in your organization without account IDs.
  • Use aws:CalledVia to allow an action only when a named service, for example CloudFormation, makes it.
  • Use policy variables in the resource part of an ARN and in string or ARN conditions.
  • A ${aws:username} prefix in the Resource gives each IAM user a private S3 prefix with one policy.
  • aws:username exists only for IAM users. A statement with it gives roles and Identity Center users no access.

Exam signals

  • "Deny all requests that do not use HTTPS" → bucket policy Deny with aws:SecureTransport = false.
  • "One policy for all users, each user only their own folder" → ${aws:username} with Version 2012-10-17. IAM replaces the variable with the name of the user who makes the request.
  • "Require MFA, also for CLI calls made with access keys" → Deny with BoolIfExists on aws:MultiFactorAuthPresent = false. Requests made with long-term keys do not include the key, and only IfExists matches them.

Explanation

  • Syntax: ${aws:username}, ${aws:PrincipalTag/team}. Use them in the resource part of an ARN and in string or ARN conditions.
  • Example: "Resource": "arn:aws:s3:::my-bucket/home/${aws:username}/*" gives each IAM user a private prefix with one policy.
  • aws:username exists only for IAM users. It is not present for roles, the root user, or IAM Identity Center users. For those principals, a Resource with this variable matches no resource, so the statement gives them no access.

Roles and trust policies

Remember

  • A role trust policy says who can assume the role.
  • A role permissions policy says what the role can do.
  • A trust policy for a service names a service principal, for example lambda.amazonaws.com, with sts:AssumeRole.
  • A role has no long-term credentials. A principal that assumes the role gets temporary credentials.
  • A principal that assumes a role gives up its own permissions for that session.
  • You create a service role, and you can edit its permissions.
  • A service-linked role is defined and owned by the service. You can view its permissions but not edit them.
  • A service-linked role has the path /aws-service-role/. Usually only the linked service can assume it.
  • To delete a service-linked role, delete the related resources first.
  • SCPs limit service roles. SCPs do not limit service-linked roles.
  • To give a role to a service, the user needs iam:PassRole on that role.
  • Without iam:PassRole, the create call fails with "not authorized to perform: iam:PassRole".
  • Limit iam:PassRole with role ARNs in Resource and with the iam:PassedToService condition key.
  • iam:PassRole without limits lets the user pass any role to any service.
  • iam:PassRole is a permission, not an API call. CloudTrail has no PassRole event.
  • To audit a passed role, look at the CloudTrail event that created the resource, for example CreateFunction.
  • You can pass a role only to a service in the same account. A cross-account service must assume a role instead.

Exam signals

  • "Not authorized to perform iam:PassRole" → add iam:PassRole for that role ARN to the user, not to the role. AWS checks the user who configures the service.
  • "Service cannot assume the role" → fix the trust policy (service principal), not the permissions policy. The trust policy controls who can assume the role.
  • "Change permissions of AWSServiceRoleFor…" → not possible. The service owns them.

Explanation

Key facts

  • A role has two policy kinds. The trust policy says who can assume the role. The permissions policies say what the role can do.
  • A trust policy for a service uses a service principal, for example "Principal": {"Service": "lambda.amazonaws.com"} with "Action": "sts:AssumeRole".
  • A role has no long-term credentials. A principal that assumes it gets temporary credentials.
  • When a principal assumes a role, it gives up its own permissions for that session. It can use only the role permissions. For example, it cannot write to a bucket that only its own policy allows.

Service role compared with service-linked role

A service role is a role that a service assumes to do work for you, for example a Lambda execution role. A service-linked role is a special service role that the service defines and owns.

iam:PassRole

  • To give a role to a service (Lambda function, EC2 instance, ECS task, CloudFormation stack), the user needs iam:PassRole on that role. This check stops a user from giving a powerful role to a service and then using the service to do actions that the user cannot do.
  • Without the permission, the create call fails with "not authorized to perform: iam:PassRole".
  • Limit it with the Resource element (the role ARNs that the user can pass) and the iam:PassedToService condition key (the service that can receive the role, for example lambda.amazonaws.com). Without these limits, the user can pass any role to any service.

STS operations

Remember

  • An IAM user or a role session calls AssumeRole, in the same account or cross-account.
  • AssumeRole supports MFA, session policies, and session tags.
  • AssumeRoleWithWebIdentity exchanges an OIDC token (JWT) for credentials. The caller needs no AWS credentials.
  • Cognito identity pools use AssumeRoleWithWebIdentity.
  • AssumeRoleWithSAML exchanges a SAML assertion from a known IdP for credentials. Use it for corporate federation.
  • AssumeRoleWithWebIdentity and AssumeRoleWithSAML do not support MFA.
  • The main use of GetSessionToken is MFA for API and CLI calls.
  • GetSessionToken credentials cannot call IAM APIs unless MFA was included.
  • You cannot pass a session policy to GetSessionToken.
  • Use GetFederationToken for a custom identity broker that gets AWS credentials for its users.
  • A GetFederationToken session can do only what both the IAM user policies and the session policy allow.
  • A GetFederationToken session with no session policy has no permissions.
  • GetFederationToken credentials cannot call IAM APIs with the CLI or API.
  • GetCallerIdentity returns the account, user ID, and ARN. It needs no permission.
  • An explicit deny does not block GetCallerIdentity.
  • The three AssumeRole* APIs allow 15 minutes to the role maximum session duration. The default is 1 hour.
  • A role maximum session duration is 1 hour by default and can be up to 12 hours.
  • DurationSeconds for AssumeRole is 900 seconds to the role maximum. The default is 3,600 seconds.
  • For an IAM user, GetSessionToken and GetFederationToken last 15 minutes to 36 hours. The default is 12 hours.
  • For the root user, GetSessionToken and GetFederationToken last 15 minutes to 1 hour. The default is 1 hour.
  • Role chaining (a role session assumes another role) has a maximum of 1 hour.
  • In role chaining, a DurationSeconds above 1 hour makes the call fail.
  • A session can have one inline session policy and up to 10 managed policy ARNs.
  • All session policies together can have up to 2,048 characters of plaintext.
  • A session can have up to 50 session tags. Policies read session tags as aws:PrincipalTag.
  • Temporary credentials have three parts: access key ID, secret access key, and session token.
  • A request without the session token fails, for example with InvalidClientTokenId. The error name varies by service.
  • For MFA with AssumeRole or GetSessionToken, pass SerialNumber and TokenCode.
  • Credentials from an MFA call make requests with aws:MultiFactorAuthPresent = true.
  • The trust policy checks the ExternalId parameter of AssumeRole with sts:ExternalId.
  • RoleSessionName shows in the session ARN and in CloudTrail. Use it to identify who used the role.

Exam signals

  • "Which identity does my code use?" → aws sts get-caller-identity.
  • "Session of 4 hours fails" → increase the role maximum session duration (up to 12 hours). DurationSeconds cannot exceed it, and the default is 1 hour.
  • "Lambda function assumes another role for 2 hours and fails" → role chaining, 1-hour maximum. The Lambda credentials are already a role session.
  • "IAM user with access keys must use MFA on the CLI" → GetSessionToken with the MFA code. The temporary credentials that it returns count as authenticated with MFA.

  • Temporary credentials have three parts: access key ID, secret access key, and session token. The application must send all three.

Cross-account access

Remember

  • Cross-account access uses one of two methods: assume a role in the other account, or a resource-based policy.
  • To assume a cross-account role, the role trust policy names the caller, and the caller identity policy allows sts:AssumeRole.
  • A caller that assumes a role gives up its own permissions while it uses the role.
  • A caller that uses a resource-based policy keeps its own permissions.
  • Use a role when the service has no resource-based policy, or when you need many services.
  • Use a resource-based policy (S3, SQS, SNS, KMS) when you must work in both accounts at the same time, for example to copy data.
  • Across accounts, the identity-based policy and the resource-based policy must both allow the request.
  • The principal arn:aws:iam::111122223333:root means the whole account, not only the root user.
  • A resource policy that names an account still needs identity policies in that account to give the access.
  • An account cannot give its users more than the resource policy allows.
  • Cross-account KMS needs a key policy that allows the other account and a caller identity policy that allows the KMS actions.
  • You cannot change the key policy of an AWS managed key. Share a customer managed key across accounts.
  • Cross-account access works only inside one partition: aws, aws-cn, or aws-us-gov.
  • In the confused deputy problem, an entity without permission makes a more-privileged entity do the action.
  • For a third-party vendor, the role trust policy names the vendor account and requires sts:ExternalId.
  • The vendor gives each customer a unique external ID. The external ID is not a secret.
  • When a resource policy allows a service principal, add aws:SourceArn and aws:SourceAccount conditions.
  • Without aws:SourceArn and aws:SourceAccount, another account can configure the same service to use your resource.

Exam signals

  • "Read from account B and write to account A in one step" → resource-based policy in B. The caller keeps its own permissions.
  • "Read from account B and write to account A in one step" with an assumed role → fails. The caller loses the write access to account A.
  • "Cross-account role does not work, trust policy is correct" → caller identity policy lacks sts:AssumeRole. Across accounts, both sides must allow the call.
  • "SaaS vendor needs access to many customer accounts" → role with sts:ExternalId. The unique external ID stops one customer from using the vendor to reach another customer's account.
  • "Only my bucket can invoke this function through S3" → aws:SourceArn and aws:SourceAccount. They identify the bucket and account that made S3 call the function.

Key facts

  • Across accounts, both the identity-based policy and the resource-based policy must allow the request. AWS evaluates both accounts.
  • The principal arn:aws:iam::111122223333:root means the whole account, not only the root user. If the resource policy names the account, that account must still give the access to its users or roles with identity policies. It cannot give more than the resource policy allows.
  • Cross-account KMS: the key policy in the key account must allow the other account. The caller identity policy must allow the KMS actions. You cannot change the key policy of an AWS managed key, so share a customer managed key.
  • Cross-account access works only inside one partition. A partition is a separate group of Regions: aws (standard Regions), aws-cn (China), and aws-us-gov (AWS GovCloud US). For example, a role in aws cannot access a resource in aws-cn.

Confused deputy

The confused deputy problem: an entity that has no permission makes a more-privileged entity (the deputy) do the action for it. In AWS, the deputy is a vendor account or an AWS service that you trust.

  • Third party (cross-account): the vendor gives you a unique external ID. Your role trust policy names the vendor account and requires sts:ExternalId.
  • Another customer of the vendor can learn your role ARN, but cannot control the external ID that the vendor sends, so the vendor cannot use your role for that customer. The external ID is not a secret.
  • AWS service (cross-service): when a resource policy allows a service principal (for example s3.amazonaws.com or cloudtrail.amazonaws.com), add aws:SourceArn and aws:SourceAccount conditions. Without them, a user in another account can configure the same service to use your resource, for example to write logs to your bucket.

References: Cross-account policy evaluation, Cross account resource access, The confused deputy problem, External IDs for third parties.

Programmatic access and the credential provider chain

Remember

  • The SDK credential provider chain checks sources in order and stops at the first source that has credentials.
  • The SDK refreshes temporary credentials automatically when they expire.
  • Credentials that you pass in code come first in the chain.
  • Environment variables come second: AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN.
  • Profile settings come after environment variables: assume role, web identity, Identity Center, credentials and config files, custom process.
  • Container credentials (ECS task role, EKS Pod Identity) come near the end of the chain.
  • EC2 instance profile credentials from IMDS come last in the chain.
  • The SDK uses environment variables before the shared credentials file.
  • On Lambda, EC2, ECS, and EKS, use the role of the compute service. Do not put access keys in code or environment variables.
  • On a developer computer, use aws configure sso one time, then aws sso login.
  • For CI/CD outside AWS, for example GitHub Actions, use OIDC federation to an IAM role.
  • For servers outside AWS, use IAM Roles Anywhere with an X.509 certificate from your CA.
  • IAM user long-term access keys are the last choice. Rotate them. Never commit them.
  • The SDKs and the CLI sign AWS API requests for you with Signature Version 4 (SigV4).
  • A request must reach AWS within five minutes of its time stamp.
  • AWS rejects a request that has a wrong signature.

Exam signals

  • "Code uses old keys, the credentials file has new keys" → old keys are still in environment variables. The SDK checks environment variables before the credentials file.
  • "Remove hardcoded keys from an app on EC2, fewest changes" → attach an instance profile and create the client with no explicit credentials. The default chain then finds the instance profile credentials.
  • "Developers need CLI access with no long-term keys" → IAM Identity Center with aws sso login.

Explanation

How the chain works

  • The SDK checks a list of sources in order. It stops at the first source that has credentials.
  • The SDK refreshes temporary credentials automatically when they expire.
  • The exact order differs a little between SDKs. These rules are the same in all of them:
  1. Credentials that you pass in code come first.
  2. Environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN) come next.
  3. Then the profile settings: assume role, web identity, IAM Identity Center, the shared credentials and config files, and a custom process (a command that you configure and that prints credentials).
  4. Container credentials (ECS task role, EKS Pod Identity) come near the end.
  5. EC2 instance profile credentials from the instance metadata service (IMDS) come last.

Example: AWS CLI v2 order

Command line options, environment variables, assume role, assume role with web identity, IAM Identity Center, credentials file, custom process, config file, container credentials, EC2 instance profile.

Roles for compute

Remember

  • An EC2 instance profile is a container for exactly one role.
  • EC2 code gets role credentials from IMDS at iam/security-credentials/role-name.
  • AWS makes new EC2 role credentials available at least 5 minutes before the old credentials expire.
  • Lambda puts the execution role credentials in the reserved variables AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN.
  • An ECS task gets task role credentials from the ECS agent at 169.254.170.2 through AWS_CONTAINER_CREDENTIALS_RELATIVE_URI.
  • An EKS pod gets credentials from the Pod Identity agent on the node through AWS_CONTAINER_CREDENTIALS_FULL_URI.
  • The Lambda execution role controls what the function can call.
  • The Lambda function resource-based policy controls who can invoke the function, for example s3.amazonaws.com.
  • The ECS task role controls what the application code can call.
  • The ECS task execution role lets the ECS agent pull ECR images, send logs, and get secrets.
  • An ECS task role trusts the service principal ecs-tasks.amazonaws.com.
  • IRSA needs one IAM OIDC provider and one trust policy entry for each EKS cluster.
  • EKS Pod Identity trusts one service principal, pods.eks.amazonaws.com, for all clusters and needs no OIDC provider.
  • Choose EKS Pod Identity when one role must work in many clusters.
  • To get an IMDSv2 token, send a PUT to /latest/api/token.
  • Send the IMDSv2 token in the X-aws-ec2-metadata-token header.
  • An IMDSv2 token has a TTL of up to 6 hours (21,600 seconds).
  • Set IMDS token use to required to turn off IMDSv1 and protect against SSRF.
  • An SSRF bug can usually send only a simple GET, so IMDS returns 401 when IMDSv2 is required.
  • The IMDS PUT response hop limit is 1 by default.
  • AMIs that require IMDSv2, for example Amazon Linux 2023, set the hop limit to 2 at launch.
  • A container on an instance adds one hop, so with hop limit 1 the IMDSv2 token does not reach the container.
  • AWS recommends an IMDS hop limit of 2 for containers.
  • The role maximum session duration does not apply to EC2 role credentials. EC2 rotates them automatically.
  • To change EC2 permissions, edit the role policies. The change applies to all instances that use the role.

Exam signals

  • "ECS task pulls the image but the app gets AccessDenied on DynamoDB" → add the permission to the task role. The task role gives credentials to the application code.
  • "Task fails to pull the image from ECR" → task execution role. The ECS agent uses it to pull images before the code starts.
  • "S3 or EventBridge cannot invoke the function" → function resource-based policy, not the execution role. The resource-based policy controls who can invoke the function.
  • "Same EKS app in many clusters, no trust policy change for each cluster" → EKS Pod Identity. The role trusts one service principal for all clusters.
  • "Protect instance credentials from SSRF" → require IMDSv2. Every GET then needs a token that only a PUT can get, and a plain GET fails with 401.

Pairs that the exam mixes up

  • Lambda execution role: what the function can call. Function resource-based policy: who can invoke the function (for example s3.amazonaws.com or events.amazonaws.com with lambda:InvokeFunction).
  • ECS task role: what the application code can call. Task execution role: what the ECS agent needs to pull images from ECR, send logs to CloudWatch Logs, and get secrets for the task.
  • IRSA: each cluster has its own OIDC provider URL. You create an IAM OIDC provider for each cluster, and the role trust policy needs an entry for each cluster.
  • EKS Pod Identity: the role trusts one service principal, pods.eks.amazonaws.com, for all clusters, and needs no OIDC provider. Choose Pod Identity when one role must work in many clusters.

EC2 instance metadata

  • IMDSv2 uses a session token. Get it with a PUT to /latest/api/token, then send it in the X-aws-ec2-metadata-token header.
  • Token TTL: up to 6 hours (21,600 seconds).
  • Set token use to required to turn off IMDSv1. This protects against server-side request forgery (SSRF): a bug that lets an attacker make your application send a request to a URL.
  • An SSRF bug can usually send only a simple GET, so it cannot get the IMDSv2 token, and IMDS returns 401.
  • The PUT response hop limit is 1 by default. AMIs that require IMDSv2 (ImdsSupport v2.0, for example Amazon Linux 2023) set the limit to 2 at launch.
  • The hop limit is the number of network hops that the token response can travel. A container on the instance adds one hop, so with limit 1 the token does not reach the container. AWS recommends a hop limit of 2 for containers.
  • EC2 role credentials are not subject to the role maximum session duration. EC2 rotates them automatically, so a change to that setting does not affect them.
  • To change permissions, edit the role policies. The change applies to all instances that use the role.

Federation

Remember

  • Use IAM Identity Center for workforce users in many accounts of AWS Organizations.
  • AWS recommends IAM Identity Center for human users.
  • IAM Identity Center identity sources: SAML 2.0 IdP, AWS Managed Microsoft AD, Identity Center directory.
  • Use an IAM identity provider (SAML 2.0 or OIDC) with IAM roles for one standalone account, machine users, or small short-term deployments.
  • Use a Cognito identity pool to give users of your mobile or web app temporary AWS credentials.
  • SAML 2.0 uses an XML assertion and the STS API AssumeRoleWithSAML.
  • OIDC uses a JSON Web Token (JWT) and the STS API AssumeRoleWithWebIdentity.
  • A Cognito identity pool exchanges an IdP token, for example from a user pool or Google, for IAM role credentials.
  • The Cognito enhanced flow is GetId, then GetCredentialsForIdentity. The identity pool chooses the role.
  • Cognito enhanced flow credentials are valid for 1 hour.
  • The Cognito basic flow is GetId, GetOpenIdToken, then AssumeRoleWithWebIdentity. The app chooses the role.
  • Choose the Cognito enhanced flow for most apps. Choose the basic flow only when the app must choose the role.
  • A Cognito identity pool uses one role for authenticated users and one role for guests.
  • Give the Cognito guest (unauthenticated) role fewer permissions than the authenticated role.
  • Do not put long-term AWS credentials in a mobile app, a browser app, or a CI system.
  • A role for OIDC federation trusts the IAM OIDC provider and uses sts:AssumeRoleWithWebIdentity.
  • The aud claim says who the token is for. The sub claim says who the caller is.
  • A GitHub OIDC role without a sub condition lets a workflow in another repository assume the role.
  • IAM rejects a new or changed GitHub trust policy without a sub or job_workflow_ref condition.

Exam signals

  • "Mobile app users sign in with Google and upload to S3" → Cognito identity pool. It gives app users temporary AWS credentials, and the app stores no keys.
  • "Employees use corporate AD to reach many AWS accounts" → IAM Identity Center. It manages workforce access to all accounts from one place.
  • "GitHub Actions deploys without stored keys" → IAM OIDC provider and a role. GitHub issues OIDC tokens that STS exchanges for temporary credentials.

SAML 2.0 compared with OIDC

  • SAML 2.0: XML assertion. Corporate IdPs such as Active Directory Federation Services. STS API: AssumeRoleWithSAML.
  • OIDC: JSON Web Token (JWT). Web IdPs and tools such as GitHub Actions. STS API: AssumeRoleWithWebIdentity.

Cognito identity pools

  • Identity pools exchange a token from an identity provider (for example a Cognito user pool or Google) for temporary AWS credentials for an IAM role.
  • Enhanced flow (recommended): GetId, then GetCredentialsForIdentity. The identity pool chooses the role. Credentials are valid for 1 hour.
  • Basic flow: GetId, GetOpenIdToken, then AssumeRoleWithWebIdentity. The app chooses the role.
  • Choose the enhanced flow for most apps. Choose the basic flow only when the app must choose one of several roles itself.
  • Use one role for authenticated identities (users who signed in) and one for unauthenticated (guest) identities. Give the guest role fewer permissions.

Key facts

  • Do not put long-term AWS credentials in a mobile app, a browser app, or a CI system.
  • A role for OIDC federation trusts the IAM OIDC identity provider and uses sts:AssumeRoleWithWebIdentity. Limit it with conditions on token claims.
  • The audience (aud) says who the token is for. The subject (sub) says who the caller is, for example one GitHub repository and branch.
  • All GitHub workflows use the same provider, so without a sub condition, a workflow in another repository could assume the role.
  • IAM rejects a new or changed GitHub trust policy that has no sub (or job_workflow_ref) condition.

Least privilege and access control models

Remember

  • Access Analyzer policy generation reads up to 90 days of CloudTrail events and generates a policy with the actions used.
  • Access Analyzer policy generation needs a CloudTrail trail.
  • Access Analyzer policy generation does not include data events (for example S3 data events) or iam:PassRole.
  • Access Analyzer policy validation checks a policy against grammar and best practices.
  • Policy validation findings are security warnings, errors, warnings, and suggestions. Fix errors and security warnings before you deploy.
  • Access Analyzer custom policy checks find new access in a policy version, or critical actions that you name.
  • Use Access Analyzer custom policy checks in a CI/CD pipeline to stop a policy change before deployment.
  • The Access Analyzer external access analyzer finds resources shared outside your account or organization.
  • The Access Analyzer unused access analyzer finds unused roles, access keys, passwords, services, and actions.
  • Last accessed information shows when an identity last used a service. Use it to remove unused permissions.
  • RBAC uses one role or policy for each job function, with the resources listed.
  • ABAC compares tags on principals and resources, for example aws:ResourceTag/project = ${aws:PrincipalTag/project}.
  • With ABAC, a new resource or project needs only tags. With RBAC, a new resource needs a policy update.
  • Choose ABAC when you add projects or resources often and do not want to change policies each time.
  • Choose RBAC when you have a small, stable set of job functions and resources.

Exam signals

  • "Generate a least-privilege policy from what the role really used" → Access Analyzer policy generation.
  • "Check a policy before deployment" → Access Analyzer policy validation or custom policy checks.
  • "Many projects, permissions must scale without policy updates" → ABAC with tags.

Troubleshooting access denied

Remember

  • An access denied message names the principal, the action, the resource, and a context that names the policy type.
  • The phrase with an explicit deny in a type policy means a Deny statement in that policy type.
  • The phrase because no type policy allows means an implicit deny: no allow in that policy type.
  • When more than one policy type denies, the error message shows only one of them.
  • After you fix one policy type, the next call can fail with a message that names another policy type.
  • Use aws sts decode-authorization-message to decode an encoded message, for example EC2 UnauthorizedOperation.
  • Decoding an authorization message needs the sts:DecodeAuthorizationMessage permission.
  • A decoded message shows explicit or implicit deny, the principal, the action, the resource, and the condition values.
  • The IAM policy simulator tests identity-based policies, boundaries, SCPs, and given resource-based policies without a real request.
  • The IAM policy simulator does not support RCPs.
  • CloudTrail records denied API calls too. A denied call has an errorCode such as AccessDenied.
  • Use aws sts get-caller-identity to confirm which principal the code really uses.
  • For cross-account access, check the policies in both accounts.
  • For SSE-KMS objects, also check the key policy and the kms:Decrypt permission.

Exam signals

  • "Encoded authorization failure message" → decode-authorization-message.
  • "Error says explicit deny in a service control policy" → the organization administrator must change the SCP. IAM changes in the account do not help.
  • "Cross-account S3 GetObject denied, bucket policy is correct, objects use SSE-KMS" → key policy and kms:Decrypt permission.

Explanation

Read the error message

Most messages have the form User: ARN is not authorized to perform: action on resource: ARN because context. The context names the policy type.

Phrase in the messageMeaning
with an explicit deny in a type policyA Deny statement in that policy type. It can also show the policy ARN.
because no type policy allows the action actionImplicit deny. No allow in that policy type.

Policy types in messages include: identity-based, resource-based, permissions boundary, session, service control, resource control, VPC endpoint, and role trust policy.

If more than one type denies, the message shows only one of them. After you fix that one, the next call can fail with a message that names another policy type.

Tools

  • aws sts decode-authorization-message: some services (for example EC2 with UnauthorizedOperation) return an encoded message. Decoding needs the sts:DecodeAuthorizationMessage permission. The result shows explicit or implicit deny, the principal, the action, the resource, and the condition values.
  • IAM policy simulator: tests identity-based policies, boundaries, SCPs, and resource-based policies that you give it. It sends no real request. It does not support RCPs.
  • CloudTrail: records API calls, also calls that AWS denied. A denied call has an errorCode such as AccessDenied.
  • aws sts get-caller-identity: confirms which principal the code really uses.

Checklist

  1. Confirm the principal with get-caller-identity.
  2. Read the policy type in the error message.
  3. Look for an explicit deny (identity, resource, boundary, SCP).
  4. Check for an allow in the identity policy, or in the resource policy for same-account access.
  5. For cross-account access, check both accounts. For SSE-KMS objects, also check the key policy and kms:Decrypt.

References: Troubleshoot access denied messages, DecodeAuthorizationMessage, IAM policy simulator.
