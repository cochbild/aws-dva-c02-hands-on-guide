Execution environment lifecycle and cold starts

Key facts

  • An execution environment has three phases: Init, Invoke, and Shutdown. SnapStart adds a Restore phase.
  • Init starts the extensions, starts the runtime, and runs the function code outside the handler (static code).
  • Code outside the handler runs one time for each execution environment, not one time for each invocation.
  • Create SDK clients and database connections outside the handler. Warm invocations then use them again.
  • One execution environment processes one request at a time. A second concurrent request gets a different environment.
  • A cold start occurs when Lambda must create a new environment. A warm start uses a frozen environment again.
  • Global variables and /tmp content stay in a frozen environment. Use them as a cache, not for correctness.
  • Lambda terminates environments every few hours, even for functions with constant traffic.
  • If an invocation crashes or times out, Lambda resets the environment. The reset does not clear /tmp.

Numbers to memorize

ItemValue
Init phase limit (on-demand)10 seconds. If Init does not complete, Lambda tries Init again at the first invocation, with the function timeout.
Init limit with provisioned concurrency or SnapStartThe 10-second limit does not apply.
Shutdown phase0 ms with no extensions; 500 ms with an internal extension; 2,000 ms with one or more external extensions.
Billed durationRounded up to the nearest 1 ms.

The REPORT log line

Each invocation writes START, END, and REPORT lines. REPORT shows Duration, Billed Duration, Memory Size, and Max Memory Used. Init Duration shows only after a cold start.

Exam signals

  • "Reuse the database connection between invocations" → open the connection outside the handler.
  • "Some requests are slow, and the log has Init Duration" → cold starts. Fix with provisioned concurrency or SnapStart, or reduce init work.
  • "Cache a downloaded file between invocations" → /tmp in the same environment. Do not expect it in every environment.

Key facts

  • More memory also gives more CPU. A CPU-bound function often runs faster with more memory.
  • The 15-minute timeout is a hard limit. Use AWS Step Functions or split the work for longer jobs.
  • Use /tmp for temporary files. Each execution environment has its own /tmp. Lambda encrypts /tmp data at rest.
  • Use Amazon S3 or Amazon EFS for data that must persist or that functions must share.

Exam signals

  • "Job runs 25 minutes" → Lambda cannot do it in one invocation (900-second maximum).
  • "Function must process a 5 GB file locally" → increase ephemeral storage (up to 10,240 MB).
  • "CPU-bound function is slow" → increase memory. CPU increases with memory.
  • "Deployment package is 70 MB zipped" → upload through Amazon S3, or use a container image.

Invocation types and async retries

Comparison

TypeWho callsErrors and retries
Synchronous (RequestResponse)API Gateway, Application Load Balancer, function URLs, SDK and CLI by defaultThe caller gets the error. Lambda does not retry. The caller must retry.
Asynchronous (Event)Amazon S3, Amazon SNS, Amazon EventBridge, SDK or CLI with --invocation-type EventLambda puts the event in a queue and returns HTTP 202. Lambda retries function errors.
Event source mapping (poll)Lambda polls SQS, Kinesis, DynamoDB Streams, and othersLambda invokes the function synchronously. Retry behavior depends on the source. See the event source mapping topic.

Async retry rules

  • Function error: Lambda tries two more times by default. It waits 1 minute before the first retry and 2 minutes before the second.
  • Throttle (429) or system error (5xx): Lambda returns the event to the queue. It tries again for up to 6 hours by default. The wait grows from 1 second to a maximum of 5 minutes.
  • MaximumRetryAttempts: 0 to 2.
  • MaximumEventAgeInSeconds: up to 6 hours (21,600 seconds). Lambda discards older events.
  • Set these on the function, a version, or an alias.
  • The async queue can deliver the same event more than one time. Make the code idempotent.

Key facts

  • With AWS CLI version 2, add --cli-binary-format raw-in-base64-out to send a raw JSON payload.
  • An unqualified function ARN invokes $LATEST.

Exam signals

  • "Caller must not wait for the result" → invoke with InvocationType=Event.
  • "Do not retry failed events, they are not safe to repeat" → set MaximumRetryAttempts to 0.
  • "Old events have no value after 10 minutes" → set MaximumEventAgeInSeconds to 600.
  • "Function processed the same S3 event twice" → async delivery is at least once. Make the code idempotent.

References: Asynchronous invocation, Async error handling, Async error settings. Lab: Lab 1.2 Event sources.

Destinations and dead-letter queues

Comparison

ItemDestinations (async)Dead-letter queue (async)
Success recordsYes (on success)No
Failure recordsYes (on failure)Yes
TargetsSQS queue, SNS topic, Lambda function, EventBridge event bus, S3 bucket (on failure only)SQS standard queue or SNS standard topic
ContentJSON record with request, response, error details, and attempt countThe original event only, plus attributes (RequestID, ErrorCode, ErrorMessage)
ScopeFunction, version, or aliasSet on the function configuration ($LATEST). Each published version keeps the DLQ setting it had when you published it.

Key facts

  • An on-failure destination does the same job as a DLQ. It also supports more targets and includes response details.
  • FIFO queues and FIFO topics are not supported as destinations or as a DLQ.
  • The execution role must allow the write: sqs:SendMessage, sns:Publish, lambda:InvokeFunction, or events:PutEvents.
  • If Lambda cannot deliver to a destination, it emits the DestinationDeliveryFailures metric. For a DLQ, it emits DeadLetterErrors.
  • For an SQS event source, configure the DLQ on the source queue (redrive policy). Do not configure it on the function.
  • For Kinesis, DynamoDB Streams, and Kafka event sources, configure the on-failure destination on the event source mapping.
  • Reserved concurrency of 0 on an async function sends new events to the DLQ or on-failure destination with no retries.

Exam signals

  • "Send the function result to another service, with no code change" → on-success destination.
  • "Capture the error message and the input of failed async events" → on-failure destination.
  • "Failed SQS messages must go to a separate queue" → redrive policy (DLQ) on the source queue.
  • "Several teams must react to each failure" → SNS topic as the failure target.

References: Capturing async records (destinations and DLQ). Lab: Lab 1.6 Destinations and DLQ.

Event source mappings: SQS and streams

An event source mapping (ESM) is a Lambda resource that polls a source, makes batches, and invokes the function. The function execution role needs permission to read the source.

Amazon SQS

  • Batch size: up to 10,000 for a standard queue; maximum 10 for a FIFO queue.
  • For a batch size over 10, set MaximumBatchingWindowInSeconds to at least 1 second.
  • Set the queue visibility timeout to at least 6 times the function timeout. Add the batch window if you use one.
  • Lambda returns an error if the function timeout is more than the queue visibility timeout.
  • By default, one error makes the whole batch visible again after the visibility timeout.
  • Partial batch response: set FunctionResponseTypes to ReportBatchItemFailures. Return the failed message IDs in batchItemFailures as itemIdentifier values.
  • With partial batch response, a thrown exception still fails the whole batch. An empty batchItemFailures list means full success.
  • Put the DLQ on the source queue with a redrive policy. AWS recommends maxReceiveCount of at least 5.
  • Scaling (standard queue): Lambda starts with 5 concurrent batches. It adds up to 300 concurrent invocations each minute, to a maximum of 1,250.
  • Maximum concurrency on the ESM (2 to 1,000) limits one queue. It is separate from reserved concurrency. Keep reserved concurrency at or above the total maximum concurrency.
  • FIFO queue: concurrency is limited by the number of message group IDs. Order is kept inside each message group.

Kinesis Data Streams and DynamoDB Streams

  • Batch size: default 100, maximum 10,000. Batch window: up to 5 minutes.
  • Lambda processes one batch at a time for each shard, in order. ParallelizationFactor (1 to 10) adds concurrent batches for each shard and keeps order for each partition key.
  • By default, a failed batch is retried until the records expire. The shard is blocked during that time.
  • Error controls: BisectBatchOnFunctionError (split the failed batch), MaximumRetryAttempts, MaximumRecordAgeInSeconds, an on-failure destination (SQS or SNS), and ReportBatchItemFailures.
  • The IteratorAge metric shows how far the function is behind the stream.
  • Kinesis enhanced fan-out gives the function a dedicated read connection to each shard.

All event source mappings

  • Processing is at least once. Duplicates can occur. Make the code idempotent.
  • Use filter criteria on the ESM to stop events that the function does not need.
  • Batches can contain up to 6 MB of payload (the synchronous invocation limit).

Exam signals

  • "Successful messages are processed again when one message fails" → ReportBatchItemFailures.
  • "Messages are processed twice, function timeout is near the visibility timeout" → visibility timeout of 6 times the function timeout.
  • "One bad record blocks the stream" → BisectBatchOnFunctionError, limit retries, and add an on-failure destination.
  • "IteratorAge increases" → the function is behind. Increase ParallelizationFactor or add shards.
  • "One queue must not use all the concurrency of a shared function" → ESM maximum concurrency.

References: SQS event source settings, SQS scaling and maximum concurrency, SQS partial batch response, Kinesis ESM parameters, DynamoDB Streams. Lab: Lab 1.2 Event sources.

Concurrency, scaling, and throttling

Key facts

  • Concurrency = average requests per second × average duration in seconds.
  • The account limit is 1,000 concurrent executions for each Region by default. All functions in the Region share it.
  • Lambda also limits requests per second to 10 times the concurrency limit.
  • Scaling rate: each function can add 1,000 execution environments every 10 seconds. Older material shows a burst limit plus 500 each minute. That rule is out of date.

Comparison

ItemReserved concurrencyProvisioned concurrency
PurposeMaximum and guaranteed minimum for one functionPre-initialized environments with no cold start
CostNo chargeExtra charge, also when idle
Where setFunctionA published version or an alias. Not $LATEST.
Over the limitThrottledSpills over to on-demand concurrency (cold starts), unless reserved concurrency stops it
  • Lambda always keeps 100 units of unreserved concurrency. With the default 1,000 limit, you can reserve up to 900.
  • Reserved concurrency of 0 stops all invocations. Use it as an off switch.
  • Provisioned concurrency cannot be more than reserved concurrency on the same function.
  • Use Application Auto Scaling for provisioned concurrency: scheduled scaling, or target tracking on LambdaProvisionedConcurrencyUtilization.
  • Use reserved concurrency to protect a downstream system, for example a database with few connections.

Throttling behavior

  • Synchronous: the caller gets HTTP 429 TooManyRequestsException. The caller must retry with backoff.
  • Asynchronous: Lambda keeps the event and retries for up to 6 hours.
  • SQS event source: Lambda reduces polling, and messages stay in the queue.
  • CloudWatch metrics: Throttles, ConcurrentExecutions, ProvisionedConcurrencyUtilization, ProvisionedConcurrencySpilloverInvocations.

Exam signals

  • "Function must not use more than 50 database connections" → reserved concurrency of 50.
  • "Critical function must always have capacity, other functions use all of it" → reserved concurrency on the critical function.
  • "Predictable spike at 9 AM, no cold starts" → provisioned concurrency with scheduled Application Auto Scaling.
  • "Clients get 429 errors" → concurrency limit reached. Check Throttles, raise the quota or reserved concurrency.
  • "Stop a function immediately without deleting it" → reserved concurrency 0.

References: Lambda concurrency, Scaling rate, Provisioned concurrency. Lab: Lab 1.5 Concurrency.

Versions, aliases, and traffic shifting

Key facts

  • $LATEST is the unpublished version. You change code and settings only on $LATEST.
  • A published version is immutable. It locks the code and most settings: runtime, handler, memory, timeout, environment variables, layers, execution role, VPC, tracing, logging, and DLQ settings.
  • Version numbers increase and Lambda never uses a number again. If $LATEST did not change, you cannot publish a new version.
  • A qualified ARN ends with a version or alias (:3, :prod). An unqualified ARN invokes $LATEST.
  • An alias is a named pointer to a version. You can move it. Callers use the alias ARN and do not change when you deploy.
  • A resource-based policy on an alias ARN applies to that alias only.

Weighted alias (canary)

  • An alias can point to a maximum of two versions, with a weight for the additional version.
  • Both versions must be published (not $LATEST), must have the same execution role, and must have the same DLQ configuration.
  • To find which version ran: the START log line shows the version, the ExecutedVersion metric dimension, or the x-amz-executed-version response header (synchronous).

Gradual deployment with AWS SAM and CodeDeploy

  • AutoPublishAlias publishes a new version when code changes and points the alias to it.
  • DeploymentPreference uses CodeDeploy to shift alias traffic. Types: Canary10Percent5Minutes (also 10, 15, 30 minutes), Linear10PercentEvery1Minute (also every 2, 3, 10 minutes), AllAtOnce.
  • Canary shifts traffic in two steps. Linear shifts traffic in equal steps.
  • Alarms: CodeDeploy rolls back when a listed CloudWatch alarm goes off.
  • Hooks: PreTraffic and PostTraffic Lambda functions run tests and report success or failure to CodeDeploy.
  • Rollback without CodeDeploy: point the alias back to the old version with one UpdateAlias call.

Exam signals

  • "Send 10% of traffic to the new version, then all after 10 minutes, roll back on errors" → SAM DeploymentPreference Canary10Percent10Minutes with alarms.
  • "Callers must not change the ARN on each release" → alias.
  • "Dev and prod must use different settings from the same function" → aliases point to different versions, each with its own locked environment variables.
  • "Run tests before traffic shifts" → PreTraffic hook.

References: Versions, Weighted aliases, SAM gradual deployments, CodeDeploy configurations. Lab: Lab 1.3 Versions and aliases.

Packaging, layers, container images, and AWS SAM

Layers

  • A layer is a .zip archive with libraries, a custom runtime, or configuration files.
  • Lambda extracts layers to /opt. Each runtime adds a path under /opt (for example, /opt/python or /opt/nodejs).
  • A function can use up to 5 layers. Total unzipped size with the function code: 250 MB.
  • Layers work only with .zip functions. A container image function puts its dependencies in the image.
  • A layer version is immutable. A function refers to an exact layer version ARN.
  • Layers let you share dependencies between functions and keep deployment packages small.

Container images

  • Push the image to an Amazon ECR repository in the same Region as the function. The repository can be in another account.
  • Maximum 10 GB uncompressed. Linux images only. One architecture for each image.
  • AWS base images include the runtime interface client and the runtime interface emulator. Other base images need a runtime interface client.
  • Use the runtime interface emulator to test the image locally.
  • You cannot change the package type (.zip or image) of an existing function. Create a new function.

AWS SAM

  • SAM is a CloudFormation transform: Transform: AWS::Serverless-2016-10-31. AWS::Serverless::Function becomes a function, an execution role, and other resources.
  • Deploying a SAM template through CloudFormation needs CAPABILITY_AUTO_EXPAND (for the transform) and CAPABILITY_IAM (for the role).
  • sam build builds the code and dependencies. sam deploy --guided deploys and saves settings.
  • sam local invoke -e event.json runs the function locally with a test event. sam local start-api runs a local API.
  • sam sync sends changes quickly to a development stack. sam logs gets function logs.

Exam signals

  • "Five functions use the same library, update it in one place" → layer.
  • "Dependencies are 3 GB" → container image (10 GB maximum), not layers.
  • "Container image function cannot use the shared layer" → layers are not supported. Build the dependency into the image.
  • "Test the function locally with a sample event" → sam local invoke -e.
  • "CloudFormation deploy fails with RequiresCapabilities" → add CAPABILITY_IAM and CAPABILITY_AUTO_EXPAND.

References: Layers, Container images, Lambda quotas. Labs: Lab 1.1 Hello SAM, Lab 1.4 Layers.

Permissions, secrets, and function URLs

Two kinds of policy

ItemExecution roleResource-based policy (function policy)
ControlsWhat the function can do with other AWS servicesWho can invoke or manage the function
ExamplesWrite to DynamoDB, read from SQS (event source mapping), write logs, write X-Ray tracesAmazon S3, Amazon SNS, EventBridge, API Gateway, or another account invokes the function
How to setIAM role that Lambda assumesAddPermission (one statement) or PutResourcePolicy (full JSON). Maximum 20 KB.
  • Limit a service principal with aws:SourceArn or aws:SourceAccount.
  • You can attach the policy to the function, a version, or an alias.
  • AWSLambdaBasicExecutionRole gives permission to write CloudWatch Logs.
  • For an event source mapping, Lambda reads the source with the execution role. Example: AWSLambdaSQSQueueExecutionRole.

Environment variables and secrets

  • Lambda always encrypts environment variables at rest. By default it uses an AWS managed key, at no charge, with no setup.
  • Use a customer managed KMS key to control key rotation and key access. Users then need kms:Decrypt to see the values.
  • Encryption helpers encrypt values on the client side before Lambda stores them. The function code must call KMS Decrypt. The execution role needs kms:Decrypt.
  • AWS recommends AWS Secrets Manager, not environment variables, for database credentials and API keys.
  • The function gets temporary credentials from the execution role. Do not put access keys in code or environment variables.

Function URLs

  • A function URL is an HTTPS endpoint for one function: https://<url-id>.lambda-url.<region>.on.aws.
  • Attach it to $LATEST or to an alias. You cannot attach it to a numbered version.
  • AuthType AWS_IAM: callers sign requests with SigV4 and need lambda:InvokeFunctionUrl and lambda:InvokeFunction.
  • AuthType NONE: public access. A resource-based policy must still allow public access.
  • Configure CORS on the function URL. Function URLs are reachable only from the public internet.

Exam signals

  • "S3 event does not start the function" → the function resource-based policy does not allow s3.amazonaws.com.
  • "AccessDenied when the function writes to DynamoDB" → add the permission to the execution role.
  • "Store a database password with rotation" → Secrets Manager.
  • "Environment variable must not be visible as plain text in the console" → encryption helpers with a customer managed key.
  • "Simple HTTPS endpoint for one function, no API features needed" → function URL.

Lambda in a VPC

Key facts

  • By default, a function can reach the public internet but cannot reach private resources in your VPC.
  • Attach the function to private subnets and security groups to reach RDS, ElastiCache, or private EC2 resources.
  • After you attach it, the function reaches only what the VPC can reach.
  • Internet access from a VPC function: route the private subnets to a NAT gateway in a public subnet.
  • A public subnet does not give the function internet access or a public IP address.
  • To reach AWS services without the internet, add VPC endpoints. Gateway endpoints are for Amazon S3 and DynamoDB.
  • The execution role needs EC2 network interface permissions. Use the AWSLambdaVPCAccessExecutionRole managed policy.
  • Lambda creates a Hyperplane ENI for each subnet and security group combination. Functions with the same combination share it.
  • While Lambda creates the ENI, a new function is Pending and cannot be invoked. After 14 days idle, the function becomes Inactive.
  • The target security group must allow inbound traffic from the function security group.
  • Use RDS Proxy to pool database connections when many functions connect.
  • Choose subnets in more than one Availability Zone for high availability.

Exam signals

  • "Function in a VPC times out when it calls an external API" → no NAT gateway route.
  • "Function in a VPC must read S3 without internet access" → S3 gateway endpoint.
  • "Too many database connections from Lambda" → RDS Proxy, or reserved concurrency.
  • "Function must reach an ElastiCache cluster" → attach the function to the VPC and allow its security group.

References: VPC access. Lab: Lab 1.7 VPC Lambda.

Logging, metrics, tracing, and extensions

Logs

  • Output to stdout and stderr goes to CloudWatch Logs. The default log group is /aws/lambda/<function-name>.
  • Log format: Text (default) or JSON.
  • Log-level filtering needs the JSON format. Application levels: TRACE, DEBUG, INFO, WARN, ERROR, FATAL. System levels: DEBUG, INFO, WARN.
  • A log level set in the function code overrides the console or API setting.
  • You can send logs to a custom log group.
  • Use CloudWatch Logs Insights to query logs.

Metrics

  • Built-in: Invocations, Errors, Throttles, Duration, ConcurrentExecutions, IteratorAge, DeadLetterErrors, DestinationDeliveryFailures.
  • Custom metrics: write logs in CloudWatch embedded metric format (EMF). CloudWatch extracts the metrics. The code does not call PutMetricData.

AWS X-Ray

  • Turn on active tracing: TracingConfig Mode: Active, or Tracing: Active in SAM.
  • The execution role needs xray:PutTraceSegments and xray:PutTelemetryRecords (AWSXRayDaemonWriteAccess).
  • Sampling: 1 request each second plus 5 percent of other requests. You cannot change the sampling rate for Lambda.
  • Lambda records two segments: AWS::Lambda (the service) and AWS::Lambda::Function (your code).
  • Add annotations to search and filter traces. Metadata is not indexed.
  • Tracing mode is locked in a published version.

Extensions

  • An external extension is a separate process. It can run after the function returns. Lambda installs it from a layer in /opt/extensions.
  • An internal extension runs in the runtime process.
  • Extensions share memory, CPU, and permissions with the function. You pay for the time they use.
  • Extension size counts toward the 250 MB unzipped package limit.

Exam signals

  • "Find which downstream call is slow" → X-Ray active tracing with subsegments.
  • "Filter traces by customer ID" → X-Ray annotation.
  • "Send only ERROR logs from production without code change" → JSON log format and application log level ERROR.
  • "Publish a custom business metric with the least latency and effort" → embedded metric format.
  • "Send telemetry to a third-party tool without changing code" → Lambda extension.

References: Log-level filtering, X-Ray with Lambda, Extensions. Lab: Lab 1.1 Hello SAM.

Performance tuning and SnapStart

Key facts

  • Memory controls CPU. More memory can lower cost if the duration falls enough.
  • Test several memory sizes and compare duration and cost. AWS Lambda Power Tuning is an open-source tool for this test.
  • Keep init work small: import only the modules you need, and load rarely used objects when needed.
  • Create clients and connections outside the handler, so warm invocations use them again.
  • Provisioned concurrency gives the lowest and most constant start latency, at extra cost.

SnapStart

  • Lambda runs Init when you publish a version, takes a snapshot, and starts new environments from the snapshot.
  • Runtimes: Java 11 and later, Python 3.12 and later, .NET 8 and later.
  • Works on published versions and aliases only, not on $LATEST.
  • Not supported with provisioned concurrency, Amazon EFS, or ephemeral storage above 512 MB.
  • Cost: no extra cost for Java. Python and .NET pay for snapshot caching and for each restore.
  • Content made during Init (unique IDs, random seeds) is the same in every restored environment. Make unique content after the restore. Use runtime hooks for before-snapshot and after-restore code.

Exam signals

  • "Java function has a slow cold start, lowest cost fix" → SnapStart.
  • "Strict latency for every request, cost is not a concern" → provisioned concurrency.
  • "Find the best memory size for cost" → test memory sizes (for example, with Lambda Power Tuning).
  • "Restored environments create the same random value" → SnapStart uniqueness. Generate it after restore.

References: SnapStart, Optimizing static initialization, Memory and CPU. Lab: Lab 1.5 Concurrency.
