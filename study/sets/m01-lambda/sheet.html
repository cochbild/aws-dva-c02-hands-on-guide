Execution environment lifecycle and cold starts

Remember

  • An execution environment is the isolated place where Lambda runs function code, with its own memory and /tmp disk.
  • An execution environment has three phases: Init, Invoke, and Shutdown. SnapStart adds a Restore phase.
  • The Init phase starts the extensions, starts the runtime, and runs the static code outside the handler.
  • Code outside the handler runs one time for each execution environment, not one time for each invocation.
  • Create SDK clients and database connections outside the handler, so that warm invocations use them again.
  • SDK clients or connections created inside the handler make every invocation wait, and the database can run out of connections.
  • One execution environment processes one request at a time. A concurrent request gets a different environment.
  • A warm start uses a frozen environment again, so the Init phase does not run.
  • A cold start creates a new environment and runs Init first, which adds latency to that request.
  • Global variables and /tmp content stay in a frozen environment, so use them only as a cache.
  • A cache in global variables or /tmp can be empty, because the next request can go to a new environment.
  • Lambda terminates environments every few hours for maintenance, even for functions with constant traffic.
  • After a crash or a timeout, Lambda resets the environment and runs Init again before the next invocation.
  • An environment reset does not clear /tmp, so files from the failed invocation can still be there.
  • The context object gives the remaining time: getRemainingTimeInMillis() or get_remaining_time_in_millis().
  • The context object gives the request ID: awsRequestId or aws_request_id.
  • The on-demand Init phase has a limit of 10 seconds.
  • If on-demand Init does not complete in 10 seconds, Lambda tries Init again at the first invocation, with the function timeout.
  • With provisioned concurrency or SnapStart, Init can run for 130 seconds or the function timeout, whichever is higher.
  • The Shutdown phase lasts 0 ms with no extensions, 500 ms with an internal extension, and 2,000 ms with external extensions.
  • Lambda rounds the billed duration up to the nearest 1 ms.
  • The REPORT log line shows Init Duration only after a cold start.

Exam signals

  • "Reuse the database connection between invocations" → open the connection outside the handler, because that code runs only one time for each environment.
  • "Some requests are slow, and the log has Init Duration" → cold starts. Init Duration appears only when Lambda creates a new environment.
  • "Reduce the latency of cold starts" → provisioned concurrency or SnapStart, or reduce the init work.
  • "Cache a downloaded file between invocations" → /tmp in the same environment. Each environment has its own /tmp, so check for the file and download it again when it is missing.
  • "Stop work safely before the timeout" → check the remaining time from the context object.

Explanation

Key facts

  • An execution environment is the isolated place where Lambda runs your function code, with its own memory and /tmp disk.
  • An execution environment has three phases: Init, Invoke, and Shutdown. SnapStart adds a Restore phase.
  • Init starts the extensions, starts the runtime, and runs the function code outside the handler. This code is called static code: imports, SDK clients, configuration, and connections at the top level of the file.
  • Code outside the handler runs one time for each execution environment, not one time for each invocation.
  • Create SDK clients and database connections outside the handler. Warm invocations then use them again.
  • If you create SDK clients and database connections inside the handler, every invocation waits for a new connection, and the database can run out of connections.
  • One execution environment processes one request at a time. A second concurrent request gets a different environment.
  • After an invocation ends, Lambda freezes the environment (pauses its processes) and keeps it for some time. A warm start uses a frozen environment again, so Init does not run.
  • A cold start occurs when no free environment exists: Lambda creates one and runs Init first. The caller sees the cold start as extra latency on that request.
  • Global variables and /tmp content stay in a frozen environment, so the next warm invocation can read them. Use them only as a cache. The next request can go to a different or a new environment where the cache is empty, so the code must also work without it.
  • Lambda terminates environments every few hours for runtime updates and maintenance, even for functions with constant traffic. Do not depend on one environment to stay alive.
  • If an invocation crashes or times out, Lambda resets the environment: it stops the runtime and runs Init again before the next invocation. The reset does not clear /tmp, so files from the failed invocation can still be there.

The context object

  • The handler gets event and context. The context object describes the invocation and the function.
  • Remaining time: getRemainingTimeInMillis() (Node.js, Java) or get_remaining_time_in_millis() (Python). Use it to stop work before the timeout.
  • Request ID: awsRequestId or aws_request_id. It also appears in the START, END, and REPORT log lines.
  • Other properties: function name and version, invoked function ARN (shows the alias or version used), memory limit, log group, and log stream.

Configuration settings and limits

Remember

  • Lambda memory defaults to 128 MB. You can set 128 MB to 10,240 MB, in 1-MB steps.
  • Lambda CPU is proportional to memory. You cannot set CPU directly.
  • At 1,769 MB of memory, a function has the equivalent of one vCPU.
  • A CPU-bound function often runs faster with more memory.
  • The function timeout defaults to 3 seconds and has a maximum of 900 seconds (15 minutes).
  • The 15-minute timeout is a hard limit. You cannot request an increase.
  • At the timeout, Lambda stops the invocation and reports a "Task timed out" error.
  • For a job longer than 15 minutes, split the work into steps and run the steps with AWS Step Functions.
  • Ephemeral storage (/tmp) defaults to 512 MB. You can set 512 MB to 10,240 MB.
  • Environment variables have a limit of 4 KB total for all variables.
  • A function can use at most 5 layers.
  • A synchronous invocation allows a 6 MB request and a 6 MB response.
  • An asynchronous invocation allows a payload of 1 MB.
  • A streamed response allows 200 MB. After the first 6 MB, the response streams at up to 2 MBps.
  • A direct .zip upload allows 50 MB zipped. Upload a larger package through Amazon S3.
  • A .zip package allows 250 MB unzipped, including layers and custom runtimes.
  • A container image allows 10 GB uncompressed, including all image layers.
  • A function resource-based policy has a limit of 20 KB.
  • Concurrent executions default to 1,000 for each Region. This soft limit can increase on request.
  • The architecture defaults to x86_64. The other choice is arm64.
  • Each execution environment has its own /tmp. Lambda encrypts /tmp data at rest.
  • Use Amazon S3 or Amazon EFS for data that must persist or that functions must share, not /tmp.
  • To use Amazon EFS, the function must connect to the VPC, because the mount targets are in the VPC.
  • A function mounts Amazon EFS through an access point, at a local path that starts with /mnt/.

Exam signals

  • "Job runs 25 minutes" → Lambda cannot do it in one invocation (900-second maximum).
  • "Function must process a 5 GB file locally" → increase ephemeral storage (up to 10,240 MB), because the default /tmp is only 512 MB.
  • "Several functions must share files that persist" → Amazon EFS, not /tmp.
  • "CPU-bound function is slow" → increase memory. CPU increases with memory.
  • "Deployment package is 70 MB zipped" → upload through Amazon S3, or use a container image, because a direct .zip upload allows only 50 MB.

Key facts

  • More memory also gives more CPU. A CPU-bound function often runs faster with more memory.
  • The 15-minute timeout is a hard limit: you cannot request an increase. At the timeout, Lambda stops the invocation and reports a "Task timed out" error.
  • For longer jobs, split the work into steps that each finish in less than 15 minutes. Run the steps with AWS Step Functions.
  • Use /tmp for temporary files. Each execution environment has its own /tmp. Lambda encrypts /tmp data at rest.
  • Use Amazon S3 or Amazon EFS for data that must persist or that functions must share. Other environments cannot read a /tmp directory, and its content is lost when the environment ends.
  • Amazon EFS: the function must connect to the VPC, because the file system mount targets are in the VPC.
  • The function mounts the file system through an access point (an EFS entry point that sets the directory and the user), at a local path that starts with /mnt/.
  • With Amazon EFS, many functions and environments can read and write the same files.

Invocation types and async retries

Remember

  • In a synchronous (RequestResponse) invocation, the caller waits for the result and gets the error.
  • Lambda does not retry a synchronous invocation. The caller must retry.
  • API Gateway, Application Load Balancer, function URLs, and the SDK and CLI (by default) invoke synchronously.
  • An asynchronous (Event) invocation puts the event in an internal queue and returns HTTP 202 at once.
  • The caller of an asynchronous invocation never sees the function result or error.
  • Amazon S3, Amazon SNS, and Amazon EventBridge invoke Lambda asynchronously.
  • An event source mapping polls SQS, Kinesis, or DynamoDB Streams and invokes the function synchronously.
  • Choose synchronous when the caller needs the result now, for example an HTTP request.
  • Choose asynchronous when the caller only hands off work and does not wait.
  • The source service decides the invocation type. You choose only when you call Lambda with the SDK or CLI.
  • After an async function error, Lambda retries two more times by default: after 1 minute, then after 2 minutes.
  • After an async throttle (429) or system error (5xx), Lambda retries for up to 6 hours by default.
  • For async throttle retries, the wait grows from 1 second to a maximum of 5 minutes.
  • MaximumRetryAttempts accepts 0 to 2. Set 0 when a second run causes harm, for example a duplicate payment.
  • MaximumEventAgeInSeconds accepts up to 21,600 seconds (6 hours). Set a low value when old events have no value.
  • Lambda discards an event older than the maximum age, or sends it to the DLQ or on-failure destination.
  • Set the async retry settings on the function, a version, or an alias.
  • The async queue can deliver the same event more than one time, even when no error occurs.
  • Make async code idempotent: two runs of the same event give the same result as one run.
  • Idempotency example: write with a DynamoDB condition on the event ID, so a second write does nothing.
  • AWS CLI version 2 needs --cli-binary-format raw-in-base64-out to send a raw JSON payload.
  • An unqualified function ARN (no version or alias) invokes $LATEST.

Exam signals

  • "Caller must not wait for the result" → invoke with InvocationType=Event.
  • "Do not retry failed events, they are not safe to repeat" → set MaximumRetryAttempts to 0.
  • "Old events have no value after 10 minutes" → set MaximumEventAgeInSeconds to 600.
  • "Function processed the same S3 event twice" → make the code idempotent. Async delivery is at least once.

Async retry rules

  • Function error: Lambda tries two more times by default. It waits 1 minute before the first retry and 2 minutes before the second.
  • Throttle (429, no concurrency is free to run the function) or system error (5xx): Lambda returns the event to the queue. It tries again for up to 6 hours by default. The wait grows from 1 second to a maximum of 5 minutes.
  • MaximumRetryAttempts: 0 to 2. Set 0 when a second run causes harm, for example a duplicate email or payment.
  • MaximumEventAgeInSeconds: up to 6 hours (21,600 seconds). Lambda discards older events, or sends them to the DLQ or on-failure destination if you configured one. Set a low value when old events have no value.
  • Set these on the function, a version, or an alias.
  • The async queue can deliver the same event more than one time, even when no error occurs.
  • Make the code idempotent: two runs of the same event must give the same result as one run. Example: write with a DynamoDB condition on the event ID, so the second write does nothing.

Key facts

  • With AWS CLI version 2, add --cli-binary-format raw-in-base64-out to send a raw JSON payload. Without it, CLI version 2 reads the payload as base64, and the call fails.
  • An unqualified function ARN (no version or alias at the end) invokes $LATEST, the newest unpublished code.

Destinations and dead-letter queues

Remember

  • An on-success destination receives records of successful async invocations. A DLQ cannot get success records.
  • On-failure destinations and a DLQ both receive records of failed async invocations.
  • Destination targets are an SQS queue, an SNS topic, a Lambda function, an EventBridge event bus, or an S3 bucket.
  • An S3 bucket can be a destination target only for failure records.
  • A DLQ target is an SQS standard queue or an SNS standard topic.
  • A destination record is JSON with the request, the response, the error details, and the attempt count.
  • A DLQ keeps only the original event and three attributes: RequestID, ErrorCode, and ErrorMessage.
  • Choose an on-failure destination over a DLQ when you need the error message or the attempt count.
  • You configure a destination on the function, a version, or an alias.
  • You add or remove a DLQ only at the function level.
  • Lambda does not support FIFO queues or FIFO topics as a destination or as a DLQ.
  • The execution role must allow the write: sqs:SendMessage, sns:Publish, lambda:InvokeFunction, or events:PutEvents.
  • A failed delivery to a destination increases the DestinationDeliveryFailures metric.
  • A failed delivery to a DLQ increases the DeadLetterErrors metric.
  • For an SQS event source, configure the DLQ as a redrive policy on the source queue, not on the function.
  • The async DLQ and destinations of a function never get messages from an event source mapping, because the mapping invokes synchronously.
  • For Kinesis, DynamoDB Streams, and Kafka, configure the on-failure destination on the event source mapping.
  • Reserved concurrency of 0 sends new async events to the DLQ or on-failure destination with no retries.

Exam signals

  • "Send the function result to another service, with no code change" → on-success destination.
  • "Capture the error message and the input of failed async events" → on-failure destination.
  • "Failed SQS messages must go to a separate queue" → redrive policy (DLQ) on the source queue.
  • "Several teams must react to each failure" → SNS topic as the failure target, because SNS sends one message to many subscribers.

  • Choose an on-failure destination when you need the error message or the attempt count. A DLQ keeps only the original event and three attributes.
  • FIFO queues and FIFO topics are not supported as destinations or as a DLQ. Lambda cannot deliver to them, and the DestinationDeliveryFailures metric increases.
  • Lambda writes the record with the function execution role, so the role must allow the write: sqs:SendMessage, sns:Publish, lambda:InvokeFunction, or events:PutEvents. Without the permission, delivery fails.
  • If Lambda cannot deliver to a destination, it emits the DestinationDeliveryFailures metric. For a DLQ, it emits DeadLetterErrors.
  • For an SQS event source, configure the DLQ on the source queue (redrive policy). Do not configure it on the function. The event source mapping invokes the function synchronously, so the async DLQ and destinations of the function never get these messages.
  • For Kinesis, DynamoDB Streams, and Kafka event sources, configure the on-failure destination on the event source mapping, for the same reason: these are not async invocations.
  • Reserved concurrency of 0 on an async function sends new events to the DLQ or on-failure destination with no retries, because Lambda cannot run the function at all.

Event source mappings: SQS and streams

Remember

  • An event source mapping (ESM) polls a queue or a stream, makes batches, and invokes the function.
  • The function execution role needs permission to read the source of an event source mapping.
  • An SQS standard queue allows a batch size of up to 10,000. An SQS FIFO queue allows at most 10.
  • For an SQS batch size over 10, set MaximumBatchingWindowInSeconds to at least 1 second.
  • SQS hides a received message for the visibility timeout. A message that Lambda does not delete becomes visible again.
  • Set the SQS visibility timeout to at least 6 times the function timeout, plus the batch window.
  • The function timeout cannot be more than the queue visibility timeout. Lambda returns an error when you create or update the mapping.
  • By default, one failed message makes the whole SQS batch visible again, so successful messages run again.
  • To return only failed messages, set FunctionResponseTypes to ReportBatchItemFailures.
  • A partial batch response returns each failed message ID as an itemIdentifier in batchItemFailures.
  • With partial batch response, a thrown exception still fails the whole batch.
  • An empty batchItemFailures list means that the whole batch succeeded.
  • Put the DLQ for an SQS source on the source queue, with a redrive policy and maxReceiveCount.
  • AWS recommends a maxReceiveCount of at least 5, so Lambda can retry before a message goes to the DLQ.
  • For an SQS standard queue, Lambda starts with 5 concurrent batches and adds up to 300 concurrent invocations each minute.
  • SQS standard queue scaling reaches a maximum of 1,250 concurrent invocations.
  • ESM maximum concurrency (2 to 1,000) caps the concurrent invocations that one queue can start.
  • Use ESM maximum concurrency when several queues share one function.
  • Keep reserved concurrency at or above the total ESM maximum concurrency, or Lambda can throttle invocations.
  • For an SQS FIFO queue, the number of different message group IDs limits the concurrency.
  • A stream batch size defaults to 100, with a maximum of 10,000.
  • A stream batch window can be up to 5 minutes.
  • Records with the same partition key go to the same shard, in order.
  • Lambda processes one batch at a time for each shard, in order.
  • ParallelizationFactor (1 to 10) adds concurrent batches for each shard and keeps the order for each partition key.
  • By default, Lambda retries a failed stream batch until the records expire, and the shard is blocked.
  • BisectBatchOnFunctionError splits a failed stream batch in two and retries each half, to find the bad record.
  • MaximumRetryAttempts and MaximumRecordAgeInSeconds stop stream retries, so the shard can continue.
  • With ReportBatchItemFailures on a stream, Lambda retries from the first failed record.
  • Stream on-failure destinations are an SQS queue, an SNS topic, or an S3 bucket (a Kafka topic for Kafka).
  • SQS and SNS failure records for a stream contain only metadata. S3 failure records also contain the payload.
  • With an SQS or SNS failure destination, read the failed records from the stream before the retention period ends.
  • A tumbling window (TumblingWindowInSeconds, up to 900 seconds) keeps state between invocations in a fixed time period.
  • Tumbling window state is up to 1 MB for each shard.
  • isFinalInvokeForWindow marks the last invocation of a tumbling window, where the function writes the result.
  • Use a tumbling window to count or sum stream data with no external database.
  • An IteratorAge metric that keeps going up means that the function falls behind the stream.
  • Without enhanced fan-out, consumers share the shard read throughput, and Lambda polls each shard once each second.
  • Kinesis enhanced fan-out gives a dedicated read connection to each shard and pushes the records, at extra cost.
  • Use enhanced fan-out when several applications read the same stream, or when you need lower latency.
  • An event source mapping processes records at least once, so make the code idempotent.
  • ESM filter criteria stop events that the function does not need, so you pay for fewer invocations.
  • An ESM allows up to 5 filters by default, with EventBridge pattern syntax.
  • For SQS, filter on the body key. Lambda removes messages that do not match from the queue.
  • ESM filter criteria work with SQS, Kinesis, DynamoDB Streams, Amazon MQ, and Kafka.
  • An ESM batch can contain up to 6 MB of payload, the synchronous invocation limit.

Exam signals

  • "Successful messages are processed again when one message fails" → ReportBatchItemFailures, because then only the reported failed messages return to the queue.
  • "Messages are processed twice, function timeout is near the visibility timeout" → visibility timeout of 6 times the function timeout. The messages became visible again while Lambda still processed or retried them.
  • "One bad record blocks the stream" → BisectBatchOnFunctionError, limit retries, and add an on-failure destination. Without a limit, Lambda retries the same batch until the records expire.
  • "IteratorAge increases" → increase ParallelizationFactor or add shards. The function is behind, and both changes give more concurrent batches.
  • "One queue must not use all the concurrency of a shared function" → ESM maximum concurrency, because it caps one queue and not the whole function.
  • "Do not invoke the function for messages it does not need" → ESM filter criteria.
  • "Aggregate stream data over fixed time periods without a database" → tumbling windows.

Explanation

An event source mapping (ESM) is a Lambda resource that polls a source, makes batches, and invokes the function. Lambda uses it for sources that store records and do not push them to Lambda: queues and streams.

The function execution role needs permission to read the source, because Lambda reads the source with that role.

Amazon SQS

  • Batch size: up to 10,000 for a standard queue; maximum 10 for a FIFO queue.
  • For a batch size over 10, set MaximumBatchingWindowInSeconds to at least 1 second. Lambda then waits up to that time to collect a larger batch.
  • When Lambda reads a message, SQS hides it from other readers for the visibility timeout. If Lambda does not delete the message in that time, the message becomes visible again and is processed again.
  • Set the queue visibility timeout to at least 6 times the function timeout. Add the batch window if you use one. The extra time lets Lambda retry a batch when the function is throttled, before the messages become visible again.
  • The function timeout must not be more than the queue visibility timeout. Lambda checks this when you create or update the event source mapping, and returns an error.
  • By default, one error makes the whole batch visible again after the visibility timeout. Lambda deletes messages only when the whole batch succeeds, so the messages that succeeded are processed again.
  • Partial batch response: set FunctionResponseTypes to ReportBatchItemFailures. Return the failed message IDs in batchItemFailures as itemIdentifier values.
  • With partial batch response, a thrown exception still fails the whole batch. An empty batchItemFailures list means full success.
  • Put the DLQ on the source queue with a redrive policy. SQS moves a message to the DLQ when it has been received more than maxReceiveCount times without being deleted. AWS recommends maxReceiveCount of at least 5, so Lambda has a few chances to retry before a message goes to the DLQ.
  • Scaling (standard queue): Lambda starts with 5 concurrent batches. It adds up to 300 concurrent invocations each minute, to a maximum of 1,250. So a sudden backlog takes a few minutes to reach full concurrency, and messages wait in the queue during that time.
  • Maximum concurrency on the ESM (2 to 1,000) caps how many concurrent invocations one queue can start. Use it when several queues share one function, so one busy queue cannot use all of the function capacity.
  • ESM maximum concurrency is separate from reserved concurrency, which caps the whole function. Keep reserved concurrency at or above the total maximum concurrency. Otherwise, Lambda can throttle the extra invocations.
  • FIFO queue: Lambda processes the messages of one message group ID one at a time, in order. So the number of different message group IDs limits the concurrency.

Kinesis Data Streams and DynamoDB Streams

  • Batch size: default 100, maximum 10,000. Batch window: up to 5 minutes.
  • A stream is divided into shards. The producer sets a partition key on each record, and records with the same partition key go to the same shard, in order.
  • Lambda processes one batch at a time for each shard, in order. ParallelizationFactor (1 to 10) adds concurrent batches for each shard and keeps order for each partition key.
  • By default, a failed batch is retried until the records expire. Lambda must keep the order in the shard, so it cannot skip the failed batch. No later records in that shard are processed during that time: the shard is blocked.
  • Error controls: BisectBatchOnFunctionError splits the failed batch in two and retries each half, to isolate the bad record.
  • MaximumRetryAttempts and MaximumRecordAgeInSeconds stop the retries, so the shard can continue. An on-failure destination keeps a record of the batch that Lambda stopped retrying.
  • ReportBatchItemFailures lets the function report the first failed record, so Lambda retries from that record.
  • Stream on-failure destinations: SQS queue, SNS topic, or S3 bucket (a Kafka topic for Kafka sources).
  • SQS and SNS records contain only metadata (shard ID and sequence numbers). S3 records also contain the payload.
  • With an SQS or SNS destination, you must read the failed records from the stream again with those sequence numbers, before the stream retention period ends.
  • A tumbling window is a fixed time period that does not overlap the next one, for example each 5 minutes. With TumblingWindowInSeconds (up to 900 seconds), Lambda keeps state between invocations in the same window.
  • The function returns a state object (up to 1 MB for each shard), and Lambda passes it to the next invocation. isFinalInvokeForWindow marks the last invocation of the window, where the function writes the result.
  • Use a tumbling window to count or sum stream data with no external database.
  • The IteratorAge metric is the age of the last record in a batch when Lambda sends the batch to the function. A value that keeps going up means records arrive faster than the function processes them: the function falls behind the stream.
  • Without enhanced fan-out, all consumers of a shard share its read throughput, and Lambda polls each shard at a base rate of once each second.
  • Kinesis enhanced fan-out gives the function a dedicated read connection to each shard, and Kinesis pushes records to it. Use it when several applications read the same stream, or when you need lower latency. Kinesis charges extra for it.

All event source mappings

  • Processing is at least once. Duplicates can occur. Make the code idempotent (two runs of the same record give the same result as one run).
  • Use filter criteria on the ESM to stop events that the function does not need. Lambda does not invoke the function for them, so you pay for fewer invocations.
  • Up to 5 filters by default, with EventBridge pattern syntax. Sources: SQS, Kinesis, DynamoDB Streams, Amazon MQ, and Kafka.
  • For SQS, filter on the body key; Lambda removes messages that do not match from the queue.
  • Batches can contain up to 6 MB of payload (the synchronous invocation limit).

Concurrency, scaling, and throttling

Remember

  • Concurrency is the number of requests that a function processes at the same time, each in its own environment.
  • Concurrency equals average requests per second × average duration in seconds. Example: 100 × 0.5 seconds = 50.
  • The account concurrency limit is 1,000 for each Region by default. All functions in the Region share it.
  • When no concurrency is free, Lambda throttles new requests with TooManyRequestsException.
  • Lambda limits requests per second to 10 times the concurrency limit (10,000 by default).
  • The requests-per-second limit can throttle a very short function before the concurrency limit does.
  • Each function can add 1,000 execution environments every 10 seconds. Older study material shows a burst limit plus 500 each minute.
  • Reserved concurrency is both a maximum and a guaranteed minimum for one function.
  • Reserved concurrency has no charge. You set it on the function.
  • Requests over the reserved concurrency of a function are throttled.
  • Provisioned concurrency keeps pre-initialized environments, so requests have no cold start.
  • Provisioned concurrency has an extra charge, also when the environments are idle.
  • Set provisioned concurrency on a published version or an alias, not on $LATEST.
  • Requests over the provisioned concurrency spill over to on-demand concurrency with cold starts, unless reserved concurrency caps the function.
  • Choose reserved concurrency to cap a function or to keep capacity for it.
  • Choose provisioned concurrency to remove cold-start latency.
  • One function can use reserved and provisioned concurrency together.
  • Lambda always keeps 100 units of unreserved concurrency. With the 1,000 limit, you can reserve up to 900.
  • Reserved concurrency of 0 stops all invocations of a function, like an off switch.
  • Provisioned concurrency cannot be more than reserved concurrency on the same function.
  • Application Auto Scaling changes provisioned concurrency. Scheduled scaling handles a known daily peak.
  • Target tracking keeps LambdaProvisionedConcurrencyUtilization near a target value, for example 0.7.
  • Reserved concurrency caps database connections, because each environment opens its own connection.
  • A throttled synchronous caller gets HTTP 429 TooManyRequestsException and must retry with backoff.
  • Lambda keeps a throttled asynchronous event and retries for up to 6 hours. The caller sees no error.
  • When an SQS event source is throttled, Lambda reduces polling, and the messages stay in the queue.
  • The Throttles metric counts rejected requests. ConcurrentExecutions shows how many environments are busy.
  • ProvisionedConcurrencyUtilization is the share of provisioned environments in use.
  • A high ProvisionedConcurrencySpilloverInvocations value means that you need more provisioned concurrency.

Exam signals

  • "Function must not use more than 50 database connections" → reserved concurrency of 50, because each environment holds its own connection.
  • "Critical function must always have capacity, other functions use all of it" → reserved concurrency on the critical function, because no other function can use reserved concurrency.
  • "Predictable spike at 9 AM, no cold starts" → provisioned concurrency with scheduled Application Auto Scaling.
  • "Clients get 429 errors" → the concurrency limit is reached. Check Throttles, and raise the quota or the reserved concurrency.
  • "Stop a function immediately without deleting it" → reserved concurrency 0.

Explanation

Key facts

  • Concurrency is the number of requests that a function processes at the same time. Each one uses its own execution environment.
  • Concurrency = average requests per second × average duration in seconds. Example: 100 requests per second × 0.5 seconds = 50.
  • The account limit is 1,000 concurrent executions for each Region by default. All functions in the Region share it. When no concurrency is free, Lambda throttles new requests (rejects them with TooManyRequestsException).
  • Lambda also limits requests per second to 10 times the concurrency limit (10,000 by default). This limit matters for very short functions. Example: a 50 ms function at 20,000 requests per second needs only 1,000 concurrency, but Lambda throttles half of the requests.
  • Scaling rate: each function can add 1,000 execution environments every 10 seconds. Requests that arrive faster than this rate are throttled until Lambda catches up.

Versions, aliases, and traffic shifting

Remember

  • $LATEST is the unpublished version. You change code and settings only on $LATEST.
  • A published version is immutable. It locks the code and most settings.
  • A version locks the runtime, handler, memory, timeout, environment variables, layers, execution role, VPC, tracing, logging, and DLQ settings.
  • Version numbers increase, and Lambda never uses a version number again.
  • You cannot publish a new version if $LATEST did not change.
  • A qualified ARN ends with a version or an alias, for example :3 or :prod.
  • An unqualified ARN invokes $LATEST.
  • An alias is a named pointer to a version, and you can move it.
  • Callers use the alias ARN, so the callers do not change when you deploy.
  • A resource-based policy on an alias ARN applies to that alias only.
  • A weighted alias points to at most two versions, with a weight for the additional version.
  • Use a weighted alias for a canary release: send a small share of traffic to the new code first.
  • Both versions of a weighted alias must be published and must have the same execution role and DLQ configuration.
  • To find which version ran, check the START log line, the ExecutedVersion dimension, or the synchronous response header x-amz-executed-version.
  • AutoPublishAlias publishes a new version when code changes and points the alias to it.
  • DeploymentPreference in AWS SAM uses CodeDeploy to shift alias traffic.
  • Canary types are Canary10Percent5Minutes and the 10, 15, and 30 minute variants.
  • Linear types are Linear10PercentEvery1Minute and the every 2, 3, and 10 minute variants.
  • A canary deployment shifts traffic in two steps, for example 10 percent, then all traffic after 5 minutes.
  • A linear deployment shifts traffic in equal steps. Linear10PercentEvery1Minute moves all traffic after 10 minutes.
  • AllAtOnce moves all traffic in one step.
  • Choose canary to test new code on a small share of users for a short time.
  • Choose linear for a slow, steady increase. Choose AllAtOnce when you do not need a gradual shift.
  • CodeDeploy rolls back all alias traffic to the old version when a listed CloudWatch alarm goes off.
  • PreTraffic and PostTraffic hook functions run tests and report success or failure to CodeDeploy.
  • Without CodeDeploy, roll back with one UpdateAlias call that points the alias to the old version.

Exam signals

  • "Send 10% of traffic to the new version, then all after 10 minutes, roll back on errors" → SAM DeploymentPreference Canary10Percent10Minutes with alarms.
  • "Callers must not change the ARN on each release" → alias, because the alias ARN stays the same when you move the alias to a new version.
  • "Dev and prod must use different settings from the same function" → aliases point to different versions, each with its own locked environment variables.
  • "Run tests before traffic shifts" → PreTraffic hook.
  • "Staging must use only the version that QA approved" → an alias (for example, staging) that points to the approved version. Move the alias after each approval.

Explanation

Key facts

  • $LATEST is the unpublished version. You change code and settings only on $LATEST.
  • A published version is immutable (you cannot change it). It locks the code and most settings: runtime, handler, memory, timeout, environment variables, layers, execution role, VPC, tracing, logging, and DLQ settings. So a version always runs exactly as it ran when you tested it.
  • Version numbers increase and Lambda never uses a number again. If $LATEST did not change, you cannot publish a new version.
  • A qualified ARN ends with a version or alias (:3, :prod). An unqualified ARN invokes $LATEST.
  • An alias is a named pointer to a version. You can move it. Callers use the alias ARN and do not change when you deploy.
  • A resource-based policy on an alias ARN applies to that alias only. Example: a statement on the prod alias ARN gives no access to other versions or aliases.

Weighted alias (canary)

  • An alias can point to a maximum of two versions, with a weight for the additional version. Lambda sends that share of invocations to the additional version.
  • Use a weighted alias for a canary release: send a small share to the new code, watch for errors, then move all traffic.
  • Both versions must be published (not $LATEST), must have the same execution role, and must have the same DLQ configuration.
  • To find which version ran: the START log line shows the version, the ExecutedVersion metric dimension, or the x-amz-executed-version response header (synchronous).

Gradual deployment with AWS SAM and CodeDeploy

  • AutoPublishAlias publishes a new version when code changes and points the alias to it.
  • DeploymentPreference uses CodeDeploy to shift alias traffic. Types: Canary10Percent5Minutes (also 10, 15, 30 minutes), Linear10PercentEvery1Minute (also every 2, 3, 10 minutes), AllAtOnce.
  • Canary shifts traffic in two steps. Example: Canary10Percent5Minutes sends 10 percent to the new version, waits 5 minutes, then sends all traffic.
  • Linear shifts traffic in equal steps. Example: Linear10PercentEvery1Minute adds 10 percent each minute, so all traffic moves after 10 minutes.
  • AllAtOnce moves all traffic in one step.
  • Choose canary to test new code on a small share of users for a short time. Choose linear for a slow, steady increase. Choose AllAtOnce when you do not need a gradual shift, for example in a development stack.
  • Alarms: CodeDeploy rolls back when a listed CloudWatch alarm goes off. Rollback moves all alias traffic back to the old version.
  • Hooks: PreTraffic and PostTraffic Lambda functions run tests and report success or failure to CodeDeploy.
  • Rollback without CodeDeploy: point the alias back to the old version with one UpdateAlias call.

Packaging, layers, container images, and AWS SAM

Remember

  • A layer is a .zip archive with libraries, a custom runtime, or configuration files.
  • Lambda extracts layers to /opt.
  • Put a library in the runtime folder of the layer, for example /opt/python, so the code imports it with no path change.
  • A function can use up to 5 layers, with 250 MB total unzipped size including the function code.
  • Layers work only with .zip functions. A container image function puts its dependencies in the image.
  • A layer version is immutable, and a function refers to an exact layer version ARN.
  • To use a new layer version, update each function configuration to the new layer version ARN.
  • Layers share dependencies between functions and keep deployment packages small.
  • A container image must be in an Amazon ECR repository in the same Region as the function.
  • The ECR repository for a container image can be in another account.
  • A container image allows 10 GB uncompressed, Linux only, with one architecture for each image.
  • The runtime interface client (RIC) gets invocation events from Lambda and passes them to the handler.
  • An image without the runtime interface client cannot run on Lambda. AWS base images include it.
  • The runtime interface emulator (RIE) lets you test the image locally with HTTP requests. AWS base images include it.
  • You cannot change the package type (.zip or image) of an existing function. Create a new function.
  • AWS SAM is a CloudFormation transform: Transform: AWS::Serverless-2016-10-31.
  • The SAM transform expands AWS::Serverless::Function into a function, an execution role, and other resources.
  • A template that creates an IAM role needs CAPABILITY_IAM, or CloudFormation stops with InsufficientCapabilities.
  • aws cloudformation create-stack with a SAM template also needs CAPABILITY_AUTO_EXPAND for the transform.
  • sam deploy and aws cloudformation deploy use change sets, which show the processed template for review.
  • sam build builds the code and dependencies. sam deploy --guided deploys and saves the settings.
  • sam local invoke -e event.json runs the function locally with a test event.
  • sam local start-api runs a local API.
  • sam remote invoke invokes a deployed function in the AWS Cloud with --event or --event-file.
  • The Lambda console keeps up to 10 test events for each function.
  • Shareable test events are available to other users in the account.
  • sam sync sends code-only changes with the Lambda API and skips the CloudFormation deployment.
  • Use sam sync only for development stacks, because the stack then no longer matches the deployed code.

Exam signals

  • "Five functions use the same library, update it in one place" → layer.
  • "Dependencies are 3 GB" → container image (10 GB maximum), not layers, because a .zip function with its layers is limited to 250 MB unzipped.
  • "Container image function cannot use the shared layer" → build the dependency into the image. Container image functions do not support layers.
  • "Test the function locally with a sample event" → sam local invoke -e.
  • "create-stack with a SAM template fails with InsufficientCapabilities" → add CAPABILITY_IAM and CAPABILITY_AUTO_EXPAND.
  • "Test the deployed function in the cloud from the SAM CLI" → sam remote invoke.

Explanation

Layers

  • A layer is a .zip archive with libraries, a custom runtime, or configuration files.
  • Lambda extracts layers to /opt. Each runtime adds a path under /opt (for example, /opt/python or /opt/nodejs) to its library search path. Put the library in that folder in the layer .zip, so the function code can import it with no path change.
  • A function can use up to 5 layers. Total unzipped size with the function code: 250 MB.
  • Layers work only with .zip functions. A container image function puts its dependencies in the image.
  • A layer version is immutable. A function refers to an exact layer version ARN. To use a new layer version, update each function configuration to the new ARN.
  • Layers let you share dependencies between functions and keep deployment packages small.

Container images

  • Push the image to an Amazon ECR repository in the same Region as the function. The repository can be in another account.
  • Maximum 10 GB uncompressed. Linux images only. One architecture for each image.
  • The runtime interface client (RIC) is the program in the image that gets invocation events from Lambda and passes them to your handler. AWS base images include it. Other base images need it, or Lambda cannot run the image.
  • The runtime interface emulator (RIE) imitates the Lambda service on your computer, so you can test the image locally with HTTP requests. AWS base images include it.
  • You cannot change the package type (.zip or image) of an existing function. Create a new function.

AWS SAM

  • SAM is a CloudFormation transform: Transform: AWS::Serverless-2016-10-31. A transform is a macro that CloudFormation runs to expand short resource types into full CloudFormation resources. AWS::Serverless::Function becomes a function, an execution role, and other resources.
  • A capability is your acknowledgment that the template does something sensitive. Without it, CloudFormation stops with an InsufficientCapabilities error.
  • A template that creates an IAM role needs CAPABILITY_IAM. If you create a stack directly from a SAM template with aws cloudformation create-stack (no change set), CloudFormation also needs CAPABILITY_AUTO_EXPAND for the transform.
  • sam deploy and aws cloudformation deploy use change sets, which show the processed template for review.
  • sam build builds the code and dependencies. sam deploy --guided deploys and saves settings.
  • sam local invoke -e event.json runs the function locally with a test event. sam local start-api runs a local API.
  • sam remote invoke invokes a deployed function in the AWS Cloud with --event or --event-file.
  • Test events are JSON payloads. The Lambda console keeps up to 10 test events for each function. Shareable test events are available to other users in the account.
  • sam sync sends changes quickly to a development stack. For code-only changes, it calls the Lambda API directly and skips the CloudFormation deployment. The stack then no longer matches the deployed code (drift), so AWS recommends it for development stacks only.
  • sam logs gets function logs.

Permissions, secrets, and function URLs

Remember

  • The execution role controls what the function can do with other AWS services.
  • The resource-based policy (function policy) controls who can invoke or manage the function.
  • When the function calls a service, change the execution role.
  • When a service or another account calls the function, change the resource-based policy.
  • Set the resource-based policy with AddPermission (one statement) or PutResourcePolicy (full JSON).
  • A resource-based policy has a maximum size of 20 KB.
  • You can attach the resource-based policy to the function, a version, or an alias.
  • A service principal statement with no condition lets any resource of that service invoke the function.
  • Use aws:SourceArn to limit a service principal to one resource, for example one topic.
  • For Amazon S3, also add aws:SourceAccount, because a bucket ARN has no account ID.
  • AWSLambdaBasicExecutionRole gives permission to write CloudWatch Logs.
  • A function without log permission runs, but Lambda cannot write its logs to CloudWatch Logs.
  • An event source mapping reads the source with the execution role. Example: AWSLambdaSQSQueueExecutionRole.
  • Lambda always encrypts environment variables at rest, by default with an AWS managed key at no charge.
  • A customer managed KMS key controls key rotation and key access. Users need kms:Decrypt to see the values.
  • With a customer managed key alone, users with kms:Decrypt see the plaintext environment variable values in the console.
  • Encryption helpers encrypt values on the client side, so the console shows only the encrypted text.
  • With encryption helpers, the function code calls KMS Decrypt, and the execution role needs kms:Decrypt.
  • Store database credentials and API keys in AWS Secrets Manager, not in environment variables.
  • Secrets Manager rotates a secret automatically, and the function reads the current value at run time.
  • An environment variable keeps the old value until you change the function configuration.
  • Do not put access keys in code or environment variables. The function gets temporary credentials from the execution role.
  • A function URL is an HTTPS endpoint for one function: https://<url-id>.lambda-url.<region>.on.aws.
  • Attach a function URL to $LATEST or to an alias. You cannot attach it to a numbered version.
  • With AuthType AWS_IAM, callers sign with SigV4 and need lambda:InvokeFunctionUrl and lambda:InvokeFunction.
  • With AuthType NONE, the resource-based policy must still allow lambda:InvokeFunctionUrl and lambda:InvokeFunction for "*".
  • Without the two function URL policy statements, callers get 403 Forbidden, also with AuthType NONE.
  • The console and AWS SAM add the function URL policy statements. With the CLI or CloudFormation, you add the statements.
  • Configure CORS on the function URL, so that browser code from another domain can call it.
  • A function URL is reachable only from the public internet. You cannot make a private function URL in a VPC.
  • The BUFFERED invoke mode is the default and allows a 6 MB response.
  • The RESPONSE_STREAM invoke mode uses InvokeWithResponseStream and allows up to 200 MB.
  • Response streaming improves the time to first byte. Node.js managed runtimes support it natively.

Exam signals

  • "S3 event does not start the function" → the function resource-based policy does not allow s3.amazonaws.com. Amazon S3 calls the function, so the permission belongs in the resource-based policy.
  • "AccessDenied when the function writes to DynamoDB" → add the permission to the execution role, because the function is the caller.
  • "Store a database password with rotation" → Secrets Manager, because it rotates the secret for you.
  • "Environment variable must not be visible as plain text in the console" → encryption helpers with a customer managed key. Encryption at rest alone still shows the plaintext to users with key access.
  • "Simple HTTPS endpoint for one function, no API features needed" → function URL.
  • "Response is larger than 6 MB, or users must see the first bytes fast" → function URL with RESPONSE_STREAM.

  • Lambda always encrypts environment variables at rest. By default it uses an AWS managed key, at no charge, with no setup.
  • Use a customer managed KMS key to control key rotation and key access. Users then need kms:Decrypt to see the values. Users who have that access still see the plaintext values in the console.

Lambda in a VPC

Remember

  • By default, a function runs in a VPC that Lambda owns. The function reaches the internet but not your private resources.
  • Attach the function to private subnets and security groups to reach RDS, ElastiCache, or private EC2 resources.
  • A function attached to your VPC loses its default internet access.
  • To give a VPC function internet access, route its private subnets to a NAT gateway in a public subnet.
  • A public subnet does not give a function internet access or a public IP address.
  • Without a route to a NAT gateway, internet calls from a VPC function wait until they time out.
  • A VPC endpoint is a private connection from the VPC to an AWS service, with no internet.
  • Gateway endpoints support Amazon S3 and DynamoDB and have no extra charge.
  • Interface endpoints support most other services and have hourly and data charges.
  • A VPC function needs EC2 network interface permissions in its execution role: use AWSLambdaVPCAccessExecutionRole.
  • Lambda creates one Hyperplane ENI for each subnet and security group combination. Functions with the same combination share it.
  • A new VPC function is Pending and cannot be invoked while Lambda creates the ENI. This state can take several minutes.
  • After 14 days idle, Lambda removes the unused ENI, and the function becomes Inactive.
  • The next invocation of an Inactive function fails, and the function is Pending until Lambda has an ENI.
  • The target security group must allow inbound traffic from the function security group, or the connection times out.
  • RDS Proxy keeps a pool of open database connections and shares them between many function environments.
  • Use RDS Proxy when a function opens many short connections, so the function can scale without exhausting database connections.
  • Use a NAT gateway for internet access, a VPC endpoint for AWS services, and RDS Proxy for connection pooling.
  • Choose subnets in more than one Availability Zone for high availability.

Exam signals

  • "Function in a VPC times out when it calls an external API" → no NAT gateway route. Without a route to the internet, the call waits until the timeout.
  • "Function in a VPC must read S3 without internet access" → S3 gateway endpoint, because it keeps the traffic on the AWS network at no extra charge.
  • "Too many database connections from Lambda, and the function must keep scaling" → RDS Proxy.
  • "Too many database connections from Lambda, and a cap on scaling is acceptable" → reserved concurrency.
  • "Function must reach an ElastiCache cluster" → attach the function to the VPC and allow its security group.

Explanation

Key facts

  • By default, a function can reach the public internet but cannot reach private resources in your VPC. The function runs in a VPC that Lambda owns, not in your VPC.
  • Attach the function to private subnets and security groups to reach RDS, ElastiCache, or private EC2 resources.
  • After you attach it, the function reaches only what the VPC can reach. It loses its default internet access.
  • Internet access from a VPC function: route the private subnets to a NAT gateway in a public subnet. The NAT gateway sends the traffic to the internet with its own public IP address.
  • A public subnet does not give the function internet access or a public IP address. Without a route to a NAT gateway, calls to the internet wait until they time out.
  • To reach AWS services without the internet, add VPC endpoints. A VPC endpoint is a private connection from the VPC to an AWS service.
  • Gateway endpoints are for Amazon S3 and DynamoDB and have no extra charge. Interface endpoints support most other services and have hourly and data charges.
  • The execution role needs EC2 network interface permissions, because Lambda uses the role to create the network interfaces in your VPC. Use the AWSLambdaVPCAccessExecutionRole managed policy.
  • A Hyperplane ENI is a network interface that Lambda creates and manages in your subnet. It connects the function to your VPC. Lambda creates one for each subnet and security group combination, and functions with the same combination share it.
  • While Lambda creates the ENI, a new function is Pending and cannot be invoked. This can take several minutes.
  • After 14 days idle, Lambda removes the unused ENI and the function becomes Inactive. The next invocation fails, and the function is Pending again until Lambda has an ENI.
  • The target security group must allow inbound traffic from the function security group. Otherwise, the connection to the database or cache times out.
  • RDS Proxy keeps a pool of open database connections and shares them between many function environments. AWS recommends it for functions that open many short connections, so the function can scale without exhausting database connections.
  • Choose the tool for the problem: NAT gateway for internet access; VPC endpoint for AWS services without the internet; RDS Proxy for database connection pooling.
  • Choose subnets in more than one Availability Zone for high availability.

References: VPC access, Lambda with Amazon RDS (RDS Proxy), Gateway endpoints, AWS PrivateLink pricing (interface endpoints). Lab: Lab 1.7 VPC Lambda.

Logging, metrics, tracing, and extensions

Remember

  • Function output to stdout and stderr goes to CloudWatch Logs.
  • The default log group is /aws/lambda/<function-name>.
  • The Lambda log format is Text by default. The other format is JSON.
  • Log-level filtering sends only lines at or above the set level, so you store and pay for fewer logs.
  • Log-level filtering needs the JSON log format. With Text, Lambda sends all lines.
  • Application log levels are TRACE, DEBUG, INFO, WARN, ERROR, and FATAL.
  • System log levels, for lines such as START and REPORT, are DEBUG, INFO, and WARN.
  • A log level set in the function code overrides the console or API setting.
  • Use a custom log group when several functions must write to one log group.
  • Built-in metrics: Invocations, Errors, Throttles, Duration, ConcurrentExecutions, IteratorAge, DeadLetterErrors, DestinationDeliveryFailures.
  • For custom metrics, write logs in embedded metric format (EMF). CloudWatch extracts the metrics from the logs.
  • With embedded metric format, the code does not call PutMetricData and does not wait for an API call.
  • Turn on active tracing with TracingConfig Mode: Active, or Tracing: Active in AWS SAM.
  • X-Ray tracing needs xray:PutTraceSegments and xray:PutTelemetryRecords (AWSXRayDaemonWriteAccess) in the execution role.
  • X-Ray samples 1 Lambda request each second plus 5 percent of other requests.
  • You cannot change the X-Ray sampling rate for Lambda, so not every request has a trace.
  • The AWS::Lambda segment shows the time that Lambda uses to prepare the environment.
  • The AWS::Lambda::Function segment shows your code, with Init as a subsegment after a cold start.
  • To see each downstream call as a subsegment, instrument the SDK clients with the X-Ray SDK or AWS Distro for OpenTelemetry.
  • X-Ray annotations are indexed key-value pairs that you can use in filter expressions to search traces.
  • X-Ray does not index metadata, so you cannot search traces on metadata.
  • A published version locks the tracing mode.
  • An extension runs in the execution environment next to the function, with no change to the function code.
  • An external extension is a separate process that can run after the function returns.
  • Lambda installs an external extension from a layer in /opt/extensions.
  • An internal extension runs in the runtime process, as part of the function.
  • Extensions share memory, CPU, and permissions with the function. You pay for the time they use.
  • Extension size counts toward the 250 MB unzipped package limit.

Exam signals

  • "Find which downstream call is slow" → X-Ray active tracing with subsegments.
  • "Filter traces by customer ID" → X-Ray annotation.
  • "Send only ERROR logs from production without code change" → JSON log format and application log level ERROR.
  • "Publish a custom business metric with the least latency and effort" → embedded metric format.
  • "Send telemetry to a third-party tool without changing code" → Lambda extension.

Explanation

Logs

  • Output to stdout and stderr goes to CloudWatch Logs. The default log group is /aws/lambda/<function-name>.
  • Log format: Text (default) or JSON.
  • With log-level filtering, Lambda sends only log lines at or above the level that you set, so you store and pay for fewer logs. It needs the JSON format; with Text, Lambda sends all lines.
  • Application logs come from your code: TRACE, DEBUG, INFO, WARN, ERROR, FATAL.
  • System logs are the lines that Lambda writes, such as START and REPORT: DEBUG, INFO, WARN.
  • A log level set in the function code overrides the console or API setting.
  • You can send logs to a custom log group. Use it when several functions must write to one log group, for example all functions of one application, so you can query and set retention in one place.
  • Use CloudWatch Logs Insights to query logs.

Metrics

  • Built-in: Invocations, Errors, Throttles, Duration, ConcurrentExecutions, IteratorAge, DeadLetterErrors, DestinationDeliveryFailures.
  • Custom metrics: write logs in CloudWatch embedded metric format (EMF), a JSON log structure that names the metric values in the log line. CloudWatch extracts the metrics from the logs. The code does not call PutMetricData, so it does not wait for an API call.

AWS X-Ray

  • Turn on active tracing: TracingConfig Mode: Active, or Tracing: Active in SAM. Lambda then sends trace data for sampled requests to X-Ray, which builds a service map.
  • The execution role needs xray:PutTraceSegments and xray:PutTelemetryRecords (AWSXRayDaemonWriteAccess).
  • Sampling: 1 request each second plus 5 percent of other requests. You cannot change the sampling rate for Lambda. So you do not see a trace for every request.
  • Lambda records two segments: AWS::Lambda (the service) and AWS::Lambda::Function (your code). The service segment shows the time that Lambda uses to prepare the environment: it schedules, creates or unfreezes the environment, and downloads the code.
  • The function segment shows your code, including Init as an Initialization subsegment after a cold start (the newer trace format names it Init).
  • To see each downstream call, instrument the SDK clients with the X-Ray SDK or AWS Distro for OpenTelemetry. Each call then gets a subsegment with its own latency.
  • Annotations are indexed key-value pairs: use them in filter expressions to search traces, for example by customer ID.
  • Metadata stores any data with the trace, but X-Ray does not index it, so you cannot search on it.
  • Tracing mode is locked in a published version.

Extensions

  • An extension is a tool that runs in the execution environment next to your function, for example a monitoring or security agent. You add it without changing the function code.
  • An external extension is a separate process. It can run after the function returns, for example to send telemetry to a third-party tool. Lambda installs it from a layer in /opt/extensions.
  • An internal extension runs in the runtime process, as part of your function.
  • Extensions share memory, CPU, and permissions with the function. You pay for the time they use.
  • Extension size counts toward the 250 MB unzipped package limit.

Performance tuning and SnapStart

Remember

  • Lambda memory controls CPU. Lambda charges for memory × duration, in GB-seconds.
  • More memory can lower the cost when the extra CPU cuts the duration enough.
  • A function at 1,024 MB for 1 second costs the same as at 512 MB for 2 seconds.
  • To find the best memory size, test several sizes, for example with AWS Lambda Power Tuning.
  • AWS Compute Optimizer recommends a Lambda memory size from the last 14 days of metrics.
  • Compare Max Memory Used with Memory Size in the REPORT log line to find unused memory.
  • Keep init work small: import only the modules you need, and load rarely used objects lazily.
  • Lambda bills the Init phase of all on-demand functions since August 1, 2025. Older study material says Init is free.
  • Create clients and connections outside the handler, so warm invocations use them again.
  • Provisioned concurrency gives the lowest and most constant start latency, at extra cost.
  • SnapStart runs Init when you publish a version and starts new environments from a snapshot.
  • A SnapStart environment skips Init, so a slow framework startup no longer delays the cold start.
  • SnapStart supports Java 11 and later, Python 3.12 and later, and .NET 8 and later.
  • SnapStart works on published versions and aliases only, not on $LATEST.
  • SnapStart does not work with provisioned concurrency, Amazon EFS, or ephemeral storage above 512 MB.
  • SnapStart has no extra cost for Java. Python and .NET pay for snapshot caching and for each restore.
  • Content made during Init, such as unique IDs and random seeds, is the same in every restored SnapStart environment.
  • Use an after-restore runtime hook to create seeds, IDs, and connections again.

Exam signals

  • "Java function has a slow cold start, lowest cost fix" → SnapStart, because it has no extra cost for Java.
  • "Strict latency for every request, cost is not a concern" → provisioned concurrency, because its environments are already initialized before requests arrive.
  • "Find the best memory size for cost" → test memory sizes (for example, with Lambda Power Tuning), or use AWS Compute Optimizer recommendations.
  • "Restored environments create the same random value" → generate the value after the restore. SnapStart restores the same Init content in every environment.

Explanation

Key facts

  • Memory controls CPU. Lambda charges for memory × duration (GB-seconds). So more memory can lower cost if the duration falls enough.
  • Example: 1,024 MB for 1 second costs the same as 512 MB for 2 seconds; if the extra CPU cuts the time to 0.8 seconds, the larger size costs less.
  • Test several memory sizes and compare duration and cost. AWS Lambda Power Tuning is an open-source tool for this test.
  • AWS Compute Optimizer recommends a memory size for Lambda functions. It analyzes the last 14 days of metrics and marks memory as under-provisioned or over-provisioned.
  • The REPORT log line shows Duration, Billed Duration, Memory Size, and Max Memory Used. Compare Max Memory Used with Memory Size to find unused memory.
  • Keep init work small, because Init time adds to each cold start. Import only the modules you need, and load rarely used objects only when the code first needs them (lazy loading).
  • Since August 1, 2025, Lambda bills the Init time of all on-demand functions, including .zip functions on managed runtimes. Older study material says Init is free for those functions. That rule is out of date.
  • Create clients and connections outside the handler, so warm invocations use them again.
  • Provisioned concurrency gives the lowest and most constant start latency, at extra cost.

SnapStart

  • Lambda runs Init when you publish a version, takes a snapshot of the memory and disk, and starts new environments from the snapshot. A new environment skips Init, so a slow framework startup no longer delays the cold start.
  • Runtimes: Java 11 and later, Python 3.12 and later, .NET 8 and later.
  • Works on published versions and aliases only, not on $LATEST.
  • Not supported with provisioned concurrency, Amazon EFS, or ephemeral storage above 512 MB.
  • Cost: no extra cost for Java. Python and .NET pay for snapshot caching and for each restore.
  • Content made during Init (unique IDs, random seeds) is the same in every restored environment. Make unique content after the restore.
  • Runtime hooks are functions that Lambda runs just before it takes the snapshot and just after it restores one. Use an after-restore hook to create seeds, IDs, and connections again.

References: SnapStart, Optimizing static initialization, Memory and CPU, Compute Optimizer for Lambda, Lambda pricing (GB-seconds), Init phase billing. Lab: Lab 1.5 Concurrency.
