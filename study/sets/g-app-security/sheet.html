Data classification

Key facts

  • Data classification puts data into categories by sensitivity. The category controls encryption, logging, retention, and who can read the data.
  • PII (personally identifiable information) identifies a person. Examples: name with address, email address, phone number, national ID or social security number, passport number, driver's license number.
  • PHI (protected health information) is health data that is linked to a person. Examples: medical record number, health insurance number, diagnosis linked to a patient. HIPAA regulates PHI in the United States.
  • Payment data: credit card numbers and related data. PCI DSS regulates card data.
  • Credentials: passwords, private keys, AWS secret access keys. Never write them to code, logs, or environment variables in plain text. Use Secrets Manager (see the m07 set).
  • Collect and keep only the data that the application needs (data minimization). Data that you do not store cannot leak.
  • Tag resources with the classification. Use the tag in access policies (ABAC) and in audits.

Controls by classification

ControlSensitive data (PII, PHI, card data)
At restEncrypt. Use a customer managed KMS key when you must control the key policy or audit key use.

LogsDo not log the values. Mask them with CloudWatch Logs data protection if they can appear.

CloudWatch Logs managed data identifiers use the same categories: credentials, financial information, PII, PHI, and device identifiers (for example IP addresses and MAC addresses).

Exam signals

  • "Patient record number, insurance ID" → PHI.
  • "Email address, phone number, passport number" → PII.
  • "Reduce the risk of a data leak with the least effort" → do not collect or store the field at all.
  • "Different handling for sensitive and public data" → classify the data, then apply encryption, access, logging, and retention controls per class.

Sanitizing and masking data

Key facts

  • Validate input: check type, length, format, and allowed values before you use the data. API Gateway request validation rejects bad requests before the backend runs.
  • Encode output for its destination (HTML, SQL, shell). Use parameterized queries. Do not build queries from strings.
  • Sanitize logs: remove or mask sensitive fields in the code before you write a log line. Do not log full request bodies or tokens.

CloudWatch Logs data protection policies

  • A data protection policy audits and masks sensitive data in log events. It uses managed data identifiers (for example credit card numbers, AWS secret access keys) and custom data identifiers (your own regex).
  • CloudWatch Logs masks the data at ingestion. Log events that arrived before you created the policy are not masked.
  • Masked data stays masked at all egress points, including Logs Insights, metric filters, and subscription filters.
  • Only principals with the logs:Unmask IAM permission can see the original values.
  • Two levels: an account-level policy (all existing and future log groups) and a policy on one log group. If both exist, both apply.
  • One log group can have only one log group-level policy. That policy can list many data identifiers.
  • Works with the Standard and Infrequent Access log classes.
  • Findings create the LogEventsWithFindings metric in the AWS/Logs namespace. You can send audit findings to CloudWatch Logs, Amazon S3, or Firehose.

S3 Object Lambda (redact on read)

  • An Object Lambda Access Point runs a Lambda function on S3 GET, LIST, and HEAD requests. The function can redact PII before the data reaches the caller. For GET, the function returns the data with WriteGetObjectResponse. For HEAD and LIST, the function returns the response as its own JSON result.
  • One copy of the data serves callers with different views. You do not store a redacted copy.
  • Availability: since November 7, 2025, S3 Object Lambda is available only to existing customers and select partners. See the m03 set.

Exam signals

  • "Credit card numbers appear in CloudWatch Logs; only the security team may see them" → data protection policy, and logs:Unmask for the security team only.
  • "Mask sensitive data in all log groups, including new ones" → account-level data protection policy.
  • "Old log events still show the data after the policy was added" → expected. Masking applies only to new events.
  • "Support staff see only the last 4 digits" → masking in the application.
  • "Must get the original value back later, only for authorized systems" → tokenization or encryption, not masking.

References: Help protect sensitive log data with masking, S3 Object Lambda (availability note). Related lab: Lab 3.7 Object Lambda.

Bearer tokens and JWT validation

Key facts

  • A bearer token gives access to anyone who holds it. Send it only over HTTPS, normally in the Authorization header. Do not put it in a URL or in logs.
  • A JWT has three parts with dots between them: header, payload (claims), and signature. The header and payload are base64url-encoded JSON. Anyone can decode them. Encoding is not encryption.
  • The header has kid (key ID) and alg. Amazon Cognito signs tokens with RS256.
  • Validate the signature with the public key from the issuer JSON Web Key Set (JWKS). Cognito JWKS URL: https://cognito-idp.<Region>.amazonaws.com/<userPoolId>/.well-known/jwks.json.
  • Cache the public keys by kid. If a token has the correct issuer but an unknown kid, refresh the cache. Cognito can rotate signing keys.
  • For Node.js, AWS recommends the aws-jwt-verify library.

Claims to check (Cognito user pool tokens)

ClaimCheck
expThe token is not expired. You can check this offline.

token_useid or access, as your API expects.

A valid signature and exp do not show revocation. If the app must honor sign-out before expiry, keep access token lifetimes short or check the token with Cognito.

Who validates the token

  • REST API Cognito authorizer (COGNITO_USER_POOLS): API Gateway validates the token. No code.
  • HTTP API JWT authorizer: validates kid, iss, aud or client_id, exp, nbf, iat, and route scopes. It checks client_id only when aud is not present. It caches public keys for up to 2 hours.
  • Lambda authorizer: your code validates the token (for any issuer, or extra rules).
  • Application Load Balancer with Cognito authentication: the ALB sends signed claims to targets in the x-amzn-oidc-data header. The target verifies them.

Exam signals

  • "Verify a Cognito token in a Lambda function" → check signature with the JWKS, then exp, iss, aud/client_id, token_use.
  • "Decoding the token shows the claims, so the app trusts them" → wrong. Decoding does not verify. Check the signature.
  • "Signature fails after some weeks" → the app hardcoded one key. Fetch keys from the JWKS by kid.
  • "Validate JWTs on an HTTP API without code" → JWT authorizer.

References: Verifying JSON web tokens, HTTP API JWT authorizers. Related lab: Lab 4.5 Cognito user pool.

Application-level authorization

REST API Cognito authorizer and scopes

  • No authorization scopes on the method: API Gateway treats the token as an ID token.
  • Authorization scopes on the method: API Gateway treats the token as an access token. The call succeeds if any method scope matches a scope in the token. Otherwise the result is 401 Unauthorized.
  • The optional token validation regex checks the aud claim. Access tokens have no aud unless the token is bound to a resource server, so this regex rejects them.
  • Pass claims to the backend: $context.authorizer.claims.sub, or $context.authorizer.claims['custom:role'] for names with a colon.

Cognito groups

  • The cognito:groups claim is in both the ID token and the access token. Use it for role-based checks in the backend or in a Lambda authorizer.
  • A group can have an IAM role. With an identity pool, the user gets temporary AWS credentials for that role.
  • A user in several groups: the group with the lowest precedence value sets cognito:preferred_role in the ID token. Groups cannot be nested.

Exam signals

  • "Only clients with the orders.write scope can call POST" → access token plus authorization scopes on the method.
  • "Admins can delete, other users can only read" → Cognito groups, and check cognito:groups.
  • "Custom token from a third-party issuer on a REST API" → Lambda authorizer.
  • "Pass the tenant ID from the authorizer to the backend" → authorizer context (string value).
  • "First call to /orders works, then /invoices returns 403 for 5 minutes" → cached policy covers one method only.

Cross-service authentication

OAuth 2.0 client credentials (machine to machine)

  • A service with no user gets an access token with its own client ID and client secret.
  • Setup: an app client with a client secret (confidential client), a resource server, and custom scopes. Scope format: resourceServerIdentifier/scopeName, for example orders-api/orders.read.
  • Get the token from the token endpoint (/oauth2/token, needs a user pool domain), or call the GetClientToken API (no domain needed).
  • The result is an access token that holds only custom scopes. There is no ID token and no user.
  • The API checks the scopes, for example with a REST API Cognito authorizer with authorization scopes, or an HTTP API JWT authorizer.
  • Cache the token until it expires. Cognito bills M2M by active app clients and token requests.

IAM authorization with SigV4

  • Use it when both services run on AWS with IAM roles. No secret to store or rotate.
  • API Gateway: set the method authorization to AWS_IAM. The caller needs execute-api:Invoke and signs the request with SigV4.
  • Lambda function URL: set AuthType to AWS_IAM. The caller signs with SigV4. Since October 2025, new function URLs need both lambda:InvokeFunctionUrl and lambda:InvokeFunction. Older study material lists only lambda:InvokeFunctionUrl.
  • Cross-account callers need an allow in their identity policy and in the resource policy (API resource policy or function resource-based policy).

Mutual TLS (REST API)

  • Both sides show X.509 certificates. Common for IoT and business-to-business clients.
  • Needs a Regional custom domain name with the TLS_1_2 security policy, an ACM certificate for the domain, and a truststore (.pem file of CA certificates) in Amazon S3.
  • Disable the default execute-api endpoint, or clients can skip mutual TLS.
  • API Gateway does not check revocation. Use a Lambda authorizer for revocation checks. API Gateway forwards client certificates to Lambda authorizers.
  • Untrusted or expired client certificate: the handshake fails and the client gets 403.
  • Not supported for private APIs.

Private APIs

  • A private API is a REST API that clients call only from a VPC, through an interface VPC endpoint for execute-api. Traffic does not leave the Amazon network.
  • Only REST APIs can be private. HTTP APIs cannot.
  • Use the API resource policy with aws:SourceVpc or aws:SourceVpce to allow only your VPCs or endpoints.

Exam signals

  • "Backend service calls an API with no user, OAuth scopes required" → Cognito client credentials grant with a resource server and custom scopes.
  • "Lambda in one account calls an API in another account, no secrets" → AWS_IAM authorization, SigV4, and a resource policy.
  • "Partners must authenticate with client certificates" → mutual TLS on a Regional custom domain, and disable the default endpoint.
  • "API reachable only from inside the VPC" → private REST API, interface endpoint, resource policy.

References: Scopes, M2M, and resource servers, REST API IAM permissions, Function URL access control, Mutual TLS for REST APIs, Private REST APIs.

Multi-tenant data access

Isolation models

ModelHowStrengthCost
SiloOne resource for each tenant (table, bucket, or account)Strongest isolation, simple per-tenant costHigher; more resources to manage
PoolShared resource. A tenant key is in every item or object key.Isolation depends on policies and codeLower; best use of capacity
BridgeMix: some tiers silo, some poolPer tierPer tier

DynamoDB fine-grained access control

  • Make the tenant ID or user ID the partition key.
  • Use the dynamodb:LeadingKeys condition with a policy variable. LeadingKeys must use the ForAllValues modifier, for example ForAllValues:StringEquals.
  • Do not allow Scan. A scan returns all items, whatever the leading keys.
  • Limit attributes with dynamodb:Attributes. Also require dynamodb:Select = SPECIFIC_ATTRIBUTES and limit dynamodb:ReturnValues. Without them, a read with no projection returns all attributes.
  • Policy variables need "Version": "2012-10-17" in the policy.

Policy variables

VariableValue
${cognito-identity.amazonaws.com:sub}The identity ID from the Cognito identity pool. It is not the sub from the user pool.
${aws:username}The IAM user name.
${aws:PrincipalTag/tenant}A tag on the principal (ABAC). Identity pools can map token claims to principal tags (attributes for access control). Do not map an attribute that users can change themselves.

S3 prefix for each tenant

  • Allow s3:GetObject and s3:PutObject on arn:aws:s3:::bucket/${cognito-identity.amazonaws.com:sub}/*.
  • Allow s3:ListBucket on the bucket with a s3:prefix condition for the same prefix.

Application rules

  • Take the tenant ID from the verified token or the authorizer context. Never take it from the request body, a query string, or a header that the client controls.
  • Add the tenant key to every query in the code. Policies are a second layer, not a replacement for the code check.

Exam signals

  • "Mobile users may read and write only their own items in one DynamoDB table" → identity pool role with dynamodb:LeadingKeys = ${cognito-identity.amazonaws.com:sub}.
  • "Each user has a private folder in one bucket" → policy variable in the object ARN.
  • "Tenant ID comes from a request header; a user read another tenant's data" → take the tenant ID from the verified token.
  • "Strict isolation and per-tenant encryption keys for regulated tenants" → silo model.

References: DynamoDB fine-grained access control, Cognito identity pool IAM roles, Attributes for access control. Related lab: Lab 4.6 Cognito identity pool.

Encryption in transit

Key facts

  • Use TLS for every connection: client to edge, edge to origin, and service to database.
  • Deny plain HTTP to Amazon S3 with a bucket policy: "Effect": "Deny" when "aws:SecureTransport": "false".
  • Requests to SQS queues and SNS topics with SSE turned on must use HTTPS and Signature Version 4.
  • Private REST APIs support only TLS 1.2.

  • To attach an ACM-managed certificate directly to an EC2 instance, you need Nitro Enclaves. For public certificates on EC2, AWS recommends the ACME protocol. ACM also offers exportable public certificates for an extra charge.

At rest compared with in transit

ServiceAt rest by default?
Amazon S3Yes. SSE-S3 for all new objects since January 5, 2023. You cannot turn it off.

Amazon SQSYes. SSE-SQS is the default for new queues created without encryption attributes (over HTTPS).
Amazon SNSNo. Set a KMS key (KmsMasterKeyId) on the topic.

Encryption at rest does not protect data on the network. Encryption in transit does not protect stored data. You need both for sensitive data.

Exam signals

  • "Bucket must reject requests that do not use HTTPS" → bucket policy deny on aws:SecureTransport false.
  • "Users who type http:// must reach the site securely" → viewer protocol policy Redirect HTTP to HTTPS.
  • "Certificate for CloudFront is not in the list" → request or import it in us-east-1.
  • "SNS messages must be encrypted at rest" → turn on SSE with a KMS key. It is not on by default.

Certificates and SSH keys for development

EC2 key pairs

  • A key pair has a public key and a private key. EC2 puts the public key on the instance (Linux: ~/.ssh/authorized_keys). You keep the private key.
  • When EC2 creates the key pair, you can save the private key one time only. EC2 does not keep a copy, so you cannot recover a lost private key from AWS.
  • Exception: a key pair that CloudFormation creates (AWS::EC2::KeyPair with no PublicKeyMaterial) stores the private key in Parameter Store as /ec2/keypair/<key_pair_id>.
  • Types: RSA (Linux and Windows) and ED25519 (Linux only). EC2 does not accept DSA.
  • Private key file formats: .pem (OpenSSH) or .ppk (PuTTY). On Linux and macOS, run chmod 400 on the file.
  • Import: create the key pair with a tool such as ssh-keygen, then import only the public key (aws ec2 import-key-pair). The private key never leaves your machine.
  • Windows instances: the private key decrypts the administrator password.
  • Quota: 5,000 key pairs for each Region (you can request more).
  • Session Manager (Systems Manager) connects with no SSH key and no open inbound port.

Certificates

NeedUse
Local development or a test endpoint onlySelf-signed certificate, for example with OpenSSL. Clients do not trust it by default.
Internal services, private hostnames, mutual TLS client certificatesAWS Private CA (private root and subordinate CAs). Private certificates are trusted only where you install your CA.

  • Private CA charges a monthly fee for each CA and a fee for each certificate that it issues. Exception: private certificates whose private key you cannot access are free. Examples are certificates used only with integrated services (ELB, CloudFront, API Gateway).
  • Private CAs are Regional. You cannot copy a CA to another Region.
  • You can import a third-party or self-signed certificate into ACM. ACM does not renew imported certificates.
  • Never commit private keys to source control. Store them in Secrets Manager or Parameter Store SecureString.

Exam signals

  • "Lost the .pem file for an EC2 instance" → AWS cannot give it back. Use another access method, then add a new public key.
  • "Use an existing SSH key from the developer's laptop" → import the public key.
  • "Internal microservices need TLS certificates that the company controls" → AWS Private CA.
  • "HTTPS on a laptop for local tests, no cost" → self-signed certificate.
  • "Shell access with no key pairs and no port 22" → Session Manager.
