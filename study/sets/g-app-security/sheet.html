Data classification

Remember

  • Data classification puts data into categories by sensitivity.
  • The classification category controls encryption, logging, retention, and who can read the data.
  • PII identifies a person. Examples: email address, phone number, passport number, national ID number.
  • PHI is health data that is linked to a person. Examples: medical record number, health insurance number.
  • HIPAA regulates PHI in the United States.
  • PCI DSS regulates payment card data.
  • Never write credentials to code, logs, or environment variables in plain text.
  • Store credentials in Secrets Manager.
  • Data minimization: collect and keep only the data that the application needs.
  • Data that you do not store cannot leak.
  • A classification tag on a resource lets an IAM policy compare it with a tag on the user (ABAC).
  • Encrypt sensitive data at rest.
  • Use a customer managed KMS key when you must control the key policy or audit key use.
  • You cannot change the key policy of an AWS managed KMS key.
  • Use TLS on every connection for sensitive data, also inside the VPC.
  • Give least-privilege access to sensitive data: separate it from other data, or restrict access by attribute.
  • Do not log sensitive values, because a value in a log is a leak.
  • If sensitive values can still appear in logs, mask them with a CloudWatch Logs data protection policy.
  • Delete sensitive data when it is no longer needed: S3 Lifecycle, DynamoDB TTL, log group retention.
  • CloudWatch Logs managed data identifiers cover credentials, financial information, PII, PHI, and device identifiers.

Exam signals

  • "Patient record number, insurance ID" → PHI, because these values link health data to one person.
  • "Email address, phone number, passport number" → PII, because each value identifies a person but holds no health data.
  • "Reduce the risk of a data leak with the least effort" → do not collect or store the field at all. A field that you do not store needs no encryption, key, or access policy.
  • "Different handling for sensitive and public data" → classify the data, then apply encryption, access, logging, and retention controls per class.

Explanation

Key facts

  • Data classification puts data into categories by sensitivity. The category controls encryption, logging, retention, and who can read the data.
  • PII (personally identifiable information) identifies a person. Examples: name with address, email address, phone number, national ID or social security number, passport number, driver's license number.
  • PHI (protected health information) is health data that is linked to a person. Examples: medical record number, health insurance number, diagnosis linked to a patient. HIPAA regulates PHI in the United States.
  • Payment data: credit card numbers and related data. PCI DSS regulates card data.
  • Credentials: passwords, private keys, AWS secret access keys. Never write them to code, logs, or environment variables in plain text. Use Secrets Manager (see the m07 set).
  • Collect and keep only the data that the application needs (data minimization). Data that you do not store cannot leak.
  • Tag resources with the classification, for example classification = confidential. An IAM policy can then compare the tag on the resource with a tag on the user (ABAC, attribute-based access control).
  • Auditors can also find all confidential resources by the classification tag.

Sanitizing and masking data

Remember

  • Validate input: check type, length, format, and allowed values before you use the data.
  • API Gateway request validation (REST APIs) checks required parameters and checks the body against a JSON schema model.
  • A request that fails API Gateway request validation gets a 400 error, and API Gateway does not call the backend.
  • Encode output for its destination: HTML, SQL, or shell.
  • To stop SQL injection, use a parameterized query, so the database treats the value only as data.
  • To stop cross-site scripting, HTML-encode user input before a browser shows it.
  • Mask or remove sensitive fields in the code before the code writes a log line.
  • Do not log full request bodies or tokens.
  • Masking hides all or part of a value. You cannot get the original back from the masked value.
  • Redaction removes the value, and nobody can get it back.
  • Tokenization replaces the value with a random token, and only the token store can give the original back.
  • Encryption gives the original value back only to a caller with the key (KMS permission).
  • Hashing is a one-way digest that cannot give the original value back.
  • Use masking when a person needs to see part of the value, for example the last 4 digits.
  • Use redaction when nobody needs the value.
  • Use tokenization or encryption when an authorized system must get the original value later.
  • Tokenization keeps the real value in one store, so other systems hold only tokens.
  • Use hashing when you only need to check that two values are the same.
  • A CloudWatch Logs data protection policy finds sensitive data in log events, masks it, and can report each finding (audit).
  • A managed data identifier is a pattern that AWS maintains, for example for credit card numbers.
  • A custom data identifier is your own regular expression.
  • CloudWatch Logs masks data at ingestion, so log events from before the policy stay unmasked.
  • Masked log data stays masked in Logs Insights, metric filters, and subscription filters.
  • Only principals with the logs:Unmask IAM permission can see the original values.
  • An account-level data protection policy covers all existing and future log groups.
  • When an account-level policy and a log group-level policy both exist, both apply.
  • One log group can have only one log group-level policy, and that policy can list many data identifiers.
  • Data protection works with both log classes: Standard and Infrequent Access.
  • Data protection findings create the LogEventsWithFindings metric in the AWS/Logs namespace.
  • Data protection audit findings can go to CloudWatch Logs, Amazon S3, or Firehose.
  • An Object Lambda Access Point runs a Lambda function on S3 GET, LIST, and HEAD requests, for example to redact PII.
  • For GET, the Object Lambda function returns the data with WriteGetObjectResponse.
  • For HEAD and LIST, the Object Lambda function returns the response as its own JSON result.
  • S3 Object Lambda serves different views from one copy of the data, so you do not store a redacted copy.
  • Since November 7, 2025, S3 Object Lambda is available only to existing customers and select partners.

Exam signals

  • "Credit card numbers appear in CloudWatch Logs; only the security team may see them" → data protection policy, and logs:Unmask for the security team only.
  • "Mask sensitive data in all log groups, including new ones" → account-level data protection policy.
  • "Old log events still show the data after the policy was added" → expected. Masking applies only to new events.
  • "Support staff see only the last 4 digits" → masking in the application, because staff need only part of the value.
  • "Must get the original value back later, only for authorized systems" → tokenization or encryption, not masking. You cannot get the original value back from a masked value.

Explanation

Key facts

  • Validate input: check type, length, format, and allowed values before you use the data. API Gateway request validation (REST APIs) checks required parameters and checks the body against a JSON schema model.
  • A request that fails API Gateway request validation gets a 400 error, and API Gateway does not call the backend.
  • Encode output for its destination (HTML, SQL, shell). If code adds user input directly into a SQL string, input such as ' OR '1'='1 changes the query itself (SQL injection). A parameterized query sends the value separately, so the database treats it only as data.
  • In the same way, HTML encoding stops user input from running as a script in a browser (cross-site scripting).
  • Sanitize logs: remove or mask sensitive fields in the code before you write a log line. Do not log full request bodies or tokens.

CloudWatch Logs data protection policies

  • A data protection policy finds sensitive data in log events, masks it, and can report each finding (audit). It uses managed data identifiers and custom data identifiers.
  • A managed data identifier is a pattern that AWS maintains, for example for credit card numbers or AWS secret access keys. A custom data identifier is your own regular expression.
  • CloudWatch Logs masks the data at ingestion, when it receives and stores the log event. Log events that arrived before you created the policy are not masked.
  • Masked data stays masked everywhere that data leaves CloudWatch Logs, including Logs Insights, metric filters, and subscription filters.
  • Only principals with the logs:Unmask IAM permission can see the original values.
  • Two levels: an account-level policy (all existing and future log groups) and a policy on one log group. If both exist, both apply.
  • One log group can have only one log group-level policy. That policy can list many data identifiers.
  • CloudWatch Logs has two log classes: Standard and Infrequent Access (a cheaper class with fewer features). Data protection works with both.
  • Findings create the LogEventsWithFindings metric in the AWS/Logs namespace. You can send audit findings to CloudWatch Logs, Amazon S3, or Firehose.

S3 Object Lambda (redact on read)

  • An Object Lambda Access Point runs a Lambda function on S3 GET, LIST, and HEAD requests. The function can redact PII before the data reaches the caller.
  • For GET, the function returns the data with WriteGetObjectResponse. For HEAD and LIST, the function returns the response as its own JSON result.
  • One copy of the data serves callers with different views. You do not store a redacted copy.
  • Availability: since November 7, 2025, S3 Object Lambda is available only to existing customers and select partners. See the m03 set.

Bearer tokens and JWT validation

Remember

  • A bearer token gives access to anyone who holds it.
  • Send a bearer token only over HTTPS, normally in the Authorization header.
  • Never put a bearer token in a URL or in logs, because anyone who reads the logs can use the token.
  • A JWT has three parts: header, payload (claims), and signature.
  • Anyone can decode the base64url-encoded JWT header and payload, because encoding is not encryption.
  • The JWT header field kid names the signing key, and alg names the signing algorithm.
  • Amazon Cognito signs tokens with RS256 and a private key that only Cognito holds.
  • Validate the JWT signature with the public key from the issuer JWKS (JSON Web Key Set).
  • A valid signature proves that Cognito issued the token and that nobody changed the claims.
  • The Cognito JWKS URL is https://cognito-idp.<Region>.amazonaws.com/<userPoolId>/.well-known/jwks.json.
  • Cache the JWKS public keys by kid, so that the app does not download the JWKS for each request.
  • Refresh the key cache when a token has the correct issuer but an unknown kid.
  • Cognito can rotate signing keys, and a new key has a new kid.
  • For Node.js, AWS recommends the aws-jwt-verify library.
  • The exp check confirms that the token is not expired, and you can do it offline.
  • The iss claim must match https://cognito-idp.<Region>.amazonaws.com/<userPoolId>.
  • The aud claim (ID token) or client_id claim (access token) must match your app client ID.
  • The token_use claim must be id or access, as your API expects.
  • Without the iss check, the app accepts tokens from any user pool.
  • Without the aud or client_id check, the app accepts tokens issued to other app clients.
  • Without the token_use check, the app accepts an ID token where it expects an access token.
  • A local signature and exp check cannot detect a revoked token.
  • Sign-out or a RevokeToken call revokes a token before it expires.
  • To honor sign-out before expiry, keep access token lifetimes short or check the token with Cognito.
  • To detect revocation, call a Cognito API with the token, for example GetUser, and Cognito rejects a revoked token.
  • The ID token tells who the user is and holds user attributes and aud.
  • The access token tells what the caller can do and holds scope, cognito:groups, and client_id.
  • Use the access token, not the ID token, for API authorization with scopes.
  • Send the ID token when the backend needs user attributes such as email or name.
  • A REST API Cognito authorizer (COGNITO_USER_POOLS) validates the token with no code.
  • An HTTP API JWT authorizer validates kid, iss, aud or client_id, exp, nbf, iat, and route scopes.
  • An HTTP API JWT authorizer checks client_id only when aud is not present.
  • An HTTP API JWT authorizer caches public keys for up to 2 hours.
  • After a key rotation, keep the old signing key valid for a grace period, because a JWT authorizer caches public keys.
  • A Lambda authorizer validates the token in your code, for an unsupported issuer or for extra rules.
  • An ALB with Cognito authentication sends signed claims to targets in the x-amzn-oidc-data header.
  • An ALB target verifies the x-amzn-oidc-data signature to know that the load balancer created the claims.

Exam signals

  • "Verify a Cognito token in a Lambda function" → check signature with the JWKS, then exp, iss, aud/client_id, token_use.
  • "Decoding the token shows the claims, so the app trusts them" → wrong, check the signature. Decoding does not verify the token.
  • "Signature fails after some weeks" → fetch keys from the JWKS by kid. The app hardcoded one key, and Cognito rotated the key, so new tokens have a kid that the app does not know.
  • "Validate JWTs on an HTTP API without code" → JWT authorizer, because API Gateway does the checks for you. The REST API Cognito authorizer is not available on HTTP APIs.

Explanation

Key facts

  • A bearer token gives access to anyone who holds it. The API does not check who sends it.
  • Send a bearer token only over HTTPS, normally in the Authorization header. Do not put it in a URL or in logs.
  • Browsers, proxies, and servers record full URLs in history and access logs. Anyone who reads those logs can use the token until it expires.
  • A JWT has three parts with dots between them: header, payload (claims), and signature.
  • The JWT header and payload are base64url-encoded JSON. Anyone can decode them. Encoding is not encryption.
  • The header has kid (key ID: which key signed the token) and alg (the signing algorithm).
  • Amazon Cognito signs tokens with RS256, an RSA signature with SHA-256. Cognito signs with a private key that only it holds. Anyone can check the signature with the matching public key.
  • Validate the signature with the public key from the issuer JSON Web Key Set (JWKS). The JWKS is a public JSON document that lists the current public keys of the issuer.
  • A valid signature proves that Cognito issued the token and that nobody changed the claims.
  • Cognito JWKS URL: https://cognito-idp.<Region>.amazonaws.com/<userPoolId>/.well-known/jwks.json.
  • Cache the public keys by kid, so that the app does not download the JWKS for each request. If a token has the correct issuer but an unknown kid, refresh the cache. Cognito can rotate signing keys, and a new key has a new kid.
  • For Node.js, AWS recommends the aws-jwt-verify library.

Claims to check (Cognito user pool tokens)

Each check stops a different misuse.

  • Without the iss check, the app accepts tokens from any user pool.
  • Without the aud or client_id check, the app accepts tokens issued to other app clients.
  • Without the token_use check, the app accepts an ID token where it expects an access token.

A valid signature and exp do not show revocation. Revocation cancels a token before it expires, for example when the user signs out or the app calls RevokeToken.

A local check does not contact Cognito, so it cannot see the revocation. If the app must honor sign-out before expiry, keep access token lifetimes short or check the token with Cognito.

For revocation only, make a Cognito API request that uses the token, for example GetUser; Cognito rejects a revoked token. Expiry is a different check: compare exp offline.

Send the ID token when the backend needs user attributes such as email or name. Send the access token when the API checks scopes.

Who validates the token

  • REST API Cognito authorizer (COGNITO_USER_POOLS): API Gateway validates the token. No code.
  • HTTP API JWT authorizer: validates kid, iss, aud or client_id, exp, nbf (not before), iat (issued at), and route scopes. It checks client_id only when aud is not present.
  • The HTTP API JWT authorizer caches public keys for up to 2 hours. When you rotate signing keys, keep the old key valid for a grace period.
  • Lambda authorizer: your code validates the token. Use it for an issuer that the built-in authorizers do not support, or for extra rules.
  • Application Load Balancer with Cognito authentication: the ALB sends signed claims to targets in the x-amzn-oidc-data header. The target verifies the signature, so that it knows the load balancer created the claims.

Application-level authorization

Remember

  • A REST API Cognito authorizer with no scopes on the method treats the token as an ID token and verifies the identity, not scopes.
  • A REST API Cognito authorizer with authorization scopes on the method treats the token as an access token.
  • A scoped method allows the call if any method scope matches a scope in the token.
  • A scoped method returns 401 Unauthorized when no method scope matches a token scope.
  • The optional token validation regex of a Cognito authorizer checks the aud claim.
  • An access token has no aud claim unless the token is bound to a resource server.
  • The token validation regex rejects an access token that has no aud claim.
  • The backend can trust authorizer claims, because API Gateway verified the token.
  • In a mapping template, read a claim with $context.authorizer.claims.sub.
  • For a claim name with a colon, use $context.authorizer.claims['custom:role'].
  • The cognito:groups claim is in both the ID token and the access token.
  • Use cognito:groups for role-based checks in the backend or in a Lambda authorizer.
  • A Cognito group can have an IAM role, and an identity pool gives the user temporary credentials for that role.
  • Use group IAM roles when the app calls AWS services directly and each group needs different AWS permissions.
  • For a user in several groups, the group with the lowest precedence value sets cognito:preferred_role in the ID token.
  • Cognito groups cannot be nested.
  • A TOKEN Lambda authorizer receives one header with a bearer token.
  • A REQUEST Lambda authorizer receives headers, query strings, stage variables, and $context variables.
  • AWS recommends the REQUEST type, because it can use several identity sources and a more specific cache key.
  • Use TOKEN when one bearer token is all that the function needs.
  • Use REQUEST when the decision also uses the path, the HTTP method, a query string, or more than one header.
  • A Lambda authorizer must return principalId and policyDocument.
  • The authorizer policyDocument is an IAM policy that allows or denies execute-api:Invoke.
  • A Lambda authorizer can also return a context map and a usageIdentifierKey.
  • Authorizer context values can be only strings, numbers, or booleans, not JSON objects or arrays.
  • The backend reads authorizer context with $context.authorizer.<key>.
  • With Lambda proxy integration, the backend reads event.requestContext.authorizer.<key>.
  • The Lambda authorizer result cache TTL has a default of 300 seconds and a maximum of 3,600 seconds.
  • A Lambda authorizer cache TTL of 0 turns caching off.
  • The TOKEN cache key is the token header, and the REQUEST cache key is all identity sources.
  • With REQUEST and caching on, a missing identity source gives 401, and API Gateway does not call the function.
  • A Deny policy from a Lambda authorizer gives the client 403.
  • A cached authorizer policy applies to later requests with the same cache key to other methods too.
  • Return a policy that covers every method that the caller may use, or use a wildcard resource.
  • A cached policy for only one method gives 403 on other methods during the TTL.
  • An HTTP API Lambda authorizer can return a simple response (isAuthorized) instead of an IAM policy.
  • ACL keeps a list of principals for each resource and fits few resources and per-object sharing.
  • RBAC decides by the role of the user, for example a Cognito group, and fits fixed job functions.
  • ABAC decides by attributes of the user and the resource, and fits many resources and tenants.
  • With ABAC, a new resource needs only the correct attribute, and the existing policy covers it.

Exam signals

  • "Only clients with the orders.write scope can call POST" → access token plus authorization scopes on the method.
  • "Admins can delete, other users can only read" → Cognito groups, and check cognito:groups.
  • "Custom token from a third-party issuer on a REST API" → Lambda authorizer. The Cognito authorizer accepts only Cognito user pool tokens, and JWT authorizers exist only on HTTP APIs.
  • "Pass the tenant ID from the authorizer to the backend" → authorizer context (string value). Lambda proxy integration reads event.requestContext.authorizer, and other integrations read $context.authorizer.<key> in a mapping template.
  • "First call to /orders works, then /invoices returns 403 for 5 minutes" → cached policy covers one method only. The default cache TTL is 300 seconds (5 minutes).

Explanation

REST API Cognito authorizer and scopes

  • No authorization scopes on the method: API Gateway treats the token as an ID token. API Gateway then verifies the claimed identity against the user pool, not scopes.
  • Authorization scopes on the method: API Gateway treats the token as an access token. The call succeeds if any method scope matches a scope in the token. Otherwise the result is 401 Unauthorized.
  • The optional token validation regex checks the aud claim. Access tokens have no aud unless the token is bound to a resource server, so this regex rejects them.
  • After the authorizer validates the token, the backend can read its claims. The backend can trust these values because API Gateway verified the token.
  • In a mapping template, use $context.authorizer.claims.sub. For a claim name with a colon, use $context.authorizer.claims['custom:role'].

Cognito groups

  • The cognito:groups claim is in both the ID token and the access token. Use it for role-based checks in the backend or in a Lambda authorizer.
  • A group can have an IAM role. With an identity pool, the user gets temporary AWS credentials for that role. Use this when the app calls AWS services directly and each group needs different AWS permissions.
  • A group can have a precedence value, a number that you set. A user in several groups: the group with the lowest precedence value sets cognito:preferred_role in the ID token.
  • Groups cannot be nested.

Cross-service authentication

Remember

  • The OAuth 2.0 client credentials grant gives a service with no user an access token.
  • A client credentials service authenticates with its own client ID and client secret.
  • Client credentials setup needs an app client with a client secret, a resource server, and custom scopes.
  • A Cognito resource server is a record for your API that defines the custom scopes that the API accepts.
  • The custom scope format is resourceServerIdentifier/scopeName. Example: orders-api/orders.read.
  • The token endpoint /oauth2/token needs a user pool domain.
  • The GetClientToken API needs no user pool domain.
  • Use the token endpoint when the service uses a standard OAuth library.
  • Use GetClientToken when the service uses the AWS SDK or CLI and you do not want a domain.
  • The client credentials grant returns only an access token with custom scopes, and no ID token.
  • An API checks M2M scopes with a REST API Cognito authorizer with scopes, or with an HTTP API JWT authorizer.
  • Cache the M2M access token until it expires, because Cognito bills each token request.
  • Cognito bills M2M access by active app clients and by the number of token requests.
  • SigV4 signs each request with AWS credentials, so AWS can check who sent it.
  • Use SigV4 when both services run on AWS with IAM roles.
  • An IAM role gives temporary credentials that AWS rotates, so there is no secret to store or rotate.
  • For IAM authorization on API Gateway, set the method authorization to AWS_IAM.
  • An AWS_IAM API Gateway caller needs execute-api:Invoke and signs the request with SigV4.
  • For IAM authorization on a Lambda function URL, set AuthType to AWS_IAM.
  • Since October 2025, new function URLs need lambda:InvokeFunctionUrl and lambda:InvokeFunction. Older study material lists only lambda:InvokeFunctionUrl.
  • A cross-account caller needs an allow in its identity policy and in the resource policy.
  • A cross-account call gets 403 if the identity policy or the resource policy does not allow it.
  • In mutual TLS, the client also shows an X.509 certificate, so the server knows which client connects.
  • REST API mutual TLS needs a Regional custom domain name with the TLS_1_2 security policy.
  • REST API mutual TLS needs an ACM certificate for the domain.
  • REST API mutual TLS needs a truststore, a .pem file of CA certificates in Amazon S3.
  • API Gateway accepts a client certificate only when a CA in the truststore signed it.
  • Disable the default execute-api endpoint, or clients can skip mutual TLS.
  • API Gateway mutual TLS does not check revocation, so a revoked client certificate still passes.
  • Use a Lambda authorizer for certificate revocation checks, because API Gateway forwards client certificates to it.
  • An untrusted or expired client certificate fails the handshake, and the client gets 403.
  • Mutual TLS is not supported for private APIs.
  • A private API is a REST API that clients call only from a VPC, through an interface VPC endpoint for execute-api.
  • Only REST APIs can be private, and HTTP APIs cannot.
  • Use aws:SourceVpc in the private API resource policy to allow every endpoint in a VPC.
  • Use aws:SourceVpce in the private API resource policy to allow only named endpoints.

Exam signals

  • "Backend service calls an API with no user, OAuth scopes required" → Cognito client credentials grant with a resource server and custom scopes.
  • "Lambda in one account calls an API in another account, no secrets" → AWS_IAM authorization, SigV4, and a resource policy. The function role gives temporary credentials, so nothing is stored.
  • "Partners must authenticate with client certificates" → mutual TLS on a Regional custom domain, and disable the default endpoint.
  • "API reachable only from inside the VPC" → private REST API, interface endpoint, resource policy.

Explanation

OAuth 2.0 client credentials (machine to machine)

  • A service with no user gets an access token with its own client ID and client secret.
  • Setup: an app client with a client secret (confidential client), a resource server, and custom scopes.
  • In Cognito, a resource server is a record for your API that defines the custom scopes that the API accepts.
  • A scope names one permission, for example read orders. Scope format: resourceServerIdentifier/scopeName, for example orders-api/orders.read.
  • Get the token from the token endpoint (/oauth2/token, needs a user pool domain), or call the GetClientToken API (no domain needed). Choose the token endpoint when the service uses a standard OAuth library. Choose GetClientToken when the service uses the AWS SDK or CLI and you do not want a domain.
  • The result is an access token that holds only custom scopes. There is no ID token and no user.
  • The API checks the scopes, for example with a REST API Cognito authorizer with authorization scopes, or an HTTP API JWT authorizer.
  • Cache the token and reuse it until it expires. Cognito bills M2M (machine-to-machine) access by active app clients and by the number of token requests. A service that requests a new token for each call pays for each request.

IAM authorization with SigV4

  • SigV4 (Signature Version 4) signs each request with AWS credentials, so AWS can check who sent it.
  • Use SigV4 when both services run on AWS with IAM roles. A role gives temporary credentials that AWS rotates, so there is no secret to store or rotate.
  • API Gateway: set the method authorization to AWS_IAM. The caller needs execute-api:Invoke and signs the request with SigV4.
  • Lambda function URL: set AuthType to AWS_IAM. The caller signs with SigV4.
  • Since October 2025, new function URLs need both lambda:InvokeFunctionUrl and lambda:InvokeFunction. Older study material lists only lambda:InvokeFunctionUrl.
  • Cross-account callers need an allow in their identity policy and in the resource policy (API resource policy or function resource-based policy). If one of the two policies does not allow the call, the caller gets 403.

Mutual TLS (REST API)

  • In normal TLS, only the server shows a certificate. In mutual TLS (mTLS), the client also shows an X.509 certificate, so the server knows which client connects. Common for IoT and business-to-business clients.
  • Needs a Regional custom domain name with the TLS_1_2 security policy, an ACM certificate for the domain, and a truststore (.pem file of CA certificates) in Amazon S3. API Gateway accepts a client certificate only when a CA in the truststore signed it.
  • Disable the default execute-api endpoint, or clients can skip mutual TLS.
  • A CA revokes a certificate to cancel it before it expires, for example after a key leak. API Gateway does not check revocation, so a revoked certificate still passes.
  • Use a Lambda authorizer for revocation checks. API Gateway forwards client certificates to Lambda authorizers.
  • Untrusted or expired client certificate: the handshake fails and the client gets 403.
  • Not supported for private APIs.

Private APIs

  • A private API is a REST API that clients call only from a VPC, through an interface VPC endpoint for execute-api. An interface VPC endpoint is a network interface with private IP addresses in your subnets (AWS PrivateLink). Traffic does not leave the Amazon network.
  • Only REST APIs can be private. HTTP APIs cannot.
  • Use the API resource policy with aws:SourceVpc or aws:SourceVpce to allow only your VPCs or endpoints. Use aws:SourceVpc to allow every endpoint in a VPC. Use aws:SourceVpce to allow only named endpoints.

References: Scopes, M2M, and resource servers, REST API IAM permissions, Function URL access control, Mutual TLS for REST APIs, Private REST APIs.

Multi-tenant data access

Remember

  • The silo model gives each tenant its own resource: a table, a bucket, or an account.
  • The silo model gives the strongest isolation and simple per-tenant cost, but a higher cost.
  • The pool model shares a resource and puts a tenant key in every item or object key.
  • The pool model has a lower cost, but its isolation depends on policies and code.
  • The bridge model mixes silo and pool by tier. Example: shared compute, but one database for each tenant.
  • Use silo when a tenant needs strict isolation, its own encryption key, or its own cost report.
  • Use pool when you have many small tenants and lower cost matters most.
  • For DynamoDB fine-grained access control, make the tenant ID or user ID the partition key.
  • The dynamodb:LeadingKeys condition can check only the partition key value in the request.
  • Use dynamodb:LeadingKeys with a policy variable, so a caller reads only items whose partition key equals the caller ID.
  • The dynamodb:LeadingKeys condition must use the ForAllValues modifier, for example ForAllValues:StringEquals.
  • Do not allow DynamoDB Scan, because LeadingKeys cannot limit it and a scan returns items of all tenants.
  • The dynamodb:Attributes condition checks only the attribute names in the request, not the response.
  • With dynamodb:Attributes, also require dynamodb:Select = SPECIFIC_ATTRIBUTES, or a read with no projection returns all attributes.
  • For DynamoDB writes, limit dynamodb:ReturnValues to NONE, UPDATED_OLD, or UPDATED_NEW.
  • The ReturnValues settings ALL_OLD and ALL_NEW return the whole item.
  • Policy variables need "Version": "2012-10-17" in the policy.
  • Without the 2012-10-17 version, IAM treats ${...} as literal text, and the condition never matches a real ID.
  • The variable ${cognito-identity.amazonaws.com:sub} is the identity pool identity ID, not the user pool sub.
  • A policy that expects the user pool sub in ${cognito-identity.amazonaws.com:sub} denies every request.
  • The variable ${aws:username} is the IAM user name.
  • The variable ${aws:PrincipalTag/tenant} is a tag on the principal (ABAC).
  • Identity pools can map token claims to principal tags (attributes for access control).
  • Do not map an attribute that users can change to a principal tag, or a user can get another tenant's data.
  • For a private S3 prefix, allow s3:GetObject and s3:PutObject on arn:aws:s3:::bucket/${cognito-identity.amazonaws.com:sub}/*.
  • s3:ListBucket acts on the bucket ARN, so limit s3:ListBucket with an s3:prefix condition.
  • Without the s3:prefix condition, a user can list the object keys of all users.
  • Take the tenant ID from the verified token or the authorizer context.
  • Never take the tenant ID from the request body, a query string, or a header that the client controls.
  • Add the tenant key to every query in the code, because IAM policies are only a second layer.

Exam signals

  • "Mobile users may read and write only their own items in one DynamoDB table" → identity pool role with dynamodb:LeadingKeys = ${cognito-identity.amazonaws.com:sub}. One policy works for all users, because IAM puts each caller's identity ID into the variable.
  • "Each user has a private folder in one bucket" → policy variable in the object ARN. One policy works for all users, because IAM puts each caller's identity ID into the variable.
  • "Tenant ID comes from a request header; a user read another tenant's data" → take the tenant ID from the verified token.
  • "Strict isolation and per-tenant encryption keys for regulated tenants" → silo model.

Explanation

In the bridge model, a tier is one layer of the application. Example: all tenants share the compute layer, but each tenant has its own database.

Choose silo when a tenant needs strict isolation, its own encryption key, or its own cost report. Choose pool when you have many small tenants and lower cost matters most.

DynamoDB fine-grained access control

  • Make the tenant ID or user ID the partition key. The IAM condition below can check only the partition key value, so the tenant must be in that key.
  • Use the dynamodb:LeadingKeys condition with a policy variable. LeadingKeys is the partition key value in the request.
  • A policy variable, such as ${cognito-identity.amazonaws.com:sub}, is a placeholder that IAM replaces with a value from the request at evaluation time. The condition then allows only items whose partition key equals the caller ID.
  • LeadingKeys must use the ForAllValues modifier, for example ForAllValues:StringEquals.
  • Do not allow Scan. A scan reads the whole table and does not name a partition key, so LeadingKeys cannot limit it. The scan returns items of all tenants.
  • Reads: limit attributes with dynamodb:Attributes. This condition checks only the attribute names in the request, not the response.
  • A read with no projection names no attributes, so it returns all attributes. To stop this, also require dynamodb:Select = SPECIFIC_ATTRIBUTES.
  • Writes: limit dynamodb:ReturnValues to NONE, UPDATED_OLD, or UPDATED_NEW. ALL_OLD and ALL_NEW return the whole item.
  • Policy variables need "Version": "2012-10-17" in the policy. Without it, IAM treats ${...} as literal text, so the condition never matches a real ID.

S3 prefix for each tenant

  • Allow s3:GetObject and s3:PutObject on arn:aws:s3:::bucket/${cognito-identity.amazonaws.com:sub}/*.
  • Allow s3:ListBucket on the bucket with a s3:prefix condition for the same prefix. ListBucket acts on the bucket ARN, not on object ARNs, so the object ARN above does not limit it. Without the condition, a user can list the object keys of all users.

Application rules

  • Take the tenant ID from the verified token or the authorizer context. Never take it from the request body, a query string, or a header that the client controls.
  • A user can change those values to another tenant ID. A user cannot change a signed token without breaking the signature.
  • Add the tenant key to every query in the code. Policies are a second layer, not a replacement for the code check.

Encryption in transit

Remember

  • Use TLS for every connection: client to edge, edge to origin, and service to database.
  • To deny plain HTTP to S3, use a bucket policy "Effect": "Deny" when "aws:SecureTransport": "false".
  • The aws:SecureTransport key is false when a request does not use TLS.
  • An explicit deny on aws:SecureTransport wins over every allow, so S3 returns 403 Access Denied for every principal.
  • Requests to SQS queues and SNS topics with SSE turned on must use HTTPS and Signature Version 4.
  • SQS and SNS reject a plain HTTP request to a queue or topic with SSE turned on.
  • Private REST APIs support only TLS 1.2.
  • A CloudFront distribution uses ACM certificates only from us-east-1, whatever Region the origin is in.
  • An API Gateway edge-optimized custom domain needs its ACM certificate in us-east-1.
  • An API Gateway Regional custom domain needs its ACM certificate in the Region of the API.
  • An Application Load Balancer needs its ACM certificate in the Region of the load balancer.
  • ACM renews ACM-issued certificates that you use with integrated services.
  • You renew imported certificates, and an expired imported certificate causes client TLS errors.
  • You cannot install a standard ACM certificate on your own web server, because ACM keeps the private key.
  • To attach an ACM-managed certificate directly to an EC2 instance, you need Nitro Enclaves.
  • For public certificates on EC2, AWS recommends the ACME protocol.
  • ACM offers exportable public certificates for an extra charge.
  • The CloudFront viewer protocol policy HTTP and HTTPS serves an HTTP request over HTTP.
  • Redirect HTTP to HTTPS returns 301 for GET and HEAD, and 307 for other methods on HTTP/1.1 or later.
  • The HTTPS only viewer protocol policy returns 403 for an HTTP request.
  • Use Redirect HTTP to HTTPS for websites, where users can type http://.
  • Use HTTPS only when all clients are programs that you control.
  • The viewer protocol policy covers only the connection from the viewer to CloudFront.
  • Use HTTPS from CloudFront to the origin with the origin protocol policy.
  • Amazon S3 encrypts all new objects with SSE-S3 since January 5, 2023, and you cannot turn it off.
  • Amazon DynamoDB always encrypts data at rest.
  • SSE-SQS is the default for new queues created through the HTTPS endpoint without encryption attributes.
  • Amazon SNS does not encrypt at rest by default, so set a KMS key (KmsMasterKeyId) on the topic.

Exam signals

  • "Bucket must reject requests that do not use HTTPS" → bucket policy deny on aws:SecureTransport false.
  • "Users who type http:// must reach the site securely" → viewer protocol policy Redirect HTTP to HTTPS.
  • "Certificate for CloudFront is not in the list" → request or import it in us-east-1. CloudFront shows only certificates from that Region.
  • "SNS messages must be encrypted at rest" → turn on SSE with a KMS key. SNS encryption is not on by default.

Explanation

Key facts

  • Use TLS for every connection: client to edge, edge to origin, and service to database.
  • Deny plain HTTP to Amazon S3 with a bucket policy: "Effect": "Deny" when "aws:SecureTransport": "false". The key is false when a request does not use TLS.
  • An explicit deny wins over every allow, so S3 rejects the request with 403 Access Denied for every principal.
  • Requests to SQS queues and SNS topics with SSE turned on must use HTTPS and Signature Version 4. A plain HTTP request to an encrypted queue or topic is rejected.
  • Private REST APIs support only TLS 1.2.

Certificates and SSH keys for development

Remember

  • An EC2 key pair has a public key that EC2 puts on the instance and a private key that you keep.
  • On Linux instances, EC2 puts the public key in ~/.ssh/authorized_keys.
  • When EC2 creates the key pair, you can save the private key one time only.
  • EC2 does not keep a copy of the private key, so AWS cannot recover a lost private key.
  • A CloudFormation AWS::EC2::KeyPair with no PublicKeyMaterial stores the private key in Parameter Store.
  • The Parameter Store name of a CloudFormation-created private key is /ec2/keypair/<key_pair_id>.
  • EC2 key pairs can be RSA (Linux and Windows) or ED25519 (Linux only).
  • EC2 does not accept DSA keys.
  • Private key file formats are .pem (OpenSSH) and .ppk (PuTTY).
  • On Linux and macOS, run chmod 400 on the private key file.
  • The SSH client refuses a private key file that other users can read.
  • To use your own key, create it with ssh-keygen and import only the public key, so the private key never leaves your machine.
  • On Windows instances, the private key decrypts the administrator password, and you sign in with that password.
  • EC2 has a quota of 5,000 key pairs for each Region, and you can request more.
  • Session Manager connects with no SSH key and no open inbound port.
  • IAM policies control who can start a Session Manager session.
  • Session Manager can log session activity.
  • Use a self-signed certificate, for example from OpenSSL, for local development or a test endpoint only.
  • Clients do not trust a self-signed certificate by default, so browsers warn until you add it to the trusted certificates.
  • Use AWS Private CA for internal services, private hostnames, and mutual TLS client certificates.
  • Private certificates are trusted only where you install your CA.
  • Use an ACM public certificate for a public endpoint on CloudFront, ALB, or API Gateway.
  • An ACM public certificate is free for integrated services, and ACM renews it.
  • ACM validates a public certificate with DNS or email validation.
  • Private CA charges a monthly fee for each CA and a fee for each certificate that it issues.
  • A private certificate whose private key you cannot access is free, for example on ELB, CloudFront, or API Gateway.
  • Private CAs are Regional, and you cannot copy a CA to another Region.
  • You can import a third-party or self-signed certificate into ACM, but ACM does not renew imported certificates.
  • Store private keys in Secrets Manager or Parameter Store SecureString.

Exam signals

  • "Lost the .pem file for an EC2 instance" → connect another way, for example with Session Manager, then add a new public key to ~/.ssh/authorized_keys. AWS cannot give the key back, because EC2 never kept a copy.
  • "Use an existing SSH key from the developer's laptop" → import the public key.
  • "Internal microservices need TLS certificates that the company controls" → AWS Private CA.
  • "HTTPS on a laptop for local tests, no cost" → self-signed certificate.
  • "Shell access with no key pairs and no port 22" → Session Manager, because IAM controls access and the instance needs no inbound port.

Explanation

EC2 key pairs

  • A key pair has a public key and a private key. EC2 puts the public key on the instance (Linux: ~/.ssh/authorized_keys). You keep the private key.
  • When EC2 creates the key pair, you can save the private key one time only. EC2 does not keep a copy, so you cannot recover a lost private key from AWS.
  • Exception: a key pair that CloudFormation creates (AWS::EC2::KeyPair with no PublicKeyMaterial) stores the private key in Parameter Store as /ec2/keypair/<key_pair_id>.
  • Types: RSA (Linux and Windows) and ED25519 (Linux only). EC2 does not accept DSA.
  • Private key file formats: .pem (OpenSSH) or .ppk (PuTTY). On Linux and macOS, run chmod 400 on the file, so that only you can read it. The SSH client refuses a private key file that other users can read.
  • Import: create the key pair with a tool such as ssh-keygen, then import only the public key (aws ec2 import-key-pair). The private key never leaves your machine.
  • Windows instances: you do not use the key to sign in. You use the private key to decrypt the administrator password, and then you sign in with that password.
  • Quota: 5,000 key pairs for each Region (you can request more).
  • Session Manager (Systems Manager) connects with no SSH key and no open inbound port. The SSM Agent on the instance opens the session channel to Systems Manager. IAM policies control who can start a session, and Session Manager can log session activity.
