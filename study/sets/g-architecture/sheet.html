Event-driven architecture and fanout

Remember

  • An event tells that something happened. Example: "OrderPlaced".
  • A command tells one receiver to do something. Example: "ChargeCard".
  • An event producer does not know the consumers. You add a consumer with no change to the producer.
  • Fanout sends a copy of one event to many consumers at the same time.
  • In fanout, a slow or failed consumer does not delay the other consumers.
  • For SNS fanout, publish one time to a topic and subscribe one SQS queue for each consumer.
  • SNS pushes each message to its subscribers and does not keep the message for later reads.
  • When an SNS endpoint stays down, SNS retries, then discards the message unless the subscription has a dead-letter queue.
  • An SQS queue stores its copy until the consumer reads and deletes it, so a slow consumer loses no messages.
  • One EventBridge rule sends a matching event to up to 5 targets. You cannot raise this quota.
  • For more than 5 EventBridge targets, add more rules with the same event pattern.
  • AWS docs now call the rule-based EventBridge bus "Custom Event Bus - Classic". The default event bus is a Classic bus.
  • The newer EventBridge "Custom Event Bus" (2026) uses subscribers and keeps events for replay. Older study material and the exam use rules and targets.
  • An SNS filter policy sends a subscriber only the messages that it needs.
  • An SNS filter policy acts on message attributes or on the message body (the filter policy scope setting).
  • SNS message attributes are optional name-value pairs (metadata) that the publisher sends with the message body.
  • An SNS subscriber with no filter policy gets every message.
  • A Lambda subscriber with no SNS filter policy runs, and costs money, for messages that it only discards.
  • An EventBridge event pattern matches on any field in the event, including fields inside the event detail.
  • Use EventBridge to route on event content, for AWS service events, and for SaaS partner events.
  • AWS services send AWS service events to the default event bus automatically. Example: an EC2 instance state change.
  • An SNS FIFO topic keeps the message order and removes duplicate messages.
  • An SNS FIFO topic delivers to SQS FIFO and SQS standard queues only. It cannot deliver to Lambda, HTTP(S), email, or SMS.
  • To process SNS FIFO messages in Lambda, subscribe an SQS FIFO queue and let Lambda read from the queue.
  • Use SNS for one message to many consumers, high throughput, and a simple attribute or body filter.
  • Use EventBridge for content routing, AWS service events, SaaS events, and archive and replay.
  • Use SQS when one consumer group pulls work at its own speed, or to buffer spikes.
  • Use Kinesis Data Streams for an ordered, replayable stream with many readers of the same records.
  • The consumers of one SQS queue share the work. One consumer reads and deletes each message.
  • Kinesis Data Streams keeps records for 24 hours by default, and up to 365 days.
  • EventBridge can archive events and replay them to the rules later. Example: reprocess events after a defect fix.
  • For SNS to SQS fanout, the queue policy must allow sns.amazonaws.com to do sqs:SendMessage.
  • Without the SNS statement in the queue policy, the publish to the topic succeeds, but the queue stays empty.
  • Add an aws:SourceArn condition with the topic ARN to the queue policy. Without it, any SNS topic can send to the queue.
  • The confused deputy problem: a trusted service does an action for a party that has no permission of its own.
  • For cross-account EventBridge, the receiver event bus needs a resource-based policy that allows the sender accounts or the organization ID.
  • For cross-account EventBridge, each sender account creates a rule with the receiver bus ARN as the target.
  • Since March 2, 2023, a rule target on an event bus in another account needs an IAM role.
  • The EventBridge console creates the cross-account IAM role for you. With the CLI, you create it yourself.

Exam signals

  • "Add new consumers without changing the producer" → publish events to SNS or EventBridge. The producer does not know the consumers, and each new consumer adds its own subscription or rule.
  • "Each consumer must process every order, at its own speed, and not lose messages" → SNS topic with one SQS queue for each consumer. SNS gives each queue its own copy, and each queue stores the messages until its consumer reads them.
  • "Route events by a field inside the event body to different services" → EventBridge rules with event patterns, because an event pattern can match any field in the event and send it to many target types.
  • "SNS publishes succeed but the queue gets nothing" → the queue policy does not allow sqs:SendMessage from the topic. SNS accepts the publish, then fails when it delivers to the queue.

Explanation

Key facts

  • An event tells that something happened (for example, "OrderPlaced"). A command tells one receiver to do something (for example, "ChargeCard").
  • A producer publishes an event and does not know the consumers. You can add a consumer without a change to the producer.
  • Fanout sends a copy of one event to many consumers at the same time. Each consumer processes its copy on its own, so a slow or failed consumer does not delay the others.
  • Fanout with Amazon SNS: publish one time to a topic, and subscribe one Amazon SQS queue for each consumer.
  • SNS pushes each message to its subscribers and does not keep it for a subscriber to read later. When an endpoint (for example, an HTTPS server) stays down, SNS retries, then discards the message unless the subscription has a dead-letter queue.
  • An SQS queue stores its copy until the consumer reads and deletes it, so a consumer that is down or slow does not lose messages.
  • Fanout with Amazon EventBridge: one rule can send a matching event to up to 5 targets. You cannot raise this quota. For more consumers, add more rules with the same event pattern.
  • AWS docs now call the rule-based bus "Custom Event Bus - Classic". The default event bus is a Classic bus.
  • The newer "Custom Event Bus" (2026) uses subscribers and keeps events for replay. Older study material and the exam use rules and targets.
  • SNS filter policies send a subscriber only the messages it needs.
  • Message attributes are optional name-value pairs (metadata) that the publisher sends with the message body.
  • A filter policy acts on message attributes or on the message body (the filter policy scope setting).
  • With no filter policy, a subscriber gets every message. A Lambda subscriber then runs, and costs money, for messages that it only discards.
  • EventBridge event patterns match on any field in the event, including fields inside the event detail.
  • AWS service events are events that AWS services send to the default event bus automatically, for example an EC2 instance state change.
  • Use EventBridge for routing on event content, for AWS service events, and for events from SaaS partner applications.
  • An SNS FIFO (first-in, first-out) topic keeps the order of messages and removes duplicate messages.
  • SNS FIFO topics deliver to SQS FIFO queues and SQS standard queues. They do not deliver directly to Lambda, HTTP(S), email, or SMS endpoints.
  • To process these messages in Lambda, subscribe an SQS FIFO queue and let Lambda read from the queue.

Security

  • For SNS to SQS fanout, the queue policy must allow the sns.amazonaws.com service principal to do sqs:SendMessage. SNS, not your publisher, sends the message to the queue. Without this statement, the publish to the topic still succeeds, but SNS cannot deliver to the queue, and the queue stays empty.
  • Add the aws:SourceArn condition with the topic ARN. Without it, any SNS topic, including a topic in another account, can send messages to the queue through the SNS service principal. This risk is the confused deputy problem: a trusted service does an action for a party that has no permission of its own.
  • Cross-account EventBridge has two parts. First, the receiver event bus needs a resource-based policy that allows the sender accounts (or the organization ID). Without it, the receiver bus does not accept their events.
  • Second, each sender account creates a rule with the receiver bus ARN as the target.
  • Since March 2, 2023, a new rule target on an event bus in another account needs an IAM role. The role lets EventBridge send events to that bus.
  • The console creates this role for you. With the CLI, you create it yourself.

Monolithic compared with microservices

Remember

  • A monolith deploys as one unit. A small change deploys the whole application.
  • A monolith scales as a whole, and one defect can stop the whole application.
  • Each microservice deploys on its own and scales on its own load.
  • Microservices have partial failure: one service can fail while the other services continue.
  • Microservices call each other over the network: HTTP APIs, queues, events.
  • Choose a monolith for a small application or a small team.
  • Choose microservices when separate teams must deploy and scale parts independently.
  • Microservices add more network calls and more deployments to operate.
  • Database per service: no other service reads or writes the tables of a service directly.
  • Other services use the API or the events of a service to get its data.
  • A shared table lets a schema change by one team break another service.
  • Network calls add latency and can fail with a timeout or a service that is down.
  • Set a timeout on each network call, so that the caller does not wait without end.
  • Retry with backoff: wait longer before each new retry, so that retries do not overload a recovering service.
  • Use asynchronous messages where the caller does not need an immediate answer.
  • AWS X-Ray (distributed tracing) records the time that each service spends on one request.
  • A correlation ID is a unique ID that the first service creates and every service writes in its logs.
  • A transaction across services cannot use one database transaction. Use a saga.
  • In a typical AWS microservice design, API Gateway or an Application Load Balancer is in front.
  • Typical microservice compute is Lambda or containers, with DynamoDB or RDS for each service.
  • Typical links between microservices are SQS, SNS, or EventBridge.

Exam signals

  • "Teams must deploy and scale components independently" → microservices with separate deployments.
  • "One service reads another service's table directly, and schema changes break it" → give each service its own data store and expose an API or events. The API or event format stays the same when the internal tables change.
  • "Find which service in a chain causes latency" → AWS X-Ray traces across services. The trace map shows the time spent in each service.

Key facts

  • Database per service: no other service reads or writes the tables of a service directly. When two services share a table, a schema change by one team can break the other service. The teams then cannot deploy independently.
  • Network calls add latency and can fail in ways that in-process calls cannot, for example a timeout or a service that is down.
  • Set a timeout on each call, so that the caller does not wait without end for a slow service.
  • Retry with backoff: wait longer before each new retry, so that retries do not overload a service that is recovering.
  • Use asynchronous messages where the caller does not need an immediate answer.
  • A request can cross many services, and each service writes its own logs. Distributed tracing (AWS X-Ray) records the time that each service spends on one request.
  • A correlation ID is a unique ID that the first service creates. Each service passes it on and writes it in its logs, so you can find all log lines for one request.
  • A transaction that spans services cannot use one database transaction. Use a saga (see the orchestration topic).
  • Typical AWS building blocks: API Gateway or an Application Load Balancer in front, and Lambda or containers for compute. Each service uses DynamoDB or RDS, with SQS, SNS, or EventBridge between services.

Orchestration compared with choreography

Remember

  • In orchestration, one controller runs the steps in order and handles errors. The AWS service is Step Functions.
  • In choreography, no controller exists. Each service reacts to events and publishes new events.
  • Choreography on AWS uses EventBridge, SNS, and SQS.
  • Orchestration shows the state of each run in one place: the execution history.
  • In choreography, the flow is spread across services, so tracing is harder.
  • To change an orchestrated flow, change the workflow definition.
  • In choreography, you add a consumer with no change to the other services.
  • In orchestration, services depend on the controller. In choreography, events couple services loosely.
  • Choose orchestration for a fixed step order, one place to see each run, or a step that waits for a person.
  • Choose choreography when services must stay independent and new consumers react to events with no change to other services.
  • A saga is a series of local transactions, one in each service.
  • A local transaction changes only the database of that one service.
  • A saga keeps data consistent without a distributed transaction (two-phase commit).
  • When a saga step fails, the saga runs compensating transactions that undo the earlier steps. Example: refund the payment, then release the inventory.
  • Saga participants must be idempotent, because a step can run again after a failure or a retry.
  • An idempotent operation gives the same result when it runs two times as when it runs one time.
  • To make a step idempotent, pass a unique request ID and record it with a conditional write.
  • A saga gives eventual consistency, not isolation. Other requests can see the data between steps.
  • A Step Functions Catch field on a Task state sends a failed task to a compensation state.
  • A Step Functions Choice state can send the workflow to compensation, based on a result value.
  • A Standard workflow runs for up to 1 year. An Express workflow runs for up to 5 minutes.
  • A Standard workflow has exactly-once execution.
  • An Express workflow is at least once when asynchronous, and at most once when synchronous.
  • Standard workflow price is based on the number of state transitions.
  • Express workflow price is based on the number of executions, the duration, and the memory.
  • Step Functions keeps Standard execution history for 90 days.
  • Express execution history is only in CloudWatch Logs, and only if you turn on logging.
  • Only Standard workflows support .waitForTaskToken and .sync. Express workflows cannot use them.
  • .waitForTaskToken pauses the workflow until an external system returns a task token.
  • .sync starts a job (for example, an ECS task or a Glue job) and waits until it finishes.
  • Exactly once: Step Functions never runs a step more than one time, unless you add a Retry.
  • At least once: an execution can run more than one time, so the steps must be idempotent.
  • At most once: a failed synchronous Express execution does not start again automatically.
  • Choose Standard for long workflows, non-idempotent steps such as payments, and callback waits.
  • Choose Express for high-volume, short, idempotent event processing. For many short runs, Express costs less.

Exam signals

  • "Central visibility of each order's progress", "run steps in a fixed order with error handling" → orchestration with Step Functions. Step Functions keeps the execution history of each run.
  • "Human approval step" → orchestration with a Step Functions Standard workflow. A Standard workflow can pause for a person with .waitForTaskToken.
  • "Add consumers without changing the producer", "services must not know each other" → choreography with EventBridge or SNS, because producers publish events and do not call the consumers.
  • "Undo earlier steps when a later step fails across services" → saga with compensating transactions, because one database transaction cannot span the databases of many services.
  • "Non-idempotent step such as a payment, workflow can run for days" → Standard workflow. Standard runs each step exactly once for up to 1 year, but asynchronous Express is at least once and stops at 5 minutes.
  • "Very high volume of short event processing, at lowest cost" → Express workflow, because Express is priced by executions, duration, and memory, not by each state transition.

Saga pattern

  • A saga is a series of local transactions, one in each service. A local transaction changes only the database of that one service.
  • Each microservice owns its database, so one database transaction cannot cover all the steps. A saga keeps data consistent without a distributed transaction (two-phase commit, where one coordinator makes all databases commit together or not at all).
  • If a step fails, the saga runs compensating transactions that undo the earlier steps (for example, refund the payment, then release the inventory).
  • Saga participants must be idempotent. An idempotent operation gives the same result when it runs two times as when it runs one time.
  • A step can run again after a failure or a retry. Without idempotency, a repeated refund step can refund a customer two times.
  • A common fix: pass a unique request ID and record it with a conditional write, so that a repeated request does nothing.
  • A saga gives eventual consistency, not isolation. Isolation means that other requests do not see the changes of a transaction until it completes.
  • In a saga, each step commits at once. Other requests can see data between steps, for example inventory that is reserved and then released by a compensating transaction.
  • Step Functions can act as the saga orchestrator. Add a Catch field to a Task state: when the task fails, the Catch sends the workflow to a compensation state (for example, RefundPayment). A Choice state can also send the workflow to compensation, based on a result value.

Coupling and synchronous compared with asynchronous

Remember

  • With tight coupling, the caller calls the callee directly and waits. A slow or failed callee makes the caller slow or fail.
  • With loose coupling, a queue, topic, or event bus sits between the components. Each side can fail, scale, or change on its own.
  • A synchronous caller waits for the result. Examples: API Gateway to Lambda, Lambda RequestResponse, StartSyncExecution.
  • An asynchronous caller gets an acknowledgment and continues. Examples: Lambda Event invocation, SQS, SNS, EventBridge.
  • Use synchronous calls only when the caller needs the answer now. Example: a price check before checkout.
  • Each synchronous call adds the latency of the callee to the caller, and the caller fails when the callee fails.
  • Load leveling: an SQS queue absorbs traffic spikes, and consumers read at a rate that the backend supports.
  • Without a queue, a traffic spike can make the backend run out of connections or throttle requests.
  • A queue keeps messages while the consumer is down. The consumer continues when it comes back.
  • SQS deletes a message when the retention period ends. A consumer that is down for longer loses those messages.
  • Most AWS asynchronous delivery is at least once: a consumer can get the same message more than one time.
  • An SQS message that the consumer does not delete becomes visible again after the visibility timeout.
  • Make asynchronous consumers idempotent, for example with a conditional write on a request ID.
  • A dead-letter queue (DLQ) is a separate queue that keeps messages that fail many times.
  • The SQS redrive policy sets maxReceiveCount: after that many receives without a delete, SQS moves the message to the DLQ.
  • Without a DLQ, a bad message comes back again and again and uses consumer capacity.
  • In an SQS FIFO queue without a DLQ, a bad message blocks the later messages in its message group.
  • SQS message retention has a default of 4 days and a range of 60 seconds to 14 days.
  • The SQS maximum message size is 1 MiB (1,048,576 bytes). Older study material says 256 KB.
  • For an SQS payload larger than 1 MiB, store the payload in S3 and send a reference.
  • The SQS Extended Client Library uploads a large payload to S3 and puts a pointer in the message.
  • The SQS visibility timeout has a default of 30 seconds and a maximum of 12 hours.
  • The visibility timeout is the time that a received message stays hidden from other consumers.
  • Set the visibility timeout longer than the processing time, or a second consumer processes the same message.
  • The API Gateway REST API integration timeout is 50 ms to 29 seconds by default.
  • You can request a longer integration timeout for Regional and private APIs, but not for edge-optimized APIs.
  • When the backend does not answer within the integration timeout, API Gateway returns HTTP 504 ("Endpoint request timed out").

Exam signals

  • "Backend database fails during traffic spikes" → put an SQS queue in front of the writer (load leveling). The queue stores the spike, and the writer reads at a steady rate.
  • "Order service must keep taking orders when the shipping service is down" → asynchronous messages through a queue. The queue stores the orders until the shipping service reads them.
  • "Long job behind an API times out" → accept the request, queue the work, return an ID, and let the client check status later. API Gateway returns HTTP 504 after the integration timeout (29 seconds by default).
  • "Duplicate processing after a retry" → idempotent consumer (for example, a conditional write on a request ID). A second write with the same ID fails the condition, so the work does not run again.

Explanation

Key facts

  • Tight coupling: the caller calls the callee directly and waits. If the callee is slow or down, the caller is slow or fails too.
  • Loose coupling: a queue, topic, or event bus sits between the components. Each side can fail, scale, or change on its own.
  • Synchronous: the caller waits for the result. Examples: API Gateway to Lambda, Lambda RequestResponse invocation, Step Functions synchronous Express (StartSyncExecution).
  • Asynchronous: the caller gets an acknowledgment and continues. Examples: Lambda Event invocation, SQS, SNS, EventBridge.
  • Use synchronous calls only when the caller needs the answer now (for example, a price check before checkout). Each synchronous call adds the latency of the callee to the caller, and the caller fails when the callee fails.
  • Load leveling: an SQS queue absorbs traffic spikes. Producers write to the queue at any rate, and consumers read at a rate that the backend can support.
  • Without the queue, a spike sends all writes to the backend at once. The backend can then run out of connections or throttle requests.
  • A queue keeps messages when the consumer is down. The consumer continues when it comes back.
  • SQS deletes a message when the retention period ends. A consumer that is down for longer than the retention period loses those messages.
  • Asynchronous delivery is at least once in most AWS services: a consumer can get the same message more than one time.
  • For example, a consumer fails before it deletes an SQS message. The message becomes visible again after the visibility timeout, and SQS delivers it again.
  • Make consumers idempotent (see the saga topic), for example with a conditional write on a request ID.
  • A dead-letter queue (DLQ) is a separate queue that keeps messages that fail many times.
  • In SQS, the redrive policy sets maxReceiveCount. After that many receives without a delete, SQS moves the message to the DLQ.
  • Without a DLQ, a bad message comes back again and again and uses consumer capacity. In a FIFO queue, it also blocks the later messages in its message group.

Stateful compared with stateless

Remember

  • A stateless component keeps no client data between requests. Any instance can serve any request.
  • A stateful component keeps client data, such as a session or a cart, in its own memory or disk.
  • Stateless compute scales out and in easily, because an instance can stop with no lost session.
  • To make compute stateless, store the session state in DynamoDB or ElastiCache.
  • Choose DynamoDB for sessions when sessions must be durable and you want a serverless store.
  • DynamoDB TTL deletes an item after the expiry time (Unix epoch seconds) in an item attribute, with no write cost.
  • DynamoDB TTL deletion usually occurs within a few days, so check the expiry time when you read a session.
  • Choose ElastiCache for sessions when you need the lowest latency, because ElastiCache keeps data in memory.
  • ElastiCache session data in one node is lost when that node fails, unless the cluster has replicas.
  • Do not keep durable state in Lambda global variables or /tmp. Each execution environment has its own copy.
  • Lambda can end an execution environment at any time.
  • Do not keep durable state on one EC2 instance or container, because Auto Scaling can terminate it.
  • A DynamoDB atomic counter (UpdateItem with ADD) changes the value on the server, so parallel updates do not overwrite each other.
  • Sticky sessions (session affinity) send all requests from one client to the same target. The client must support cookies.
  • Duration-based stickiness uses the load balancer cookie AWSALB for a duration of 1 second to 7 days.
  • Use duration-based stickiness when the application has no session cookie of its own.
  • Application-based stickiness follows the application session cookie with the load balancer cookie AWSALBAPP.
  • Use application-based stickiness when the application already has a session cookie.
  • Stickiness is a target group setting and needs no code change.
  • Sticky sessions let a stateful application run behind a load balancer.
  • Sticky sessions can make load uneven: existing clients stay on their old targets, and new targets get only new clients.
  • When a sticky target fails, its clients go to another target, and the session data in its memory is lost.
  • Sticky sessions are a workaround. The better design is an external session store.

Exam signals

  • "Users are logged out when Auto Scaling removes an instance" → move sessions to ElastiCache or DynamoDB.
  • "Shopping cart must survive instance failure and scale with traffic" → external session store, stateless instances.
  • "Lambda function counts requests in a global variable, and the count is wrong" → DynamoDB atomic counter: an UpdateItem call with an ADD expression. Each environment has its own memory, but the atomic counter changes the value on the server, so parallel updates do not overwrite each other.
  • "Legacy application keeps sessions in memory, fastest fix with no code change" → ALB sticky sessions, because stickiness is a target group setting and needs no code change.

Explanation

Key facts

  • A stateless component keeps no client data between requests. Any instance can serve any request.
  • A stateful component keeps client data (for example, a session or a cart) in its own memory or disk.
  • Stateless compute scales out and in easily. An instance can stop at any time and no session is lost.
  • Make compute stateless: store session state outside the compute, in DynamoDB or Amazon ElastiCache.
  • Choose DynamoDB for sessions when sessions must be durable and you want a serverless store.
  • With Time to Live (TTL), you store an expiry time (Unix epoch seconds) in an item attribute. DynamoDB then deletes the item after that time, with no write cost. Deletion usually occurs within a few days, so check the expiry time when you read a session.
  • Choose ElastiCache for sessions when you need the lowest latency, because it keeps data in memory. Session data in one node is lost when that node fails, unless the cluster has replicas.
  • Do not keep durable state in Lambda global variables or /tmp. Each execution environment has its own copy, and Lambda can end an environment at any time.
  • Do not keep durable state on one EC2 instance or container. Auto Scaling can terminate it.

Sticky sessions (Application Load Balancer)

  • Sticky sessions (session affinity) send all requests from one client to the same target. The client must support cookies.
  • Duration-based stickiness: the load balancer creates a cookie named AWSALB and keeps the client on one target for a duration that you set (1 second to 7 days). Use it when the application has no session cookie of its own.
  • Application-based stickiness: the application sets its own session cookie, and the load balancer adds its own AWSALBAPP cookie to follow it. Use it when the application already has a session cookie and stickiness must follow that session.
  • Sticky sessions let a stateful application run behind a load balancer. But load can become uneven, because existing clients stay on their old targets and new targets get only new clients.
  • When a target fails, the load balancer sends its clients to another target, and the session data in the memory of the failed target is lost.
  • Sticky sessions are a workaround. The better design is an external session store.

Application-level caching

Remember

  • CloudFront caches HTTP responses at edge locations for all users near an edge location.
  • The API Gateway cache (REST APIs only) caches integration responses for each stage, by cache key.
  • ElastiCache (Valkey, Redis OSS, Memcached) caches any data that your code puts there, for all application instances.
  • DAX caches DynamoDB items and query results with no change to the data access logic.
  • A Lambda cache in global variables or /tmp serves only that one execution environment.
  • Choose the cache layer by who reads the data and how often the data changes.
  • Cache close to the user for data that many users read.
  • Set a TTL (time to live) on every cached item.
  • A short TTL gives fresher data, but more cache misses and more backend calls.
  • A long TTL gives more cache hits, but users can see old data for longer.
  • Lazy loading reads the cache first. On a miss, the code reads the database and writes the result to the cache.
  • Lazy loading caches only requested data, but a cached item stays stale after a database change until its TTL ends.
  • Write-through writes to the cache each time the code writes to the database.
  • A write-through cache stays current, but it also holds data that nobody reads.
  • Use a TTL with both lazy loading and write-through.
  • You turn on the API Gateway cache for a stage. The cache costs money for each hour, by cache size.
  • The API Gateway cache TTL has a default of 300 seconds and a maximum of 3,600 seconds.
  • An API Gateway cache TTL of 0 turns caching off.
  • API Gateway caches only GET methods by default. Override the method settings to cache other methods.
  • An API Gateway cache key can include headers, path parameters, and query strings.
  • If a parameter changes the response but is not in the cache key, a client can get a response made for another value.
  • A client sends Cache-Control: max-age=0 to skip the API Gateway cache and replace the entry with a fresh response.
  • Turn on Require authorization, and allow execute-api:InvalidateCache only for the clients that need it.
  • Without Require authorization, any client can invalidate cache entries, and many invalidations increase backend calls and latency.
  • For an unauthorized invalidation request, you choose: fail it with HTTP 403, or ignore the header.
  • To flush the whole stage cache, use the console or flush-stage-cache.
  • After an API Gateway cache flush, every request reaches the backend until the cache fills again.
  • A CloudFront cache policy sets the minimum, default, and maximum TTL.
  • CloudFront uses the origin Cache-Control: max-age value, but keeps it inside the minimum and maximum TTL.
  • With no caching header from the origin, CloudFront uses the default TTL, or the minimum TTL if that is larger.
  • CloudFront legacy cache settings (no cache policy) have a default TTL of 24 hours.
  • To remove CloudFront content before it expires, create an invalidation.
  • A versioned file name (for example, app-v2.js) is a new cached object, so users get the new file at once.
  • DAX is a write-through cache. Writes through DAX update DynamoDB first, then the item cache.
  • DAX passes strongly consistent reads to DynamoDB and does not cache the result.
  • DAX serves only eventually consistent reads from cache.
  • Writes made directly to DynamoDB do not update the DAX cache. The item stays stale until its TTL expires.
  • The DAX item cache (GetItem, BatchGetItem) and query cache (Query, Scan) are separate.
  • An item update does not refresh cached DAX Query and Scan results. Those results can be old until their TTL expires.
  • The DAX client uses the same API calls as the DynamoDB client.

Exam signals

  • "Same GET response for many users, reduce backend calls, no code change" → API Gateway cache or CloudFront. Both return the cached response without a call to the backend.
  • "DynamoDB reads need microsecond latency with minimal code change" → DAX, because the DAX client uses the same API calls as the DynamoDB client.
  • "Read needs strongly consistent data" → DAX does not help. It sends the read to DynamoDB.
  • "Cache results of an expensive RDS query for many instances" → ElastiCache, because all instances share it, and it can cache any data, not only DynamoDB data.
  • "Some clients must be able to force a fresh response" → Cache-Control: max-age=0 with the execute-api:InvalidateCache permission.

Key facts

  • Choose the layer by who reads the data and how often it changes. Cache close to the user for data that many users read.
  • Set a TTL (time to live: how long an item stays in the cache before it expires) on every cached item. A short TTL gives fresher data but more cache misses, so more calls reach the backend. A long TTL gives more cache hits, but users can see old data for longer.
  • Lazy loading (details in Module 2): the code reads the cache first. On a miss, it reads the database and writes the result to the cache. Only requested data goes into the cache, but a cached item stays stale after a database change until its TTL ends.
  • Write-through: the code writes to the cache each time it writes to the database. The cache stays current, but it also holds data that nobody reads. Use a TTL with both strategies.

API Gateway cache

  • Only REST APIs have a cache. You turn it on for a stage. It costs money for each hour, by cache size.
  • TTL: default 300 seconds, maximum 3,600 seconds. TTL 0 turns caching off.
  • Only GET methods are cached by default. Override method settings to cache other methods.
  • A cache key is the set of request parts that API Gateway uses to decide whether two requests get the same cached response. Cache keys can include headers, path parameters, and query strings.
  • Each key value gets its own cache entry. If a parameter changes the response but is not in the cache key, a client can get a cached response that was made for a different value.
  • A client can send Cache-Control: max-age=0 to skip the cache and replace the entry with a fresh response.
  • Turn on Require authorization, and allow execute-api:InvalidateCache only for the clients that need it. Without this setting, any client can invalidate entries, and many invalidations increase backend calls and latency.
  • You choose what happens to an unauthorized request: fail it with HTTP 403, or ignore the header.
  • Flush the whole stage cache from the console or the CLI (flush-stage-cache), for example after a deployment that changes the responses. Until the cache fills again, every request reaches the backend.

CloudFront TTL

  • A cache policy sets minimum, default, and maximum TTL.
  • The origin can send Cache-Control: max-age. CloudFront uses that value but keeps it inside the minimum and maximum TTL.
  • CloudFront uses the default TTL (or the minimum TTL, if that is larger) when the origin sends no caching header.
  • A distribution that uses the older per-behavior TTL settings instead of a cache policy (legacy cache settings) has a default TTL of 24 hours.
  • To remove content before it expires, create an invalidation. Or use versioned file names (for example, app-v2.js): a new name is a new cached object, so users get the new file at once.

DAX

  • DAX is a write-through cache. Writes through DAX update DynamoDB first, then the item cache.
  • DAX passes strongly consistent reads to DynamoDB and does not cache the result. DAX serves only eventually consistent reads from cache.
  • Writes made directly to DynamoDB (not through DAX) do not update the DAX cache. The item stays stale until its TTL expires.
  • The item cache (GetItem, BatchGetItem) and the query cache (Query, Scan) are separate. An item update does not refresh cached Query and Scan results. Those results can return old data until their TTL expires.

Storage options: block, file, object, ephemeral

Remember

  • Block storage is a raw disk for one operating system, which puts its own file system on it.
  • File storage is a shared directory tree that many clients mount over the network.
  • Object storage keeps each file as a whole object under a key, with access through an HTTPS API.
  • Object storage writes whole objects, and reads objects or byte ranges of objects.
  • Ephemeral storage is temporary. The data goes away with the instance or the execution environment.
  • EBS is block storage in one Availability Zone. An EBS volume attaches to an instance in the same Availability Zone.
  • EBS data persists independently from the instance life.
  • To use EBS data in another Availability Zone, create a snapshot, then create a new volume from it.
  • EBS Multi-Attach attaches one volume to up to 16 Nitro-based instances in the same Availability Zone.
  • EBS Multi-Attach works only with Provisioned IOPS SSD volumes (io1, io2).
  • Use EBS Multi-Attach for clustered applications that control writes to shared storage.
  • EBS Multi-Attach needs a cluster-aware file system, which coordinates writes from many instances.
  • XFS and EXT4 do not coordinate writes, so many writers on Multi-Attach can corrupt or lose data.
  • EFS is shared file storage (NFS) that many clients use at the same time.
  • EFS Regional file systems store data across Availability Zones. EFS One Zone file systems use one Availability Zone.
  • EFS uses NFS version 4 (4.0 and 4.1).
  • EC2, ECS, EKS, Fargate, and Lambda can mount EFS.
  • EFS does not support Windows instances.
  • EFS grows and shrinks automatically. You do not provision capacity.
  • To mount EFS, a Lambda function must connect to the VPC, because mount targets are endpoints in VPC subnets.
  • Create an EFS mount target in each Availability Zone that the Lambda function uses.
  • Lambda with EFS needs an access point and a local mount path that starts with /mnt/.
  • Security groups must allow NFS traffic on port 2049 between the function and the EFS mount targets.
  • With an EFS IAM policy, the execution role needs elasticfilesystem:ClientMount, and elasticfilesystem:ClientWrite to write.
  • An EFS access point sets the POSIX user, group, and root directory for each client.
  • Use an EFS access point to limit an application to one directory.
  • S3 is object storage with an HTTPS API from anywhere, by key. S3 is not a mounted disk.
  • Amazon S3 Files (2026) is a separate S3 file system with mount targets and an access point.
  • EC2 and Lambda can mount Amazon S3 Files over NFS. Older study material says S3 is object storage only.
  • EC2 instance store is block storage on the host, for only the one instance.
  • Instance store disks are physically attached to the host computer, so instance store is the fastest local disk.
  • Instance store data survives a reboot. Instance store data is lost on stop, hibernate, or terminate.
  • Lambda /tmp is ephemeral storage for one execution environment, with a size of 512 MB to 10,240 MB.
  • Lambda /tmp data is lost when the execution environment ends.

Exam signals

  • "Many Lambda functions or containers must share files with a file system interface" → EFS.
  • "Scratch data, fastest local disk, loss is acceptable" → instance store, because its disks are physically attached to the host computer.
  • "Boot or database volume for one instance" → EBS.
  • "Store large objects for many readers over HTTP at low cost" → S3.
  • "Data on a disk is missing after the instance was stopped and started" → the data was on instance store. Instance store data does not survive a stop, but EBS data does.

Purpose-built data stores

Remember

  • Use DynamoDB for key-value or document access by key, at any scale, serverless.
  • Use RDS or Aurora for relational data, joins, complex SQL, and transactions across tables.
  • Use ElastiCache for microsecond to sub-millisecond reads, caches, sessions, and leaderboards.
  • Use OpenSearch Service for full-text search, fuzzy match, relevance ranking, and log analytics.
  • Use Athena for ad hoc SQL on files in S3, with no servers and no data load.
  • Use S3 for large binary objects, files, and a data lake.
  • DynamoDB has no joins and no foreign keys.
  • DynamoDB finds items fast only by key, so DynamoDB is not good at text search.
  • A DynamoDB Scan with a contains filter reads every item and uses read capacity for all of them.
  • A DynamoDB contains filter gives no relevance ranking and no match for misspelled words.
  • To search DynamoDB data, keep DynamoDB as the main store and copy the data to OpenSearch Service.
  • With the DynamoDB zero-ETL integration, AWS runs the copy to OpenSearch Service through Amazon OpenSearch Ingestion.
  • The zero-ETL integration loads a first snapshot through export to S3, then copies changes from DynamoDB Streams.
  • The zero-ETL integration needs point-in-time recovery (PITR), because export to S3 needs PITR.
  • The zero-ETL integration needs DynamoDB Streams with new and old images.
  • The zero-ETL integration does not use the read or write capacity of the table.
  • DynamoDB Streams to a Lambda function that writes to OpenSearch Service also works, but needs custom code.
  • Athena runs standard SQL on data in S3, with no infrastructure to manage.
  • Athena charges for the data that each query scans. Less data scanned gives lower cost and faster queries.
  • Partition Athena data under Hive-style S3 prefixes. Example: year=2026/month=10/.
  • An Athena query with the partition column in the WHERE clause scans only that partition.
  • Use columnar formats (Apache Parquet, ORC) and compression, so Athena reads only the columns that the query needs.
  • Athena gets the list of partitions of a table from the AWS Glue Data Catalog.
  • When files arrive under a new S3 prefix, add the new partition, or Athena queries do not see the data.
  • MSCK REPAIR TABLE scans S3 and adds new Hive-style partitions.
  • Athena partition projection calculates the partitions from table properties, so you do not add them.
  • An Athena workgroup is a named group of users and queries with shared settings.
  • An Athena workgroup can set a data scanned limit for each query. Athena cancels a query that scans more.

Exam signals

  • "Search product descriptions by keywords, with relevance" → OpenSearch Service.
  • "Search DynamoDB data with the least operational overhead" → DynamoDB zero-ETL integration with OpenSearch Service, because AWS runs the pipeline and you write no copy code.
  • "Query logs in S3 with SQL occasionally, no servers" → Athena.
  • "Athena queries cost too much" → partition the data, convert to Parquet, and compress. Athena charges for the data that each query scans, and each change reduces that amount.
  • "Joins across many tables with referential integrity" → RDS or Aurora, not DynamoDB. DynamoDB has no joins and no foreign keys.

OpenSearch Service

  • DynamoDB is not good at text search, because it finds items fast only by key.
  • A Scan with a contains filter reads every item in the table and uses read capacity for all of them. It then drops the items that do not match. It also gives no relevance ranking and no match for misspelled words.
  • Keep DynamoDB as the main store, and copy the data to OpenSearch Service for search.
  • ETL (extract, transform, load) is a copy pipeline that you build and run yourself. With the DynamoDB zero-ETL integration, AWS runs the copy for you through Amazon OpenSearch Ingestion. It loads a first snapshot through export to S3, then copies changes from DynamoDB Streams.
  • The integration needs point-in-time recovery (PITR), because export to S3 needs it. It also needs DynamoDB Streams with new and old images, so that each change record contains the item data. It does not use the table's read or write capacity.
  • Another option: DynamoDB Streams to a Lambda function that writes to OpenSearch Service. This option needs custom code.

Athena

  • Athena runs standard SQL on data in S3. There is no infrastructure to manage.
  • You pay for the data that each query scans. Less data scanned means lower cost and faster queries.
  • Partition the data: put each group of files under its own S3 prefix (for example, year=2026/month=10/). This name=value form is called Hive style. A query with the partition column in the WHERE clause scans only that partition.
  • Use columnar formats (Apache Parquet, ORC) and compression. A columnar file stores each column separately, so Athena reads only the columns that the query needs.
  • Athena gets the list of partitions of a table from the AWS Glue Data Catalog. When files arrive under a new prefix, add the new partition, or queries do not see its data.
  • MSCK REPAIR TABLE scans S3 and adds new Hive-style partitions.
  • Partition projection calculates the partitions from table properties, so you do not add them.
  • An Athena workgroup is a named group of users and queries with shared settings. A workgroup can set a data scanned limit for each query. Athena cancels a query that scans more, so one unfiltered query cannot create a large bill.
