Event-driven architecture and fanout

Key facts

  • An event tells that something happened (for example, "OrderPlaced"). A command tells one receiver to do something (for example, "ChargeCard").
  • A producer publishes an event and does not know the consumers. You can add a consumer without a change to the producer.
  • Fanout sends one event to many consumers in parallel. Each consumer processes the event on its own.
  • Fanout with Amazon SNS: publish one time to a topic. Subscribe one Amazon SQS queue for each consumer. Each queue keeps its own copy of the message.
  • Fanout with Amazon EventBridge: one rule can send a matching event to up to 5 targets. For more consumers, add more rules on the same event pattern.
  • SNS filter policies send a subscriber only the messages it needs. A filter policy acts on message attributes or on the message body (filter policy scope). With no filter policy, a subscriber gets every message.
  • EventBridge event patterns match on any field in the event. Use EventBridge for routing on event content, for AWS service events, and for SaaS partner events.
  • SNS FIFO topics deliver to SQS FIFO queues and SQS standard queues. They do not deliver directly to Lambda, HTTP(S), email, or SMS endpoints.

Which service

NeedChoose
One message to many consumers, high throughput, simple attribute or body filterAmazon SNS topic (often with one SQS queue for each consumer)

Security

  • For SNS to SQS fanout, the queue policy must allow the sns.amazonaws.com service principal to do sqs:SendMessage.
  • Add the aws:SourceArn condition with the topic ARN. This stops other topics from sending to the queue (confused deputy protection).
  • Cross-account EventBridge: the receiver event bus needs a resource-based policy that allows the sender accounts (or the organization). The sender account creates a rule with the receiver bus ARN as the target. New cross-account bus targets need an IAM role.

Exam signals

  • "Add new consumers without changing the producer" → publish events to SNS or EventBridge.
  • "Each consumer must process every order, at its own speed, and not lose messages" → SNS topic with one SQS queue for each consumer.
  • "Route events by a field inside the event body to different services" → EventBridge rules with event patterns.
  • "SNS publishes succeed but the queue gets nothing" → the queue policy does not allow sqs:SendMessage from the topic.

Monolithic compared with microservices

Comparison

ItemMonolithMicroservices
DeploymentOne unit. A small change deploys the whole application.Each service deploys on its own.
ScalingThe whole application scales together.Each service scales on its own load.
DataOne shared database is common.Each service owns its data store. Other services use its API or its events.
Calls between partsIn-process function calls.Network calls (HTTP APIs, queues, events).
FailureOne defect can stop the whole application.Partial failure: one service can fail while others continue.

Key facts

  • Database per service: no other service reads or writes the tables of a service directly. A shared table couples the services again.
  • Network calls add latency and new failure modes. Use timeouts, retries with backoff, and asynchronous messages where the caller does not need an immediate answer.
  • A request can cross many services. Use distributed tracing (AWS X-Ray) and correlation IDs to follow one request.
  • A transaction that spans services cannot use one database transaction. Use a saga (see the orchestration topic).
  • Typical AWS building blocks: API Gateway or an Application Load Balancer in front, Lambda or containers for compute, DynamoDB or RDS for each service, SQS, SNS, or EventBridge between services.

Exam signals

  • "Teams must deploy and scale components independently" → microservices with separate deployments.
  • "One service reads another service's table directly, and schema changes break it" → give each service its own data store and expose an API or events.
  • "Find which service in a chain causes latency" → AWS X-Ray traces across services.

References: Implementing Microservices on AWS (whitepaper). Lab: Module 10 capstone.

Comparison

CouplingServices depend on the controller.Services are loosely coupled through events.

Saga pattern

  • A saga is a series of local transactions, one in each service. It keeps data consistent across services without a distributed transaction (two-phase commit).
  • If a step fails, the saga runs compensating transactions that undo the earlier steps (for example, refund the payment, then release the inventory).
  • Saga participants must be idempotent, because a step can run again after a failure.
  • A saga gives eventual consistency, not isolation. Other requests can see the data between steps.
  • Step Functions can act as the saga orchestrator. When a step fails, the workflow goes to compensation states (for example, through a Catch field or a Choice state).

Exam signals

  • "Central visibility of each order's progress", "human approval step", "run steps in a fixed order with error handling" → orchestration with Step Functions.
  • "Add consumers without changing the producer", "services must not know each other" → choreography with EventBridge or SNS.
  • "Undo earlier steps when a later step fails across services" → saga with compensating transactions.
  • "Non-idempotent step such as a payment, workflow can run for days" → Standard workflow.
  • "Very high volume of short event processing, at lowest cost" → Express workflow.

Coupling and synchronous compared with asynchronous

Key facts

  • Tight coupling: the caller calls the callee directly and waits. If the callee is slow or down, the caller is slow or fails too.
  • Loose coupling: a queue, topic, or event bus sits between the components. Each side can fail, scale, or change on its own.
  • Synchronous: the caller waits for the result. Examples: API Gateway to Lambda, Lambda RequestResponse invocation, Step Functions synchronous Express (StartSyncExecution).
  • Asynchronous: the caller gets an acknowledgment and continues. Examples: Lambda Event invocation, SQS, SNS, EventBridge.
  • Use synchronous calls only when the caller needs the answer now (for example, a price check before checkout).
  • Load leveling: an SQS queue absorbs traffic spikes. Consumers read at a rate that the backend can support.
  • A queue keeps messages when the consumer is down. The consumer continues when it comes back, within the retention period.
  • Asynchronous delivery is at least once in most AWS services. Make consumers idempotent.
  • Use a dead-letter queue to keep messages that fail many times. Then one bad message does not block the others.

Numbers to memorize

ItemValue

Exam signals

  • "Backend database fails during traffic spikes" → put an SQS queue in front of the writer (load leveling).
  • "Order service must keep taking orders when the shipping service is down" → asynchronous messages through a queue.
  • "Long job behind an API times out" → accept the request, queue the work, return an ID, and let the client check status later.
  • "Duplicate processing after a retry" → idempotent consumer (for example, a conditional write on a request ID).

Stateful compared with stateless

Key facts

  • A stateless component keeps no client data between requests. Any instance can serve any request.
  • A stateful component keeps client data (for example, a session or a cart) in its own memory or disk.
  • Stateless compute scales out and in easily. An instance can stop at any time and no session is lost.
  • Make compute stateless: store session state outside the compute, in DynamoDB or Amazon ElastiCache.
  • DynamoDB for sessions: durable, serverless, and Time to Live (TTL) deletes expired sessions. ElastiCache for sessions: in-memory, lowest latency.
  • Do not keep durable state in Lambda global variables or /tmp. Each execution environment has its own copy, and Lambda can end an environment at any time.
  • Do not keep durable state on one EC2 instance or container. Auto Scaling can terminate it.

Sticky sessions (Application Load Balancer)

  • Sticky sessions (session affinity) send all requests from one client to the same target. The client must support cookies.
  • Duration-based stickiness uses the load balancer cookie AWSALB. Application-based stickiness uses a cookie that your application sets.
  • Sticky sessions let a stateful application run behind a load balancer. But load can become uneven, and a session is lost when its target fails.
  • Sticky sessions are a workaround. The better design is an external session store.

Exam signals

  • "Users are logged out when Auto Scaling removes an instance" → move sessions to ElastiCache or DynamoDB.
  • "Shopping cart must survive instance failure and scale with traffic" → external session store, stateless instances.
  • "Lambda function counts requests in a global variable, and the count is wrong" → each environment has its own memory. Use DynamoDB (for example, an atomic counter).
  • "Legacy application keeps sessions in memory, fastest fix with no code change" → ALB sticky sessions.

References: ALB sticky sessions, Lambda execution environment, DynamoDB Time to Live. Lab: Lab 2.10 ElastiCache.

Application-level caching

Where to cache

LayerWhat it cachesWho shares the cache
Amazon CloudFrontHTTP responses at edge locations (static files, API GET responses)All users near an edge location
API Gateway cache (REST APIs)Integration responses for each stage, by cache keyAll clients of the stage
Amazon ElastiCache (Valkey, Redis OSS, Memcached)Any data your code puts there: query results, sessions, computed valuesAll application instances
DynamoDB Accelerator (DAX)DynamoDB items and query results, with no change to the data access logicAll clients of the DAX cluster
Lambda execution environment memoryValues in global variables or /tmpOnly that one execution environment

Key facts

  • Choose the layer by who reads the data and how often it changes. Cache close to the user for data that many users read.
  • Set a TTL on every cached item. A short TTL gives fresher data. A long TTL gives more cache hits.
  • Strategy definitions (lazy loading, write-through) are in Module 2. Lazy loading caches only requested data, but data can be stale. Write-through keeps the cache current, but caches data that nobody reads.

API Gateway cache

  • Only REST APIs have a cache. You turn it on for a stage. It costs money for each hour, by cache size.
  • TTL: default 300 seconds, maximum 3,600 seconds. TTL 0 turns caching off.
  • Only GET methods are cached by default. Override method settings to cache other methods.
  • Cache keys can include headers, path parameters, and query strings. Each key value gets its own cache entry.
  • A client can send Cache-Control: max-age=0 to get a fresh response. Require the execute-api:InvalidateCache permission, or any client can invalidate entries.
  • Flush the whole stage cache from the console or the CLI (flush-stage-cache).

CloudFront TTL

  • A cache policy sets minimum, default, and maximum TTL. The origin can send Cache-Control: max-age. CloudFront keeps it inside the minimum and maximum TTL.
  • Without a cache policy (legacy settings), the default TTL is 24 hours.
  • To remove content before it expires, create an invalidation or use versioned file names.

DAX

  • DAX is a write-through cache. Writes through DAX update DynamoDB first, then the item cache.
  • DAX passes strongly consistent reads to DynamoDB and does not cache the result. DAX serves only eventually consistent reads from cache.
  • Writes made directly to DynamoDB (not through DAX) do not update the DAX cache. The item stays stale until its TTL expires.
  • The item cache and the query cache are separate. An item update does not refresh cached query results.

Exam signals

  • "Same GET response for many users, reduce backend calls, no code change" → API Gateway cache or CloudFront.
  • "DynamoDB reads need microsecond latency with minimal code change" → DAX.
  • "Read needs strongly consistent data" → DAX does not help. It sends the read to DynamoDB.
  • "Cache results of an expensive RDS query for many instances" → ElastiCache.
  • "Some clients must be able to force a fresh response" → Cache-Control: max-age=0 with the execute-api:InvalidateCache permission.

References: API Gateway caching, CloudFront expiration, DAX and consistency, ElastiCache caching strategies. Lab: Lab 2.10 ElastiCache, Module 4 overview.

Storage options: block, file, object, ephemeral

Comparison

StorageTypeScope and accessPersistence
Amazon EBSBlockOne Availability Zone. Attaches to an instance in the same Availability Zone.Persists independently from the instance life.
Amazon EFSFile (NFS)Many clients at the same time. Regional file systems store data across Availability Zones. One Zone file systems use one Availability Zone.Persistent and shared.
Amazon S3ObjectHTTPS API from anywhere, by keyPersistent. Not a mounted disk.
EC2 instance storeBlock, on the hostOnly the one instanceKept on reboot. Lost on stop, hibernate, or terminate.
Lambda /tmpEphemeralOnly one execution environmentLost when the environment ends. Size 512 MB to 10,240 MB.

EBS

  • To use the data in another Availability Zone, create a snapshot, then create a new volume from it.
  • Multi-Attach: only Provisioned IOPS SSD (io1, io2), up to 16 Nitro instances in the same Availability Zone.
  • Multi-Attach needs a cluster-aware file system. Standard file systems such as XFS and EXT4 are not safe for many writers.

EFS

  • EFS uses NFS version 4 (4.0 and 4.1). EC2, ECS, EKS, Fargate, and Lambda can mount it. EFS does not support Windows instances.
  • EFS grows and shrinks automatically. You do not provision capacity.
  • Lambda and EFS: the function must connect to the VPC. Create a mount target in each Availability Zone that the function uses. Configure an access point and a local mount path that starts with /mnt/.
  • Security groups must allow NFS traffic on port 2049 between the function and the mount targets.
  • If the file system has an IAM policy, the execution role needs elasticfilesystem:ClientMount, and elasticfilesystem:ClientWrite for write access.
  • An access point sets the POSIX user, group, and root directory for each client. Use it to limit an application to one directory.

Exam signals

  • "Many Lambda functions or containers must share files with a file system interface" → EFS.
  • "Scratch data, fastest local disk, loss is acceptable" → instance store.
  • "Boot or database volume for one instance" → EBS.
  • "Store large objects for many readers over HTTP at low cost" → S3.
  • "Data on a disk is missing after the instance was stopped and started" → it was on instance store.

References: EBS volumes, EBS Multi-Attach, What is Amazon EFS, Lambda with EFS, Instance store data persistence. Lab: Module 1 overview.

Purpose-built data stores

Choose by access pattern

Access patternData store
Key-value or document access by key, any scale, serverlessAmazon DynamoDB
Relational data, joins, complex SQL, transactions across tablesAmazon RDS or Amazon Aurora
Microsecond to sub-millisecond reads, cache, sessions, leaderboardsAmazon ElastiCache
Full-text search, fuzzy match, relevance ranking, log analyticsAmazon OpenSearch Service
Ad hoc SQL on files in S3, no servers, no data loadAmazon Athena
Large binary objects, files, data lakeAmazon S3

OpenSearch Service

  • DynamoDB is not good at text search. A Scan with a contains filter reads the whole table.
  • Keep DynamoDB as the main store, and copy the data to OpenSearch Service for search.
  • DynamoDB zero-ETL integration uses Amazon OpenSearch Ingestion. It loads a first snapshot through export to S3, then copies changes from DynamoDB Streams.
  • The integration needs point-in-time recovery (for the export) and DynamoDB Streams with new and old images. It does not use the table's read or write capacity.
  • Another option: DynamoDB Streams to a Lambda function that writes to OpenSearch Service. This option needs custom code.

Athena

  • Athena runs standard SQL on data in S3. There is no infrastructure to manage.
  • You pay for the data that each query scans. Less data scanned means lower cost and faster queries.
  • Partition the data (for example, year=2026/month=10/). A query with the partition in the WHERE clause scans only that partition.
  • Use columnar formats (Apache Parquet, ORC) and compression. Athena then reads only the columns that the query needs.
  • Load new Hive-style partitions with MSCK REPAIR TABLE, or use partition projection.
  • A workgroup can set a data scanned limit for each query. Athena cancels a query that scans more.

Exam signals

  • "Search product descriptions by keywords, with relevance" → OpenSearch Service.
  • "Search DynamoDB data with the least operational overhead" → DynamoDB zero-ETL integration with OpenSearch Service.
  • "Query logs in S3 with SQL occasionally, no servers" → Athena.
  • "Athena queries cost too much" → partition the data, convert to Parquet, and compress.
  • "Joins across many tables with referential integrity" → RDS or Aurora, not DynamoDB.

References: DynamoDB zero-ETL integration with OpenSearch Service, Athena partitions, Athena columnar formats, Athena data usage controls. Lab: Module 2 overview.
