REST, HTTP, and WebSocket APIs and endpoint types

Remember

  • A REST API supports edge-optimized (the default), Regional, and private endpoints.
  • An HTTP API supports only Regional endpoints.
  • Only a REST API has API keys, usage plans, and per-client throttling.
  • Only a REST API has request validation and request body transformation with mapping templates. An HTTP API has parameter mapping only.
  • Only a REST API has API caching, AWS WAF, resource policies, and canary release deployments.
  • Only a REST API has execution logs, X-Ray tracing, and mock integrations. An HTTP API has access logs only.
  • Only an HTTP API has automatic deployments.
  • REST APIs and HTTP APIs both support stage variables.
  • An HTTP API costs less than a REST API.
  • A REST API supports IAM, Cognito user pool, and Lambda (TOKEN or REQUEST) authorizers.
  • An HTTP API supports IAM, JWT (including Cognito), and Lambda authorizers.
  • Use a REST API when the scenario needs API keys, usage plans, validation, caching, AWS WAF, resource policies, or a private endpoint.
  • Use an HTTP API for a low-cost proxy to Lambda or HTTP backends with JWT authorization.
  • Use a WebSocket API when the backend must send messages to the client without a client request (server push).
  • A WebSocket API suits chat, live dashboards, and notifications.
  • With a REST API or an HTTP API, the client must poll to get new data.
  • A WebSocket API calls the $connect route when a client connects and the $disconnect route when the connection closes.
  • The route selection expression, for example $request.body.action, picks the WebSocket route for each message.
  • A WebSocket message that matches no route goes to the $default route.
  • The backend gets the WebSocket connection ID from requestContext.connectionId in the $connect event.
  • To send a message to a WebSocket client, the backend makes a SigV4-signed POST to @connections/{connection_id}.
  • On @connections, GET returns the connection status and DELETE disconnects the client.
  • A POST to a closed WebSocket connection fails with GoneException. Remove that stored connection ID.
  • A WebSocket connection lasts 2 hours maximum.
  • API Gateway closes a WebSocket connection after 10 minutes with no messages (idle timeout).
  • A WebSocket message payload has a limit of 128 KB, in frames of 32 KB maximum.
  • Choose an edge-optimized endpoint for clients in many countries. Requests go through the nearest CloudFront edge location.
  • API Gateway manages the CloudFront distribution of an edge-optimized API, and you cannot change its settings.
  • Choose a Regional endpoint for clients in the same Region.
  • To control caching, AWS WAF, or edge functions, put your own CloudFront distribution in front of a Regional API.
  • A private API is reachable only from a VPC through an interface VPC endpoint.
  • A resource policy controls access to a private API.
  • Edge-optimized and Regional endpoints are always public.

Exam signals

  • "Partner API keys and per-customer quotas" → REST API. Only REST APIs have API keys and usage plans.
  • "Lowest cost, Lambda proxy, validate JWTs" → HTTP API with a JWT authorizer. HTTP APIs cost less and validate JWTs with no code.
  • "Server must push updates to connected browsers" → WebSocket API and @connections. Only a WebSocket API keeps a connection that the server can send on.
  • "API must not be reachable from the internet" → private REST API with an interface VPC endpoint. Edge-optimized and Regional endpoints are always public.

Key facts

  • Choose a REST API when the scenario needs API keys, usage plans, request validation, caching, AWS WAF, resource policies, or a private endpoint.
  • Choose an HTTP API for a low-cost proxy to Lambda or HTTP backends with JWT authorization.
  • A WebSocket API keeps a two-way connection open between the client and API Gateway. The backend can then send a message to the client at any time, without a client request (server push).
  • Use a WebSocket API for chat, live dashboards, and notifications. With REST or HTTP APIs, the client must poll (ask again and again) to get new data.
  • WebSocket routes: API Gateway calls the $connect route when a client connects and the $disconnect route when the connection closes.
  • For each message, API Gateway reads the value that the route selection expression names (for example, $request.body.action, the action field of the JSON message). It sends the message to the custom route with that key, for example sendmessage.
  • Messages that match no route go to $default.
  • Each connection has a connection ID. The backend gets it from requestContext.connectionId in the $connect event and usually stores it, for example in DynamoDB.
  • To send a message, the backend makes a POST to @connections/{connection_id} (API Gateway Management API). The request must have a SigV4 signature (Signature Version 4: a signature made with AWS credentials).
  • GET on @connections/{connection_id} returns the connection status. DELETE disconnects the client.
  • A POST to a closed connection fails with GoneException, so remove that stored ID.
  • Edge-optimized: requests go to the nearest CloudFront edge location (a CloudFront data center near the user), then over the AWS network to the API Region. Choose it for clients in many countries.
  • API Gateway manages the CloudFront distribution of an edge-optimized API, and you cannot change its settings.
  • Regional: for clients in the same Region. You can put your own CloudFront distribution in front of it when you need control of caching, AWS WAF, or edge functions.
  • Private: reachable only from a VPC through an interface VPC endpoint. A resource policy controls access.

Integrations, proxy formats, and timeouts

Remember

  • AWS_PROXY (Lambda proxy) sends the whole request to Lambda, and Lambda returns the full HTTP response.
  • AWS (Lambda custom or other AWS service) uses mapping templates for the integration request and response.
  • HTTP_PROXY passes the request to an HTTP endpoint without changes.
  • HTTP calls an HTTP endpoint with mapping templates.
  • A MOCK integration returns a response from a mapping template with no backend.
  • Use a proxy integration when the backend reads the request as it is and builds its own response.
  • Use a non-proxy integration when API Gateway must change the request or response. Examples: rename fields, set status codes.
  • A non-proxy AWS integration can call an AWS service such as Amazon SQS directly, with no Lambda function.
  • A Lambda proxy function must return statusCode, and optionally headers, multiValueHeaders, body, and isBase64Encoded.
  • The Lambda proxy body must be a string. Convert a JSON object first, for example with JSON.stringify().
  • A Lambda proxy output in the wrong format makes API Gateway return 502 Bad Gateway.
  • REST API proxy events use payload format 1.0 (httpMethod, path, queryStringParameters).
  • HTTP API Lambda integrations support payload formats 1.0 and 2.0.
  • Payload format 2.0 puts the method in requestContext.http.method and uses rawPath and rawQueryString.
  • Code written for format 1.0 reads event.httpMethod as undefined with payload format 2.0.
  • A REST API integration timeout is 50 ms to 29 seconds.
  • You can request a longer REST API timeout for Regional and private APIs, not for edge-optimized APIs.
  • An HTTP API integration timeout is 30 seconds maximum.
  • REST APIs and HTTP APIs both have a payload limit of 10 MB.
  • An integration timeout returns 504 to the client, even if the Lambda function continues to run.
  • A longer Lambda function timeout does not change the 29-second API Gateway limit.
  • For long work in a Lambda custom integration, set the header X-Amz-Invocation-Type to 'Event' to invoke asynchronously.
  • An asynchronous Lambda integration responds at once without the function result. The client gets the result later, for example from a status endpoint.
  • Use a mock integration to test clients or prototype an API before the backend exists.
  • The CORS OPTIONS method uses a mock integration.
  • {proxy+} is a greedy path variable that matches every path below its resource.
  • {proxy+} with the ANY method sends all paths and methods to one integration. Use it when one Lambda function does its own routing.
  • Without permission to invoke the Lambda function, API Gateway returns 500 and logs "Invalid permissions on Lambda function".
  • The console adds the Lambda invoke permission for API Gateway. With the CLI or plain CloudFormation, add the permission yourself.
  • A private integration (VPC link) lets the API reach resources in a VPC that are not public.
  • A REST API uses a VPC link V2 to an Application Load Balancer or a Network Load Balancer.
  • VPC links V1 are legacy and support only a Network Load Balancer. Older study material says "REST API → NLB".
  • REST APIs do not support AWS Cloud Map in a private integration.
  • An HTTP API uses a VPC link to an Application Load Balancer, a Network Load Balancer, or an AWS Cloud Map service.

Exam signals

  • "502 Bad Gateway from a Lambda proxy API" → wrong response format from the function. Examples: an object with no statusCode, or a body that is not a string.
  • "504 after about 29 seconds" → integration timeout. Make the work asynchronous.
  • "504 after about 29 seconds" → a longer function timeout does not help. The 29-second API Gateway limit does not change.
  • "Function moved from REST API to HTTP API and event.httpMethod is undefined" → payload format 2.0. Set format 1.0 or change the code.
  • "event.httpMethod is undefined on an HTTP API" → format 2.0 puts the method in requestContext.http.method.
  • "Front-end team must test against the API before the backend exists" → mock integration.

Stages, deployments, stage variables, and canary releases

Remember

  • A deployment is a snapshot of the REST API configuration.
  • A stage points to one deployment and has its own URL: https://{api-id}.execute-api.{region}.amazonaws.com/{stage}.
  • Changes to a REST API do not reach clients until you deploy the API to a stage again.
  • Each stage has its own throttling, caching, logging, tracing, and stage variables.
  • Stage variables are key-value pairs for a stage that work like environment variables.
  • Use stage variables in integration URIs, Lambda function names or aliases, and mapping templates.
  • Stage variables let one API definition call a different backend from each stage, for example a dev alias and a prod alias.
  • The stage variable syntax is ${stageVariables.name}. Example: ...:function:my-fn:${stageVariables.alias}.
  • When a stage variable picks the Lambda function or alias, add a Lambda permission for each function or alias yourself.
  • API Gateway cannot add the Lambda permission for a stage variable ARN, because it knows the real ARN only at run time.
  • A missing Lambda permission for a stage variable ARN makes calls fail with 500.
  • Do not put secrets in stage variables. Anyone who can read the stage configuration can read them.
  • To pass sensitive data to an integration, AWS recommends the output of a Lambda authorizer.
  • A Lambda proxy event includes the stage variable values in stageVariables.
  • A canary release (REST API) sends a percentage (0.0 to 100.0) of stage traffic to a new deployment.
  • A canary can override stage variables, for example to send canary traffic to a new Lambda alias.
  • Canary requests have separate execution logs and access logs. The log group name ends with /Canary.
  • After tests pass, promote the canary. The canary deployment then becomes the stage deployment.
  • A stage has a limit of 100 stage variables.
  • An API has a soft limit of 10 stages.

Exam signals

  • "One API, dev and prod stages call different Lambda aliases" → stage variable in the integration ARN, and a permission for each alias.
  • "Send 10% of API traffic to the new API configuration" → canary release on the stage.
  • "Change in the console has no effect" → deploy the API to the stage. A REST API stage serves only the deployment snapshot that it points to.

Explanation

  • A deployment is a snapshot of the REST API configuration. A stage points to one deployment and has its own URL: https://{api-id}.execute-api.{region}.amazonaws.com/{stage}.
  • Changes to a REST API do not reach clients until you deploy the API to a stage again.
  • Each stage has its own settings: throttling, caching, logging, tracing, and stage variables.
  • Stage variables are key-value pairs for a stage. They work like environment variables.
  • Use stage variables in integration URIs, Lambda function names or aliases, and mapping templates. One API definition can then call a different backend from each stage, for example the dev alias from the dev stage and the prod alias from the prod stage.

  • To pass sensitive data to an integration, AWS recommends the output of a Lambda authorizer.
  • The proxy event includes the values in stageVariables, so the function can read them.

  • A canary sends a percentage (0.0 to 100.0) of stage traffic to a new deployment. The rest goes to the current deployment.
  • The canary can override stage variables. Use this to send canary traffic to a new backend, for example a new Lambda alias.
  • Canary requests have separate execution logs and access logs (log group name ends with /Canary).
  • After tests pass, promote the canary. It then becomes the stage deployment.

Mapping templates, request validation, and status codes

Remember

  • A REST API request flows in this order: method request, integration request, backend, integration response, method response.
  • The method request and method response are the public interface that the client sees.
  • The integration request and integration response are what the backend sees.
  • The method request holds authorization, required parameters, the request model, and the request validator.
  • The integration request holds the backend target and the request mapping template.
  • The integration response holds the response mapping template and the status code selection.
  • The method response lists the status codes and headers that the API can return.
  • Request validation needs a model (JSON Schema draft 4) and a request validator on the method.
  • A request validator checks the body, the query string parameters and headers, or both.
  • API Gateway rejects an invalid request with 400 before it calls the backend.
  • Request validation saves backend invocation cost and backend validation code.
  • To change the validation error message, use a gateway response, for example BAD_REQUEST_BODY.
  • $context.error.validationErrorString has the details of a validation error.
  • A mapping template is a VTL script that builds a new request or response body from the original.
  • Mapping templates work only with non-proxy integrations (AWS, HTTP). Proxy integrations do not use them.
  • $input.body returns the raw request body as a string.
  • $input.json('$.x') returns the value at a JSON path as a JSON string.
  • $input.path('$.x') returns the value at a JSON path as an object, so the template can loop over it.
  • $input.params('x') looks for parameter x in the path, then the query string, then the headers.
  • $context.authorizer.claims.sub gives the Cognito user ID from the token.
  • $context.identity.sourceIp gives the client IP address, and $context.requestId gives the request ID.
  • $util.escapeJavaScript() escapes a string to stop injection from request parameters.
  • $util.escapeJavaScript() output has \', which is not valid JSON. Replace \' with ' in a JSON template.
  • $util.parseJson() turns a JSON string into an object.
  • $stageVariables.name reads a stage variable in a mapping template. $util.base64Encode() and $util.urlEncode() encode values.
  • $context.responseOverride.status sets the response status code from a template, for example 201 or 404.
  • A non-proxy Lambda integration returns 200 by default, even when the function fails.
  • To return an error status code, add an integration response with a selection pattern.
  • For Lambda, the selection pattern regular expression matches the errorMessage of the function error.
  • The status code of an integration response must also exist as a method response.

Exam signals

  • "Reject requests without required fields before Lambda runs" → model and request validator. API Gateway checks the request against the model before it calls the backend.
  • "Legacy backend expects other field names, no backend change" → non-proxy integration with a mapping template. The template rebuilds the body in API Gateway with no new compute.
  • "Return 422 when Lambda throws ORDER_TOO_LARGE" → integration response with selection pattern .*ORDER_TOO_LARGE.* and a 422 method response.

Explanation

Request flow (REST API)

A request passes through these steps in this order: method request, integration request, the backend, integration response, and method response.

The method request and method response are the public interface that the client sees. The integration request and integration response are what the backend sees. In a non-proxy integration, API Gateway can change the data between these two sides.

  • Method request: authorization, required parameters, request model, request validator.
  • Integration request: backend target and request mapping template.
  • Integration response: response mapping template and status code selection.
  • Method response: status codes and headers that the API can return.

Request validation

  • You need a model (JSON Schema draft 4) and a request validator on the method.
  • Validator options: validate body, validate query string parameters and headers, or both.
  • API Gateway rejects an invalid request with 400 before it calls the backend. The backend does not run for bad input, so you do not pay for those invocations or write that validation code.
  • Change the error message with a gateway response (for example, BAD_REQUEST_BODY). $context.error.validationErrorString has the details.

Mapping templates (VTL)

  • A mapping template is a script in VTL (Apache Velocity Template Language) that builds a new request or response body from the original. Use it when the backend expects a different body shape than the client sends.
  • Mapping templates work with non-proxy integrations (AWS, HTTP). Proxy integrations do not use them.
  • $input.body returns the raw body as a string.
  • $input.json('$.x') returns the value at JSON path $.x as a JSON string, ready to put into a JSON template.
  • $input.path('$.x') returns the value as an object, so the template can read its fields or loop over it.
  • $input.params('x') returns the request parameter x. It looks in the path first, then the query string, then the headers.
  • Useful variables: $context.requestId (the unique ID of the request), $context.identity.sourceIp (the client IP address), $context.authorizer.claims.sub (the Cognito user ID from the token), and $stageVariables.name (a stage variable).
  • Helper function $util.escapeJavaScript() escapes a string with JavaScript rules. Use it to stop injection from request parameters.
  • The escaped single quotes (\') from $util.escapeJavaScript() are not valid JSON, so replace \' with ' in a JSON template.
  • $util.parseJson() turns a JSON string into an object. $util.base64Encode() and $util.urlEncode() encode values.
  • $context.responseOverride.status sets the response status code from a template. Use it, for example, to return 201 or 404 based on the backend data.

Status codes from a non-proxy Lambda integration

  • By default, the integration response returns 200, even when the function fails. The default integration response has no selection pattern, so it matches every result, and the client gets the error object in a 200 body.
  • Add an integration response with a selection pattern. For Lambda, the regular expression matches the errorMessage of the function error. When it matches, API Gateway returns the status code of that integration response.
  • The status code must also exist as a method response, because the method response lists every status code that the API can return to clients.

Throttling, usage plans, and API keys

Remember

  • API Gateway throttles with a token bucket. Each request uses one token.
  • The throttle rate is the steady number of requests each second.
  • The throttle burst is the bucket size: the number of requests that can arrive at the same moment.
  • A throttled request gets 429 Too Many Requests.
  • A throttled client must retry with exponential backoff and jitter.
  • API Gateway applies limits in this order: usage plan, stage or method, account for the Region, AWS Regional.
  • The lowest throttle limit that applies controls the request.
  • All APIs in one account and Region share the account throttle limit.
  • One busy API can use the account limit and cause 429 errors for other APIs.
  • The account throttle is 10,000 requests per second with a burst of 5,000 in each Region.
  • Some newer Regions have an account throttle of 2,500 requests per second with a burst of 1,250.
  • You can request a higher account throttle rate.
  • Throttles and quotas are best effort. Do not use them as a security or cost control.
  • A usage plan (REST API only) sets throttle and quota for API keys on one or more API stages.
  • A usage plan quota period is DAY, WEEK, or MONTH.
  • Clients send the API key in the x-api-key header.
  • Set apiKeyRequired on each method. Without it, API Gateway ignores the key and the usage plan limits.
  • A missing or wrong API key returns 403 Forbidden.
  • An API key can be in more than one usage plan, but only in one usage plan for each stage.
  • With API key source AUTHORIZER, a Lambda authorizer returns the key in usageIdentifierKey.
  • API keys are not authentication. Use IAM, Cognito, or a Lambda authorizer to control access.
  • Use API keys for metering: counting requests for each customer.
  • Do not rely on usage plans to control cost. Use AWS Budgets, and AWS WAF to manage requests.

Exam signals

  • "Gold and Silver customers get different request rates and monthly quotas" → usage plans and an API key for each customer. The key tells API Gateway which plan limits to apply.
  • "Secure the API that uses API keys" → add an authorizer. A key does not prove identity.
  • "API keys in a secured API" → keep keys for metering (counting requests for each customer).
  • "Clients get 429 during spikes" → retry with exponential backoff, or raise stage or account limits. A 429 means a throttle limit, not a server fault.

Explanation

Throttling

  • API Gateway uses a token bucket. Each request uses one token.
  • Rate is the number of tokens added each second, so it is the steady request rate. Burst is the bucket size, so it is the number of requests that can arrive at the same moment.
  • Example: rate 100 and burst 200 accept a short spike of 200 requests, then about 100 each second.
  • Over the limit, clients get 429 Too Many Requests.
  • Clients must retry with exponential backoff (a longer wait after each failure) and jitter (a random part of the wait). Jitter stops all clients from retrying at the same moment.
  • Order that API Gateway applies limits: usage plan per-client or per-method limits, then stage or method limits, then the account limit for the Region, then AWS Regional limits. A request must pass every level, so the lowest limit that applies controls the request.
  • The account limit is shared by all APIs in the account in that Region. One busy API can use the limit and cause 429 errors for the other APIs.
  • Throttles and quotas are best effort. They are targets, not guaranteed ceilings. Some requests can pass after a client reaches its limit, so do not use them as a security or cost control.

Usage plans and API keys (REST API only)

  • A usage plan sets throttle (rate and burst) and quota for API keys on one or more API stages.
  • Clients send the key in the x-api-key header.
  • Set apiKeyRequired on each method. If a method does not require a key, API Gateway does not check the key, and the usage plan limits do not apply to that method.
  • A missing or wrong key returns 403 Forbidden.
  • A key can be in more than one usage plan, but only in one usage plan for each stage. API Gateway must know which one set of limits to apply to the key on that stage.
  • Clients do not always send the key themselves. With API key source AUTHORIZER, a Lambda authorizer finds the key for the caller (for example, from the tenant in the token) and returns it in usageIdentifierKey. API Gateway then applies the usage plan of that key.
  • API keys are not authentication. AWS says: do not use API keys to control access.
  • A key is a fixed string in a header. Anyone who copies it can use it, and it does not prove who the caller is. Use IAM, Cognito, or a Lambda authorizer.
  • Do not rely on usage plans to control cost, because limits are best effort and some requests pass. Use AWS Budgets, and AWS WAF to manage requests.

API caching

Remember

  • API caching is for REST APIs only.
  • You turn on the API cache for a stage, and you can override the settings for each method.
  • By default, API Gateway caches only GET methods.
  • The default API cache TTL is 300 seconds.
  • The API cache TTL range is 0 to 3,600 seconds. TTL 0 turns caching off.
  • The largest cached response is 1,048,576 bytes (1 MB).
  • The API cache is charged by the hour for the cache size and is not in the AWS Free Tier.
  • Add query strings, headers, or path parameters as cache keys to cache their values separately.
  • A parameter that changes the response but is not a cache key makes users get responses made for other values.
  • Encrypt the cache data when responses contain sensitive data.
  • Flush the whole stage cache in the console or with flush-stage-cache.
  • After a cache flush, all requests go to the backend until the cache fills again.
  • A client invalidates one cache entry with the header Cache-Control: max-age=0.

  • SUCCEED_WITHOUT_RESPONSE_HEADER ignores an unauthorized invalidation and adds no warning.
  • Monitor the API cache with CacheHitCount and CacheMissCount.
  • Many cache misses can mean cache keys that are too specific, a short TTL, or client invalidations.

Authorizers, IAM authorization, and resource policies

Remember

  • IAM (AWS_IAM) authorization works on REST, HTTP, and WebSocket APIs.
  • IAM authorization checks a SigV4 signature, and the caller needs execute-api:Invoke.
  • A Cognito user pool authorizer (COGNITO_USER_POOLS) is for REST APIs and checks a user pool ID token or access token.
  • A JWT authorizer is for HTTP APIs and checks any OIDC or OAuth 2.0 JWT, including Cognito tokens.
  • A TOKEN Lambda authorizer is for REST APIs and checks one token in one header.
  • A REQUEST Lambda authorizer works on REST, HTTP, and WebSocket APIs.
  • A REQUEST Lambda authorizer checks headers, query strings, stage variables, and context variables.
  • A resource policy (REST API) allows or denies by principal, account, IP range, or VPC endpoint.
  • Use IAM authorization when the callers are AWS identities that sign requests.
  • Use a Cognito or JWT authorizer when users sign in, send a token, and you want no authorizer code.
  • Use a Lambda authorizer for tokens that built-in authorizers cannot check, or for custom logic.
  • A Cognito user pool authorizer reads the token from the Authorization header.
  • An ID token describes the user. An access token lists the OAuth scopes.
  • With no OAuth scopes on the method, a Cognito user pool authorizer treats the token as an ID token.
  • With OAuth scopes on the method, a Cognito user pool authorizer treats the token as an access token.
  • An access token with no matching scope gets 401.
  • The backend gets token claims in $context.authorizer.claims (proxy: requestContext.authorizer.claims).
  • A Lambda authorizer returns principalId, a policyDocument, and an optional context map.
  • An HTTP API Lambda authorizer can return the simple response {"isAuthorized": true}.
  • A Lambda authorizer policy that denies the method gives 403 Forbidden.
  • A Lambda authorizer error with the exact message "Unauthorized" gives 401 Unauthorized.
  • A Lambda authorizer that fails with any other error gives 500.
  • A cached REQUEST authorizer returns 401 without a call when an identity source is missing, null, or empty.
  • AWS recommends REQUEST authorizers over TOKEN authorizers.
  • A REQUEST authorizer can use several identity sources, and all of them form the cache key.
  • The Lambda authorizer cache TTL defaults to 300 seconds, with a maximum of 3,600. TTL 0 turns caching off.
  • A cached Lambda authorizer policy applies to other methods for the same identity.
  • With authorizer caching, return a policy that covers every method that the caller can use, or turn off caching.
  • A JWT authorizer checks the signature with the public keys at the issuer jwks_uri.
  • A JWT authorizer checks the claims iss, aud or client_id, exp, nbf, iat, and the route scopes.
  • The Cognito issuer URL is https://cognito-idp.{region}.amazonaws.com/{userPoolId}.
  • Same account: an IAM identity policy that allows execute-api:Invoke is enough.
  • Cross-account IAM access needs an identity policy for the caller and a resource policy on the API.
  • A private API needs a resource policy that allows access from the VPC endpoint or VPC.
  • Identity pool users can sign API requests with their temporary credentials.

  • "HTTP API, tokens from a third-party OIDC provider" → JWT authorizer. It validates any OIDC or OAuth 2.0 JWT with no code.

  • Cross-account: the caller needs an identity policy, and the API needs a resource policy that allows the caller.
  • A private API needs a resource policy that allows access from the VPC endpoint or VPC.
  • Callers from an identity pool can sign requests with their temporary credentials.

CORS

Remember

  • An origin is the protocol, domain, and port of the web page.
  • A different domain, subdomain, port, or protocol is cross-origin.
  • A browser blocks a cross-origin response unless the response has the correct CORS headers.
  • A blocked cross-origin request can reach the API, but the browser hides the response from the page code.
  • A non-simple request, for example with an Authorization header or JSON content type, causes a preflight OPTIONS request.
  • If the preflight OPTIONS response does not allow the request, the browser does not send the real request.
  • Access-Control-Allow-Origin lists the origins that can read the response.
  • Access-Control-Allow-Methods lists the allowed HTTP methods.
  • Access-Control-Allow-Headers lists the request headers that the client can send.
  • For a REST API non-proxy integration, "Enable CORS" adds an OPTIONS mock method and integration response headers.
  • For a REST API Lambda proxy or HTTP proxy integration, the backend must return the CORS headers in each response.
  • API Gateway cannot add CORS headers to a proxy integration response.
  • To put CORS headers on API Gateway errors (4XX, 5XX), add them to the gateway responses.
  • An API Gateway error without CORS headers shows in the browser as a CORS error and hides the real status code.
  • For an HTTP API, configure CORS on the API. API Gateway answers preflight requests itself.
  • An HTTP API with CORS configured ignores CORS headers from the backend.

Exam signals

  • "CORS enabled in the console, but the browser still blocks a Lambda proxy response" → return Access-Control-Allow-Origin from the function. A proxy integration has no integration response where API Gateway can add the header.
  • "HTTP API, browser app on another domain, least effort" → CORS configuration on the HTTP API.

Explanation

Key facts

  • An origin is the protocol, domain, and port of the web page, for example https://app.example.com.
  • A browser blocks a cross-origin call unless the response has the correct CORS headers. A different domain, subdomain, port, or protocol is cross-origin. The request can reach the API, but the browser does not give the response to the page code.
  • A non-simple request (for example, with an Authorization header or JSON content type) causes a preflight OPTIONS request.
  • In the preflight, the browser asks the API if the origin, method, and headers are allowed. If the OPTIONS response does not allow them, the browser does not send the real request.
  • Headers: Access-Control-Allow-Origin (the origins that can read the response), Access-Control-Allow-Methods (the allowed HTTP methods), Access-Control-Allow-Headers (the request headers that the client can send).
  • REST API, non-proxy integration: "Enable CORS" adds an OPTIONS mock method and adds headers to the integration responses.
  • REST API, Lambda proxy or HTTP proxy: the backend must return the CORS headers in each response. API Gateway cannot add them.
  • For CORS headers on API Gateway errors (4XX, 5XX), add them to the gateway responses. When API Gateway itself rejects a request (for example, 401 from an authorizer or 429 from throttling), the backend does not run and cannot add the headers. The browser then shows a CORS error and hides the real status code.
  • HTTP API: configure CORS on the API. API Gateway answers preflight requests itself and ignores CORS headers from the backend.

Cognito user pools: tokens, sign-in, and triggers

Remember

  • A user pool is a user directory for sign-up, sign-in, and MFA.
  • A user pool issues JWTs: an ID token, an access token, and a refresh token.
  • Use user pool tokens to authorize calls to your own API.
  • An identity pool gives temporary AWS credentials from AWS STS to call AWS services directly.
  • The ID token holds identity claims: sub, email, custom attributes, and cognito:groups.
  • The access token holds scope, client_id, and cognito:groups, and has no aud claim by default.
  • The ID token and the access token are valid for 1 hour by default, with a maximum of 1 day.
  • The refresh token is valid for 30 days by default, with a range of 60 minutes to 10 years.
  • The refresh token is encrypted and gets new ID and access tokens without a new sign-in.
  • Send the access token when the API checks OAuth scopes. Only the access token carries scopes.
  • Send the ID token when the backend needs user facts, such as the email address.
  • To verify a Cognito JWT, check the signature with the JWKS at https://cognito-idp.{region}.amazonaws.com/{userPoolId}/.well-known/jwks.json.
  • After the JWT signature, check exp, iss, and token_use (id or access).
  • Check token_use so that nobody can use an ID token as an access token.
  • Last, check that aud (ID token) or client_id (access token) is your app client.
  • GlobalSignOut and AdminUserGlobalSignOut revoke all refresh, ID, and access tokens of a user.
  • RevokeToken revokes one refresh token and the access tokens that it issued.
  • Cognito APIs reject revoked tokens.
  • A service that checks only the signature and expiry accepts revoked tokens until they expire.
  • Keep access token validity short, because revoked tokens stay valid for signature-only checks.
  • Refresh token rotation issues a new refresh token at each refresh and does not extend the original validity.
  • With refresh token rotation, the old refresh token stops working after an optional grace period of up to 60 seconds.
  • Use an app client with no secret for browser and mobile apps.
  • Use an app client with a secret for server-side apps.
  • ALLOW_USER_SRP_AUTH sends proof of the password, not the password. Use it in client apps.
  • ALLOW_USER_PASSWORD_AUTH sends the password to Cognito over TLS.
  • The migrate user trigger needs a flow that sends the password, for example ALLOW_USER_PASSWORD_AUTH.
  • ALLOW_ADMIN_USER_PASSWORD_AUTH lets a server-side app sign users in with AdminInitiateAuth and IAM credentials.
  • ALLOW_CUSTOM_AUTH uses Lambda challenge triggers to decide the sign-in steps.
  • ALLOW_REFRESH_TOKEN_AUTH gets new ID and access tokens with a refresh token.
  • ALLOW_USER_AUTH is choice-based sign-in: password, passkey, or a one-time code by email or SMS.
  • Managed login (formerly hosted UI) gives OAuth 2.0 sign-in pages and federation with SAML, OIDC, and social providers.
  • User pool MFA supports SMS, email, and TOTP (authenticator app).
  • User pool groups put a cognito:groups claim in tokens for role-based access.
  • Only administrators can change group membership, so users cannot add themselves to a group.
  • A user pool group can have an IAM role for identity pools.
  • A resource server defines custom scopes for your API, for example orders/read.
  • Use the authorization code grant with PKCE for web, single-page, and mobile apps where users sign in.
  • PKCE makes a stolen authorization code useless.
  • The implicit grant is an older flow that returns tokens in the redirect URL. Use authorization code with PKCE instead.
  • Use the client credentials grant for machine-to-machine calls. An app client with a secret gets an access token with custom scopes and no ID token.
  • The pre sign-up trigger accepts or denies sign-up and can auto-confirm users.
  • The post confirmation trigger sends a welcome message or writes the user to a database.
  • The pre authentication trigger accepts or denies a sign-in.
  • The post authentication trigger logs sign-in events.
  • The pre token generation trigger adds, changes, or removes token claims.
  • The migrate user trigger moves users from an old directory at sign-in.
  • The custom message and custom sender triggers change messages or send them through a third-party provider.
  • The define, create, and verify auth challenge triggers build a custom authentication flow.
  • Cognito invokes Lambda triggers synchronously, except custom sender triggers.
  • A Cognito Lambda trigger must respond within 5 seconds, and you cannot change this limit.
  • A Cognito trigger that returns an error, or fails on every attempt, makes the sign-up or sign-in fail.

  • "Add a tenant ID claim to tokens" → pre token generation trigger. It runs just before Cognito issues the tokens.

  • App client with no secret: browser and mobile apps. With a secret: server-side apps.

Cognito identity pools and temporary AWS credentials

Remember

  • An identity pool exchanges proof of sign-in for temporary AWS credentials.
  • An identity pool accepts user pool ID tokens, OIDC ID tokens, SAML assertions, social provider tokens, and developer-authenticated identities.
  • With identity pool credentials, the app calls AWS services such as S3 or DynamoDB directly.
  • Each identity pool has an authenticated role and an optional unauthenticated (guest) role.
  • Anyone who runs the app can get guest credentials without a sign-in.
  • Turn on guest access only if you need it, and give the guest role fewer permissions.
  • An identity pool role trust policy trusts cognito-identity.amazonaws.com for sts:AssumeRoleWithWebIdentity.
  • The trust policy needs a cognito-identity.amazonaws.com:aud condition equal to your identity pool ID.
  • IAM returns an error if you save an identity pool trust policy without the aud condition.
  • Use the cognito-identity.amazonaws.com:amr condition so that guests cannot assume the authenticated role.
  • The enhanced flow (recommended) calls GetId, then GetCredentialsForIdentity.
  • In the enhanced flow, the identity pool picks the role, and the credentials are valid for 1 hour.
  • The basic flow calls GetId, GetOpenIdToken, then STS AssumeRoleWithWebIdentity.
  • In the basic flow, the app picks the role, and role mappings are not supported.
  • Use the enhanced flow, because in the basic flow a changed app can ask for any role that trusts the identity pool.
  • By default, all authenticated users get the default authenticated role.
  • Choose role from token uses cognito:preferred_role or cognito:roles from user pool groups.
  • When a user is in more than one group, the group with the lowest precedence value wins.
  • Role mapping rules map a token claim to a role. The first matching rule wins.
  • An identity pool has a maximum of 25 role mapping rules for each provider.
  • Do not map roles from claims that users can change, for example custom:role.
  • The policy variable ${cognito-identity.amazonaws.com:sub} is the identity ID of the caller, not the user pool sub.
  • To limit each user to an S3 prefix, use arn:aws:s3:::bucket/${cognito-identity.amazonaws.com:sub}/*.
  • To limit each user to DynamoDB items with their identity ID as partition key, use dynamodb:LeadingKeys.

  • "Group members get a different IAM role" → group IAM role and "choose role from token". The group role arrives in the token claim.
  • "User pool or identity pool" → JWT for your API: user pool. AWS credentials: identity pool.

Explanation

Key facts

  • An identity pool exchanges proof of sign-in for temporary AWS credentials.
  • Accepted proof: user pool ID token, OIDC ID token, SAML assertion, social provider token, or a developer-authenticated identity (your own backend signs the user in and vouches for the user).
  • The app then calls AWS services such as S3 or DynamoDB directly with these credentials.
  • Each identity pool has an authenticated role and an optional unauthenticated (guest) role.
  • Turn on guest access only if you need it. Give the guest role fewer permissions, because anyone who runs the app can get guest credentials without a sign-in.
  • The role trust policy must trust cognito-identity.amazonaws.com for sts:AssumeRoleWithWebIdentity, with a cognito-identity.amazonaws.com:aud condition equal to your identity pool ID.
  • The aud condition limits the role to your identity pool. IAM returns an error if you save this trust policy without it.
  • The cognito-identity.amazonaws.com:amr condition (authentication method) has the value authenticated or unauthenticated. Use it so that guests cannot assume the authenticated role.

CloudFront caching, origin access, and private content

Remember

  • Requests with the same CloudFront cache key get the same cached object.
  • Each value added to the cache key splits the cache into more entries and lowers the cache hit ratio.
  • A cache policy sets the cache key (headers, cookies, query strings) and the minimum, maximum, and default TTLs.
  • An origin request policy sends extra values to the origin without adding them to the cache key.
  • Values in the cache key always go to the origin.
  • The origin Cache-Control or Expires header sets the TTL inside the minimum and maximum TTL.
  • With no origin Cache-Control or Expires header, CloudFront uses the default TTL.
  • Remove cached objects with an invalidation, for example /images/*.
  • Versioned file names, for example app.v2.js, give users new files at once with no invalidation.
  • The first 1,000 CloudFront invalidation paths each month are free. After that, you pay for each path.
  • The response header X-Cache shows Hit from cloudfront or Miss from cloudfront.
  • Use origin access control (OAC) to keep an S3 origin bucket private. Origin access identity (OAI) is legacy.
  • With OAC, users cannot read objects directly from S3 and skip CloudFront rules.
  • OAC supports SSE-KMS buckets, all Regions, and PUT and DELETE requests. OAI does not.
  • The OAC bucket policy allows cloudfront.amazonaws.com with an AWS:SourceArn condition for the distribution.
  • For an SSE-KMS bucket behind OAC, the KMS key policy must also allow CloudFront.
  • An S3 website endpoint is a custom origin.
  • OAC does not work with an S3 website endpoint, because the endpoint needs public read access and does not accept signed requests.
  • Signed URLs and signed cookies give access to private content for a limited time.
  • CloudFront checks a signature with the matching public key in a trusted key group.
  • A request for private content with no valid signature gets 403.
  • Choose signed URLs for one file, or for clients that do not support cookies.
  • Choose signed cookies for many files when the URLs must not change.
  • The viewer protocol policy redirects HTTP requests to HTTPS, or rejects them with 403.
  • Field-level encryption encrypts selected form fields at the edge with a public key, for example card numbers.
  • Geographic restrictions allow or block countries for the whole distribution.
  • CloudFront Functions run JavaScript on viewer request and viewer response events only, in submillisecond time.
  • CloudFront Functions have no network access and no request body access.
  • Lambda@Edge runs Node.js and Python on viewer and origin events, for up to 30 seconds.
  • Lambda@Edge has network access and request body access.
  • Choose CloudFront Functions for header changes, redirects, cache key normalization, and simple token checks.
  • Choose Lambda@Edge when the code needs the network, the request body, more run time, or origin events.

Exam signals

  • "Low cache hit ratio, all headers in the cache key" → cache policy with only the values that change the response. Use an origin request policy for the rest.
  • "Private S3 bucket encrypted with SSE-KMS behind CloudFront" → OAC, bucket policy, and KMS key policy.
  • "Paid users stream many video files" → signed cookies. One cookie covers all the files, and the URLs stay the same.
  • "Lightweight header rewrite at high scale" → CloudFront Functions. They are cheaper and faster than Lambda@Edge for simple viewer request changes.

Explanation

Cache key and policies

  • The cache key decides if two requests are the same. Requests with the same cache key get the same cached object.
  • Each value that you add to the key (for example, a header with many values such as User-Agent) splits the cache into more entries, so fewer requests find a cached copy. Fewer values in the cache key give a higher cache hit ratio (the percentage of requests that CloudFront serves from the cache).
  • A cache policy sets the cache key (headers, cookies, query strings) and the TTLs (minimum, maximum, default).
  • An origin request policy sends extra values to the origin without adding them to the cache key.
  • Values in the cache key always go to the origin. You do not need to add them to the origin request policy too.
  • The origin Cache-Control or Expires header sets the TTL inside the minimum and maximum TTL. With no origin header, CloudFront uses the default TTL.
  • Remove cached objects with an invalidation (for example, /images/*), or use versioned file names (for example, app.v2.js). A new file name is a new cache key, so users get the new file at once with no invalidation.
  • The first 1,000 invalidation paths each month are free. After that, you pay for each path.
  • Response header X-Cache: Hit from cloudfront or Miss from cloudfront shows the result.

S3 origin access

  • Use origin access control (OAC). With OAC, CloudFront signs its requests to S3, and the bucket stays private.
  • Users cannot read objects directly from S3, so they cannot skip CloudFront rules such as signed URLs or AWS WAF.
  • Origin access identity (OAI) is legacy.
  • OAC supports SSE-KMS buckets, all Regions, and PUT and DELETE requests. OAI does not, which is why OAI is legacy.
  • The bucket policy allows cloudfront.amazonaws.com with an AWS:SourceArn condition for the distribution. For SSE-KMS, the KMS key policy must also allow CloudFront.
  • An S3 website endpoint is a custom origin. OAC does not work with it, because a website endpoint needs public read access and does not accept signed requests.

Private content and security

  • Signed URLs and signed cookies give access to private content for a limited time.
  • Your application signs a policy (expiry time, paths) with a private key. CloudFront checks the signature with the matching public key in a trusted key group. A request with no valid signature gets 403.
  • Signed URLs: choose them for one file, or for clients that do not support cookies. The signature is in the URL query string, so each file URL changes.
  • Signed cookies: choose them for many files (for example, all video segments), when URLs must not change.
  • The viewer protocol policy sets what CloudFront does with an HTTP request: redirect it to HTTPS (browsers), or reject it with 403 (APIs that must never use HTTP).
  • Field-level encryption encrypts selected form fields at the edge with a public key. Only the application that has the private key can decrypt them. Use it for data such as card numbers that other services in the request path must not read.
  • Geographic restrictions allow or block countries for the whole distribution.

Route 53, AWS WAF, and certificates

Remember

  • Route 53 simple routing answers with one resource.
  • Route 53 weighted routing splits traffic by weight, for example 90/10 for a test.
  • Route 53 latency routing sends users to the Region with the lowest latency.
  • Route 53 failover routing is active-passive. A health check on the primary record decides.
  • Route 53 geolocation routing answers by the location of the user: continent, country, or state.
  • Route 53 geoproximity routing answers by distance. A bias value moves traffic toward or away from a resource.
  • Route 53 IP-based routing answers by the source IP range (CIDR) of the user.
  • Route 53 multivalue answer routing returns up to 8 healthy records, selected at random.
  • Use multivalue answer routing to spread clients across servers and skip unhealthy ones when you have no load balancer.
  • An alias record points to an AWS resource such as CloudFront, API Gateway, a load balancer, or an S3 website.
  • An alias record works at the zone apex, for example example.com. A CNAME cannot.
  • An AWS WAF web ACL is a set of rules that AWS WAF checks for each request.
  • If no web ACL rule matches, the default action (Allow or Block) applies.
  • AWS WAF blocked requests get 403.
  • AWS WAF rule types: managed rule groups, rate-based rules, IP sets, geo match, regex, size, SQL injection, and XSS match.
  • AWS WAF protects Regional resources such as an API Gateway REST API, an Application Load Balancer, AWS AppSync, and a Cognito user pool.
  • For CloudFront, create the web ACL in us-east-1 with scope CLOUDFRONT.
  • AWS WAF does not support HTTP APIs. Put CloudFront in front and attach the web ACL to the distribution.
  • Each resource can have only one web ACL.
  • A rate-based rule counts requests for each aggregation key over a window and acts on keys over the limit.
  • A rate-based rule window is 60, 120, 300 (default), or 600 seconds.
  • A rate-based rule limit is 10 to 2,000,000,000 requests in the window.
  • A rate-based rule aggregates by source IP (default), forwarded IP header, custom keys, or all matching requests.
  • When the rate falls below the limit again, AWS WAF stops the rate-based rule action.
  • Use the forwarded IP header aggregation when a proxy sits in front of the resource.
  • CloudFront and edge-optimized API custom domains need an ACM certificate in us-east-1.
  • A certificate in another Region does not appear in the list for an edge-optimized custom domain.
  • Regional API custom domains need an ACM certificate in the same Region as the API.
  • ACM public certificates are free and renew automatically.
  • API mappings (base path mappings) connect a custom domain path to an API stage.
  • API Gateway removes the mapped base path before it calls the API.
  • You can map REST and HTTP API stages to the same custom domain.
  • After you create the API custom domain, create a Route 53 alias record that points to its API Gateway domain name.

Exam signals

  • "Block IPs that send too many requests" → WAF rate-based rule. It counts requests for each IP address and blocks those over the limit.
  • "WAF for an HTTP API" → CloudFront in front, web ACL in us-east-1. AWS WAF cannot attach to an HTTP API directly.
  • "Secondary Region serves only when the primary fails" → failover routing and a health check. Route 53 returns the secondary record only when the primary health check fails.
  • "Edge-optimized custom domain, certificate not listed" → request it in us-east-1. Edge-optimized domains use CloudFront.
  • "Several APIs under one domain, each with its own path" → API mappings on one custom domain. Each mapping sends one base path to one API stage.
