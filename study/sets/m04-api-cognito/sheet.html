REST, HTTP, and WebSocket APIs and endpoint types

Comparison: REST API and HTTP API

Key facts

  • Choose a REST API when the scenario needs API keys, usage plans, request validation, caching, AWS WAF, resource policies, or a private endpoint.
  • Choose an HTTP API for a low-cost proxy to Lambda or HTTP backends with JWT authorization.
  • A WebSocket API keeps a two-way connection open. Use it for chat, live dashboards, and server push.
  • WebSocket routes: $connect, $disconnect, $default, and custom routes. A route selection expression (for example, $request.body.action) picks the route.
  • The backend sends a message to a client with a SigV4-signed POST to @connections/{connection_id} (API Gateway Management API). GET returns the connection status. DELETE disconnects the client.
  • Edge-optimized: requests go through the nearest CloudFront point of presence. Good for clients in many countries.
  • Regional: for clients in the same Region. You can put your own CloudFront distribution in front of it.
  • Private: reachable only from a VPC through an interface VPC endpoint. A resource policy controls access.

Exam signals

  • "Partner API keys and per-customer quotas" → REST API.
  • "Lowest cost, Lambda proxy, validate JWTs" → HTTP API with a JWT authorizer.
  • "Server must push updates to connected browsers" → WebSocket API and @connections.
  • "API must not be reachable from the internet" → private REST API with an interface VPC endpoint.

Integrations, proxy formats, and timeouts

Integration types (REST API)

TypeWhat it does
AWS_PROXY (Lambda proxy)Sends the whole request to Lambda as an event. Lambda returns the full HTTP response. No mapping templates.
AWS (Lambda custom or other AWS service)You configure integration request and response, with mapping templates.
HTTP_PROXYPasses the request to an HTTP endpoint without changes.
HTTPHTTP endpoint with mapping templates.
MOCKAPI Gateway returns a response without a backend.

Lambda proxy response format

  • The function must return statusCode, and optionally headers, multiValueHeaders, body (a string), and isBase64Encoded.
  • If the output has a different format, API Gateway returns 502 Bad Gateway.
  • REST API proxy events use payload format 1.0 (httpMethod, path, queryStringParameters).
  • HTTP API Lambda integrations support payload format 1.0 and 2.0. Format 2.0 uses requestContext.http.method, rawPath, and rawQueryString.

Numbers to memorize

ItemREST APIHTTP API
Integration timeout50 ms to 29 seconds. You can request an increase for Regional and private APIs, not for edge-optimized APIs.30 seconds maximum
Payload size10 MB10 MB

Key facts

  • A timeout returns 504 to the client, even if the Lambda function continues to run.
  • For long work, return at once and process in the background. In a Lambda custom integration, set the integration request header X-Amz-Invocation-Type to 'Event'. Lambda then runs asynchronously.
  • A mock integration returns a response from a mapping template with no backend. Use it to test clients or prototype an API before the backend exists. The CORS OPTIONS method also uses it.
  • Use {proxy+} and the ANY method to send all paths and methods to one integration.
  • API Gateway needs permission to invoke the function (Lambda resource-based policy or an IAM role).

Private integrations (VPC links)

  • A private integration lets the API reach resources in a VPC that are not public.
  • REST API: a VPC link V2 to an Application Load Balancer or a Network Load Balancer. VPC links V1 are legacy and support only a Network Load Balancer (older study material says "REST API → NLB"). REST APIs do not support AWS Cloud Map.
  • HTTP API: a VPC link to an Application Load Balancer, a Network Load Balancer, or an AWS Cloud Map service.

Exam signals

  • "502 Bad Gateway from a Lambda proxy API" → the function returns the wrong response format.
  • "504 after about 29 seconds" → integration timeout. Make the work asynchronous.
  • "Function moved from REST API to HTTP API and event.httpMethod is undefined" → payload format 2.0. Set format 1.0 or change the code.
  • "Front-end team must test against the API before the backend exists" → mock integration.

Stages, deployments, stage variables, and canary releases

Key facts

  • A deployment is a snapshot of the REST API configuration. A stage points to one deployment and has its own URL: https://{api-id}.execute-api.{region}.amazonaws.com/{stage}.
  • Changes to a REST API do not reach clients until you deploy the API to a stage again.
  • Each stage has its own settings: throttling, caching, logging, tracing, and stage variables.
  • Stage variables are key-value pairs for a stage. Use them in integration URIs, Lambda function names or aliases, and mapping templates.
  • Syntax: ${stageVariables.name}. Example Lambda ARN: ...:function:my-fn:${stageVariables.alias}.
  • When a stage variable picks the Lambda function or alias, add a Lambda permission for API Gateway on each function or alias yourself (for example, with aws lambda add-permission).
  • Do not put secrets in stage variables.
  • The proxy event includes the values in stageVariables.

Canary release (REST API)

  • A canary sends a percentage (0.0 to 100.0) of stage traffic to a new deployment. The rest goes to the current deployment.
  • The canary can override stage variables.
  • Canary requests have separate execution logs and access logs (log group name ends with /Canary).
  • After tests pass, promote the canary. It then becomes the stage deployment.

Numbers to memorize

ItemValue
Stage variables for each stage100
Stages for each API10 (soft limit)

Exam signals

  • "One API, dev and prod stages call different Lambda aliases" → stage variable in the integration ARN, and a permission for each alias.
  • "Send 10% of API traffic to the new API configuration" → canary release on the stage.
  • "Change in the console has no effect" → deploy the API to the stage.

Mapping templates, request validation, and status codes

Request flow (REST API)

Client → method request → integration request → backend → integration response → method response → client.

  • Method request: authorization, required parameters, request model, request validator.
  • Integration request: backend target and request mapping template.
  • Integration response: response mapping template and status code selection.
  • Method response: status codes and headers that the API can return.

Request validation

  • You need a model (JSON Schema draft 4) and a request validator on the method.
  • Validator options: validate body, validate query string parameters and headers, or both.
  • API Gateway rejects an invalid request with 400 before it calls the backend.
  • Change the error message with a gateway response (for example, BAD_REQUEST_BODY). $context.error.validationErrorString has the details.

Mapping templates (VTL)

  • Mapping templates work with non-proxy integrations (AWS, HTTP). Proxy integrations do not use them.
  • $input.body: raw body. $input.json('$.x'): JSON string. $input.path('$.x'): object.
  • $input.params('x'): searches path, then query string, then header.
  • $context.requestId, $context.identity.sourceIp, $context.authorizer.claims.sub, $stageVariables.name.
  • $util.escapeJavaScript(), $util.parseJson(), $util.base64Encode(), $util.urlEncode().
  • $context.responseOverride.status overrides the response status code from a template.

Status codes from a non-proxy Lambda integration

  • By default, the integration response returns 200, even when the function fails.
  • Add an integration response with a selection pattern. For Lambda, the regular expression matches the errorMessage of the function error.
  • The status code must also exist as a method response.

Exam signals

  • "Reject requests without required fields before Lambda runs" → model and request validator.
  • "Legacy backend expects other field names, no backend change" → non-proxy integration with a mapping template.
  • "Return 422 when Lambda throws ORDER_TOO_LARGE" → integration response with selection pattern .*ORDER_TOO_LARGE.* and a 422 method response.

References: Request validation, Mapping template variables, Gateway responses. Lab: Lab 4.3 Validation and transformation.

Throttling, usage plans, and API keys

Throttling

  • API Gateway uses a token bucket. Rate is tokens added each second. Burst is the bucket size.
  • Over the limit, clients get 429 Too Many Requests. Clients must retry with exponential backoff and jitter.
  • Order that API Gateway applies limits: usage plan per-client or per-method limits, then stage or method limits, then the account limit for the Region, then AWS Regional limits.
  • Throttles and quotas are best effort. They are targets, not guaranteed ceilings.

Numbers to memorize

ItemValue
Account throttle for each Region (all APIs)10,000 requests per second, burst 5,000. You can request a higher rate. Some newer Regions: 2,500 and 1,250.
Usage plan quota periodDAY, WEEK, or MONTH

Usage plans and API keys (REST API only)

  • A usage plan sets throttle (rate and burst) and quota for API keys on one or more API stages.
  • Clients send the key in the x-api-key header. Set apiKeyRequired on each method.
  • A missing or wrong key returns 403 Forbidden.
  • A key can be in more than one usage plan, but only in one usage plan for each stage.
  • A Lambda authorizer can return the key in usageIdentifierKey (API key source AUTHORIZER).
  • API keys are not authentication. AWS says: do not use API keys to control access. Use IAM, Cognito, or a Lambda authorizer.
  • Do not rely on usage plans to control cost. Use AWS Budgets, and AWS WAF to manage requests.

Exam signals

  • "Gold and Silver customers get different request rates and monthly quotas" → usage plans and an API key for each customer.
  • "Secure the API that uses API keys" → add an authorizer. Keep keys for metering.
  • "Clients get 429 during spikes" → retry with exponential backoff, or raise stage or account limits.

References: Throttling, Account quotas, Usage plans and API keys. Lab: Lab 4.4 Throttling and usage plans.

API caching

Numbers to memorize

ItemValue
Default TTL300 seconds
TTL range0 to 3,600 seconds. TTL 0 turns caching off.
Largest cached response1,048,576 bytes (1 MB)
CostCharged by the hour for the cache size. Not in the AWS Free Tier.

Key facts

  • REST API only. You turn on the cache for a stage. You can override settings for each method.
  • By default, only GET methods are cached.
  • Add query strings, headers, or path parameters as cache keys. Responses for different key values are cached separately.
  • You can encrypt cache data. Do this when responses contain sensitive data.
  • Flush the whole stage cache in the console or with flush-stage-cache.
  • A client can invalidate one entry with the header Cache-Control: max-age=0.
  • Control invalidation with execute-api:InvalidateCache and "require authorization". Without this control, any client can invalidate the cache.
  • Unauthorized invalidation options: FAIL_WITH_403, SUCCEED_WITH_RESPONSE_HEADER, SUCCEED_WITHOUT_RESPONSE_HEADER.
  • Monitor with CacheHitCount and CacheMissCount.

Exam signals

  • "Cached responses for one category show for another category" → add the query string as a cache key.
  • "Anyone can bypass the cache with Cache-Control" → require authorization for invalidation.
  • "Reduce backend calls for repeated GET requests" → stage cache with a TTL.

Authorizers, IAM authorization, and resource policies

Comparison

OptionAPI typeWhat it checks
IAM (AWS_IAM)REST, HTTP, WebSocketSigV4 signature. Caller needs execute-api:Invoke.
Cognito user pool authorizer (COGNITO_USER_POOLS)RESTA user pool ID token or access token
JWT authorizerHTTPAny OIDC or OAuth 2.0 JWT, including Cognito tokens
Lambda authorizer TOKENRESTOne token in one header
Lambda authorizer REQUESTREST, HTTP, WebSocketHeaders, query strings, stage variables, context variables
Resource policyRESTAllows or denies by principal, account, IP range, or VPC endpoint

Cognito user pool authorizer

  • The client sends the token in the Authorization header (the token source).
  • No OAuth scopes on the method: API Gateway treats the token as an ID token.
  • Scopes on the method: API Gateway treats the token as an access token and checks the scopes. No matching scope gives 401.
  • The backend gets claims in $context.authorizer.claims (proxy: requestContext.authorizer.claims).

Lambda authorizer

  • Returns principalId, an IAM policy (policyDocument), and an optional context map. HTTP APIs can also use a simple response: {"isAuthorized": true}.
  • Deny policy: 403. The function returns "Unauthorized": 401.
  • REQUEST authorizer with caching on: if an identity source is missing, null, or empty, API Gateway returns 401 and does not call the function.
  • AWS recommends REQUEST authorizers: several identity sources and finer cache keys.
  • Result caching: default TTL 300 seconds, maximum 3,600. TTL 0 turns caching off.
  • With caching, the cached policy applies to other methods for the same identity. Return a policy that covers every method the caller can use, or turn off caching.

JWT authorizer (HTTP API)

  • Checks the signature with keys from the issuer jwks_uri, and checks iss, aud or client_id, exp, nbf, iat, and route scopes.
  • Cognito issuer URL: https://cognito-idp.{region}.amazonaws.com/{userPoolId}.

IAM authorization and resource policies

  • Same account: an IAM identity policy that allows execute-api:Invoke is enough.
  • Cross-account: the caller needs an identity policy, and the API needs a resource policy that allows the caller.
  • A private API needs a resource policy that allows access from the VPC endpoint or VPC.
  • Callers from an identity pool can sign requests with their temporary credentials.

Exam signals

  • "REST API, users sign in with Cognito, least code" → Cognito user pool authorizer.
  • "HTTP API, tokens from a third-party OIDC provider" → JWT authorizer.
  • "Authorize on a header and a query string together" → REQUEST Lambda authorizer.
  • "User gets 403 on a second method after the first call works" → cached policy covers only the first method.
  • "Another AWS account must call the API" → IAM authorization and a resource policy.

References: Cognito user pool authorizer, Lambda authorizers, CreateAuthorizer (TTL), JWT authorizers, HTTP API Lambda authorizers. Lab: Lab 4.5 Cognito user pool.

CORS

Key facts

  • A browser blocks a cross-origin call unless the response has the correct CORS headers. A different domain, subdomain, port, or protocol is cross-origin.
  • A non-simple request (for example, with an Authorization header or JSON content type) causes a preflight OPTIONS request.
  • Headers: Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headers.
  • REST API, non-proxy integration: "Enable CORS" adds an OPTIONS mock method and adds headers to the integration responses.
  • REST API, Lambda proxy or HTTP proxy: the backend must return the CORS headers in each response. API Gateway cannot add them.
  • For CORS headers on API Gateway errors (4XX, 5XX), add them to the gateway responses.
  • HTTP API: configure CORS on the API. API Gateway answers preflight requests itself and ignores CORS headers from the backend.

Exam signals

  • "CORS enabled in the console, but the browser still blocks a Lambda proxy response" → return Access-Control-Allow-Origin from the function.
  • "HTTP API, browser app on another domain, least effort" → CORS configuration on the HTTP API.

References: CORS for REST APIs, CORS for HTTP APIs. Lab: Lab 4.1 REST vs HTTP API.

Common status codes

403Explicit deny, missing API key, WAF block, or (REST API) a path or method that does not exist: "Missing Authentication Token"
429Throttled, or usage plan quota exceeded

CloudWatch metrics

  • Count, 4XXError, 5XXError, CacheHitCount, CacheMissCount.
  • IntegrationLatency: time the backend takes.
  • Latency: total time from request to response. It includes integration latency and API Gateway overhead, for example a Lambda authorizer.
  • Metrics for each method need detailed CloudWatch metrics on the stage (extra cost).

Logs and tracing

  • Execution logs (REST API): how API Gateway processed the request, with errors and traces. Levels: ERROR or INFO. Optional full request and response data.
  • Access logs: one line for each request, in a format you choose with $context variables. REST and HTTP APIs.
  • To write logs, set an IAM role with AmazonAPIGatewayPushToCloudWatchLogs as cloudWatchRoleArn in the API Gateway account settings. Do this in each Region.
  • X-Ray tracing: turn it on for a REST API stage. HTTP APIs do not support X-Ray.

Exam signals

  • "Latency is high, IntegrationLatency is low" → delay is in API Gateway, for example an uncached Lambda authorizer.
  • "No execution logs appear" → set the CloudWatch role ARN in account settings and turn on logging for the stage.
  • "Find which service in the request path is slow" → X-Ray on the REST API stage and on Lambda.

  • Verify a JWT: check the signature with the public keys at https://cognito-idp.{region}.amazonaws.com/{userPoolId}/.well-known/jwks.json. Then check exp, iss, token_use, and aud (ID token) or client_id (access token).
  • GlobalSignOut and AdminUserGlobalSignOut revoke all refresh tokens of a user. RevokeToken revokes one refresh token.
  • Refresh token rotation (optional) issues a new refresh token at each refresh. It does not extend the original validity.

Sign-in and features

  • App client with no secret: browser and mobile apps. With a secret: server-side apps.
  • Auth flows: ALLOW_USER_SRP_AUTH, ALLOW_USER_PASSWORD_AUTH, ALLOW_ADMIN_USER_PASSWORD_AUTH, ALLOW_CUSTOM_AUTH, ALLOW_REFRESH_TOKEN_AUTH, ALLOW_USER_AUTH.
  • Managed login (formerly hosted UI) gives OAuth 2.0 sign-in pages and federation with SAML, OIDC, and social providers.
  • MFA: SMS, email, or TOTP (authenticator app).
  • Groups put a cognito:groups claim in tokens. A group can have an IAM role for identity pools.
  • Resource servers define custom scopes for access tokens.

Cognito identity pools and temporary AWS credentials

Key facts

  • An identity pool exchanges proof of sign-in for temporary AWS credentials. Accepted proof: user pool ID token, OIDC ID token, SAML assertion, social provider token, or a developer-authenticated identity.
  • Each identity pool has an authenticated role and an optional unauthenticated (guest) role.
  • Turn on guest access only if you need it. Give the guest role fewer permissions.
  • The role trust policy must trust cognito-identity.amazonaws.com for sts:AssumeRoleWithWebIdentity, with a cognito-identity.amazonaws.com:aud condition (the identity pool ID). Use amr to separate authenticated and guest users.

Authentication flows

FlowAPI callsNotes
Enhanced (recommended)GetId, then GetCredentialsForIdentityIdentity pool picks the role. Credentials valid for 1 hour.
Basic (classic)GetId, GetOpenIdToken, then STS AssumeRoleWithWebIdentityThe app picks the role. Not supported with role mappings.

Role selection

  • Default authenticated role for all users.
  • Choose role from token: uses cognito:preferred_role or cognito:roles from user pool groups. The group with the lowest precedence value wins.
  • Rules: map a token claim to a role. Rules run in order. The first match wins. Maximum 25 rules for each provider.
  • Do not map roles from claims that users can change.

Per-user access with policy variables

  • ${cognito-identity.amazonaws.com:sub} is the identity ID of the caller (not the user pool sub).
  • Example resource: arn:aws:s3:::bucket/${cognito-identity.amazonaws.com:sub}/*.
  • DynamoDB: condition dynamodb:LeadingKeys equal to the identity ID.

Exam signals

  • "Mobile app uploads directly to S3, each user only in their own folder" → identity pool and a policy variable.
  • "Guest users read the catalog without sign-in" → unauthenticated role with read-only access.
  • "Group members get a different IAM role" → group IAM role and "choose role from token".
  • "User pool or identity pool" → JWT for your API: user pool. AWS credentials: identity pool.

References: Identity pool authentication flow, IAM roles for identity pools, Role-based access control. Lab: Lab 4.6 Cognito identity pool.

CloudFront caching, origin access, and private content

Cache key and policies

  • The cache key decides if two requests are the same. Fewer values in the cache key give a higher cache hit ratio.
  • A cache policy sets the cache key (headers, cookies, query strings) and the TTLs (minimum, maximum, default).
  • An origin request policy sends extra values to the origin without adding them to the cache key.
  • Values in the cache key always go to the origin.
  • The origin Cache-Control or Expires header sets the TTL inside the minimum and maximum TTL. With no origin header, CloudFront uses the default TTL.
  • Remove cached objects with an invalidation (for example, /images/*), or use versioned file names.
  • Response header X-Cache: Hit from cloudfront or Miss from cloudfront shows the result.

S3 origin access

  • Use origin access control (OAC). Origin access identity (OAI) is legacy.
  • OAC supports SSE-KMS, all Regions, and PUT and DELETE requests.
  • The bucket policy allows cloudfront.amazonaws.com with an AWS:SourceArn condition for the distribution. For SSE-KMS, the KMS key policy must also allow CloudFront.
  • An S3 website endpoint is a custom origin. OAC does not work with it.

Private content and security

  • Signed URLs: one file, or clients that do not support cookies.
  • Signed cookies: many files (for example, all video segments), and URLs do not change.
  • Viewer protocol policy: redirect HTTP to HTTPS, or HTTPS only.
  • Field-level encryption encrypts selected form fields at the edge with a public key.
  • Geographic restrictions allow or block countries for the whole distribution.

Edge functions

ItemCloudFront FunctionsLambda@Edge

Exam signals

  • "Low cache hit ratio, all headers in the cache key" → cache policy with only the values that change the response; origin request policy for the rest.
  • "Private S3 bucket encrypted with SSE-KMS behind CloudFront" → OAC, bucket policy, and KMS key policy.
  • "Paid users stream many video files" → signed cookies.
  • "Lightweight header rewrite at high scale" → CloudFront Functions.

  • An alias record points to an AWS resource (CloudFront, API Gateway, load balancer, S3 website). It works at the zone apex. A CNAME does not.

AWS WAF

  • A web ACL has rules and a default action (Allow or Block). Blocked requests get 403.
  • Rule types: AWS managed rule groups, rate-based rules, IP sets, geo match, regex, size, SQL injection, and XSS match.
  • Regional resources: API Gateway REST API, Application Load Balancer, AWS AppSync, Cognito user pool, App Runner, Verified Access, and others.
  • CloudFront: create the web ACL in us-east-1 (scope CLOUDFRONT).
  • HTTP APIs are not supported. Put CloudFront in front and attach the web ACL to the distribution.
  • Each resource can have only one web ACL.

Numbers to memorize (rate-based rule)

ItemValue

Certificates and custom domains

  • CloudFront and edge-optimized API custom domains: the ACM certificate must be in us-east-1.
  • Regional API custom domains: the ACM certificate must be in the same Region as the API.
  • ACM public certificates are free and renew automatically.
  • API mappings (base path mappings) connect a custom domain to API stages. Example: api.example.com/orders → orders API, prod stage, and api.example.com/users → users API, prod stage. API Gateway removes the mapped base path before it calls the API. You can map REST and HTTP API stages to the same domain.
  • After you create the custom domain, create a Route 53 alias record that points to the API Gateway domain name for the custom domain.

Exam signals

  • "Block IPs that send too many requests" → WAF rate-based rule.
  • "WAF for an HTTP API" → CloudFront in front, web ACL in us-east-1.
  • "Secondary Region serves only when the primary fails" → failover routing and a health check.
  • "Edge-optimized custom domain, certificate not listed" → request it in us-east-1.
  • "Several APIs under one domain, each with its own path" → API mappings on one custom domain.
