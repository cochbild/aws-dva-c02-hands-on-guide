REST, HTTP, and WebSocket APIs and endpoint types

Key facts

  • Choose a REST API when the scenario needs API keys, usage plans, request validation, caching, AWS WAF, resource policies, or a private endpoint.
  • Choose an HTTP API for a low-cost proxy to Lambda or HTTP backends with JWT authorization.
  • A WebSocket API keeps a two-way connection open between the client and API Gateway. The backend can then send a message to the client at any time, without a client request (server push). Use it for chat, live dashboards, and notifications. With REST or HTTP APIs, the client must poll (ask again and again) to get new data.
  • WebSocket routes: API Gateway calls the $connect route when a client connects and the $disconnect route when the connection closes. For each message, API Gateway reads the value that the route selection expression names (for example, $request.body.action, the action field of the JSON message). It sends the message to the custom route with that key, for example sendmessage. Messages that match no route go to $default.
  • Each connection has a connection ID. The backend gets it from requestContext.connectionId in the $connect event and usually stores it, for example in DynamoDB. To send a message, the backend makes a POST to @connections/{connection_id} (API Gateway Management API). The request must have a SigV4 signature (Signature Version 4: a signature made with AWS credentials). GET returns the connection status. DELETE disconnects the client. A POST to a closed connection fails with GoneException, so remove that stored ID.
  • Edge-optimized: requests go to the nearest CloudFront edge location (a CloudFront data center near the user), then over the AWS network to the API Region. Choose it for clients in many countries. API Gateway manages this CloudFront distribution, and you cannot change its settings.
  • Regional: for clients in the same Region. You can put your own CloudFront distribution in front of it when you need control of caching, AWS WAF, or edge functions.
  • Private: reachable only from a VPC through an interface VPC endpoint. A resource policy controls access.

Numbers to memorize (WebSocket API)

API Gateway closes a connection after 2 hours, or after 10 minutes with no messages. The client must detect the close and connect again. To keep an idle connection open, the client can send a small message (a heartbeat) more often than every 10 minutes.

Exam signals

  • "Partner API keys and per-customer quotas" → REST API, because only REST APIs have API keys and usage plans.
  • "Lowest cost, Lambda proxy, validate JWTs" → HTTP API with a JWT authorizer, because HTTP APIs cost less and validate JWTs with no code.
  • "Server must push updates to connected browsers" → WebSocket API and @connections, because only a WebSocket API keeps a connection that the server can send on.
  • "API must not be reachable from the internet" → private REST API with an interface VPC endpoint, because edge-optimized and Regional endpoints are always public.

Integrations, proxy formats, and timeouts

Integration types (REST API)

TypeWhat it does
AWS_PROXY (Lambda proxy)Sends the whole request to Lambda as an event. Lambda returns the full HTTP response. No mapping templates.
AWS (Lambda custom or other AWS service)You configure integration request and response, with mapping templates.
HTTP_PROXYPasses the request to an HTTP endpoint without changes.
HTTPHTTP endpoint with mapping templates.
MOCKAPI Gateway returns a response without a backend.

Choose a proxy type (AWS_PROXY, HTTP_PROXY) when the backend can read the request as it is and build its own response. This is the least configuration. Choose a non-proxy type (AWS, HTTP) when API Gateway must change the request or response, for example to rename fields, to set status codes from errors, or to call an AWS service such as Amazon SQS directly without a Lambda function.

Lambda proxy response format

  • The function must return statusCode, and optionally headers, multiValueHeaders, body (a string), and isBase64Encoded. The body must be a string, so convert a JSON object first, for example with JSON.stringify().
  • If the output has a different format, API Gateway returns 502 Bad Gateway.
  • REST API proxy events use payload format 1.0 (httpMethod, path, queryStringParameters).
  • HTTP API Lambda integrations support payload format 1.0 and 2.0. Format 2.0 uses requestContext.http.method, rawPath, and rawQueryString. Code written for format 1.0 then reads event.httpMethod as undefined.

Key facts

  • A timeout returns 504 to the client, even if the Lambda function continues to run.
  • For long work, return at once and process in the background. In a Lambda custom integration, set the integration request header X-Amz-Invocation-Type to 'Event' (the quotes mean a fixed value). Lambda then queues the event and runs the function asynchronously. API Gateway responds to the client at once, without the function result. The client must get the result later, for example from a status endpoint.
  • A mock integration returns a response from a mapping template with no backend. Use it to test clients or prototype an API before the backend exists. The CORS OPTIONS method also uses it.
  • {proxy+} is a greedy path variable: one resource that matches every path below it, for example /orders/7/items. With the ANY method, it sends all paths and methods to one integration. Use it when one Lambda function does its own routing.
  • API Gateway needs permission to invoke the function (Lambda resource-based policy or an IAM role). Without it, the client gets 500 Internal Server Error, and the execution log shows "Invalid permissions on Lambda function". The console adds the permission when you choose the function. Infrastructure as code and the CLI do not.

Private integrations (VPC links)

  • A private integration lets the API reach resources in a VPC that are not public.
  • REST API: a VPC link V2 to an Application Load Balancer or a Network Load Balancer. VPC links V1 are legacy and support only a Network Load Balancer (older study material says "REST API → NLB"). REST APIs do not support AWS Cloud Map.
  • HTTP API: a VPC link to an Application Load Balancer, a Network Load Balancer, or an AWS Cloud Map service.

Exam signals

  • "502 Bad Gateway from a Lambda proxy API" → the function returns the wrong response format, for example an object with no statusCode or a body that is not a string.
  • "504 after about 29 seconds" → integration timeout. Make the work asynchronous, because a longer function timeout does not change the 29-second API Gateway limit.
  • "Function moved from REST API to HTTP API and event.httpMethod is undefined" → payload format 2.0. Set format 1.0 or change the code, because format 2.0 puts the method in requestContext.http.method.
  • "Front-end team must test against the API before the backend exists" → mock integration.

Stages, deployments, stage variables, and canary releases

Key facts

  • A deployment is a snapshot of the REST API configuration. A stage points to one deployment and has its own URL: https://{api-id}.execute-api.{region}.amazonaws.com/{stage}.
  • Changes to a REST API do not reach clients until you deploy the API to a stage again.
  • Each stage has its own settings: throttling, caching, logging, tracing, and stage variables.
  • Stage variables are key-value pairs for a stage. They work like environment variables. Use them in integration URIs, Lambda function names or aliases, and mapping templates. One API definition can then call a different backend from each stage, for example the dev alias from the dev stage and the prod alias from the prod stage.
  • Syntax: ${stageVariables.name}. Example Lambda ARN: ...:function:my-fn:${stageVariables.alias}.
  • When a stage variable picks the Lambda function or alias, add a Lambda permission for API Gateway on each function or alias yourself (for example, with aws lambda add-permission). API Gateway knows the real ARN only at run time, so it cannot add the permission for you. Without it, calls fail with 500.
  • Do not put secrets in stage variables. AWS says they are not for sensitive data such as credentials. Anyone who can read the stage configuration can read them. To pass sensitive data to an integration, AWS recommends the output of a Lambda authorizer.
  • The proxy event includes the values in stageVariables, so the function can read them.

Canary release (REST API)

  • A canary release tests a new API deployment on a small part of real traffic before all users get it. If errors increase, only that part of the traffic is affected.
  • A canary sends a percentage (0.0 to 100.0) of stage traffic to a new deployment. The rest goes to the current deployment.
  • The canary can override stage variables. Use this to send canary traffic to a new backend, for example a new Lambda alias.
  • Canary requests have separate execution logs and access logs (log group name ends with /Canary).
  • After tests pass, promote the canary. It then becomes the stage deployment.

Numbers to memorize

ItemValue
Stage variables for each stage100
Stages for each API10 (soft limit)

Exam signals

  • "One API, dev and prod stages call different Lambda aliases" → stage variable in the integration ARN, and a permission for each alias.
  • "Send 10% of API traffic to the new API configuration" → canary release on the stage.
  • "Change in the console has no effect" → deploy the API to the stage, because a REST API stage serves only the deployment snapshot that it points to.

Mapping templates, request validation, and status codes

Request flow (REST API)

A request passes through these steps in this order: method request, integration request, the backend, integration response, and method response. The method request and method response are the public interface that the client sees. The integration request and integration response are what the backend sees. In a non-proxy integration, API Gateway can change the data between these two sides.

  • Method request: authorization, required parameters, request model, request validator.
  • Integration request: backend target and request mapping template.
  • Integration response: response mapping template and status code selection.
  • Method response: status codes and headers that the API can return.

Request validation

  • You need a model (JSON Schema draft 4) and a request validator on the method.
  • Validator options: validate body, validate query string parameters and headers, or both.
  • API Gateway rejects an invalid request with 400 before it calls the backend. The backend does not run for bad input, so you do not pay for those invocations or write that validation code.
  • Change the error message with a gateway response (for example, BAD_REQUEST_BODY). $context.error.validationErrorString has the details.

Mapping templates (VTL)

  • A mapping template is a script in VTL (Apache Velocity Template Language) that builds a new request or response body from the original. Use it when the backend expects a different body shape than the client sends. Mapping templates work with non-proxy integrations (AWS, HTTP). Proxy integrations do not use them.
  • $input.body returns the raw body as a string. $input.json('$.x') returns the value at JSON path $.x as a JSON string, ready to put into a JSON template. $input.path('$.x') returns the value as an object, so the template can read its fields or loop over it.
  • $input.params('x') returns the request parameter x. It looks in the path first, then the query string, then the headers.
  • Useful variables: $context.requestId (the unique ID of the request), $context.identity.sourceIp (the client IP address), $context.authorizer.claims.sub (the Cognito user ID from the token), and $stageVariables.name (a stage variable).
  • Helper functions: $util.escapeJavaScript() escapes quotes and other characters so that a string is safe inside JSON. $util.parseJson() turns a JSON string into an object. $util.base64Encode() and $util.urlEncode() encode values.
  • $context.responseOverride.status sets the response status code from a template. Use it, for example, to return 201 or 404 based on the backend data.

Status codes from a non-proxy Lambda integration

  • By default, the integration response returns 200, even when the function fails. The default integration response has no selection pattern, so it matches every result, and the client gets the error object in a 200 body.
  • Add an integration response with a selection pattern. For Lambda, the regular expression matches the errorMessage of the function error. When it matches, API Gateway returns the status code of that integration response.
  • The status code must also exist as a method response, because the method response lists every status code that the API can return to clients.

Exam signals

  • "Reject requests without required fields before Lambda runs" → model and request validator, because API Gateway checks the request against the model before it calls the backend.
  • "Legacy backend expects other field names, no backend change" → non-proxy integration with a mapping template, because the template rebuilds the body in API Gateway with no new compute.
  • "Return 422 when Lambda throws ORDER_TOO_LARGE" → integration response with selection pattern .*ORDER_TOO_LARGE.* and a 422 method response.

Throttling, usage plans, and API keys

Throttling

  • API Gateway uses a token bucket. Each request uses one token. Rate is the number of tokens added each second, so it is the steady request rate. Burst is the bucket size, so it is the number of requests that can arrive at the same moment. Example: rate 100 and burst 200 accept a short spike of 200 requests, then about 100 each second.
  • Over the limit, clients get 429 Too Many Requests. Clients must retry with exponential backoff (a longer wait after each failure) and jitter (a random part of the wait). Jitter stops all clients from retrying at the same moment.
  • Order that API Gateway applies limits: usage plan per-client or per-method limits, then stage or method limits, then the account limit for the Region, then AWS Regional limits. A request must pass every level, so the lowest limit that applies controls the request.
  • The account limit is shared by all APIs in the account in that Region. One busy API can use the limit and cause 429 errors for the other APIs.
  • Throttles and quotas are best effort. They are targets, not guaranteed ceilings. Some requests can pass after a client reaches its limit, so do not use them as a security or cost control.

Usage plans and API keys (REST API only)

  • A usage plan sets throttle (rate and burst) and quota for API keys on one or more API stages.
  • Clients send the key in the x-api-key header. Set apiKeyRequired on each method. If a method does not require a key, API Gateway does not check the key, and the usage plan limits do not apply to that method.
  • A missing or wrong key returns 403 Forbidden.
  • A key can be in more than one usage plan, but only in one usage plan for each stage. API Gateway must know which one set of limits to apply to the key on that stage.
  • Clients do not always send the key themselves. With API key source AUTHORIZER, a Lambda authorizer finds the key for the caller (for example, from the tenant in the token) and returns it in usageIdentifierKey. API Gateway then applies the usage plan of that key.
  • API keys are not authentication. AWS says: do not use API keys to control access. A key is a fixed string in a header. Anyone who copies it can use it, and it does not prove who the caller is. Use IAM, Cognito, or a Lambda authorizer.
  • Do not rely on usage plans to control cost. Use AWS Budgets, and AWS WAF to manage requests.

Exam signals

  • "Gold and Silver customers get different request rates and monthly quotas" → usage plans and an API key for each customer, because the key tells API Gateway which plan limits to apply.
  • "Secure the API that uses API keys" → add an authorizer, because a key does not prove identity. Keep keys for metering (counting requests for each customer).
  • "Clients get 429 during spikes" → retry with exponential backoff, or raise stage or account limits, because 429 means a throttle limit, not a server fault.

API caching

Numbers to memorize

ItemValue
Default TTL300 seconds
TTL range0 to 3,600 seconds. TTL 0 turns caching off.
Largest cached response1,048,576 bytes (1 MB)
CostCharged by the hour for the cache size. Not in the AWS Free Tier.

Key facts

  • REST API only. You turn on the cache for a stage. You can override settings for each method.
  • By default, only GET methods are cached.
  • Add query strings, headers, or path parameters as cache keys. Responses for different key values are cached separately. If a parameter changes the response but is not a cache key, requests with different values share one entry. Users can then get a response that was made for another value.
  • You can encrypt cache data. Do this when responses contain sensitive data.
  • Flush the whole stage cache in the console or with flush-stage-cache. After a flush, all requests go to the backend until the cache fills again.
  • A client can invalidate one entry with the header Cache-Control: max-age=0. API Gateway then gets a new response from the backend and replaces the cached entry.
  • To control who can invalidate, turn on "Require authorization" and allow execute-api:InvalidateCache only to the callers who need it. Without this control, any client can send the header, and many requests go to the backend. This increases latency and backend load.
  • Choose what happens to an unauthorized invalidation request. FAIL_WITH_403: the request fails with 403. SUCCEED_WITH_RESPONSE_HEADER: API Gateway ignores the header, processes the request, and adds a warning header to the response. SUCCEED_WITHOUT_RESPONSE_HEADER: API Gateway ignores the header and adds no warning.
  • Monitor with CacheHitCount and CacheMissCount. Many misses can mean that the cache keys are too specific, the TTL is too short, or clients invalidate entries.

Exam signals

  • "Cached responses for one category show for another category" → add the query string as a cache key, because without it all categories share one cache entry.
  • "Anyone can bypass the cache with Cache-Control" → require authorization for invalidation, because then only callers with execute-api:InvalidateCache can replace entries.
  • "Reduce backend calls for repeated GET requests" → stage cache with a TTL.

Authorizers, IAM authorization, and resource policies

Comparison

OptionAPI typeWhat it checks
IAM (AWS_IAM)REST, HTTP, WebSocketSigV4 signature. Caller needs execute-api:Invoke.
Cognito user pool authorizer (COGNITO_USER_POOLS)RESTA user pool ID token or access token
JWT authorizerHTTPAny OIDC or OAuth 2.0 JWT, including Cognito tokens

Lambda authorizer REQUESTREST, HTTP, WebSocketHeaders, query strings, stage variables, context variables
Resource policyRESTAllows or denies by principal, account, IP range, or VPC endpoint

Choose IAM when the callers are AWS identities (roles, users, or identity pool users) that sign requests. Choose a Cognito or JWT authorizer when users sign in and send a token, and you want no authorizer code. Choose a Lambda authorizer when the token comes from a provider that the built-in authorizers cannot check, or the rule needs custom logic. Add a resource policy to allow or block other accounts, IP ranges, or VPC endpoints.

Cognito user pool authorizer

  • The client sends the token in the Authorization header (the token source).
  • An ID token describes the user (name, email, groups). An access token lists the OAuth scopes: the permissions that the client may use, for example orders/read.
  • No OAuth scopes on the method: API Gateway treats the token as an ID token.
  • Scopes on the method: API Gateway treats the token as an access token and checks the scopes. No matching scope gives 401.
  • The backend gets claims in $context.authorizer.claims (proxy: requestContext.authorizer.claims).

Lambda authorizer

  • Returns principalId, an IAM policy (policyDocument), and an optional context map. HTTP APIs can also use a simple response: {"isAuthorized": true}.
  • What the client gets: if the returned policy denies the method, 403 Forbidden. If the function fails with the exact error message "Unauthorized", 401 Unauthorized. If the function fails with any other error, 500.
  • REQUEST authorizer with caching on: if an identity source is missing, null, or empty, API Gateway returns 401 and does not call the function. API Gateway builds the cache key from the identity sources, so it cannot continue without them.
  • AWS recommends REQUEST authorizers over TOKEN authorizers. A REQUEST authorizer can use several identity sources (for example, a header and a query string), and all of them form the cache key. A TOKEN authorizer gets only one header.
  • Result caching: API Gateway stores the returned policy for the same identity and does not call the function again until the TTL ends. Default TTL 300 seconds, maximum 3,600. TTL 0 turns caching off.
  • With caching, the cached policy applies to other methods for the same identity. Return a policy that covers every method the caller can use, or turn off caching.

JWT authorizer (HTTP API)

  • Checks the signature with the public keys that the issuer publishes at its jwks_uri (JSON Web Key Set URL). Then checks the claims: iss (issuer), aud or client_id (the intended audience or app), exp (expiry time), nbf (not-before time), iat (issue time), and the route scopes.
  • Cognito issuer URL: https://cognito-idp.{region}.amazonaws.com/{userPoolId}.

IAM authorization and resource policies

  • With AWS_IAM, the caller signs each request with SigV4 (a signature made from its AWS access keys). API Gateway checks the signature and the IAM policies.
  • Same account: an IAM identity policy that allows execute-api:Invoke is enough.
  • Cross-account: the caller needs an identity policy, and the API needs a resource policy that allows the caller.
  • A private API needs a resource policy that allows access from the VPC endpoint or VPC.
  • Callers from an identity pool can sign requests with their temporary credentials.

Exam signals

  • "REST API, users sign in with Cognito, least code" → Cognito user pool authorizer, because API Gateway validates the tokens with no function to write.
  • "HTTP API, tokens from a third-party OIDC provider" → JWT authorizer, because it validates any OIDC or OAuth 2.0 JWT with no code.
  • "Authorize on a header and a query string together" → REQUEST Lambda authorizer, because a TOKEN authorizer sees only one header.
  • "User gets 403 on a second method after the first call works" → cached policy covers only the first method. API Gateway reuses that policy for the second method, and the policy does not allow it.
  • "Another AWS account must call the API" → IAM authorization and a resource policy, because a cross-account call needs an allow on both sides.

CORS

Key facts

  • An origin is the protocol, domain, and port of the web page, for example https://app.example.com. A browser blocks a cross-origin call unless the response has the correct CORS headers. A different domain, subdomain, port, or protocol is cross-origin. The request can reach the API, but the browser does not give the response to the page code.
  • A non-simple request (for example, with an Authorization header or JSON content type) causes a preflight OPTIONS request. In the preflight, the browser asks the API if the origin, method, and headers are allowed. If the OPTIONS response does not allow them, the browser does not send the real request.
  • Headers: Access-Control-Allow-Origin (the origins that can read the response), Access-Control-Allow-Methods (the allowed HTTP methods), Access-Control-Allow-Headers (the request headers that the client can send).
  • REST API, non-proxy integration: "Enable CORS" adds an OPTIONS mock method and adds headers to the integration responses.
  • REST API, Lambda proxy or HTTP proxy: the backend must return the CORS headers in each response. API Gateway cannot add them.
  • For CORS headers on API Gateway errors (4XX, 5XX), add them to the gateway responses. When API Gateway itself rejects a request (for example, 401 from an authorizer or 429 from throttling), the backend does not run and cannot add the headers. The browser then shows a CORS error and hides the real status code.
  • HTTP API: configure CORS on the API. API Gateway answers preflight requests itself and ignores CORS headers from the backend.

Exam signals

  • "CORS enabled in the console, but the browser still blocks a Lambda proxy response" → return Access-Control-Allow-Origin from the function, because a proxy integration has no integration response where API Gateway can add the header.
  • "HTTP API, browser app on another domain, least effort" → CORS configuration on the HTTP API.

References: CORS for REST APIs, CORS for HTTP APIs. Lab: Lab 4.1 REST vs HTTP API.

Errors, logs, metrics, and tracing

Common status codes

CodeUsual cause
400Request validation failed
401Missing or invalid token for an authorizer
403Explicit deny, missing API key, WAF block, or (REST API) a path or method that does not exist: "Missing Authentication Token"
429Throttled, or usage plan quota exceeded
502Bad response from the backend, for example a wrong Lambda proxy format
504Integration timeout

The name "Missing Authentication Token" is misleading. A REST API returns it for a resource or method that does not exist, for example a wrong path, a wrong HTTP method, or a missing stage name in the URL. It also appears when a method with IAM authorization gets a request with no SigV4 signature.

CloudWatch metrics

  • Count, 4XXError, 5XXError, CacheHitCount, CacheMissCount.
  • IntegrationLatency: time the backend takes.
  • Latency: total time from request to response. It includes integration latency and API Gateway overhead, for example a Lambda authorizer.
  • Metrics for each method need detailed CloudWatch metrics on the stage (extra cost). Without them, you see metrics only for the whole API and stage, so you cannot tell which method is slow or fails.

Logs and tracing

  • Execution logs (REST API): how API Gateway processed the request, with errors and traces. Levels: ERROR or INFO. Optional full request and response data. Use them to debug, for example to see mapping template output or authorizer results.
  • Access logs: one line for each request, in a format you choose with $context variables. REST and HTTP APIs. Use them to record who called the API and the result, for audits and traffic analysis.
  • To write logs, set an IAM role with AmazonAPIGatewayPushToCloudWatchLogs as cloudWatchRoleArn in the API Gateway account settings. Do this in each Region. API Gateway writes the logs with this role. Without it, no execution logs appear, even when logging is on for the stage.
  • X-Ray tracing: turn it on for a REST API stage. HTTP APIs do not support X-Ray.

Exam signals

  • "Latency is high, IntegrationLatency is low" → delay is in API Gateway, for example an uncached Lambda authorizer, because Latency minus IntegrationLatency is the time spent outside the backend.
  • "No execution logs appear" → set the CloudWatch role ARN in account settings and turn on logging for the stage.
  • "Find which service in the request path is slow" → X-Ray on the REST API stage and on Lambda.

Cognito user pools: tokens, sign-in, and triggers

Tokens

TokenContentsDefault validity
ID tokenIdentity claims: sub, email, custom attributes, cognito:groups1 hour (maximum 1 day)
Access tokenscope, client_id, cognito:groups. No aud claim by default.1 hour (maximum 1 day)
Refresh tokenEncrypted. Gets new ID and access tokens.30 days (60 minutes to 10 years)

Send the access token when the API checks OAuth scopes, because only the access token carries them. Send the ID token when the backend needs facts about the user, such as the email address, or when a Cognito user pool authorizer method has no scopes. The app keeps the refresh token and uses it to get new ID and access tokens without a new sign-in.

  • Verify a JWT (JSON Web Token): check the signature with the public keys (the JWKS) at https://cognito-idp.{region}.amazonaws.com/{userPoolId}/.well-known/jwks.json. A valid signature proves that your user pool issued the token and nobody changed it. Then check exp (not expired), iss (your user pool), token_use (id or access, so nobody can use an ID token as an access token), and aud (ID token) or client_id (access token) for your app client.
  • GlobalSignOut and AdminUserGlobalSignOut revoke all refresh, ID, and access tokens of a user. RevokeToken revokes one refresh token and the access tokens that it issued. Cognito APIs reject revoked tokens. A service that only checks the signature and expiry still accepts them until they expire, so keep access token validity short.
  • Refresh token rotation (optional) issues a new refresh token at each refresh. It does not extend the original validity.

Sign-in and features

  • App client with no secret: browser and mobile apps. With a secret: server-side apps. Code that runs on a user device cannot keep a secret, because anyone can read it from the app.
  • Auth flows are the sign-in methods that an app client allows:
    • ALLOW_USER_SRP_AUTH: SRP (Secure Remote Password). The app sends proof that it knows the password, not the password itself. Use it in client apps.
    • ALLOW_USER_PASSWORD_AUTH: the app sends the password to Cognito (over TLS). The migrate user trigger needs this flow (or the admin flow or USER_AUTH with a password), because the trigger must receive the password.
    • ALLOW_ADMIN_USER_PASSWORD_AUTH: a server-side app signs users in with AdminInitiateAuth and its own IAM credentials.
    • ALLOW_CUSTOM_AUTH: Lambda challenge triggers decide the sign-in steps.
    • ALLOW_REFRESH_TOKEN_AUTH: gets new ID and access tokens with a refresh token.
    • ALLOW_USER_AUTH: choice-based sign-in. The user can choose a password, a passkey, or a one-time code by email or SMS.
  • Managed login (formerly hosted UI) gives OAuth 2.0 sign-in pages and federation with SAML, OIDC, and social providers. Federation means that users sign in with an account at another identity provider (for example, Google or a company directory), and the user pool then issues its own tokens.
  • MFA: SMS, email, or TOTP (authenticator app).
  • Groups put a cognito:groups claim in tokens. The backend reads the claim for role-based access, for example to allow admin operations. Only administrators can change group membership, so users cannot add themselves. A group can have an IAM role for identity pools.
  • A resource server represents your API in the user pool. It defines custom scopes, for example orders/read. Cognito puts the scopes that the app client may use into the access token, and the API checks them.

Cognito identity pools and temporary AWS credentials

Key facts

  • An identity pool exchanges proof of sign-in for temporary AWS credentials. Accepted proof: user pool ID token, OIDC ID token, SAML assertion, social provider token, or a developer-authenticated identity (your own backend signs the user in and vouches for the user). The app then calls AWS services such as S3 or DynamoDB directly with these credentials.
  • Each identity pool has an authenticated role and an optional unauthenticated (guest) role.
  • Turn on guest access only if you need it. Give the guest role fewer permissions, because anyone who runs the app can get guest credentials without a sign-in.
  • The role trust policy must trust cognito-identity.amazonaws.com for sts:AssumeRoleWithWebIdentity, with a cognito-identity.amazonaws.com:aud condition equal to your identity pool ID. The aud condition limits the role to your identity pool. IAM returns an error if you save this trust policy without it. The cognito-identity.amazonaws.com:amr condition (authentication method) has the value authenticated or unauthenticated. Use it so that guests cannot assume the authenticated role.

Authentication flows

FlowAPI callsNotes
Enhanced (recommended)GetId, then GetCredentialsForIdentityIdentity pool picks the role. Credentials valid for 1 hour.
Basic (classic)GetId, GetOpenIdToken, then STS AssumeRoleWithWebIdentityThe app picks the role. Not supported with role mappings.

Use the enhanced flow unless you have a special reason. In the basic flow, the app code chooses the role, so a user who changes the app can ask for any role that trusts the identity pool.

Role selection

  • Default authenticated role for all users.
  • Choose role from token: uses cognito:preferred_role or cognito:roles from user pool groups. When a user is in more than one group, the group with the lowest precedence value wins.
  • Rules: map a token claim to a role. Rules run in order. The first match wins. Maximum 25 rules for each provider.
  • Do not map roles from claims that users can change. A user could edit a writable attribute, for example custom:role, and get a more powerful role.

Per-user access with policy variables

  • ${cognito-identity.amazonaws.com:sub} is the identity ID of the caller (not the user pool sub). The identity pool gives each user its own identity ID. IAM puts that value into the policy at request time, so one policy gives each user a different resource.
  • Example resource: arn:aws:s3:::bucket/${cognito-identity.amazonaws.com:sub}/*. Each user can then use only the prefix with their own identity ID.
  • DynamoDB: add the condition dynamodb:LeadingKeys equal to the identity ID. The user can then read and write only items whose partition key is their identity ID.

Exam signals

  • "Mobile app uploads directly to S3, each user only in their own folder" → identity pool and a policy variable, because S3 needs AWS credentials and the variable limits each user to one prefix.
  • "Guest users read the catalog without sign-in" → unauthenticated role with read-only access, because guests get credentials with no sign-in.
  • "Group members get a different IAM role" → group IAM role and "choose role from token", because the group role arrives in the token claim.
  • "User pool or identity pool" → JWT for your API: user pool. AWS credentials: identity pool.

CloudFront caching, origin access, and private content

Cache key and policies

  • The cache key decides if two requests are the same. Requests with the same cache key get the same cached object. Each value that you add to the key (for example, a header with many values such as User-Agent) splits the cache into more entries, so fewer requests find a cached copy. Fewer values in the cache key give a higher cache hit ratio (the percentage of requests that CloudFront serves from the cache).
  • A cache policy sets the cache key (headers, cookies, query strings) and the TTLs (minimum, maximum, default).
  • An origin request policy sends extra values to the origin without adding them to the cache key.
  • Values in the cache key always go to the origin. You do not need to add them to the origin request policy too.
  • The origin Cache-Control or Expires header sets the TTL inside the minimum and maximum TTL. With no origin header, CloudFront uses the default TTL.
  • Remove cached objects with an invalidation (for example, /images/*), or use versioned file names (for example, app.v2.js). A new file name is a new cache key, so users get the new file at once with no invalidation. The first 1,000 invalidation paths each month are free. After that, you pay for each path.
  • Response header X-Cache: Hit from cloudfront or Miss from cloudfront shows the result.

S3 origin access

  • Use origin access control (OAC). With OAC, CloudFront signs its requests to S3, and the bucket stays private. Users cannot read objects directly from S3, so they cannot skip CloudFront rules such as signed URLs or AWS WAF. Origin access identity (OAI) is legacy.
  • OAC supports SSE-KMS, all Regions, and PUT and DELETE requests.
  • The bucket policy allows cloudfront.amazonaws.com with an AWS:SourceArn condition for the distribution. For SSE-KMS, the KMS key policy must also allow CloudFront.
  • An S3 website endpoint is a custom origin. OAC does not work with it, because a website endpoint needs public read access and does not accept signed requests.

Private content and security

  • Signed URLs and signed cookies give access to private content for a limited time. Your application signs a policy (expiry time, paths) with a private key. CloudFront checks the signature with the matching public key in a trusted key group. A request with no valid signature gets 403.
  • Signed URLs: choose them for one file, or for clients that do not support cookies. The signature is in the URL query string, so each file URL changes.
  • Signed cookies: choose them for many files (for example, all video segments), when URLs must not change.
  • Viewer protocol policy: redirect HTTP to HTTPS, or HTTPS only.
  • Field-level encryption encrypts selected form fields at the edge with a public key. Only the application that has the private key can decrypt them. Use it for data such as card numbers that other services in the request path must not read.
  • Geographic restrictions allow or block countries for the whole distribution.

Edge functions

Cache key normalization means you change a request (for example, make header values lowercase) so that more requests share one cache key.

Exam signals

  • "Low cache hit ratio, all headers in the cache key" → cache policy with only the values that change the response; origin request policy for the rest.
  • "Private S3 bucket encrypted with SSE-KMS behind CloudFront" → OAC, bucket policy, and KMS key policy.
  • "Paid users stream many video files" → signed cookies, because one cookie covers all the files and the URLs stay the same.
  • "Lightweight header rewrite at high scale" → CloudFront Functions, because they are cheaper and faster than Lambda@Edge for simple viewer request changes.

Geolocation answers by where the user is (for example, users in France get the French site). Latency answers by the fastest Region for the user. Failover keeps a standby resource for when the primary fails.

  • An alias record points to an AWS resource (CloudFront, API Gateway, load balancer, S3 website). It works at the zone apex: the domain name with no subdomain, for example example.com. A CNAME does not, because DNS rules do not allow a CNAME at the zone apex.

AWS WAF

  • A web ACL (web access control list) is a set of rules that AWS WAF checks for each request. If no rule matches, the default action (Allow or Block) applies. Blocked requests get 403.
  • Rule types: AWS managed rule groups, rate-based rules, IP sets, geo match, regex, size, SQL injection, and XSS match.
  • Regional resources: API Gateway REST API, Application Load Balancer, AWS AppSync, Cognito user pool, App Runner, Verified Access, and others.
  • CloudFront: create the web ACL in us-east-1 (scope CLOUDFRONT). CloudFront is a global service, and AWS WAF manages its web ACLs in us-east-1.
  • HTTP APIs are not supported. Put CloudFront in front and attach the web ACL to the distribution.
  • Each resource can have only one web ACL.

Numbers to memorize (rate-based rule)

ItemValue
Evaluation window60, 120, 300 (default), or 600 seconds
Limit10 to 2,000,000,000 requests in the window
AggregationSource IP (default), forwarded IP header, custom keys, or all matching requests

A rate-based rule counts requests for each aggregation key (by default, each source IP address) over the window. When a key goes over the limit, the rule acts on its requests, for example Block. When its rate falls below the limit again, AWS WAF stops the action. Use the forwarded IP header when a proxy sits in front, because then all requests come from the proxy IP address.

Certificates and custom domains

  • CloudFront and edge-optimized API custom domains: the ACM certificate must be in us-east-1. An edge-optimized API uses CloudFront, and CloudFront reads certificates only from us-east-1. A certificate in another Region does not appear in the list.
  • Regional API custom domains: the ACM certificate must be in the same Region as the API.
  • ACM public certificates are free and renew automatically.
  • API mappings (base path mappings) connect a custom domain to API stages. Example: api.example.com/orders → orders API, prod stage, and api.example.com/users → users API, prod stage. API Gateway removes the mapped base path before it calls the API. You can map REST and HTTP API stages to the same domain.
  • After you create the custom domain, create a Route 53 alias record that points to the API Gateway domain name for the custom domain.

Exam signals

  • "Block IPs that send too many requests" → WAF rate-based rule, because it counts requests for each IP address and blocks those over the limit.
  • "WAF for an HTTP API" → CloudFront in front, web ACL in us-east-1, because AWS WAF cannot attach to an HTTP API directly.
  • "Secondary Region serves only when the primary fails" → failover routing and a health check, because Route 53 returns the secondary record only when the primary health check fails.
  • "Edge-optimized custom domain, certificate not listed" → request it in us-east-1, because edge-optimized domains use CloudFront.
  • "Several APIs under one domain, each with its own path" → API mappings on one custom domain, because each mapping sends one base path to one API stage.
