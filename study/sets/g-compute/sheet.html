EC2 for developers

Remember

  • User data is a shell script or cloud-init directives that configure an instance at launch.
  • User data runs only at the first boot by default. A reboot or a stop and start does not run it again.
  • A user data script on Linux runs as root. Do not use sudo in it.
  • A user data script cannot answer prompts. Use non-interactive commands, for example yum update -y.
  • To find user data script errors, read /var/log/cloud-init-output.log on the instance.
  • To change user data, stop the instance first.
  • Any process on the instance can read user data from IMDS. Do not put secrets or access keys in user data.
  • A script that calls AWS APIs gets credentials from an instance profile, which attaches an IAM role to the instance.
  • The instance metadata service (IMDS) is at 169.254.169.254 and returns instance data and role credentials.
  • IMDSv1 answers a plain GET with no token.
  • IMDSv2 first needs a PUT to /latest/api/token with header X-aws-ec2-metadata-token-ttl-seconds.
  • Each IMDSv2 GET sends the token in the header X-aws-ec2-metadata-token.
  • To require IMDSv2, set HttpTokens to required. Then IMDSv1 calls fail.
  • When IMDSv2 is required, a request without a valid token gets 401 - Unauthorized.
  • IMDSv2 blocks most SSRF attacks, because most SSRF flaws can send only a GET, not a PUT.
  • IMDS rejects a token PUT that has an X-Forwarded-For header, so an open reverse proxy cannot get a token.
  • An IMDSv2 token works only on the instance that created it.
  • An IMDSv2 token time to live is 1 second to 6 hours (21,600 seconds).
  • The MetadataNoToken CloudWatch metric counts IMDSv1 calls. Check it before you require IMDSv2.
  • The default PUT response hop limit is 1. It is 2 for AMIs with ImdsSupport: v2.0, for example Amazon Linux 2023.
  • A container on EC2 adds one network hop. Set the hop limit to 2 so the container gets an IMDSv2 token.
  • With hop limit 1, the token request from a container times out.
  • Session Manager gives shell access with no open inbound ports, no bastion hosts, and no SSH keys.
  • IAM policies control who can start a Session Manager session on which instance.
  • Session Manager can log session data to S3 or CloudWatch Logs. CloudTrail records the Session Manager API calls.
  • Session Manager needs SSM Agent and an instance profile with AmazonSSMManagedInstanceCore.
  • Session Manager needs outbound HTTPS (port 443) to the ssm, ssmmessages, and ec2messages endpoints.
  • For Session Manager in a private subnet with no internet access, create interface VPC endpoints for these three services.

Exam signals

  • "Protect instance credentials from SSRF" → require IMDSv2 (HttpTokens required). An SSRF GET cannot get the session token first.
  • "After IMDSv2 was required, the script gets 401" → get a token with PUT, then send it in the header. IMDSv2 rejects requests without a token.
  • "Container on EC2 cannot get IMDSv2 credentials" → set the PUT response hop limit to 2. The container network adds one hop.
  • "Shell access, no port 22, no bastion, audit the sessions" → Session Manager with session logging. SSM Agent connects outbound, and IAM controls who can connect.
  • "User data script did not work" → read /var/log/cloud-init-output.log. It holds the script output and errors.

Explanation

User data

  • User data is text that you give to an instance at launch to configure it automatically, for example to install and start a web server. It can be a shell script or cloud-init directives.
  • cloud-init is the package on Amazon Linux that reads the user data at boot and runs it.
  • By default, user data runs only during the first boot cycle of the instance. A reboot or a stop and start does not run it again.
  • On Linux, the script runs as the root user. Do not use sudo in the script.
  • The script does not run interactively, so no person can answer a prompt. A command that waits for input does not complete. Use the non-interactive form of each command, for example yum update -y.
  • To find script errors, read /var/log/cloud-init-output.log on the instance. This file captures the console output of the script, with its error messages.
  • To change user data, stop the instance first. When you start it again, the new script does not run by default, because user data runs only at the first boot.
  • If the script calls AWS APIs, attach an instance profile. An instance profile attaches an IAM role to the instance, and the CLI and SDKs get temporary credentials for that role automatically.
  • Do not put access keys in the script.
  • Any process on the instance can read user data from the instance metadata service. Do not put secrets in user data.

Instance metadata service (IMDS)

  • The instance metadata service (IMDS) is an HTTP endpoint at 169.254.169.254 that software on the instance can call. It returns data about the instance, for example the instance ID, the AMI ID, and the user data.
  • IMDS also returns the temporary credentials of the instance profile role. The AWS SDKs get these credentials from IMDS automatically.
  • IMDSv1 answers any plain GET request, with no token. IMDSv2 first requires a session token from a PUT request. Each GET must then send that token.
  • IMDSv2 step 1: send a PUT to /latest/api/token with the header X-aws-ec2-metadata-token-ttl-seconds.
  • IMDSv2 step 2: send each GET with the header X-aws-ec2-metadata-token.
  • To require IMDSv2, set HttpTokens to required (--http-tokens required). Then IMDSv1 calls fail.
  • When IMDSv2 is required, a request without a valid token gets 401 - Unauthorized.
  • Server-side request forgery (SSRF) is a flaw in which an attacker makes your application send an HTTP request to a URL that the attacker chooses.
  • With IMDSv1, one SSRF GET to the credentials path returns the role credentials. With IMDSv2, the attacker must also send a PUT with a special header, and most SSRF flaws can send only a GET.
  • IMDS rejects a token PUT that has an X-Forwarded-For header. Proxies add this header. Thus an open reverse proxy on the instance (a proxy that forwards requests from outside) cannot get a token for an attacker.
  • The token works only on the instance that created it.
  • The MetadataNoToken CloudWatch metric counts IMDSv1 calls. Check it before you require IMDSv2. If the count is not zero, some software still uses IMDSv1, and its calls fail with 401 after the change.

The PUT response hop limit is the IP time to live of the token response. Each network hop, for example the bridge network of a container, lowers it by 1. When it reaches 0, the response is dropped.

With hop limit 1, the token reaches processes on the host but not a container one hop further. The token request then times out.

Shell access with Session Manager

  • Session Manager (AWS Systems Manager) gives shell access with no open inbound ports, no bastion hosts, and no SSH keys.
  • A bastion host is a server in a public subnet that you connect to with SSH first, to reach private instances.
  • IAM policies control who can start a session on which instance.
  • You can log session data to Amazon S3 or CloudWatch Logs. CloudTrail records the Session Manager API calls.
  • The instance needs SSM Agent and an instance profile with the needed permissions. AmazonSSMManagedInstanceCore gives the needed permissions.
  • SSM Agent is the program on the instance that connects it to Systems Manager.
  • The instance needs outbound HTTPS (port 443) to the ssm, ssmmessages, and ec2messages endpoints. SSM Agent opens these connections from the instance, so no inbound rule is necessary.
  • For a private subnet with no internet access, create interface VPC endpoints for these three services. An interface VPC endpoint puts a private IP address for an AWS service in your subnet, so traffic does not use the internet.

Elastic Load Balancing

Remember

  • An ALB works at layer 7 (HTTP, HTTPS, gRPC) and routes by path, host, header, method, query string, or source IP.
  • An NLB works at layer 4 (TCP, UDP, TLS) and sends each connection to one target by a flow hash.
  • Choose an ALB to route HTTP requests by content.
  • Choose an NLB for TCP or UDP traffic, static IP addresses, or extreme throughput.
  • An NLB has one static IP address in each Availability Zone. You can attach one Elastic IP address for each subnet.
  • An ALB cannot use your own Elastic IP addresses.
  • ALB target types are instance, ip, and lambda. NLB target types are instance, ip, and alb.
  • Use target type ip for ECS tasks in awsvpc mode (Fargate) and for private addresses outside the VPC.
  • To put static IP addresses in front of an ALB, use an NLB with target type alb.
  • An ALB needs subnets in at least two Availability Zones.
  • A lambda target group holds one Lambda function. Use one target group for each function.
  • ALB cross-zone load balancing is always on at the load balancer level. You can turn it off for a target group.
  • The deregistration delay default is 300 seconds (range 0 to 3,600). Set it longer than your longest request.
  • A request still in progress when the deregistration delay ends fails with 502.
  • Slow start increases traffic to a new target linearly over 30 to 900 seconds. The default is 0 (off).
  • Slow start does not work with least outstanding requests or weighted random.
  • The default routing algorithm is round robin. Use it when requests are similar.
  • Use least outstanding requests when request times vary.
  • Use weighted random for Automatic Target Weights anomaly mitigation. Weighted random does not work with sticky sessions or slow start.
  • The ALB idle timeout default is 60 seconds. A target slower than the idle timeout causes 504.
  • Sticky sessions send all requests from one client to the same target. The client must accept cookies.
  • Stickiness duration default is 1 day (range 1 second to 7 days).
  • Duration-based stickiness uses the ALB cookie AWSALB. Application-based stickiness follows your application cookie.
  • Sticky sessions do not work when cross-zone load balancing is off.
  • Sticky sessions lose user sessions when a target fails. A shared session store (ElastiCache, DynamoDB) is the better design.
  • The target sees the ALB IP address. The client IP address is in the X-Forwarded-For header.
  • The default XFF mode is append. The remove mode deletes the header.
  • X-Forwarded-Proto holds the client protocol. X-Forwarded-Port holds the client destination port.
  • ALB 502 means the target closed the connection, sent a bad response, or a Lambda target failed.
  • ALB 503 means the target group has no registered targets, or all targets are unused.
  • ALB 504 means no target connection in 10 seconds, a target slower than the idle timeout, or a blocking network ACL.
  • A Lambda target with a request body above 1 MB gives 413. A response body above 1 MB gives 502.
  • ALB 460 means the client closed the connection before the idle timeout.
  • ALB 463 means X-Forwarded-For has more than 30 IP addresses.
  • HTTPCode_Target_5XX_Count counts target errors. HTTPCode_ELB_5XX_Count counts errors that the ALB makes.

Exam signals

  • "Route /api and /images to different services" or "route by host name" → ALB listener rules. Only the ALB reads the HTTP path and headers.
  • "Static IP addresses for an allow list" or "TCP or UDP, extreme throughput" → NLB. It has one static IP address in each Availability Zone and works at layer 4.
  • "Application logs show the load balancer IP, not the client" → read X-Forwarded-For. The ALB puts the client address there.
  • "Users lose their session; sessions are in memory; fewest code changes" → sticky sessions. The cookie sends each user back to the same target.
  • "502 errors during deployments for long requests" → increase the deregistration delay. The ALB ends in-flight requests when the delay ends.
  • "504 errors for slow requests" → make the target faster or increase the idle timeout. The target response time is above the idle timeout (default 60 seconds).

Explanation

An ALB reads each HTTP request, so it can route by the URL path, host name, or headers.

An NLB does not read HTTP content. For TCP, it calculates a flow hash from the protocol, source and destination IP addresses and ports, and the TCP sequence number. All packets of one connection then go to the same target.

Choose an ALB to route HTTP requests by content. Choose an NLB for TCP or UDP traffic, static IP addresses, or extreme throughput.

Use target type instance to register EC2 instances by instance ID. Use ip for ECS tasks in awsvpc network mode, for example Fargate tasks, which have no instance ID.

Also use ip for private addresses outside the VPC, for example in a peered VPC or on premises.

Use alb on an NLB to put static IP addresses in front of an ALB.

  • An ALB needs subnets in at least two Availability Zones. The ALB runs a node in each enabled zone, so the failure of one zone does not stop the load balancer.
  • A target group with type lambda holds one Lambda function. To route to several functions, create one target group for each function and use listener rules.
  • Cross-zone load balancing lets each load balancer node send traffic to targets in all enabled Availability Zones. When it is off, each node sends traffic only to targets in its own Availability Zone.
  • For an ALB, cross-zone load balancing is always on at the load balancer level. You can turn it off for a target group.

  • Deregistration delay: when you deregister a target, for example during a deployment or a scale-in, the target is draining for this time. The ALB sends no new requests to it, and in-flight requests can complete.
  • When the deregistration delay ends, a request that is still in progress fails with 502. Set the delay longer than your longest request.
  • Slow start: a new healthy target gets a share of requests that increases linearly over the slow start duration. Use it when a new target needs time to warm up, for example to fill a cache.
  • You cannot use slow start with least outstanding requests or weighted random.
  • Routing algorithm: round robin sends requests to the targets in turn. Use it when requests are similar.
  • Least outstanding requests sends each request to the target with the fewest requests in progress. Use it when request times vary.
  • Weighted random supports Automatic Target Weights anomaly mitigation, which sends less traffic to a target with a high error rate. Choose weighted random when you want anomaly mitigation.
  • Weighted random does not work with sticky sessions or slow start.
  • Idle timeout: the ALB closes a connection when no data moves on it for this time. If a target takes longer than the idle timeout to respond, the client gets 504.
  • Sticky sessions (session affinity): the ALB sends all requests from one client to the same target, so the target can keep session data in memory. The client must accept cookies.
  • Duration-based stickiness uses the ALB cookie AWSALB with a duration that you set. Application-based stickiness follows a cookie that your application sets. Choose it when your application already has its own session cookie.
  • Sticky sessions do not work when cross-zone load balancing is off.
  • Sticky sessions are a fast fix for in-memory sessions, with no code change. But when a target fails or is removed, its users lose their sessions. A shared session store (for example, ElastiCache or DynamoDB) is the better design, because any target can then serve any user.

Client information

  • The ALB opens its own connection to the target, so the target sees the ALB IP address as the source.
  • The ALB puts the client IP address in the X-Forwarded-For (XFF) request header. Read this header to log or check the client address.
  • Default XFF mode is append. The ALB adds the client IP address to the end of an existing header. The remove mode deletes the header, so the target does not get the client address.
  • X-Forwarded-Proto holds the client protocol (HTTP or HTTPS). X-Forwarded-Port holds the client destination port. Use them when the ALB ends HTTPS and sends HTTP to the target, for example to find out if the client used HTTPS.

Health checks and readiness probes

Remember

  • The ALB health check path default is /.
  • The ALB health check interval default is 30 seconds (35 for lambda). The range is 5 to 300 seconds.
  • The ALB health check timeout default is 5 seconds (30 for lambda). The range is 2 to 120 seconds.
  • The ALB healthy threshold default is 5. The unhealthy threshold default is 2. Both have a range of 2 to 10.
  • The ALB health check matcher default is 200. The range is 200 to 499.
  • A new ALB target must pass one health check before it gets traffic.
  • When all targets are unhealthy, the ALB fails open and sends traffic to all of them.
  • The target security group must allow the load balancer on the health check port. If not, targets show Target.Timeout.
  • Target.ResponseCodeMismatch means a wrong status code, for example a 302. Use a path that returns 200, or change the matcher.
  • Target.FailedHealthChecks means the application is down or does not listen on the health check port.
  • Elb.InitialHealthChecking means the initial health checks are in progress.
  • EC2 Auto Scaling uses only EC2 status checks by default. These checks do not see a crashed application.
  • To replace instances that fail the target group health check, turn on ELB health checks for the Auto Scaling group.
  • The Auto Scaling health check grace period default is 300 seconds in the console and 0 with the CLI or an SDK.
  • Set the Auto Scaling grace period to cover the application start time. Without it, Auto Scaling can terminate starting instances.
  • An ECS container health check runs a command inside the container. Exit code 0 means healthy.
  • An ECS health check command starts with CMD or CMD-SHELL.
  • ECS container health check defaults: interval 30 seconds, timeout 5 seconds, retries 3, startPeriod off.
  • ECS container health check ranges: interval 5 to 300, timeout 2 to 60, retries 1 to 10, startPeriod 0 to 300 seconds.
  • Failed checks during startPeriod do not count toward retries.
  • ECS ignores a HEALTHCHECK in the image. ECS uses only the health check in the task definition.
  • In a service, ECS stops an unhealthy task and starts a replacement.
  • ECS healthCheckGracePeriodSeconds ignores failed ELB, VPC Lattice, and container health checks after a task starts. The default is 0.
  • ECS startPeriod does not stop ELB health checks from failing a task.
  • A Kubernetes liveness probe failure makes the kubelet restart the container.
  • A Kubernetes readiness probe failure removes the Pod from Service endpoints, with no restart.
  • A Kubernetes startup probe gives a slow application time to start. Liveness and readiness probes wait for it.
  • A Kubernetes httpGet probe passes on a 200 to 399 status.
  • A Kubernetes tcpSocket probe passes on a connection, exec on exit code 0, and grpc on SERVING.
  • Do not check external dependencies in a liveness probe. Put dependency checks in the readiness probe.
  • A shallow health check confirms only that the process answers. Use it for liveness and restart decisions.
  • A deep health check also tests dependencies. One shared database failure fails every target at the same time.
  • Route 53 health checks control DNS failover. Route 53 stops returning a record with an unhealthy health check.
  • Route 53 health checks monitor an endpoint, other health checks (calculated), or a CloudWatch alarm.
  • A calculated Route 53 health check is healthy when at least N of its monitored health checks are healthy.
  • A Route 53 HTTP or HTTPS check needs a 2xx or 3xx status code.
  • A Route 53 string match must appear in the first 5,120 bytes of the response body.
  • The Route 53 request interval is 30 seconds (standard) or 10 seconds (fast, extra cost).
  • Route 53 health checkers cannot reach private IP addresses. For a private resource, monitor a CloudWatch alarm.

Exam signals

  • "Targets unhealthy, ResponseCodeMismatch, app redirects" → health check path that returns 200. The default matcher accepts only 200, not a 302 redirect.
  • "Targets unhealthy with Target.Timeout, app works locally" → security group does not allow the health check port. A blocked port gives no answer while the app itself works.
  • "Slow-starting tasks are killed in a loop" → ECS healthCheckGracePeriodSeconds. ECS ignores failed health checks during the grace period.
  • "Crashed application stays in service in the Auto Scaling group" → turn on ELB health checks for the group. EC2 status checks do not see the application.
  • "Database outage restarts all Pods" → move the dependency check from liveness to readiness. A readiness failure stops traffic without a restart.
  • "Route 53 failover for a resource with a private IP address" → CloudWatch alarm health check. Route 53 health checkers cannot reach private addresses.

The healthy threshold is the number of checks in a row that a target must pass to become healthy. The unhealthy threshold is the number of checks in a row that it must fail to become unhealthy.

The matcher is the list of HTTP status codes that count as a pass.

  • A new target must pass one health check before it gets traffic.
  • If all targets in a target group are unhealthy, the ALB fails open. It sends traffic to all of them.
  • AWS says that this increases the chance that a client connection succeeds when targets fail health checks for a short time. It also reduces the risk of overloading the remaining healthy targets.
  • The target security group must allow traffic from the load balancer on the health check port. If it does not, the checks get no answer and the targets show Target.Timeout.

EC2 Auto Scaling health checks

  • By default, Auto Scaling uses only EC2 status checks. These checks test the instance and its host, not your application. An instance with a crashed application process passes them and stays in service.
  • Turn on Elastic Load Balancing health checks for the group. Then Auto Scaling replaces instances that fail the target group health check.
  • Health check grace period: the time after a new instance enters InService during which Auto Scaling does not replace it for failed health checks.
  • Set the grace period to cover the start time of the application. Without it, Auto Scaling can terminate instances that are still starting.
  • The grace period default is 300 seconds in the console and 0 seconds (off) with the AWS CLI or an SDK.

  • A container health check is a command that ECS runs inside the container at each interval.
  • The command starts with CMD (run the command directly) or CMD-SHELL (run it with the default shell of the container). Example: ["CMD-SHELL", "curl -f http://localhost/ || exit 1"]. Exit code 0 means healthy.
  • retries is the number of failed checks in a row before the container is unhealthy.
  • During startPeriod, failed checks do not count toward retries. Use it to give a slow container time to start.
  • ECS monitors only the health check in the task definition. It ignores a HEALTHCHECK in the image.
  • In a service, ECS stops an unhealthy task and starts a replacement.
  • healthCheckGracePeriodSeconds is a service setting. For this number of seconds after a task starts, the scheduler ignores failed ELB, VPC Lattice, and container health checks.
  • Set healthCheckGracePeriodSeconds longer than the start time of the application. With the default of 0, ECS can stop a slow-starting task before it is ready, and the replacement fails the same way.
  • startPeriod applies only to the container health check. It does not stop ELB health checks from failing a task.

Kubernetes probes (Amazon EKS)

A probe is a check that the kubelet runs on a container at an interval.

The kubelet is the Kubernetes agent on each node. Service endpoints are the list of Pod addresses that a Service sends traffic to.

ProbePurposeOn failure
LivenessFind a stuck process, for example a deadlockThe kubelet restarts the container.
ReadinessFind out if the container can take trafficThe Pod is removed from Service endpoints. No restart.
StartupGive a slow application time to startThe kubelet kills the container and restarts it according to the Pod restart policy. Liveness and readiness probes wait until the startup probe succeeds.
  • Probe types: httpGet passes on a 200 to 399 status.
  • tcpSocket passes when the port accepts a connection.
  • exec passes on exit code 0.
  • grpc passes when the gRPC health service returns SERVING.
  • Do not check external dependencies in a liveness probe. A database outage then restarts every Pod. Put dependency checks in the readiness probe.

Shallow and deep health checks

  • A shallow check confirms that the process answers. Use it for liveness and restart decisions.
  • A deep check also tests dependencies, for example the database. When all targets share that dependency, one database failure makes every target fail its check at the same time.
  • Use a deep check only where removing the target from traffic is the correct result, for example a readiness probe.

Route 53 health checks

  • Route 53 uses health checks for DNS failover. It stops returning a record when the health check of that record is unhealthy.
  • Three types: monitor an endpoint, monitor other health checks (calculated), or monitor a CloudWatch alarm.
  • A calculated health check is healthy when at least N of the health checks that it monitors are healthy. Use it to fail over only when several endpoints are down.
  • HTTP and HTTPS endpoint checks need a 2xx or 3xx status code.
  • With string matching, Route 53 also searches the response body for a string that you set. The string must appear in the first 5,120 bytes.
  • Request interval: 30 seconds (standard) or 10 seconds (fast, extra cost).
  • Route 53 health checkers run in AWS data centers around the world. They cannot reach endpoints with private IP addresses. For a private resource, use a health check that monitors a CloudWatch alarm.

Container images

Remember

  • Each Dockerfile instruction makes a layer. Docker reuses a cached layer when its inputs did not change.
  • When a layer changes, Docker rebuilds that layer and all layers after it. Put rarely changed steps first.
  • Copy and install the dependency file (for example, package.json) before you copy the source code.
  • A multi-stage build copies only the build output into a small runtime image, without compilers, build tools, or source code.
  • Use a small base image. A smaller image downloads faster and has fewer packages to attack.
  • Do not put secrets in an image. Get secrets at run time, for example from Secrets Manager.
  • For ECS, put all dependencies in the image and build a new image for each change.
  • Run one application process in each ECS container.
  • When ECS stops a task, it sends SIGTERM first and SIGKILL later. Handle SIGTERM for a clean shutdown.
  • Write container logs to stdout and stderr. The awslogs log driver sends them to CloudWatch Logs.
  • Tag each build with a unique tag, for example the git commit SHA. Use latest only for tests.
  • To log in to ECR, pipe aws ecr get-login-password into docker login --username AWS --password-stdin.
  • To push to ECR, docker tag the image with the repository URI, then docker push it.
  • Docker cannot use IAM credentials directly. Docker needs an ECR authorization token from get-login-password.
  • An ECR authorization token is valid for 12 hours. After that, pushes and pulls fail until you log in again.
  • One docker login covers all repositories in one registry. Run docker login for each registry.
  • An ECR push needs ecr:GetAuthorizationToken plus the layer upload actions and ecr:PutImage.
  • ecr:GetAuthorizationToken uses the resource *, because the token is for the whole registry.
  • ECR tag immutability stops a tag from moving to a different image.
  • With tag immutability, a push of an existing tag fails with ImageTagAlreadyExistsException.
  • An image digest (sha256:...) always identifies the same image content. Deploy by digest to run an exact image.
  • Lambda runs container images up to 10 GB.
  • A Lambda container image uses an AWS base image or adds the runtime interface client.

Exam signals

  • "Every code change reinstalls all dependencies" → copy and install dependencies before the source code. Docker then reuses the cached install layer.
  • "Image is large and contains compilers" → multi-stage build with a small runtime base image. Only the build output goes into the final image.
  • "A tag must never point to a different image" → ECR tag immutability. ECR then rejects a push that reuses a tag.
  • "Push fails: no basic auth credentials" or "push fails after 12 hours" → run get-login-password and docker login again. Docker has no valid ECR token.

Explanation

Dockerfile practice

  • Layer order: each Dockerfile instruction, for example COPY or RUN, makes a layer. Docker caches the layers and reuses a layer when its inputs did not change.
  • When a layer changes, Docker rebuilds that layer and all layers after it. Put rarely changed steps first.
  • Copy the dependency file (for example, package.json) and install dependencies before you copy the source code. Then a change to the source code does not invalidate the install layer, and Docker reuses the installed dependencies.
  • Multi-stage build: build in a first stage with compilers and tools. Copy only the build output into a small runtime image. The final image then does not contain the compilers, the build tools, or the source code.
  • Use a small base image. A smaller image downloads faster and has fewer packages to attack.
  • Do not put secrets in an image. Anyone who can pull the image can read the files in its layers. Get secrets at run time, for example from Secrets Manager.

Amazon ECS image practice

  • Put all dependencies in the image. Build a new image for each change. Then each task starts with the same complete content, with no installs at start time.
  • Run one application process in each container. The container lives as long as that process runs, and ECS replaces a crashed process.
  • Handle SIGTERM for a clean shutdown. When ECS stops a task, it first sends SIGTERM and later SIGKILL.
  • On SIGTERM, the application must stop taking new work and finish or save the work in progress.
  • Write logs to stdout and stderr. Then the log configuration of the task, not the application code, decides where the logs go. For example, the awslogs log driver sends them to CloudWatch Logs.
  • Tag each build with a unique tag, for example the git commit SHA. Then you can see which code each task runs. The latest tag moves to each new build, so use it only for tests.

Amazon ECR

  • Log in: aws ecr get-login-password --region <region> | docker login --username AWS --password-stdin <account>.dkr.ecr.<region>.amazonaws.com
  • Then docker tag the image with the repository URI and docker push it.
  • Docker cannot use IAM credentials directly. get-login-password gets an ECR authorization token, and docker login stores it for Docker.
  • The authorization token is valid for 12 hours. After that, pushes and pulls fail until you log in again.
  • To use several registries, run docker login for each registry. One login covers all repositories in that registry, because Docker stores the login for the registry URI, not for one repository.
  • To push, the principal needs ecr:GetAuthorizationToken and the layer upload actions: ecr:BatchCheckLayerAvailability, ecr:InitiateLayerUpload, ecr:UploadLayerPart, ecr:CompleteLayerUpload, ecr:PutImage, ecr:BatchGetImage.
  • ecr:GetAuthorizationToken uses the resource *, because the token is for the whole registry, not for one repository.
  • Tag immutability: after you push a tag, no later push can move that tag to a different image. A push of a tag that already exists fails with ImageTagAlreadyExistsException. Use it so that a release tag always means the same image.
  • An image digest (sha256:...) is a hash of the image content, so it always identifies the same image content. Deploy by digest when you must run an exact image, even if a tag moves.

Lambda container images

Lambda runs container images up to 10 GB. Use an AWS base image, or add the runtime interface client to your own image.

The runtime interface client is the library that gets invocation events from Lambda and passes them to your code. Module 1 covers this in topic lambda-packaging.

Amazon EKS basics

Remember

  • Amazon EKS manages the Kubernetes control plane. You run the workloads on EC2 nodes or on Fargate.
  • A Pod is one or more containers that run together.
  • A Deployment keeps a set number of Pod replicas running.
  • A Service gives a stable network endpoint for a set of Pods. Clients call the Service, not a Pod.
  • Choose EKS when the team uses Kubernetes tools (kubectl, Helm, manifests) or needs Kubernetes portability.
  • Choose ECS for a simpler, AWS native orchestrator with less cluster management.
  • EKS Pod Identity and IRSA both map a Kubernetes service account to an IAM role.
  • EKS Pod Identity needs the EKS Pod Identity Agent add-on and an association of a role to a namespace and service account.
  • An EKS Pod Identity role trusts pods.eks.amazonaws.com. The role then works in new clusters with no trust policy change.
  • IRSA needs an IAM OIDC provider for each cluster and a service account annotation with the role ARN.
  • An IRSA role trusts the OIDC provider of each cluster, with sts:AssumeRoleWithWebIdentity.
  • AWS recommends EKS Pod Identity when possible.
  • EKS Pod Identity does not support Fargate Pods. EKS Pod Identity works only on Amazon EKS with Linux EC2 nodes.
  • Choose IRSA for Pods on Fargate, or for Kubernetes on AWS that is not Amazon EKS.
  • With unrestricted IMDS on a node, every Pod on the node gets the node IAM role credentials.
  • To restrict IMDS on EKS nodes, require IMDSv2 and set the PUT response hop limit to 1.
  • Pod Identity and IRSA credentials do not come from IMDS, so Pod roles keep working with hop limit 1.
  • Do not disable IMDS on EKS nodes. Node components, for example the node termination handler, need it.
  • Fargate Pods cannot use IMDS.
  • Containers cannot use the Fargate Pod execution role. Give Fargate containers a role with IRSA.

Exam signals

  • "Each Pod gets its own permissions; no OIDC provider" → EKS Pod Identity. Only IRSA needs an OIDC provider.
  • "Pods on Fargate need AWS permissions" → IRSA. EKS Pod Identity does not support Fargate.
  • "Pods use the node role; stop that" → require IMDSv2 with hop limit 1 on the nodes, and give Pods their own role. The token response then cannot reach the Pods.
  • "Team already uses Kubernetes manifests and Helm" → EKS. It runs standard Kubernetes, and the team keeps its tools.

Explanation

Concepts

  • Amazon EKS runs and manages the Kubernetes control plane for you. You run the workloads on EC2 nodes or on AWS Fargate.
  • The control plane is the Kubernetes API server and the components that schedule Pods and store the cluster state.
  • A Pod is one or more containers that run together.
  • A Deployment keeps a set number of Pod replicas running.
  • A Service gives a stable network endpoint for a set of Pods. Pods get new IP addresses when they are replaced, so clients call the Service, not a Pod.

Choose EKS or ECS

  • Choose EKS when the team uses Kubernetes tools (kubectl, Helm, manifests) or needs Kubernetes portability across environments.
  • Choose ECS for a simpler, AWS native orchestrator with less cluster management.

Resource sizing and usage

Remember

  • For Lambda, you set memory only. CPU grows with memory.
  • For ECS on Fargate, task-level CPU and memory are required. Only some CPU and memory pairs are valid.
  • A Fargate task definition with an invalid CPU and memory pair fails to register.
  • Fargate CPU is in units: 1024 units = 1 vCPU.
  • Fargate 256 CPU (0.25 vCPU) allows 512 MiB, 1 GB, or 2 GB of memory.
  • Fargate 512 CPU allows 1 to 4 GB. Fargate 1024 CPU allows 2 to 8 GB.
  • Fargate 2048 CPU allows 4 to 16 GB. Fargate 4096 CPU allows 8 to 30 GB. Both use 1 GB steps.
  • Fargate 8192 CPU allows 16 to 60 GB, in 4 GB steps (Linux platform 1.4.0 or later).
  • Fargate 16384 CPU allows 32 to 120 GB, in 8 GB steps (Linux platform 1.4.0 or later).
  • For EC2, you choose the instance type. The family sets the ratio of vCPU to memory.
  • EC2 families: M is general purpose, C is compute optimized, R is memory optimized, T is burstable.
  • Choose the EC2 family that matches the resource that limits your application.
  • A burstable instance earns CPU credits below a baseline and spends them during peaks.
  • To find the minimum size, run a load test at the expected peak. Measure CPU, memory, and latency or duration.
  • EC2 does not send memory metrics by default. Install the CloudWatch agent to collect memory use.
  • Choose the smallest size that meets the latency goal and still has spare capacity for peaks.
  • AWS Compute Optimizer gives rightsizing recommendations. You must opt in first.
  • Compute Optimizer covers EC2, Auto Scaling groups, EBS volumes, Lambda functions, ECS services on Fargate, and more.
  • Compute Optimizer analyzes the last 14 days of metrics by default.
  • Compute Optimizer enhanced infrastructure metrics (paid) extends the lookback period to 93 days.
  • Compute Optimizer rightsizing preferences allow a free 32-day lookback, which includes a monthly peak.
  • For Compute Optimizer EC2 memory recommendations, install the CloudWatch agent on the instances.
  • Scale on the metric that limits the application.
  • For a web tier behind an ALB, ALBRequestCountPerTarget can be a better scaling signal than CPU.

Exam signals

  • "Fargate task definition fails: invalid CPU or memory" → use a valid task CPU and memory pair. Fargate accepts only the pairs in the table.
  • "Rightsizing recommendations with the least effort" → AWS Compute Optimizer. It analyzes the metrics and recommends sizes for you.
  • "Recommendations ignore memory" → install the CloudWatch agent. EC2 does not publish memory metrics by default.
  • "Monthly peak is outside the analysis window" → 32-day lookback (free) or enhanced infrastructure metrics (93 days, paid). The default 14 days can miss the peak.

  • Run a load test at the expected peak. Measure CPU, memory, and latency or duration.
  • EC2 does not send memory metrics by default. Install the CloudWatch agent to collect memory use. Without memory data, you can choose a size that has too little memory.
  • Choose the smallest size that meets the latency goal and still has spare capacity for peaks.

Optimize resource usage (skill 4.3.7)

  • AWS Compute Optimizer gives rightsizing recommendations. Rightsizing means changing a resource to the smallest size that still meets the needs of the workload.
  • You must opt in to Compute Optimizer first. Compute Optimizer makes no recommendations before you opt in.
  • It covers EC2 instances, Auto Scaling groups, EBS volumes, Lambda functions, ECS services on Fargate, and more.
  • It analyzes the last 14 days of metrics by default. Enhanced infrastructure metrics is a paid Compute Optimizer option that extends the lookback period to 93 days.
  • A 14-day window can miss a peak that comes once a month. Rightsizing preferences also allow a free 32-day lookback, which includes a full monthly cycle.
  • For EC2 memory recommendations, install the CloudWatch agent on the instances.
  • Scale on the metric that limits the application.
  • For a web tier behind an ALB, request count for each target (ALBRequestCountPerTarget) can be a better signal than CPU. For example, an application that waits on I/O can be overloaded while its CPU stays low.
