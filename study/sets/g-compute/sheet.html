EC2 for developers

User data

  • User data passes a shell script or cloud-init directives to an instance at launch.
  • By default, user data runs only during the first boot cycle of the instance.
  • On Linux, the script runs as the root user. Do not use sudo in the script.
  • The script must not need user input. For example, use yum update -y.
  • To find script errors, read /var/log/cloud-init-output.log on the instance.
  • To change user data, stop the instance first. When you start it again, the new script does not run by default.
  • If the script calls AWS APIs, attach an instance profile (IAM role). Do not put access keys in the script.
  • Any process on the instance can read user data from the instance metadata service. Do not put secrets in user data.

Instance metadata service (IMDS)

  • IMDS is at 169.254.169.254. The AWS SDKs get instance profile credentials from IMDS.
  • IMDSv1 is request and response. IMDSv2 uses a session token.
  • IMDSv2 step 1: send a PUT to /latest/api/token with the header X-aws-ec2-metadata-token-ttl-seconds.
  • IMDSv2 step 2: send each GET with the header X-aws-ec2-metadata-token.
  • To require IMDSv2, set HttpTokens to required (--http-tokens required). Then IMDSv1 calls fail.
  • When IMDSv2 is required, a request without a valid token gets 401 - Unauthorized.
  • IMDS rejects a token PUT that has an X-Forwarded-For header. The session token adds protection against SSRF and open reverse proxies.
  • The token works only on the instance that created it.
  • The MetadataNoToken CloudWatch metric counts IMDSv1 calls. Use it before you require IMDSv2.

Shell access with Session Manager

  • Session Manager (AWS Systems Manager) gives shell access with no open inbound ports, no bastion hosts, and no SSH keys.
  • IAM policies control who can start a session on which instance.
  • You can log session data to Amazon S3 or CloudWatch Logs. CloudTrail records the Session Manager API calls.
  • The instance needs SSM Agent and an instance profile with the needed permissions. AmazonSSMManagedInstanceCore gives them.
  • The instance needs outbound HTTPS (port 443) to the ssm, ssmmessages, and ec2messages endpoints.
  • For a private subnet with no internet access, create interface VPC endpoints for these three services.

Exam signals

  • "Protect instance credentials from SSRF" → require IMDSv2 (HttpTokens required).
  • "After IMDSv2 was required, the script gets 401" → get a token with PUT, then send it in the header.
  • "Container on EC2 cannot get IMDSv2 credentials" → set the PUT response hop limit to 2.
  • "Shell access, no port 22, no bastion, audit the sessions" → Session Manager with session logging.
  • "User data script did not work" → read /var/log/cloud-init-output.log.

Elastic Load Balancing

  • An ALB needs subnets in at least two Availability Zones.
  • A target group with type lambda holds one Lambda function.
  • Cross-zone load balancing is always on for an ALB at the load balancer level. You can turn it off for a target group.

Target group attributes

AttributeDefaultRange
Deregistration delay300 seconds0 to 3,600 seconds

Stickiness duration (lb_cookie or app_cookie)1 day1 second to 7 days

  • Deregistration delay: the target is draining. The ALB sends no new requests to it, and in-flight requests can complete.
  • Sticky sessions: duration-based stickiness uses the ALB cookie AWSALB. Application-based stickiness follows a cookie that your application sets.
  • Sticky sessions do not work when cross-zone load balancing is off. Weighted random does not work with sticky sessions.
  • Sticky sessions are a fast fix for in-memory sessions. A shared session store (for example, ElastiCache or DynamoDB) is the better design.

Client information

  • The target sees the ALB IP address as the source. The ALB puts the client IP address in X-Forwarded-For.
  • Default XFF mode is append. The ALB adds the client IP address to the end of an existing header.
  • X-Forwarded-Proto holds the client protocol (HTTP or HTTPS). X-Forwarded-Port holds the client destination port.

HTTP errors that the ALB makes

503 Service UnavailableThe target group has no registered targets, or all targets are in the unused state.
504 Gateway TimeoutNo connection to the target within 10 seconds. Target did not respond before the idle timeout. Network ACL blocks ephemeral ports.

Exam signals

  • "Route /api and /images to different services" or "route by host name" → ALB listener rules.
  • "Static IP addresses for an allow list" or "TCP or UDP, extreme throughput" → NLB.
  • "Application logs show the load balancer IP, not the client" → read X-Forwarded-For.
  • "Users lose their session; sessions are in memory; fewest code changes" → sticky sessions.
  • "502 errors during deployments for long requests" → increase the deregistration delay.
  • "504 errors for slow requests" → target response time is above the idle timeout.

EC2 Auto Scaling health checks

  • By default, Auto Scaling uses only EC2 status checks. They do not see application failures.
  • Turn on Elastic Load Balancing health checks for the group. Then Auto Scaling replaces instances that fail the target group health check.
  • Health check grace period: 300 seconds by default in the console. 0 seconds by default with the AWS CLI or an SDK.

  • The command starts with CMD or CMD-SHELL. Exit code 0 means healthy.
  • ECS monitors only the health check in the task definition. It ignores a HEALTHCHECK in the image.
  • In a service, ECS stops an unhealthy task and starts a replacement.
  • healthCheckGracePeriodSeconds on the service: the scheduler ignores unhealthy ELB, VPC Lattice, and container health checks after a task starts. Default 0.

Kubernetes probes (Amazon EKS)

ProbePurposeOn failure
LivenessFind a stuck process, for example a deadlockThe kubelet restarts the container.
ReadinessFind out if the container can take trafficThe Pod is removed from Service endpoints. No restart.
StartupGive a slow application time to startThe kubelet kills the container. Liveness and readiness probes wait until the startup probe succeeds.
  • Probe types: httpGet (200 to 399 is success), tcpSocket, exec (exit code 0), grpc.
  • Do not check external dependencies in a liveness probe. A database outage then restarts every Pod. Put dependency checks in the readiness probe.

Shallow and deep health checks

  • A shallow check confirms that the process answers. Use it for liveness and restart decisions.
  • A deep check also tests dependencies. It can remove all targets when one shared dependency fails.

Route 53 health checks

  • Three types: monitor an endpoint, monitor other health checks (calculated), or monitor a CloudWatch alarm.
  • HTTP and HTTPS endpoint checks need a 2xx or 3xx status code. String matching searches the first 5,120 bytes of the body.
  • Request interval: 30 seconds (standard) or 10 seconds (fast, extra cost).
  • Route 53 cannot check endpoints with private IP addresses. For a private resource, use a health check that monitors a CloudWatch alarm.

Exam signals

  • "Targets unhealthy, ResponseCodeMismatch, app redirects" → health check path that returns 200.
  • "Targets unhealthy with Target.Timeout, app works locally" → security group does not allow the health check port.
  • "Slow-starting tasks are killed in a loop" → ECS healthCheckGracePeriodSeconds.
  • "Crashed application stays in service in the Auto Scaling group" → turn on ELB health checks for the group.
  • "Database outage restarts all Pods" → move the dependency check from liveness to readiness.
  • "Route 53 failover for a resource with a private IP address" → CloudWatch alarm health check.

Container images

Dockerfile practice

  • Layer order: when a layer changes, Docker rebuilds that layer and all layers after it. Put rarely changed steps first.
  • Copy the dependency file (for example, package.json) and install dependencies before you copy the source code.
  • Multi-stage build: build in a first stage with compilers and tools. Copy only the build output into a small runtime image.
  • Use a small base image. A smaller image downloads faster and has fewer packages to attack.
  • Do not put secrets in an image. Get them at run time, for example from Secrets Manager.

Amazon ECS image practice

  • Put all dependencies in the image. Build a new image for each change.
  • Run one application process in each container. Handle SIGTERM for a clean shutdown.
  • Write logs to stdout and stderr.
  • Tag each build with a unique tag, for example the git commit SHA. Use latest only for tests.

Amazon ECR

  • Log in: aws ecr get-login-password --region <region> | docker login --username AWS --password-stdin <account>.dkr.ecr.<region>.amazonaws.com
  • Then docker tag the image with the repository URI and docker push it.
  • The authorization token is valid for 12 hours. Get a new token for each registry.
  • To push, the principal needs ecr:GetAuthorizationToken and the layer upload actions: ecr:BatchCheckLayerAvailability, ecr:InitiateLayerUpload, ecr:UploadLayerPart, ecr:CompleteLayerUpload, ecr:PutImage, ecr:BatchGetImage. ecr:GetAuthorizationToken uses the resource *.
  • Tag immutability: a push of a tag that already exists fails with ImageTagAlreadyExistsException.
  • An image digest (sha256:...) always identifies the same image content.

Lambda container images

Lambda runs container images up to 10 GB. Use an AWS base image, or add the runtime interface client to your own image. Module 1 covers this in topic lambda-packaging.

Exam signals

  • "Every code change reinstalls all dependencies" → copy and install dependencies before the source code.
  • "Image is large and contains compilers" → multi-stage build with a small runtime base image.
  • "A tag must never point to a different image" → ECR tag immutability.
  • "Push fails: no basic auth credentials" or "push fails after 12 hours" → run get-login-password and docker login again.

References: Push an image to ECR (12-hour token), ECR tag immutability, ECR push permissions, ECS container image best practices, Docker multi-stage builds, Docker build cache.

Amazon EKS basics

Concepts

  • Amazon EKS runs and manages the Kubernetes control plane for you. You run the workloads on EC2 nodes or on AWS Fargate.
  • A Pod is one or more containers that run together. A Deployment keeps a set number of Pod replicas running.
  • A Service gives a stable network endpoint for a set of Pods.

Choose EKS or ECS

  • Choose EKS when the team uses Kubernetes tools (kubectl, Helm, manifests) or needs Kubernetes portability across environments.
  • Choose ECS for a simpler, AWS native orchestrator with less cluster management.

Exam signals

  • "Each Pod gets its own permissions; no OIDC provider" → EKS Pod Identity.
  • "Pods on Fargate need AWS permissions" → IRSA.
  • "Pods use the node role; stop that" → restrict IMDS on the nodes and give Pods their own role.
  • "Team already uses Kubernetes manifests and Helm" → EKS.

Find the minimum size (skill 4.3.3)

  • Run a load test at the expected peak. Measure CPU, memory, and latency or duration.
  • EC2 does not send memory metrics by default. Install the CloudWatch agent to collect memory use.
  • Choose the smallest size that meets the latency goal with some headroom.

Optimize resource usage (skill 4.3.7)

  • AWS Compute Optimizer gives rightsizing recommendations. You must opt in first.
  • It covers EC2 instances, Auto Scaling groups, EBS volumes, Lambda functions, ECS services on Fargate, and more.
  • It analyzes the last 14 days of metrics by default. Enhanced infrastructure metrics (paid) extend this to 93 days.
  • For EC2 memory recommendations, install the CloudWatch agent on the instances.
  • Scale on the metric that limits the application. For a web tier behind an ALB, request count for each target can be a better signal than CPU.

Exam signals

  • "Fargate task definition fails: invalid CPU or memory" → use a valid task CPU and memory pair.
  • "Rightsizing recommendations with the least effort" → AWS Compute Optimizer.
  • "Recommendations ignore memory" → install the CloudWatch agent.
  • "Monthly peak is outside the analysis window" → enhanced infrastructure metrics (93 days).

References: Fargate task CPU and memory, What is Compute Optimizer?, Metrics analyzed (14 and 93 days), EC2 memory with the CloudWatch agent.
