SQS standard and FIFO queues

Remember

  • Use Amazon SQS to decouple a producer from a consumer. The consumer pulls work at its own speed.
  • Use an SQS FIFO queue for strict order and no duplicates in a group of related messages.
  • Use Amazon SNS to send one message to many subscribers (push).
  • Use Amazon EventBridge to route events by content, receive AWS service events, or connect SaaS partners.
  • Use Kinesis Data Streams for an ordered, replayable stream that many consumers read at the same time.
  • Use Amazon Data Firehose to load streaming data into Amazon S3, Amazon Redshift, or OpenSearch with no consumer code.
  • Use AWS AppSync for a GraphQL API with real-time subscriptions.
  • A standard queue gives best-effort order and at-least-once delivery, so duplicates can occur.
  • A standard queue supports nearly unlimited API calls each second.
  • Standard queue consumers must be idempotent, because a message can arrive more than one time.
  • Choose a standard queue for the most throughput when the consumer can handle duplicates and a changed order.
  • A FIFO queue keeps strict order inside each MessageGroupId.
  • A FIFO queue name must end in .fifo.
  • A FIFO queue requires a MessageGroupId on every message.
  • Choose a FIFO queue when the order of related messages matters or when a duplicate causes harm.
  • A FIFO queue allows 300 transactions each second for each API action, for the whole queue, not for each group.
  • A FIFO queue with batches of 10 messages handles 3,000 messages each second.
  • Batch API calls (SendMessageBatch, DeleteMessageBatch) take a maximum of 10 messages.
  • FIFO high throughput mode is a queue setting. Its limit depends on the Region, for example 70,000 transactions each second without batching in us-east-1.
  • A FIFO queue does not support a per-message delay (message timer). Use a queue-level delay.
  • A FIFO queue does not deliver a second message with the same deduplication ID in the 5-minute deduplication interval.
  • A FIFO queue needs a MessageDeduplicationId or content-based deduplication. Without either, SendMessage fails.
  • Content-based deduplication uses a SHA-256 hash of the message body, not the message attributes.
  • Send your own MessageDeduplicationId when identical bodies must count as different messages, or different bodies as one message.
  • SQS tracks a deduplication ID until the 5-minute interval ends, also after the message is deleted.
  • A FIFO queue does not deliver the next message of a group while an earlier message of that group is in flight.
  • One slow message in a FIFO queue blocks all later messages of its group.
  • The number of active MessageGroupId values limits how many FIFO consumers can work at the same time.
  • On a standard queue, a MessageGroupId turns on fair queues and identifies a tenant.
  • Fair queues deliver the messages of other tenants first when one tenant makes a backlog.
  • Fair queues do not give order on a standard queue.

Exam signals

  • "Process each customer's orders in order, but process different customers in parallel" → FIFO queue, MessageGroupId = customer ID. Order is kept inside a group, and different groups are processed at the same time.
  • "Producer retries can send the same order twice; process it one time" → FIFO queue with deduplication. SQS does not deliver a second message with the same deduplication ID in the 5-minute interval.
  • "Messages have a timestamp in the body, but repeats must be removed" → explicit MessageDeduplicationId, not content-based deduplication. The timestamp makes each body different, so the body hash is different and SQS does not see a duplicate.
  • "Highest throughput, order not important" → standard queue with idempotent consumers. A standard queue has nearly unlimited throughput, and idempotent consumers make the duplicates harmless.

"Best effort" order means that SQS usually delivers messages in the order they were sent, but some messages can arrive out of order. "At least once" means that SQS can deliver a copy of a message a second time.

Choose a standard queue when you need the most throughput and your consumer can handle duplicates and a changed order.

Choose a FIFO queue when the order of related messages matters, for example the steps of one order. Also choose it when a duplicate causes harm, for example a second payment.

Fair queues: on a standard queue, the MessageGroupId identifies a tenant, for example a customer. One tenant can send a large burst and make a backlog.

SQS then delivers the messages of the other tenants first, so that their messages do not wait. The MessageGroupId does not give order on a standard queue.

Key facts

  • Standard queue consumers must be idempotent, because a message can arrive more than one time. Idempotent means that processing the same message two times gives the same result as one time.
  • Example: before the consumer charges a card, it checks whether it already processed that order ID. Without this check, a duplicate message charges the customer two times.
  • FIFO deduplication: SQS needs a deduplication ID for every message. Send a MessageDeduplicationId, or turn on content-based deduplication so that SQS makes the ID for you. If you do neither, SendMessage fails with an error.
  • If a second message with the same deduplication ID arrives in the 5-minute interval, SQS accepts the send call but does not deliver the second message. So a producer can safely retry a send that timed out.
  • Content-based deduplication uses a SHA-256 hash of the message body. It does not use the message attributes.
  • Send your own MessageDeduplicationId when identical bodies must count as different messages, or different bodies must count as one message.
  • SQS continues to track a deduplication ID after the message is deleted, until the 5-minute interval ends.
  • In a FIFO queue, the next message of a group is not available while an earlier message of that group is in flight. "In flight" means that a consumer received the message but did not delete it yet.
  • SQS holds the rest of the group so that the group stays in order. One slow message therefore blocks all later messages of its group.
  • To get more parallel processing from a FIFO queue, use many different MessageGroupId values. Only one consumer at a time can hold messages of a group, so the number of active groups limits how many consumers can work at the same time.
  • High throughput mode for FIFO queues is set on the queue. Turn it on when 300 transactions each second for each API action is not enough. Its limit depends on the Region (for example, up to 70,000 transactions each second without batching in US East (N. Virginia)).
  • Batch API calls (SendMessageBatch, DeleteMessageBatch) take a maximum of 10 messages.

SQS visibility timeout, polling, delay, and Lambda consumers

Remember

  • The visibility timeout has a default of 30 seconds and a range of 0 seconds to 12 hours.
  • SQS message retention has a default of 4 days and a range of 60 seconds to 14 days.
  • An SQS delay (queue delay or message timer) has a default of 0 seconds and a maximum of 15 minutes.
  • The long polling wait time has a default of 0 (short polling) and a maximum of 20 seconds.
  • The SQS message size limit is 1 MiB (1,048,576 bytes). Older study material says 256 KB.
  • The SQS Extended Client Library stores payloads up to 2 GB in Amazon S3 (Java and Python libraries).
  • One SQS message can have a maximum of 10 message attributes.
  • A standard queue allows about 120,000 in-flight messages (received but not deleted).
  • At the in-flight limit, a short-poll ReceiveMessage returns an OverLimit error, and a long poll returns no new messages.
  • A received message stays in the queue, but other consumers cannot see it for the visibility timeout.
  • The consumer must call DeleteMessage before the visibility timeout ends, or the message becomes visible again.
  • Use ChangeMessageVisibility at intervals (a heartbeat) to extend the visibility timeout for a long task.
  • The 12-hour visibility timeout maximum counts from the first receive.
  • Set the visibility timeout to 0 with ChangeMessageVisibility to release a message to other consumers at once.
  • For a Lambda event source mapping, set the visibility timeout to at least 6 times the function timeout.
  • Lambda rejects an SQS mapping if the function timeout is more than the visibility timeout.
  • Short polling (default) asks only a subset of servers and can return a "false empty" response.
  • SQS bills each empty receive response as a request.
  • Long polling asks all servers and waits for a message, so it reduces empty responses and cost.
  • The queue attribute ReceiveMessageWaitTimeSeconds turns on long polling for all receives with no consumer code change.
  • WaitTimeSeconds on one ReceiveMessage call overrides the queue attribute for that call.
  • A delay hides a message when it is added to the queue. A visibility timeout hides a message after it is received.
  • Use a delay queue when every new message must wait. Use a message timer when only some messages must wait.
  • A message timer (DelaySeconds on one message) overrides the queue delay.
  • For delays longer than 15 minutes, use EventBridge Scheduler.
  • By default, when a Lambda function returns an error, all messages of the SQS batch return to the queue.
  • Set FunctionResponseTypes to ReportBatchItemFailures so that only the failed messages return to the queue.
  • With partial batch response, the function returns the failed message IDs in batchItemFailures.
  • Event source mapping filter criteria use EventBridge pattern syntax on the message body or the record metadata.
  • An event source mapping allows 5 filters by default, with a quota increase to 10.
  • For SQS, Lambda deletes the messages that do not match the filter, so no other consumer can read them.
  • The batching window (MaximumBatchingWindowInSeconds) is the time Lambda waits to fill a batch.
  • For a standard queue batch size over 10, the batching window must be at least 1 second.
  • With a batching window, set the visibility timeout to 6 times the function timeout plus the batching window.

Exam signals

  • "Many empty ReceiveMessage responses, high cost" → long polling (ReceiveMessageWaitTimeSeconds = 20). Each receive waits for messages, so there are fewer empty, billable responses.
  • "Processing sometimes takes longer than the visibility timeout, and messages are processed twice" → increase the visibility timeout or call ChangeMessageVisibility. The message then stays hidden until the first consumer deletes it.
  • "Payload is 5 MB" → SQS Extended Client Library with Amazon S3. The SQS message limit is 1 MiB, so the library stores the payload in S3 and sends a reference.
  • "Every new message must wait 5 minutes before processing" → delay queue. The queue delay hides every new message for the set time (maximum 15 minutes).
  • "One bad message makes the whole batch run again" → ReportBatchItemFailures. Only the failed messages return to the queue.
  • "Function must not be invoked for messages it does not need" → filter criteria on the event source mapping. Lambda checks the filter before it invokes the function.

In-flight messages are messages that consumers received but did not delete yet.

When a standard queue reaches the in-flight limit, a short-poll ReceiveMessage returns an OverLimit error. A long poll returns no new messages. This continues until consumers delete messages or messages become visible again.

Visibility timeout

  • A received message stays in the queue, but other consumers cannot see it for the visibility timeout. This stops two consumers from processing the same message at the same time.
  • The consumer must call DeleteMessage before the timeout ends. If it does not, the message becomes visible again and another consumer can process it.
  • Use ChangeMessageVisibility to extend the timeout for a long task. Call it at intervals while the task runs (a heartbeat). The 12-hour maximum counts from the first receive.
  • Set the visibility timeout to 0 with ChangeMessageVisibility to release a message at once. Use this when a consumer knows that it cannot process the message, for example during a shutdown. Another consumer can then take the message now, not after the timeout ends.
  • With a Lambda event source mapping, set the visibility timeout to at least 6 times the function timeout. The extra time lets Lambda retry the batch if the function is throttled.
  • If the timeout is too short, messages become visible again while Lambda still works on them, and they are processed two times.
  • Lambda rejects a mapping if the function timeout is more than the visibility timeout. See the Module 1 sheet for more Lambda details.

Short and long polling

  • SQS stores the messages of a queue on many servers.
  • Short polling (default) asks only a subset of those servers and returns at once. It can return an empty response even when messages exist on the other servers (a "false empty" response). SQS bills each empty response as a request.
  • Long polling asks all servers and waits until a message arrives or the wait time ends. It reduces empty and false empty responses, so it reduces cost.
  • Turn on long polling for all receives with the queue attribute ReceiveMessageWaitTimeSeconds. This needs no code change in the consumers. Or set WaitTimeSeconds on one ReceiveMessage call, which overrides the queue attribute for that call.

Delay queues and message timers

  • A delay hides a message when it is added to the queue. A visibility timeout hides a message after it is received.
  • Use a queue delay (a delay queue) when every new message must wait before consumers can see it. Use a message timer when only some messages need a wait.
  • A message timer (DelaySeconds on one message) overrides the queue delay. FIFO queues do not support message timers.
  • For delays longer than 15 minutes, use EventBridge Scheduler. 15 minutes is the maximum SQS delay.

Lambda consumers (event source mapping)

  • By default, if the function returns an error, Lambda deletes no message from the batch. All messages in the batch become visible again after the visibility timeout.
  • The messages that succeeded are then processed again, so their side effects (for example, an email) happen again.
  • Partial batch response: set FunctionResponseTypes to ReportBatchItemFailures. The function returns the failed message IDs in batchItemFailures; only those messages return to the queue.
  • Filter criteria on the event source mapping use EventBridge pattern syntax. Filter on the message body or on the metadata fields of the record.
  • Use filters so that you do not invoke, and pay for, the function for messages that it ignores. Up to 5 filters by default (quota increase to 10).
  • For SQS, Lambda deletes messages that do not match the filter. The function is not invoked for them. No other consumer can read those messages, so do not filter out messages that another process needs.
  • Batching window (MaximumBatchingWindowInSeconds): Lambda waits up to this time to fill a batch. For a batch size over 10 (standard queue), you must set it to at least 1 second.
  • Messages stay in flight while Lambda waits. So set the visibility timeout to 6 times the function timeout plus the batching window.

SQS dead-letter queues and redrive

Remember

  • A dead-letter queue (DLQ) holds messages that consumers fail to process many times.
  • Without a DLQ, a poison message returns after each visibility timeout until its retention period ends.
  • Set the redrive policy on the source queue. The policy names the DLQ ARN and maxReceiveCount.
  • maxReceiveCount is the number of receives before SQS moves a message to the DLQ.
  • maxReceiveCount has a range of 1 to 1,000 and no default.
  • A very low maxReceiveCount moves a message to the DLQ after one temporary error.
  • With a Lambda consumer, AWS recommends a maxReceiveCount of at least 5.
  • The DLQ type must match the source queue type: FIFO uses a FIFO DLQ, and standard uses a standard DLQ.
  • The DLQ must be in the same AWS account and Region as the source queue.
  • SQS does not create the DLQ. Create the DLQ first as an ordinary queue.
  • A message moved from a standard queue keeps its original enqueue timestamp, so source time counts against DLQ retention.
  • Set the DLQ retention longer than the source queue retention.
  • A message moved from a FIFO queue gets a new enqueue timestamp in the DLQ.
  • A DLQ can break the exact order of a FIFO queue. Do not use a DLQ if the order of every message is critical.
  • SQS does not notify you when a message arrives in a DLQ.
  • Alarm on the DLQ metric ApproximateNumberOfMessagesVisible.
  • The NumberOfMessagesSent metric does not count messages that SQS moves to a DLQ.
  • The redrive allow policy is on the DLQ and sets redrivePermission.
  • redrivePermission allowAll is the default and lets any source queue use the DLQ.
  • redrivePermission byQueue allows only the listed source queue ARNs (up to 10). Use it when one team owns the DLQ.
  • redrivePermission denyAll stops the queue from being a DLQ.
  • DLQ redrive (StartMessageMoveTask) moves messages out of a DLQ so that consumers process them again.
  • StartMessageMoveTask with no destination moves messages back to their original source queues.
  • DLQ redrive works only on a DLQ of SQS queues, not on a DLQ of a Lambda function or SNS subscription.
  • A queue can have one active move task, with an optional rate of up to 500 messages each second.
  • Use ListMessageMoveTasks to see move progress and CancelMessageMoveTask to stop a move.
  • Configure the DLQ at the place where the failed step happens.
  • For an SQS consumer, including a Lambda event source mapping, put the redrive policy on the source queue.
  • For an asynchronous Lambda invocation, use a Lambda on-failure destination or a function DLQ.
  • For SNS delivery failures, put the redrive policy on the SNS subscription.
  • For EventBridge delivery failures, put the DLQ on the rule target.

Exam signals

  • "Poison message is retried forever" → redrive policy with a DLQ and maxReceiveCount. After that number of receives, SQS moves the message out of the source queue.
  • "Bug is fixed; reprocess the failed messages with the least effort" → DLQ redrive (StartMessageMoveTask). It moves the messages back with no code.
  • "Messages expire in the DLQ sooner than expected" → increase the DLQ retention. A standard queue keeps the original timestamp.
  • "Only one team's queue may use this DLQ" → redrive allow policy byQueue.

Explanation

Key facts

  • A dead-letter queue (DLQ) holds messages that consumers fail to process many times.
  • Without a DLQ, a message that always fails (a "poison message") returns to the queue after each visibility timeout. It is received again and again until its retention period ends, and it uses consumer capacity each time.
  • Set the redrive policy on the source queue. It names the dead-letter queue (DLQ) ARN and maxReceiveCount.
  • maxReceiveCount (1 to 1,000) is how many times a consumer can receive a message before SQS moves it to the DLQ. There is no default; you set it. A very low value moves a message to the DLQ after one temporary error.
  • With Lambda, AWS recommends maxReceiveCount of at least 5. This gives Lambda a few retries (for example, after throttling) before SQS moves the message to the DLQ.
  • The DLQ type must match the source: a FIFO queue uses a FIFO DLQ, and a standard queue uses a standard DLQ. A redrive policy that points to the wrong type fails.
  • The DLQ must be in the same AWS account and Region as the source queue.
  • SQS does not create the DLQ for you. Create it first. A DLQ is an ordinary queue.
  • Standard queues: a moved message keeps its original enqueue timestamp. The time in the source queue counts against the DLQ retention.
  • Example: both queues keep messages for 4 days, and a message waits 3 days in the source. It then expires after only 1 day in the DLQ.
  • Set the DLQ retention longer than the source retention.
  • FIFO queues: the enqueue timestamp resets when the message moves to the DLQ.
  • A DLQ can break the exact order of a FIFO queue. SQS moves the failed message out, and consumers then process the later messages of its group. Do not use a DLQ if the order of every message is critical.
  • Alarm on the DLQ metric ApproximateNumberOfMessagesVisible. SQS does not notify you when a message arrives in a DLQ. Do not use NumberOfMessagesSent, because it does not count messages that SQS moves to a DLQ.

DLQ redrive

  • "Redrive" means to move messages out of a DLQ so that consumers process them again, usually after you fix a bug.
  • StartMessageMoveTask moves messages from a DLQ to another queue. If you do not give a destination, messages go back to their original source queues.

SQS and SNS access policies and encryption

Remember

  • A queue policy controls who can call SQS actions on the queue.
  • A topic policy controls who can call SNS actions, such as sns:Publish, on the topic.
  • For SNS to deliver to a queue, the queue policy must allow sns.amazonaws.com to call sqs:SendMessage.
  • Add an aws:SourceArn condition (or aws:SourceAccount) to prevent the confused deputy problem.
  • A queue policy without aws:SourceArn trusts SNS for any topic, also a topic in another account.
  • For EventBridge to deliver to a queue, allow events.amazonaws.com with an aws:SourceArn of the rule.
  • Cross-account access needs the other account as a principal in the resource policy and IAM permissions in that account.
  • Use IAM identity policies for your own users and roles. Example: sqs:ReceiveMessage and sqs:DeleteMessage for a consumer.
  • SQS encryption at rest uses SSE-SQS (keys that SQS manages) or SSE-KMS (an AWS KMS key).
  • Choose SSE-SQS when you need only encryption at rest, with no key to manage.
  • Choose SSE-KMS with a customer managed key to control the key policy or to see each key use in CloudTrail.
  • SQS SSE encrypts only the message body, not queue metadata, message metadata, or message attributes.
  • Do not put sensitive data in SQS message attributes.
  • SQS encrypts only messages sent after you turn on SSE. Messages already in the queue stay unencrypted.
  • All requests to an SSE queue must use HTTPS and SigV4. Other requests fail with InvalidSecurity.
  • The SQS data key reuse period has a range of 60 seconds to 24 hours and a default of 5 minutes.
  • A longer data key reuse period gives fewer KMS calls and lower KMS cost.
  • With SSE-KMS, a producer needs kms:GenerateDataKey and kms:Decrypt.
  • With SSE-KMS, a consumer needs kms:Decrypt. A Lambda function that reads an encrypted queue also needs kms:Decrypt.
  • Missing KMS permissions make the SQS call fail with KmsAccessDenied.
  • SNS topics support SSE with AWS KMS keys.
  • SNS data in transit uses TLS.
  • For SNS to send to an encrypted queue, use a customer managed KMS key on the queue.
  • The queue key policy must allow sns.amazonaws.com to use kms:GenerateDataKey* and kms:Decrypt.
  • SNS cannot send to a queue encrypted with aws/sqs, because you cannot edit the key policy of that AWS managed key.
  • An encrypted queue that is an SNS subscription DLQ also needs a customer managed key.
  • A queue encrypted with aws/sqs cannot invoke a Lambda function in a different account.

Exam signals

  • "SNS subscription is confirmed but the queue gets no messages" → queue policy does not allow sns.amazonaws.com, or the KMS key policy does not allow SNS. A confirmed subscription does not give SNS permission to send to the queue or to use its key.
  • "Only this topic may send to the queue" → aws:SourceArn condition in the queue policy.
  • "Encrypt messages and audit key use in CloudTrail" → SSE-KMS with a customer managed key. KMS logs each use of a customer managed key in CloudTrail, but SSE-SQS uses keys that SQS owns, so you cannot set a key policy or see key use in your CloudTrail.
  • "Reduce KMS cost for a busy encrypted queue" → increase the data key reuse period. SQS then calls KMS less often, and KMS charges for each call.

Explanation

Resource policies

  • A queue policy controls who can call SQS actions on the queue. A topic policy controls who can call SNS actions, such as sns:Publish, on the topic.
  • For SNS to deliver to a queue, the queue policy must allow principal sns.amazonaws.com to call sqs:SendMessage.
  • Add an aws:SourceArn condition with the topic ARN (or aws:SourceAccount). This prevents the confused deputy problem.
  • Without the condition, the policy trusts the SNS service for any topic, including a topic in another account. The owner of that topic could then use SNS to send messages into your queue. The condition allows only your topic.
  • The same pattern applies to EventBridge: allow events.amazonaws.com with an aws:SourceArn of the rule.
  • Cross-account access to a queue or topic: add the other account as a principal in the resource policy. The other account must also give its users or roles the permission in their IAM policies.
  • Use IAM identity policies for your own users and roles, for example sqs:ReceiveMessage and sqs:DeleteMessage for a consumer.

Encryption at rest

  • SQS: SSE-SQS (keys that SQS manages) or SSE-KMS (an AWS KMS key).
  • Choose SSE-SQS when you only need encryption at rest, with no key to manage. Choose SSE-KMS with a customer managed key when you must control the key policy or see each use of the key in CloudTrail.
  • SSE encrypts the message body. It does not encrypt queue metadata, message metadata, or message attributes. Do not put sensitive data in message attributes.
  • SQS encrypts only messages sent after you turn on SSE. Messages already in the queue stay unencrypted.
  • All requests to an SSE queue must use HTTPS and Signature Version 4 (SigV4). Other requests fail with an InvalidSecurity error.
  • Data key reuse period: 60 seconds to 24 hours, default 5 minutes. SQS gets a data key from KMS and uses it to encrypt messages for this period. A longer period means fewer KMS calls and lower KMS cost.
  • With SSE-KMS, a producer needs kms:GenerateDataKey and kms:Decrypt, and a consumer needs kms:Decrypt.
  • When the data key reuse period ends, SQS calls GenerateDataKey with the producer's permissions to get a new data key. SQS also calls Decrypt with the producer's and the consumer's permissions to verify the data key before it uses it.
  • Without these permissions, the SQS call fails with a KMS access denied error (KmsAccessDenied). A Lambda function that reads an encrypted queue needs kms:Decrypt.
  • SNS topics also support SSE with AWS KMS keys. Data in transit uses TLS.

SNS to an encrypted queue

  • SNS acts as the producer when it sends to the queue, so SNS must be able to use the queue key.
  • Use a customer managed KMS key on the queue.
  • The key policy must allow sns.amazonaws.com to use kms:GenerateDataKey* and kms:Decrypt.
  • You cannot edit the key policy of the AWS managed key aws/sqs. SNS cannot use that key, so delivery fails.
  • The same rule applies to an encrypted queue that is an SNS subscription DLQ.
  • A queue encrypted with aws/sqs cannot invoke a Lambda function in a different account. You cannot edit the aws/sqs key policy to give the other account access to the key.

SNS fan-out, filter policies, and raw delivery

Remember

  • SNS is push-based publish/subscribe. SNS delivers a copy of each message to each subscription.

SNS delivery retries, dead-letter queues, and FIFO topics

Remember

  • SNS retries AWS managed endpoints (SQS, Lambda) with 100,015 attempts over 23 days.
  • You cannot change the SNS retry policy for AWS managed endpoints.
  • SNS retries email (SMTP), SMS, and mobile push endpoints with 50 attempts over 6 hours.
  • Only HTTP/S endpoints accept a custom delivery policy, at the topic or subscription level.
  • An HTTP/S delivery policy allows a maximum total retry time of 3,600 seconds.
  • SNS retries server-side errors, for HTTP/S the 5xx and 429 responses.
  • SNS does not retry client-side errors, for example a deleted endpoint or a policy that blocks delivery.
  • When retries end, or after a client-side error, SNS discards the message unless the subscription has a DLQ.
  • Attach an SNS DLQ to the subscription with a redrive policy (deadLetterTargetArn), not to the topic.
  • An SNS DLQ is an SQS queue in the same account and Region as the subscription.
  • A standard topic subscription uses a standard queue DLQ. A FIFO topic subscription uses a FIFO queue DLQ.
  • AWS recommends the maximum retention (14 days) for an SNS subscription DLQ.
  • An SNS FIFO topic keeps strict order inside each MessageGroupId.
  • An SNS FIFO topic deduplicates in a 5-minute interval with MessageDeduplicationId or content-based deduplication.
  • An SNS FIFO topic delivers only to SQS queues, FIFO or standard.
  • An SNS FIFO topic cannot deliver to Lambda, HTTP/S, email, SMS, or mobile push.
  • To reach Lambda from an SNS FIFO topic, subscribe a queue and use the queue as the function trigger.
  • With FifoThroughputScope = MessageGroup, each message group can receive up to 300 messages each second.
  • With FifoThroughputScope = Topic, the topic shares one limit: 3,000 messages or 20 MB each second by default.
  • Choose FifoThroughputScope = MessageGroup when you have many message groups and need more total throughput.
  • SNS FIFO topics support message archiving and replay. SNS standard topics do not.

Retries and DLQ

  • By default, EventBridge retries delivery to a target for 24 hours and up to 185 times, with exponential backoff and jitter.
  • Exponential backoff means that the wait between attempts grows after each failure. Jitter adds a random part to each wait, so that many retries do not arrive at the same moment.
  • You can set a shorter retry policy (maximum event age and retry attempts) on each target. Use it when an old event has no value, for example a price update that is more than 1 hour old.

  • An archive stores events from one source bus. An event pattern can select which events to archive. Use an archive when you may need to process past events again, for example after you fix a bug in a target.

  • A replay sends archived events back to the source bus only. It cannot send them to a different bus or account. You can limit it to specific rules, so that only the fixed rules process the events again and other targets do not get duplicates.

  • Make consumers idempotent and test them with repeated events. SQS standard queues, SNS, EventBridge, and Scheduler can deliver an event more than one time.
  • Use a separate bus or account for tests, so that test events do not reach production targets.

  • The sender account pays for the events. The receiver account does not.

Kinesis Data Streams: shards, partition keys, and consumers

Remember

  • A Kinesis data stream is a set of shards. The stream capacity is the sum of the shard capacities.
  • One Kinesis shard accepts writes of 1 MB/s or 1,000 records/s.
  • One Kinesis shard gives 2 MB/s of reads in total for all shared-throughput consumers.
  • One Kinesis shard allows 5 GetRecords calls each second.
  • Enhanced fan-out gives each consumer its own 2 MB/s for each shard, pushed over HTTP/2 (SubscribeToShard).
  • A Kinesis stream allows up to 20 enhanced fan-out consumers (provisioned and on-demand standard).
  • Kinesis retention has a default of 24 hours and a maximum of 8,760 hours (365 days).
  • A Kinesis record holds up to 10 MiB of data before base64 encoding. Older study material says 1 MB.
  • PutRecords takes up to 500 records in one request.
  • A Kinesis stream can switch capacity mode two times in 24 hours.
  • The partition key decides the shard. Kinesis hashes the key (MD5) to a 128-bit number.
  • Records with the same partition key go to the same shard, in order.
  • Kinesis keeps order inside a shard, not across shards.
  • A hot shard gets more writes than its limit while other shards are almost idle.
  • A partition key with few distinct values, or one very busy value, causes a hot shard.
  • A good partition key has many distinct values. Example: device ID, not device type.
  • Writes to a hot shard fail with ProvisionedThroughputExceededException, even when the stream has spare capacity.
  • To fix ProvisionedThroughputExceededException, retry with exponential backoff, spread partition keys, or add shards.
  • Kinesis does not write a throttled record. The producer must retry it, or the record is lost.
  • PutRecords can partly fail. Check FailedRecordCount and send the failed records again.
  • In provisioned mode, you set the shard count. Choose provisioned mode for steady, predictable traffic.
  • In on-demand mode, Kinesis scales shards. Choose on-demand mode when traffic is unknown or changes quickly.
  • Resharding (provisioned mode) splits one shard into two or merges two shards into one.
  • UpdateShardCount changes the shard count of the whole stream.
  • After resharding, the parent shard is closed for writes, but its records stay readable until retention ends.
  • Read the parent shard before its child shards to keep the order.
  • The IteratorAge metric shows how far a consumer is behind the newest record.
  • A rising IteratorAge means that consumers cannot keep up, and data can expire before it is read.
  • To lower Lambda IteratorAge, increase ParallelizationFactor, add shards, or make the function faster.
  • ParallelizationFactor (1 to 10) is the number of batches that Lambda processes at the same time from each shard.
  • With a ParallelizationFactor above 1, Lambda still keeps the order for each partition key.
  • Kinesis keeps data until retention ends, so many consumers can read it and a consumer can replay it.
  • A shared-throughput consumer has a latency of about 200 ms.
  • An enhanced fan-out consumer has a latency of about 70 ms.
  • Choose enhanced fan-out when several consumers read the same stream or when you need low latency.
  • In provisioned mode, enhanced fan-out adds a charge for each consumer-shard hour and for each GB read.
  • The Kinesis Client Library (KCL) uses a DynamoDB table to track shard leases and checkpoints.
  • Kinesis server-side encryption uses AWS KMS keys.
  • Without kms:GenerateDataKey, the producer PutRecord calls to an encrypted stream fail.
  • Without kms:Decrypt, the consumer GetRecords calls to an encrypted stream fail.
  • In a Lambda event, the Kinesis record data is base64-encoded. Decode it before you parse it.
  • For a Kinesis event source mapping, Lambda on-failure destinations SQS and SNS get batch metadata only: stream ARN, shard ID, and sequence numbers.
  • For a Kinesis event source mapping, a Lambda on-failure destination in Amazon S3 also gets the records.

Exam signals

  • "Several applications read the same records in order, and replay is needed" → Kinesis Data Streams. Reading does not delete records, so each application reads all records.
  • "Five consumers on one stream are slow and throttled" → enhanced fan-out. Each consumer gets its own 2 MB/s for each shard.
  • "One shard is throttled, the others are idle" → better partition key. The current key sends too many records to one shard.
  • "Keep records for 30 days for reprocessing" → increase retention (up to 365 days).
  • "IteratorAge of the Lambda consumer keeps growing" → increase ParallelizationFactor or add shards. Both let Lambda process more batches at the same time.

Explanation

A Kinesis data stream is a set of shards. A shard is an ordered sequence of records with a fixed write and read capacity. The capacity of the stream is the sum of the capacity of its shards.

Key facts

  • The partition key decides the shard. Kinesis hashes the key (MD5) to a 128-bit number, and each shard owns a range of those numbers. Records with the same key therefore go to the same shard, in order.
  • Order is kept inside a shard, not across shards.
  • A hot shard is a shard that gets more writes than its limit (1 MB/s or 1,000 records/s) while other shards are almost idle. It comes from a partition key with few distinct values, or one value with much more traffic.
  • Writes to the hot shard fail with ProvisionedThroughputExceededException, even when the stream has spare capacity.
  • Use a key with many distinct values. Example: with device type as the key, 3 types fill at most 3 shards; with device ID, writes spread across all shards.
  • ProvisionedThroughputExceededException: retry with exponential backoff, spread partition keys, or add shards. A throttled record is not written, so the producer must retry it or the record is lost.
  • PutRecords can partly fail. Check FailedRecordCount in the response and send the failed records again.
  • Provisioned mode: you set the shard count. On-demand mode: Kinesis scales shards for you.
  • Choose provisioned mode for steady, predictable traffic. Choose on-demand mode when traffic is unknown or changes quickly.
  • Resharding (provisioned mode): split one shard into two (more capacity, more cost) or merge two shards into one. UpdateShardCount changes the shard count of the whole stream.
  • After resharding, the parent shard is closed for writes. Its records stay readable until retention ends.
  • Read the parent shard before its child shards to keep the order. The parent holds the older records for the same keys.
  • The IteratorAge metric shows how far a consumer is behind the newest record. A rising value means consumers cannot keep up, and data can expire before it is read.
  • To lower Lambda IteratorAge: increase ParallelizationFactor, add shards, or make the function faster.
  • ParallelizationFactor (1 to 10) is the number of batches that Lambda processes at the same time from each shard. Lambda still keeps the order for each partition key.
  • Data stays in the stream until retention ends. Many consumers can read it, and a consumer can read it again (replay).
  • Shared-throughput consumers share 2 MB/s for each shard; latency is about 200 ms with one consumer. Enhanced fan-out latency is about 70 ms.
  • Choose enhanced fan-out when several consumers read the same stream or when you need low latency. In provisioned mode, it adds a charge for each consumer-shard hour and for each GB of data read.
  • Kinesis Client Library (KCL) uses an Amazon DynamoDB table to track shard leases and checkpoints. A lease records which worker reads which shard, so that workers share the shards. A checkpoint records the last processed record, so that a restarted worker continues from that point.
  • Server-side encryption uses AWS KMS keys. Producers and consumers need permission to use the key.
  • Without kms:GenerateDataKey, the producer's PutRecord calls fail. Without kms:Decrypt, the consumer's GetRecords calls fail.
  • In a Lambda event, the record data is base64-encoded. Decode it before you parse the payload.
  • Lambda event source mapping on-failure destinations: SQS and SNS get batch metadata only: the stream ARN, shard ID, and first and last sequence numbers. Use them to read the records from the stream before retention ends.
  • Amazon S3 also gets the records. See the Module 1 sheet for the other stream settings.

Amazon Data Firehose

Remember

  • Amazon Data Firehose delivers data to destinations with no consumer code.
  • Firehose does not store records, so Firehose has no replay.
  • Firehose scales automatically and has no shards.
  • Choose Firehose when you only need to load data into a store such as Amazon S3, with no code.
  • Choose Kinesis Data Streams when your own applications must read the records, or must read them again.
  • Firehose sources are Direct PUT (PutRecord, PutRecordBatch), Kinesis Data Streams, and Amazon MSK.
  • Firehose destinations include S3, Redshift, OpenSearch, Apache Iceberg tables, Splunk, Snowflake, HTTP endpoints, and partner services.
  • Firehose delivers when the buffer size or the buffer interval is reached first.
  • The Firehose S3 buffer size has a default of 5 MiB and a range of 1 to 128 MiB.
  • The Firehose S3 buffer interval has a default of 300 seconds and a range of 0 to 900 seconds.
  • A buffer interval of 0 (zero buffering) delivers within a few seconds. Older study material says the minimum is 60 seconds.
  • Zero buffering is not available with dynamic partitioning or for the S3 backup destination.
  • A buffer interval of less than 60 seconds to S3 uses multipart upload, which adds S3 PUT cost.
  • Small buffers make many small files, which slow down analytics queries and add S3 request cost.
  • Large buffers make fewer, larger files for analytics, but the data arrives later.
  • A Firehose Lambda transformation changes, masks, or drops records before delivery.
  • Firehose format conversion changes JSON to Apache Parquet or ORC, with the schema in an AWS Glue table.
  • Parquet and ORC make Amazon Athena queries faster and cheaper.
  • Firehose can compress data before delivery, for example with GZIP.
  • Dynamic partitioning writes each record under an S3 prefix that comes from a key in the record.
  • Source record backup writes the original source records to an S3 bucket.
  • A common pattern: Kinesis Data Streams keeps data for replay, and Firehose archives the stream to S3.
  • Firehose invokes the transformation function synchronously with a batch.
  • A Firehose transformation function can run for up to 5 minutes.
  • Each returned record needs recordId (same as input), result, and data (base64-encoded).
  • Firehose treats a returned recordId that does not match the input as a transformation failure.
  • The result value Ok delivers the record.
  • The result value Dropped removes the record on purpose, and Firehose counts it as a success.
  • The result value ProcessingFailed tells Firehose that the record is an error.
  • Firehose retries a failed transformation invocation 3 times by default.
  • Firehose writes failed records to the processing-failed folder in the S3 bucket.

Exam signals

  • "Load clickstream data into S3 with the least operational overhead" → Data Firehose. It is fully managed and needs no consumer code.
  • "Store as Parquet for Amazon Athena" → Firehose format conversion.
  • "Write S3 prefixes by customer ID from the record" → dynamic partitioning.
  • "Remove some records and mask fields before delivery" → Lambda transformation with Dropped and Ok. Dropped removes a record without an error, and Ok delivers the changed record.
  • "Replay data or custom real-time consumers" → Kinesis Data Streams, not Firehose. Firehose does not store records, so nothing can read them again.

AppSync resolvers, subscriptions, and caching

Remember

  • AWS AppSync is a managed GraphQL API.
  • A GraphQL client names the fields it needs in one request, and the API returns only those fields.
  • In GraphQL, a query reads data, a mutation changes data, and a subscription receives changes in real time.
  • AppSync data sources are DynamoDB, Lambda, OpenSearch Service, HTTP endpoints, EventBridge, Amazon RDS, and None.
  • A None data source stores nothing. Use it when the resolver can create the result itself.
  • A resolver connects a field to a data source.
  • Write AppSync resolvers in JavaScript (APPSYNC_JS) or VTL, the older template format.
  • A unit resolver uses one data source.
  • A pipeline resolver runs functions in order and can use several data sources for one field.
  • Direct DynamoDB resolvers do simple CRUD with no Lambda function to write, run, or pay for.
  • AppSync calls data sources with an IAM role that trusts appsync.amazonaws.com and allows the data source actions.
  • AppSync subscriptions push data to clients over WebSockets.
  • A mutation triggers a subscription. Use @aws_subscribe(mutations: ["addPost"]) on the subscription field.
  • A change made directly in the data source, not through an AppSync mutation, does not trigger a subscription.
  • Subscription arguments filter which mutation results a client gets.
  • An AppSync cache returns a stored result without a data source call, so it lowers latency and data source load.
  • Full request caching caches all resolver results, with keys from context.arguments and context.identity.
  • Per-resolver caching caches only the resolvers that opt in, each with its own TTL and keys.
  • Operation level caching caches whole query responses.
  • Choose per-resolver caching when only some fields are read often or can be stale for a time.
  • The AppSync maximum cache TTL is 3,600 seconds (1 hour).
  • New AppSync caches are always encrypted at rest and in transit.
  • Flush the whole AppSync cache with the console or CLI.
  • Call evictFromApiCache in a mutation resolver to remove one cache entry for a changed item.

Exam signals

  • "Mobile app needs data from DynamoDB and a REST service in one request" → AppSync with two data sources (pipeline resolver if one field needs both). One GraphQL request can read fields from several data sources.
  • "Clients must get updates in real time when data changes" → AppSync subscriptions linked to mutations. AppSync pushes each mutation result to the subscribed clients.
  • "Read-heavy GraphQL API, reduce data source load" → AppSync caching. Repeated queries get the cached result, not a data source call.

Explanation

Key facts

  • AWS AppSync is a managed GraphQL API. GraphQL is a query language for APIs.
  • The client names the fields it needs in one request, and the API returns only those fields. One request can get data that a REST client gets with several requests.
  • In GraphQL, a query reads data, a mutation changes data, and a subscription receives changes in real time.
  • Data sources: Amazon DynamoDB, AWS Lambda, OpenSearch Service, HTTP endpoints, Amazon EventBridge, relational databases (Amazon RDS), and None (local).
  • A None data source stores nothing; use it when the resolver can create the result itself, for example to convert data.
  • A resolver connects a field to a data source. Write resolvers in JavaScript (APPSYNC_JS) or VTL (Velocity Template Language, the older template format).
  • A unit resolver uses one data source. A pipeline resolver runs functions in order and can use several data sources for one field. Example: the first function checks a permission in one table, and the second function reads the item.
  • Direct DynamoDB resolvers do simple CRUD (create, read, update, delete) with no Lambda function. There is no function to write, run, or pay for.
  • AppSync calls data sources with an IAM role that trusts appsync.amazonaws.com. The role must allow the actions on the data source, for example dynamodb:GetItem on the table.

Subscriptions

  • Subscriptions push data to clients over WebSockets. A WebSocket is a connection that stays open, so the server can send data to the client at any time.
  • A subscription is triggered by a mutation. Use @aws_subscribe(mutations: ["addPost"]) on the subscription field.
  • A change made directly in the data source (not through an AppSync mutation) does not trigger a subscription. AppSync sees only the mutations that run through the API.
  • Subscription arguments filter which mutation results a client gets. Example: a client that subscribes with roomId: "42" gets only new messages for room 42.

AppSync authorization modes

Remember

  • Use API_KEY for development or for public data that is safe to expose. An API key is not user identity.
  • An API_KEY client sends the key in the x-api-key header.
  • Use AWS_IAM for AWS services, or for apps with Cognito identity pool credentials. The client signs requests with SigV4.
  • Use AMAZON_COGNITO_USER_POOLS for signed-in users and group-based access. The client sends a JWT in the Authorization header.
  • Use OPENID_CONNECT for users of a third-party OIDC provider. The client sends an OIDC token.
  • Use AWS_LAMBDA for custom authorization logic. The client sends a token in the Authorization header.
  • An AppSync API key can expire up to 365 days after you set it.
  • You can extend an AppSync API key up to 365 days more. After the key expires, requests with it fail.
  • One AppSync API can use a default mode plus additional modes.
  • Schema directives set the mode for a type or field: @aws_api_key, @aws_iam, @aws_cognito_user_pools, @aws_oidc, @aws_lambda.
  • A field with no directive uses the default mode.
  • When Cognito is the only mode, restrict to groups with @aws_auth(cognito_groups: ["Admins"]).
  • With additional modes, restrict to Cognito groups with @aws_cognito_user_pools(cognito_groups: [...]).
  • In IAM mode, allow appsync:GraphQL on the API, or on field ARNs to allow only some fields.
  • An AppSync API can have one Lambda authorizer.
  • A Lambda authorizer returns isAuthorized and can return deniedFields and ttlOverride.
  • AppSync returns null for each field in deniedFields, even when the request is allowed.
  • ttlOverride sets how long AppSync caches the Lambda authorizer result.
  • The Lambda authorizer function needs a resource policy that allows appsync.amazonaws.com.
  • For fine-grained data access, compare ctx.identity with the item in the resolver.

Exam signals

  • "Public read for guests, write only for signed-in users" → API key or IAM (guest) for queries plus Cognito user pools for mutations, with directives. Additional modes let each field use the mode that fits its callers.
  • "Only the Admins group may call deletePost" → Cognito group in a directive. AppSync reads the groups from the user token, so no resolver code is needed.
  • "Backend service in AWS calls the API" → AWS_IAM. The service signs requests with its IAM role credentials, so it needs no stored secret.
  • "Production API uses an API key that will expire" → move to Cognito or IAM; API keys are not user identity. Anyone who has the key can call the API, and the key stops working when it expires.
