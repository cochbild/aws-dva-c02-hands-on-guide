SQS standard and FIFO queues

Key facts

  • Standard queue consumers must be idempotent, because a message can arrive more than one time.
  • FIFO deduplication: turn on content-based deduplication, or send a MessageDeduplicationId.
  • Content-based deduplication uses a SHA-256 hash of the message body. It does not use the message attributes.
  • Send your own MessageDeduplicationId when identical bodies must count as different messages, or different bodies must count as one message.
  • SQS continues to track a deduplication ID after the message is deleted, until the 5-minute interval ends.
  • In a FIFO queue, the next message of a group is not available while an earlier message of that group is in flight.
  • To get more parallel processing from a FIFO queue, use many different MessageGroupId values.
  • High throughput mode for FIFO queues is set on the queue. Its limit depends on the Region (for example, up to 70,000 transactions each second without batching in US East (N. Virginia)).
  • Batch API calls (SendMessageBatch, DeleteMessageBatch) take a maximum of 10 messages.

Exam signals

  • "Process each customer's orders in order, but process different customers in parallel" → FIFO queue, MessageGroupId = customer ID.
  • "Producer retries can send the same order twice; process it one time" → FIFO queue with deduplication.
  • "Messages have a timestamp in the body, but repeats must be removed" → explicit MessageDeduplicationId, not content-based deduplication.
  • "Highest throughput, order not important" → standard queue with idempotent consumers.

SQS visibility timeout, polling, delay, and Lambda consumers

Visibility timeout

  • A received message stays in the queue, but other consumers cannot see it for the visibility timeout.
  • The consumer must call DeleteMessage before the timeout ends. If it does not, the message becomes visible again and another consumer can process it.
  • Use ChangeMessageVisibility to extend the timeout for a long task (a heartbeat). The 12-hour maximum counts from the first receive.
  • Set the visibility timeout to 0 with ChangeMessageVisibility to release a message at once.
  • With a Lambda event source mapping, set the visibility timeout to at least 6 times the function timeout. Lambda rejects a mapping if the function timeout is more than the visibility timeout. See the Module 1 sheet for more Lambda details.

Short and long polling

  • Short polling (default) asks a subset of servers and returns at once. It can return an empty response even when messages exist.
  • Long polling asks all servers and waits until a message arrives or the wait time ends. It reduces empty and false empty responses, so it reduces cost.
  • Turn on long polling for all receives with the queue attribute ReceiveMessageWaitTimeSeconds. Or set WaitTimeSeconds on one ReceiveMessage call.

Delay queues and message timers

  • A delay hides a message when it is added to the queue. A visibility timeout hides a message after it is received.
  • A message timer (DelaySeconds on one message) overrides the queue delay. FIFO queues do not support message timers.
  • For delays longer than 15 minutes, use EventBridge Scheduler.

Lambda consumers (event source mapping)

  • By default, one failed message makes the whole batch visible again. Successful messages are then processed again.
  • Partial batch response: set FunctionResponseTypes to ReportBatchItemFailures. The function returns the failed message IDs in batchItemFailures; only those messages return to the queue.
  • Filter criteria on the event source mapping use EventBridge pattern syntax. Filter on the message body or on metadata. Up to 5 filters by default (quota increase to 10).
  • For SQS, Lambda deletes messages that do not match the filter. The function is not invoked for them.
  • Batching window (MaximumBatchingWindowInSeconds): Lambda waits up to this time to fill a batch. For a batch size over 10 (standard queue), set it to at least 1 second. Add it to the visibility timeout calculation.

Exam signals

  • "Many empty ReceiveMessage responses, high cost" → long polling (ReceiveMessageWaitTimeSeconds = 20).
  • "Processing sometimes takes longer than the visibility timeout, and messages are processed twice" → increase the visibility timeout or call ChangeMessageVisibility.
  • "Payload is 5 MB" → SQS Extended Client Library with Amazon S3.
  • "Every new message must wait 5 minutes before processing" → delay queue.
  • "One bad message makes the whole batch run again" → ReportBatchItemFailures.
  • "Function must not be invoked for messages it does not need" → filter criteria on the event source mapping.

SQS dead-letter queues and redrive

Key facts

  • Set the redrive policy on the source queue. It names the dead-letter queue (DLQ) ARN and maxReceiveCount.
  • maxReceiveCount (1 to 1,000) is how many times a consumer can receive a message before SQS moves it to the DLQ. There is no default; you set it.
  • With Lambda, AWS recommends maxReceiveCount of at least 5.
  • The DLQ type must match the source: a FIFO queue uses a FIFO DLQ, and a standard queue uses a standard DLQ.
  • The DLQ must be in the same AWS account and Region as the source queue.
  • SQS does not create the DLQ for you. Create it first. A DLQ is an ordinary queue.
  • Standard queues: a moved message keeps its original enqueue timestamp. Set the DLQ retention longer than the source retention.
  • FIFO queues: the enqueue timestamp resets when the message moves to the DLQ.
  • A DLQ can break the exact order of a FIFO queue. Do not use one if the order of every message is critical.
  • Alarm on the DLQ metric ApproximateNumberOfMessagesVisible.

DLQ redrive

  • StartMessageMoveTask moves messages from a DLQ to another queue. If you do not give a destination, messages go back to their original source queues.
  • The source must be a DLQ of other SQS queues. A DLQ of a Lambda function or an SNS subscription is not supported.
  • One active move task for each queue. Optional rate: up to 500 messages each second.
  • Use ListMessageMoveTasks to see progress and CancelMessageMoveTask to stop.

Exam signals

  • "Poison message is retried forever" → redrive policy with a DLQ and maxReceiveCount.
  • "Bug is fixed; reprocess the failed messages with the least effort" → DLQ redrive (StartMessageMoveTask).
  • "Messages expire in the DLQ sooner than expected" → standard queue keeps the original timestamp. Increase DLQ retention.
  • "Only one team's queue may use this DLQ" → redrive allow policy byQueue.

SQS and SNS access policies and encryption

Resource policies

  • A queue policy controls who can call SQS actions on the queue. A topic policy controls who can call SNS actions, such as sns:Publish, on the topic.
  • For SNS to deliver to a queue, the queue policy must allow principal sns.amazonaws.com to call sqs:SendMessage.
  • Add an aws:SourceArn condition with the topic ARN (or aws:SourceAccount). This prevents the confused deputy problem.
  • The same pattern applies to EventBridge: allow events.amazonaws.com with an aws:SourceArn of the rule.
  • Cross-account access to a queue or topic: add the other account as a principal in the resource policy.
  • Use IAM identity policies for your own users and roles, for example sqs:ReceiveMessage and sqs:DeleteMessage for a consumer.

Encryption at rest

  • SQS: SSE-SQS (keys that SQS manages) or SSE-KMS (an AWS KMS key).
  • SSE encrypts the message body. It does not encrypt queue metadata, message metadata, or message attributes.
  • SQS encrypts only messages sent after you turn on SSE.
  • All requests to an SSE queue must use HTTPS and Signature Version 4.
  • Data key reuse period: 60 seconds to 24 hours, default 5 minutes. A longer period means fewer KMS calls and lower KMS cost.
  • With SSE-KMS, a producer needs kms:GenerateDataKey and a consumer needs kms:Decrypt. A Lambda function that reads an encrypted queue needs kms:Decrypt.
  • SNS topics also support SSE with AWS KMS keys. Data in transit uses TLS.

SNS to an encrypted queue

  • Use a customer managed KMS key on the queue.
  • The key policy must allow sns.amazonaws.com to use kms:GenerateDataKey* and kms:Decrypt.
  • You cannot edit the key policy of the AWS managed key aws/sqs. SNS cannot use that key, so delivery fails.
  • The same rule applies to an encrypted queue that is an SNS subscription DLQ.
  • A queue encrypted with aws/sqs cannot invoke a Lambda function in a different account.

Exam signals

  • "SNS subscription is confirmed but the queue gets no messages" → queue policy does not allow sns.amazonaws.com, or the KMS key policy does not allow SNS.
  • "Only this topic may send to the queue" → aws:SourceArn condition in the queue policy.
  • "Encrypt messages and audit key use in CloudTrail" → SSE-KMS with a customer managed key.
  • "Reduce KMS cost for a busy encrypted queue" → increase the data key reuse period.

References: Subscribe a queue to a topic, SNS with an encrypted queue, SQS encryption at rest. Lab: Lab 5.2 SNS fan-out.

SNS fan-out, filter policies, and raw delivery

Key facts

  • SNS is push-based publish/subscribe. A publisher sends one message; SNS delivers a copy to each subscription.
  • Standard topic subscription types include SQS, Lambda, HTTP/HTTPS, email, SMS, mobile push, and Amazon Data Firehose.
  • SNS does not store messages for consumers. For durable fan-out, subscribe SQS queues to the topic (SNS to SQS fan-out).
  • SNS invokes a Lambda subscriber asynchronously. The publisher does not get the function result.
  • Message size: default maximum 256 KiB. Set the topic attribute MaximumMessageSize to allow up to 1 MiB.
  • For payloads over 1 MiB, use the SNS Extended Client Library (payload in Amazon S3, up to 2 GB).
  • PublishBatch takes up to 10 messages.

Filter policies

  • A filter policy is a JSON document on a subscription, not on the topic. Each subscription can have a different policy.
  • With no filter policy, a subscription receives every message.
  • FilterPolicyScope: MessageAttributes (default) or MessageBody. The body must be valid JSON to filter on it.
  • SNS does not deliver a message that does not match. This saves Lambda invocations and SQS receives.
  • Operators include exact match, prefix, suffix, anything-but, numeric, exists, and cidr.
  • Quota: 200 filter policies for each topic.

Raw message delivery

  • By default, SNS wraps the message in a JSON envelope (Type, MessageId, TopicArn, Message, Timestamp, signature fields).
  • Set RawMessageDelivery to true on an SQS, HTTP/S, or Firehose subscription to deliver only the message body.
  • With raw delivery to SQS, a maximum of 10 message attributes is sent. SNS discards messages with more.

Exam signals

  • "One order event must go to billing, shipping, and analytics queues" → SNS topic with three SQS subscriptions.
  • "Each consumer wants only some messages, with no code change in the publisher" → subscription filter policies.
  • "Filter on a field in the JSON payload" → FilterPolicyScope = MessageBody.
  • "Consumer code must not parse the SNS envelope" → raw message delivery.

References: SNS message filtering, SetSubscriptionAttributes, Raw message delivery, SNS quotas. Lab: Lab 5.2 SNS fan-out.

SNS delivery retries, dead-letter queues, and FIFO topics

Delivery retries

Endpoint typeDefault retry policy
AWS managed (SQS, Lambda)100,015 attempts over 23 days
SMTP (email), SMS, mobile push50 attempts over 6 hours
HTTP/SYou can set a custom delivery policy. Total retry time is a maximum of 3,600 seconds.
  • Only HTTP/S endpoints accept a custom delivery policy, at the topic or subscription level.
  • SNS retries server-side errors. SNS does not retry client-side errors (for example, a deleted endpoint or a policy that blocks delivery).
  • When retries end, SNS discards the message, unless the subscription has a DLQ.

Subscription dead-letter queue

  • Attach the DLQ to the subscription with a redrive policy (deadLetterTargetArn), not to the topic.
  • The DLQ is an SQS queue in the same account and Region as the subscription.
  • Standard topic subscriptions use a standard queue DLQ. FIFO topic subscriptions use a FIFO queue DLQ.
  • AWS recommends the maximum retention (14 days) for the DLQ.

FIFO topics

  • Strict order inside each MessageGroupId, and deduplication in a 5-minute interval (MessageDeduplicationId or content-based).
  • A FIFO topic delivers only to SQS queues: FIFO queues and standard queues.
  • A FIFO topic cannot deliver to Lambda, HTTP/S, email, SMS, or mobile push. To reach Lambda, subscribe a queue and use it as the function trigger.
  • Throughput: 300 messages each second for each message group. The topic default is 3,000 messages each second or 20 MB each second.
  • FIFO topics support message archiving and replay. Standard topics do not.

Exam signals

  • "Keep messages that SNS could not deliver" → DLQ on the subscription.
  • "HTTP endpoint is overloaded by retries" → custom HTTP/S delivery policy (for example, maxReceivesPerSecond).
  • "Fan out ordered price updates to several services" → SNS FIFO topic to SQS FIFO queues.
  • "FIFO topic must notify a Lambda function" → topic to SQS queue, then queue to Lambda.

References: SNS delivery retries, SNS dead-letter queues, FIFO topic delivery, SNS quotas (FIFO throughput). Lab: Lab 5.2 SNS fan-out.

EventBridge buses, rules, patterns, and targets

Event buses

BusReceives
Default busAWS service events (one bus for each account and Region), plus PutEvents calls
Custom busEvents that your applications send with PutEvents
Partner busEvents from SaaS partners

Event structure

Every event has the same top-level fields: version, id, detail-type, source, account, time, region, resources, and detail (your payload).

Key facts

  • A rule matches events with an event pattern and sends them to targets.
  • A rule can have a maximum of 5 targets. This quota cannot be increased. For more targets, add a rule with the same pattern or send to an SNS topic.
  • Pattern operators include exact match, prefix, suffix, anything-but, numeric, exists, cidr, wildcard, and equals-ignore-case.
  • EventBridge patterns can match any field in the event, including nested fields in detail.
  • Input transformer: InputPathsMap takes values from the event; InputTemplate builds the new input for the target.
  • PutEvents: up to 10 entries in one request, total size less than 1 MB.
  • PutEvents can partly fail. Check FailedEntryCount and send the failed entries again.
  • Targets include Lambda, SQS, SNS, Step Functions, Kinesis, Firehose, ECS tasks, API destinations (HTTP), and other event buses.
  • Schema registry: EventBridge can discover event schemas and generate code bindings.

API destinations

  • An API destination is an HTTPS endpoint that a rule (or a pipe) invokes as a target. Use it to send events to SaaS or your own HTTP APIs with no code.
  • A connection holds the authorization method and credentials. EventBridge stores the credentials in AWS Secrets Manager.
  • You set an invocation rate limit for each destination (default 300 each second).
  • The endpoint must respond within 5 seconds, or EventBridge times out the request and retries it.
  • EventBridge retries 401, 407, 409, 429, and 5xx errors. It does not retry other 4xx errors. Add a DLQ so that you do not lose events.

Target permissions

  • Lambda, SNS, and SQS targets: a resource-based policy that allows events.amazonaws.com, or an IAM execution role on the target.
  • Kinesis stream targets: an IAM role (identity-based policy).
  • CloudWatch Logs targets: a resource-based policy only.

Exam signals

  • "React to an AWS service event (for example, an EC2 state change)" → rule on the default bus.
  • "Route by a nested field, with ranges or prefixes" → EventBridge pattern.
  • "Target needs a different JSON shape, no code" → input transformer.
  • "Rule needs 8 targets" → two rules with the same pattern.
  • "Send events to a third-party HTTP API with OAuth, no code" → API destination with a connection.

References: EventBridge quotas, PutEvents, Target permissions, API destinations. Lab: Lab 5.3 EventBridge rules.

EventBridge retries, archive and replay, testing, and cross-account events

Retries and DLQ

  • By default, EventBridge retries delivery to a target for 24 hours and up to 185 times, with exponential backoff and jitter.
  • You can set a shorter retry policy (maximum event age and retry attempts) on each target.
  • When retries end, EventBridge drops the event, unless the target has a DLQ (a standard SQS queue).

Archive and replay

  • An archive stores events from one source bus. An event pattern can select which events to archive.
  • Retention: a number of days, or indefinite (default).
  • A replay sends archived events back to the source bus only. You can limit it to specific rules.
  • Replayed events have a replay-name field. Replayed events do not go into the archive again.
  • A replay does not keep the exact original order. AWS recommends waiting 10 minutes before you replay recent events.

Testing event-driven applications

  • TestEventPattern checks whether a sample event matches an event pattern. It returns Result true or false. Use it in unit tests and CI before you deploy a rule.
  • A test listener is a temporary rule that sends matched events to CloudWatch Logs or an SQS queue, so that a test can check that events arrive.
  • Use archive and replay to run real past events through new or fixed rules.
  • Make consumers idempotent and test them with repeated events. SQS standard queues, SNS, EventBridge, and Scheduler can deliver an event more than one time.
  • Use a separate bus or account for tests, so that test events do not reach production targets.

Cross-account events

  • Receiver account: add a resource-based policy to the receiving bus that allows the sender account or organization.
  • Sender account: create a rule whose target is the receiver bus ARN. New cross-account bus targets need an IAM role.
  • If a bus accepts events from other accounts, add an account field to your rule patterns.
  • The sender account pays for the events. The receiver account does not.

Exam signals

  • "Do not lose events when the target is down for 2 days" → DLQ on the target (default retry is 24 hours).
  • "Reprocess last week's events after a bug fix" → archive and replay.
  • "Central account collects events from member accounts" → resource policy on the central bus, rules in member accounts.
  • "Check in the CI pipeline that a new rule pattern matches sample events" → TestEventPattern.

References: Retry policy, Archive and replay, Cross-account events, TestEventPattern. Lab: Lab 5.3 EventBridge rules.

EventBridge Scheduler and Pipes

EventBridge Scheduler

  • Schedule types: one-time (at(yyyy-mm-ddThh:mm:ss)), rate (rate(5 minutes)), and cron (cron(min hour day-of-month month day-of-week year)).
  • Cron and one-time schedules run in UTC or in an IANA time zone that you set. Scheduler adjusts for daylight saving time.
  • Precision is 60 seconds. A flexible time window spreads invocations over a period.
  • Delivery is at least once. You can set retries and a DLQ (a standard SQS queue; FIFO is not supported).
  • Scheduler uses an execution role that trusts scheduler.amazonaws.com and allows the target action (for example, sqs:SendMessage).
  • Templated targets: SQS, SNS, Lambda, and EventBridge. Universal targets call more than 6,000 API operations.
  • A completed one-time schedule still counts against your quota. Delete it after it runs.
  • AWS recommends Scheduler for schedules. Scheduled rules are a legacy feature: default bus only, UTC only.

EventBridge Pipes

  • A pipe connects one source to one target: source, optional filter, optional enrichment, target.
  • Sources: SQS, Kinesis Data Streams, DynamoDB Streams, Amazon MSK, Amazon MQ, and Apache Kafka.
  • Pipes reduce integration code between services. A pipe uses an IAM role; Pipes do not support resource-based policies.

Exam signals

  • "Send a reminder one time, 3 days after sign-up, for millions of users" → one-time schedules in EventBridge Scheduler.
  • "Run a job at 8:00 local time in New York, with daylight saving time" → Scheduler cron with time zone America/New_York.
  • "SQS to Step Functions with filtering and no custom code" → EventBridge Pipes.

References: Scheduler schedule types, Scheduler execution role, EventBridge Pipes. Lab: Lab 5.3 EventBridge rules.

Kinesis Data Streams: shards, partition keys, and consumers

Numbers to memorize

Capacity mode switchTwo times in 24 hours for each stream

Key facts

  • The partition key decides the shard. Records with the same key go to the same shard, in order.
  • Order is kept inside a shard, not across shards.
  • A hot shard comes from a partition key with too much traffic. Use a key with many distinct values.
  • ProvisionedThroughputExceededException: retry with exponential backoff, spread partition keys, or add shards.
  • Provisioned mode: you set the shard count. On-demand mode: Kinesis scales shards for you.
  • Resharding (provisioned mode): split one shard into two (more capacity, more cost) or merge two shards into one. UpdateShardCount changes the shard count of the whole stream.
  • After resharding, the parent shard is closed for writes. Its records stay readable until retention ends. Read the parent shard before its child shards to keep the order.
  • The IteratorAge metric shows how far a consumer is behind the newest record. A rising value means consumers cannot keep up, and data can expire before it is read.
  • To lower Lambda IteratorAge: increase ParallelizationFactor, add shards, or make the function faster.
  • Data stays in the stream until retention ends. Many consumers can read it, and a consumer can read it again (replay).
  • Shared-throughput consumers share 2 MB/s for each shard; latency is about 200 ms with one consumer. Enhanced fan-out latency is about 70 ms.
  • Kinesis Client Library (KCL) uses an Amazon DynamoDB table to track shard leases and checkpoints.
  • Server-side encryption uses AWS KMS keys. Producers and consumers need permission to use the key.
  • In a Lambda event, the record data is base64-encoded.
  • Lambda event source mapping on-failure destinations: SQS and SNS get batch metadata only. Amazon S3 also gets the records. See the Module 1 sheet for the other stream settings.

Exam signals

  • "Several applications read the same records in order, and replay is needed" → Kinesis Data Streams.
  • "Five consumers on one stream are slow and throttled" → enhanced fan-out.
  • "One shard is throttled, the others are idle" → better partition key.
  • "Keep records for 30 days for reprocessing" → increase retention (up to 365 days).
  • "IteratorAge of the Lambda consumer keeps growing" → increase ParallelizationFactor or add shards.

References: Kinesis quotas and limits, Enhanced fan-out, Kinesis ESM on-failure destinations, Resharding, Lambda with Kinesis. Lab: Lab 5.5 Kinesis Data Streams.

Amazon Data Firehose

Comparison

ItemData FirehoseKinesis Data Streams
ConsumersManaged delivery to destinations. You write no consumer code.You write consumers (Lambda, KCL applications)
Storage and replayNo storage, no replayRetention of 24 hours to 365 days; replay is possible

Key facts

  • Sources: Direct PUT (PutRecord, PutRecordBatch), Kinesis Data Streams, and Amazon MSK.
  • Destinations include Amazon S3, Amazon Redshift, OpenSearch Service, OpenSearch Serverless, Apache Iceberg tables, Splunk, Snowflake, HTTP endpoints, and partner services.
  • Firehose buffers data and delivers when the buffer size or the buffer interval is reached first.
  • Optional Lambda transformation, format conversion (JSON to Apache Parquet or ORC, with an AWS Glue table), compression, and dynamic partitioning for S3 prefixes.
  • Source record backup: Firehose can also write source records to an S3 bucket. For some destinations you choose all records or failed records only.
  • Common pattern: producers write to Kinesis Data Streams for replay, and Firehose reads the stream and archives it to S3.

Buffering hints (S3 destination)

HintDefaultRange
Buffer size5 MiB1 to 128 MiB
Buffer interval300 seconds0 to 900 seconds
  • A buffer interval of 0 (zero buffering) delivers within a few seconds. Older study material says the minimum is 60 seconds.
  • Zero buffering is not available with dynamic partitioning or for the S3 backup destination.
  • An interval of less than 60 seconds to S3 uses multipart upload, which adds S3 PUT cost.
  • Small buffers make many small files. Larger buffers make fewer, larger files for analytics.

Lambda transformation

  • Firehose invokes the function synchronously with a batch. The function can run for up to 5 minutes.
  • Each returned record needs recordId (same as input), result, and data (base64-encoded).
  • result values: Ok, Dropped (removed on purpose), ProcessingFailed.
  • Firehose retries a failed invocation 3 times by default. Failed records go to the processing-failed folder in the S3 bucket.

Exam signals

  • "Load clickstream data into S3 with the least operational overhead" → Data Firehose.
  • "Store as Parquet for Amazon Athena" → Firehose format conversion.
  • "Write S3 prefixes by customer ID from the record" → dynamic partitioning.
  • "Remove some records and mask fields before delivery" → Lambda transformation with Dropped and Ok.
  • "Replay data or custom real-time consumers" → Kinesis Data Streams, not Firehose.

AppSync resolvers, subscriptions, and caching

Key facts

  • AWS AppSync is a managed GraphQL API. The client chooses the fields it needs in one request.
  • Data sources: Amazon DynamoDB, AWS Lambda, OpenSearch Service, HTTP endpoints, Amazon EventBridge, relational databases (Amazon RDS), and None (local).
  • A resolver connects a field to a data source. Write resolvers in JavaScript (APPSYNC_JS) or VTL.
  • A unit resolver uses one data source. A pipeline resolver runs functions in order and can use several data sources for one field.
  • Direct DynamoDB resolvers do simple CRUD with no Lambda function.
  • AppSync calls data sources with an IAM role that trusts appsync.amazonaws.com.

Subscriptions

  • Subscriptions push data to clients over WebSockets.
  • A subscription is triggered by a mutation. Use @aws_subscribe(mutations: ["addPost"]) on the subscription field.
  • A change made directly in the data source (not through an AppSync mutation) does not trigger a subscription.
  • Subscription arguments filter which mutation results a client gets.

Exam signals

  • "Mobile app needs data from DynamoDB and a REST service in one request" → AppSync with two data sources (pipeline resolver if one field needs both).
  • "Clients must get updates in real time when data changes" → AppSync subscriptions linked to mutations.
  • "Read-heavy GraphQL API, reduce data source load" → AppSync caching.

Key facts

  • An API key can expire up to 365 days after you set it. You can extend it up to 365 days more from that day.
  • One API can use a default mode plus additional modes.
  • Schema directives set the mode for a type or field: @aws_api_key, @aws_iam, @aws_cognito_user_pools, @aws_oidc, @aws_lambda.
  • A field with no directive uses the default mode.
  • Cognito groups: @aws_auth(cognito_groups: ["Admins"]) when Cognito is the only mode. With additional modes, use @aws_cognito_user_pools(cognito_groups: [...]).
  • IAM mode: allow appsync:GraphQL on the API, or on field ARNs such as .../types/Query/fields/getPost.
  • Lambda authorizer: one for each API. It returns isAuthorized and can return deniedFields and ttlOverride. The function needs a resource policy that allows appsync.amazonaws.com.
  • Fine-grained data access (for example, only the owner can edit an item): compare ctx.identity with the item in the resolver.

Exam signals

  • "Public read for guests, write only for signed-in users" → API key or IAM (guest) for queries plus Cognito user pools for mutations, with directives.
  • "Only the Admins group may call deletePost" → Cognito group in a directive.
  • "Backend service in AWS calls the API" → AWS_IAM.
  • "Production API uses an API key that will expire" → move to Cognito or IAM; API keys are not user identity.
