SQS standard and FIFO queues

"Best effort" order means that SQS usually delivers messages in the order they were sent, but some messages can arrive out of order. "At least once" means that SQS can deliver a copy of a message a second time. Choose a standard queue when you need the most throughput and your consumer can handle duplicates and a changed order. Choose a FIFO queue when the order of related messages matters, for example the steps of one order. Also choose it when a duplicate causes harm, for example a second payment.

Fair queues: on a standard queue, the MessageGroupId identifies a tenant, for example a customer. One tenant can send a large burst and make a backlog. SQS then delivers the messages of the other tenants first, so that their messages do not wait. It does not give order on a standard queue.

Key facts

  • Standard queue consumers must be idempotent, because a message can arrive more than one time. Idempotent means that processing the same message two times gives the same result as one time. Example: before the consumer charges a card, it checks whether it already processed that order ID. Without this check, a duplicate message charges the customer two times.
  • FIFO deduplication: SQS needs a deduplication ID for every message. Send a MessageDeduplicationId, or turn on content-based deduplication so that SQS makes the ID for you. If you do neither, SendMessage fails with an error.
  • If a second message with the same deduplication ID arrives in the 5-minute interval, SQS accepts the send call but does not deliver the second message. So a producer can safely retry a send that timed out.
  • Content-based deduplication uses a SHA-256 hash of the message body. It does not use the message attributes.
  • Send your own MessageDeduplicationId when identical bodies must count as different messages, or different bodies must count as one message.
  • SQS continues to track a deduplication ID after the message is deleted, until the 5-minute interval ends.
  • In a FIFO queue, the next message of a group is not available while an earlier message of that group is in flight. "In flight" means that a consumer received the message but did not delete it yet. SQS holds the rest of the group so that the group stays in order. One slow message therefore blocks all later messages of its group.
  • To get more parallel processing from a FIFO queue, use many different MessageGroupId values. Only one consumer at a time can hold messages of a group, so the number of active groups limits how many consumers can work at the same time.
  • High throughput mode for FIFO queues is set on the queue. Turn it on when 300 transactions each second for each API action is not enough. Its limit depends on the Region (for example, up to 70,000 transactions each second without batching in US East (N. Virginia)).
  • Batch API calls (SendMessageBatch, DeleteMessageBatch) take a maximum of 10 messages.

Exam signals

  • "Process each customer's orders in order, but process different customers in parallel" → FIFO queue, MessageGroupId = customer ID. Order is kept inside a group, and different groups are processed at the same time.
  • "Producer retries can send the same order twice; process it one time" → FIFO queue with deduplication. SQS does not deliver a second message with the same deduplication ID in the 5-minute interval.
  • "Messages have a timestamp in the body, but repeats must be removed" → explicit MessageDeduplicationId, not content-based deduplication. The timestamp makes each body different, so the body hash is different and SQS does not see a duplicate.
  • "Highest throughput, order not important" → standard queue with idempotent consumers. A standard queue has nearly unlimited throughput, and idempotent consumers make the duplicates harmless.

SQS visibility timeout, polling, delay, and Lambda consumers

In-flight messages are messages that consumers received but did not delete yet. When a standard queue reaches the in-flight limit, a short-poll ReceiveMessage returns an OverLimit error. A long poll returns no new messages. This continues until consumers delete messages or messages become visible again.

Visibility timeout

  • A received message stays in the queue, but other consumers cannot see it for the visibility timeout. This stops two consumers from processing the same message at the same time.
  • The consumer must call DeleteMessage before the timeout ends. If it does not, the message becomes visible again and another consumer can process it.
  • Use ChangeMessageVisibility to extend the timeout for a long task. Call it at intervals while the task runs (a heartbeat). The 12-hour maximum counts from the first receive.
  • Set the visibility timeout to 0 with ChangeMessageVisibility to release a message at once. Use this when a consumer knows that it cannot process the message, for example during a shutdown. Another consumer can then take the message now, not after the timeout ends.
  • With a Lambda event source mapping, set the visibility timeout to at least 6 times the function timeout. The extra time lets Lambda retry the batch if the function is throttled. If the timeout is too short, messages become visible again while Lambda still works on them, and they are processed two times. Lambda rejects a mapping if the function timeout is more than the visibility timeout. See the Module 1 sheet for more Lambda details.

Short and long polling

  • SQS stores the messages of a queue on many servers.
  • Short polling (default) asks only a subset of those servers and returns at once. It can return an empty response even when messages exist on the other servers (a "false empty" response). SQS bills each empty response as a request.
  • Long polling asks all servers and waits until a message arrives or the wait time ends. It reduces empty and false empty responses, so it reduces cost.
  • Turn on long polling for all receives with the queue attribute ReceiveMessageWaitTimeSeconds. This needs no code change in the consumers. Or set WaitTimeSeconds on one ReceiveMessage call, which overrides the queue attribute for that call.

Delay queues and message timers

  • A delay hides a message when it is added to the queue. A visibility timeout hides a message after it is received.
  • Use a queue delay (a delay queue) when every new message must wait before consumers can see it. Use a message timer when only some messages need a wait.
  • A message timer (DelaySeconds on one message) overrides the queue delay. FIFO queues do not support message timers.
  • For delays longer than 15 minutes, use EventBridge Scheduler. 15 minutes is the maximum SQS delay.

Lambda consumers (event source mapping)

  • By default, if the function returns an error, Lambda deletes no message from the batch. All messages in the batch become visible again after the visibility timeout. The messages that succeeded are then processed again, so their side effects (for example, an email) happen again.
  • Partial batch response: set FunctionResponseTypes to ReportBatchItemFailures. The function returns the failed message IDs in batchItemFailures; only those messages return to the queue.
  • Filter criteria on the event source mapping use EventBridge pattern syntax. Filter on the message body or on the metadata fields of the record. Use filters so that you do not invoke, and pay for, the function for messages that it ignores. Up to 5 filters by default (quota increase to 10).
  • For SQS, Lambda deletes messages that do not match the filter. The function is not invoked for them. No other consumer can read those messages, so do not filter out messages that another process needs.
  • Batching window (MaximumBatchingWindowInSeconds): Lambda waits up to this time to fill a batch. For a batch size over 10 (standard queue), you must set it to at least 1 second. Messages stay in flight while Lambda waits. So set the visibility timeout to 6 times the function timeout plus the batching window.

Exam signals

  • "Many empty ReceiveMessage responses, high cost" → long polling (ReceiveMessageWaitTimeSeconds = 20). Each receive waits for messages, so there are fewer empty, billable responses.
  • "Processing sometimes takes longer than the visibility timeout, and messages are processed twice" → increase the visibility timeout or call ChangeMessageVisibility. The message then stays hidden until the first consumer deletes it.
  • "Payload is 5 MB" → SQS Extended Client Library with Amazon S3. The SQS message limit is 1 MiB, so the library stores the payload in S3 and sends a reference.
  • "Every new message must wait 5 minutes before processing" → delay queue. The queue delay hides every new message for the set time (maximum 15 minutes).
  • "One bad message makes the whole batch run again" → ReportBatchItemFailures. Only the failed messages return to the queue.
  • "Function must not be invoked for messages it does not need" → filter criteria on the event source mapping. Lambda checks the filter before it invokes the function.

SQS dead-letter queues and redrive

Key facts

  • A dead-letter queue (DLQ) holds messages that consumers fail to process many times. Without a DLQ, a message that always fails (a "poison message") returns to the queue after each visibility timeout. It is received again and again until its retention period ends, and it uses consumer capacity each time.
  • Set the redrive policy on the source queue. It names the dead-letter queue (DLQ) ARN and maxReceiveCount.
  • maxReceiveCount (1 to 1,000) is how many times a consumer can receive a message before SQS moves it to the DLQ. There is no default; you set it. A very low value moves a message to the DLQ after one temporary error.
  • With Lambda, AWS recommends maxReceiveCount of at least 5. This gives Lambda a few retries (for example, after throttling) before SQS moves the message to the DLQ.
  • The DLQ type must match the source: a FIFO queue uses a FIFO DLQ, and a standard queue uses a standard DLQ. A redrive policy that points to the wrong type fails.
  • The DLQ must be in the same AWS account and Region as the source queue.
  • SQS does not create the DLQ for you. Create it first. A DLQ is an ordinary queue.
  • Standard queues: a moved message keeps its original enqueue timestamp. The time in the source queue counts against the DLQ retention. Example: both queues keep messages for 4 days, and a message waits 3 days in the source. It then expires after only 1 day in the DLQ. Set the DLQ retention longer than the source retention.
  • FIFO queues: the enqueue timestamp resets when the message moves to the DLQ.
  • A DLQ can break the exact order of a FIFO queue. SQS moves the failed message out, and consumers then process the later messages of its group. Do not use a DLQ if the order of every message is critical.
  • Alarm on the DLQ metric ApproximateNumberOfMessagesVisible. SQS does not notify you when a message arrives in a DLQ. Do not use NumberOfMessagesSent, because it does not count messages that SQS moves to a DLQ.

Use byQueue when a DLQ belongs to one team, so that other source queues cannot send their failed messages into it. Use denyAll for a queue that must never be a DLQ.

DLQ redrive

  • "Redrive" means to move messages out of a DLQ so that consumers process them again, usually after you fix a bug.
  • StartMessageMoveTask moves messages from a DLQ to another queue. If you do not give a destination, messages go back to their original source queues.
  • The source must be a DLQ of other SQS queues. A DLQ of a Lambda function or an SNS subscription is not supported.
  • One active move task for each queue. Optional rate: up to 500 messages each second. Set a rate so that the moved messages do not overload the consumers.
  • Use ListMessageMoveTasks to see progress and CancelMessageMoveTask to stop.

Which dead-letter mechanism

Configure the DLQ at the place where the failed step happens. A queue consumer fails after it receives a message, so the DLQ is on the queue. SNS and EventBridge fail when they push to an endpoint, so the DLQ is on the subscription or the target.

Exam signals

  • "Poison message is retried forever" → redrive policy with a DLQ and maxReceiveCount. After that number of receives, SQS moves the message out of the source queue.
  • "Bug is fixed; reprocess the failed messages with the least effort" → DLQ redrive (StartMessageMoveTask). It moves the messages back with no code.
  • "Messages expire in the DLQ sooner than expected" → standard queue keeps the original timestamp. Increase DLQ retention.
  • "Only one team's queue may use this DLQ" → redrive allow policy byQueue.

SQS and SNS access policies and encryption

Resource policies

  • A queue policy controls who can call SQS actions on the queue. A topic policy controls who can call SNS actions, such as sns:Publish, on the topic.
  • For SNS to deliver to a queue, the queue policy must allow principal sns.amazonaws.com to call sqs:SendMessage.
  • Add an aws:SourceArn condition with the topic ARN (or aws:SourceAccount). This prevents the confused deputy problem. Without the condition, the policy trusts the SNS service for any topic, including a topic in another account. The owner of that topic could then use SNS to send messages into your queue. The condition allows only your topic.
  • The same pattern applies to EventBridge: allow events.amazonaws.com with an aws:SourceArn of the rule.
  • Cross-account access to a queue or topic: add the other account as a principal in the resource policy. The other account must also give its users or roles the permission in their IAM policies.
  • Use IAM identity policies for your own users and roles, for example sqs:ReceiveMessage and sqs:DeleteMessage for a consumer.

Encryption at rest

  • SQS: SSE-SQS (keys that SQS manages) or SSE-KMS (an AWS KMS key). Choose SSE-SQS when you only need encryption at rest, with no key to manage. Choose SSE-KMS with a customer managed key when you must control the key policy or see each use of the key in CloudTrail.
  • SSE encrypts the message body. It does not encrypt queue metadata, message metadata, or message attributes. Do not put sensitive data in message attributes.
  • SQS encrypts only messages sent after you turn on SSE. Messages already in the queue stay unencrypted.
  • All requests to an SSE queue must use HTTPS and Signature Version 4 (SigV4). Other requests fail with an InvalidSecurity error.
  • Data key reuse period: 60 seconds to 24 hours, default 5 minutes. SQS gets a data key from KMS and uses it to encrypt messages for this period. A longer period means fewer KMS calls and lower KMS cost.
  • With SSE-KMS, a producer needs kms:GenerateDataKey and a consumer needs kms:Decrypt. SQS calls GenerateDataKey with the producer's permissions when it needs a new data key. SQS calls Decrypt with the consumer's permissions to read the message. Without these permissions, the SQS call fails with a KMS access denied error (KmsAccessDenied). A Lambda function that reads an encrypted queue needs kms:Decrypt.
  • SNS topics also support SSE with AWS KMS keys. Data in transit uses TLS.

SNS to an encrypted queue

  • SNS acts as the producer when it sends to the queue, so SNS must be able to use the queue key.
  • Use a customer managed KMS key on the queue.
  • The key policy must allow sns.amazonaws.com to use kms:GenerateDataKey* and kms:Decrypt.
  • You cannot edit the key policy of the AWS managed key aws/sqs. SNS cannot use that key, so delivery fails.
  • The same rule applies to an encrypted queue that is an SNS subscription DLQ.
  • A queue encrypted with aws/sqs cannot invoke a Lambda function in a different account. You cannot edit the aws/sqs key policy to give the other account access to the key.

Exam signals

  • "SNS subscription is confirmed but the queue gets no messages" → queue policy does not allow sns.amazonaws.com, or the KMS key policy does not allow SNS. A confirmed subscription does not give SNS permission to send to the queue or to use its key.
  • "Only this topic may send to the queue" → aws:SourceArn condition in the queue policy.
  • "Encrypt messages and audit key use in CloudTrail" → SSE-KMS with a customer managed key. KMS logs each use of a customer managed key in CloudTrail. SSE-SQS uses keys that SQS owns, so you cannot set a key policy or see key use in your CloudTrail.
  • "Reduce KMS cost for a busy encrypted queue" → increase the data key reuse period. SQS then calls KMS less often, and KMS charges for each call.

References: Subscribe a queue to a topic, SNS with an encrypted queue, SQS encryption at rest, SendMessage errors (KmsAccessDenied). Lab: Lab 5.2 SNS fan-out.

SNS fan-out, filter policies, and raw delivery

Key facts

  • SNS is push-based publish/subscribe. A publisher sends one message; SNS delivers a copy to each subscription. "Push" means that SNS sends the message to the subscribers at once; they do not poll for it. Sending one message to many receivers is called "fan-out".
  • Standard topic subscription types include SQS, Lambda, HTTP/HTTPS, email, SMS, mobile push, and Amazon Data Firehose.
  • SNS does not store messages for consumers. If a subscriber is down, SNS retries for a limited time and then discards the message. For durable fan-out, subscribe SQS queues to the topic (SNS to SQS fan-out). Each queue keeps its copy (up to 14 days), and each consumer reads its queue at its own speed.
  • SNS invokes a Lambda subscriber asynchronously. The publisher does not get the function result. If the function fails, Lambda retries it by the rules of asynchronous invocation, not SNS.
  • Message size: default maximum 256 KiB. Set the topic attribute MaximumMessageSize to allow up to 1 MiB.
  • For payloads over 1 MiB, use the SNS Extended Client Library (payload in Amazon S3, up to 2 GB).
  • PublishBatch takes up to 10 messages.

Filter policies

  • A filter policy is a JSON document on a subscription, not on the topic. Each subscription can have a different policy.
  • With no filter policy, a subscription receives every message.
  • FilterPolicyScope: MessageAttributes (default) or MessageBody. The body must be valid JSON to filter on it.
  • SNS does not deliver a message that does not match. This saves Lambda invocations and SQS receives.
  • Operators include exact match, prefix, suffix, anything-but, numeric, exists, and cidr.
  • Quota: 200 filter policies for each topic.
  • A new or changed filter policy can take up to 15 minutes to take full effect. During that time, the subscription can still get messages by the old policy.

Raw message delivery

  • By default, SNS wraps the message in a JSON envelope (Type, MessageId, TopicArn, Message, Timestamp, signature fields). The consumer must parse this JSON and read your payload from the Message field.
  • Set RawMessageDelivery to true on an SQS, HTTP/S, or Firehose subscription to deliver only the message body. Use it when the consumer expects your original payload, not the SNS envelope.
  • With raw delivery to SQS, a maximum of 10 message attributes is sent. SNS discards messages with more, so that subscription never gets them.

Exam signals

  • "One order event must go to billing, shipping, and analytics queues" → SNS topic with three SQS subscriptions. SNS puts a copy in each queue, and each team reads its own queue.
  • "Each consumer wants only some messages, with no code change in the publisher" → subscription filter policies. SNS checks the policy of each subscription before delivery.
  • "Filter on a field in the JSON payload" → FilterPolicyScope = MessageBody. The default scope checks only the message attributes.
  • "Consumer code must not parse the SNS envelope" → raw message delivery.

SNS delivery retries, dead-letter queues, and FIFO topics

Delivery retries

Endpoint typeDefault retry policy
AWS managed (SQS, Lambda)100,015 attempts over 23 days
SMTP (email), SMS, mobile push50 attempts over 6 hours
HTTP/SYou can set a custom delivery policy. Total retry time is a maximum of 3,600 seconds.

SNS retries AWS managed endpoints (SQS, Lambda) for about 23 days, and you cannot change that policy. HTTP/S is the only endpoint type whose retries you can tune to fit your server.

  • Only HTTP/S endpoints accept a custom delivery policy, at the topic or subscription level.
  • SNS retries server-side errors: the endpoint is not available, or it says that it cannot process the request now. For HTTP/S, SNS retries 5xx and 429 responses.
  • SNS does not retry client-side errors. These happen when the subscription is out of date, for example a deleted endpoint or a policy that blocks delivery. Retries cannot fix them.
  • When retries end, or after a client-side error, SNS discards the message, unless the subscription has a DLQ.

Subscription dead-letter queue

  • Attach the DLQ to the subscription with a redrive policy (deadLetterTargetArn), not to the topic. SNS delivers to each subscription separately, so each subscription fails separately.
  • The DLQ is an SQS queue in the same account and Region as the subscription.
  • Standard topic subscriptions use a standard queue DLQ. FIFO topic subscriptions use a FIFO queue DLQ.
  • AWS recommends the maximum retention (14 days) for the DLQ. This gives you the most time to fix the endpoint and send the messages again.

FIFO topics

  • Strict order inside each MessageGroupId, and deduplication in a 5-minute interval (MessageDeduplicationId or content-based).
  • A FIFO topic delivers only to SQS queues: FIFO queues and standard queues.
  • A FIFO topic cannot deliver to Lambda, HTTP/S, email, SMS, or mobile push. To reach Lambda, subscribe a queue and use it as the function trigger.
  • Throughput depends on the topic attribute FifoThroughputScope. With MessageGroup, each message group can receive 300 messages each second, so the total grows with the number of groups. With Topic, the whole topic shares one limit: by default 3,000 messages each second or 20 MB each second. Choose MessageGroup when you have many message groups and need more total throughput.
  • FIFO topics support message archiving and replay. Standard topics do not. Use replay to send past messages again to a subscriber, for example after you fix a bug in it.

Exam signals

  • "Keep messages that SNS could not deliver" → DLQ on the subscription. Without it, SNS discards the message when retries end.
  • "HTTP endpoint is overloaded by retries" → custom HTTP/S delivery policy (for example, maxReceivesPerSecond). This setting limits the average number of deliveries each second to that subscription.
  • "Fan out ordered price updates to several services" → SNS FIFO topic to SQS FIFO queues. The topic keeps the order, and each FIFO queue keeps it for its consumer.
  • "FIFO topic must notify a Lambda function" → topic to SQS queue, then queue to Lambda.

EventBridge buses, rules, patterns, and targets

Event buses

BusReceives
Default busAWS service events (one bus for each account and Region), plus PutEvents calls
Custom busEvents that your applications send with PutEvents
Partner busEvents from SaaS partners

Use the default bus to react to AWS service events. Use a custom bus for your own application events, so that they stay apart from AWS events and have their own access policy.

Event structure

Every event has the same top-level fields: version, id, detail-type, source, account, time, region, resources, and detail (your payload).

Key facts

  • A rule matches events with an event pattern and sends them to targets. An event pattern is a JSON document that lists field values. An event matches when every field in the pattern matches. Example: {"source": ["aws.ec2"], "detail": {"state": ["stopped"]}} matches EC2 instances that stop.
  • A rule can have a maximum of 5 targets. This quota cannot be increased. For more targets, add a rule with the same pattern or send to an SNS topic.
  • Pattern operators include exact match, prefix, suffix, anything-but, numeric, exists, cidr, wildcard, and equals-ignore-case.
  • EventBridge patterns can match any field in the event, including nested fields in detail.
  • In September 2026, AWS released a new Custom Event Bus that sends events to subscribers instead of rules and targets. It accepts up to 100 entries in each PutEvents call and keeps events for 1 to 365 days. The exam guide covers the default bus and the rules-and-targets bus, now named Custom Event Bus - Classic. The limits on this sheet are for those buses.
  • Input transformer: use it when a target needs a different JSON shape than the event, and you do not want to write code. InputPathsMap takes values from the event with JSON paths, for example "id": "$.detail.instance-id". InputTemplate builds the new input for the target and uses the names as placeholders, for example {"instance": <id>}.
  • PutEvents: up to 10 entries in one request, total size less than 1 MB.
  • PutEvents can partly fail. The call returns success even when some entries fail. Check FailedEntryCount and send the failed entries again. If you do not check, those events are lost.
  • Targets include Lambda, SQS, SNS, Step Functions, Kinesis, Firehose, ECS tasks, API destinations (HTTP), and other event buses.
  • Schema registry: EventBridge can discover event schemas and generate code bindings. Code bindings are classes for your language, so your code reads typed fields and does not parse raw JSON.

API destinations

  • An API destination is an HTTPS endpoint that a rule (or a pipe) invokes as a target. Use it to send events to SaaS or your own HTTP APIs with no code.
  • A connection holds the authorization method and credentials. EventBridge stores the credentials in AWS Secrets Manager.
  • You set an invocation rate limit for each destination (default 300 each second). Use a lower limit to protect an endpoint that cannot accept many requests.
  • The endpoint must respond within 5 seconds, or EventBridge times out the request and retries it.
  • EventBridge retries 401, 407, 409, 429, and 5xx errors. It does not retry other 4xx errors. Add a DLQ so that you do not lose events.

Target permissions

EventBridge must have permission to call each target. If it does not, the invocation fails and the rule metric FailedInvocations increases. The console adds the permission for you; the AWS CLI does not.

  • Lambda, SNS, and SQS targets: a resource-based policy that allows events.amazonaws.com, or an IAM execution role on the target.
  • Kinesis stream targets: an IAM role (identity-based policy).
  • CloudWatch Logs targets: a resource-based policy only.

Exam signals

  • "React to an AWS service event (for example, an EC2 state change)" → rule on the default bus. AWS services send their events only to the default bus.
  • "Route by a nested field, with ranges or prefixes" → EventBridge pattern. Patterns can match any field in detail and use operators such as numeric and prefix.
  • "Target needs a different JSON shape, no code" → input transformer.
  • "Rule needs 8 targets" → two rules with the same pattern. A rule can have only 5 targets, and you cannot increase this quota.
  • "Send events to a third-party HTTP API with OAuth, no code" → API destination with a connection. The connection holds the OAuth credentials.

EventBridge retries, archive and replay, testing, and cross-account events

Retries and DLQ

  • By default, EventBridge retries delivery to a target for 24 hours and up to 185 times, with exponential backoff and jitter. Exponential backoff means that the wait between attempts grows after each failure. Jitter adds a random part to each wait, so that many retries do not arrive at the same moment.
  • You can set a shorter retry policy (maximum event age and retry attempts) on each target. Use it when an old event has no value, for example a price update that is more than 1 hour old.
  • When retries end, EventBridge drops the event, unless the target has a DLQ (a standard SQS queue).

Archive and replay

  • An archive stores events from one source bus. An event pattern can select which events to archive. Use an archive when you may need to process past events again, for example after you fix a bug in a target.
  • Retention: a number of days, or indefinite (default).
  • A replay sends archived events back to the source bus only. It cannot send them to a different bus or account. You can limit it to specific rules, so that only the fixed rules process the events again and other targets do not get duplicates.
  • Replayed events have a replay-name field, so a consumer can tell a replayed event from a new one. Replayed events do not go into the archive again.
  • A replay does not keep the exact original order. AWS recommends waiting 10 minutes before you replay recent events, because an event can arrive in the archive some time after the bus receives it. A replay that starts too early can miss those events.

Testing event-driven applications

  • TestEventPattern checks whether a sample event matches an event pattern. It returns Result true or false. Use it in unit tests and CI before you deploy a rule.
  • A test listener is a temporary rule that sends matched events to CloudWatch Logs or an SQS queue, so that a test can check that events arrive.
  • Use archive and replay to run real past events through new or fixed rules.
  • Make consumers idempotent and test them with repeated events. SQS standard queues, SNS, EventBridge, and Scheduler can deliver an event more than one time.
  • Use a separate bus or account for tests, so that test events do not reach production targets.

Cross-account events

  • Receiver account: add a resource-based policy to the receiving bus that allows the sender account or organization.
  • Sender account: create a rule whose target is the receiver bus ARN. New cross-account bus targets need an IAM role. EventBridge uses this role in the sender account to put events on the receiver bus.
  • If a bus accepts events from other accounts, add an account field to your rule patterns. Without it, a rule also matches events that other accounts send, and its targets process events that you did not expect.
  • The sender account pays for the events. The receiver account does not.

Exam signals

  • "Do not lose events when the target is down for 2 days" → DLQ on the target (default retry is 24 hours).
  • "Reprocess last week's events after a bug fix" → archive and replay. The replay sends the stored events back through the rules on the bus.
  • "Central account collects events from member accounts" → resource policy on the central bus, rules in member accounts. The policy lets the members send, and the member rules forward the events.
  • "Check in the CI pipeline that a new rule pattern matches sample events" → TestEventPattern. It tests a pattern against an event with no deployed rule.

EventBridge Scheduler and Pipes

EventBridge Scheduler

  • Schedule types: one-time (at(yyyy-mm-ddThh:mm:ss)), rate (rate(5 minutes)), and cron (cron(min hour day-of-month month day-of-week year)). Use one-time for a single future action, rate for a fixed interval, and cron for calendar times such as "every Monday at 09:00".
  • Cron and one-time schedules run in UTC or in an IANA time zone that you set. Scheduler adjusts for daylight saving time.
  • Precision is 60 seconds. A flexible time window spreads invocations over a period. Use it when many schedules run at the same time, so that the target does not get all the calls at once.
  • Delivery is at least once, so the target can get the same invocation two times. Make the target idempotent. You can set retries and a DLQ (a standard SQS queue; FIFO is not supported).
  • Scheduler uses an execution role that trusts scheduler.amazonaws.com and allows the target action (for example, sqs:SendMessage). Scheduler does not use the credentials of the person who created the schedule. Without the role permission, each invocation fails.
  • Templated targets: SQS, SNS, Lambda, and EventBridge. They have preset settings for common actions. Universal targets let a schedule call any of more than 6,000 API operations by service and action name.
  • A completed one-time schedule still counts against your quota. Delete it after it runs, or set ActionAfterCompletion to DELETE so that Scheduler deletes it for you.
  • AWS recommends Scheduler for schedules. Scheduled rules are a legacy feature: default bus only, UTC only.

EventBridge Pipes

  • A pipe connects one source to one target: source, optional filter, optional enrichment, target. The filter drops events that the target does not need. Enrichment calls a service (for example, a Lambda function) to add data to each event before the target gets it.
  • Sources: SQS, Kinesis Data Streams, DynamoDB Streams, Amazon MSK, Amazon MQ, and Apache Kafka.
  • Pipes reduce integration code between services. Without a pipe, you write and run a function that reads the source and calls the target. A pipe uses an IAM role; Pipes do not support resource-based policies. So give the pipe role permission to read the source and to call the target.

Exam signals

  • "Send a reminder one time, 3 days after sign-up, for millions of users" → one-time schedules in EventBridge Scheduler. An SQS delay stops at 15 minutes, and Scheduler supports very large numbers of schedules.
  • "Run a job at 8:00 local time in New York, with daylight saving time" → Scheduler cron with time zone America/New_York. Scheduled rules use UTC only, so they do not follow daylight saving time.
  • "SQS to Step Functions with filtering and no custom code" → EventBridge Pipes. A pipe reads the queue, filters, and starts the target with no function code.

References: Scheduler schedule types, Scheduler execution role, Scheduler automatic deletion, EventBridge Pipes. Lab: Lab 5.3 EventBridge rules.

Kinesis Data Streams: shards, partition keys, and consumers

A Kinesis data stream is a set of shards. A shard is an ordered sequence of records with a fixed write and read capacity. The capacity of the stream is the sum of the capacity of its shards.

Numbers to memorize

ItemValue
Write to one shard1 MB/s or 1,000 records/s
Read from one shard (shared)2 MB/s in total for all shared-throughput consumers; 5 GetRecords calls each second
Enhanced fan-out2 MB/s for each consumer for each shard, pushed over HTTP/2 (SubscribeToShard)
Enhanced fan-out consumersUp to 20 for each stream (provisioned and on-demand standard)
Retention24 hours default; up to 8,760 hours (365 days)
Record data sizeUp to 10 MiB before base64 encoding. Older study material says 1 MB.
PutRecordsUp to 500 records in one request
Capacity mode switchTwo times in 24 hours for each stream

Key facts

  • The partition key decides the shard. Kinesis hashes the key (MD5) to a 128-bit number, and each shard owns a range of those numbers. Records with the same key therefore go to the same shard, in order.
  • Order is kept inside a shard, not across shards.
  • A hot shard is a shard that gets more writes than its limit (1 MB/s or 1,000 records/s) while other shards are almost idle. It comes from a partition key with few distinct values, or one value with much more traffic. Writes to the hot shard fail with ProvisionedThroughputExceededException, even when the stream has spare capacity. Use a key with many distinct values. Example: with device type as the key, 3 types fill at most 3 shards; with device ID, writes spread across all shards.
  • ProvisionedThroughputExceededException: retry with exponential backoff, spread partition keys, or add shards. A throttled record is not written, so the producer must retry it or the record is lost.
  • PutRecords can partly fail. Check FailedRecordCount in the response and send the failed records again.
  • Provisioned mode: you set the shard count. On-demand mode: Kinesis scales shards for you. Choose provisioned mode for steady, predictable traffic. Choose on-demand mode when traffic is unknown or changes quickly.
  • Resharding (provisioned mode): split one shard into two (more capacity, more cost) or merge two shards into one. UpdateShardCount changes the shard count of the whole stream.
  • After resharding, the parent shard is closed for writes. Its records stay readable until retention ends. Read the parent shard before its child shards to keep the order. The parent holds the older records for the same keys.
  • The IteratorAge metric shows how far a consumer is behind the newest record. A rising value means consumers cannot keep up, and data can expire before it is read.
  • To lower Lambda IteratorAge: increase ParallelizationFactor, add shards, or make the function faster. ParallelizationFactor (1 to 10) is the number of batches that Lambda processes at the same time from each shard. Lambda still keeps the order for each partition key.
  • Data stays in the stream until retention ends. Many consumers can read it, and a consumer can read it again (replay).
  • Shared-throughput consumers share 2 MB/s for each shard; latency is about 200 ms with one consumer. Enhanced fan-out latency is about 70 ms. Choose enhanced fan-out when several consumers read the same stream or when you need low latency. In provisioned mode, it adds a charge for each consumer-shard hour and for each GB of data read.
  • Kinesis Client Library (KCL) uses an Amazon DynamoDB table to track shard leases and checkpoints. A lease records which worker reads which shard, so that workers share the shards. A checkpoint records the last processed record, so that a restarted worker continues from that point.
  • Server-side encryption uses AWS KMS keys. Producers and consumers need permission to use the key. Without kms:GenerateDataKey, the producer's PutRecord calls fail. Without kms:Decrypt, the consumer's GetRecords calls fail.
  • In a Lambda event, the record data is base64-encoded. Decode it before you parse the payload.
  • Lambda event source mapping on-failure destinations: SQS and SNS get batch metadata only: the stream ARN, shard ID, and first and last sequence numbers. Use them to read the records from the stream before retention ends. Amazon S3 also gets the records. See the Module 1 sheet for the other stream settings.

Exam signals

  • "Several applications read the same records in order, and replay is needed" → Kinesis Data Streams. Reading does not delete records, so each application reads all records.
  • "Five consumers on one stream are slow and throttled" → enhanced fan-out. Each consumer gets its own 2 MB/s for each shard.
  • "One shard is throttled, the others are idle" → better partition key. The current key sends too many records to one shard.
  • "Keep records for 30 days for reprocessing" → increase retention (up to 365 days).
  • "IteratorAge of the Lambda consumer keeps growing" → increase ParallelizationFactor or add shards. Both let Lambda process more batches at the same time.

Amazon Data Firehose

Comparison

ItemData FirehoseKinesis Data Streams
ConsumersManaged delivery to destinations. You write no consumer code.You write consumers (Lambda, KCL applications)
Storage and replayNo storage, no replayRetention of 24 hours to 365 days; replay is possible
CapacityScales automatically; no shardsShards (provisioned) or on-demand

Choose Firehose when you only need to load data into a store such as Amazon S3, with no code to run. Choose Kinesis Data Streams when your own applications must read the records, or when you need to read the records again.

Key facts

  • Sources: Direct PUT (PutRecord, PutRecordBatch), Kinesis Data Streams, and Amazon MSK. Direct PUT means that producers call the Firehose API themselves.
  • Destinations include Amazon S3, Amazon Redshift, OpenSearch Service, OpenSearch Serverless, Apache Iceberg tables, Splunk, Snowflake, HTTP endpoints, and partner services.
  • Firehose buffers data and delivers when the buffer size or the buffer interval is reached first. Example: with the S3 defaults (5 MiB, 300 seconds), a low-traffic stream delivers one file every 5 minutes.
  • Optional processing before delivery:
    • Lambda transformation: a function changes, masks, or drops records.
    • Format conversion: JSON to Apache Parquet or ORC. An AWS Glue table holds the schema that Firehose uses. These column formats make Amazon Athena queries faster and cheaper.
    • Compression, for example GZIP.
    • Dynamic partitioning: Firehose reads a key from each record (for example, the customer ID) and writes the record under an S3 prefix with that value. A query can then read only one prefix.
  • Source record backup: Firehose can also write source records to an S3 bucket. For some destinations you choose all records or failed records only. Use it to keep the original data when a transformation changes or drops records.
  • Common pattern: producers write to Kinesis Data Streams for replay, and Firehose reads the stream and archives it to S3.

Buffering hints (S3 destination)

HintDefaultRange
Buffer size5 MiB1 to 128 MiB
Buffer interval300 seconds0 to 900 seconds
  • A buffer interval of 0 (zero buffering) delivers within a few seconds. Older study material says the minimum is 60 seconds.
  • Zero buffering is not available with dynamic partitioning or for the S3 backup destination.
  • An interval of less than 60 seconds to S3 uses multipart upload, which adds S3 PUT cost.
  • Small buffers make many small files. Many small files slow down analytics queries and add S3 request cost. Larger buffers make fewer, larger files for analytics, but the data arrives later.

Lambda transformation

  • Firehose invokes the function synchronously with a batch. The function can run for up to 5 minutes.
  • Each returned record needs recordId (same as input), result, and data (base64-encoded). Firehose treats a record ID that does not match the input as a transformation failure.
  • result values: Ok (deliver the record), Dropped (removed on purpose; Firehose counts it as a success and does not deliver it), ProcessingFailed (the function could not transform it; Firehose treats it as an error).
  • Firehose retries a failed invocation 3 times by default. Failed records go to the processing-failed folder in the S3 bucket.

Exam signals

  • "Load clickstream data into S3 with the least operational overhead" → Data Firehose. It is fully managed and needs no consumer code.
  • "Store as Parquet for Amazon Athena" → Firehose format conversion.
  • "Write S3 prefixes by customer ID from the record" → dynamic partitioning.
  • "Remove some records and mask fields before delivery" → Lambda transformation with Dropped and Ok. Dropped removes a record without an error, and Ok delivers the changed record.
  • "Replay data or custom real-time consumers" → Kinesis Data Streams, not Firehose. Firehose does not store records, so nothing can read them again.

AppSync resolvers, subscriptions, and caching

Key facts

  • AWS AppSync is a managed GraphQL API. GraphQL is a query language for APIs. The client names the fields it needs in one request, and the API returns only those fields. One request can get data that a REST client gets with several requests.
  • In GraphQL, a query reads data, a mutation changes data, and a subscription receives changes in real time.
  • Data sources: Amazon DynamoDB, AWS Lambda, OpenSearch Service, HTTP endpoints, Amazon EventBridge, relational databases (Amazon RDS), and None (local). A None data source stores nothing; use it when the resolver can create the result itself, for example to convert data.
  • A resolver connects a field to a data source. Write resolvers in JavaScript (APPSYNC_JS) or VTL (Velocity Template Language, the older template format).
  • A unit resolver uses one data source. A pipeline resolver runs functions in order and can use several data sources for one field. Example: the first function checks a permission in one table, and the second function reads the item.
  • Direct DynamoDB resolvers do simple CRUD (create, read, update, delete) with no Lambda function. There is no function to write, run, or pay for.
  • AppSync calls data sources with an IAM role that trusts appsync.amazonaws.com. The role must allow the actions on the data source, for example dynamodb:GetItem on the table.

Subscriptions

  • Subscriptions push data to clients over WebSockets. A WebSocket is a connection that stays open, so the server can send data to the client at any time.
  • A subscription is triggered by a mutation. Use @aws_subscribe(mutations: ["addPost"]) on the subscription field.
  • A change made directly in the data source (not through an AppSync mutation) does not trigger a subscription. AppSync sees only the mutations that run through the API.
  • Subscription arguments filter which mutation results a client gets. Example: a client that subscribes with roomId: "42" gets only new messages for room 42.

Server-side caching

BehaviorWhat is cached
NoneNothing
Full request cachingAll resolver results. Keys come from context.arguments and context.identity.
Per-resolver cachingOnly resolvers that opt in, with their own TTL and keys
Operation level cachingWhole query responses

A cache returns a stored result without a call to the data source, so it lowers latency and data source load. The TTL (time to live) is how long an entry stays in the cache. Choose per-resolver caching when only some fields are read often or can be stale for a time. Full request caching caches every resolver.

  • Maximum cache TTL: 3,600 seconds (1 hour).
  • New caches are always encrypted at rest and in transit.
  • Flush the whole cache with the console or CLI, or remove one entry with evictFromApiCache in a resolver. Call it in a mutation that changes an item, so that the next query does not return the old cached data.

Exam signals

  • "Mobile app needs data from DynamoDB and a REST service in one request" → AppSync with two data sources (pipeline resolver if one field needs both). One GraphQL request can read fields from several data sources.
  • "Clients must get updates in real time when data changes" → AppSync subscriptions linked to mutations. AppSync pushes each mutation result to the subscribed clients.
  • "Read-heavy GraphQL API, reduce data source load" → AppSync caching. Repeated queries get the cached result, not a data source call.

Key facts

  • An API key can expire up to 365 days after you set it. You can extend it up to 365 days more from that day. After the key expires, requests that use it fail.
  • One API can use a default mode plus additional modes. Use this when different callers need different modes, for example guests with IAM and signed-in users with Cognito user pools.
  • Schema directives set the mode for a type or field: @aws_api_key, @aws_iam, @aws_cognito_user_pools, @aws_oidc, @aws_lambda.
  • A field with no directive uses the default mode.
  • Cognito groups: @aws_auth(cognito_groups: ["Admins"]) when Cognito is the only mode. With additional modes, use @aws_cognito_user_pools(cognito_groups: [...]).
  • IAM mode: allow appsync:GraphQL on the API, or on field ARNs such as .../types/Query/fields/getPost. Use field ARNs to let a role call only some fields.
  • Lambda authorizer: one for each API. It returns isAuthorized and can return deniedFields and ttlOverride. AppSync returns null for each field in deniedFields, even when the request is allowed. ttlOverride sets how long AppSync caches the result, so that the function is not called for every request. The function needs a resource policy that allows appsync.amazonaws.com.
  • Fine-grained data access (for example, only the owner can edit an item): compare ctx.identity with the item in the resolver. ctx.identity holds the caller identity, for example the Cognito user name.

Exam signals

  • "Public read for guests, write only for signed-in users" → API key or IAM (guest) for queries plus Cognito user pools for mutations, with directives. Additional modes let each field use the mode that fits its callers.
  • "Only the Admins group may call deletePost" → Cognito group in a directive. AppSync reads the groups from the user token, so no resolver code is needed.
  • "Backend service in AWS calls the API" → AWS_IAM. The service signs requests with its IAM role credentials, so it needs no stored secret.
  • "Production API uses an API key that will expire" → move to Cognito or IAM; API keys are not user identity. Anyone who has the key can call the API, and the key stops working when it expires.
